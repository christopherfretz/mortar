# spec: AArch64 (`mortar_a64`)

The AArch64 instance of the `Arch` trait (`spec/arch.md`): every
relocation type, what it computes, where it writes, when it overflows,
what it demands, what it becomes in a dynamic output and how it may be
relaxed; the bytes of every table and stub the linker writes; erratum
843419; TLS; and the ELF header facts.

Two implementations are written from this document and must agree:
`mortar_a64` and the verifier `mortar_plumb` (`docs/AGENTS.md` rule 10).
Where the text says "the verifier checks", that is the check `mortar_plumb`
makes from the output and the inputs alone. A statement this document
could not ground in a cited document or an experiment is marked
**[open]** and listed in §15 with a recommended answer.

Documents cited, all public:

- **AAELF64**: "ELF for the Arm 64-bit Architecture (AArch64)", the
  ARM-software `abi-aa` repository, main branch (2025 releases). Section
  names are cited, as the numbering changes between releases.
- **SYSVABI64**: "System V ABI for the Arm 64-bit Architecture", same
  repository: PLT shapes, TLS, GNU properties, BTI.
- **PAUTHABIELF64**: "PAuth ABI Extension to ELF for the Arm 64-bit
  Architecture", same repository (only to name what is refused).
- **TLSDESC**: A. Oliva, "Thread-Local Storage Descriptors for IA32 and
  AMD64/EM64T", and its ARM port, cited by AAELF64.
- **Arm A64 ISA**: the instruction encodings in the Arm Architecture
  Reference Manual for A-profile (instruction classes and fields only).
- **843419**: "Cortex-A53 MPCore Software Developers Errata Notice",
  erratum 843419.

Every instruction word in this document was checked against the GNU
assembler of the reference container (binutils 2.44); the commands are in
`landed/a64/WP-013.md`.

## 1. Scope and status

- ELFCLASS64, little-endian, `EM_AARCH64` (183), LP64 only. ELFCLASS32
  AArch64 (ILP32) objects are refused by the reader (`spec/elf.md`).
  Big-endian objects are refused by the reader.
- Relocation sections are `SHT_RELA`. AAELF64 allows `SHT_REL`; no
  producer of the census writes it; an `SHT_REL` section in an
  `EM_AARCH64` object is refused by name (class `section-type`, name
  `SHT_REL`). §3.3 says how a REL addend would be read, for the day it is
  needed.
- Status of a type: **M1** (static non-PIE executables, `docs/ROADMAP.md`),
  **M2** (dynamic executables, PIE, the TLS and GOT relaxations), **later**
  (specified here, refused by name until a milestone takes it), or
  **refused** (refused by name with no plan). A type that is not M1 or M2
  is refused by name (class `relocation-type`, the AAELF64 name) at scan,
  with the place of the relocation. Every type the census of §2 found is
  M1 or M2.

Summary of §6.1 (static types; the rows are authoritative): 60 are M1,
42 are M2, 16 are later, 22 are refused (the PAuth and Structure
Protection types and a static `TLS_DTPMOD64`), besides the private and
platform ranges. Of the 34 types of the census, 32 are M1 and 2 (the
traditional-dialect TLSGD pair) are M2. Of the dynamic types (§6.2) mortar
writes `IRELATIVE` from M1, the other nine from M2, and never the four
PAuth ones.

## 3. Terms

### 3.1 Values

Terms are those of AAELF64 "Relocation operations", defined here against
the tables of `spec/model.md`. All arithmetic is in 64-bit two's
complement unless a check says otherwise; a check is on the mathematical
value before truncation.

| term | meaning | from |
|---|---|---|
| `S` | the address of the symbol: for a `SymKey` through `def` and `redirect` (§3.3), then `place`, `Split`/`MergeMap`, `sym_place` or `defined` (§4.5). For a symbol whose value is its PLT or IPLT entry (`CANON_PLT` or `IPLT`, arch.md §4.2), that entry's address. `SHN_ABS`: its `st_value`. Undefined weak: §7 | model §4.5 |
| `A` | `r_addend` | input bytes |
| `P` | the address of the place: `addr(place[section]) + r_offset` | model §4.4 |
| `X` | the value the operation computes, before the field takes its bits | — |
| `Page(x)` | `x & !0xFFF` | AAELF64 |
| `GOT` | the address of `_GLOBAL_OFFSET_TABLE_`: the start of `.got` (§10.1) | SYSVABI64 |
| `G(GDAT(S))` | the address of the GOT slot of `S` holding its address | `Slots` |
| `G(GTPREL(S))` | the address of the GOT slot of `S` holding its TP offset | `Slots` |
| `G(GTLSDESC(S))` | the address of the first of the two descriptor words of `S` | `Slots` |
| `G(GTLSIDX(S))` | the address of the first of the two module/offset words of `S` | `Slots` |
| `G(GLDM(S))` | the address of the module/offset pair of this output's module (offset 0), one per output | `Slots` |
| `TPREL(x)` | `x − tls.start + TCB_ALIGNED` (§12.2) | `Placement.tls` |
| `DTPREL(x)` | `x − tls.start` | `Placement.tls` |
| `Delta` | the difference between the load address and the link address (dynamic loader only) | — |

The `G(...)` terms ignore `A`; AAELF64 requires `A = 0` for them
(GDAT, GTPREL, GTLSDESC, GTLSIDX). A non-zero addend on a GOT, TLSGD,
TLSLD, TLSIE or TLSDESC type is diagnosed `relocation-incompatible`
(arch.md §7, reason `the addend must be 0`) at scan; the per-row rule is
the `A` column of §6.1 (`0`: must be zero; `any`). The case is real: GNU
as writes a `:got:` reference to a *local* symbol as the section symbol
plus an offset (`ADR_GOT_PAGE .data+8`, `LD64_GOT_LO12_NC .data+8`;
Clang names the symbol instead). GNU ld fills the slot with the section's
address and drops the `+8`, lld and mold produce a wrong slot as well; the
program loads the wrong object (review experiment; `spec/plumb.md` §10.2
A6). Giving each `(symbol, addend)` its own slot holding `S + A` would be
correct but is outside AAELF64's `GDAT(S)`; refusing names the problem.
`GOTPCREL32` is the one GOT type that adds `A` outside `G` (row 315).

### 3.2 Fields

Each row names one field form. Bits of `X` are inserted into the 32-bit
instruction word (little-endian) at `P`; every other bit of the word is
kept from the input. Data forms write the low bytes of `X`.

**Every instruction form requires its instruction.** The input word at
`P` must match the form's `requires` column (a mask test, and for the
scaled loads and stores the access size); otherwise the relocation is
refused at scan with `relocation-incompatible`, reason `the instruction
does not match the relocation` (arch.md §7, §10). A mismatch is never
encoded. The case is real: GNU as accepts `ldr w0, [x0, #:got_lo12:g]`
and emits `LD64_GOT_LO12_NC` on a 32-bit load; GNU ld inserts `X[11:3]`
into an immediate the CPU scales by 4 and mold also writes a wrong
address (review experiment). A second case is `hi12`. GNU as encodes
`add x0, x0, #:dtprel_hi12:v` with `sh = 0`, and for an offset of 0x5000
GNU ld then writes `add x0, x0, #0x5`, which is wrong code (second review
experiment). mortar refuses it, because `hi12` requires `sh = 1`. The
test is input-only, so it is a scan check like the addend rule; the
verifier repeats it.

| form | inserts | requires (input word `w`) |
|---|---|---|
| `d64`, `d32`, `d16` | `X[63:0]`, `X[31:0]`, `X[15:0]` into the 8, 4, 2 bytes at `P` | nothing (data) |
| `adr` | `X[20:0]`: `X[1:0]` → word `[30:29]`, `X[20:2]` → `[23:5]` | ADR: `w & 0x9F000000 = 0x10000000` |
| `adrp` | `X[32:12]`: `X[13:12]` → `[30:29]`, `X[32:14]` → `[23:5]` | ADRP: `w & 0x9F000000 = 0x90000000` |
| `add12` | `X[11:0]` → `[21:10]` | ADD/ADDS (immediate), 32 or 64 bit, `sh = 0`: `w & 0x5FC00000 = 0x11000000` |
| `hi12` | `X[23:12]` → `[21:10]` | ADD/ADDS (immediate) with `sh = 1`: `w & 0x5FC00000 = 0x11400000` |
| `ls12/n` | `X[11:n]` → `[21:10]`, n = 0..4 | load/store register (unsigned immediate), `w & 0x3B000000 = 0x39000000`, integer, SIMD&FP or PRFM, whose access size is `2^n` bytes: `size = w[31:30]`, `V = w[26]`, `opc = w[23:22]`; the size is 16 bytes when `V = 1, size = 0, opc[1] = 1`, else `2^size` (PRFM counts as 8) |
| `ldx12` | `X[11:3]` → `[21:10]` | `LDR Xt, [Xn, #imm]` (64-bit integer load, unsigned immediate): `w & 0xFFC00000 = 0xF9400000` |
| `ls15` | `X[14:3]` → `[21:10]` | as `ldx12` |
| `lit19` | `X[20:2]` → `[23:5]` | load register (literal), any size or class, including PRFM: `w & 0x3B000000 = 0x18000000` |
| `ldx19` | `X[20:2]` → `[23:5]` | `LDR Xt, label`: `w & 0xFF000000 = 0x58000000` |
| `bc19` | `X[20:2]` → `[23:5]` | B.cond or FEAT_HBC BC.cond (`w & 0xFF000000 = 0x54000000`: bit 4 is 0 for B.cond and 1 for BC.cond; GNU as emits `CONDBR19` on both and the references link both), or CBZ/CBNZ (`w & 0x7E000000 = 0x34000000`) |
| `tb14` | `X[15:2]` → `[18:5]` | TBZ/TBNZ: `w & 0x7E000000 = 0x36000000` |
| `b26` | `X[27:2]` → `[25:0]` | B or BL: `w & 0x7C000000 = 0x14000000` |
| `mov/k` | `X[16k+15:16k]` → `[20:5]`, k = 0..3 | move wide (MOVN, MOVZ, MOVK; opcode kept): `w & 0x1F800000 = 0x12800000`, `hw = w[22:21] = k`, and `sf = 1` when `k ≥ 2` |

The relaxations of §8 replace whole words; the requirement applies to the
input word, and a relaxation whose own instruction check fails is not
taken (§8.3, §8.5).

### 3.3 Checks

| check | holds when |
|---|---|
| `none` | always |
| `s(n)` | `−2^(n−1) ≤ X < 2^(n−1)` |
| `u(n)` | `0 ≤ X < 2^n` |
| `su(n)` | `−2^(n−1) ≤ X < 2^n` (a value that is valid read as signed or as unsigned) |
| `ms(n)` | the signed-MOVW range: `−2^n ≤ X < 2^n` |
| `a(k)` | `X mod k = 0` (alignment; combined with a range check as `s(28)+a(4)`) |

`a(k)` is checked on every scaled field whose dropped low bits would
otherwise be lost silently: a target that is not a multiple of the scale
cannot be encoded, and writing it anyway produces a wrong address. For
the `LDST*_ABS_LO12_NC` group AAELF64 already says the linker should
check; for branches (`b26`, `bc19`, `tb14`) and literal loads (`lit19`,
`ldx19`) the check is mortar's addition (§14, Q3).

If the target were ever REL: the addend of a data form is the field
sign-extended; of an instruction form, the field's immediate extracted
and scaled as written (ADRP: the 21-bit value, unshifted; MOVW: the
16-bit value, unshifted, signed), per AAELF64 "Addends and PC-bias".
Not implemented (§1).

### 3.4 Instruction ranges (mapping symbols)

A word with a relocation is an instruction because its field form says
so (§3.2). A word **without** a relocation is treated as an instruction,
whether decoded or rewritten, only with proof (arch.md §3.6, rule 1).
AArch64's proof is the mapping symbols of AAELF64 "Mapping symbols".
That section also says: "A section that contains instructions must have
a mapping symbol defined at the beginning of the section. If a section
contains only data no mapping symbol is required."

- **Mapping symbols** are the `STT_NOTYPE` local symbols of the section
  named `$x` or `$x.<anything>` (code) and `$d` or `$d.<anything>`
  (data).
- **Ranges.** Sort a section's mapping symbols by `st_value`, then by
  symbol-table index. Each one opens a range that runs to the
  `st_value` of the next mapping symbol with a greater value, or to the
  end of the section. Among symbols with the same value, the last one in
  symbol-table index order sets that range's kind (deterministic; a tie
  between `$x` and `$d` at one address is a producer defect, and the
  rule only fixes the outcome).
- **Instruction words.** A word is an instruction exactly when its four
  bytes lie in one `$x` range. Words before the first mapping symbol,
  and words of a section with no mapping symbols, are not proved
  instructions.
- **Synthetic chunks.** Every word of a synthetic code chunk (PLT, IPLT,
  thunk, erratum patch) is an instruction, because mortar wrote it.
  Padding between chunks is not.
- **Where the rule applies.** It applies wherever this document reads or
  rewrites a word that has no relocation:
  - the `o+12` word of R4 (§8.4);
  - the BTI check of a thunk's target (§9);
  - every word of the 843419 predicate (§11.1).
- **Coverage.** In the system libraries, all 8,864 executable sections
  have a mapping symbol at offset 0 (second review's count).
- **What removes them.** `strip -s` on an object, `ld -r -s` and
  `ld.lld -r --discard-all` remove mapping symbols. Such objects are
  where §11.1's refusal can apply.

## 4. Targets and outputs

The **target kind** of a relocation (arch.md §4.1) is one of `local`,
`abs`, `pre` (preemptible, defined in this output), `shlib` (defined only
in a shared object; `shlib-func` or `shlib-data` by `st_type`),
`ifunc` (a non-preemptible `STT_GNU_IFUNC` defined here), `weak0` (an
undefined weak that is not dynamic: its value is 0) and `weakdyn` (an
undefined weak that is in the dynamic symbol table and preemptible); an
undefined non-weak symbol that nothing defines is `undef` and gives
`undefined-symbol` at scan unless its relocation is consumed (R4's
`CALL26`; arch.md §3.4). The
**output kind** is `static` (ET_EXEC, no `.dynamic`), `exec` (ET_EXEC with
`.dynamic`), `pie` (ET_DYN executable, including static PIE) and
`shared`. Which undefined weak symbols are `weakdyn` is `spec/resolve.md`'s
(§15, Q4).

## 5. Demand classes

A class says, per output kind and target kind, what a relocation demands
(arch.md §4.2 flags) or which error it raises. Every row of §6 names its
class. Abbreviations: `—` nothing; `R` one `R_AARCH64_RELATIVE` at the
place (counted per section; RELR-eligible, §6.3); `D` one symbolic
dynamic relocation of the row's dynamic type at the place (`ABS64` or
TLS), with `EXPORT`; `I` the `IPLT` flag (the symbol's value becomes its
IPLT entry, §10.4); `C` `COPY` for `shlib-data`, `CANON_PLT` for
`shlib-func`; `PLT` the `PLT` flag; `E` the error `relocation-incompatible`
(arch.md §7); `TX` the same error, named as a text relocation, when the
place is in a read-only section (mortar never writes `DT_TEXTREL`).
`static` never sees `pre`, `shlib`, `weakdyn`.

Notes:

- `AW` in `exec` against `shlib` in a read-only section: `C` (copy for data,
  canonical PLT for functions), as GNU ld does; `pie` cannot copy (it can,
  but mortar does not: copy relocations exist for non-PIC code, and a PIE
  is PIC) **[open: Q5]**.
- `PC` with `shlib` in `exec`: `C`, which is what makes non-PIC code
  referencing shared data and functions work (copy relocation, canonical
  PLT). In `pie` the same is `E` (`recompile with -fPIE`, lld's text).
- `GT` slot contents are §10.1's table; the class itself only demands the
  slot.
- `ifunc` everywhere demands `I`: a non-preemptible IFUNC always gets an
  IPLT entry and every address of it is that entry's address, in every
  output kind (§10.4). This keeps function-pointer equality without a
  second rule for PIE.
- `weak0` demands nothing but a `GOT` slot where the class wants one; the
  slot holds 0 and carries no dynamic relocation in any output kind.
- **The table is for places in `SHF_ALLOC` sections.** A place in a
  non-alloc section (`.debug_*`, `.comment`, `.note` without alloc) never
  demands anything and never raises `E` for its output kind: it gets the
  static value with link-time addresses, and no dynamic relocation is
  written for it (it is not loaded). §13.2 gives the rule, the classes
  allowed there, and the tombstone for discarded targets. Without this
  exemption every `-g` PIE (`ABS64`/`ABS32` against local section symbols
  in `.debug_info`) would be refused or get dynamic relocations at
  unloaded places; GNU ld, lld and mold all resolve them statically.

| 1027 | `RELATIVE` | `R`; a `GDAT` slot of `local` (and of `ifunc`'s IPLT entry) in pie/shared | `S + A` (link address; also the `r_addend`, §6.3) | 0 | `S + A` | M2 |
| 1028 | `TLS_DTPMOD64` | a GD slot's first word, and the LD module word, in `shared` | 0 | the symbol, or 0 for a `local` one | 0 | M2 |
| 1029 | `TLS_DTPREL64` | a GD slot's second word for a dynamic target in `shared` | 0 | the symbol | 0 | M2 |
| 1030 | `TLS_TPREL64` | a `GTPREL` slot of a dynamic target; of a `local` one in `shared` | 0 | the symbol, or 0 with `r_addend = DTPREL(S)` | 0 or `DTPREL(S)` | M2 |
| 1031 | `TLSDESC` | the two descriptor words, unrelaxed, in `.rela.dyn` | 0, 0 | the symbol, or 0 with `r_addend = DTPREL(S)` | 0 or `DTPREL(S)` | M2 |
| 1032 | `IRELATIVE` | an IPLT entry's `.got.plt` slot | the resolver's link address | 0 | the resolver's address | M1 (static), M2 |
| 1041-1044 | `AUTH_RELATIVE`, `AUTH_GLOB_DAT`, `AUTH_TLSDESC`, `AUTH_IRELATIVE` | never written | | | | refused |

Every place of a dynamic relocation is 8-byte aligned (AAELF64 "Dynamic
relocations"); layout guarantees it for slots, and an `AW` place that is
not aligned is diagnosed `relocation-misaligned` (arch.md §7).

Static content of a slot carrying a RELA dynamic relocation: mortar
writes the value the loader would write if `Delta = 0` and the target were
the one this link resolved (for `RELATIVE` and `IRELATIVE`, `S + A`; for
the rest 0), as GNU ld writes `RELATIVE` slots. RELA consumers ignore the
place; the value makes the image a function of the layout either way
**[open: Q6]**.

Order (model §4.3 `Slots`; the rule is `spec/synth.md`'s, these are the
ABI's constraints): `IRELATIVE` relocations follow every other dynamic
relocation of the same table (SYSVABI64 "GNU Indirect Functions");
`.rela.plt` holds the `JUMP_SLOT`s in PLT order and, in dynamic outputs,
the `IRELATIVE` of IPLT entries after them; `TLSDESC` is never lazy (no
`DT_TLSDESC_PLT`, §10.6).

### 6.3 RELR

With `-z pack-relative-relocs` (M2), a `RELATIVE` relocation whose place
is 8-byte aligned and whose `r_addend` equals the value written at the
place is emitted into `.relr.dyn` instead (every `RELATIVE` mortar writes
qualifies, by §6.2's static content). `IRELATIVE` never does. The
encoding is the gABI's `SHT_RELR`; `DT_RELR`, `DT_RELRSZ`, `DT_RELRENT`;
and the `GLIBC_ABI_DT_RELR` version need (`spec/synth.md`).

## 7. Undefined weak

For `weak0` (the symbol is undefined, weak, and not dynamic):

| relocation | what is written |
|---|---|
| `AW`, `AN` | `X = 0 + A` (`S = 0`) |
| `PC` data (`PREL64`, `PREL32`, `PREL16`, `PLT32`) | `S = P`: `X = A`. With the usual `A = 0` an unwinder reads the `pcrel` value 0 as null (`.eh_frame` personality and LSDA pointers). GNU ld and lld both write `A` (review experiment: `.word wf+5-.` and `.xword wf+5-.` give 5) |
| `PC` instructions (`ADR*`, `LD_PREL_LO19`, `MOVW_PREL_*`) | `S = P`: `X = A` for ADR and literal loads; `X = Page(P + A) − Page(P)` for ADRP |
| `LO` (`ADD_ABS_LO12_NC`, `LDST*_ABS_LO12_NC`) | `S = 0`: `X = A` |
| `BR`, `BC` (`CALL26`, `JUMP26`, `CONDBR19`, `TSTBR14`) | `X = 4`: a branch to the next instruction |
| `GT` | the slot holds 0, no dynamic relocation |
| TLS classes | accepted, never refused: the symbol is TLS-local (§8) with `TPREL(S + A) = A` and `DTPREL(S + A) = A`, below |

AAELF64 "Call and Jump relocations" makes a `CALL26` to an unresolved
weak a branch to the next instruction; `JUMP26` and `PLT32` are left
unspecified there. GNU ld writes a `NOP` for `CALL26` and `JUMP26` and
sets `S = P` for conditional branches (which then branch to themselves);
lld writes `b .+4` style branches for all four. mortar writes `X = 4` for
all four branch types: the behavior AAELF64 names for `CALL26`, and the
only one that does not turn a conditional branch into a loop. For
mortar's own output the verifier requires exactly this form; for a
reference linker's output it accepts the GNU `nop` too (`spec/plumb.md`
§5.3 W4, W5; §8.7 here). ADRP/ADR/literal loads and the `LO` group
agree in GNU ld and lld (the experiments of `landed/a64/WP-013.md`); the
resulting address of an ADRP+ADD pair against `weak0` is not 0, which is
the producers' problem (GCC and Clang reach undefined weak symbols
through the GOT when they cannot prove definition).

**Thread-local `weak0`.** Value rule: the TP offset and the DTP offset
of a thread-local `weak0` are 0, so `TPREL(S + A) = A` and
`DTPREL(S + A) = A`, with no `PT_TLS` needed; its module is the output's
own. Everything else follows from treating it as TLS-local:

- IE: the `GTPREL` slot holds 0 (no dynamic relocation in an exec
  output); R3 relaxes it to `movz/movk` of `T = 0` unless the symbol has
  `TLSIE_NORELAX`, which keeps IE with that slot (§8.3: the flag is about
  registers, not values, so the two forms compute the same `TP + 0`).
- LE (`TE`) and `TD`: `X = A`, checked as usual.
- TLSDESC in an exec output: R1 with `T = A`. GD with R4's pattern: R4's
  LE form with `T = 0`; without it, a `GTLSIDX` pair `1, 0`.
- In a `shared` output (a hidden undefined weak): as a `local` TLS
  symbol whose `DTPREL` is `A` (§10.1's `shared` column with
  `DTPREL(S) = 0`), which is lld's; M2, untested.

The address the code computes is `TP + A`, not null; a program cannot
test a thread-local weak for presence through its address. glibc does
not: every access to `_nl_current_LC_<cat>` in static `libc.a`
(`uselocale.o`, `setlocale.o`: 24 IE pairs each) is guarded by
`cbz` on the non-TLS weak `_nl_current_LC_<cat>_used`, loaded through
the GOT, which the same `lc-<cat>.o` defines. When it is undefined the
IE result is never used; the link must only not be refused, which is
every static glibc C and C++ link.

Experiment (WP-023, `as` objects, `-static` and non-PIE dynamic): 

| form | GNU ld 2.44 | lld 22 | mold 2.37.1 | mortar |
|---|---|---|---|---|
| IE slot | `0 − tls.start + TCB_ALIGNED` (the formula with `S = 0`) | relaxed to LE, `T = A` (also with `--no-relax`) | the formula with `S = 0` | 0; R3 (M2): LE, `T = 0` |
| IE, non-PIE dynamic | the same, no dynamic relocation | slot 0 + `TLS_TPREL64` against the symbol | the formula with `S = 0` | M2 (exec as static) |
| LE `movz/movk`, `add` | 0 (the addend dropped) | `A` | the formula with `S = 0`; `HI12`/`LO12` refused as out of range | `A` |
| GD (513/514) | kept: `1`, `0 − tls.start` | refused (unknown type) | kept: `1`, the formula | R4 LE `T = 0`, else `1`, 0 |
| TLSDESC | → IE with the IE slot above; crashes (SIGSEGV) on one input | → LE, `T = A` | → LE with the formula | R1, `T = A` |

GNU ld also warns `Weak TLS is implementation defined and may not work
as expected` when a thread-local weak also has a non-TLS relocation (an
`ABS64` in `.debug_info`, which §13.2 resolves statically to `A`). The
references agree on no single value; lld's is the one rule that is a
function of `A` alone, and GNU ld writes it for LE when `A = 0`. The
verifier checks mortar's output against this rule; for a reference
linker's output the slot and LE values above are recorded differences
(§14). Tests: `relax.rs` `s7_thread_local_undefined_weak` (every form,
with and without a template), and the differential (`differential.rs`),
which links static glibc C programs and compares the 204 records
against `_nl_current_LC_*` per linker (none refused; GNU ld's and mold's
slots located by their own value; lld's LE bytes equal to R3's).

`weakdyn` is an ordinary dynamic target (§5): `PC` and `AN` against it are
`E`, as GNU ld and lld refuse them.

## 8. Relaxations

A relaxation rewrites instructions of a sequence into an equivalent,
cheaper form. Each is a rule `fill` evaluates (model §5): a precondition
over `Resolution`, `Demands`, the output kind, the input bytes and
records, and, for R5 only, addresses. Which instructions change and how
is fixed; nothing is recorded per relocation. The verifier evaluates the
same precondition from the same tables and, **for mortar's own output**,
requires the output to hold exactly the taken form: there is no "either
is fine". Checking a reference linker's output is a different mode,
defined by `spec/plumb.md` §5.3 (its rewritings W1-W8); §8.7 lists the
reference forms that mode must accept.

Common terms: **exec output** is `static`, `exec` or `pie`. A symbol is
**TLS-local** when it is `local` in an exec output (defined in this
output, so its TP offset is a link-time constant) or `weak0` (its TP
offset is 0, §7), and **TLS-dynamic**
when it is `shlib` or `weakdyn` in an exec output. In a `shared` output
no TLS relaxation is taken (SYSVABI64 restricts them to executables; GNU
ld's GD→IE in shared objects is not followed). Register numbers: `Rd`,
`Rt`, `Rn` are the fields `[4:0]`, `[4:0]`, `[9:5]` of the input word.

| id | sequence | when | kind (arch.md §5.2) | status |
|---|---|---|---|---|
| R1 | TLSDESC small → LE | exec output, TLS-local | 1 | M1 |
| R1t | TLSDESC tiny → LE | idem | 1 | M2 |
| R1l | TLSDESC large → LE | idem | 1 | M2 |
| R2 | TLSDESC small → IE | exec output, TLS-dynamic | 1 | M2 |
| R2t | TLSDESC tiny → IE | idem | 1 | M2 |
| R3 | IE small → LE | exec output, TLS-local, not `TLSIE_NORELAX` | 2 (reads `Demands`) | M2 |
| R4 | GD (traditional) → LE or IE | exec output, the pattern holds | 1 | M2 |
| R5 | GOT load → address (ADRP+LDR → ADRP+ADD) | below | 2 (reads `Demands`, and an address) | M2 |
| R6 | ADRP+ADD → NOP+ADR | | | later |
| R7 | `GOT_LD_PREL19` → ADR | | | later |

In an exec output every TLS target is TLS-local or TLS-dynamic (a
thread-local `weak0` is TLS-local, §7). A static output has no TLSDESC
runtime, and every TLS target in it is TLS-local, so R1 always applies
there: no descriptor is left in a static output.

### 8.1 R1, R1t, R1l: TLSDESC → LE

Each relocation of the sequence is rewritten on its own; the decision is
a function of the symbol and the output kind only, so all members agree
without looking at each other. `T = TPREL(S + A)`; check `u(32)` on `T`
(`relocation-out-of-range` against the `ADR_PAGE21`, `LD_PREL19` or
`OFF_G1` record).

| relocation | input | output | word |
|---|---|---|---|
| 562 `ADR_PAGE21` | `adrp x0, :tlsdesc:v` | `movz x0, #T[31:16], lsl #16` | `0xD2A00000 \| T[31:16] << 5` |
| 563 `LD64_LO12` | `ldr x1, [x0, :tlsdesc_lo12:v]` | `movk x0, #T[15:0]` | `0xF2800000 \| T[15:0] << 5` |
| 564 `ADD_LO12` | `add x0, x0, :tlsdesc_lo12:v` | `nop` | `0xD503201F` |
| 569 `CALL` | `blr x1` | `nop` | `0xD503201F` |
| 560 `LD_PREL19` (tiny) | `ldr x1, :tlsdesc:v` | `movz x0, #T[31:16], lsl #16` | as 562 |
| 561 `ADR_PREL21` (tiny) | `adr x0, :tlsdesc:v` | `movk x0, #T[15:0]` | as 563 |
| 565 `OFF_G1` (large) | `movz x0, :tlsdesc_off_g1:v` | `movz x0, #T[31:16], lsl #16` | as 562 |
| 566 `OFF_G0_NC` (large) | `movk x0, :tlsdesc_off_g0_nc:v` | `movk x0, #T[15:0]` | as 563 |
| 567 `LDR` (large) | `ldr x1, [x<gp>, x0]` | `nop` | |
| 568 `ADD` (large) | `add x0, x<gp>, x0` | `nop` | |

The descriptor sequences use x0 and x1 by ABI (SYSVABI64 "TLS
descriptors"); the rewritten words are fixed. The verifier checks the
words exactly. Experiment: GNU ld and lld write these words in static
links and PIE; mold relaxes TLSDESC to IE instead in both.

Demand: in an exec output a TLS-local target of class `TS` demands
nothing (the rule depends only on `Resolution`, model §3.7).

### 8.2 R2, R2t: TLSDESC → IE

Target TLS-dynamic in an exec output. The GTPREL slot replaces the
descriptor (demand: `GOT_TPREL`, not `TLSDESC`).

| relocation | output | word |
|---|---|---|
| 562 | `adrp x0, :gottprel:v` (`X = Page(G(GTPREL(S))) − Page(P)`, `adrp`, `s(33)`) | `0x90000000 \| adrp(X)` |
| 563 | `ldr x0, [x0, :gottprel_lo12:v]` (`X = G(GTPREL(S))`, `ldx12`) | `0xF9400000 \| ldx12(X)` |
| 564, 569 | `nop` | `0xD503201F` |
| 560 (tiny) | `ldr x0, :gottprel:v` (`X = G(GTPREL(S)) − P`, `ldx19`) | `0x58000000 \| ldx19(X)` |
| 561, 569 (tiny) | `nop` | |

The large form has no IE relaxation in SYSVABI64; against a TLS-dynamic
target it stays a descriptor (`TLSDESC` dynamic relocation).

### 8.3 R3: IE → LE

The decision is **all or none per symbol**. `T = TPREL(S)`, check
`u(32)` (`relocation-out-of-range` on the record being rewritten).

**The flag.** Scan raises `TLSIE_NORELAX` (arch.md §4.2) on a symbol
when any 542 against it has `Rt ≠ Rn`. The flag is input-only and merged
by OR, like `GOT_NORELAX` (§8.5).

Instruction checks are a separate matter. A 541 whose word is not ADRP,
or a 542 whose word is not `LDR Xt, [Xn, #imm]`, fails its field form's
`requires` (`adrp`, `ldx12`, §3.2). The relocation is then refused at
scan, so it never reaches this rule and does not set the flag.

**The rule.** In an exec output, for a TLS-local target that does not
carry `TLSIE_NORELAX`, every 541 and every 542 against it is rewritten;
otherwise none is.

| relocation | output | word |
|---|---|---|
| 541 `ADR_GOTTPREL_PAGE21` | `movz xd, #T[31:16], lsl #16` (`d` = the ADRP's `Rd`) | `0xD2A00000 \| T[31:16] << 5 \| d` |
| 542 `LD64_GOTTPREL_LO12_NC` | `movk xt, #T[15:0]` (`t` = the LDR's `Rt` = `Rn`) | `0xF2800000 \| T[15:0] << 5 \| t` |
| 543 `LD_GOTTPREL_PREL19` | not relaxed (it reads the slot) | |

**Why `Rt = Rn` on every 542 suffices.** The premise is the IE model of
AAELF64 and SYSVABI64: the base of a 542 against `S` holds the page that
a 541 against `S` computed. Relocations give no other way to name the
page of `S`'s `GTPREL` slot.

1. Under the rule, every 541 against `S` is rewritten. The base `Xn` of
   every 542 therefore holds `T[31:16] << 16`, with every other bit
   zero (MOVZ clears them).
2. The 542 becomes `movk xn, #T[15:0]`, because `Rt = Rn`. It keeps
   bits 16-63 of `Xn` and sets bits 0-15, so `Xt = Xn = T`. That is the
   value the LDR loaded from the slot. `T` fits 32 bits by the check.
3. When some 542 has `Rt ≠ Rn`, a `movk xt` would combine whatever is in
   `Xt` with `T[15:0]`. The review saw GNU ld 2.44 and lld 22 write
   exactly that wrong code (`movz x2` / `movk x3`). The flag makes every
   use of the symbol keep IE, so no 541 is rewritten either. This
   matters because the 541's `Xd` may also feed a 542 elsewhere that
   *does* meet the register condition: rewriting that 541 would hand the
   other 542 a non-page value.
4. A 541 or 542 whose instruction is not the expected one is refused
   (§3.2). So every word the rule rewrites is known to be the ADRP or
   LDR of the IE model.

**541 rewritten and 542 not, or the reverse, cannot happen.** Both are
rewritten exactly when this holds: the output is an exec output, the
target is TLS-local, and the symbol does not carry `TLSIE_NORELAX`.
That condition is a function of the symbol alone, and it is the same
for every 541 and every 542 against it. No per-word condition remains:
the instruction checks refuse the link instead of letting a member
fail.

**Demand.** The rule reads `Demands`, so it is kind 2. Every 541, 542
and 543 against a TLS-local target in an exec output demands
`GOT_TPREL`. When R3 is taken the slot is filled (`TPREL(S)`) and unused,
which costs 8 bytes. Before M2, IE is applied unrelaxed in static links
and the slot holds `TPREL(S)`.

**Incremental.** The flag of one file decides the bytes of another, so it
is in the dependency index (model M-8, arch.md §9).

### 8.4 R4: GD (traditional) → LE / IE

The traditional GD sequence is four instructions:

```text
o+0   adrp x0, :tlsgd:v              513 TLSGD_ADR_PAGE21      (record i)
o+4   add  x0, x0, :tlsgd_lo12:v     514 TLSGD_ADD_LO12_NC     (record i+1)
o+8   bl   __tls_get_addr            283 CALL26 __tls_get_addr (record i+2)
o+12  nop                            no relocation
```

**Pattern.** All of these hold:

- record `i+1` is a 514 at `o+4` against the same `SymKey`;
- record `i+2` is a `CALL26` at `o+8` against `__tls_get_addr`;
- the words at `o` and `o+4` are ADRP (`0x90000000` under
  `0x9F00001F`, so `Rd = 0`) and `ADD x0, x0, #imm`
  (`w & 0xFFC003FF = 0x91000000`);
- the word at `o+8` is BL (`0x94000000` under `0xFC000000`);
- the word at `o+12` is `0xD503201F` and is an instruction (§3.4);
- `o+12` lies inside the section;
- the records at `[o, o+16)` are exactly records `i`, `i+1` and `i+2`.
  The pattern itself reads only those three records: any other record
  whose window (§6.1; a marker's is its word) meets `[o, o+16)` overlaps
  the matched unit and is refused by arch.md §3.4's overlap check
  (feature `overlapping relocations`), never relaxed around nor applied
  unrelaxed. No ordinary input has one: over every corpus object, a
  `-mtls-dialect=trad` build (4 patterns) and every member of `libc.a`,
  `libm.a`, `libstdc++.a`, `libgfortran.a`, `libgcc.a`, `libgcc_eh.a`
  (3424 members, no traditional GD), no record meets a window
  (`differential.rs` `s8_3_r3_from_the_inputs`).

The pattern is a function of the input section's bytes and its
relocation records. Each member evaluates it from the lead record `i`,
which it finds by looking back: the 514 looks one record back, the
`CALL26` two. This is the one AArch64 rule that needs neighbouring
records (arch.md §3.5).

**Words and their owners.** These apply in an exec output with the
pattern holding. Every rewritten word belongs to exactly one member
(arch.md §3.6). The `CALL26` member's window is `[o+8, o+16)`: it owns
the `nop` at `o+12`, which has no relocation of its own. That is 4 bytes
past its field, the largest `after` of any AArch64 window, so
`Facts.max_reach` is `(0, 4)` (arch.md §3.1; `mortar_a64::MAX_REACH`
derives it from the table and `relax::MEMBER_WINDOWS`).
`sequence_extent` is 3 at the 513 (arch.md §3.5), and the pattern is
skipped when `RelocAt.leads` is false (`Facts.seq_leads` = `[513]`).

| word | owner | LE (TLS-local), `T = TPREL(S)`, check `u(32)` | IE (TLS-dynamic) |
|---|---|---|---|
| `o+0` | 513 | `movz x0, #T[31:16], lsl #16` | `adrp x0, Page(G(GTPREL(S)))`: `X = Page(G(GTPREL(S))) − Page(o)`, `adrp`, `s(33)` |
| `o+4` | 514 | `movk x0, #T[15:0]` | `ldr x0, [x0, #lo12(G(GTPREL(S)))]`: `0xF9400000 \| ldx12(G(GTPREL(S)))` |
| `o+8` | `CALL26` | `mrs x1, tpidr_el0` (`0xD53BD041`) | the same |
| `o+12` | `CALL26` | `add x0, x1, x0` (`0x8B000020`) | the same |

**Demand.** R4 is kind 1. The pattern, the output kind and the target
kind are all input-only.

- With the pattern holding in an exec output, a TLS-local target
  demands nothing.
- A TLS-dynamic target demands `GOT_TPREL`, never `TLS_GD`.
- The `CALL26` raises no `PLT` demand.
- In every other case, the members demand `TLS_GD` and the `CALL26`
  demands what its class gives.

**The consumed `CALL26`.**

- It is not a branch site. It is left out of the thunk need-list of
  arch.md §6 and of the undefined-weak rule (§7), and it has no
  redirect.
- A redirect that names it is invalid (§11.3 applies the same rule to
  erratum redirects).
- The verifier recognizes the sequence by the same pattern and checks
  the four words, not a branch.
- The reference to `__tls_get_addr` still counts for archive extraction
  in `spec/resolve.md`, which runs first, so a static link pulls it in
  as GNU ld does.
- Clobbering x1 is allowed, because the call it replaces clobbers it.

Without the pattern, or in `shared`, GD is applied unrelaxed: a GTLSIDX
pair (§10.1) and the call.

Experiments:
- GNU ld writes exactly the LE words in static links and PIE.
- lld 19 refuses 513 and 514 outright.
- mold leaves the sequence unrelaxed, and the program runs (review
  experiment).

### 8.5 R5: GOT load → address

```text
o+0   adrp xd, :got:s              311 ADR_GOT_PAGE      (record i)
o+4   ldr  xd, [xd, :got_lo12:s]   312 LD64_GOT_LO12_NC  (record i+1)
      becomes
o+0   adrp xd, s                   X = Page(S) − Page(P), adrp, s(33)
o+4   add  xd, xd, :lo12:s         0x91000000 | S[11:0] << 10 | d << 5 | d
```

Precondition, all of:

1. **pair**: record `i+1` is 312 at `o+4` against the same `SymKey`, both
   addends 0; word `o` is ADRP with `Rd = d`; word `o+4` is
   `LDR Xt, [Xn, #imm]` (`& 0xFFC00000 = 0xF9400000`) with `Rn = Rt = d`;
2. **symbol**: `local` (defined here, not preemptible), not `ifunc`, not
   `abs` (not `SHN_ABS`), not `weak0`;
3. **every use paired**: the symbol does not carry the `GOT_NORELAX`
   flag. Scan raises it for a symbol when any 311 or 312 against it is
   not part of a pair satisfying 1 (AAELF64 "Relocation optimization":
   the optimization is valid for a symbol only if all its uses are such
   pairs; a hoisted ADRP shared by two loads would otherwise be broken);
4. **reach**: `Page(S) − Page(P)` satisfies `s(33)`. This is the only
   address-dependent condition, so the GOT slot stays demanded (model
   §3.7) and is still filled; the slot is then unused, which costs 8 bytes
   and nothing else.

Both words are rewritten (the ADRP's immediate changes meaning), so both
members evaluate the same predicate from the lead record. The verifier
recognizes the taken form by the opcode at `o+4` (ADD immediate,
`& 0xFF800000 = 0x91000000`, against LDR) and requires it to equal the
rule's verdict. Experiment: mold writes exactly this; lld goes further
(R5 then R6: `nop; adr`); GNU ld does neither.

`GOT_NORELAX` of one file decides the bytes of another (the pair in a
file that has no unpaired use flips when an unpaired use appears
elsewhere), so the flag is in the incremental dependency index (model
M-8, arch.md §9). The pair is evaluated on the input words, so a 312
whose word fails `ldx12`'s requirement is refused (§3.2) before R5 is
considered.

### 8.6 Not relaxed

- R6 (ADRP+ADD → NOP+ADR) and R7: later, for code size only.
- The AAELF64 single-instruction forms (`ADD #0` → `MOV`; IE → `MOVZ`
  of a 16-bit offset with a `NOP`): not taken.
- Any rewrite in a `shared` output.
- 843419's ADRP → ADR is an erratum fix, not a relaxation (§11).

### 8.7 Reference forms (a request to `spec/plumb.md`)

The verifier checks mortar's output against the forms of this document
exactly. `spec/plumb.md` §5.3 separately defines the rewritings (W1-W8)
it accepts when checking a reference linker's output. The review found
these reference forms. They are **not mortar's forms**. They are listed
for plumb.md's reference mode to accept (or to report by name), and
plumb.md decides how:

| form | linker | plumb.md today |
|---|---|---|
| `nop` for a `CALL26`/`JUMP26` to an undefined weak; a branch to itself for `CONDBR19`/`TSTBR14` | GNU ld | W4 covers `nop`; the branch to itself is not covered |
| a 16-byte veneer `adrp x16; add x16; br x16; udf` | GNU ld | W6 (the emulator follows it) |
| a 24-byte long veneer `ldr x16, .+16; adr x17, .; add x16, x16, x17; br x16; .xword off` (seen at 256 MiB) | GNU ld | not followed: the emulator lacks `ADR` into x17 followed by `ADD x16, x16, x17` |
| `AbsLongThunk`: `ldr x16, .+8; br x16; .xword` | lld | W6 |
| GOT load → `nop; adr` | lld | W3 |
| GOT load → `adrp; add`, including against an undefined weak | mold | W2 |
| TLSDESC → IE in a static link | mold | not covered |
| traditional GD left unrelaxed in an executable | mold | ordinary records |
| IE → LE with `Rt ≠ Rn` (`movz x2`/`movk x3`) | GNU ld 2.44, lld 22 | not covered. It is a miscompile, to be reported as an anomaly rather than accepted |
| no 843419 fix at all | mold | A4 |
| the 843419 fix when W3 is a branch (ADR) | GNU ld | W7 |

## 9. Range-extension thunks

AAELF64 "Call and Jump relocations" allows a linker to route `CALL26`,
`JUMP26` (and `PLT32`) through a veneer that may clobber x16, x17 and
the condition flags. mortar inserts thunks for `CALL26` and `JUMP26`
only; `PLT32` is data (a veneer would not be reached), `CONDBR19` and
`TSTBR14` are not covered by the ABI's permission.

- **Need**: a `CALL26`/`JUMP26` site at `P` whose target `T` (the
  symbol, its PLT or IPLT entry, plus `A`) has `T − P` outside `s(28)`.
  A `CALL26` consumed by R4 (§8.4) and a branch to a `weak0` target (§7)
  are not sites.
- **Body** (12 bytes, alignment 4), target `T`:

  ```text
  adrp x16, T            0x90000010 | adrp(Page(T) − Page(Q))
  add  x16, x16, :lo12:T 0x91000210 | T[11:0] << 10
  br   x16               0xD61F0200
  ```

  where `Q` is the thunk's address. Reach of the body: `Page(T) −
  Page(Q)` in `s(33)`; beyond that the link fails with
  `relocation-out-of-range` on the `ADRP` of the thunk (unit 0, the patch
  chunk's `ChunkId`), no long form exists **[open: Q7]**.
- **Key**: `Sym(SymKey, addend)` for a direct target, `Plt(SymKey)` when
  the class routes the branch through the PLT or IPLT (model §4.4
  `patches`). One thunk serves every site in reach with the same key.
- **BTI**: in an output whose `GNU_PROPERTY_AARCH64_FEATURE_1_BTI` is set,
  the word at a direct target must be an instruction (§3.4) and
  BTI-compatible for `br x16` (a target outside a `$x` range is refused
  with the same feature name as a missing pad):
  `bti c` (`0xD503245F`), `bti j` (`0xD503249F`), `bti jc`
  (`0xD50324DF`), `paciasp` (`0xD503233F`) or `pacibsp` (`0xD503237F`).
  `br x16` sets `BTYPE = 01`, which `bti c`, `bti j` and `bti jc` all
  accept, and `paciasp`/`pacibsp` act as `bti c` **[open: Q15]**; a PLT
  entry starts with
  `bti c` in such an output (§10.3). Otherwise SYSVABI64 requires a
  landing pad (`bti c; b T`), which mortar does not yet write: refused by
  name (feature `BTI landing pad`), later. `SHN_ABS` targets need none.
- **Placement** is the layout's (arch.md §6); the thunk shape gives size
  12, alignment 4, and the reach of a branch, `s(28)`.

GNU ld writes 16-byte veneers (`adrp; add; br; udf #0`), named
`__<sym>_veneer`; lld and mold reorder sections first. mortar writes no
padding and names thunks `<sym>$thunk` in `.symtab` (`spec/synth.md`).

## 10. Shapes

All tables are little-endian words. `.got`, `.got.plt` and their entries
are 8-byte aligned; `.plt` is 16-byte aligned.

### 10.1 GOT

`.got` holds the `GDAT`, `GTPREL`, `GTLSIDX`, `GLDM` and `GTLSDESC`
slots in `Slots` order. `_GLOBAL_OFFSET_TABLE_` is its start (SYSVABI64);
mortar defines it when referenced or when `GOT_BASE` is demanded, and a
`GOT` term without a `.got` makes the layout give `.got` a header word.

- `.got[0]`: in an output with `.dynamic`, the link-time address of
  `_DYNAMIC` (SYSVABI64 "may hold"; GNU ld writes it, older glibc reads
  it). In a static output there is no header word **[open: Q8]**.
- Slot contents:

| slot | static, exec (`local`, `abs`, `ifunc`) | pie, shared `local` | `abs` | dynamic target | `weak0` |
|---|---|---|---|---|---|
| `GDAT` (8) | `S` | `S` + `RELATIVE` | `S` | 0 + `GLOB_DAT` | 0 |
| `GTPREL` (8) | `TPREL(S)` | exec: `TPREL(S)`; shared: 0 + `TLS_TPREL64` (sym 0, addend `DTPREL(S)`) | — | 0 + `TLS_TPREL64` | exec: 0; shared: as `local` with `DTPREL(S) = 0` (§7) |
| `GTLSIDX` (16) | static: `1`, `DTPREL(S)` | exec, pie: `1`, `DTPREL(S)`; shared: 0 + `TLS_DTPMOD64` (sym 0), `DTPREL(S)` | — | 0 + `TLS_DTPMOD64`, 0 + `TLS_DTPREL64` | exec: `1`, 0; shared: as `local` with `DTPREL(S) = 0` |
| `GLDM` (16) | `1`, 0 | exec, pie: `1`, 0; shared: 0 + `TLS_DTPMOD64` (sym 0), 0 | — | — | — |
| `GTLSDESC` (16) | (relaxed) | exec: relaxed; shared: 0, 0 + `TLSDESC` | — | `TLSDESC` (sym) | — |

`ifunc` in a `GDAT` slot is the address of its IPLT entry (`S`).
Module id 1 is the executable's (TLS ABI, glibc assigns 1 to the main
program): GNU ld writes 1 into executables' GD slots.

### 10.2 `.got.plt`

In an output with `.dynamic`: three reserved words, then one word per PLT
entry in PLT order (entry `N` uses `.got.plt[N + 3]`, SYSVABI64), then
the IPLT words. `.got.plt[0..2]` are written 0 (the loader fills 1 and
2); each PLT word initially holds the PLT header's address and carries a
`JUMP_SLOT`; each IPLT word holds the resolver's address and carries an
`IRELATIVE`. `DT_PLTGOT` is `.got.plt`'s address. In a static output,
`.got.plt` holds only the IPLT words, no reserved ones (lld; GNU ld keeps
three). GNU ld and lld write 0 into `.got.plt[0]`; mold writes
`_DYNAMIC`.

### 10.3 PLT

`G` below is the `.got.plt` word the entry or header uses; `Q` the
address of the word holding the ADRP.

| shape | when | header (32 bytes) | entry |
|---|---|---|---|
| plain | default | `stp x16, x30, [sp, #-16]!` `0xA9BF7BF0`; `adrp x16, G2` `0x90000010\|adrp`; `ldr x17, [x16, :lo12:G2]` `0xF9400211\|ls12/3`; `add x16, x16, :lo12:G2` `0x91000210\|add12`; `br x17` `0xD61F0220`; `nop` ×3 | 16 bytes: `adrp x16, G`; `ldr x17, [x16, :lo12:G]`; `add x16, x16, :lo12:G`; `br x17` |
| BTI | output BTI bit set (§13.3) | `bti c` `0xD503245F`; the five header words; `nop` ×2 | 24 bytes: `bti c`; the four entry words; `nop` |
| PAC | `-z pac-plt` | as plain | 24 bytes: the first three entry words; `autia1716` `0xD503219F`; `br x17`; `nop` |
| BTI+PAC | both | as BTI | 24 bytes: `bti c`; the three; `autia1716`; `br x17` |

`G2` is `.got.plt[2]`. Status: plain and BTI M2; PAC and BTI+PAC later
(`-z pac-plt` refused by name, class `option`). The dynamic section gets
`DT_AARCH64_BTI_PLT` (0x70000001) with a BTI PLT, `DT_AARCH64_PAC_PLT`
(0x70000003) with a PAC PLT, and `DT_AARCH64_VARIANT_PCS` (0x70000005)
when a `JUMP_SLOT` refers to a symbol with `STO_AARCH64_VARIANT_PCS`
(0x80) in `st_other` (SYSVABI64, AAELF64).

Experiments: all three reference linkers write the plain header and
entry above (GNU ld and lld pad with `nop`, mold with `brk #0x3e8`). With
BTI inputs GNU ld writes `bti c` in every entry; lld omits it from
entries that are not address-taken; mold writes no BTI PLT and drops the
property. mortar writes `bti c` in every entry: one shape, and correct
for any entry whose address escapes.

### 10.4 IPLT and IRELATIVE

A non-preemptible IFUNC `f` with the `IPLT` demand gets an IPLT entry: the
plain or BTI PLT entry shape (16 or 24 bytes), loading a `.got.plt` IPLT
word that carries `IRELATIVE` with addend = the resolver's address
(`st_value` of `f`'s definition). Every address of `f` is the IPLT
entry's address (`S` of §3.1): branches, GOT slots, data words, and its
`.dynsym` and `.symtab` value, typed `STT_FUNC` there (lld does the same in
static links). IPLT entries follow the PLT entries in `.plt`, in `Slots`
order; a static output's `.plt` has IPLT entries and no header.

In a static output the IRELATIVE relocations go into `.rela.plt` and the
linker defines `__rela_iplt_start` and `__rela_iplt_end` (hidden,
`STB_LOCAL` in `.symtab`) at its start and end; glibc's static start code
applies them. In an output with `.dynamic` (including static PIE) the two
symbols are not defined (SYSVABI64), stay undefined weak, and resolve to
0. Experiments: GNU ld uses `.rela.plt` and `.plt`; lld `.rela.dyn` and
`.iplt`; mold `.rela.dyn` and `.plt.got`; all define the two symbols in
static links. The section names do not matter to glibc **[open: Q9]**.

### 10.5 Copy relocations and canonical PLTs

`C` for `shlib-data`: `sym_place` allocates `st_size` bytes in `.bss` (or
`.data.rel.ro` when the shared object's symbol is in a read-only
segment, `spec/synth.md`) with the shared symbol's alignment, and a
`COPY` relocation. For `shlib-func`: the symbol's PLT entry is its address
(`CANON_PLT`), exported with `st_shndx` = the PLT's section and `st_value`
= the entry, so the loader binds other references to it. Only in `exec`.

### 10.6 TLSDESC

No lazy TLSDESC: descriptors are relocated by `TLSDESC` in `.rela.dyn`;
no TLSDESC PLT stub, no `DT_TLSDESC_PLT`/`DT_TLSDESC_GOT`. Experiment:
lld and mold do this; GNU ld writes a lazy stub in `.plt` and both tags.
glibc's loader handles `TLSDESC` in `.rela.dyn` **[open: Q10]**.

## 11. Erratum 843419

With `--fix-cortex-a53-843419` (M1: GCC on Debian passes it to every link
through its specs; Clang only with `-mfix-cortex-a53-843419`). Without the
option nothing in this section applies.

**How the predicate was established.** The Arm errata notice could not be
fetched (the published PDF location returned 404 to both the author and
the reviewer). The predicate below was therefore established **by
black-box experiment**, not from the notice. 552 generated sequences were
linked by GNU ld 2.44 and lld 22 with `--fix-cortex-a53-843419`, and the
sites each linker patched were recorded (`landed/a64/WP-013.md`). The
predicate is chosen to be a superset of the union of both: patching a
non-site costs a few bytes, missing a site is a miscompile on the affected
cores. Every place where the predicate is strictly larger than the union
is listed in §11.4. **[open: Q2]**: confirm against the notice when it
can be obtained; a narrower predicate needs that evidence.

### 11.1 The predicate

The predicate runs over the **output words of each output section with
`SHF_EXECINSTR`**, in address order, across input-section and chunk
boundaries (the processor sees addresses, not sections). The words are
those `fill` writes with every §8 rewrite applied and before any fix of
this section (§11.3 says how the verifier excludes them). Relocations change only
immediates; no relocation field overlaps the bits the predicate reads
(`W1`'s opcode and `Rd`, `W2`'s bits 27 and 25, the final word's opcode
bits and `Rn`). The predicate on the pre-fix output words is therefore
the predicate on the input words, except at relaxed words.

A **site** is `(Q, F)`: a word `W1` at address `Q` and a final word at
address `F`, such that all of the following hold:

| # | condition | test |
|---|---|---|
| 1 | `W1` is ADRP at the end of a 4 KiB page | `Q mod 4096 ∈ {0xFF8, 0xFFC}` and `W1 & 0x9F000000 = 0x90000000`; `n = W1[4:0]` |
| 2 | `W2` (at `Q + 4`) is in the A64 encoding group "Loads and Stores" | `W2 & 0x0A000000 = 0x08000000` (any load, store, pair, exclusive, acquire/release, atomic, SIMD structure or PRFM; no register condition) |
| 3 | `F = Q + 8` (3-word form), or `F = Q + 12` (4-word form, with `W3` at `Q + 8` **any** word) | — |
| 4 | the word at `F` is a load/store register (unsigned immediate) with base `Xn` | `w & 0x3B000000 = 0x39000000` and `w[9:5] = n` (integer, SIMD&FP and PRFM, every size; writing `Xn` as `Rt` included) |
| 5 | `W1`, `W2`, `W3` (4-word form) and the word at `F` are instructions | each of the three or four words lies in a `$x` range of its input section, or in a synthetic code chunk (§3.4) |

A **candidate** is a `(Q, F)` that satisfies conditions 1-4, whatever its
words are. Condition 5 then decides:

- **In a `$x` range:** all words in `$x` ranges or synthetic code make
  a site.
- **In a `$d` range:** if any word lies in a `$d` range, or in padding,
  the candidate is not a site. Data is never patched, and neither
  reference linker patches it.
- **No proof either way:** if any word lies in an executable input
  section with content and no mapping symbol at offset 0, outside every
  mapping range, the candidate can be neither proved code nor safely
  skipped. The link is refused by name:
  - diagnostic `refused`, class `feature`, name `erratum 843419 scan
    without mapping symbols`;
  - the place is the candidate's input section and the offset of `W1`;
  - the key is `(90, 0, ChunkId of that section)`, because candidates
    depend on the layout's addresses (model §8);
  - the message names `--no-fix-cortex-a53-843419` as the user's way
    out. With that option this section does not apply.

The second review reproduced the data case. The words `.word 0x90000000;
.word 0xf9000062; .word 0xf9400401` at page offset 0xFF8 of an executable
section are not patched by GNU ld 2.44 or lld 22, with or without mapping
symbols, because both scan only `$x` ranges.

An ADR fix or a redirect never touches a word outside a `$x` range.

Both forms are tested at every `W1`, and each match is a site. Sites are
keyed by the final word: `(SectionId, offset of F in that input
section)`. The tables are total. Each condition is a mask test that
decides every 32-bit word, so there is no "unknown instruction" case.
Where the experiment was silent, the condition is the wider one:
condition 2 has no register test, and condition 3 does not constrain `W3`.

**Sites and synthetic chunks.** The scan covers mortar's own code chunks
as instructions. By construction, no site has a word in a synthetic chunk.

1. **No `W1` inside a chunk.** The only ADRP in a synthetic chunk is in a
   PLT or IPLT entry or in a thunk. Each is followed by `ldr x17,
   [x16, …]`, whose base is `x16` (the PLT and IPLT entries), or by
   `add x16, …`, which is not a load or store (the thunk). The PLT
   entry's `ldr x17, [x16, …]` as `W2` is followed by `add x16` and
   `br`, neither of which is an unsigned-immediate load/store, so neither
   can be `F`. A PLT header is `stp; adrp x16; ldr x17, [x16]; add x16;
   br x17`; the same argument applies.
2. **No site from an input `W1` running into a chunk.** That would need
   the chunk to start at `Q + 4`, `Q + 8` or `Q + 12` for some
   `Q mod 4096 ∈ {0xFF8, 0xFFC}`. Layout never starts a synthetic code
   chunk at an address whose page offset is `0xFFC`, `0x000`, `0x004`
   or `0x008`. It pads before the chunk to the next allowed start
   (`spec/layout.md` L-118), at most 16 bytes for a chunk alignment of
   at most 16 (islands 4, PLT 16; L-112 counts this margin in the reach
   arithmetic). The padding is not instructions, so it breaks every
   candidate through it (condition 5). Placement rule for
   `spec/layout.md`.
3. **No site from a chunk running into input.** By 1, a synthetic chunk
   holds no `W1` that could start one.

A test enforces 1-3 over every shape at every page offset (§16). So no
valid input reaches a site with a word in a synthetic chunk, and a site
whose final word is not in an input section is an internal error of
layout (arch.md §3.7), never a user diagnostic.

### 11.2 The fix

Each site gets exactly one of two fixes, chosen deterministically.

1. **Patch**, when `Placement.patches` has an erratum redirect with the
   site's key.
   - The word at `F` becomes `b patch`: `0x14000000 | b26(patch − F)`.
     Both branches (`b patch` and `b F + 4`) must satisfy `s(28)`:
     `patch − F ∈ [−2^27, 2^27 − 4]` and
     `(F + 4) − (patch + 4) ∈ [−2^27, 2^27 − 4]`, so the patch lies in
     the asymmetric window `[F − 2^27 + 4, F + 2^27 − 4]`
     (`patch_reach`, arch.md §3.7). If a
     later round moves the patch out of that range, it is a need of the
     fixed point (arch.md §6 step 1). The site is redirected to a new
     patch within range, and the old one stays, unused. This is never a
     `relocation-out-of-range` failure unless no island within range can
     be placed (arch.md §7, as for thunks).
   - The patch (8 bytes, alignment 4) holds `W4'`, then `b F + 4`
     (`0x14000000 | b26(F + 4 − (patch + 4))`).
   - `W4'` is the word `fill` computes for `F`. By condition 4 it is a
     load or store with an unsigned immediate. Its address is
     `Xn + imm`, and every relocation allowed on such a word has a value
     that does not involve `P`: the `ls12/n`, `ldx12` and `ls15` forms of
     §6.1 (278, 284-286, 299, 310, 312, 313, 531-538, 542, 552-559, 563,
     570-573). So the same
     word is correct at the patch.
   - `W1` stays an ADRP with its ordinary value.
   - lld writes this shape (`__CortexA53843419_<addr>`).
2. **ADR**, otherwise.
   - `W1` becomes `adr xn, Page(V)`:
     `0x10000000 | adr(Page(V) − Q) | n`.
   - `Page(V)` is the page that `W1` computes as `fill` writes it:
     `Page(Q) + (immhi:immlo << 12)` of the pre-fix word.
   - For a `W1` that carries a relocation, `V` is the operand of `Page`
     in the formula the word is written with:

     | `W1`'s record | `V` |
     |---|---|
     | 275, 276 | `S + A` |
     | 311 | `G(GDAT(S))` |
     | 311 after R5 | `S` |
     | 513 | `G(GTLSIDX(S))` |
     | 513 after R4 (IE) | `G(GTPREL(S))` |
     | 518 | `G(GLDM(S))` |
     | 541 | `G(GTPREL(S))` |
     | 562 | `G(GTLSDESC(S))` |
     | 562 after R2 | `G(GTPREL(S))` |

     A relaxation that turns `W1` into a MOVZ removes the site.
   - `Page(V) − Q` must satisfy `s(21)`.
   - GNU ld writes this form.

**Who decides.** Layout adds the redirect, inside the fixed point of
arch.md §6, exactly when a site would otherwise need the ADR form and
`Page(V) − Q` is outside `s(21)`. Patches are only added, so a site that
got a patch keeps it even if ADR would later reach. `fill` follows the
table: redirect present means a patch, absent means ADR.

**Stale redirects.** A later round can move code so that a redirected
word is no longer a site. When the fixed point ends, layout drops every
erratum redirect whose key is not a site at the final addresses. The
patch chunk stays where it is, so no address moves and no site appears
or disappears. Model M-4 allows the chunk to be unused, and `fill` writes
it as if it were used: a function of its key and the addresses. The
final `Placement` therefore has the following invariant: every erratum
redirect names a site, and every site without a redirect is in ADR
range.

A thunk redirect never meets an erratum fix on the same word. `W1` and
the final word are not branches. A branch at `W3` (4-word form) may be
redirected to a thunk independently, because the predicate does not read
`W3`.

### 11.3 What the verifier checks

The verifier checks mortar's output, using the map's patches and
redirects.

1. **Undo the fixes.** At each erratum redirect's `F`, read the patch's
   first word instead of the `b`. At every `$x` word at `Q ≡ 0xFF8/0xFFC`
   whose **input word** is an ADRP and whose output word is an ADR of the
   same register, take the ADRP that `fill` would write: the record's
   value for a relocated ADRP (the §11.2 list), computed independently,
   or the input word itself for an ADRP without a relocation. The
   comparison is against the input word, so an ADR written over an ADRP
   that has no relocation is checked too. This gives the pre-fix words.
2. **Find the sites** with §11.1 on the pre-fix words.
3. **For each site:**
   - **with a redirect:**
     - `W1` is the ADRP with its ordinary value;
     - the word at `F` is exactly `b patch`;
     - the patch holds `W4'` (recomputed) and then exactly `b F + 4`.
   - **without a redirect:** `W1` is exactly `adr xn, Page(V)` with
     `Page(V) − Q` in `s(21)`.
   - Any other form is a finding.
4. **Every erratum redirect names a site.** A redirect whose key is not
   a site (stale, from layout or from incremental state) is a finding.
5. **No ADR fix outside a site.** An ADR fix at a `W1` that is not a
   site, or both fixes on one site, is a finding.
6. **Unused patches** are allowed. Their words are checked as code (no
   site may be formed by them).
7. **Data and unproved words.** No fix touches a word outside a `$x`
   range. A candidate in a section without a mapping symbol at offset 0
   in an output mortar wrote is a finding: mortar must have refused.
8. **Synthetic chunk starts.** No synthetic code chunk starts at a page
   offset in `{0xFFC, 0x000, 0x004, 0x008}`.

Reference linkers' fixes are checked by `spec/plumb.md` W7/W8 (§8.7).

### 11.4 The experiment and the superset

Both GNU ld 2.44 and lld 22 patch:

- every load or store `W2` tried, in both forms and at both offsets:
  single-register integer and SIMD&FP loads and stores of every size;
  unscaled, pre- and post-index, register-offset and literal forms;
  `LDTR`/`STTR`; `STP`/`STNP` (including pre-index and Q pairs); `ST1`
  (one and two registers, post-index, lane); `LDXR`/`STXR`; `LDAR`/`STLR`;
  `LDAXR`; `PRFM`; `CAS`;
- a `W3` of `nop`, `hint`, `bti c`, `bti j`, `mrs`, `msr`, `isb`, `dmb`,
  `svc`, `brk`, `paciasp`, `fmov`, `add`, an ADRP of another register,
  a load, and an instruction writing `Xn`;
- a final word of `ldr`/`str` of X, W, B, H, SW, Q, D, and `prfm`, all
  with base `Xn`, and `ldr x0, [x0, …]`.

Neither patches:

- an ADRP at `0xFF4`;
- a `W2` that is not a load or store (`add`, `nop`, `mov`, `b`);
- a final word that is unscaled, post-index, register-offset, a pair,
  `ST1`, on another base, or an `add`;
- a final word at `Q + 16`.

The two linkers differ here (each one alone patches these):

| GNU ld only | lld only |
|---|---|
| a `W2` that writes `Xn` (`ldr x0, …`, `ldr w0, …`, `ldr q0, …`, `ldr x1, [x0], #8`); `LD1`, `LD1R`, `ST2` as `W2`; any branch as `W3` (`b`, `bl`, `b.eq`, `cbz`, `tbz`, `br`, `blr`, `ret`) | `LDAPR`, `LDADD`, `SWP` as `W2` |

The results at `0xFF8` and `0xFFC` are identical.

Where the predicate is a **strict superset** of the union:

- `LDP`, `LDNP`, `LDP` of Q registers, `LDP` writing `Xn`, and `STLUR`
  as `W2`. Neither linker patches these; the predicate does, because
  they are loads and stores, and condition 2 has no exception the
  experiment could justify.
- As `W2`, reported by the second review as patched by neither
  linker: `LDAPUR`, `LDRAA`/`LDRAB`, the MOPS `CPY*`/`SET*` forms, `LDP`
  with writeback, `LDPSW`, and the unallocated encodings of the
  load/store group.
- As `W2`, untested: the MTE tag forms (`LDG`, `STG` and others).

Not a superset place: lld does patch `LD64B` (second review).

There is no place where the predicate is narrower than the union.

### 11.5 835769

Erratum 835769 (a 64-bit multiply-accumulate after a load) is fixed by
GCC's `-mfix-cortex-a53-835769` in the compiler; GCC passes the linker
option only when that flag is given. `--fix-cortex-a53-835769` is refused
by name (class `option`), later.

Experiments: the §11.4 matrix; mold accepted the option and changed
nothing (`spec/plumb.md` A4).

## 12. TLS

### 12.1 Variant and TCB

AArch64 uses TLS variant I (SYSVABI64 "Thread Local Storage"): the
thread pointer (`tpidr_el0`) points to the TCB, 16 bytes, and the TLS
block of the executable follows the TCB, aligned to `p_align` of
`PT_TLS`.

### 12.2 TP offsets

`TCB_ALIGNED = align_up(16, tls.align)`. The validity of a layout requires
`tls.start ≡ 0 (mod tls.align)` (requested of model §4.4 rule 3, arch.md
§9); under it SYSVABI64's padding `(p_vaddr − 16) mod p_align` reduces to
`TCB_ALIGNED − 16`, and

```text
TPREL(x) = x − tls.start + TCB_ALIGNED
```

for any address `x` in the TLS template, and `TPREL(weak0 + A) = A`
(§7). Experiment: a variable at offset
0x10 of a template aligned to 16 has TP offset 0x20 in GNU ld, lld and
mold outputs. glibc computes the executable's offset as
`roundup(16, p_align)` and does not honor a `p_vaddr` misaligned to
`p_align`, which is why the congruence is a validity rule and not a
choice.

### 12.3 LE ranges

`TPREL` is non-negative in variant I. The LE relocations' checks (§6.1)
apply to it: `HI12` with `LO12_NC` addresses `u(24)` (16 MiB of TLS),
`MOVW_TPREL_G1` and `G0_NC` `u(32)` via `ms(32)`, `G2` beyond. R1, R3 and
R4 check `u(32)`.

### 12.4 `_TLS_MODULE_BASE_`

The local-dynamic model through TLSDESC uses a descriptor for
`_TLS_MODULE_BASE_` and adds `DTPREL` offsets (SYSVABI64). The linker
defines `_TLS_MODULE_BASE_` (hidden) at `tls.start` when referenced and
the output has TLS. After R1 the sequence computes `TPREL(tls.start) +
DTPREL(x) = TPREL(x)`; no DTPREL field changes.

### 12.5 Static links

In a `static` output: R1 always; IE slots hold `TPREL(S)`, 0 for `weak0`
(R3 from M2 on); GD slots hold `1, DTPREL(S)` (`1, 0` for `weak0`) when
R4's pattern does not hold (glibc's
static `__tls_get_addr` serves module 1); `GLDM` the same with 0.
`DF_STATIC_TLS` is set in a `shared` output that has a `GTPREL` slot or an
LE relocation (the latter is `E` anyway).

## 13. Other sections, the header and segments

### 13.1 `.eh_frame`

Producers' FDE encodings (experiments and `hod/spec/eh.md`): pointer
encoding `0x1b` (`pcrel | sdata4`) with `PREL32` for the initial location
(GCC, Clang, hod); hod's large model uses `0x1c` (`pcrel | sdata8`) with
`PREL64`; personality `0x9b` (`indirect | pcrel | sdata4`), the CIE's
pointer relocated by `PREL32` to a `DW.ref.*` data word that `ABS64`
relocates (GCC; every CIE with a personality in the libraries of all
three targets, `spec/landed/synth/WP-025-spec.md` X-1); `0x9c` is
`indirect | pcrel | sdata8`, with `PREL64`, where a producer uses it
(clang's large code model); both occur, and neither needs a rule of its
own: the pointer is an ordinary relocated field. LSDA `0x1b` or `0x1c`. The FDE's
code range is found from its first relocation (model §3.5), which is one
of `PREL32`, `PREL64` or `ABS64`; another type there is refused by name.
`.eh_frame_hdr` is written with `eh_frame_ptr` `0x1b`, `fde_count`
`0x03` (`udata4`) and table `0x3b` (`datarel | sdata4`), arch.md §3.9.

### 13.2 Non-alloc sections and tombstones

**Places in non-alloc sections.** A relocation whose place is in a
section without `SHF_ALLOC`:

- is applied statically, with link-time addresses (`Delta = 0`), in every
  output kind;
- never demands anything (no `R`, `D`, `C`, `PLT`, `GOT`, `EXPORT`);
- never raises §5's `E` for its output kind;
- never produces a dynamic relocation;
- against a `weak0` target follows §7; against a `pre`, `shlib` or
  `weakdyn` target it uses the link-time value of `S` (0 for a symbol
  not defined in this output), as GNU ld, lld and mold do for debug
  information;
- is restricted to data types:
  - `NONE` (0, and the withdrawn 256), which write nothing;
  - `ABS64`, `ABS32`, `ABS16` (`AW`, `AN` with a `d*` field);
  - `PREL64`, `PREL32`, `PREL16` (`PC` with a `d*` field);
  - `TLS_DTPREL64` (`TD`).

  The types that occur are `ABS64`, `ABS32`, `PREL32` and
  `TLS_DTPREL64`. Any other type in a non-alloc section is refused with
  `relocation-incompatible`, reason `not allowed in a non-allocated
  section`. That covers an instruction form of an allowed class (MOVW,
  `ADR*`), and any GOT, PLT, branch, TLS-model or `LO` type. This is
  arch.md §4.3's rule, in AArch64 types.

**Discarded targets.** A relocation in a non-`SHF_ALLOC` section with a
debug name (`spec/resolve.md` §6.3) whose target lies in a section
that is not live (garbage-collected, a discarded COMDAT copy, not folded)
writes a tombstone instead of `X`, independent of `A`: 1 in
`.debug_ranges` and `.debug_loc` (where 0 would end the list and all
ones would select a base address), all ones elsewhere, with the
aranges length written 0 (`spec/image.md` I-47, I-112: a 0 is an
address, and lldb attributes low code to the dead copy). The length is
written by the image phase, not by `apply` (arch.md §3.11).
`.gcc_except_table` gets 0; any other section is refused at scan
(`discarded-section-reference`, arch.md §3.4). Experiment (DWARF 4 and 5, `--gc-sections`): GNU ld, lld and
mold write 1 into `.debug_ranges` and 0 into `.debug_aranges`,
`.debug_info`, `.debug_rnglists` and `.debug_addr`; into `.debug_loc`
lld and mold write 1 and GNU ld 0. mortar takes 1 (the value that does not
end the list early). In an `SHF_ALLOC` section such a relocation is an
error (`spec/image.md`), except in `.gcc_except_table`. For dropped
COMDAT copies (`spec/image.md` E9) GNU ld instead redirects to the kept
copy when the sizes are equal.

The tombstone is arch.md §3.11's `tombstone(section name, ELFCLASS64)`,
truncated to the field. It replaces `X` for every type allowed above,
whatever `A` is. `spec/x64.md` (WP-029) takes the same text for x86-64
and the ELFCLASS32 column for i386.

### 13.3 ELF header and segments

| fact | value |
|---|---|
| `e_machine` | `EM_AARCH64` (183) |
| `EI_CLASS`, `EI_DATA` | `ELFCLASS64`, `ELFDATA2LSB` |
| `EI_OSABI` | `ELFOSABI_NONE` (0) **[open: Q11]** |
| `e_flags` | 0 (AAELF64 defines none); inputs' `e_flags` are not checked |
| max page size | 64 KiB (SYSVABI64: "should be 64KiB" so that one binary runs on 4K, 16K and 64K kernels); `-z max-page-size` overrides |
| common page size | 4 KiB; `-z common-page-size` overrides |
| non-PIE image base | `0x400000` **[open: Q12]** |

**GNU property merge** (SYSVABI64 "Program Property"):
`GNU_PROPERTY_AARCH64_FEATURE_1_AND` (0xc0000000), bits BTI (1), PAC (2),
GCS (4). The output's value is the bitwise AND over every live relocatable
input; an input without the property contributes 0; the property is
omitted when the AND is 0. Shared objects do not take part.
`GNU_PROPERTY_AARCH64_FEATURE_PAUTH` (0xc0000001) is `EqualOrAbsent`
(arch.md §3.13: copied when every input that has it agrees, refused when
two disagree). Other `pr_type`s in the AArch64 processor range have no
rule (`property_merge` is `None`) and are dropped with the warning
`unknown-property` (`spec/synth.md` S-95; Q13). `-z force-bti`,
`-z bti-report`, `-z gcs=`, `-z gcs-report` are refused (class `option`),
later. Experiment: inputs with BTI and PAC, start files with BTI, PAC and
GCS: GNU ld and lld write BTI and PAC; mold writes no property.

**MTE**: no linker action. Memory tagging of globals (Android's
`--android-memtag-*` options and the `.note.android.memtag` note) is
refused by option name.

`SHF_AARCH64_PURECODE` (0x20000000, execute-only) is refused by name
(class `section-flag`), later. `STO_AARCH64_VARIANT_PCS` is kept in the
output symbol tables; thunks and PLT entries clobber only x16, x17 and the
flags, which the variant PCS permits.
