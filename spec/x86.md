# spec: i386 (`mortar_x86`)

**Status: draft (WP-030 stage 1; awaiting review).**

The i386 instance of the `Arch` trait (`spec/arch.md`). It covers every
`R_386_*` relocation type: what it computes, where its implicit addend
lives, where it writes, when it overflows, what it demands and how it may
be relaxed. It also gives the bytes of every table and stub the linker
writes, the GOT base and the PIC idioms, IFUNC, TLS, GNU properties and
CET, and the ELF header facts.

It replaces the provisional fit check of arch.md Appendix B. It cites
that appendix and corrects it where measurement disagreed (§17).
`spec/x64.md` is its template. Where a rule here is the same as an x64.md
rule, it says so and gives only what differs.

Two implementations are written from this document and must agree:
`mortar_x86` and the verifier `mortar_plumb` (`docs/AGENTS.md` rule 10).

Rule numbering and tags:
- Rules are numbered `X86-1`, `X86-2`, … and tagged **[M1]** or **[M2]**.
  - **[M1]**: static executables, non-PIE and static-pie.
  - **[M2]**: dynamic executables, PIE with a dynamic loader, shared
    objects.
- Every rule has a test idea in §19.
- Experiments are `E1`–`E16` (Appendix A). Each is a script in the review
  harness, which `run-all.sh` reproduces.
- A statement this document could not ground in a cited document or an
  experiment is marked **[open]** and listed in §18 with a recommended
  answer.
- Estimates are marked "(estimate)".

Documents cited, all public:

- **psABI**: "System V Application Binary Interface, Intel386
  Architecture Processor Supplement", version 1.1 and its 2015–2024
  updates (the `i386-ABI` repository: `GOT32X`, `TLS_GOTDESC`,
  `IRELATIVE`, the x86 GNU properties). It defines the relocation types
  and their calculations, the GOT/PLT and the GOT base.
- **TLS**: U. Drepper, "ELF Handling For Thread-Local Storage". It
  defines variant II, the IA-32 sequences and their linker rewrites,
  including the `@indntpoff`/`@gotntpoff` forms.
- **TLSDESC**: A. Oliva, "Thread-Local Storage Descriptors for IA32 and
  AMD64/EM64T".
- **binutils**: `bfd/elf32-i386.c`, `bfd/elfxx-x86.c` and
  `include/elf/i386.h` of binutils 2.44, cited for GNU ld's behavior where
  an experiment showed it.
- **SDM**: the Intel 64 and IA-32 Architectures Software Developer's
  Manual, volume 2. Cited for instruction encodings only.

## 1. Scope and status

In scope: `EM_386`, `ELFCLASS32`, `ELFDATA2LSB`, relocation sections
`SHT_REL`. The inputs are GCC 14 (`i686-linux-gnu-gcc`, the Debian
cross compiler) and Clang 19 and 22 (`--target=i686-linux-gnu`) objects.
They link against the Debian i386 glibc 2.41 static archives, libstdc++,
libgcc and the GCC runtime libraries.

kiln and hod do not target i386 (operator ruling, 2026-11-14). Every
i386 object comes from GCC or Clang.

- **M1, this document's scope**: `static` (non-PIE) and `static-pie`
  outputs. That means every type of §6.1 marked M1, the relaxations of §8
  and §9, IFUNC through the IPLT (§11.3), TLS in a static image (§13),
  and CET properties (§12).
- **M2, sketched only**: the PLT and `.rel.plt` (§11.4), `GLOB_DAT`,
  `JUMP_SLOT`, `COPY`, the TLS dynamic types, and shared objects.
- **later**: `-r` (relocatable output, needs `write_addend`, arch.md
  §3.3). Also the obsolete `TLS_IE_32`/`TLS_LE_32` pair (X86-14) and the
  Sun TLS types (§6.3).

The x86 family shares a crate: `mortar_x86` holds i386; `mortar_x64`
holds x86-64. The byte-level helpers for the ModRM reading of §3.4, the
`endbr` constants and the GNU property merge (x64.md X-41) are shared code
(request R-12). The relocation tables are not shared.

- **X86-1 [M1] What mortar accepts.** An `EM_386` `ET_REL` input with
  class `ELFCLASS32` and data `ELFDATA2LSB`, and `e_flags` 0. Any other
  `e_flags` value is refused by name (`input-flags`): the psABI defines
  none, and every object of both censuses has 0 (§2.4). An `EM_386`
  input with class `ELFCLASS64`, or an `EM_X86_64` input in an i386
  link, is refused (`spec/input.md`'s machine check).
- **X86-2 [M1] Relocation sections are `SHT_REL`.** An `SHT_RELA`
  section applying to an `EM_386` input section is refused by name
  (`relocation-section-kind`, request R-5). The psABI uses `Elf32_Rel`
  only. No producer of either census writes one. The three reference
  linkers disagree on such an input:
  - GNU ld ignores `r_addend` and reads the implicit bytes;
  - lld honors `r_addend`;
  - mold leaves the field untouched, which is wrong code (§15.2 W12;
    E9 `typeprobe.py`, case `rela`).

sets of objects:

- **the system set**: every member of the i386 sysroot and GCC runtime

- **X86-3 [M1] Addends are free, except where §8 and §9 say.** Every
  row's `A` column is "any". A relaxation requires the addend the census
  shows (`GOT32X` `A = 0`; the TLS sequence leads `A = 0`). With any other
  addend the record is applied unrelaxed, or refused where §8 or §9 say.
  The `GOTPC` addend is the byte distance from the start of the
  `get_pc_thunk`'s return address to the field (2 for `addl $imm32,
  %ebx`, `81 c3`; 1 for the `05` short form of `%eax`; Clang's
  `+[.-.L0$pb]` gives 3, 7, …). The linker never interprets it (§10.1).

### 2.3 Instruction forms around GOT and TLS places

`scan32.py` records the two bytes before every `GOT32`, `GOT32X` and TLS
field (`before` in the census JSON):

- **`GOT32X` (17 701 records).**
  - About 96% are `8b` (mov) with ModRM mod = 10 (`8b 83` 5019,
    `8b 80` 1377, …).
  - The rest:
    - `ff 15` (`call *foo@GOT`, no base: GCC `-fno-plt -fno-pic`, 516);
    - `ff 9r` (call with base, 1000+);
    - `3b 9r`/`3b 8r` (cmp);
    - `0b 91` (or);
    - `03 85` (add, libgcc `bid64_div.o`, 88);
    - `8b 0d`… (no-base mov, GCC `-fno-pic -fno-plt`).
  - No SIB form occurs (`rm = 100`). No moffs form (`a1`/`a3` before the
    field) occurs. No pair of readings of §3.4 disagrees for any record.
- **`GOT32` (5 851).** The same opcodes, plus forms that `GOT32X` may not
  carry:
  - `83 bb`/`83 be` (`cmpl $imm8, foo@GOT(%reg)`);
  - `ff b6`/`ff b3` (push);
  - `83 3d` and `ff 35` (no-base cmp and push, GCC `-fno-pic -fno-plt`);
  - `0f 44 83`/`0f 44 8b` (cmov, Clang).

  `GOT32` is never relaxed (X86-26), so these only need §3.4's base
  test.
- **`TLS_GD` (4 490).**
  - `8d 04 1d` (SIB `leal x@tlsgd(,%ebx,1), %eax`, 4182), followed at
    `+5` by a `PLT32` (GCC, Clang, libgcc) or a `PC32` (GCC non-PIC, 254)
    against `___tls_get_addr`.
  - `8d 8r` (base `leal x@tlsgd(%reg), %eax`, 308), always followed at
    `+6` by `GOT32` or `GOT32X` `ff 9r` (`call *___tls_get_addr@GOT(%reg)`,
    `-fno-plt`).
  - No producer emits a base-register GD followed by a direct call.
- **`TLS_LDM` (1 373).** `8d 83` only (`leal x@tlsldm(%ebx), %eax`),
  followed at `+5` by `PLT32`/`PC32`, or at `+6` by
  `GOT32`/`GOT32X` `ff 93`. There is one exception: GCC `-fno-plt`
  writes `8d 87` + `ff 97` (base `%edi`) twice.
- **`TLS_IE` (1 563).**
  - `a1` (`movl x@indntpoff, %eax`). Once it is at offset 1 of its
    section (`.text.addr_tls+1`), so only one byte precedes the field.
  - `8b 0d`/`8b 15`/`8b 3d` (no-base mov);
  - `03 05` (`addl x@indntpoff, %eax`).
- **`TLS_GOTIE` (4 129).** `8b` with mod = 10 (any registers), and
  `03 81`/`03 88`/`03 83` (add).
- **`TLS_GOTDESC` (598).** `8d 83` only. **`TLS_DESC_CALL`**: always
  `ff 10` at `P`.
- **`TLS_LE` (17 297)** and **`TLS_LDO_32`**: immediate or displacement
  of any instruction. They are never rewritten.

### 2.4 Other facts

- **Relocation order.**
  - Records are not sorted by `r_offset` in 615 sections (libc 73,
    libstdc++ 267, GCC objects 229, libgomp and others 46).
  - No two records share an `r_offset`.
  - The GD and LD sequence partner is still the next record by index in
    every case (`follow` in the census, which pairs by index). X86-31
    pairs by offset nonetheless.
- **SHF_MERGE section symbols.** `32` against a section symbol of an
  `SHF_MERGE` section occurs in every set:
  - GCC 53 616 in `.debug_str` references;
  - libstdc++ 1 713 in alloc data.

  `GOTOFF` against a string section's symbol is GCC's `-fPIC` string
  reference (`leal .LC0@GOTOFF(%ebx)`).
- **TLS mismatch.** `32` against an `STT_TLS` symbol at a non-alloc place
  occurs 138 times. It comes from GCC `-gsplit-dwarf`, in `.debug_addr`
  (X86-62).
- **Undefined weak TLS.**
  - glibc's `_nl_current_LC_*` (12 symbols, libc.a);
  - the corpus's `weak_tls` (285 objects).
- **IFUNC definitions.** libc 46, libm 37, and every corpus object built
  from `c1.c`.
- **`.eh_frame`.**
  - Every CIE has augmentation `zR` with FDE encoding `0x1b`
    (`pcrel|sdata4`).
  - Some have `zPLR` with personality `0x9b` (`indirect|pcrel|sdata4`)
    and LSDA `0x1b`.
  - Clang/GCC `-fno-pic` C++ objects have `zPLR` with `P00 L00` (absolute
    `udata4`): an `R_386_32` in `.eh_frame`.
- **Header.**
  - `e_flags` = 0 in every object.
  - `EI_OSABI` is 0, or 3 (`ELFOSABI_GNU`) in objects that define an
    IFUNC: libc 28, libm 10, libstdc++ 27, and every `c1.c` object.
- **GNU properties.** `GNU_PROPERTY_X86_FEATURE_1_AND` = 3 (IBT|SHSTK)
  appears only in objects built with `-fcf-protection` (GCC, Clang 45
  each; gfortran 15). No system archive member has a property note.
- **`.note.GNU-stack`.** Present and non-executable in every object.
- **COMMON alignment.** COMMON symbols have alignment 4, and 32 in
  gfortran (`-fno-common` is the GCC 14 default; the corpus forces
  `-fcommon` for one source).
- **COMDAT.** Groups occur throughout, for example 8 290 in the GCC
  objects and 5 666 in libstdc++.

## 3. Terms, REL addends, fields, checks

### 3.1 Values

Terms are the psABI's ("Relocation Types"), defined against
`spec/model.md`. Arithmetic is on mathematical integers. A check is on
the value before truncation. The field takes `X mod 2^(8·width)`.

| term | meaning |
|---|---|
| `S` | the symbol's address (x64.md §3.1). For a symbol whose value is its IPLT entry (§11.3), that entry's address. Undefined weak: §7 |
| `A` | the implicit addend read from the field (§3.2) |
| `P` | the place, `addr(section) + r_offset` |
| `X` | the computed value |
| `Z` | `st_size` |
| `GOT` | `_GLOBAL_OFFSET_TABLE_`: the start of `.got.plt` (`Facts.got_base = GotPltStart`, §11.2) |
| `G` | the address of the GOT slot holding `S`'s address (`G(GDAT(S))`); `G − GOT` is its offset from the GOT base |
| `G(GTPREL(S))` | the address of the slot holding `S`'s TP offset, `TpRel(S)` |
| `L` | the IPLT (or, M2, PLT) entry of `S` when it has one, else `S` |
| `TpRel(x)` | `x − tls.start − align_up(tls.size, tls.align)`, negative (variant II, §13) |
| `DtpRel(x)` | `x − tls.start` |

### 3.2 REL addends

- **X86-4 [M1] Every implicit addend is the field itself.** For every
  type with a field, `Implicit { bytes: width(field), signed: true,
  shift: 0 }`, and `A` is the field's bytes read little-endian and
  sign-extended. arch.md Appendix B.1 has this right for widths 4, 2 and
  1. Nothing on i386 stores an addend outside the field. No form has a
  shifted or split immediate, and no instruction is decoded to find an
  addend.
- **X86-5 [M1] The addend is read once per use, from the input bytes.**
  The scan and the apply each call `read_addend(h, field)` on the input
  section's bytes, never on the output buffer (arch.md §3.3). The same
  `A` is used:
  - by `classify`, `scan` and the demand;
  - by `apply`, to compute `X`;
  - by the verifier, from the inputs.

  A consequence for the output buffer (arch.md §3.6, image.md I-35): the
  buffer starts as a copy of the input bytes. So the field holds `A`
  until `apply` overwrites it with `X`. A field outside the clip of the
  piece being written (image.md I-35's clip `[a, b)`) is not written by
  that piece and keeps the bytes the adjacent piece writes. A REL field
  is only 1, 2 or 4 bytes. Under I-35 no field straddles a clip
  boundary, because `max_reach` (X86-40) includes every field's width.
  An input whose field would straddle a split-section piece boundary is
  refused by name (`relocation-straddles-piece`, model.md §3.5).
- **X86-6 [M1] `16`, `8`, `PC16`, `PC8` read signed.** `A` is the 2- or
  1-byte field sign-extended. The written field is the same modulo
  2^16 (2^8) whichever way the addend is read. The reading changes only
  which values pass the check, and the signed reading is what `.word sym
  - 1` means.
  - lld reads signed.
  - GNU ld and mold read unsigned.
    - mold therefore refuses a valid `PC16` with `A = −2` ("65582 is not
      in [-32768, 32768)", E9 case `pc16neg`), which is wrong (§15.2
      W13).
    - GNU ld's bitfield check accepts both readings.
- **X86-7 [M1] Write-back.** For a final link, `apply` overwrites the
  field with `X`, and nothing else records `A`.
  - `-r` (later) writes `A + delta` back with `write_addend`, checked
    against the width (arch.md §3.3).
  - `--emit-relocs` (later) emits the relocation and leaves `X` in the
    field, as GNU ld does (arch.md Q3). Its consumer cannot recover `A`.
- **X86-8 [M1] SHF_MERGE section-symbol pieces.** A relocation against
  the section symbol of a split section (model.md §3.5) resolves its
  piece from `A` as read by X86-4. The piece is the one containing input
  offset `A` (`32`, `GOTOFF`: `.long .LC0+2` and `leal .LC1@GOTOFF(%ecx)`
  locate offsets 2 and the start of `.LC1`). For `PC32` the field is
  the place-relative word itself: `.long .LC1+1 - .` has `A = 1` and the
  piece is at offset 1.

  The output value is `S' + (A − piece_start)`, where `S'` is the
  piece's output address. All four references agree, and the program
  sees deduplicated strings (E14 `misc.sh` merge: `[hello][world][orld]`,
  `dedup=1`, both `GOTOFF` loads equal the data words; static and
  static-pie).

  An `A` outside the section (before 0, or at or past its size) is
  refused by name (`merge-addend-out-of-section`, model.md §3.5).
  No census record has one.

### 3.3 Fields

Every i386 field is a little-endian data field at `P`:

| form | bytes at `P` | used by |
|---|---|---|
| `d32` | 4 | 1, 2, 3, 4, 9, 10, 15–19, 32, 38, 39, 43 |
| `d16` | 2 | 20, 21 |
| `d8` | 1 | 22, 23 |
| `none` | 0 (a marker) | 0, 40 |

- **X86-9 [M1] Fields are data.** As x64.md X-5. `apply` writes only the
  field's bytes, except in a matched relaxation, which writes exactly the
  bytes of its window (§8, §9).

### 3.4 Checks and the GOT32 operand

| check | range of `X` | types |
|---|---|---|
| `mod(32)` | none: the field takes `X mod 2^32` | 1, 2, 4, 9, 10, 3, 43 (the GOT forms after their base is chosen), 32 |
| `s(32)` | [−2^31, 2^31 − 1] | 17, and every TP offset written by §9 |
| `u(32)` | [0, 2^32 − 1] | 38 |
| `su(16)` | [−2^15, 2^16 − 1] | 20 |
| `s(16)` | [−2^15, 2^15 − 1] | 21 |
| `su(8)` | [−2^7, 2^8 − 1] | 22 |
| `s(8)` | [−2^7, 2^7 − 1] | 23 |

- **X86-10 [M1] Word-size fields are modular.** On i386 a 32-bit field is
  the machine word, and address arithmetic wraps modulo 2^32 in the
  processor, so `32`, `PC32`, `PLT32`, `GOTOFF`, `GOTPC`, `GOT32`,
  `GOT32X` and `TLS_LDO_32` have no overflow check. This differs from
  x64.md X-6, where `32` is `u(32)` in a 64-bit space. The psABI defines
  no overflow for them. Measured (E9): `.long sym+2` with `sym =
  0xffffffff` (an absolute symbol) writes 1 under GNU ld, lld 22 and
  mold, and a `PC32` that wraps also links under all three.

  `.long sym - k` with `sym < k` must link: GCC emits it for `&a[-k]`.
  Under a `u(32)` check it would be refused. Every reference accepts it.
- **X86-11 [M1] Narrow overflow is an error.** `16`, `8`, `PC16`, `PC8`
  and `TLS_LE` outside their check give `relocation-out-of-range` (§10,
  x64.md X-6), never a truncated write. Measured (E9):
  - lld accepts `16` in [−32768, 65535] and `8` in [−128, 255], and
    refuses beyond.
  - GNU ld accepts and truncates −32769 (writes 0x7fff) and −129 (writes
    0x7f): wrong code (§15.2 W11).
  - mold checks `16`/`8` unsigned.
  - All three refuse `PC8` = 128.
- **X86-12 [M1] `SIZE32` is `u(32)`.** As x64.md X-7.
  - GNU ld and mold write `Z + A` (12 in E9).
  - lld 19 refuses it as "unknown relocation (38)".
  - lld 22 fails with "internal linker error: cannot read addend" (§15.1).
- **X86-13 [M1] The GOT32/GOT32X operand: base or none.** `GOT32` and
  `GOT32X` compute `G + A − GOT` when the instruction's memory operand
  has a base register, and `G + A` (the absolute slot address) when it
  has none (psABI, `GOT32X` note). The field is always the operand's
  `disp32`, and the bytes before it decide which form applies. Let
  `b1 = byte(P − 1)` and `b2 = byte(P − 2)` (bytes before the start of
  the section do not exist).

  `classify` computes every reading of these bytes that is consistent
  with the field being a `disp32` that ends the operand:

  1. **ModRM reading**, with `b1` as the ModRM byte:
     - `(b1 & 0xc7) == 0x05` (mod = 00, rm = 101) is **none**;
     - mod = 10 with rm ≠ 100 is **base**;
     - any other `b1` gives no ModRM reading.
  2. **SIB reading**, with `b1` as a SIB and `b2` as a ModRM with
     rm = 100. It applies when `b2` exists and mod(`b2`) ∈ {00, 10}.
     - mod = 00 with SIB base = 101: the operand is `disp32(,%index,s)`,
       which is **none** (the index is not a base).
     - mod = 10, or SIB base ≠ 101: **base**.
  3. **moffs reading**: `b1` ∈ {`a0`, `a1`, `a2`, `a3`} (the moffs32
     forms of mov), which is **none**.

  If every reading that exists gives the same answer, that answer is
  used. If there is no reading, or two readings disagree, the record is
  refused by name: `got-operand-ambiguous`, which names the file, the
  section, the offset and the two readings. It is an error class of
  `spec/diag.md` (request R-9).

  Why this matters:
  - The three reference linkers each misread a form (§15.2 W1–W3).
    - GNU ld and lld treat `0d` in `mov foo@GOT(%ebp,%ecx,1)` (`8b 84
      0d`) as a no-base ModRM.
    - GNU ld and lld write `G + A − GOT` for the moffs store `a3`, which
      is wrong because the moffs form is absolute.
    - mold writes `G + A − GOT_mold` for every no-base form. Its GOT
      base is `.got`, not `_GLOBAL_OFFSET_TABLE_`, so this is wrong for
      every one of them.

    Each crashes under qemu-i386 (E5 `gotform.sh`, E3 `relaxrun.sh`
    family `sib`).
  - No census record is ambiguous or has no reading (§2.3), so the rule
    refuses nothing real. The verifier recomputes the readings from the
    input bytes.
  - The window for this test is `before = 2` (`[P − 2, P)`), within
    `max_reach` (X86-40).

## 4. Targets and outputs

Target kinds and output kinds are arch.md §4.1's, as x64.md §4.

- **X86-15 [M1] Static-pie is position-independent.** As x64.md X-9. An
  absolute address in an alloc section of a `static-pie` output needs
  `R_386_RELATIVE` (synth.md). Text relocations are refused: an `R_386_32`
  against a non-absolute target in an executable section of a static-pie
  output is an error. GNU ld's message is "relocation R_386_32 against
  `x' can not be used when making a PIE object; recompile with -fPIE"
  (X86-58).

  Measured (E10 `layout.sh`, E8 `ifunc.sh`): the static-pie outputs of
  the three references carry only these dynamic relocations:
  - `RELATIVE` and `IRELATIVE`, in `.rel.dyn`;
  - GNU ld also uses `.rel.plt` for `IRELATIVE` (§11.3).

## 7. Undefined weak

For `weak0` (undefined, weak, not dynamic), measured in E14
(`misc.sh wk`) and E3 (`tw`):

| relocation | static | static-pie | references |
|---|---|---|---|
| `32` | 0 | 0, and no `RELATIVE` | all agree |
| `PC32`, `PC16`, `PC8` | `0 + A − P` | `E` (X86-21) | GNU ld and lld write `−P`, which reads as the load base at run time (the program saw 0x400000); mold refuses |
| `PLT32` | `0 + A − P`, a call to 0 | the same | all agree |
| `GOT32`, `GOT32X` | slot holds 0; relaxed forms write imm 0 (X86-24) | slot holds 0 (no `RELATIVE`), not relaxed | all agree on the loaded value 0 |
| `GOTOFF` | `0 + A − GOT` | `E` (X86-22) | GNU ld and lld write `−GOT`, which gives the load base at run time; mold writes the same |
| `TLS_*` | X86-23 | X86-23 | §15.1 |

- **X86-21 [M1] `Pc` against `weak0` in `Pie` is an error.** As x64.md
  X-15. The run-time value would be the load base, not 0.
- **X86-22 [M1] `GotRel` against `weak0` in `Pie` is an error.**
  `GOTOFF` is `S − GOT` added to a run-time GOT address. With `S = 0`
  it yields the load base: E14 printed `gotoff=0x400000` under GNU ld and
  lld 19/22 in static-pie. The class is `undefined-weak-pic`
  (diag.md), with GNU ld's own phrase for `PC32`: "can not be used when
  making a PIE object". No census object takes the `GOTOFF` of a weak
  undefined symbol (GCC and Clang load it from the GOT). In static,
  `GOTOFF` against `weak0` is `−GOT`, and the program reads 0.
- **X86-23 [M1] Thread-local `weak0`.** As x64.md X-18:
  - the TP offset and the DTP offset are 0;
  - every relaxed GD/LD/IE/GOTIE/DESC form writes `T = 0`;
  - `TLS_LE` writes `A` and `TLS_LDO_32` writes `A`.

  This is lld's choice (E3: the address printed equals TP). GNU ld
  writes `TpRel(0)` (the `TLS_GOTDESC` immediate 0xf7ef26c0 in E13
  `cmp-pic-x-static`), and mold keeps the GOT for the descriptor form.
  glibc reaches `_nl_current_LC_*` only behind a check of the
  `_nl_current_*_used` weak symbol.
- **X86-24 [M1] GOT forms against `weak0`.** The slot holds 0 in both
  outputs. In static-pie it gets no `RELATIVE`, because 0 is not an
  address of the image. The static relaxations of §8 write imm 0 (GNU
  ld, E3 `wund`: `mov $0`). `call`/`jmp` through the GOT of a `weak0`
  keep the GOT (no direct call to 0 is invented).
