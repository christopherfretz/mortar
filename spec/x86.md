# spec: i386 (`mortar_x86`)

**Status: draft (WP-030 stage 1; awaiting review).**

The i386 instance of the `Arch` trait (`spec/arch.md`). It covers every
`R_386_*` relocation type: what it computes, where its implicit addend
lives, where it writes, when it overflows, what it demands and how it may
be relaxed. It also gives the bytes of every table and stub the linker
writes, the GOT base and the PIC idioms, IFUNC, TLS, GNU properties and
CET, and the ELF header facts.

It replaces the provisional fit check of arch.md Appendix B. It cites
that appendix and corrects it where measurement disagreed (§17).
`spec/x64.md` is its template. Where a rule here is the same as an x64.md
rule, it says so and gives only what differs.

Two implementations are written from this document and must agree:
`mortar_x86` and the verifier `mortar_plumb` (`docs/AGENTS.md` rule 10).

Rule numbering and tags:
- Rules are numbered `X86-1`, `X86-2`, … and tagged **[M1]** or **[M2]**.
  - **[M1]**: static executables, non-PIE and static-pie.
  - **[M2]**: dynamic executables, PIE with a dynamic loader, shared
    objects.
- Every rule has a test idea in §19.
- Experiments are `E1`–`E16` (Appendix A). Each is a script in the review
  harness, which `run-all.sh` reproduces.
- A statement this document could not ground in a cited document or an
  experiment is marked **[open]** and listed in §18 with a recommended
  answer.
- Estimates are marked "(estimate)".

Documents cited, all public:

- **psABI**: "System V Application Binary Interface, Intel386
  Architecture Processor Supplement", version 1.1 and its 2015–2024
  updates (the `i386-ABI` repository: `GOT32X`, `TLS_GOTDESC`,
  `IRELATIVE`, the x86 GNU properties). It defines the relocation types
  and their calculations, the GOT/PLT and the GOT base.
- **TLS**: U. Drepper, "ELF Handling For Thread-Local Storage". It
  defines variant II, the IA-32 sequences and their linker rewrites,
  including the `@indntpoff`/`@gotntpoff` forms.
- **TLSDESC**: A. Oliva, "Thread-Local Storage Descriptors for IA32 and
  AMD64/EM64T".
- **binutils**: `bfd/elf32-i386.c`, `bfd/elfxx-x86.c` and
  `include/elf/i386.h` of binutils 2.44, cited for GNU ld's behavior where
  an experiment showed it.
- **SDM**: the Intel 64 and IA-32 Architectures Software Developer's
  Manual, volume 2. Cited for instruction encodings only.

## 1. Scope and status

In scope: `EM_386`, `ELFCLASS32`, `ELFDATA2LSB`, relocation sections
`SHT_REL`. The inputs are GCC 14 (`i686-linux-gnu-gcc`, the Debian
cross compiler) and Clang 19 and 22 (`--target=i686-linux-gnu`) objects.
They link against the Debian i386 glibc 2.41 static archives, libstdc++,
libgcc and the GCC runtime libraries.

kiln and hod do not target i386 (operator ruling, 2026-11-14). Every
i386 object comes from GCC or Clang.

- **M1, this document's scope**: `static` (non-PIE) and `static-pie`
  outputs. That means every type of §6.1 marked M1, the relaxations of §8
  and §9, IFUNC through the IPLT (§11.3), TLS in a static image (§13),
  and CET properties (§12).
- **M2, sketched only**: the PLT and `.rel.plt` (§11.4), `GLOB_DAT`,
  `JUMP_SLOT`, `COPY`, the TLS dynamic types, and shared objects.
- **later**: `-r` (relocatable output, needs `write_addend`, arch.md
  §3.3). Also the obsolete `TLS_IE_32`/`TLS_LE_32` pair (X86-14) and the
  Sun TLS types (§6.3).

The x86 family shares a crate: `mortar_x86` holds i386; `mortar_x64`
holds x86-64. The byte-level helpers for the ModRM reading of §3.4, the
`endbr` constants and the GNU property merge (x64.md X-41) are shared code
(request R-12). The relocation tables are not shared.

- **X86-1 [M1] What mortar accepts.** An `EM_386` `ET_REL` input with
  class `ELFCLASS32` and data `ELFDATA2LSB`, and `e_flags` 0. Any other
  `e_flags` value is refused by name (`input-flags`): the psABI defines
  none, and every object of both censuses has 0 (§2.4). An `EM_386`
  input with class `ELFCLASS64`, or an `EM_X86_64` input in an i386
  link, is refused (`spec/input.md`'s machine check).
- **X86-2 [M1] Relocation sections are `SHT_REL`.** An `SHT_RELA`
  section applying to an `EM_386` input section is refused by name
  (`relocation-section-kind`, request R-5). The psABI uses `Elf32_Rel`
  only. No producer of either census writes one. The three reference
  linkers disagree on such an input:
  - GNU ld ignores `r_addend` and reads the implicit bytes;
  - lld honors `r_addend`;
  - mold leaves the field untouched, which is wrong code (§15.2 W12;
    E9 `typeprobe.py`, case `rela`).

  shows (`GOT32X` `A = 0`; the TLS sequence leads `A = 0`). With any other
  addend the record is applied unrelaxed, or refused where §8 or §9 say.

  `+[.-.L0$pb]` gives 3, 7, …). The linker never interprets it (§10.1).

### 2.3 Instruction forms around GOT and TLS places

`scan32.py` records the two bytes before every `GOT32`, `GOT32X` and TLS
field (`before` in the census JSON):

- **`GOT32X` (17 701 records).**
  - About 96% are `8b` (mov) with ModRM mod = 10 (`8b 83` 5019,
    `8b 80` 1377, …).
  - The rest:
    - `ff 15` (`call *foo@GOT`, no base: GCC `-fno-plt -fno-pic`, 516);
    - `ff 9r` (call with base, 1000+);
    - `3b 9r`/`3b 8r` (cmp);
    - `0b 91` (or);
    - `03 85` (add, libgcc `bid64_div.o`, 88);
    - `8b 0d`… (no-base mov, GCC `-fno-pic -fno-plt`).
  - No SIB form occurs (`rm = 100`). No moffs form (`a1`/`a3` before the
    field) occurs. No pair of readings of §3.4 disagrees for any record.
- **`GOT32` (5 851).** The same opcodes, plus forms that `GOT32X` may not
  carry:
  - `83 bb`/`83 be` (`cmpl $imm8, foo@GOT(%reg)`);
  - `ff b6`/`ff b3` (push);
  - `83 3d` and `ff 35` (no-base cmp and push, GCC `-fno-pic -fno-plt`);
  - `0f 44 83`/`0f 44 8b` (cmov, Clang).

  `GOT32` is never relaxed (X86-26), so these only need §3.4's base
  test.
- **`TLS_GD` (4 490).**
  - `8d 04 1d` (SIB `leal x@tlsgd(,%ebx,1), %eax`, 4182), followed at
    `+5` by a `PLT32` (GCC, Clang, libgcc) or a `PC32` (GCC non-PIC, 254)
    against `___tls_get_addr`.
  - `8d 8r` (base `leal x@tlsgd(%reg), %eax`, 308), always followed at
    `+6` by `GOT32` or `GOT32X` `ff 9r` (`call *___tls_get_addr@GOT(%reg)`,
    `-fno-plt`).
  - No producer emits a base-register GD followed by a direct call.
- **`TLS_LDM` (1 373).** `8d 83` only (`leal x@tlsldm(%ebx), %eax`),
  followed at `+5` by `PLT32`/`PC32`, or at `+6` by
  `GOT32`/`GOT32X` `ff 93`. There is one exception: GCC `-fno-plt`
  writes `8d 87` + `ff 97` (base `%edi`) twice.
- **`TLS_IE` (1 563).**
  - `a1` (`movl x@indntpoff, %eax`). Once it is at offset 1 of its
    section (`.text.addr_tls+1`), so only one byte precedes the field.
  - `8b 0d`/`8b 15`/`8b 3d` (no-base mov);
  - `03 05` (`addl x@indntpoff, %eax`).
- **`TLS_GOTIE` (4 129).** `8b` with mod = 10 (any registers), and
  `03 81`/`03 88`/`03 83` (add).
- **`TLS_GOTDESC` (598).** `8d 83` only. **`TLS_DESC_CALL`**: always
  `ff 10` at `P`.
- **`TLS_LE` (17 297)** and **`TLS_LDO_32`**: immediate or displacement
  of any instruction. They are never rewritten.

### 2.4 Other facts

- **Relocation order.**
  - Records are not sorted by `r_offset` in 615 sections (libc 73,
    libstdc++ 267, GCC objects 229, libgomp and others 46).
  - No two records share an `r_offset`.
  - The GD and LD sequence partner is still the next record by index in
    every case (`follow` in the census, which pairs by index). X86-31
    pairs by offset nonetheless.
- **SHF_MERGE section symbols.** `32` against a section symbol of an
  `SHF_MERGE` section occurs in every set:
  - GCC 53 616 in `.debug_str` references;
  - libstdc++ 1 713 in alloc data.

  `GOTOFF` against a string section's symbol is GCC's `-fPIC` string
  reference (`leal .LC0@GOTOFF(%ebx)`).
- **TLS mismatch.** `32` against an `STT_TLS` symbol at a non-alloc place
  occurs 138 times. It comes from GCC `-gsplit-dwarf`, in `.debug_addr`
  (X86-62).
- **Undefined weak TLS.**
  - glibc's `_nl_current_LC_*` (12 symbols, libc.a);
  - the corpus's `weak_tls` (285 objects).
- **IFUNC definitions.** libc 46, libm 37, and every corpus object built
  from `c1.c`.
- **`.eh_frame`.**
  - Every CIE has augmentation `zR` with FDE encoding `0x1b`
    (`pcrel|sdata4`).
  - Some have `zPLR` with personality `0x9b` (`indirect|pcrel|sdata4`)
    and LSDA `0x1b`.
  - Clang/GCC `-fno-pic` C++ objects have `zPLR` with `P00 L00` (absolute
    `udata4`): an `R_386_32` in `.eh_frame`.
- **Header.**
  - `e_flags` = 0 in every object.
  - `EI_OSABI` is 0, or 3 (`ELFOSABI_GNU`) in objects that define an
    IFUNC: libc 28, libm 10, libstdc++ 27, and every `c1.c` object.
- **GNU properties.** `GNU_PROPERTY_X86_FEATURE_1_AND` = 3 (IBT|SHSTK)
  appears only in objects built with `-fcf-protection` (GCC, Clang 45
  each; gfortran 15). No system archive member has a property note.
- **`.note.GNU-stack`.** Present and non-executable in every object.
- **COMMON alignment.** COMMON symbols have alignment 4, and 32 in
  gfortran (`-fno-common` is the GCC 14 default; the corpus forces
  `-fcommon` for one source).
- **COMDAT.** Groups occur throughout, for example 8 290 in the GCC
  objects and 5 666 in libstdc++.

## 3. Terms, REL addends, fields, checks

### 3.1 Values

Terms are the psABI's ("Relocation Types"), defined against
`spec/model.md`. Arithmetic is on mathematical integers. A check is on
the value before truncation. The field takes `X mod 2^(8·width)`.

| term | meaning |
|---|---|
| `S` | the symbol's address (x64.md §3.1). For a symbol whose value is its IPLT entry (§11.3), that entry's address. Undefined weak: §7 |
| `A` | the implicit addend read from the field (§3.2) |
| `P` | the place, `addr(section) + r_offset` |
| `X` | the computed value |
| `Z` | `st_size` |
| `GOT` | `_GLOBAL_OFFSET_TABLE_`: the start of `.got.plt` (`Facts.got_base = GotPltStart`, §11.2) |
| `G` | the address of the GOT slot holding `S`'s address (`G(GDAT(S))`); `G − GOT` is its offset from the GOT base |
| `G(GTPREL(S))` | the address of the slot holding `S`'s TP offset, `TpRel(S)` |
| `L` | the IPLT (or, M2, PLT) entry of `S` when it has one, else `S` |
| `TpRel(x)` | `x − tls.start − align_up(tls.size, tls.align)`, negative (variant II, §13) |
| `DtpRel(x)` | `x − tls.start` |

### 3.2 REL addends

- **X86-4 [M1] Every implicit addend is the field itself.** For every
  type with a field, `Implicit { bytes: width(field), signed: true,
  shift: 0 }`, and `A` is the field's bytes read little-endian and
  sign-extended. arch.md Appendix B.1 has this right for widths 4, 2 and
  1. Nothing on i386 stores an addend outside the field. No form has a
  shifted or split immediate, and no instruction is decoded to find an
  addend.
- **X86-5 [M1] The addend is read once per use, from the input bytes.**
  The scan and the apply each call `read_addend(h, field)` on the input
  section's bytes, never on the output buffer (arch.md §3.3). The same
  `A` is used:
  - by `classify`, `scan` and the demand;
  - by `apply`, to compute `X`;
  - by the verifier, from the inputs.

  A consequence for the output buffer (arch.md §3.6, image.md I-35): the
  buffer starts as a copy of the input bytes. So the field holds `A`
  until `apply` overwrites it with `X`. A field outside the clip of the
  piece being written (image.md I-35's clip `[a, b)`) is not written by
  that piece and keeps the bytes the adjacent piece writes. A REL field
  is only 1, 2 or 4 bytes. Under I-35 no field straddles a clip
  boundary, because `max_reach` (X86-40) includes every field's width.
  An input whose field would straddle a split-section piece boundary is
  refused by name (`relocation-straddles-piece`, model.md §3.5).
- **X86-6 [M1] `16`, `8`, `PC16`, `PC8` read signed.** `A` is the 2- or
  1-byte field sign-extended. The written field is the same modulo
  2^16 (2^8) whichever way the addend is read. The reading changes only
  which values pass the check, and the signed reading is what `.word sym
  - 1` means.
  - lld reads signed.
  - GNU ld and mold read unsigned.
    - mold therefore refuses a valid `PC16` with `A = −2` ("65582 is not
      in [-32768, 32768)", E9 case `pc16neg`), which is wrong (§15.2
      W13).
    - GNU ld's bitfield check accepts both readings.
- **X86-7 [M1] Write-back.** For a final link, `apply` overwrites the
  field with `X`, and nothing else records `A`.
  - `-r` (later) writes `A + delta` back with `write_addend`, checked
    against the width (arch.md §3.3).
  - `--emit-relocs` (later) emits the relocation and leaves `X` in the
    field, as GNU ld does (arch.md Q3). Its consumer cannot recover `A`.
- **X86-8 [M1] SHF_MERGE section-symbol pieces.** A relocation against
  the section symbol of a split section (model.md §3.5) resolves its
  piece from `A` as read by X86-4. The piece is the one containing input
  offset `A` (`32`, `GOTOFF`: `.long .LC0+2` and `leal .LC1@GOTOFF(%ecx)`
  locate offsets 2 and the start of `.LC1`). For `PC32` the field is
  the place-relative word itself: `.long .LC1+1 - .` has `A = 1` and the
  piece is at offset 1.

  The output value is `S' + (A − piece_start)`, where `S'` is the
  piece's output address. All four references agree, and the program
  sees deduplicated strings (E14 `misc.sh` merge: `[hello][world][orld]`,
  `dedup=1`, both `GOTOFF` loads equal the data words; static and
  static-pie).

  An `A` outside the section (before 0, or at or past its size) is
  refused by name (`merge-addend-out-of-section`, model.md §3.5).
  No census record has one.

### 3.3 Fields

Every i386 field is a little-endian data field at `P`:

| form | bytes at `P` | used by |
|---|---|---|
| `d32` | 4 | 1, 2, 3, 4, 9, 10, 15–19, 32, 38, 39, 43 |
| `d16` | 2 | 20, 21 |
| `d8` | 1 | 22, 23 |
| `none` | 0 (a marker) | 0, 40 |

- **X86-9 [M1] Fields are data.** As x64.md X-5. `apply` writes only the
  field's bytes, except in a matched relaxation, which writes exactly the
  bytes of its window (§8, §9).

### 3.4 Checks and the GOT32 operand

| check | range of `X` | types |
|---|---|---|
| `mod(32)` | none: the field takes `X mod 2^32` | 1, 2, 4, 9, 10, 3, 43 (the GOT forms after their base is chosen), 32 |
| `s(32)` | [−2^31, 2^31 − 1] | 17, and every TP offset written by §9 |
| `u(32)` | [0, 2^32 − 1] | 38 |
| `su(16)` | [−2^15, 2^16 − 1] | 20 |
| `s(16)` | [−2^15, 2^15 − 1] | 21 |
| `su(8)` | [−2^7, 2^8 − 1] | 22 |
| `s(8)` | [−2^7, 2^7 − 1] | 23 |

- **X86-10 [M1] Word-size fields are modular.** On i386 a 32-bit field is
  the machine word, and address arithmetic wraps modulo 2^32 in the
  processor, so `32`, `PC32`, `PLT32`, `GOTOFF`, `GOTPC`, `GOT32`,
  `GOT32X` and `TLS_LDO_32` have no overflow check. This differs from
  x64.md X-6, where `32` is `u(32)` in a 64-bit space. The psABI defines
  no overflow for them. Measured (E9): `.long sym+2` with `sym =
  0xffffffff` (an absolute symbol) writes 1 under GNU ld, lld 22 and
  mold, and a `PC32` that wraps also links under all three.

  `.long sym - k` with `sym < k` must link: GCC emits it for `&a[-k]`.
  Under a `u(32)` check it would be refused. Every reference accepts it.
- **X86-11 [M1] Narrow overflow is an error.** `16`, `8`, `PC16`, `PC8`
  and `TLS_LE` outside their check give `relocation-out-of-range` (§10,
  x64.md X-6), never a truncated write. Measured (E9):
  - lld accepts `16` in [−32768, 65535] and `8` in [−128, 255], and
    refuses beyond.
  - GNU ld accepts and truncates −32769 (writes 0x7fff) and −129 (writes
    0x7f): wrong code (§15.2 W11).
  - mold checks `16`/`8` unsigned.
  - All three refuse `PC8` = 128.
- **X86-12 [M1] `SIZE32` is `u(32)`.** As x64.md X-7.
  - GNU ld and mold write `Z + A` (12 in E9).
  - lld 19 refuses it as "unknown relocation (38)".
  - lld 22 fails with "internal linker error: cannot read addend" (§15.1).
- **X86-13 [M1] The GOT32/GOT32X operand: base or none.** `GOT32` and
  `GOT32X` compute `G + A − GOT` when the instruction's memory operand
  has a base register, and `G + A` (the absolute slot address) when it
  has none (psABI, `GOT32X` note). The field is always the operand's
  `disp32`, and the bytes before it decide which form applies. Let
  `b1 = byte(P − 1)` and `b2 = byte(P − 2)` (bytes before the start of
  the section do not exist).

  `classify` computes every reading of these bytes that is consistent
  with the field being a `disp32` that ends the operand:

  1. **ModRM reading**, with `b1` as the ModRM byte:
     - `(b1 & 0xc7) == 0x05` (mod = 00, rm = 101) is **none**;
     - mod = 10 with rm ≠ 100 is **base**;
     - any other `b1` gives no ModRM reading.
  2. **SIB reading**, with `b1` as a SIB and `b2` as a ModRM with
     rm = 100. It applies when `b2` exists and mod(`b2`) ∈ {00, 10}.
     - mod = 00 with SIB base = 101: the operand is `disp32(,%index,s)`,
       which is **none** (the index is not a base).
     - mod = 10, or SIB base ≠ 101: **base**.
  3. **moffs reading**: `b1` ∈ {`a0`, `a1`, `a2`, `a3`} (the moffs32
     forms of mov), which is **none**.

  If every reading that exists gives the same answer, that answer is
  used. If there is no reading, or two readings disagree, the record is
  refused by name: `got-operand-ambiguous`, which names the file, the
  section, the offset and the two readings. It is an error class of
  `spec/diag.md` (request R-9).

  Why this matters:
  - The three reference linkers each misread a form (§15.2 W1–W3).
    - GNU ld and lld treat `0d` in `mov foo@GOT(%ebp,%ecx,1)` (`8b 84
      0d`) as a no-base ModRM.
    - GNU ld and lld write `G + A − GOT` for the moffs store `a3`, which
      is wrong because the moffs form is absolute.
    - mold writes `G + A − GOT_mold` for every no-base form. Its GOT
      base is `.got`, not `_GLOBAL_OFFSET_TABLE_`, so this is wrong for
      every one of them.

    Each crashes under qemu-i386 (E5 `gotform.sh`, E3 `relaxrun.sh`
    family `sib`).
  - No census record is ambiguous or has no reading (§2.3), so the rule
    refuses nothing real. The verifier recomputes the readings from the
    input bytes.
  - The window for this test is `before = 2` (`[P − 2, P)`), within
    `max_reach` (X86-40).

## 4. Targets and outputs

Target kinds and output kinds are arch.md §4.1's, as x64.md §4.

- **X86-15 [M1] Static-pie is position-independent.** As x64.md X-9. An

  `R_386_RELATIVE` (synth.md). Text relocations are refused: an `R_386_32`
  against a non-absolute target in an executable section of a static-pie
  output is an error. GNU ld's message is "relocation R_386_32 against
  `x' can not be used when making a PIE object; recompile with -fPIE"

  the three references carry only these dynamic relocations:
  - `RELATIVE` and `IRELATIVE`, in `.rel.dyn`;
  - GNU ld also uses `.rel.plt` for `IRELATIVE` (§11.3).

## 7. Undefined weak

For `weak0` (undefined, weak, not dynamic), measured in E14
(`misc.sh wk`) and E3 (`tw`):

| relocation | static | static-pie | references |
|---|---|---|---|
| `32` | 0 | 0, and no `RELATIVE` | all agree |
| `PC32`, `PC16`, `PC8` | `0 + A − P` | `E` (X86-21) | GNU ld and lld write `−P`, which reads as the load base at run time (the program saw 0x400000); mold refuses |
| `PLT32` | `0 + A − P`, a call to 0 | the same | all agree |
| `GOT32`, `GOT32X` | slot holds 0; relaxed forms write imm 0 (X86-24) | slot holds 0 (no `RELATIVE`), not relaxed | all agree on the loaded value 0 |
| `GOTOFF` | `0 + A − GOT` | `E` (X86-22) | GNU ld and lld write `−GOT`, which gives the load base at run time; mold writes the same |
| `TLS_*` | X86-23 | X86-23 | §15.1 |

- **X86-21 [M1] `Pc` against `weak0` in `Pie` is an error.** As x64.md
  X-15. The run-time value would be the load base, not 0.
- **X86-22 [M1] `GotRel` against `weak0` in `Pie` is an error.**
  `GOTOFF` is `S − GOT` added to a run-time GOT address. With `S = 0`
  it yields the load base: E14 printed `gotoff=0x400000` under GNU ld and
  lld 19/22 in static-pie. The class is `undefined-weak-pic`
  (diag.md), with GNU ld's own phrase for `PC32`: "can not be used when
  making a PIE object". No census object takes the `GOTOFF` of a weak
  undefined symbol (GCC and Clang load it from the GOT). In static,
  `GOTOFF` against `weak0` is `−GOT`, and the program reads 0.
- **X86-23 [M1] Thread-local `weak0`.** As x64.md X-18:
  - the TP offset and the DTP offset are 0;
  - every relaxed GD/LD/IE/GOTIE/DESC form writes `T = 0`;
  - `TLS_LE` writes `A` and `TLS_LDO_32` writes `A`.

  This is lld's choice (E3: the address printed equals TP). GNU ld
  writes `TpRel(0)` (the `TLS_GOTDESC` immediate 0xf7ef26c0 in E13
  `cmp-pic-x-static`), and mold keeps the GOT for the descriptor form.
  glibc reaches `_nl_current_LC_*` only behind a check of the
  `_nl_current_*_used` weak symbol.
- **X86-24 [M1] GOT forms against `weak0`.** The slot holds 0 in both
  outputs. In static-pie it gets no `RELATIVE`, because 0 is not an
  address of the image. The static relaxations of §8 write imm 0 (GNU
  ld, E3 `wund`: `mov $0`). `call`/`jmp` through the GOT of a `weak0`
  keep the GOT (no direct call to 0 is invented).

## 8. GOT32/GOT32X and PIC relaxations

A relaxation rewrites the bytes of one record's window so that the
instruction no longer goes through the GOT or the TLS runtime. "kind 1"
and "kind 2" are arch.md §5.2's, as in x64.md §8. `reg` is the input
ModRM's reg field (bits 5..3).

| id | input (bytes before and at `P`) | when | output over `[P − 2, P + 4)` | kind | status |
|---|---|---|---|---|---|
| G1 | `GOT32X`, `8b` ModRM, ModRM reading only (X86-13) | X86-25 | `c7 (c0 \| reg) imm32` (mov $S) | 1 | M1 |
| G2 | `GOT32X`, op ModRM, op ∈ {`03`, `0b`, `13`, `1b`, `23`, `2b`, `33`, `3b`} | X86-25 | `81 (c0 \| (op & 38) \| reg) imm32` | 1 | M1 |
| G3 | `GOT32X`, `85` ModRM (test) | X86-25 | `f7 (c0 \| reg) imm32` | 1 | M1 |
| G4 | `GOT32X`, `ff` ModRM with reg = 2 (call) | X86-25, target defined | `67 e8 rel32`, rel32 = `S − (P + 4)` | 1 | M1 |
| G5 | `GOT32X`, `ff` ModRM with reg = 4 (jmp) | X86-25, target defined | `e9 rel32 90`: `e9` at `P − 2`, rel32 = `S − (P + 3)` at `P − 1`, `90` at `P + 3` | 1 | M1 |

`imm32` is `S` (`A = 0`), or 0 for `weak0`. Every output has the input's
length, so no other byte moves.

- **X86-25 [M1] GOT32X → immediate, static only (G1–G5).** In a
  `static` (non-PIE) output, a `GOT32X` record is rewritten when all of
  these hold:
  - its operand has a ModRM reading and no other (X86-13), with mod = 00
    rm = 101 (none) or mod = 10 rm ≠ 100 (base);
  - the opcode at `P − 2` is one of G1–G5;
  - `A = 0`;
  - the target is `local` or `abs`, or `weak0` for G1–G3.

  The forms and bytes are GNU ld 2.44's (`elf_i386_convert_load_reloc`).
  Measured (E3 `relaxrun.sh`, E4 `relaxcmp.sh`, condensed in
  `logs-sum-*.txt` by `relaxsum.py`): GNU ld writes exactly G1–G5 for all
  of these, with base and without (`8b 05` → `c7 c0`, `3b 05` → `81 f8`,
  `85 05` → `f7 c0`, `ff 15` → `67 e8`, `ff 25`/`ff a3` → `e9 … 90`).
  Every site's value is then checked under qemu-i386 and passes.

  lld 19/22 and mold relax no `GOT32X` at all, in any output, and those
  programs also run. The relaxation is kind 1: the decision depends on
  the output kind, the target kind and the bytes, never on an address.
  `imm32` and `rel32` cannot overflow (X86-10).

  The `call` form keeps its length with the `addr32` prefix (`67`),
  which has no effect on a `call rel32`. The `jmp` form puts a `nop`
  after the 5-byte jump (SDM).
- **X86-26 [M1] Plain `GOT32` is never relaxed.** As x64.md X-31. The
  producer did not mark it relaxable (`-mrelax-relocations=no`, or forms
  `GOT32X` may not carry, §2.3). All three references leave it (E4).
- **X86-27 [M1] Static-pie keeps the GOT.** In `static-pie` no `GOT32X`
  is relaxed. A G1 `mov` with a base could become `lea S − GOT(%reg)`
  (`8d`, psABI). That is not taken in M1: no reference does it in
  static-pie (E4: lld and mold keep every `8b`), so it cannot be measured
  differentially. GNU ld 2.44 refuses the E4 object outright, because of
  its IFUNC `GOTOFF` (§15.1). §18 Q4 recommends taking it in M2 with the
  patcher check of §16.

  A no-base `GOT32`/`GOT32X` in static-pie writes an absolute slot
  address into code. That is a text relocation, so it is refused with
  GNU ld's phrase: "direct GOT relocation R_386_GOT32X against `x'
  without base register can not be used when making a shared object"
  (E5).
- **X86-28 [M1] `ifunc` keeps the GOT.** As x64.md X-22. A `GOT32X`
  against an IFUNC is not relaxed (GNU ld keeps it too, E4 `ifn`). Its
  slot holds the canonical address of §11.3.
- **X86-29 [M1] `PLT32` is direct in M1.** A `PLT32` against a defined
  non-IFUNC symbol is `S + A − P` (`L = S`). No PLT entry exists in a
  static output. Against an IFUNC it is the IPLT entry (§11.3). All four
  references agree (E4, E8).

### 8.1 The GOT base and the get_pc_thunk idiom

- **X86-30 [M1] `GOTPC` needs no rewriting.** The PIC prologue is:

  ```
  call __x86.get_pc_thunk.bx
  addl $_GLOBAL_OFFSET_TABLE_, %ebx
  ```

  GCC writes `81 c3` + `GOTPC` with `A = 2`. Clang instead writes
  `call .L0$pb; .L0$pb: popl %ebx; addl $_GLOBAL_OFFSET_TABLE_+(.Ltmp-.L0$pb), %ebx`,
  with `A = 3`, 7, …. Either way `%ebx = GOT` at run time, and
  `GOT + A − P` is computed with no knowledge of the instruction.

  The symbol of a `GOTPC` record is ignored: GNU ld, lld and mold write
  `GOT + A − P` even against another symbol (E9 `gotpc_other`). The
  `__x86.get_pc_thunk.*` functions are ordinary COMDAT functions
  (`.text.__x86.get_pc_thunk.bx`, group of the same name) and need
  nothing from the linker.

  `_GLOBAL_OFFSET_TABLE_` is defined by the linker (hidden, at
  `.got.plt`'s start) whenever any record has class `Got`, `GotRel`,
  `GotBaseRef` or `TlsIe` `TLS_GOTIE`, or names it. In that case the
  `.got.plt` section exists even when it holds only the reserved words
  (§11.2).

## 9. TLS relaxations

Every M1 output is an executable. A TLS reference resolves within it,
so every GD, LD and descriptor sequence becomes LE, and IE becomes LE
where the form is recognized. `T` is `TpRel(S)` for the lead's target,
negative, little-endian 4 bytes. `T = 0` when the target is `weak0`
(X86-23) or `_TLS_MODULE_BASE_` (X86-63).

| id | input | when | window | output | kind |
|---|---|---|---|---|---|
| I1 | `TLS_IE`, `a1` at `P − 1` (`movl x@indntpoff, %eax`) | static, static-pie; `A = 0` | `[P − 1, P + 4)` | `b8 T` | 1 |
| I2 | `TLS_IE`, `8b` ModRM `00 reg 101` | as I1 | `[P − 2, P + 4)` | `c7 (c0 \| reg) T` | 1 |
| I3 | `TLS_IE`, `03` ModRM `00 reg 101` | as I1 | `[P − 2, P + 4)` | `81 (c0 \| reg) T` | 1 |
| I4 | `TLS_GOTIE`, `8b` ModRM `10 reg rm`, rm ≠ 100 | as I1 | `[P − 2, P + 4)` | `c7 (c0 \| reg) T` | 1 |
| I5 | `TLS_GOTIE`, `03` ModRM `10 reg rm`, rm ≠ 100 | as I1 | `[P − 2, P + 4)` | `81 (c0 \| reg) T` | 1 |
| D1 | `TLS_GD` `8d 04 1d` at `P − 3`; next record at `P + 5`, `PLT32` or `PC32` against `___tls_get_addr`, `e8` at `P + 4` | static, static-pie; lead `A = 0`, call `A = −4` | `[P − 3, P + 9)` | `65 a1 00 00 00 00 81 e8 (−T)` | 1 |
| D2 | `TLS_GD` `8d` ModRM `10 000 rm` (rm ≠ 100) at `P − 2`; next record at `P + 6`, `GOT32` or `GOT32X` against `___tls_get_addr`, `ff` ModRM `10 010 rm'` at `P + 4` | as D1, call `A = 0` | `[P − 2, P + 10)` | the same 12 bytes | 1 |
| D3 | `TLS_GD` as D2's lead; next record at `P + 5` as D1's call; `90` at `P + 9` | as D1 | `[P − 2, P + 10)` | the same 12 bytes | 1 |
| L1 | `TLS_LDM` `8d` ModRM `10 000 rm` (rm ≠ 100) at `P − 2`; next record at `P + 5`, `PLT32`/`PC32` against `___tls_get_addr`, `e8` at `P + 4` | static, static-pie | `[P − 2, P + 9)` | `65 a1 00 00 00 00 90 8d 74 26 00` | 1 |

| T1 | `TLS_GOTDESC`, `8d` ModRM `10 000 rm` (rm ≠ 100) | static, static-pie | `[P − 2, P + 4)` | `8d 05 T` | 1 |

What the outputs mean (SDM):
- `65 a1 00 00 00 00` is `movl %gs:0, %eax`.
- `81 e8 imm32` is `subl $imm32, %eax`.
- `90 8d 74 26 00` is a 1-byte and a 4-byte NOP (`nop; lea 0(%esi,%eiz,1), %esi`).
- `8d b6 00 00 00 00` is a 6-byte NOP (`lea 0(%esi), %esi`).
- `8d 05 T` is `leal T, %eax`, an absolute operand, so it loads `T`.
- `66 90` is a 2-byte NOP.

### 9.1 Which bytes, and why

- **X86-31 [M1] Sequences.** A `TLS_GD` or `TLS_LDM` record is a
  sequence lead (arch.md §3.5). Its partner is the record with the next
  index in the same relocation section, and that partner must also be
  at the offset the form names (`P + 5` or `P + 6`) against
  `___tls_get_addr`. The partner is consumed: it raises no demand and
  `apply` does not write it.

  Pairing by index is arch.md's look-back of 1. The census has 615
  unsorted relocation sections (§2.4), and in every one the partner is
  the next index. A lead whose next record does not satisfy the form is
  refused (X86-36), never paired with a record found by searching.
- **X86-32 [M1] IE → LE (I1–I5).** In static and static-pie every
  recognized `TLS_IE`/`TLS_GOTIE` with `A = 0` and a defined or `weak0`
  TLS target is rewritten. GNU ld 2.44 and lld 19/22 write exactly I1–I4
  (E4: `a1` → `b8`, `8b 0d` → `c7 c1`, `03 05` → `81 c0`, `8b 83` →
  `c7 c0`), and so does GNU ld for I5 (`03 83` → `81 c0`).

  lld writes I5 as `8d (80 | reg·9) T` (`lea T(%reg), %reg`). That has
  the same value but does not set the flags `addl` sets. I5 keeps the
  `add`, as x64.md X-23 does and for the same reason: a producer may test
  the flags (§15.1).

  mold relaxes no IE form and keeps the GOT slot holding `TpRel(S)`,
  which is also correct (E4).

  I1 reads only `[P − 1, P)`. Its window starts 1 byte before the field,
  because a census record (`.text.addr_tls+1`, §2.3) has only one byte
  before it in its section. For `TLS_IE` the forms are the three that
  Drepper's IA-32 IE model defines, so `a1` at `P − 1` is read as the
  moffs form: the psABI admits no other `TLS_IE` instruction.
- **X86-33 [M1] An unrecognized IE keeps IE.** As x64.md X-24. In
  `static`, a `TLS_IE` that is not I1–I3 is applied unrelaxed, with a
  `GTPREL` slot and the absolute slot address. A `TLS_GOTIE` that is not
  I4–I5 keeps `G(GTPREL(S)) + A − GOT`. In `static-pie`, an unrelaxed
  `TLS_IE` is a text relocation and is refused (X86-18). The census has
  no unrecognized IE form (§2.3).
- **X86-34 [M1] GD → LE (D1–D3).** In static and static-pie every GD
  sequence of form D1, D2 or D3 is rewritten. `%eax` receives `TP + T`
  (`subl $(−T)` from `TP`).
  - D1 is the census's main form (4 182).
  - D2 is the `-fno-plt` form (308).
  - D3 is the form GNU's documentation gives for a base register with a
    direct call. It is not in the census but is generated by
    `genrelax32.py` (`gdnop`).

  GNU ld and lld write the 12 bytes of D1–D3 (E4: `65 a1 00 00 00 00 81
  e8 74 00 00 00` for `T = −0x74`). mold writes `81 c0 T` (`addl $T`),
  which gives the same `%eax`.

  For D3, mold starts its rewrite at `P − 3` instead of `P − 2`, which
  clobbers the last byte of the previous instruction: wrong code (§15.2
  W4; E15 `gdmold/`).

  The lead's `rm` and the call's `rm'` need not be equal: both
  instructions are replaced.
- **X86-35 [M1] LD → LE (L1, L2).** In static and static-pie every LD
  sequence of form L1 or L2 becomes `movl %gs:0, %eax` plus NOPs, so
  `%eax = TP`. The `TLS_LDO_32` fields added to it are then `TpRel`
  (X86-61). The bytes are GNU ld's and lld's (E4).

  mold writes `65 a1 00 00 00 00 2d <size>` (`subl $tls_block`),
  leaving `%eax` at the block start, and keeps `DtpRel` fields. That
  program also runs.

  L1 with a base register other than `%ebx` is accepted:
  - GNU ld 2.44 refuses it ("TLS transition from R_386_TLS_LDM to
    R_386_TLS_LE_32 against `tv' … failed", E3 family `ldnonebx`);
  - lld relaxes it, and the program runs;
  - the output does not depend on the base;
  - no census object has it (§2.3: `8d 83` + `e8`, and `8d 87` with
    `ff 97` only).
- **X86-36 [M1] An unmatched GD or LD is refused by name.** As x64.md
  X-26: `tls-sequence-unrecognized`, naming the file, section, offset
  and the bytes of the would-be window. Examples:
  - a `TLS_GD` whose next record is not at the form's offset or not
    against `___tls_get_addr`;
  - a base-register GD followed by `e8` with no `90` after it;
  - a SIB `TLS_LDM`.

  The census has none.
- **X86-37 [M1] TLSDESC → LE (T1, T2).** In static and static-pie each
  member is rewritten independently.
  - T1 writes `leal T, %eax` (`8d 05`). GNU ld and lld write exactly
    that (E4).
  - mold writes `90 b8 T` from `P − 2` (`nop; movl $T, %eax`) when it
    relaxes, and otherwise keeps the GOT form.
  - T2 is `66 90` in all three references.

  gas accepts `@tlsdesc` only with `%ebx` ("@TLSDESC operator requires
  `%ebx' as base register"). T1 accepts any base because the base is
  discarded. The reg field must be 000 (`%eax`): the psABI's descriptor
  ABI returns in `%eax`.
- **X86-38 [M1] TP-offset range.** `T` and every `TLS_LE` value must be
  in `s(32)`, and are in any image smaller than 2 GiB of TLS. That is
  the only TLS check (§3.4).
- **X86-39 [M1] Static links have no TLS runtime calls.** As x64.md
  X-48. After §9, no `PLT32`, `PC32`, `GOT32` or `GOT32X` against
  `___tls_get_addr` remains unconsumed in a static output, and the
  verifier checks this. A reference to `___tls_get_addr` outside a
  sequence (a function pointer, say) is an ordinary reference and is
  allowed.

### 9.2 Windows, `max_reach` and `sequence_extent`

- **X86-40 [M1] `max_reach` = (3, 10).**
  - The largest `before` is 3: the D1 lead's `8d 04 1d`.
  - The largest `after`, measured from a lead's `P`, is 10: D2, D3 and
    L2 end at `P + 10`.
  - X86-13's operand test reads `before = 2`.
  - Every other window lies within `[P − 2, P + 4)`.

  `max_reach` is derived from this table and not written by hand
  (image.md I-111, request R-3). arch.md Appendix B.5 gives window
  lengths of 12, 13, 11 and 12. The correct lengths are 12 (D1, D2, D3,
  L2) and 11 (L1), measured from the window's first byte.
- **X86-41 [M1] `sequence_extent`.** For a lead at record `i`, the
  sequence is records `i` and `i + 1`. Its byte extent is the lead's
  window: `[P − 3, P + 9)` for D1, `[P − 2, P + 10)` for D2, D3 and L2,
  and `[P − 2, P + 9)` for L1.

  `seq_leads(j)` is `{j − 1}` when record `j − 1` is a lead of a matched
  sequence whose partner is `j`; otherwise it is empty. An incremental
  relink that changes either record re-applies both (arch.md §3.5).
- **X86-42 [M1] Reference forms (a request to `spec/plumb.md`).** The
  verifier recognizes exactly G1–G5, I1–I5, D1–D3, L1–L2 and T1–T2 by
  their input bytes, and checks:
  - that the output window holds this table's bytes, with `T`, `S` and
    `rel32` recomputed from the inputs;
  - that every byte outside the windows equals the unrelaxed
    application.

  It must also reproduce X86-13's operand readings and refuse what they
  refuse (request R-8).

## 10. Range

- **X86-43 [M1] No thunks.** i386 `call`/`jmp` take a rel32, and the
  processor computes the target modulo 2^32 (SDM: in 32-bit mode the
  instruction pointer is truncated to 32 bits). Every branch reaches
  every address, so no veneer, thunk or range extension exists on i386
  (arch.md §6's fixed point is trivial: no patch is ever demanded).
  `PC32`/`PLT32` are `mod(32)` (X86-10).
- **X86-44 [M1] Out of range is only narrow.** The only range errors are
  `16`, `8`, `PC16`, `PC8` (§3.4), `SIZE32` and the TP offsets. As
  x64.md X-34, the message contains "relocation truncated to fit", which
  scripts that parse GNU ld output look for. Example: "relocation
  truncated to fit: R_386_16 against `sym' at a.o:(.data+0x4): value
  −32769 not in [−32768, 65535]".
- **X86-45 [M1] The 32-bit image.** The output is `ELFCLASS32`, so every
  address, size and file offset must be below 2^32:
  - the end of the highest `PT_LOAD` (`p_vaddr + p_memsz`) must be
    ≤ 2^32;
  - the file size must be < 2^32;
  - `PT_TLS`'s `p_memsz` must be < 2^31 (X86-38).

  An image that violates any of these is refused (`output-too-large`,
  naming the segment or section that crosses the limit). Address
  arithmetic in relocation values wraps (X86-10), but layout never does:
  layout.md's assignment computes in 64 bits and checks the bound once
  (request R-6).

## 11. Shapes

### 11.1 GOT slots

- **X86-46 [M1] GOT slots.** `.got` holds 4-byte slots, with no header
  word in a static output (synth.md orders them). Contents:

| slot | static | static-pie |
|---|---|---|
| `GDAT`, `local` | `S` | `S`, with a `RELATIVE` |
| `GDAT`, `abs` | `S` | `S` |
| `GDAT`, `ifunc` | the IPLT entry (X86-49) | the resolver's address, with an `IRELATIVE` (X86-50) |
| `GDAT`, `weak0` | 0 | 0 |
| `GTPREL` | `TpRel(S)` | `TpRel(S)` |

  GNU ld, lld and mold write these values for `local`, `abs`, `weak0` and
  `GTPREL` (E3, E4, E8). For `ifunc`, §11.3 says where each reference
  differs.

### 11.2 `.got.plt` and `_GLOBAL_OFFSET_TABLE_`

- **X86-47 [M1] `_GLOBAL_OFFSET_TABLE_` is the start of `.got.plt`.**
  - The GOT base `GOT` (`Facts.got_base = GotPltStart`) is `.got.plt`'s
    first byte.
  - In a static output `.got.plt` holds 3 reserved zero words
    (`Facts.got_plt_reserved = 3`, 12 bytes; synth.md S-67), followed by
    one 4-byte word per IPLT entry. This is x64.md X-36 with 4-byte
    words.
  - GNU ld and lld define `_GLOBAL_OFFSET_TABLE_` there and compute
    `GOTPC`/`GOTOFF` against it (E5).
  - mold defines the symbol there too, but computes `GOTPC` against its
    internal `_GLOBAL_OFFSET_TABLE_$got`, the start of `.got`. It also
    computes the no-base `GOT32` against that base, which is wrong
    (§15.2 W3).

  On i386 the GOT base is the PIC register's value, so `GOT32`, `GOTOFF`
  and `GOTPC` must all use the same base. Mortar uses the one the
  psABI's PLT shape fixes: `.got.plt`'s start, which `ff a3`/`ff b3`
  entries address (§11.4).

### 11.3 IFUNC and the IPLT

The i386 IPLT entry jumps through its `.got.plt` word. How it reaches the
word depends on the output:

- in `static` it uses the word's absolute address, `ff 25 <abs32>`, and
  needs no register;
- in `static-pie` it can only use `ff a3 <word − GOT>`, which needs
  `%ebx = GOT` at the call.

x64 needs neither, because x64 has RIP-relative addressing. The two
outputs therefore choose different canonical addresses.

- **X86-48 [M1] Plain IPLT entries.** In `.iplt`, part of the text
  output section, 16-byte aligned, entries of 8 bytes:
  - static: `ff 25 <abs32 word>` then `66 90`;
  - static-pie: `ff a3 <word − GOT>` then `66 90`.

  The bytes after the indirect `jmp` never execute. GNU ld writes the
  static form exactly (E8: entries at 0x8049020, 0x8049028, …).
  - lld uses 16-byte entries `ff 25/ff a3 …; 68 n; e9 …`, of which only
    the first 6 bytes ever run.
  - mold uses `.plt.got` entries `f3 0f 1e fb; ff 25/ff a3 …; cc…`.
  - GNU ld's static-pie IPLT keeps a lazy-PLT header
    (`ff b3 04 00 00 00; ff a3 08 00 00 00; …`) and 16-byte entries.
- **X86-49 [M1] IBT IPLT entries.** When the output's `FEATURE_1_AND`
  has IBT (X86-56), entries are 16 bytes: `f3 0f 1e fb` (`endbr32`),
  the jump of X86-48, then `66 0f 1f 44 00 00` (a 6-byte NOP). GNU ld
  writes exactly that in static under `-z ibt` (E8). mold pads with
  `cc`. lld writes no IBT entry and no property note at all on i386
  (§15.1).
- **X86-50 [M1] The canonical address of an IFUNC.**
  - **static**: the canonical address is the IPLT entry. Every reference
    to the function's address uses it:
    - `32`, `GOTOFF`, `PC32` and `PLT32` use the entry;
    - the `GDAT` slot holds the entry, statically;
    - the entry's `.got.plt` word holds the resolver's address, with an
      `IRELATIVE` in `.rel.iplt` whose word is that address (REL: the
      addend is the word, §6.2).

    `__rel_iplt_start`/`__rel_iplt_end` bracket `.rel.iplt` (glibc's
    `apply_irel`). Pointer equality holds because there is one address.
    Calls through any form reach the entry, which jumps through the
    resolved word. The entry needs no `%ebx`, so callers from
    `-fno-pic`, `-fPIE` and `-fPIC` code all work.
  - **static-pie**: the canonical address is the resolved function.
    - every address word gets an `IRELATIVE` whose word is the resolver:
      the `GDAT` slot, and `32` in data (in a writable section; in a
      read-only one it is a text relocation, X86-15);
    - `PLT32` calls go to the entry (`ff a3`), whose word also has an
      `IRELATIVE`. The psABI requires `%ebx = GOT` at every `PLT32` call
      site of PIC code, and GCC and Clang `-fPIC`/`-fPIE` emit it so;
    - `GOTOFF` against an IFUNC is refused with GNU ld's phrase
      "relocation R_386_GOTOFF against STT_GNU_IFUNC symbol `f' isn't
      supported" (E8);
    - `PC32` against an IFUNC is refused with GNU ld's phrase
      "unsupported non-PIC call to IFUNC `f'" (E8).

    Neither value is available without `%ebx`: `GOTOFF` would have to
    give the run-time resolved address as a constant offset, and a
    `PC32` call would land on an entry that needs `%ebx`. Pointer
    equality holds because every address-taking form reads an
    `IRELATIVE`-resolved word.

  Measured, and why mortar's choice is the only one that is both correct
  and accepts the census (E8 `ifunc.sh`, `ifunc/ebx.s`, `hcall2.c`):
  - GNU ld in static writes `GOTOFF` against a global IFUNC as entry −
    12, a jump into the middle of an entry, which crashes (§15.2 W5).
  - lld in static-pie makes the canonical address an `ff a3` entry. A
    caller with `%ebx ≠ GOT` that calls the pointer crashes (`ebx.s`),
    and so does a GCC `-fPIE` `PC32` call to a hidden IFUNC (§15.2 W6).
    mold crashes on the latter as well.
  - mold in static-pie breaks pointer equality: the `GOTOFF` address
    differs from the GOT address (§15.2 W7).
  - GNU ld's static-pie refuses both `GOTOFF` and the hidden `PC32` call,
    as mortar does.
- **X86-51 [M1] `IRELATIVE` placement.**
  - static: the IPLT words' `IRELATIVE`s are in `.rel.iplt`, and nothing
    else is.
  - static-pie: every `IRELATIVE` is in `.rel.dyn` after every
    `RELATIVE`, as x64.md X-56. glibc's `_dl_relocate_static_pie` applies
    the relative relocations first, and a resolver may read relocated
    data.
  - `__rel_iplt_start` = `__rel_iplt_end` (an empty range, hidden) in
    static-pie. glibc's `apply_irel` then does nothing, and the loader's
    self-relocation applies the `IRELATIVE`s.

  Measured (E8):
  - mold defines both as absolute 0;
  - lld leaves them undefined weak, also 0;
  - GNU ld uses `.rel.plt` for the IPLT words in static-pie.

  All of these run. An empty range at any address is equivalent.

### 11.4 PLT (M2)

- **X86-52 [M2] PLT shapes.** As arch.md Appendix B.4, which E8 and the
  references confirm:
  - `Abs` for `exec`: `ff 35 <GOT+4>; ff 25 <GOT+8>; 00 00 00 00` and
    entries `ff 25 <abs word>; 68 <8n>; e9 <PLT0>`;
  - `Pic` for `pie`/`shared`: `ff b3 04 00 00 00; ff a3 08 00 00 00;
    00 00 00 00` and entries `ff a3 <word − GOT>; 68 <8n>; e9 <PLT0>`;
  - IBT variants as x64.md's.

  Not tested in M1.

## 12. GNU properties and CET

- **X86-53 [M1] Properties.** `.note.gnu.property` in an ELFCLASS32
  output has 4-byte alignment and 4-byte `pr_datasz` padding (gABI
  "Program Property", ELFCLASS32 rows). Merge rules are x64.md X-41's,
  shared code (R-12): `FEATURE_1_AND` (IBT bit 0, SHSTK bit 1) is ANDed,
  and `ISA_1_NEEDED`/`FEATURE_2_USED` are ORed.
- **X86-54 [M1] Static glibc links are not IBT.** As x64.md X-42. No
  member of the i386 libc.a, libm.a or GCC runtime archives carries a
  property note (§2.4). An object without one clears the AND, so a
  default static link has no `FEATURE_1_AND`. All three references agree
  (E8: no note, no `endbr32` in the IPLT).
- **X86-55 [M1] `-z ibt`, `-z shstk`, `-z cet-report`.** As x64.md X-43.
  `-z ibt` forces the IBT bit and selects X86-49's entries.
  - GNU ld and mold do this on i386 (E8: note "x86 feature: IBT").
  - lld 19/22 write no note and plain entries under `-z ibt` on i386.
    lld implements `-z ibt` only for x86-64, so it disagrees (§15.1).
- **X86-56 [M1] `endbr32` is not checked.** qemu-i386 user mode does not
  enforce IBT, and neither does any i386 Linux kernel. An IBT output
  therefore cannot be run-checked for a missing `endbr32` (§18 Q5). The
  verifier checks the bytes of X86-49 and that the note is present.

## 13. TLS layout

- **X86-57 [M1] Variant II on `%gs`.** As x64.md X-44, with `%gs`:
  - the thread pointer (`%gs:0`) points at the TCB, which follows the
    TLS block;
  - `TpRel(x) = x − tls.start − align_up(tls.size, tls.align)`;
  - `PT_TLS` has `p_align = tls.align`, `p_vaddr = tls.start`, and
    `p_memsz`/`p_filesz` per synth.md.

  Measured (E7 `tlslayout.sh`, `.tdata`/`.tbss` alignments 4, 16, 64
  and 4096): GNU ld, lld 19/22 and mold place the block identically and
  write the same offsets, and every program reads its variables
  correctly under qemu-i386. For example, with alignment 4096, `d1` is
  at −8192, `b2` at −4096, and `p_memsz` is 0x102c. An over-aligned
  block needs no extra rule beyond the formula: glibc's static TLS setup
  aligns TP so that `TP − align_up(size, align)` is aligned (E7).
- **X86-61 [M1] `TLS_LDO_32`.** As x64.md X-46:
  - in a section with `SHF_EXECINSTR` of an M1 output,
    `X = TpRel(S + A)`. That is where a relaxed LD (L1, L2) or a
    `_TLS_MODULE_BASE_` descriptor leaves `%eax = TP`;
  - in every other section, alloc or not, `X = DtpRel(S + A)`.

  Measured (E4): GNU ld and lld write `TpRel` in code (`8d 80 8c ff ff
  ff` after an L1), while mold writes `DtpRel` with its own `subl` form.
  All four write `DtpRel` for Clang's `TLS_LDO_32` in `.debug_addr` and
  `.debug_info` (E12 `dbgtls.sh`).
- **X86-62 [M1] `32` against TLS at a non-alloc place is `DtpRel`.** As
  x64.md X-53's first addition. GCC 14 `-gsplit-dwarf` emits
  `.debug_addr` entries as `R_386_32` against the TLS symbol (138 census
  records). lld writes `DtpRel` (0, 0x68, 0x78, 4 in E12). GNU ld and
  mold write the template address (0x080e4898 …), and gdb 16.3 then
  reports "offset 0x80e4900 in the thread-local storage" for a variable
  at offset 0x68. That is wrong debug information (§15.2 W10).
- **X86-63 [M1] `_TLS_MODULE_BASE_`.** As x64.md X-47. Defined by the
  linker when referenced, hidden, at `tls.start`. Its T1 value is
  `T = 0`, and the code-section `TLS_LDO_32` fields added to it are
  `TpRel`. GNU ld and lld write 0 (E4 `leal _TLS_MODULE_BASE_@tlsdesc`
  → `8d 05 00 00 00 00`). mold writes `TpRel(tls.start)` (−128 in E4)
  and keeps `DtpRel` fields. Both run.

## 14. Other sections, the header and segments

- **X86-64 [M1] Header.**
  - `e_machine` = `EM_386` (3), `ELFCLASS32`, `ELFDATA2LSB`, `e_flags`
    = 0.
  - `EI_OSABI` = 0, as x64.md X-49. GNU ld writes `ELFOSABI_GNU` when
    there is an IFUNC (E10: every static glibc link); lld and mold write
    0. The kernel and glibc accept both.
  - `e_entry` = `_start` (layout.md).
- **X86-65 [M1] Base, pages and fill.**
  - `Facts.image_base` = 0x08048000 for `static`. This is GNU ld's
    i386 default and the address i386 tools and users expect; lld uses
    0x400000 and mold 0x200000 (E10). `static-pie` uses 0.
  - `max_page = common_page = 0x1000`: every reference writes `p_align`
    0x1000.
  - `code_fill` 0xCC and `code_nop` 0x90, as x64.md X-50.
  - The default is no separate-code (layout.md L-71). GNU ld defaults
    to separate-code on i386 too (E10: four `PT_LOAD`s, R / R E / R /
    RW; request R-7 notes this).
  - The padding inside `.init` and `.fini` is `code_nop` (layout.md
    L-82). On i386 the crt fragments are contiguous: crti's `.init` is
    0x1b bytes with alignment 4, crtn's is 5 bytes with alignment 1, and
    `.fini` is 0xf + 5. So no padding arises from the crt files under
    any reference (E10).
  - The lea-NOP fill seen in GCC outputs (`2e 8d b4 26 00 00 00 00 8d
    b6 00 00 00 00`) is the assembler's padding inside an input section,
    copied unchanged.
- **X86-66 [M1] `PT_GNU_STACK`.** Flags `PF_R|PF_W` when every input has
  a non-executable `.note.GNU-stack` (all census objects). Otherwise the
  layout.md rule applies. `p_align` = 16, GNU ld's value. lld writes 0
  and mold 1 (E10). Linux's `binfmt_elf` reads only `p_flags` of this
  header.
- **X86-67 [M1] `.eh_frame`.** The pointer encodings are:
  - `0x1b` and `0x9b` (`PC32`, possibly through an indirect word);
  - `0x00` (absolute `udata4`, `R_386_32`), from `-fno-pic` C++
    objects.

  All are ordinary relocations of §6. `.eh_frame_hdr` uses `0x3b`
  (`datarel|sdata4`) for its table, as on x64. An absolute `0x00`
  pointer in a static-pie output is a relocation in a read-only section
  and falls under X86-58.
- **X86-58 [M1] Non-PIC objects in static-pie are refused.** Any record
  that would need a dynamic relocation in a non-writable section of a
  static-pie output is refused. That covers `32` in text or in
  `.eh_frame`, a no-base GOT form, and an unrelaxed `TLS_IE`. The message
  is GNU ld's, which is the phrase users search for (E14 `np`):
  - "relocation in read-only section `.text'" for the record;
  - "read-only segment has dynamic relocations" for the link.

  GNU ld itself only warns on the first and errors on the second. lld
  reports "relocation R_386_32 cannot be used against symbol 'g';
  recompile with -fPIC", and mold "can not be used; recompile with
  -fPIC". mortar's diagnostic carries both GNU phrases and lld's
  "recompile with -fPIC" hint (diag.md `text-relocation`, R-9).
- **X86-59 [M1] Non-alloc relocations and tombstones.** Non-alloc places
  follow arch.md §4.3. The allowed types are `NONE`, `32`, `16`, `8`,
  `PC32`, `PC16`, `PC8`, `TLS_LDO_32` (X86-61), `SIZE32` and `GOTOFF`
  (as x64.md X-53's `GOTOFF64`). `32` against TLS is X86-62. The census
  has only `32` and `TLS_LDO_32` at non-alloc places (§2.2).

  A reference to a discarded COMDAT copy or a dead section gets
  image.md I-47's ELFCLASS32 tombstone:
  - 1 in `.debug_ranges`/`.debug_loc`;
  - all ones (0xffffffff) in `.debug_aranges` (with length 0) and
    `.debug_frame`;
  - 0 elsewhere.

  Measured (E14 `cd`, an inline function in two TUs, `-O0 -g`, DWARF 4
  and 5):
  - lld and mold write 0 in the discarded copy's `DW_AT_low_pc`.
  - GNU ld writes the kept copy's address (0x80497d5 in both CUs), so
    two CUs claim the same code. gdb accepts this. It matches I-47's
    "0 elsewhere" only for lld and mold (§15.1).
- **X86-60 [M1] COMMON.** A COMMON symbol's alignment is its `st_value`
  (4, and 32 for gfortran arrays in the census). It is allocated in
  `.bss` per resolve.md, with no i386-specific rule. i386 has no large
  COMMON section index.
