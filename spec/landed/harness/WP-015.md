# WP-015 — hosted CI green on both lanes

The gate (`cargo xtask ci`, `MORTAR_REQUIRE_TOOLS=1`) passes on the
`ubuntu-24.04-arm` and the `ubuntu-24.04` runners with the same strength:
a test's subject decides its tools, no assertion is weakened for a host,
no test is deleted, and what cannot run on a host is a named, counted
skip that never happens on AArch64. `ci.yml` now runs on a push to
`main`, on pull requests and in the merge queue (`spec/harness.md`
"Hosted CI").

## What landed

- **`scripts/ci-tools.sh` complete.** The lists of every name a test
  looks a tool up by (`TOOLS`, `TRIPLE_TOOLS`, `LLVM_TOOLS`,
  `SETUP_TOOLS`, `FALLBACK_TOOLS`), Debian's own LLVM 19 (`clang-19`,
  `lldb-19`, `lld`), coreutils, and pins for every reference tool:
  binutils 2.44, GCC 14.2, LLVM 22.1.8, Debian LLVM 19.1.7, mold 2.37.1,
  gdb 16.3, elfutils 0.192, qemu 10.0.13.
- **The tool guard** (`mortar_testutil::ci_tools`): `tool` and
  `find_listed_tool` panic on a name the script's lists do not cover, on
  every machine. Several names built at run time (`sha256sum`, `ps`,
  `mkfifo`, `<triple>-ld`, `clang-19`) were missing and are listed now.
- **A test's subject decides its tools** (`mortar_testutil::target::Arch`:
  `gnu`, `tool`, `clang_args`, `sysroot`, `command`, `runner`, `gdb`,
  `is_host`; `MORTAR_TEST_CROSS=1` makes the host foreign too). Every
  test that compiled, linked or ran an AArch64 program with the host's
  default tools now names the AArch64 ones.
- **Named skips** (`mortar_testutil::named_skip`, recorded in
  `$MORTAR_NAMED_SKIPS`, listed and counted by `xtask ci` after `test`).
  AArch64 lane: 0. x86-64 lane: 10 (the gdb and lldb sessions of
  `debuggers.rs`, 8; `gc.rs`'s gdb session; `s8_shared_objects.rs`'s
  AArch64 `libelf.so.1` line).
- **`cargo xtask ci --no-fail-fast`** and the by-hand input
  `no_fail_fast`: every step and test binary runs, failures named last.
- **One static-identical baseline per host**
  (`tests/identical/baseline.on-<host>.tsv`); a failed check prints the
  run's rows of the links that differ, from which the x86-64 one was cut
  (182 links of 43 tests; 99 rows equal to AArch64's, all i386 rows).
- **Link tests**: anomaly defaults can be limited to the cross runtime
  (`cross`, `tests/link/anomalies`); `exit: no-start` (127 natively, 255
  under qemu) for a program the loader cannot start.
- **Triggers** switched; `xtask/tests/hosted_ci.rs` checks them.

## Native and cross runtimes

A host builds its own architecture against Debian's native runtime
(`libc6-dev` 2.41-12+deb13u*, `libstdc++-14-dev` 14.2.0-19) and the
others against the cross packages (2.41-11cross1, 14.2.0-19cross1).
They are other builds: the cross `crt1.o` has a 0x74-byte
`.note.package`, which is mold's A13 on x86-64; static bytes differ, so
the baselines are per host; the cross `libstdc++.a` has other members
and 4-byte (not 32-byte) aligned function sections. A Debian point
release of either moves a baseline.

## debug_gc: what follows `helper` (the proof)

`debug_gc_aarch64`, case `aarch64-gcc-cxx--gdwarf-5-O2`, failed on the
x86-64 lane: gdb's `info line helper` said "ends at ADDR
<_ZNSt9bad_allocD2Ev>" on mortar's output and "<_ZNSt9exceptionC2Ev>"
on GNU ld's. Reproduced on AArch64 with the test's sources, the cross
`libstdc++.a` and cross libc, `--gc-sections`, and the maps of five
linkers:

| linker | input section after `dg_b.o(.text._Z6helperi)` (8 bytes, align 32) |
|---|---|
| GNU ld 2.44 | `libstdc++.a(eh_alloc.o)` `.text._ZNSt9exceptionC2Ev` (0x2c, align 4) |
| lld 19.1.7, 22.1.8 | the same |
| mold 2.37.1 | `libstdc++.a(bad_alloc.o)` `.text._ZNSt9bad_allocD2Ev` (0x3c, align 4) |
| mortar | the same as mold |

The map lines:

```
GNU ld:  .text._Z6helperi  0x400820  0x8 dg_b.o
         .text._ZNSt9exceptionC2Ev  0x400828  0x2c .../libstdc++.a(eh_alloc.o)
lld 22:  23cb80 23cb80 8 32  dg_b.o:(.text._Z6helperi)
         23cb88 23cb88 2c 4  .../libstdc++.a(eh_alloc.o):(.text._ZNSt9exceptionC2Ev)
mold:    0x23f340 8 32  dg_b.o:(.text._Z6helperi)
         0x23f348 60 4  .../libstdc++.a(bad_alloc.o):(.text._ZNSt9bad_allocD2Ev)
mortar:  place 4 8 43cbe0 8      (file 4 dg_b.o, section 8)
         place 5 7 43cbe8 3c     (file 5 libstdc++.a bad_alloc.o, section 7)
```

GNU ld's map lists `eh_alloc.o` as the first member included (for
`dg_a.o`'s `__cxa_allocate_exception`); mortar's numbers `bad_alloc.o`
FileId 5 and `eh_alloc.o` 13. Cause: not a COMDAT keeper (`bad_alloc.o`
has no copy of `_ZNSt9exceptionC5Ev`) and not padding: mortar places
archive members' sections in archive order (load order, `model.md` §2.1;
`layout.md` §9), GNU ld and lld in extraction order. It is by design
(supervisor's ruling): the order does not depend on the history of
resolution. Recorded in `spec/layout.md` §9 and §21 ("Archive members").
With the native `libstdc++.a` the order differs as well, but its
function sections are 32-byte aligned, so padding follows `helper` in
both outputs and gdb names no neighbour.

## Follow-ups

- The `.eh_frame` `$d` gap on the cross runtime (13; bound 16) is
  unproven. Suspected: COMDAT keeper differences leave different input
  `.eh_frame` sections without records (S-50, S-76). The proof: derive
  the expected gap from lld's `-Map`.
- `mortar_plumb` should judge lld's `__CortexA53843419_*` symbols inside
  a recognised 843419 patch region instead of the corpus test allowing
  them (not done here: WP-050 owned `crates/mortar_plumb/src`).
- mortar's x86-64 static output differs from GNU ld's in places
  (`.tdata` alignment 8 against 16, `.plt` entry 16 against 8, the sizes
  of `.rodata` and `.eh_frame`), seen in links of the x86-64 lane; for
  the x86-64 packages (WP-048, WP-055).
- `buildpack-deps:trixie-scm` is not pinned by digest: a new image or a
  Debian point release can move the pins (a red set-up step names the
  tool) and the baselines.
