# WP-014 — hosted CI

`spec/harness.md` gains "Hosted CI": GitHub Actions runs `cargo xtask ci`
on an AArch64 and an x86-64 runner, in a Debian 13 container with the
reference tools of `scripts/ci-tools.sh`.

## What landed

- `.github/workflows/ci.yml` (entry: `workflow_dispatch` only while the
  repository is private; `push` to `main`, `pull_request` and
  `merge_group` commented out, to be enabled when it is public),
  `.github/workflows/ci-lane.yml` (reusable: one `gate` job per
  architecture), `.github/actions/mortar-ci` (set-up: the tools, Rust
  1.95.0, the cargo cache, the jobserver pool). Fan-in checks `check` and
  `check-x86_64`. Structure, concurrency rule, permissions and caching as
  hod's and kiln's.
- `scripts/ci-tools.sh`: the one list of the gate's reference tools
  (install, `--check`, `--list`), with the pinned versions (binutils 2.44,
  GCC 14.2, LLVM 22.1.8, mold 2.37.1).
- `scripts/ci-summary.py`: the link tests' results file as Markdown, for
  the job summary.
- `xtask/tests/hosted_ci.rs`: the lane runs the gate as the development
  machine does; this machine has every tool of the list.

## Departures from hod and kiln

- One job per lane, not one per step: the gate takes minutes, and a
  private repository pays every job's set-up and rounds its minutes up.
- `buildpack-deps:trixie-scm`, not `buildpack-deps:trixie`: the script
  corpus test reads every text library of the machine, so the hosted
  machine should not carry the full image's `-dev` libraries; and the
  tool list is then complete on its own, also in a bare Debian 13
  container.
- The jobserver pool runs in the job (hod's and kiln's hosted jobs have
  none), so the gate runs under the same pool rules as on the
  development machine.
- The tool versions are checked, not only the tools' presence.

## The x86-64 host

The code base had only run on an AArch64 host. What depends on the host,
by reading:

- `xtask/src/linktest/target.rs`: every name, system root, library
  directory and runner is a function of the host (`Arch::host()`); on an
  x86-64 host x86-64 is native and unprefixed, AArch64 and i386 are cross
  (`aarch64-linux-gnu-*`, `qemu-aarch64 -L /usr/aarch64-linux-gnu`). Its
  tests pass an explicit host. No change.
- `crates/mortar_elf/tests/tools.rs` (`find_gcc`): the prefixed name
  first, which Debian gives the host's own compilers too. Only its comment
  changed (it said the native compiler is AArch64's).
- `crates/mortar_script/tests/corpus.rs`: the ten known text libraries
  were the AArch64 host's paths, which an x86-64 host does not have, a
  failure under `MORTAR_REQUIRE_TOOLS=1`. Now `KNOWN_ON_AARCH64` (the old
  table, unchanged) and `KNOWN_ON_X86_64`, chosen by `target_arch`. The
  x86-64 table is written by analogy with Debian's packages, not observed.
- `crates/mortar_script/tests/differential.rs` (`check_row`): lld refuses
  an input of another machine than `OUTPUT_FORMAT` names, and `e.o` is
  the host's, so on an x86-64 host the recorded lld result of
  `OUTPUT_FORMAT(elf64-littleaarch64, elf64-bigaarch64,
  elf64-littleaarch64)` does not hold. Off an AArch64 host, lld does not
  witness a row that names `aarch64`. Measured here by running the test
  with the x86-64 cross `as`, `ar` and `ld.bfd` in place of the host's:
  exactly that row disagreed, and with the rule applied the test passes.
- `crates/mortar_script/tests/hostile.rs`: reads AArch64-host paths when
  they exist; seeds only, no change needed.

**Expected x86-64-host failures**, to read the first hosted x86-64 run
against (none could be run here):

1. `crates/mortar_script/tests/corpus.rs` `KNOWN_ON_X86_64`: the paths
   and the structure of the AArch64 cross C library's scripts (`libc.so`,
   `libm.so`, `libm.a` in `/usr/aarch64-linux-gnu/lib`, the loader in
   `lib`) and of the native x86-64 ones (`/usr/lib/x86_64-linux-gnu`, the
   loader `/lib64/ld-linux-x86-64.so.2`) are inferred; a mismatch fails
   `system_text_libraries` with the path and what was read. Correct the
   table from the message.
2. `crates/mortar_script/tests/differential.rs`
   `acceptance_matches_the_reference_linkers`: the native x86-64 GNU ld
   is built with more BFD targets than the cross `x86_64-linux-gnu-ld`
   the simulation used; a row whose acceptance depends on a target
   (`OUTPUT_FORMAT`, `TARGET`, `OUTPUT_ARCH` rows) could differ.
3. `scripts/ci-tools.sh` on `amd64`: the package names are Debian 13's
   (`gcc-i686-linux-gnu`, `gfortran-aarch64-linux-gnu`,
   `libc6-dev-arm64-cross`, ...) and were checked only on `arm64`; a name
   that does not exist there fails the set-up step with apt's message.
4. `crates/mortar_elf/tests/tools.rs` `s4_3_compiled_*` with Clang for
   `--target=aarch64-linux-gnu`: Clang finds the AArch64 GCC installation
   under `/usr/lib/gcc-cross` as it finds the x86-64 one on AArch64; not
   run.
5. The link-test corpus with AArch64 under `qemu-aarch64`
   (`reloc/aarch64-veneer`, `lang/fortran-c` with the cross `gfortran`,
   `lang/clang-mixed`): the mirror of what runs on AArch64; not run.
6. Timing on a 2- or 4-processor runner: the tests' bounds are hang
   guards, not measurements (`spec/harness.md` "Time in these tests"),
   so none is expected, but none has run on so small a machine.

## Evidence

- `MORTAR_REQUIRE_TOOLS=1 cargo xtask ci --quick` and the full
  `MORTAR_REQUIRE_TOOLS=1 cargo xtask ci`: `[ci] ok` (the full gate 1 min
  53 s on the development machine, the link tests 23 s: 372 records, 276
  PASS, 96 XFAIL).
- `scripts/ci-tools.sh --check`: every tool, the pinned versions.
- The workflow files: checked by reading against GitHub Actions' rules
  for reusable workflows and composite actions (no YAML parser on the
  development machine). They have not run.
