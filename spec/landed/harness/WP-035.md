## Item 1 — the bench verifies what it times

Per workload, before its timed runs, `cargo xtask bench` makes one
untimed mortar link of the same response file with `--mortar-map` and
runs `cargo xtask plumb` on it as a child process (the verifier's memory
never sits in the process that times; `--fix-cortex-a53-843419` as the
response file says). The verdict:

- **clean**: the golden `output_hash` is the verified output's hash; a
  timed output with another hash fails mortar's rows ("the timed output
  is not the verified output");
- **findings**: mortar's rows of that workload are `failed` with the
  count by rule and the first findings, the output and map are kept, the
  summary says FINDINGS, and the run exits 1 ("the verifier finds
  mortar's output WRONG"); `--update-baseline` records nothing;
- **not judged** (`machine`, `pie-or-shared`, `dynamic`, `relocatable`),
  **refused** (mortar's first line, by name) or **failed to link**: no
  `output_hash` is recorded for mortar.

The end of every run names each workload in one of those groups.
`--no-verify` turns it off, says so in the output and in the results
(`verify = off`), records no output hash, and is refused with
`--update-baseline`.

Today mortar links 2 of the bench's 12 measured workloads:
`hello-c-static` and `hello-cxx-static`, both verified clean. `hello-c`
and every other workload linked by `gcc` without `-static` are refused by
name (`-dynamic-linker`, `-pie`), so the verifier's stage-1 limit (static
non-PIE) costs nothing today.

**Timing.** The verifier run precedes the timed rounds and is out of the
figures. Medians (ms) of four alternating pairs, `--runs 10`,
`hello-c-static` and `hello-cxx-static`, a loaded shared machine:

| workload | threads | verified (4 runs) | `--no-verify` (4 runs) | median v / nv |
|---|---|---|---|---|
| hello-c-static | default | 44.1 44.5 52.4 48.5 | 64.3 52.8 44.8 45.2 | 46.5 / 49.0 |
| hello-c-static | 1 | 20.0 19.1 20.7 22.4 | 24.1 20.1 18.8 21.7 | 20.4 / 20.9 |
| hello-cxx-static | default | 76.9 67.6 74.5 74.3 | 90.4 65.4 70.1 68.6 | 74.4 / 69.4 |
| hello-cxx-static | 1 | 47.5 42.5 47.5 50.2 | 52.7 44.1 43.0 48.9 | 47.5 / 46.5 |

No difference beyond the machine's noise. A first version ran the
verifier in the bench's own process; its medians were 5–10% higher on
both workloads in six pairs, hence the child process.

reverted in scratch to the old one-window-per-0xFF8 code, release mortar
built from it, and the bench run on a static twin of `synthetic-sections`

## Item 3 — the audit

The table is in `docs/VALIDATION.md` ("Where mortar writes an output, and
who judges it"). Closed here:

- `cargo xtask bench` (item 1);
- `pipeline.rs`: `mortar()` judges every output (the determinism runs
  judge the first and compare the rest byte for byte);
- `options.rs`: every link of the option audit (`Cx::mortar`), one
  exception below;
- `sysroot.rs`, `x64.rs` determinism, `image.rs`
  (`i40_compares_with_gnu_ld`), `deferred.rs` (the tombstone test, with
  the map rendered from the link);
- `cargo xtask mason programs` and the libc++ lane's `ld` shim:
  they passed `-Map=`, which since WP-027e is GNU's text map, which the
  verifier cannot read; now `--mortar-map`.

**A finding on a mortar output.** `options.rs`'s
`--build-id=0x0123456789abcdef` link gets B1 ("the 8-byte build id is not
I-72's function of the output"). Not a mislink: the id is the user's, and
mortar's map does not yet state the style `given` (`spec/plumb.md` §6.7
names the writer). The test checks that the findings are exactly B1, so
the exception fails once the map catches up. No other finding on any
mortar output.

## Item 4 — the verifier's hasher

`crates/mortar_plumb/src/hasher.rs` (60 lines): a fixed multiply-rotate
hash over eight-byte words for every `HashMap`/`HashSet` of the crate
(mechanical: `HashMap::new()` → `default()`). Byte-wise FNV-1a was tried
first and was slower than `SipHash` on long C++ names. `cargo xtask plumb`
on static protoc (built with mortar from the `cxx-medium` objects; clean,
nine runs each; RSS 176 MB, unchanged):

| hasher | user s (median) | wall s (median) |
|---|---|---|
| `SipHash` (before) | 0.20 | 0.28 |
| FNV-1a, bytes | 0.23 | 0.30 |
| words (landed) | 0.18 | 0.25 |

The verifier's output is identical.

## Item 5 — the gate's cost

The closed holes add verifier runs to six test binaries of
`crates/mortar` (`pipeline`, `options`, `sysroot`, `x64`, `image`,
`deferred`); nothing else in `cargo xtask ci --quick` changed. Those six,
at 426d140 and at this package, both target directories on the same
file system, alternating, `MORTAR_REQUIRE_TOOLS=1`, a shared machine at
load 7–15:

| | wall s | user s (CPU, the tests run in parallel) |
|---|---|---|
| 426d140 | 30.5 21.4 20.8 · 37.6 63.8 29.9 | 71.2 78.9 74.3 |
| WP-035 | 21.0 19.5 19.9 · 24.9 86.1 39.4 | 64.1 83.5 78.0 |

(The first three wall pairs were run with `mortar_plumb` optimised in the
dev profile, an experiment not kept.) The cost is about 4 s of CPU
summed over parallel tests (median 78.0 against 74.3); in wall time it
is below the machine's noise. The largest verified outputs are the
far-call tests' (a 128 MiB gap).

An observation for the gate's time, not this package's: the tests'
scratch is `CARGO_TARGET_TMPDIR`, under `.build/` on this machine's
virtiofs workspace mount. The same `pipeline` binaries run from a target
directory in `/tmp` were 2–3× faster on the far-call tests.

## Follow-ups

- **The bench must link something mortar links.** 10 of the 12
  workloads are `-pie` or dynamic (`bench/workloads/manifest`, e.g. lines
  34 and 52), refused by mortar today, so the bench times and verifies
  mortar on two hello-worlds. Add static twins (as `hello-*-static`) of
  `cxx-medium`, `synthetic-*`, or wait for PIE. Performance package.
- **The map's build-id style** (`crates/mortar_image/src/link.rs`'s
  synthetic chunks, `spec/plumb.md` §6.7): then `options.rs`'s exception
  (`crates/mortar/tests/options.rs:329`) goes. Image package.
- **`xtask plumb --inputs-from`** (`xtask/src/plumb.rs:104`
  `response_entries`) takes only the response file's paths and misses
  `-l` archives: 955 spurious findings on `hello-c-static`. The bench
  does not use it (the map names the inputs).
- **`mason libcxx`** judges only with `--plumb` (thousands of links); a
  sample by default would close the lane.
- **Performance packages' byte-identity scripts** are not in the
  repository and not judged; `docs/VALIDATION.md` asks them to state the
  verifier's verdict or measure through the bench.
- **Default threads on small links**: on this machine mortar at default
  threads took 2× its one-thread time on `hello-c-static` (46 vs 20 ms):
  for the performance packages (WP-032e's `par` notes).
