# WP-081: the large real link (LLVM/clang 19.1.7, `-g` and split DWARF)

Record of WP-081. It covers:
- the bench's `ninja` kind and the workloads `cxx-large-g`,
  `cxx-large-g-opt` and `cxx-large-split` (`spec/harness.md` "bench",
  "Large workloads");
- the archive-line workloads `synthetic-line-{1000,3000}[-group]`;
- what mortar does on them: correctness first, then the numbers, then
  what the incremental design needs.

Measured on the AArch64 development container: 12 CPUs, 17 GB, a cgroup
shared with the other agents' packages. mortar is the release build of
`ce33303`; this branch changes no mortar crate. The references are GNU ld
2.44, LLD 22.1.8 (`ld.lld-22`), mold 2.37.1 (`--no-fork`), gdb 16.3,
lldb 19.1.7 and llvm-dwarfdump 19.

**The host was never quiet.** The brief's rule is a 1-minute load under
2. The load was 8 to 15 for the whole package, with other packages'
builds and gates running beside it. **Every number below is
provisional**: medians of interleaved runs, with the load beside them,
and the page cache warm (each series follows a link of the same inputs).
The correctness results do not depend on the load.

## 1. The workload

- **Source**: `llvm-project-19.1.7.src.tar.xz`, SHA-256
  `82401fea7b79d0078043f7598b835284d6650a75b93e64b6f761ea7b63097501`,
  fetched from LLVM's GitHub release, unpacked once into
  `<work>/src/82401fea7b79d007/`. 19.1.7 is the container's own
  clang/lld/lldb version.
- **Build** (`bench/workloads/large/llvm-build.sh <work> g|split <jobs>`):
  - CMake + Ninja, `RelWithDebInfo` (`-O2 -g`; LLVM adds
    `-ffunction-sections -fdata-sections` and `--gc-sections`);
  - `LLVM_ENABLE_PROJECTS=clang`, `LLVM_TARGETS_TO_BUILD=AArch64`, no
    assertions, `-static`;
  - zlib, zstd, libxml2, terminfo, libedit and libpfm off, so the static
    link needs only glibc and libstdc++;
  - `LLVM_APPEND_VC_REV=OFF`;
  - thin archives while building (`ar DqcT`);
  - no `LLVM_USE_LINKER`. CMake's lld probe would otherwise add lld-only
    flags to the captured line, which GNU ld rejects.
  - `split` adds `LLVM_USE_SPLIT_DWARF=ON`.
- **What the script builds**: every input of `bin/clang-19`, `bin/opt`
  and `bin/llvm-lto2` (`ninja -t inputs`), plus the test tools (FileCheck,
  not, count, split-file, llvm-config, clang-resource-headers). It links
  none of the large binaries.
- **How long**: `ninja -j4` (the coordinator's cap) under `nice -n 10`.
  The `-g` tree took several hours, with restarts and a resumed build
  (the log is kept). The split tree took 35 min (2,364 compiles, 15:23 to
  15:58Z).
- **The capture**: as `harness.md` "Large workloads" says. The `-g`
  tree's 117 inputs became `<work>/workloads/cxx-large-g/inputs/`, the
  thin archives rewritten as regular ones. opt shares 52 of them. The
  split tree's inputs went to `cxx-large-split/inputs/`.
- **Why opt and not llvm-lto2**: they link the same 52 archives, except
  `LLVMLTO` in place of `LLVMOptDriver`. opt is what check-llvm's tests
  run.

## 2. Correct first

### 2.1 The links

Every link succeeded:
- mortar, GNU ld, lld and mold on clang `-g`, opt `-g` and clang split;
- mortar in plain mode and in `--incremental=full`.

mortar refused nothing. Like GNU ld, it warns that `dlopen`,
`getpwuid_r` and `getpwnam_r` in a static link need the shared libc at
run time.

The findings were triaged. **None is a defect in mortar's output.**
- **E4 ×49 + I1 + P-I1 ×32** (any linker, with `--inputs-from` only).
  `libm.a` is a linker script, `GROUP ( libm-2.41.a libmvec.a )`.
  `--inputs-from` takes the response file's words and does not follow
  the script. The members of `libm-2.41.a` (feclearexcept, fetestexcept,
  logl, …) are therefore not inputs: I1 names the archive, E4 their 49
  FDEs, P-I1 the 32 ranges of their code and tables. Without
  `--inputs-from` the map names the archive, and mortar's outputs are
  clean. This is a verifier limit with a request below (§6).
- **Y3 (GNU ld)**: `__TMC_END__`, a label of an empty section.
- **E5 (lld)**: zero-length FDEs, each sharing its initial location with
  the next function's FDE (`llvm::get_cpus` and
  `get_thread_affinity_mask` at one address). lld's `.eh_frame_hdr`
  keeps one entry per address.
- **mold**:
  - E5: `fde_count` is 0x10aaa against 0x109ff live FDEs; the +171 are
    the neutralised FDEs of dropped functions. The table is not sorted.
  - S8 and Y1: the static IFUNC symbols (`memcpy`, `memchr`, `strlen`,
    …) get values before `.text`, which is neither their resolver nor
    an IPLT entry.
  - Y5: `_TLS_MODULE_BASE_` is the TLS segment's end, not 0.

### 2.3 The linked clang at work

**Programs.** `bench/workloads/large/programs.sh CLANG OUT SRC BUILD N`:
- compiles four programs (sieve.c, templates.cc, containers.cc,
  exceptions.cc), each at `-O2 -g` and at `-O2`;
- links them dynamic and static and runs them;
- compiles the first N sources (in name order) of `llvm/lib/Support`,
  `llvm/lib/IR` and `clang/lib/Sema` at `-O2 -g`;
- writes each object's SHA-256 and each program's exit status and output
  hash.

Every clang runs from one path, `/tmp/mortar-wp081-1/T/bin/clang-19`
(hard-linked in turn), because the objects' debug information names the
resource directory.

**Debugger sessions.** `bench/workloads/large/debugger.sh CLANG OUT` runs
`clang -cc1 -fsyntax-only` on templates.cc under gdb and under lldb, with
a breakpoint on
`clang::TreeTransform<(anonymous namespace)::TemplateInstantiator>::TransformType`
(39 locations). The session takes `bt 6` / `thread backtrace -c 6`, the
arguments, frame 1's locals (`Instantiator`), `ptype clang::QualType` and
`sizeof(clang::Sema)`.
- The transcripts are 168 lines (gdb) and 217 (lldb), normalised:
  addresses are written `0x?` and pids and paths are replaced.
- mortar against GNU ld: **one line differs in each**, `-g` and split
  alike. In gdb it is `Instantiator`'s `NumEntries` and `Loc`; in lldb it
  is frame 2's `Entity` pointer.
- A second run of the GNU ld binary differs from the first in exactly
  that line. The container may not disable ASLR (gdb warns; lldb needs
  `target.disable-aslr false`), so values derived from pointers change
  from run to run.
- Wall and peak, `-g`: gdb 5.2 s / 2.23 GB (mortar) and 6.5 s / 2.25 GB
  (GNU ld); lldb 5.3 s / 3.06 GB and 5.2 s / 3.06 GB.
- Split: gdb 19.6 s / 3.12 GB and 19.1 s / 3.13 GB; lldb 5.7 s / 3.69 GB
  and 5.3 s / 3.68 GB.
- The split binaries find their `.dwo` files in the tree (locals print).

**Stop condition**: not met. No mortar-linked binary behaved differently
from the reference, and the verifier found nothing in mortar's output.

**Dirty windows**: 50 windows, 51,950,504 B refilled, 49 jobs. By kind:
header 1, the changed file 9, `.eh_frame` 10, `.symtab`/`.strtab` 30,
build id 1. (g10x: 170 windows.)

**The state's load time** is phase 15: 619-779 ms for 210 MB here, against
124 ms for 82 MB on g10x.

**Which parts scale how** (clang `-g` against g10x):
- **The state** is 2.6× larger and takes 5× longer to read.
- **Stamps** take 11× longer: 2,358 inputs, and virtiofs `stat`.
- **The replay's translation** is 2.3× slower. It grows with the
  sections and relocations of the line (541 k sections, 20 M
  relocations). The keys are 6.7× cheaper: real C++ has fewer, larger
  symbols per section than g10x's uniform C.
- **The dirty windows are fewer** (50 against 170): clang has
  `.eh_frame_hdr`, and its `.symtab` is smaller than g10x's.
- **The input phase reads every file**. On virtiofs it is the largest
  single cost after the replay.
- **The test path's update costs as much as a full link here**
  (0.95×). §1.5's rule asks at most 1/3 on the large workload. As on
  g10x, the cost is the O(everything) front and replay, which the
  design's O(change) front (WP-064) removes. This record does not apply
  the rule (the host was loaded).

`synthetic-line-1000` and `synthetic-line-3000` use the `line` shape
(`spec/harness.md` "Generated workloads"), sized by the census:
- 25 members an archive (clang: 2,251 members in 88 archives);
- 64 functions a member (clang: 69 global definitions a member);
- seven members in eight needed (clang: 1,949 of 2,251 loaded, 0.87).

Each needed member calls into the next archive and into one further on,
so one pass over the line in order loads them all. The `-group` twins
put every archive in one `--start-group`. Inputs: 365.8 MiB and 1.52 M
symbols (1000 archives); 1,080.6 MiB and 4.56 M symbols (3000).

`cargo xtask bench --runs 3`: medians, with calibration NOISY (326 ms
before, 62 ms after) and load around 10. **Provisional.**

| workload | GNU ld | lld default / 1 | mold default / 1 | mortar default / 1 | mortar RSS / mold RSS |
|---|---|---|---|---|---|
| line-1000 | 30,730 ms, 1,879 MiB | 1,701 / 1,835 ms | 1,302 / 2,611 ms | 1,325 / 3,006 ms | 953 / 836 MiB |
| line-1000-group | 18,424 ms | 1,417 / 1,502 | 777 / 2,205 | 1,093 / 3,170 | 962 / 836 |
| line-3000 | 63,004 ms, 5,652 MiB | 5,389 / 4,804 | 2,378 / 7,440 | 4,004 / 10,131 | 2,837 / 2,491 |
| line-3000-group | 76,262 ms | 5,050 / 4,742 | 2,654 / 8,441 | 6,535 / 9,888 | 2,836 / 2,492 |

What these show:
- **Three times the archives costs mortar three times the time.** At
  one thread, 3,006 ms becomes 10,131 ms (3.4×). At the default threads,
  1,325 ms becomes 4,004 ms (3.0×). The inputs grow 2.95×. No term
  superlinear in the number of archives shows at this size.
- **`--start-group` costs mortar nothing it can measure at 1000**
  (1,093 against 1,325 ms). At 3000 the group is 6,535 ms against
  4,004, but within one configuration the range is 3,762-6,541 ms, so
  this is not separable from the noise.
- **GNU ld** takes 23-29× mold's time and 2.25× its memory.
- All four mortar outputs verify clean.
- The line programs are not run: each needed member calls two further
  on, so a run makes exponentially many calls.

## 6. Findings and requests (not this package's to fix)

1. **plumb `--inputs-from` does not follow linker-script libraries**
   (`libm.a` = `GROUP ( libm-2.41.a libmvec.a )`). It gives E4/I1/P-I1
   on every linker's static C++ link against libm. Request to
   `mortar_plumb`: resolve a `-l`/path that is a linker script the way
   the link did (the map names the archives it opened).
2. **The verifier's memory on the large link.** Plumb peaks at 9.2 GB on
   opt `-g` (531 MB out), and above 14.6 GB on clang `-g` (1.13 GB out),
   where it was OOM-killed. `--equiv` needs more than 12.2 GB on opt `-g`.
   The bench verifies every mortar output it measures, so `cxx-large-g`
   cannot be a bench row on a 17 GB host until this falls. Request to
   `mortar_plumb`: bound the resident inputs (stream members), or give
   `plumb` a memory budget. Split DWARF stays in reach (2.2 GB).
3. **`plumb --equiv` reads the inputs relative to the cwd**, and gives
   no warning when none of the map's paths resolve. It then reports
   thousands of findings on each side. Request: a usage error when no
   input resolves, or resolve them against the map's own `cwd` record.
4. **`--equiv`'s time**: 2,600 s of a single thread on opt `-g` even with
   no inputs. The plain verifier takes 15.8 s on the same output.
5. **llvm-dwarfdump on tombstoned COMDAT copies.** mortar's output gives
   the same errors as mold's (and lld's). GNU ld's kept-copy resolution
   gives about 1/17 of them, but it has its own `.debug_str_offsets`
   errors. Nothing to change. Tuck's debugger index should expect these
   zero-address DIEs.
