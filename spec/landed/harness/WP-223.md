# WP-223 (H-1): the judge of an incremental update (landed)

Branch `wp/223-incr-judge`, base 294101b1. A harness package: no linker
crate edited, `crates/mortar_plumb` not read. The rules are
`spec/incr.md` IN-75, IN-75a, IN-78, IN-79 and `spec/harness.md`
"incr-update" (made exact here).

## Rulings needed

1. **A fifth elflint pattern.** Every C++ program that throws, linked
   statically, carries libstdc++'s SystemTap probes, and `eu-elflint
   --gnu-ld` says of each (GNU ld's output of the same objects alike):
   `section [23] '.note.stapsdt': unknown object file note type 3 with
   owner name 'stapsdt' at offset 72` (three lines on
   `eh_frame_overflow_then_edit_unchanged_file`, AArch64, GCC and kiln
   alike; x86-64's output passes: elfutils knows the note there or the
   x86-64 libstdc++ has none, not looked into). It is not one
   of the four, so the judge fails that scenario at its first link on
   AArch64 (the brief: a finding, never an addition).
   Proposed: a fifth allow pattern held to its meaning (a note of
   section `.note.stapsdt`, owner `stapsdt`, type 3).
2. **The full matrix in the gate.** harness.md's planned text put the
   lane in the full gate. It is not there yet: (1) fails it, and the
   kiln configurations need kiln and hod on the hosted runners
   (`MORTAR_REQUIRE_TOOLS=1` fails a configuration that cannot run).
   The gate runs `--quick` (quick and full gate alike, as L10's smoke).
3. **prev_output is caught by `verify`**, not by run or equiv, as the
   brief allowed: the old map describes the inputs' old bytes and plumb
   reads the inputs on disk. Run would refuse it too.

## The judge (`tests/l10/judge.py`)

One function, `judge_step(tools, x, f, base, new, hop=None)`: with
`hop=None` it is L10's five checks, unchanged (one change on that path:
`run_program` reports an `OSError` as `cannot run: ...` instead of
raising). With a `Hop` it runs IN-79's checks in this order: `exit`,
`stderr`, `dirty`, `elflint`, `verify`, `equiv`, `run`, `oracle`,
`state`, `duty` (table in harness.md). `l10 --quick` and `l10
--self-test` verdicts are unchanged (Gate).

- **stderr, what is normalised and why.** Only X's lines that begin
  with `incremental:` are dropped: the report line, which a full link
  does not print. Nothing else: F links the same file names in its own
  directory, so every `>>> referenced by` line agrees byte for byte; any
  path or ordering difference is a difference. With `--fatal-warnings`
  both links exit 1; `exit` compares the status and that the failed X
  left the state it found (its sha256 before and after, IN-48).
- **elflint before verify.** I looked for a corruption that elflint
  refuses and `plumb verify` accepts, so that the elflint subject is
  caught by elflint alone. I tried 30 on a kept output: `.comment`
  flags, entsize, link, align, addr and its last NUL; a local's value or
  size; swapped local names; `.symtab` info and align; a hidden or
  nameless or misplaced `STT_FILE` symbol; note align and namesz;
  EI_PAD, e_flags, the ABI version; a bit of `.text`, `.got`,
  `.init_array`, `.fini_array`, `.data.rel.ro`. verify refused every one
  of them. Only an OSABI byte passed both. So elflint runs first (the
  outside tool speaks first), and the subject `elflint_bad` (EI_PAD set)
  is caught by it. Note that verify is the stronger of the two.
- **The four allow patterns** are held to what they say: an `invalid
  type` or `invalid symbol index` of `.rela.plt`/`.rel.plt` record i
  passes only when record i's type is the machine's `R_*_IRELATIVE`
  (183: 1032, 62: 37, 3: 42); `__ehdr_start` by name; `unknown bit set
  in st_other` only on EM_AARCH64.
- **dirty** (IN-75): the ranges are read from `MORTAR_INCR_DIRTY`'s
  file. They must be sorted and disjoint and lie inside the file, and
  every differing byte (bytes past the previous end included) must be
  in a range. A full link gives `n/a (full link: <reason>)`, and the
  floor gives `n/a (full link: the floor ...)`. A missing file after
  `incremental: update` is a FAIL.
- **(d)**:
  - `state` puts C(U) at `h<i>/capture.mortar-state` and prints the
    first differing row as `<table> row <key>: <what> (and n more
    rows)`.
  - `duty` holds the comparison to `tests/incr-update/duty.py`, which is
    IN-78's derived table as DATA. Each row has the id, the spec's cause
    cell verbatim, the names it puts in backticks, and the tables it
    changes.
  - A unit test checks the causes, the named tables and IN-18e's kinds
    against spec/incr.md.
  - Both stay behind `CanonStub` until U-2 lands. The stub reports
    `n/a (d) not run (canon: U-2)` and `P_U: decision records not read`
    (`placement_of_map`).

## What the live (d) needs (not guessed: what the stub stands for)

1. From U-2: `canon` and `compare` of `mortar_incr::state5` behind a
   command the lane can call, either a test binary or `incr_state
   canon`. It takes two state files and prints the differing rows one
   per line as table, row key and what differs. `[]` means equal.
   `CanonStub` is replaced by a class with `live = True` whose
   `compare(a, b, p_u)` runs that command.
2. From V-1 (WP-222) and U-6: `P_U`, the update's decision records read
   from its map into a `LayoutRows`. `placement_of_map` returns it, or
   why not. Until both exist, `state` passes with "decision rows not
   compared".
3. The replay (IN-78 as amended): IN-61's replay entry, given `P_U`'s
   rows and run by a test binary the lane calls, writes C(U) to
   `h<i>/capture.mortar-state` and writes no output.
4. S, for `duty`: the lane copies the state before X's link into
   `Hop.state_prev`. It does so only when canon is live, since a copy
   costs a state-sized write per hop.
5. The update's causes: `Hop.causes` (`None`: any cause). The report
   would have to name them, for instance `delta cause <id>` lines
   (REQUEST to the supervisor; the ids are `duty.py`'s).

## Findings for the spec

- IN-18e's tables that no cause of IN-78's derived table changes:
  `FILE_INDEX`, `ODR_CLASSES`, `PROBES`, `STRINGS`. A difference in one
  of them fails `duty` as "no cause names it". Either these tables never
  change in an update, or the table lacks rows.
- IN-78's second row ("a gone or no longer extracted file") names only
  `LAZY` in backticks. Its tables ("its ranges gone, its key-keyed rows
  deleted") are classes, and `duty.py` spells them out from IN-18e's
  class table (`WORDS`).
- On i386 the PLT relocation section is `.rel.plt`. harness.md's
  pattern names `.rela.plt`, and the judge accepts both.

## How H-2 and U-10 call the judge

Both use the same `judge_step(..., hop=Hop(prev, ranges, state,
state_before, state_prev, scratch, canon, causes))`:

- H-2's crash series builds a `Hop` for the link after each crash point.
- U-10's L10 runs pass a `Hop` to get IN-79's checks on L10's steps.

The checks that need nothing from the hop (`verify`, `equiv`, `run`,
`oracle`) are L10's code.

## The oracle (`tests/incr-oracle/oracle.py`)

- WP-067 §7.2's two patches are applied: thin archives (`thin_member`)
  and member identity by name (`Link.by_name`, `real_offset`). This
  removes L10's adapters from judge.py.
- Patch 2 is refined. The ordinal "among the members of that name" now
  counts the archive's headers (`archive_members`), not the members the
  link extracted, which was the adapter's reading. When the first of
  two `m.o` stops being extracted (`w_archive_a1`), the second keeps
  ordinal 1. Under the old reading the oracle saw a changed file and
  asked for its units ("MISS unit of a changed file").

## The lane

- The scenarios, the wrong subjects, the self-test and `--quick` are
  described in harness.md "incr-update" and `tests/incr-update/README`.
- `xtask/src/incr_update.rs` builds the testhooks mortar into
  `<target>/testhooks`: 33.6 MB binary, 161 MB directory, built with
  `CARGO_PROFILE_DEV_DEBUG=0`.
- One lane fix that matters elsewhere: the hop directories get COPIES
  of the inputs, not hard links. On the workspace's virtiofs, a hard
  link whose other name was just renamed over opened ENOENT although
  `listdir` showed it. This was reproduced at `-j 1` and fixed by
  copying. judge.py's old one-retry note for the oracle ("seen once on
  virtiofs under load") is probably this.

Shapes without a form:

- C with `-fcommon` (three scenarios) and the assembly ports (fourteen)
  are GCC only: kiln compiles C++ only.
- `s2c_gcc_strings` is gcc `-O2` by definition.
- `s3_local_permute` has no i386 form: its GOT load needs a PIC base
  register (parked, per the ruling).
- `w_archive_a3`'s thin members are `d1m.o` and `d2m.o`, not two `m.o`,
  because the lane installs a thin archive's members in one directory.
- `w11`'s edited copy of `h` is weak, so that the edited link has one
  strong `h`. Without that, GNU ld and mortar both refuse it as a
  duplicate definition.

The 2 FAILs are ruling 1 (`eh_frame_overflow_then_edit_unchanged_file`

warning_mktemp_fatal's hops 1-3 on four configurations: two failed links,

20 PASS, 5 s warm, so it joins `ci --quick` (after L10's smoke).
`--self-test`: 28 units ok, 12 wrong subjects each found by its check at

`oracle`).

## Not verified

- No update exists: every hop of every scenario is a full link (reason
  `no-state` or `small-output`). `dirty`, `state` and `duty` have
  therefore only ever been `n/a` on real links. Their logic is exercised
  by the units and by the wrong subjects, which claim an update.
- (d) has never run against a real canon: it is a stub plus a fake
  comparator in the units.
- i386: run once for free (all pass), not required and not in the gate (ruling).
- `--crash` (H-2) does not exist yet.
- L10's verdicts were not compared line by line with a run of the base
  tree: they pass, with the same shape as before (only fall-backs).
