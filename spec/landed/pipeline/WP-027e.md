## 1. Tombstones

### What the references write (static AArch64, 20 configurations)

Fields that refer to a discarded COMDAT copy, by section, in an ELFCLASS64
output (`exp.py`: g++ and clang++ 14/19/22, `-gdwarf-4`/`-gdwarf-5`,
`-O0`/`-O2`, on AArch64, x86-64 and i386):

| section | GNU ld 2.44 | lld 19, lld 22 | mold 2.37 | mortar before | mortar now |
|---|---|---|---|---|---|
| `.debug_info` | kept copy's address | 0 | 0 | all ones | all ones |
| `.debug_line` | kept copy's address | 0 | 0 | all ones | all ones |
| `.debug_aranges` | kept copy's address | 0 | 0 | all ones, length 0 | all ones, length 0 |
| `.debug_ranges`, `.debug_loc` | kept copy's address | 1 | 1 | 1 | 1 |
| `.debug_rnglists`, `.debug_loclists` | kept copy's address | 0 | 0 | all ones | **0** |
| `.debug_addr` (Clang DWARF 5) | kept copy's address | 0 | 0 | all ones | **0** |

### The consumer matrix

Consumers: gdb 16 (scripted break, step, finish, backtrace, `info line`;
its complaints), lldb 19 (breakpoint counts, `image lookup`),
`llvm-dwarfdump --verify` 19 and 22, binutils and elfutils `addr2line`,
`eu-readelf`. Variants: the references, mortar before, "hyb" (the chosen
table), "hyb2" (0 in rnglists and loclists only, `.debug_addr` all ones),
and "lld" (lld's values everywhere).

| variant | configurations | gdb `inverted range` | gdb session differs from GNU ld's | lldb bad lookups |
|---|---|---|---|---|
| GNU ld | 20 | 0 | — | 0 |
| lld 19, lld 22, mold | 20 each | 0 | 4 | 0 |
| mortar before | 16 | **8** (every DWARF 5 config) | 8 | 0 |
| hyb (chosen) | 16 | 0 | 4 | 0 |
| hyb2 | 16 | 4 (Clang DWARF 5: `startx_length` through `.debug_addr`) | 4 | 0 |
| lld's values | 16 | 0 | 4 | 0 |

The 4 sessions that differ for every non-GNU variant are the `-O2`
`DW_AT_call_target` edges into a dead copy: the debuggers drop the
dead address as intended, while GNU ld's redirect gives the kept copy's,
so gdb cannot take entry values there (`CALL_TARGET_DEAD` in
`debuggers.rs`). mortar does not link i386 or x86-64 yet, so it has 16
configurations.

### The rule

image.md I-47's table, amended in its own paragraph: `.debug_rnglists`,
`.debug_loclists` and `.debug_addr` get 0, because in a DWARF 5
address-plus-length pair all ones wraps. The other rows stand
(`.debug_ranges`/`.debug_loc` 1, `.debug_aranges` all ones with length
0, `.debug_frame` all ones, ELFCLASS64 elsewhere all ones, ELFCLASS32
elsewhere 0). The text gives the reason for each row and why 0 is sound
in the M1 non-PIE layout (L-68's 4 MiB base). It also says a PIE or low
layout (M2) must revisit the row.

## 2. The text map

### Spec corrections (image.md §9.3, verified against GNU ld 2.44)

I-120 to I-122 were WP-027d's proposal; they are now M1, with:
- `-Map`/`-M` write GNU's layout. The machine map (`mortar-map 1`)
  moves to `--mortar-map` (mortar's own row; cli.md's bookkeeping list
  and the own-rows count of 3). Every consumer was switched: the
  pipeline, x64 and debugger tests, and the linktest engine, which
  always adds `--mortar-map` for mortar's plumb.
- Archive lines: the referencing file is at column 30, or on the next
  line when the member text is 30 columns or wider. A root
  (`-u`, `--require-defined`, the entry) prints 30 spaces then `(sym)`.
- The discarded list: dropped sections, including empty ones, but not
  consumed ones (`.note.gnu.property`, `.note.GNU-stack`), as GNU does.
- `Memory Configuration` with `*default*` and the class's all-ones
  length; a `LOAD` line per input, with an archive once.
- A name wraps to its own line when it, with the leading space of an
  input line, is 15 columns or wider. Addresses are `0x%016x` (`%08x`
  for ELFCLASS32), sizes `%10s` of `0x…`.
- Globals only (GNU's default), each under the input section that
  defines it.
- `*fill*` lines with the code fill pattern (`cc` on x86, `00000000` on
  AArch64); data gaps have no pattern.
- Merged chunks and synthetic chunks are lines of the file `mortar`;
  patches and thunks are lines of the file `linker stubs`.
- Non-alloc sections are shown at address 0, as GNU does.
- The map ends `OUTPUT(<file> <bfd target>)` then `LOAD linker stubs`.
- Script lines are absent (mortar has no default script to echo).

### Comparison with GNU's map

The pipeline test `the_text_map_matches_the_output_and_gnus_map` checks
the map of a C program and of a C++ program (exceptions, TLS,
templates, `-g`):
- plumb is clean;
- section lines equal the section headers;
- every input lies inside its section;
- every symbol equals its `.symtab` value;
- the (name, size, file) sets of placed inputs equal GNU's, apart from
  the linker-made and merged pieces and the COMDAT copy choice, over
  more than 100 compared inputs;
- the archive member sets equal GNU's.

By hand on a static glibc hello (`mapcmp.py`), 0 addresses disagree
with the output. Every remaining difference is explained:
- GNU attributes synthetic content (`.eh_frame`, `.note.*`, `.group`,
  merged `.rodata.str*`, `.debug_str`, `.comment`) to input files.
- COMDAT kept copies differ. mortar keeps `iofclose.o`'s
  `.data.rel.local.DW.ref.__gcc_personality_v0`, GNU `ioputs.o`'s. In
  C++, mortar keeps a 72-byte `.text._ZNSt16__numpunct_cacheIcED0Ev`
  (with its `.gcc_except_table`), GNU a 44-byte one. Both choices are
  legitimate.
- The referencing file differs for 129 of 381 archive members, because
  resolve records its first taker. The member sets are identical.

### Cost (protoc, static, median of 11 interleaved runs)

| threads | no map | `-Map` | `--mortar-map` |
|---|---|---|---|
| 1 | 0.782 s | 0.836 s (+7%) | 0.804 s |
| 8 | 0.268 s | 0.320 s (+19%) | 0.283 s |

The text map is 14.7 MB and 140682 lines; the machine map is 2.3 MB.
Output sections are formatted in parallel. The serial parts are the
discard list, the archive list and the concatenation into one buffer
before the write.

## 3. `.comment`

S-100's merge-piece design (R-M6) needed fill to copy from a non-file
source. Layout already joins a synthetic chunk to an output section of
its name, so `.comment` is synthetic chunk 23 (last, so every other
`ChunkId` is unchanged). Its bytes are `mortar <version>\0`, with no
hash, date, host or path. It sorts after the inputs' merged strings,
lld's place. With no input `.comment` it is the section itself
(`PROGBITS`, `MS`, entsize 1).

| linker | `readelf -p .comment` on the static glibc hello |
|---|---|
| GNU ld 2.44 | `GCC: (Debian 14.2.0-19) 14.2.0` |
| lld 22 | the same, then `Linker: Debian LLD 22.1.8` |
| mold 2.37.1 | `mold 2.37.1 (compatible with GNU ld)`, then the GCC string |
| mortar | the GCC string, then `mortar 0.0.0` |

Test: `the_comment_names_mortar_after_the_inputs` (`pipeline.rs`). It
checks GNU's strings followed by mortar's, lld's input strings equal
to mortar's, an assembled object giving `mortar` alone, and plumb clean.

## 5. BTI pad veneer

a64.md §9 does not specify the veneer for M1 ("refused by name
(feature `BTI landing pad`), later"), so the refusal stays
(`a_bti_far_call_without_a_proved_pad_is_refused`). Measured on a
static hello built with `-mbranch-protection=standard` (glibc's objects
carry BTI and PAC, so the output is BTI): 461 of 3921 `bl` sites
(11.8%) call a function without a landing pad, mostly static glibc
functions that are only called directly. A thunk is needed only beyond
±128 MiB, so the refusal fires only in a BTI output with that much
code. Nothing linked here comes near it.
