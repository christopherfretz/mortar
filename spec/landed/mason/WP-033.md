# WP-033 — the Mason lane

Branch `wp/033-mason-lane`, cut from main d7a12b9. The first links of
kiln + hod objects by mortar, a census of those objects, libc++'s tests
through the lane, and the harness that repeats all of it
(`cargo xtask mason`, contract `tests/mason/README.md`). No linker crate
changed.

## Tools

kiln 1.2.1 at b6c546bd6 (`target-kiln/release/kiln++`), hod at 7e30d7c8
(`target-hod/release/hod`, 0.0.0), both release builds already in the
build root, run as `KILN_BACKEND=hod KILN_HOD_STRICT=1`: every object job
of this WP was hod's (kiln's statistics log: no `hod-declined`, no
`hod-failed`). References: GNU ld 2.44, lld 19.1.7, mold 2.37.1; GCC,
g++ and gfortran 14.2; Clang 22.1.8; libc++ 22.1.8 (Debian
`1:22.1.8-1~deb13u4`, static archives); libstdc++ of GCC 14. AArch64.

`-ffunction-sections -fdata-sections`, `-fno-pic`) + 2 libc++ variants
for the 7 kiln-only programs = 58 cells. Every output of every linker
runs; mortar's output and status equal GNU ld's in every cell, and lld's
and mold's do too.

The verifier on main reports 728 to 2153 findings per output, all of

**Wrong output: none.**

## Census (kiln + hod against g++ and clang++ on the same 38 sources, `-O0` and `-g`)

`cargo xtask mason programs --census`. hod's relocations, all in
a64.md's census and all linked: `ABS32`, `ABS64`, `PREL32`, `PREL64`,
`ADR_PREL_PG_HI21`, `ADD_ABS_LO12_NC`, `CALL26`, `ADR_GOT_PAGE`,
`LD64_GOT_LO12_NC`, `TLSIE_ADR_GOTTPREL_PAGE21`,
`TLSIE_LD64_GOTTPREL_LO12_NC` (PIC), `TLSLE_ADD_TPREL_HI12`,
`TLSLE_ADD_TPREL_LO12_NC` (`-fno-pic`); no TLS descriptors, no
`LDST*_ABS_LO12_NC` (hod uses `add` then the load where `llc` folds the
low part into the load), no `JUMP26`. On 75 libc++ test objects
(vector, copy_file), hod against kiln's `llc` path: the same groups,
`.eh_frame` shapes and symbol kinds, with only the differences below.
Differences from Clang (hod's oracle is `llc`; kiln's `llc` path writes no
`.llvm_addrsig` either):

- No `.comment` (`!llvm.ident` is dropped, hod `ll.md` §3), no
  `.llvm_addrsig` (so an identical-code-folding pass must treat hod
  objects as address-taken everywhere), no `STT_FILE` symbol.
- No `$d` mapping symbols in data sections (Clang marks each data
  section; hod brackets only islands in code, hod `codegen.md` §5.5).
  The `$x` symbols are there.
- `.rela.*` have `SHF_INFO_LINK` (as GCC; `llc` sets it only outside
  groups).
- A COMDAT signature symbol is defined in the group's first member, not
  in `.group` (as GCC's are).
- `R_AARCH64_PREL64` in `.eh_frame` and `.gcc_except_table`, CIEs
  `"zR"` and `"zPLR"` with `R=0x1b`, `L=0x1c`, `P=0x9c`, code 1, data -4:
  Clang's shapes exactly (GCC: `PREL32`, `L=0x1b P=0x9b`, code 4 data -8).
- DWARF 5 with `.debug_addr` / `.debug_str_offsets` (as Clang); no
  `.debug_aranges`.
- `SHF_GNU_RETAIN` on `.bss.*` of retained variables (as Clang).
- No notes but `.note.GNU-stack`; no `.note.gnu.property` (BTI/PAC) in
  any producer's objects at these flags.

These are the deviations hod documents (`codegen.md` "differences from
llc"). **hod bugs: none found.** kiln bugs: none found.

## libc++ through the lane

kiln's runner (`kiln/spec/libcxx.md`) with the lane's compiler; libc++
22.1.8 static. Link modes: `dyn` (kiln's procedure: static libc++,
dynamic glibc, the host's ld), and fully static with GNU ld, lld, mold,
mortar; mortar also on the archives without `.ARM.attributes`
(`mortar-noattrs`) and without `.ARM.attributes` and `.deplibs`
(`mortar-stripped`). Every link of mortar's verified (`--plumb`).

| sample | tests | dyn / bfd / lld / mold | mortar | mortar-noattrs | mortar-stripped |
|---|---|---|---|---|---|
| `std/containers/sequences/vector` | 83 | 81 pass, 2 unsupported | 15 pass, 66 refused | - | 81 pass |
| `wp033`: algorithms, strings, input.output, language.support, thread, localization, shard 1/4 | 590 | 556 pass, 1 fail, 33 unsupported | 161 pass, 396 refused | 161 pass, 396 refused | 556 pass, 1 fail |

mortar's refusals, by diagnostic (`wp033`): 396
`unsupported section type: SHT_AARCH64_ATTRIBUTES`; without that
section, 396 `unsupported section type: 0x6fff4c04` (`.deplibs`): every
link that takes libc++abi takes a member with each. Plumb: 105 + 501
mortar links, all clean but for the known case. No test passes with GNU
ld and fails with mortar after mortar linked it (**WRONG: 0**). The one
failure is common to every mode, `dyn` included:
`std/input.output/filesystems/fs.op.funcs/fs.op.copy_file/copy_file.pass.cpp`
(run: assertion failed), with kiln's `llc` back end too: the
container's file system, not a toolchain bug.

Features that would unlock the most tests, in order:

1. **Accept `SHT_AARCH64_ATTRIBUTES`** (`.ARM.attributes`, the
   `aeabi_feature_and_bits` subsection Clang 22 writes into every
   member of libc++, libc++abi, libunwind): 395 of 395 lost tests in the
   sample, 66 of 66 in vector, together with 2. layout.md L-35 already says "accepted and
   consumed"; resolve.md "Section types" refuses (WP-027d item 4).
2. **`.deplibs` (`SHT_LLVM_DEPENDENT_LIBRARIES`)**: the same 395 tests
   (neither feature alone unlocks any: `mortar-noattrs` = `mortar`). GNU ld
   ignores the section; lld adds the libraries. For the lane, ignoring
   is correct (the only value is `pthread`, in libc 2.34+ an empty
   archive). Its diagnostic names the type as `0x6fff4c04`.
3. Nothing else: with both, the lane equals GNU ld on all 673 tests.

Reproducers: `tests/mason/repro/` (both refusals, with the counts of
members carrying each section).

## Harness

`cargo xtask mason [programs|census|setup|libcxx|verify]`
(`xtask/src/mason.rs`, `xtask/src/mason/`): every child through
`xtask::process::run` (kiln's runner and cargo through `run_step`); the
lane's `kiln++` and `ld` shims in `tests/mason/lane/`. Without kiln/hod
builds every command says `skipped` and exits 0; `MASON_REQUIRE_TOOLS=1`
makes it an error. `programs` takes about two minutes at `-j 4`, so it
is not in `ci --quick`. `libcxx --sample wp033` takes about 15 minutes for
six modes with `--plumb` (the debug verifier is most of the mortar modes'
time).

## Metadata channel (`.note.mason.*`): facts and options

Facts:

- kiln emits LLVM IR text; hod is the only consumer that writes the
  object. Anything kiln knows reaches the object only as IR hod
  lowers: a global with `section "<name>"` (hod picks type and flags by
  `llc`'s `getELFKindForNamedSection`/`getELFSectionType`, so a name
  beginning `.note` gets `SHT_NOTE`), `module asm` (hod has its own
  assembler, `asm.md`), `@llvm.used`/`@llvm.compiler.used`
  (`SHF_GNU_RETAIN`), `!llvm.dependent-libraries` and
  `!llvm.linker.options` (`.deplibs`, `.linker-options`).
- hod declines `!associated` (`global-metadata:associated`, `ir.md`
  §2.2), so a per-function record cannot yet be a `SHF_LINK_ORDER`
  section that dies with its function under `--gc-sections`; hod's
  object model has `set_linked_section` already. Unknown named metadata
  is declined (`named-metadata:<name>`), so metadata outside a section
  is not a channel.
- kiln has no ODR hash: "is this the same entity" is redeclaration-group
  identity (`kiln/spec/ast.md` §4.4), and merged GMF definitions are not
  compared (`modules.md` §10 item 11). An ODR fingerprint would be new
  work in kiln (per entity: mangled name, a hash of the token sequence
  or of the canonical AST of its definition, and the TU).
- GCC/Clang objects carry nothing of the kind; mortar must treat a
  missing note as "unknown", never as "consistent".
- Tried (`hod --strict`, then each linker): a kiln-style global with
  `section ".note.mason.odr"` and in `@llvm.used` becomes an
  `SHT_NOTE` section with `SHF_ALLOC | SHF_GNU_RETAIN`; GNU ld, lld, mold
  and mortar all output it in a `PT_NOTE`. An IR global cannot make a
  non-alloc section, and hod refuses `.section` in `module asm`
  (`unsupported construct 'asm:section'`). A non-alloc `SHT_NOTE` (from
  Clang's assembler) is copied by all four as a non-alloc section, no
  `PT_NOTE`.

Options:

1. **`SHT_NOTE` per object**, owner `Mason`, one note type per record
   kind (ODR fingerprints; incremental-link hints; Tuck data), written by
   kiln as a `section ".note.mason.<kind>"` constant byte array in
   `@llvm.used`. Works with hod today, but alloc: other linkers load it
   (bytes in the image, a `PT_NOTE`), and mortar would consume it and not
   output it. Non-alloc needs a hod request: a way to mark an explicit
   section non-alloc (or `.section` in `module asm`). No relocations
   (records name symbols by string), so no relocation rules to specify.
2. **The same, `SHF_LINK_ORDER`-linked per function** to its text
   section, so `--gc-sections` and COMDAT deduplication drop records with
   their entities. Needs `!associated` in hod (request) and a rule in
   mortar for a note in a discarded group.
3. **Alloc note + load-time hook** for dynamic-link checks: the
   records in a `PT_NOTE` of the output, read by an init hook. Only once
   mortar writes shared objects (not M1-M3).

Recommendation: option 1 now (a kiln request for the fingerprint, a
hod request for non-alloc explicit sections, a mortar spec section for
the note's format and the owner name), option 2 as a hod request when
`--gc-sections` lands.

## Provisioning

No apt package installed. `cargo xtask mason setup` downloads the three
libc++ `.deb`s with `apt-get download` (no install) and the test tree
from GitHub. Proposed for `scripts/provision.sh`: nothing required; to
make `MASON_REQUIRE_TOOLS=1` meaningful, building kiln and hod in
provisioning (`cargo build --release` in each with the wrapper's
`scripts/env.sh`, about 10 minutes) and `cargo xtask mason setup`.
