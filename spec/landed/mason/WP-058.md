## 1. The lane on the dynamic line

- **libc++ modes** `dyn-bfd`, `dyn-lld`, `dyn-mold`, `dyn-mortar`
  (`xtask/src/mason/libcxx.rs` `MODES`, `linker_of`, `reference_of`;
  `tests/mason/lane/kiln++`): kiln's runner's line unchanged (static
  libc++ between its `-Bstatic`/`-Bdynamic`, dynamic glibc, `libgcc_s`,
  the driver's default PIE), with `-B` naming the lane's `ld` of that
  linker, so every link is timed and mortar's are logged and verified.
  `dyn-bfd` is the reference of the `dyn-*` modes as `bfd` is of the
  static ones; `dyn` (the host's `ld`, untimed) stays as it was.
- **The verifier gets the line.** The mortar shim writes the link's words
  next to the output and runs `xtask mason verify <out> <map> <line>`
  (`xtask/src/mason.rs` `plumb(.., line)`, `verify_main`): stage 3 judges
  a dynamic output with its line, as the census lane does. With
  `--plumb`, a mortar link that is not clean (a finding, a second link
  that differs, a second link that fails) now fails the command.
- **Scratch outside the workspace.** kiln's runner keeps each test's
  directory (the objects, the link outputs) under its target directory;
  the lane now gives it `<out>/<mode>/runner`, so with `--out /tmp/...`
  every link writes to `/tmp` (WP-034's follow-up). GNU ld's times below
  are therefore fair, unlike WP-034's in-suite figures.
- **Lane defect fixed**: without `--out`, `--results`/`--baseline` read the
  run's directory after it had been removed (`results.tsv: No such file`);
  the results are now collected first.

### 3.2 Against the shared `libc++.so`

Not run. It would need no kiln change: a `dyn-so-*` mode whose `kiln++`
shim drops the runner's `-Wl,-Bstatic`/`-Bdynamic`, points `-L` at a
directory holding `libc++.so.1`, `libc++abi.so.1` (and `libc++.so`,
`libc++abi.so` as copies, since `setup` extracts no symlinks) plus
`libc++experimental.a`, and adds `-Wl,-rpath,<that directory>`. What is
missing is the runtime: Debian 13 has no `libc++1-22`
(`libc++-22-dev` 1:22.1.8-1~deb13u4 depends on `libc++1-19`), and
libc++ 22's headers against a 19 runtime would fail links in every
linker. It needs a libc++ 22 shared build (from LLVM's own packages, or
built from the `llvmorg-22.1.8` sources the lane already fetches tests
of): a `setup` step, about 30 MB.

## 6. The lane in `ci` (scope 5)

A new gate step `mason`, after `census` (`xtask/src/ci.rs` `MASON`,
`xtask/src/mason.rs` `ci`; `spec/harness.md` "ci"):

- both gates: libc++'s sample `ci` (eleven tests: `type_info`,
  `throw_with_nested`, a replaced `operator new`, `quick_exit`, threads,
  `call_once`, a locale, `cout.sh`, `current_path`, `atomic<bool>`,
  `push_back`) in modes `mortar` and `dyn-mortar`, with the debug mortar
  the gate builds, `--plumb`, against `tests/mason/baseline-mortar.tsv`
  (one baseline for both modes: their not-passing tests are the same).
  It fails on a regression, a verifier finding or a nondeterministic
  second link. 10 pass and 1 unsupported in each mode; 10 links each,
  all clean.
- the full gate adds the programs table (171 cells).
- skipped by name (exit 0) without kiln and hod builds or the lane's
  setup, unless `MASON_REQUIRE_TOOLS=1`: the hosted lanes skip it.

Cost here: the step 10 s with mortar built (35 s with its debug build;
load 9-12); the programs table 65 s at `-j 2`. The full suite stays an
on-request run (§7).

## 7. Repeatable

From the mortar checkout, after `source scripts/env.sh`; one shard at a
time, scratch outside the workspace:

```
cargo xtask mason setup                                     # once
for k in 1 2 3 4 5 6; do
  cargo xtask mason libcxx --full --shard $k/6 --mode dyn-bfd --mode dyn-mortar --plumb -j 4 \
      --out /tmp/<dir>/d$k --results /tmp/<dir>/d-$k.tsv --baseline tests/mason/baseline-mortar.tsv
done
cargo xtask mason libcxx --full --shard 1/6 --mode dyn-lld --mode dyn-mold -j 4 --out /tmp/<dir>/lm1 --results /tmp/<dir>/lm-1.tsv
cargo xtask mason libcxx --compare <dyn-bfd.tsv> <dyn-mortar.tsv>
cargo xtask mason programs -j 2
cargo xtask census --filter kiln/
```

One shard of the two modes is 7-11 minutes at `-j 4` on this host; the
whole suite about 50 minutes.
