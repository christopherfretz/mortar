# WP-111: the four options of BusyBox's final link

BusyBox's `scripts/trylink` links its final executable with
`--sort-common`, `--sort-section=alignment`, `--warn-common` and
`--verbose` (with `--gc-sections` and `--start-group`), and retries
without them only when a try fails. All four were `refused`; this
package accepts them, each with a rule, code and tests.

| option | row | rule | code | tests |
|---|---|---|---|---|
| `--sort-common[=ascending\|descending]` | supported, `shaping.sort_common` | `spec/layout.md` L-88a (and L-88's corrected note on GNU's order) | `mortar_layout::run::sort_commons`, applied in `place_with_copies` | `tests/link/layout/sort-common.test`; `run.rs` `l88a_sort_commons`; `crates/mortar/tests/options.rs` `sort_common` |
| `--sort-section=name\|alignment` | supported, `shaping.sort_section` | L-53a | `mortar_layout::order` (`sort_named`, `SCRIPT_SECTIONS`) | `tests/link/layout/sort-section.test`; `order.rs` `l53a_script_sections`; `options.rs` `sort_section` |
| `--warn-common`, `--no-warn-common` | supported (the resolve code existed) | `spec/resolve.md` §3.3 (GNU's five texts, mortar's two kinds) | `mortar_resolve` (unchanged) | `tests/link/resolve/warn-common.test`; `options.rs` `warn_common` |
| `--verbose[=N]` | supported, `bookkeeping.verbose` | `spec/cli.md` §5.1 | `mortar_cli` grammar (no `no-input-files`), `mortar::invoke_with` | `tests/link/diag/verbose.test` (with BusyBox's whole option set); `options.rs` `verbose` |

## What the references do (measured: GNU ld 2.44, lld 19 and 22, mold 2.37.1)

- **`--sort-common`.** GNU: descending without a value; it sorts each
  holder file's `COMMON` section on its own (the holder: the first
  common of the largest size), by the classes ≥ 16, 8, 4, 2, 1
  (ascending: 1, 2, 4, 8, then ≥ 16 together); ties and the alignments
  inside ≥ 16 are in its hash table's order. Large commons (`.lbss`,
  x86-64) are sorted alike. Without the option GNU's order is per holder
  file, in hash order, not by name as L-88 said (corrected). lld and
  mold accept `--sort-common` and ignore it; neither accepts a value.
  mortar: the key (alignment, `SymbolId`), a refinement of GNU's order.
- **`--sort-section`.** GNU: every input-section statement of its
  built-in script without a sort keyword becomes `SORT_BY_ALIGNMENT`
  (descending, stable) or `SORT_BY_NAME` (byte order, stable); each
  statement on its own, so the `.text` categories stay;
  `SORT(.text.sorted.*)` becomes name then alignment;
  `SORT_BY_INIT_PRIORITY` and `SORT_NONE` (`.init`, `.fini`) are kept;
  orphans are not sorted. lld and mold ignore it without a script.
  mortar: outcome (a), L-53a's key (group, sort key, `SectionId`).
  Byte-compared section by section against GNU ld on the scratch objects
  (`.text` with two categories, `.rodata`, `.data`, `.bss`, `.tdata`):
  the same order in every section, with both values.
- **`--warn-common`.** GNU's five texts (resolve.md §3.3's table), one
  per merge, archive members named `libw.a(w2.o)`; `--fatal-warnings`
  fails the link; GNU ld has no `--no-warn-common`. lld 22: `common x is
  overridden`, `multiple common of x`; it does not extract an archive
  member for a common, so it does not warn there. mold: `multiple common
  symbols: x` for both kinds. mortar keeps its two named kinds, one per
  symbol.
- **`--verbose`.** GNU prints version, emulations, its script between
  `=====` lines and `attempt to open` lines on standard output, exit 0
  with no input; `=N` takes any word. lld and mold fail with no input.
  BusyBox writes the text to a file and reads it only to show a failure;
  no configure probe of the realbuild projects reads it. mortar prints
  `-V`'s text through descriptor 1.

## `-v` and `-V` with inputs (added to the scope from WP-112's finding)

`-v` and `-V` on a line with inputs linked and printed nothing; GNU ld
2.44, lld and mold print their version line and link. Now
(`spec/cli.md` §5.1): the text on standard output through descriptor 1,
once, before the link, which goes on; the exit status is the link's, and
a failed link has still printed it. A line whose parse fails or that
names a refused option prints nothing. The `docs/status/options.md` rows
for `-v` ("Print the version and go on") and `-V` were already right.
Code: `mortar::invoke_with`; tests: `options.rs` `verbose` (both flags,
a link and a failed link), `lib.rs` `requests_are_answered`. WP-112's
`tests/link/input/print-version.test` (`xfail(mortar)`) was not on main
when this package handed back: its marker comes off, and its
static-identical rows are recorded, at integration.

## Incremental mode

`--sort-common` and `--sort-section` are IN-12 unsupported options
(`crates/mortar/src/incremental.rs` `unsupported`, `spec/incr.md`):
`--incremental` warns `incremental-unsupported` naming the option and
links plainly, writing no state; `--incremental=update` fails by name.
Changing either option between links is never a silent reuse: the
option is part of the plan hash (IN-18b), and a link with it writes no
state. `--warn-common` and `--verbose` do not change the image.
Test: `crates/mortar/tests/incremental.rs` `sort_options_are_unsupported`.

## The verifier

`crates/mortar_plumb/src/opts.rs` gained the five rows. The verifier must
also learn, in its stage-3 line reader (`line.rs` `WITH_ARG`, the words
read by `spec/cli.md` §2.3), that `--sort-section` (and `-sort-section`)
takes the next word as its value; today the two-word form is a P-D2
finding on every dynamic or PIE link (the BusyBox rows above). The
verifier does
not judge the order of inputs or commons inside an output section
(`spec/plumb.md` P-I1 judges coverage and alignment only): lld's and
mold's outputs of the new tests, which ignore both sort options, pass L3
with the options on their lines. What it would need (cut for a verifier
package):

> **P-sort (WP-111).** With `--sort-common` (last use; `=ascending`
> ascending, else descending) on the line, the `common` records of each
> output section, in address order, have non-increasing (descending) or
> non-decreasing (ascending) `<align>`. With `--sort-section=alignment`
> (`=name`), in each output section of layout.md L-53a's list, the `place`
> records in address order, partitioned into L-53a's groups (the L-53
> category in `.text`; numbered / unnumbered in `.init_array` and
> `.fini_array`, the numbered keeping L-54), have non-increasing input
> `sh_addralign` (non-decreasing input section names, byte order) within
> each group, except across `SHF_LINK_ORDER` members (L-57).

## BusyBox

The test step first (`tests/realbuild/projects/busybox.sh`): as root,
`testsuite/mount.tests` reaches `libbb/loop.c` `set_loop`, which with no
`/dev/loop-control` and `CONFIG_FEATURE_MOUNT_LOOP_CREATE=y` mknods every
missing `/dev/loopN` up to 0xfffff (the 1,048,576 nodes of 2026-11-16);
`testsuite/makedevs.tests` mknods a device table. Both are removed before
`make check` and their four tests recorded SKIP (a configuration
choice, stated in the script's header). Read from the 1.36.1 sources, not
run. The other projects' test steps were read for root-only behaviour:
none changes the machine (process-local `setrlimit` only; GNU tar's
`tar.tests` writes `/tmp/passwd` in the container's own `/tmp`).

gap, not a mislink, and this package may not change that file (below).
