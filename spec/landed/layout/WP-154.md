# WP-154: `-r` (relocatable output), the design

This is a design record; no linker code was written. The rules are tagged
M4-r in their owning specs:

- `spec/cli.md` §3.2 (corrected) and §3.16 C-R1 to C-R6 (and C-R2a, the
  `-z` table);
- `spec/resolve.md` §11 RV-R1 to RV-R10;
- `spec/layout.md` §24 L-R1 to L-R11 (and L-103);
- `spec/image.md` §17 I-R1 to I-R12 (and I-11);
- `spec/arch.md` §4.6 A-R1 to A-R5 (and §3.3);
- `spec/model.md` §4.6 MD-R1 to MD-R3;
- `spec/meta.md` MT-30 (checked), MT-30a, MT-16.

The verifier's side is a list of numbered requests (§D, V-R1 to V-R12)
and is not an edit of `spec/plumb.md`. The adversarial review
(`briefs/reviews/review-154-relocatable.md` in the context repo: 0
blockers, 7 majors, 9 minors) and the fix pass are in §H. The experiments are in
`tests/relocatable-design/` (the README there lists them; `exp/run-all.sh
WORK` reruns all of them). This file cites them by their path in that
directory.

Environment: AArch64 host, 12 cores shared. GCC/G++/gfortran 14.2.0
(native, and the x86_64 and i686 cross compilers); clang 19.1.7 and
22.1.8; GNU ld 2.44 and objcopy 2.44; ld.lld 22.1.8; mold 2.37.1;
qemu-user 10.0.13; glibc 2.41; gdb 16; lldb 19. mortar is the binary
`mortar-3ad9867a` (batch 10's tree, a debug build). kiln++ is kiln
d854b23bc (`.build/target-kiln-next`, read-only), and hod is the
workspace's release build.

## A. Census

### A.1 BusyBox (`exp/busybox/`, `work/busybox.log`)

I built BusyBox 1.36.1 (defconfig, `CONFIG_TC` off) by hand with `make
-j4 V=1`, with GCC and with clang-22. Its Kbuild has `LD = $(CC)
-nostdlib` and `cmd_link_o_target = $(LD) -nostdlib $(ld_flags) -r -o
$@ $(filter $(obj-y), $^)`. A directory with nothing to link gets an
empty archive named `built-in.o` (`ar rcs`), not a `-r`. The survey's
two lines are the `-r` of `applets/applets.o` into
`applets/built-in.o`, once per compiler:

- gcc: `-plugin …/liblto_plugin.so -plugin-opt=…/lto-wrapper
  -plugin-opt=-fresolution=… --eh-frame-hdr --hash-style=gnu
  --as-needed -dynamic-linker /lib/ld-linux-aarch64.so.1 -X -EL
  -maarch64linux --fix-cortex-a53-843419 -o applets/built-in.o -r
  applets/applets.o`
- clang-22: `-EL --hash-style=gnu --build-id --eh-frame-hdr -m
  aarch64linux -o applets/built-in.o -r applets/applets.o`

GNU ld, lld and mold all link both lines. Their outputs, replayed into
BusyBox's final `trylink` line (`--sort-common --sort-section alignment
--gc-sections --start-group … --end-group`), give the same program from
GNU ld and from mortar (`ok|42|edeaaff3f1774ad2`, the applet's output
hash). mortar refuses the `-r` itself: `unsupported option: -r`.

### A.3 Lines that are not from a driver (`exp/facts/`, `exp/options/`, `exp/more/`)

- **Kernel-style** `ld -r -o built-in.o a.o b.o`, with and without
  `-m`: every reference links it.
- **`-T script`**: GNU ld and lld honour `SECTIONS` at `-r`, so
  `.text.*` goes into `.text`. mold refuses the script. The final links
  run (`more.log`, `script-*`).
- **`--whole-archive` of a thin archive**, `--start-group`: all three.
- **`ld -r -b binary -o blob.o file`**: GNU ld writes `.data` (WA,
  alignment 1) and `_binary_*_start`, `_end`, `_size` (ABS). lld needs
  `-m` and gives alignment 8. mold refuses `-b binary`.
  `--format=binary` with `-b default` back to objects: GNU ld and lld.
- **Kernel modules** (the review's x07): Kbuild's module line is `ld -r
  -z noexecstack --build-id=sha1 -T module.lds`, and every module has
  `.gnu.linkonce.this_module`, a plain section. GNU ld and lld write a
  build ID into the `.ko`. Kernel modules are OUT OF SCOPE for now:
  `.gnu.linkonce.*` stays refused by L-37 and `-T` at `-r` until
  RL-11, lifted when a real line of the target needs them.
- **`-Ur`**: GNU ld writes the same sections as for `-r`; lld and mold
  reject it. **`-i`**: GNU ld writes the same bytes as `-r`; lld and
  mold reject it (`more.log`).

### A.4 The pre-link idiom (`exp/more/run.sh`, `exp/more/prelink.sh`)

The idiom is `ld -r` of a component, then `objcopy --localize-hidden`
(or `-G`), then a final link.

- **C**: it works with GNU ld's and lld's `-r`. The hidden symbol `hid`
  is `GLOBAL HIDDEN` after `-r` and `LOCAL HIDDEN` after
  `--localize-hidden`. The final links by GNU ld and by mortar run like
  the direct link. With mold's `-r` the program crashes, from mold's
  COMMON bug (§D).
- **C++ with exceptions, plain `-r`**: it aborts. This happens with every
  reference's `-r` and with GNU ld's and mortar's final links alike:
  `terminate called after throwing an instance of 'int'`. The mechanism
  (`prelink.log`):
  - after `-r`, the component's only hidden globals are the signatures
    of two COMDAT groups, `DW.ref.__gxx_personality_v0` and
    `DW.ref._ZTISt13runtime_error`;
  - `--localize-hidden` makes them local, and the groups stay groups;
  - in the final link, `mainx.o`'s group of the same signature loses the
    election, so its `.eh_frame` CIE names a global whose only
    definition is in the dropped member;
  - the reference resolves as an undefined weak, value 0, and the
    personality pointer is null.
  This was reported to the supervisor at once. It is a hole in
  `spec/resolve.md` §6.2/§6.3 that is wider than `-r`: the supervisor
  reproduced it with two hand-written objects and no `-r` or objcopy.
  The ruling is that a reference through a demoted mention whose key
  ends with no definition is `comdat-mismatch` whatever the mention's
  binding. That fix is **WP-176**, a linker package, plus a verifier
  package, and is not part of this design. Its sibling **WP-177**
  rules that a LIVE `.eh_frame` record or LSDA pointing into a dropped
  copy is an error by name; the review's §6 internal error
  (`objcopy --localize-hidden` of a `-r` output, then mortar's final
  link: `no live target in the tables at offset 0x13`) is WP-177's
  defect 2. RL-8's `-r` applies both rules (`spec/resolve.md` RV-R7).
- **What makes the idiom sound with C++.** `--localize-hidden` may
  localize a symbol only when no group carries it. A group's signature
  and its member symbols must stay as they are, or the group must be
  dissolved first. objcopy 2.44 does not check this, and `ld -r` by the
  three references keeps every COMDAT group (B.2), so the hidden
  `DW.ref.*` symbols are group signatures. The sound form is `ld -r
  --force-group-allocation` (GNU ld, lld) before localizing: no group is
  left (0 groups, the 2 hidden symbols outside any group), the
  component uses its own local `DW.ref` copies, and `mainx.o` keeps its
  group. Measured with EH and `-g` at `-O0`:

  | `-r` by | final GNU ld | final mortar |
  |---|---|---|
  | GNU ld | aborts (gdb transcript same) | refused (finding 1, §D) |
  | GNU ld `--force-group-allocation` | **runs, gdb same** | refused (finding 1) |
  | lld | aborts | aborts |
  | lld `--force-group-allocation` | **runs, gdb same** | **runs, gdb same** |
  | mold | aborts | aborts |

  mortar's `-r` offers the sound form: `--force-group-allocation` is
  part of RL-8 (`spec/cli.md` C-R3, `spec/resolve.md` RV-R7). The sound
  idiom, in one line: `ld -r --force-group-allocation`, THEN `objcopy
  --localize-hidden`. A
  dissolved group costs duplicate code when the final link also has a
  copy, because both copies are linked in and every reference binds to
  the first global definition. Weak globals that are not hidden keep one
  identity.

### B.4 Relocations

Every record type is carried unchanged by all three. There is no
relaxation, no GOT, no PLT, no TLS transition and no range check
(`facts.log` row 6, `facts-supp.log` 9-gotpcrelx). The types seen:
- x86-64: `GOTTPOFF`, `PC32`, `PLT32`, `REX_GOTPCRELX`, `TLSGD`;
- AArch64: `ADR_GOT_PAGE`, `LD64_GOT_LO12_NC`, `CALL26`, `PREL32`,
  `TLSDESC_ADR_PAGE21`, `TLSDESC_LD64_LO12`, `TLSDESC_ADD_LO12`,
  `TLSDESC_CALL`;
- i386: `GOT32X`, `GOTPC`, `PC32`, `PLT32`, `TLS_GOTIE`.
An i386 `R_386_16` whose rewritten addend overflows (0x10004): GNU ld
and mold truncate it to 0x4 silently (a mislink), lld refuses; mortar
refuses (A-R2's `relocation-out-of-range`; the review's x09).
On i386 (REL) the addend of a section-symbol record is rewritten in the
bytes by all three (`8-rel-addend`: `.data` holds `0b 16`, and rcheck
finds "records equal 2"). Against the C++ component (rcheck,
`final/<arch>.gcc/comp.cxx.*.o`, `work/rcheck-cxx.log`):
- GNU ld: every input record has its output record, equal (AArch64
  2264 of 2264; x86-64 2230; i686 2044). The only output records
  rcheck cannot explain are its `.eh_frame` `NONE` records.
- lld and mold: records into merged strings name the same string
  (1640, 1617, 1613); the rest are equal.
- lld on i686 has one record missing: the dropped `get_pc_thunk` FDE's.
Nested `-r` (a `-r` output as the input of a `-r`, with a group whose
signature the other input repeats): the same group and section counts as
the flat `-r`, in all three.

### B.5 `.eh_frame`, mergeable and debug sections

- **`.eh_frame`**: see B.2. No driver adds `crtend.o` to a `-r` line
  unless `-no-pie -Wl,-r` without `-nostdlib` (A.2).
- **Mergeable sections**: GNU ld does not merge them. lld and mold merge
  `.debug_str`, `.debug_line_str`, `.comment` and `.rodata.*.str*`, and
  the records into them are correct. Nothing breaks either way in the
  corpus.
- **Debug at `-O0 -g`, C++, AArch64** (`work/debug.log`): gdb stops at
  `x1.cc:10` and `x2.cc:8` with the same backtraces through both inputs
  on every route that links:
  - bfd→bfd, lld→bfd, mold→bfd, lld→mortar and mold→mortar equal the
    direct link;
  - bfd→mortar is refused (finding 1).
  lldb gives the same transcripts on every route, compared against the
  final linker's own direct link. mortar's direct link and its `-r`
  routes differ from GNU ld's only in the libc frame's alias name
  (`__libc_start_main` against `__libc_start_main_impl`), which is not
  specific to `-r`.
- **`-gsplit-dwarf`**: every route links and runs. The skeleton-unit
  count was not read (Appendix B).

## D. The verifier's side

### D.1 Requests (for `spec/plumb.md`'s owners; not applied here)

- **V-R1 (the oracle is the final program).** A `-r` is judged by
  composition: stage 3 judges the final link of the `-r` output against
  its inputs, and V-R2-V-R8, V-R10 and V-R11 judge the `-r` output
  against the `-r`'s inputs. The lane adds the end-to-end comparison. With the
  component's objects contiguous on the direct line and the `-r` output
  in their place, `link(inputs)` and `link(-r output)` must give:
  - the same output sections, in the same order;
  - per input piece, the same bytes after relocation;
  - the same symbol values for every global.

  What MAY differ, and nothing else (the tolerances):
  - (t1) addresses, by the padding that a merged section's alignment
    adds at its start: the `-r`'s `.text` is one input aligned to its
    largest piece;
  - (t2) `.symtab`'s local entries: the `-r` output's `STT_SECTION` and
    `STT_FILE` symbols, and the order of locals;
  - (t3) the build ID, which hashes (t1) and (t2);
  - (t4) the COMDAT keeper of a group whose copies' bytes differ and
    which has a copy outside the component (the `-r` elects first).

  The comparison does not apply at all (the exclusions) when:
  - **(a) archive extraction depends on symbols outside the `-r`
    line.** An archive on the `-r` line is extracted against the `-r`'s
    inputs alone (RV-R2). The review's x06 case 1: the archive's strong
    `foo` is extracted by the `-r`, while the direct link keeps the weak
    `foo` of an object outside the archive. "weak foo in C" against
    "strong foo from archive member", by GNU ld and by mortar.
  - **(b) the final link uses `--gc-sections` or `--icf`, and the `-r`
    merged same-named sections of different inputs** (L-R1's default
    merge). x06 case 2: two inputs' `.text.helper` are glued into one
    section, the live one keeps the dead one alive, and the final link
    fails on `undefined reference to missing_function` by GNU ld and by
    mortar, where the direct link runs. `-r --unique` removes it (L-R11;
    `work/unique-buildid.log`: the final `--gc-sections` links of GNU
    ld's `--unique` output run under GNU ld and mortar).
  - **(c) the final link uses `--wrap=SYM` and the component defines or
    references `SYM` internally** (found by this pass, `exp/review/
    equiv.sh`, `work/equiv.log`). A call inside the component is bound
    by the `-r` (it stays a reference to `foo`, but the definition is in
    the same file), and the final `--wrap` then cannot tell it from a
    call from outside. GNU ld: direct `callfoo=101`, via `-r`
    `callfoo=1`. mortar 3ad9867a refuses `--wrap` in a final link, so
    only GNU ld's row exists (WP-170 adds it).
  - **(d) the final link uses `--exclude-libs` and an archive member is
    on the `-r` line** (also found by this pass, `work/equiv.log`). The
    member's symbols come from an object after the `-r`, not from an
    archive, so `--exclude-libs ALL -shared` no longer hides them: the
    direct link's `.dynsym` has `api`, the `-r` route's has `api
    lib_fn`, under GNU ld and under mortar alike.

  Looked at and found to compose (`work/equiv.log`, both finals): the
  COMDAT keeper with the group only inside the component and with an
  outside copy first (`v=1,1` and `v=3,3`); `.init_array` order with
  priorities and a default entry on both sides of the component (`b200
  c a d`); a common's alignment (`cx%32=0`); visibility merging of a
  hidden reference against a default definition (`.dynsym` `api`). (t4)
  is still listed because a keeper with differing bytes was not built.

  The default stays the merge by name (L-R1): the exclusions are a
  property of the oracle, and a user who needs (b) uses `--unique`.
  The program is also run, both ways round.
- **V-R2 (every live input section once).** Each input section of a live
  file that RV-R7/I-R9 do not drop is exactly one piece of one output
  section of L-R1's key. It sits at an offset aligned to its
  `sh_addralign`. Its bytes equal the input's in every bit that no
  relocation writes. For a relocated field, the bits OUTSIDE the
  field's encoded value (the instruction's opcode and register bits,
  by `spec/plumb.md` §4.2's per-type table of what each type writes;
  none for a data field) are compared too, so a changed opcode bit
  under `CALL26` or `ADR_PREL_PG_HI21` is caught. Inside the field:
  - on RELA, the bits equal the input's (`-r` writes nothing there);
  - on REL, they hold `A + delta` (A-R2);
  - for a record that I-R7 does not write, they hold I-47's tombstone
    for the referring section and the field's width (I-R7), and
    nothing else.
  Mergeable pieces are byte-identical (L-R5). Dropped sections are
  absent.
- **V-R3 (every input relocation once).** For each input record that is
  not `NONE` and not dropped by RV-R7 or I-R7, there is exactly one
  output record:
  - in the relocation section whose `sh_info` names the output section
    that holds the record's piece (`.rela<name>` on RELA targets,
    `.rel<name>` on i386, with the piece's L-R1 key, so two output
    sections of one name have two relocation sections);
  - keyed by (that target output section, the input offset plus the
    piece's offset), so a record is matched by place and never by its
    target's name alone;
  - with the same type and an equivalent target. A global is equivalent
    when name and addend are the same. A local or section target is
    equivalent when it is the same (output section, offset), with the
    addend in the record (RELA) or in the field (REL).
  There are no other records: no `NONE`. This is rcheck's rule;
  `exp/tools/rcheck.py` is the prototype, minus its `.eh_frame` limit
  (V-R5).
- **V-R4 (the symbol table).** These must hold:
  - locals first and `sh_info` correct;
  - the `STT_SECTION` set and order of I-R4;
  - every key of RV-R6 exactly once, with the binding, type and
    visibility the rules give: hidden stays global, `UNIQUE` kept,
    commons per RV-R5, undefined per RV-R3, versioned names unchanged;
  - every defined symbol, local or global, with its VALUE and SECTION:
    `st_shndx` is the output section that holds the symbol's input
    piece, and `st_value` is the input value plus that piece's offset.
    For a symbol in `.eh_frame` (AArch64 `$d`), the offset is the record
    map's (I-R4's "kept local symbols at `-r`"). A common keeps
    `SHN_COMMON` with size and alignment (RV-R5), and an `SHN_ABS`
    symbol keeps its value. A type-unit group's local signature has
    `st_shndx` = its output `SHT_GROUP` section (L-R3);
  - no other local: the kept set is I-R4's, no more and no fewer;
  - no linker-defined symbol (RV-R8);
  - the signatures of the groups present.
- **V-R5 (`.eh_frame` parsed).** CIE/FDE framing valid; each kept FDE's
  CIE pointer names a CIE of its input; the FDEs of dropped sections are
  absent; every other input FDE is present once, byte for byte except
  its CIE pointer; its records are moved by V-R3. A LIVE FDE (or an LSDA
  of a live FDE) whose record targets a dropped copy is not in the
  output: the `-r` was refused by name (`spec/resolve.md` RV-R7, WP-177).
- **V-R6 (groups).** One `SHT_GROUP` per kept group, with the signature
  symbol, `GRP_COMDAT` and the members (with their relocation sections)
  `SHF_GROUP`. No member is in two groups. The keepers are recomputed
  by `spec/resolve.md` §6.1 over the `-r`'s inputs alone. Non-COMDAT
  groups are all present. With `--force-group-allocation` there is no
  group.
- **V-R7 (the header).** `ET_REL`; no program headers; `e_entry` 0; I-R2's
  `EI_OSABI`; A-R3's `e_flags`; L-R8's section order; I-R3's mode.
- **V-R8 (the Mason container).** At most one container. Its bytes equal
  `kept_units` over the live inputs (MT-30), and no input container
  survives as a section.
- **V-R9 (S1 on `ET_REL`).** `spec/harness.md` says that `relocatable` is
  not judged today. The request is that S1 judge it with V-R2-V-R8,
  V-R10 and V-R11.
- **V-R11 (every output section header).** For each output section,
  every field of its header is recomputed from the rules and compared:
  - `sh_type` and `sh_flags` by L-R1a (L-49 to L-51 over its pieces;
    `SHF_GNU_RETAIN` by key; `SHF_GROUP` iff a member of a kept group,
    L-R2);
  - `sh_addralign` the largest piece alignment; `sh_entsize` the pieces'
    common entsize, or 0 when they differ (L-R1a);
  - `sh_size` the end of the last piece; `sh_offset` aligned, L-R8's
    order, no overlap;
  - `sh_link`: for `SHF_LINK_ORDER`, the output section of the
    linked-to section (L-R1's key); for a relocation section, the
    `.symtab`; for `SHT_GROUP`, the `.symtab`; for `.symtab`, the
    `.strtab`; for `.symtab_shndx`, the `.symtab`; 0 otherwise;
  - `sh_info`: for a relocation section, its target output section; for
    `SHT_GROUP`, its signature's symbol index; for `.symtab`, the index
    of the first non-local; 0 otherwise (or the input's, copied, for a
    section type the rules copy, such as a note);
  - `sh_name` names the L-R1 name in `.shstrtab` (S-90).
  This is the check mold's `-r` fails on `__patchable_function_entries`
  (`sh_link` 0, the review's `w/lo`).
- **V-R10 (the `-z` and stack notes).** `.note.GNU-stack` present and
  flagged by L-R6a's table for the inputs and `-z` options; the
  property note by L-R1 (S-94/S-95 per property); the build-id note
  iff `--build-id` (I-R8), with its descriptor recomputed over the file
  as I-R8 says.
- **V-R12 (mutations).** At least one per rule, each caught:
  - a record moved by 4 bytes;
  - a section-symbol addend without the piece offset (RELA, and REL in
    the field);
  - a piece dropped or written twice;
  - two copies of a COMDAT group kept;
  - a hidden global demoted to local;
  - a common turned `SHN_ABS` (mold's bug);
  - a `.symver` name stripped;
  - an FDE of a dropped copy kept;
  - a `NONE` record left at a live record's offset;
  - a container duplicated;
  - added by the fix pass: an opcode bit flipped under a `CALL26`; a
    tombstone written as 0 in a `.debug_info` field (DWARF 5); a
    global's value off by its piece offset; a local `$d` left at a

## E. Incremental and speed

**Incremental (IN-12).** A pre-linked component should be **ignored** as
a unit by the incremental design, and treated as one ordinary input
object: when it changes, its pieces are compared like any input's. Two
choices of this design make that cheap later, so nothing more is needed
now:
- mortar's `-r` keeps every input piece byte-identical (L-R5: no
  merging; L-R6: `.eh_frame` records copied), so a content-hash diff at
  piece level finds the unchanged pieces of a re-pre-linked component;
- the `-r` layout is data (MD-R1), so a later "incremental `-r`" can
  move pieces without new kinds of state.
A `-r` output loses per-object identity (one `FileId`), which costs the
incremental design's per-file granularity. That is a reason not to
build on `-r` outputs, not a thing to fix in `-r`. IN-12 stays:
`--incremental` with `-r` is a warning and a plain link.

**Speed** (`exp/bench/`, `work/bench.log`). The input was the first 400
objects under `lib/` of `.build/bench-work`'s cxx-large-g tree
(read-only): 326 MB, `-g`. Three runs each, on the shared host:

| reference | wall time | peak RSS | output | sections | symbols | `.rela*` | `.strtab` | groups |
|---|---|---|---|---|---|---|---|---|
| GNU ld | 8.5-11.5 s | 225 MB | 322 MB | 48,879 | 86,048 | 67.1 MB in 16,323 sections (2.79 M records) | 4.65 MB | 10,434 |
| lld 22 | 0.89-1.16 s | 770 MB | 245 MB | 48,879 | 86,047 | 67.1 MB | 6.48 MB | 10,434 |
| mold | 1.17-1.31 s | 931 MB | 245 MB | 48,879 | 101,978 | 66.9 MB | 6.48 MB | 10,434 |

What `-r` costs a large link:
- **Relocations dominate.** 2.8 M records for 400 objects, about 7k per
  object, so about 16 M for the whole tree's 2,375 objects. Each is read,
  moved and renamed once (I-R5), with no scan.
- **Merged strings: 77 MB here.** GNU ld's output is 77,144,032 bytes
  larger. Split by section (`exp/review/gap.sh`, `work/gap.log`):
  `.debug_str` accounts for 77,068,559 bytes (99.9%), `.debug_line_str`
  for 2,071,085, and lld's larger `.shstrtab` (−1,739,672) and
  `.eh_frame` (−209,776) take some back. So the gap is `.debug_str`,
  which GNU ld does not merge. L-R5 accepts that cost (Q2).
- **`.strtab`.** GNU ld deduplicates symbol names (4.65 MB against
  6.48 MB).
- **Memory.** lld and mold hold 2.4 and 2.9 times the input in memory.
  GNU ld streams, using 0.7 times the input, at ten times their time.
  mortar's `-r` should stay below the input's size: pieces are copied by
  positioned writes and relocation sections are rewritten per input
  section in parallel (`spec/image.md` §10's design). That is a target
  for the bench, not a package of its own (order of work: no package for
  speed alone).

## G. Open questions (each with its recommendation)

- **Q1 (closed by this design): `-Ur` and `-i`.** Accept both, as
  `-r`. GNU ld links them; a line GNU ld links must link.
- **Q2 (merging at `-r`).** GNU ld does not merge; lld and mold do.
  *Decided (supervisor, fix pass):* mergeable sections are NOT merged
  in v1 (L-R5). The verifier matches bytes, the final link merges
  anyway, and pieces stay reusable. The cost is file size: 77 MB of
  322 here, 99.9% of it `.debug_str` (`work/gap.log`). Merging is a
  later optional package (`spec/layout.md` L-R5's last paragraph): it
  would rewrite the merged sections' bytes, every relocation record
  into them (a section-symbol addend becomes the output string's
  offset, rcheck's "same string" form), and the symbols defined in
  them, and V-R2/V-R3 would read "the same string" for those pieces.
  No rule forbids it: L-R5 makes "not merged" v1's choice, not an
  invariant, and E's piece-level reuse is the only thing it costs.
- **Q3 (section order).** The three references differ. *Recommendation:*
  first appearance, with each relocation section after its target
  (L-R8). It is a function of input order alone, so V-R7 recomputes it
  without a name table.
- **Q4 (`.eh_frame` of a dropped copy).** GNU ld leaves `NONE` records
  that break mortar's own final link (finding 1); lld keeps a dangling
  FDE; mold rewrites everything. *Recommendation:* remove the FDE and
  its records, keep CIEs, write no `NONE` (L-R6). Every byte left is an
  input byte, and V-R5 can check it.
- **Q5 (debug records into a dropped copy). Closed.** No record, and
  I-47's tombstone in the field, with I-112's aranges rule (I-R7). The
  review measured the case (x02, rerun in `work/review-x.log`): GNU ld
  retargets every such record to the kept copy, lld writes `NONE`,
  mold writes them against symbol 0. The tombstone form is checked by
  execution through all four final linkers (the review's x01). The
  first version's "GNU ld does this" was false and is gone.
- **Q6 (`e_entry` with `-e`).** GNU ld and lld write an offset, mold 0.
  *Recommendation:* 0 (L-R7). An `ET_REL` entry means nothing, and 0 is
  verifiable.
- **Q7 (crt files in a `-r`).** `-no-pie -Wl,-r` without `-nostdlib`
  pre-links `crt1.o … crtend.o`, which puts an `.eh_frame` terminator
  into the middle of the final link's `.eh_frame`. *Recommendation:*
  link it, because GNU ld does, but warn by name when a `-r` input
  defines `_start` or holds a zero-length `.eh_frame` terminator that is
  not at the end of its input. The warning is part of RL-11.
- **Q8 (an `SHT_REL` input on a RELA target).** No compiler on the
  matrix makes one. *Recommendation:* refuse by name (A-R4). Converting
  needs the addend read from the bytes, which is easy, but no line needs
  it.
- **Q9 (GCC LTO sections at `-r`).** *Recommendation:* refuse (RV-R9)
  until a GCC LTO build needs `-r`. Then measure what GCC's driver does
  at `-r -flto`: it runs the plugin.
- **Q10 (MT-16 anchors through `-r` and objcopy). NOT decided; options
  for the supervisor.** `spec/meta.md` MT-16 now says only that it is
  open, and that until it is decided every MT-16 anchor is unanchored.

  *How anchors are expressed today.* A kind that names a section of its
  own object names it by the triple (section name, group signature or
  empty, ordinal among the unit's sections of that name and signature),
  never by index. No kind uses it yet; kind 0x10 (`incr.md`'s content
  hashes) is the first that will. A reader resolves the triple in the
  object it reads and takes offset 0 of the section it finds.

  *Today's failure* (`exp/review/anchors.sh`, `work/anchors.log`). The
  first version's test, "the anchors hold iff the container has one
  unit" (D0 below), is wrong in 8 rows: a GNU ld or lld `-r` of one
  kiln object after a GCC object leaves one unit whose `.text`,
  `.comment` and `.eh_frame` now start at offsets 8, 32 (31) and 40;
  `objcopy --rename-section .text=.text.moved` and `--remove-section
  .comment` leave one unit whose triple names nothing. The reviewer's
  m7 is right.

  *Ways a reader can decide from the file alone* (each measured by
  `anchors.py` on T0-T6: unchanged, bfd `-r` alone, bfd and lld `-r`
  with GCC first, kiln first, two units, the two objcopy cases):
  - **(a) D1, the producer records each anchored section's size.** A
    reader accepts an anchor only if the resolved section has exactly
    that size; anything else is unanchored. Never wrong in the
    experiment. Conservative: a `-r` that merges a kiln section with
    others always fails it, even when kiln's piece is first (T3), and
    a coincidentally equal size is the one way it can be fooled (two
    merges that cancel, not seen). For a reference's `-r`, an objcopy
    output and mortar's own `-r` alike, it detects but cannot repair.
    kiln and hod: one more field per anchored section in the unit. A
    section's size is known only when the object's bytes are final, so
    the field is filled by whatever writes the object (hod on the hod
    route; on the llc route, the request goes to kiln's emitter).
  - **(b) D3, the producer emits an anchor symbol.** A local symbol at
    offset 0 of each anchored section, named with the unit's id
    (for example `__mason_anchor.<unit-id>.<n>`, an `STT_NOTYPE`
    local; not a `.L` name, which assemblers discard). The reader resolves the symbol, not the
    triple, and gets (section, offset). It survives every `-r` (locals
    are kept, I-R4) and objcopy's renames and moves; `strip` or `-x`
    removes it, which makes the anchor unanchored, the safe direction.
    In the experiment it gave the right section and offset in every
    row where the symbol existed. Costs: one symbol per anchored
    section per unit (`.symtab` and `.strtab` grow; at cxx-large-g's
    scale about one per function section with `-ffunction-sections`),
    and a unit id. kiln: the unit id and the symbol names in the unit;
    hod: emit the symbols (it owns the object's `.symtab`).
  - **(c) D2, the producer hashes the object's section list.** A reader
    accepts the anchors only if the object's section headers still hash
    to the value. Never wrong, but it fails even for a `-r` of one
    object alone (T1), so every pre-linked component loses its
    anchors. kiln/hod: the hash, computed after the object is final
    (hod).
  - **mortar's own `-r`, where mortar could repair.** Two forms:
    - *rewrite the anchors* in the unit. That needs mortar to decode
      every kind and version that uses MT-16, and MT-30 becomes
      "rewritten by mortar, unchanged by others";
    - *add a map unit* (a producer-3 unit, mortar's own, of the triples
      it moved: input unit, triple → output section, offset). The input
      units stay byte-identical, MT-30 keeps "unchanged", and a reader
      that knows the map kind repairs, one that does not falls back to
      (a)'s test. Its cost is one unit per `-r` with one row per
      anchored section.

  *Recommendation (open):* (a) for detection everywhere, because it is
  never wrong and costs one field; plus mortar's map unit for repair
  through mortar's own `-r`. (b) is the alternative if the incremental
  design needs anchors to survive references' `-r` and objcopy too;
  then (a) is redundant. The format requests go to kiln and hod when
  kind 0x10 is designed, not before: nothing uses MT-16 today.
- **Q11 (ODR at `-r`).** *Recommendation:* yes, the same checks as a
  final link over the component's own units (MT-30a). The component's
  build is where its own violation is first known. The final link
  checks again.
- **Q12 (`--build-id` at `-r`). Changed (M4).** With `--build-id` in
  any form the final link accepts, the note IS written (GNU ld and lld
  do; mold does not): `spec/image.md` I-R8. The bare form is mortar's
  20-byte fast tree (image.md §8.3) over the whole `-r` output with the
  descriptor zeroed (I-69/I-72); `sha1`, `sha256`, `fast` and `0xHEX` as in a
  final link, `uuid` the one nondeterministic form (an exception to
  I-R11), `md5` refused as in a final link. Without the option no note
  is written. The first reason ("every final link drops it") fails for
  a `-r` that is itself the product: a kernel module. Kernel modules
  are nevertheless OUT OF SCOPE for now: `.gnu.linkonce.this_module`
  stays refused by L-37 and `-T` at `-r` stays refused until RL-11,
  both lifted when a real line of the target needs them. The
  references' own hash formulas were not reproduced (Appendix B); the
  descriptor's bytes need not match theirs.
- **Q13 (`.llvm_addrsig`).** *Recommendation:* drop it at `-r` (L-R1).
  All three references copy the inputs' bytes (4 in the review's x08)
  with `sh_link` 0, so the indexes no longer name the output's symbols;
  lld's `--icf=safe` warns and ignores such a section, which is safe.
  Dropping it is the same outcome without a stale section. (The first
  version said "written empty", which x08 contradicts.)
- **Q14 (detecting mold's mislinks).** A mold `-r` output has
  `SHN_ABS` symbols whose value equals a power of two and whose size is
  that of a variable. *Recommendation:* no linker rule, because it
  cannot be told apart from a real absolute symbol. The lane keeps
  `skip(mold)` with the reason (D.2).
- **Q15 (the pre-link idiom).** *Recommendation:*
  `--force-group-allocation` in RL-8 (A.4), and a sentence in the
  user-facing docs: the sound idiom is `ld -r --force-group-allocation`
  BEFORE `objcopy --localize-hidden`. The unsound form is refused by
  name in the final link, not aborted at run time:
  - WP-176: a reference through a demoted mention (here the localized
    `DW.ref.*`) whose key ends with no definition is `comdat-mismatch`,
    whatever the mention's binding;
  - WP-177: a LIVE `.eh_frame` record, or an LSDA, that points into a
    dropped copy is an error by name; that is the review's §6
    internal error (its defect 2).
  Both rules are cited from `spec/resolve.md` §6.3 as their packages
  merge them, not restated here; RL-8's `-r` applies the same rules
  (RV-R7).
