# WP-203: an input section named `COMMON` goes to `.bss` in the final link

RL-6's finding, ruled a linker gap (`spec/plumb.md` §14.8): lld's `-r`
of a component with a common writes an input section `COMMON`
(`NOBITS`, `WA`, the commons' size; A120); GNU ld and lld put it in
`.bss` at the final link, mortar made it an orphan output section
`COMMON`.

## 1. Measurement

GNU ld 2.44 (`aarch64-linux-gnu-ld.bfd`, `x86_64-linux-gnu-ld.bfd`),
lld 19.1.7 (the lane's `ld.lld`; lld 22 cross-checked on AArch64 for
the `-r` input and the base, `PROGBITS` and `COMMON.x` links: the same
placement), and mortar before the change (base 1bfce906), through the
gcc driver (`-B` wrapper, as the lane does), `-static` and `-pie`, on
AArch64 (native) and x86-64 (cross, run under qemu). Inputs from
assembly unless said; every symbol is referenced by `main` so it is
live; every program that linked ran and printed the expected values.
Evidence: `readelf -SW`, `nm -n` and `-Map` of each output (scripts and
sources were in the package's scratch, `w203/measure.sh`,
`measure2.sh`).

### 1.3 Order inside `.bss`, and `--sort-section` (L-53a)

Two files: `vs1.o` (`COMMON` align 4 `sa`, then `.bss.zz` align 32
`sb`), `vs2.o` (`COMMON` align 32 `sc`, `.bss.aa` align 4 `sd`); the
same on both targets, static and pie:

| | GNU ld | lld | mortar with the rule (input order, L-53a) |
|---|---|---|---|
| no option | `sb sd` (`.bss*` statement), then `sa sc` (`*(COMMON)`, file order) | `sa sb sc sd` (input order) | `sa sb sc sd` (lld's) |
| `--sort-section=alignment` | `sb sd`, then `sc sa`: each statement sorted on its own | ignored: `sa sb sc sd` | `sb sc sa sd`: one group (differs from GNU) |
| `--sort-section=name` | `sd sb`, then `sa sc` | ignored | `sd sb sa sc`: `.` (0x2e) sorts before `C` (0x43), so every `.bss*` name precedes `COMMON`: GNU's order |

## 2. The rule (proposed text; the supervisor writes the spec)

In `spec/layout.md` §8.2, after L-44's table and its notes:

> - **L-44a [C] (`COMMON`, WP-203)** An input section whose name is
>   exactly `COMMON` goes to `.bss`, whatever its type and flags, unless
>   a row of §8.1 or L-45 applies first (on x86-64, `SHF_X86_64_LARGE`
>   sends it to `.lbss` by L-36; a note keeps its name). It is lld's
>   `-r` output of commons (A120; lld names its own commons so) and GNU
>   ld's `*(COMMON)`. The prefix rule does not apply: `COMMON.x` is an
>   orphan (L-48), as in GNU ld and lld; so are `LARGE_COMMON` and
>   `LARGE_COMMON.*` without `SHF_X86_64_LARGE` (lld's outcome; GNU ld's
>   x86-64 script puts a flagless `LARGE_COMMON` in `.lbss` by name, no
>   producer writes one: GNU ld's and lld's `-r` keep a large common a
>   symbol). In `.bss` it is an input section like any other: in
>   `SectionId` order among `.bss`'s inputs (lld's order; GNU's
>   `*(COMMON)` statement puts it after them; no observable effect),
>   before the commons (L-88); its type by L-49 (a `PROGBITS` one makes
>   `.bss` `PROGBITS`, as in both references), its flags by L-50; L-47
>   refuses a TLS or a non-allocated live `COMMON` beside `.bss`'s
>   inputs (`section-conflict`: lld refuses the TLS one, GNU ld refuses
>   it in a static link; both merge a non-allocated one silently);
>   `--gc-sections` treats it as any input (not a root, as in both);
>   `--sort-section` sorts it with `.bss`'s other inputs (L-53a).
>   Measured, GNU ld 2.44 and lld 19/22, AArch64 and x86-64, static and
>   pie (record `spec/landed/layout/WP-203.md`).

L-44's table, `.bss` row: "`.bss`, and the commons of §12.2" becomes
"`.bss`, the input section `COMMON` (L-44a), and the commons of §12.2".

L-53a's "Known differences from GNU ld", one item more:

> - GNU's `.bss` holds `*(COMMON)` as a statement of its own, after the
>   `.bss` inputs' statement: GNU places an input section `COMMON`
>   after them and sorts it on its own; mortar sorts it with `.bss`'s
>   other inputs (L-44a). With `name` the orders agree (every `.bss*`
>   name sorts before `COMMON`); with `alignment` they differ.

Which reference each disputed variant follows, and why:

- TLS `COMMON`: refused by name (`section-conflict`, L-47), with lld and
  GNU's static link; GNU's pie outcome (a TLS `.bss`) is not followed.
- non-allocated `COMMON`: refused by name (`section-conflict`, L-47);
  both references merge it, which L-47 already refuses for every name.
- x86-64 `COMMON` / `LARGE_COMMON.*` with `SHF_X86_64_LARGE`: L-36 (the
  flag wins over the name, `.lbss`), as for every name; both references
  make the small `.bss` large instead (GNU and lld for `COMMON`).
- x86-64 `LARGE_COMMON` without the flag: orphan (lld), not `.lbss`
  (GNU's by-name statement): L-44's uniform rule, no producer.
- order inside `.bss`: input order (lld), not GNU's statement order.
  Following GNU would need a `.bss` group in `order.rs` and the same in
  the update's ordering (`delta.rs`, the update's packages), for an
  order with no observable effect (L-88's argument). `rank.rs` and
  `order.rs` are unchanged.

## 3. Code

`crates/mortar_layout/src/assign.rs`, `output_name`: the exact name
`COMMON` returns `.bss`, after L-45/L-46 and before the table. `fate`'s
§8.1 rows run before `output_name`, so L-36 keeps its precedence.
`output_name` is the one producer of an output name for the whole link
(`assign`), the update's changed file (`fate`, `file_split.rs`) and the
delta (`delta.rs`): all three take the rule at once. `-r` does not read
it (L-R1).

Why some steps are not run for a reference (each is named in the test):
the verifier (L3) judges every reference output, and on outputs of
GNU ld, lld and mold it does not place an input section `COMMON` from
the map. A relocation against a symbol defined in one is R5 "refers to
section 'COMMON', which is not in the output" (GNU ld, lld and mold
alike, AArch64 and x86-64; for mortar's output, from its own map, no
finding). So the links every linker runs reference no symbol of a
`COMMON` section, and the programs that do are mortar's alone. Beyond
that, three reference outputs give L3 findings of linker-defined
symbols (Y5): GNU ld's `_edata`/`__bss_start` when `.bss` became
`PROGBITS`, GNU ld's `__bss_end__` on AArch64 with an orphan `NOBITS`
after `.bss` (`COMMON.x`), and mold's `__start_COMMON` (mold makes
`COMMON` an orphan): those steps run for lld and mortar only, mold is
skipped for `common-section.test`. Each is a verifier question (§6),
not a mortar one.

## 5. Incremental, and what a plain link pays

**Does the change reach the state?** The state stores each input
section's placement (output section, offset; IN-19), and the update
reads output names through the same `output_name`: `fate`
(`delta.rs`, called by `file_split.rs`) for a changed file's sections.
So a state written by this mortar has `COMMON` inputs in `.bss`, and an
update places a changed file's `COMMON` in `.bss`'s regions. Nothing in
`crates/mortar_incr` or `crates/mortar/src/update/` changes.

`cargo xtask incr-update -j 1` on this tree:

    incr-update: live-check (WP-238 P0-7): 97 links: agree:97
    incr-update: state (d0, WP-267 P-4): exact:38 outside-placement:213 n/a:385 FAIL:0
    incr-update: 49 scenarios, 636 hops: 636 PASS, 0 FAIL, 1649 n/a (...); 887s

No scenario has an input section `COMMON` (its three common scenarios
use `SHN_COMMON` symbols, L-88), so nothing in it changed.

By hand (testhooks mortar, `MORTAR_INCR_SMALL_OUTPUT=0`, AArch64
`-static`, `main.o comp.lld.o v1.o v2.o`: lld's `-r` `COMMON`, an
assembly `COMMON` holding `cn`, `.bss` and `.bss.b2`):

| hop | outcome | layout |
|---|---|---|
| base | full (no-state) | no `COMMON` section; `cn` in `.bss` |
| `v1.s`'s `COMMON` grows 16 -> 24 bytes | `update (InPlace) changed=1` | `v1.o`'s `.bss` region at `0x50c470` size `0x58` (map): `b1` `0x50c470`, `cn` `0x50c478`..`0x50c490`, then slack; `v2.o`'s region (`b2`) stays at `0x50c4c8` (a full link: `0x50c4d0`). No overlap; runs `15 4 1 3 1` as the full link |
| `c1.c` or `main.c` edited | full (`update-not-implemented (scan)`) | as a full link |

**A state written before WP-203.** IN-18 checks the mortar version
string, which is `CARGO_PKG_VERSION`: WP-203 does not change it, so a
state whose `COMMON` inputs sit in an output section `COMMON` is read
by this mortar. Measured (the rule disabled in a testhooks build, the
base linked with it, the update with this tree's, the same wrapper
path): `v1.s`'s `COMMON` grown, and separately a code-only `main.c`
edit, each give `full (update-not-implemented (image))` and the output
of a full link (`.bss` only, `b2` at `0x50c4d0`, runs right). I did
not find which check gives `image`, so that this holds for every such
state is NOT shown; whether WP-203 needs a state-version bump is the
supervisor's (`mortar_incr` is not this package's).

**A plain link pays nothing.** The rule is one comparison of a name
with `COMMON` per input section, inside `output_name`. A/B, release
builds by the same command, old = the `if` disabled: a static link of
two objects of 60,013 sections each (10 MB each), 20 alternating runs:

| build | mean | min | mean RSS |
|---|---|---|---|
| old | 0.1280 s | 0.090 s | 91,043 KB |
| new | 0.1250 s | 0.080 s | 91,006 KB |

The outputs are byte-identical (`cmp`). The difference is noise.

## 6. Findings outside the package

- **The verifier and an input section `COMMON` of a reference** (§4):
  R5 on every relocation against a symbol of an input section `COMMON`
  in GNU ld's, lld's and mold's outputs, and the three Y5 findings of
  linker-defined symbols. For WP-210 or a verifier package: today the
  lane cannot have a reference link a program that uses such a symbol.

- **A TLS `NOBITS` orphan in a static link is an internal error**
  (§1.2): `Layout::check` (Segments) refuses mortar's own layout,
  "TLS chunks overlap or are out of order", for a section
  `.section mytbss,"awT",%nobits` linked `-static` with glibc's
  `.tdata`/`.tbss`, on AArch64 and x86-64 (pie links and runs). lld
  links and runs it. Not a mislink (the check refuses the output), but
  an internal error where a refusal by name or a placement belongs.
- **lld 19's `-r` of an x86-64 large common** makes the symbol `ABS`
  (§1.1): a reference-tool defect (an anomaly for the verifier's list
  if it is ever met), not a mortar one.
