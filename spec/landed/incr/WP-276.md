# WP-276: thunks at the update's addresses (MEASUREMENT, then DESIGN)

Branch `wp/276-thunks`, base a4a450c9 (main 2064dd12 + WP-271's record
and review). No linker code is changed. Mortar is the release build of
a4a450c9. Evidence: `.build/target-wp-140/w276/` (`links.sh`,
`links.log`, `p1/<link>.{phdr,sections,syms,mapcounts,capacity,time,log}`,
`o0.py`, `o0.log`). WP-273's `replan` was read on `wp/273-island-replan`
1bec2922..b28e16e4 with `git show` only. Rule text below is PROPOSED.

## 1. Part 1: the measurement

### 1.1 How it was run

- The workload is WP-081's `cxx-large-g`: clang 19.1.7, `RelWithDebInfo`
  (`-O2 -g`), `LLVM_TARGETS_TO_BUILD=AArch64`, AArch64, `-static`.
- The cwd is the workload's `inputs/`. The response file is the bench's
  copy, with ONE change: `--dependency-file=` points into the scratch
  (`w276/response.txt`). The original writes `link.d` into the workload
  tree, which is read-only to me.
- `-o` is in the scratch. Each link ran alone, after a gate (1-minute
  load < 12 and ≥ 8 GB available; 1-minute load at start 7.1 to 11.9).
  Every output, map and state was measured, then deleted by its literal
  path before the next link.
- The links are `mortar @response -o out --mortar-map=out.map [extra]`,
  `ld.bfd @response -o out [extra]` (GNU ld 2.44) and
  `ld.lld-22 @response -o out [extra]` (LLD 22.1.8).
- The captured line has no `--gc-sections` and no
  `--fix-cortex-a53-843419`. WP-081 §1 says LLVM adds `--gc-sections`, but
  the capture does not hold it. The link driver was clang++, which does
  not pass the erratum option.
- I added a fifth mortar link with `--fix-cortex-a53-843419`, which is
  what Debian's GCC passes, to count erratum patches on the operator's
  shape.

### 1.2 The numbers

"RX span" is the `R E` `PT_LOAD`'s `p_memsz`, which is
`[.init, .fini end)` for mortar and lld. GNU ld makes ONE `R E` `PT_LOAD`
from the ELF header through `.eh_frame`, so its code span is given as
well: `.init` start to `.fini` end.

"v1 test" is WP-273's `replan::fast_path` (replan.rs ~:255), computed
from the numbers: `p_memsz + Σ (C − island size)` over the islands in the
RX `PT_LOAD`, with `C = 2^22`. Mortar makes 3 islands (`.init`, `.text`
and `.fini`, one part each), all of size 0 except m5's `.text` island
(0xf8).

- **Executable output sections.**
  - Mortar and GNU ld: `.init` 0x1c, `.plt` 0x50 (IPLT), `.text`,
    `.fini` 0x18.
  - lld: `.text`, `.init`, `.fini`, `.iplt` 0x50.
  - No other section has `SHF_EXECINSTR` in any of the nine links.
- **Thunk count.**
  - Mortar: `chunk thunk` lines in the map (0 in all five links) and
    `_veneer` symbols in `.symtab`. The only `_veneer` symbols are m5's
    31 `__erratum_843419_veneer`, which agrees with the map's 31
    `chunk patch` lines and 31 `redirect` lines.
  - GNU ld: `_veneer` symbols, 0.
  - lld: `__AArch64ADRPThunk_` / `__AArch64AbsLongThunk_`, 0.
  - The `Thunk_` names that `nm` shows in every output are LLVM's own
    functions (`CC_AArch64_Arm64EC_Thunk_Native`, …), not linker
    thunks.
- **How "fast path" was found.** Mortar does not report it.
  - At a4a450c9 the fixed point (`fixed.rs` `needs`) judges every branch

  - WP-273 adds `replan::fast_path`, which is not on this base. I derived

    and checked it against the map: 0 thunks.
- **Island capacities** (map `capacity` lines, incremental links):
  - m2: `.init 1 p0` capacity 3; `.text 1 p0` at 0x6007e00, capacity
    0x459548 (4.35 MiB, `.text`'s tail reserve); `.fini 1 p0` capacity 0.
    The `.fini` island is the last chunk of the RX `PT_LOAD`

### 1.3 The distance from 2^27

Write X for a link's plain code span (`.init`..`.fini` of a plain link).
Incremental mode's span is 1.1961·X (§1.2).

| what trips | when | X | this workload's growth to get there: no gc / gc |
|---|---|---|---|
| WP-273's v1 refusal (`fast_path`, span + 3C) | 1.1961·X + 12 MiB > 2^27 − 4 | > 96.98 MiB | ×1.569 / ×1.670 |
| the same with the update form proposed in §2.1 (span only) | 1.1961·X > 2^27 − 4 | > 107.0 MiB | ×1.731 / ×1.843 |
| a thunk possible in an incremental-mode link | the span exceeds 2^27 − 4 | > 107.0 MiB | ×1.731 / ×1.843 |
| a thunk possible in a plain link (mortar, GNU ld, lld) | X > 2^27 − 4 | > 128 MiB | ×2.071 / ×2.204 |
| `.text` cut into 2 parts (L-110) in incremental mode | body > S = 124 MiB − 32 | > ≈110.2 MiB | ×1.78 / ×1.90 |

How far that is:

- **Releases of LLVM.** I found no cheap per-release table. The web gives
  anecdotes only, none of them verified here:
  - an llvm-dev thread (March 2018, "Clang executable sizes and build
    stats"): the text segment grew about 41 % over several releases;
  - a clangd issue: the Windows clangd binary went from 40 MB in 18.1.7
    to 78 MB in 19.1.7;
  - a Zig report: static LLVM + clang + LLD 22.1.8 on aarch64-linux,
    ReleaseFast, all LLVM targets as far as I can tell, has 96.65 MB
    (92.2 MiB) of `.text`. That is X = 92.2 MiB, 5 % under WP-273's v1
    refusal, and 0.86 of the update-form threshold.
- **`-O0` instead of `-O2`** (`w276/o0.py`, `o0.log`). I compiled 24 of
  the workload's own translation units (every 108th of 2,610 in
  `llvm/lib` and `clang/lib`, AArch64 the only target) with their own
  command lines, at `-O2` and at `-O0`. Then I summed the
  `SHF_EXECINSTR` bytes:
  - outside COMDAT groups: ×1.274 (350,528 → 446,428 B);
  - in COMDAT groups, each name counted once in the sample: ×6.03
    (170,088 → 1,025,940 B);
  - together: ×2.83.

  The COMDAT figure overstates a whole link, which deduplicates across
  all 2,610 units, not 24. A linked `-O0` clang is therefore between
  about ×1.3 and ×2.8 of the `-O2` one. Not measured: that would take a
  full `-O0 -g` build (hours) and its link.
- **LLVM's other targets.** Not measured. The workload builds only the
  AArch64 back end.
- **The operator's own codebase.** It is unknown to me. The brief calls it
  "very large", larger than clang is a fair reading.

**Verdict of Part 1.**

- The measured workload needs no thunk in any of the five mortar
  configurations, and neither reference linker made one.
- WP-273's v1 holds the fast path with a margin of ×1.57 (×1.67 with
  `--gc-sections`).
- That margin is within reach of configurations the operator plausibly
  uses: `-O0`, all LLVM targets, or a codebase 1.6× clang.
- So thunks are reachable, and Part 2 is the full design (§2).
- x86-64 needs none: a static x86-64 link's `R_X86_64_PLT32`/`PC32` reach
  ±2 GiB, so no branch in a static image under 2 GiB is out of reach.

### 1.4 A finding outside this package: this workload writes no state

Every `--incremental=full` link of this workload (m2, m3, m5) ends with:

```
incremental: no state written: DIAGS: a warning gnu-warning: it names FileRef { path: "lib/libLLVMSupport.a", member: Some("DynamicLibrary.cpp.o") }, which is not one file of the link (IN-75a)
```

- This is WP-265's refusal "a file display two inputs share, when named"
  (`capture.rs` ~:2735-2750: a display held by two `FileId`s maps to
  `None`).
- The response file names `lib/libLLVMSupport.a` twice (lines 47 and
  139). So do 24 other archives, which is CMake's usual output.
- The warnings are glibc's `.gnu.warning.dlopen`, `getpwuid_r` and
  `getpwnam_r`, referenced from `libLLVMSupport.a` members.
- WP-081 §4.1 recorded a 209,791,911 B state for this link before WP-265.
- So today no update of the operator-shaped workload is possible: every
  update is `no-state`, whatever the thunk design. §1.5 holds the test of
  the cause.

### 1.5 The cause, tested

`w276/once.sh` runs the m2 link (`--incremental=full`) on
`w276/response-once.txt`. That is the same response file with its second
`lib/libLLVMSupport.a` (line 139) removed.

- The link succeeds (16.5 s, 2.65 GiB RSS).
- The output is 1,226,586,552 B, the size of m2's. I compared sizes only,
  not bytes.
- **A 195,628,530 B state is written.**

So the refusal comes from the repeated archive alone. The fix is not
this package's. It is the DIAGS producer's (`capture.rs`
`diag_rows_named`'s display map, WP-265): a display shared by two
command-line instances of ONE archive names the same member, and only
two different files sharing a display are ambiguous. That is a proposal,
not a design.

It needs a ruling before U-10's go/no-go on the large workload, which
needs a state.
