# WP-276: thunks at the update's addresses (MEASUREMENT, then DESIGN)

Branch `wp/276-thunks`, base a4a450c9 (main 2064dd12 + WP-271's record
and review). No linker code is changed. Mortar is the release build of
a4a450c9. Evidence: `.build/target-wp-140/w276/` (`links.sh`,
`links.log`, `p1/<link>.{phdr,sections,syms,mapcounts,capacity,time,log}`,
`o0.py`, `o0.log`). WP-273's `replan` was read on `wp/273-island-replan`
1bec2922..b28e16e4 with `git show` only. Rule text below is PROPOSED.

## 0. What needs a ruling

1. **The operator-shaped workload writes no state (§1.4, §1.5).** This is
   outside this package, but it blocks every update on it.
   - Every `--incremental=full` link of `cxx-large-g` ends with
     `no state written: DIAGS: a warning gnu-warning: it names ...
     libLLVMSupport.a(DynamicLibrary.cpp.o), which is not one file of the
     link (IN-75a)`. That is WP-265's "a file display two inputs share".
   - The cause is CMake's repeated archive on the command line. Listing it
     once writes a 195,628,530 B state.
   - U-10's go/no-go on the large workload cannot be taken until the
     DIAGS producer accepts a repeated archive.
2. **Thunks are reachable, so §2 is the full design.**
   - The measured link needs none: the RX span is 0.578 of 2^27 at most,
     and 0.671 under WP-273's v1 test.
   - But v1 refuses at ×1.57 of this workload's code (×1.67 with
     `--gc-sections`). `-O0` (a sample: ×1.3 to ×2.8), all LLVM targets,
     or a codebase 1.6× clang reach that.
   - Rule whether the follow-up (§2.10) is cut now, after WP-273 as
     ruled, or parked until the operator's codebase is measured.
3. **The update's fast path (§2.1).** In an update every island is fixed
   at its capacity, inside the RX `PT_LOAD`, so the exact test is
   `p_memsz ≤ 2^27 − 4`. WP-273's L-113 form adds 3·C = 12 MiB. The
   proposal widens v1 from 97 to 107 MiB of plain code. Both forms are
   correct, and WP-273 may keep its own.
4. **Non-last islands have no capacity (§2.6).** `chunk.rs` gives the
   tail reserve to an output section's last chunk only.
   - Once `.text` has two parts (about 110 MiB of plain code in
     incremental mode), every new thunk or erratum patch from part 0 is
     `island-exhausted`.
   - Proposed: in incremental mode, an IN-33 reserve for each non-last
     island, capped at `C`. A plain link pays nothing.
5. **WP-273's v1 judges EVERY branch of the link per update** (`replan`
   step 5 over `b.sites`). Its caller is not yet written. It should pass
   only the branches of refilled sections (§2.2), even in v1. With all of
   them, an update costs O(all branches), and phase B cannot supply them.

## 2. Part 2: the design of thunks at the update's addresses

This fills in WP-271 §2 step 5's follow-up. It builds on WP-273's
`replan` (`crates/mortar_layout/src/replan.rs`):
- `Input { placement, dirty, words, branches: Option<Branches>, cap }`;
- `Replan { patches, redirects, holes, sized, judged, appended, dropped }`;
- the gone-key holes are `hole_gone`.

The package is cut after WP-273 merges (ruling 3). AArch64 only.
x86-64's `replan` returns the placement's rows unchanged, as in WP-273.

The property it rests on is WP-273's. Islands are fixed (R-1), so no
address moves after U7. One round at U7's addresses is final: an
appended thunk moves nothing, and a thunk's words cannot form an 843419
site (a64.md §11.1 item 1: `adrp x16` is followed by `add`, never a
load/store).

### 2.1 The fast path in an update's form

- **WP-273's test** is L-113's literal form: `p_memsz + Σ (C − size)`.
  It is the right test for a FULL link, whose islands grow up to `C` and
  push later code.
- **In an update nothing grows past its capacity.**
  - An island's capacity ends where the next chunk starts: `.text`'s
    island at 0x6007e00 + 0x459548 = `.fini` at 0x6461348 in m2.
  - The last chunk of a `PT_LOAD` has no capacity (L-87, IN-72 item 3):
    m2's `.fini` island, capacity 0, ends the RX `PT_LOAD` at 0x6461360.
  - So the RX `PT_LOAD`'s `p_memsz` already covers every island at its
    capacity, and an append never exceeds the capacity or `C` (R-5).
- **Proposed:** in an update the fast path is `p_memsz ≤ 2^27 − 4` with
  one RX `PT_LOAD`, exactly WP-271 §0 item 3's words ("islands at
  capacity").
  - That is exact, and it widens v1 from X = 97.0 to 107.0 MiB of plain
    code (§1.3).
  - It is conservative-correct either way. WP-273 may keep its form until
    this package, which replaces it.
- **What the fast path still leaves to judge:** branches of B (§2.2)
  whose target lies outside the RX `PT_LOAD`. L-113 skips only targets
  inside it. In a static link these are absolute targets and targets in
  non-exec sections. They are rare, but the judgement is cheap, so B is
  judged whether or not the fast path holds. The fast path is then only
  a name for the refusal counter: §2.9's `thunks:` line says whether it
  held.

### 2.2 The branches judged: B, against the update's addresses

**B** is every `CALL26`/`JUMP26` site (`need::branch_site` is `Some`) in
a section of the refill set that is in an exec output section. It is
judged at U7's final addresses: `P` is the site's address in the update's
placement, and `T` is its final target there (symbol, PLT or IPLT entry,
plus addend).

**Why B is enough** (argued from IN-27's rows; §2.10's oracle checks it
in the lane). A branch's need is a function of `(P, T, r)`, where `r` is
its redirect's thunk address (`need::thunk_need`). For a site outside the
refill set, each of the three is unchanged:

- `P` moves only with its section. A moved, revived or changed section is
  refilled (IN-27: the moved row, the liveness row, the changed-file
  row).
- `T` moves only when:
  - a global's value changes, and its referrers are refilled (IN-27
    row 3);
  - a section moves, and the referrers of the section and of the globals
    defined in it are refilled (the moved row);
  - a PLT/IPLT entry moves, which is a synthetic table's growth step:
    code moves, so it is refused (R-1, "an island moved") or the units
    are refilled (the synthetic-table row);
  - the key's class changes (direct ↔ PLT), which is
    `update-not-implemented (slots)` (IN-72 item 7).
- `r` changes only by this re-plan. Islands are fixed, so a kept thunk
  never moves. A thunk that becomes a hole (§2.5) is the thunk of a key
  whose definition is gone or in a changed file, and so are its
  referrers.

So the words of a branch outside B are the previous output's, and they
are right at the update's addresses. **WP-273's v1 judges every branch of
the link** (`replan.rs` step 5, `for (s, t) in b.sites.iter().zip(b.targets)`).
- That is O(all branches) per update, and phase B (C') cannot supply it.
  The caller, which WP-273 has not written yet, should pass B even in v1.
- A full branch list is for the lane-only compare only (§2.10).

### 2.3 The judgement of one branch

`need::thunk_need(site, P, T, r)` is applied to B. The needs are taken in
arch.md §6 step 3's order (`P`, `SectionId`, record), so the result is a
function of the placement.

1. **No need**: `T` is in reach of `P`, or `r` is. The redirect is kept
   if there is one. This is the full link's monotone choice: a redirect
   is never dropped only because `T` came within reach. A full link of
   the same placement writes the same bytes, because the placement holds
   the redirect.
2. **Reuse by key.** Look for the thunk of the need's key,
   `Sym(SymKey, addend)` or `Plt(SymKey)`, in reach of `P`, with the
   lowest address, in ANY island. That covers stored rows, translated
   (materialize), and rows appended earlier in this re-plan.
   - Reach is exact: `reaches(Reach::s28, P, thunk)`.
   - The redirect `(section, offset) → row` is added or replaced.
   - This is arch.md §6 step 3 and L-111's "any island (k−2, k+1, another
     output section's)". L-126 admits it: an island "that already held a
     thunk of its key".
   - **The key index**: one map `Key → [(addr, row)]`, built from
     `PATCHES`' thunk rows (kinds 0, 1). Its cost is O(thunks), with
     whole `PATCHES` rows already read by WP-273.
3. **Append.** Otherwise add one thunk to the island of the site's part
   (L-111), at `align_up(island end, 4)`, 12 bytes (a64.md §9). It is
   taken only if all of these hold:
   - `new_end ≤ capacity` and `new_end ≤ C` (R-5; on m2 `C` binds:
     capacity 0x459548 > 0x400000);
   - `P` → thunk is in `s(28)`, exactly;
   - `Page(T) − Page(thunk)` is in `s(33)` (a64.md §9; the ADRP's reach;
     always true below 4 GiB, but checked so that it is refused by name,
     not by fill);
   - **L-118**: with `--fix-cortex-a53-843419`, a first chunk byte of an
     empty island at page offset 0xFFC/0x000/0x004/0x008 would need the
     padding that moves the island. That is `update-not-implemented
     (layout)` by name, as WP-273 does for a first erratum patch (R-1);
   - **BTI**: in an output with the BTI property, the direct target's
     word must pass a64.md §9's BTI test. Otherwise it is refused with
     the full link's feature name (`BTI landing pad`), using the full
     link's own check function.

   The island then holds at most one thunk per key (rule 4, condition
   (C)). If its own island already holds the key's thunk and it is out
   of reach, the update is `island-exhausted` by name. L-112 makes that
   impossible for a site in the island's part, so it would be a
   placement out of its rules.
4. **Overflow**: past the capacity or `C`, the update is
   `island-exhausted` (IN-72 item 9 (ii)). On m2 that is about 349,525
   thunks in `.text`'s island. `.init`'s island (capacity 3) and
   `.fini`'s (0) take none.

The erratum steps (WP-273, steps 1-4) run after this one, on the same
`patches` vector. The two kinds are appended in the update's order, and
the placement records that order (ruling 2, L-115 scoped to a full link).

### 2.4 A thunk whose target moved

A thunk's 12 bytes are a function of its own address `Q` and its final
target `T` alone (a64.md §9: `adrp x16, Page(T) − Page(Q)`,
`add x16, x16, T[11:0]`, `br x16`).

- `Q` never moves in an update.
- `T` moves with its key's value. That happens even when no branch to
  the thunk is in the refill set: an unchanged file's far call, whose
  callee in a changed file moved, is a referrer and IS refilled, but the
  thunk is not.
- IN-27's row "a patch or thunk was added, moved or removed" does not
  cover it. The image writes thunks from `PATCHES` and the target at the
  placement, so the full link of `P_U` writes the new `T`. An update that
  does not rewrite the thunk leaves the old one: a call that arrives at
  the OLD address. That is the stale-datum class, exactly.

**The rule: every thunk row is rewritten by every update of a link that
has thunks.** That is 12 bytes per row, used or unused: an unused thunk
is written too, because L-116 says its bytes are a valid thunk, and
IN-78 needs them equal to the full link's.

- The rows are contiguous at the island's start in a full link's key
  order (L-115), so the writes are a few ranges per island.
- Cost: O(thunks) target look-ups and 12·thunks bytes. 10,000 thunks are
  120 KB.
- The alternative, rewriting only the thunks whose `T` changed, needs the
  previous `T` of each key (the stored `SYMBOLS` value, or the PLT
  entry's stored place) and one more decision to get wrong. I recommend
  the unconditional form, given the bug history. The narrower form can
  replace it later if a measurement asks for it.
- **Phase A**: the image writes every thunk row from `PATCHES` and the
  key's target at `P_U`, used or not (`link.rs` `patches` ~:508-575).
  It does this for an island in the refill set today.
- **Phase B**: the thunk rows' ranges are dirty ranges of the island,
  12 bytes each. They are not the whole island: an erratum patch's `W4'`
  needs `F`'s relocated word, which C' has only for refilled sections,
  and it is unchanged otherwise (R-3's invariant).
- **Proposed IN-27 row:** "an island holding a thunk: every thunk row's
  12 bytes (IN-72 item 9 (iv))".

### 2.5 Gone keys, dropped redirects

- **A thunk whose key is gone becomes a hole.** That is any of:
  - a `Sym` key of a changed or removed file's LOCAL (materialize's
    `Globals::key` refuses it today: "a stored local of file N");
  - a global with no definition in the update;
  - under `--gc-sections`, a key whose defining section died (IN-29).

  The image makes a thunk whose target has no live place an internal
  error (`mortar_image/src/link.rs` `patches` ~:522-535: "a thunk at
  chunk N has no target"), so a gone key that is not holed fails the
  update. It does not mislink, but it is a defect.
  - It becomes a `Fill` hole of its island, and its row is removed. That
    is WP-273's `hole_gone`, with thunk positions added to `gone`.
  - R-6's meaning holds: a hole is zeros, as the full link of `P_U`
    writes an unused island byte.
  - A redirect to it can come only from a section of `d.files` (a local
    is file-local), and materialize drops those. Any other is the corrupt
    error WP-273 already raises.
- **A redirect of a section of `d.files`** is dropped (WP-273 does this
  for every kind). The new version's branches are in B and are judged
  from scratch.
- **A redirect whose site has no place** (killed) is dropped (WP-273).
- **A thunk that loses every redirect** stays and is rewritten (§2.4,
  L-116).
- **Renumbering.** Appends and holes renumber later redirects. Every
  redirect is rewritten (ruling 7, WP-273's sort).

### 2.6 Islands at capacity

- **One part (X ≤ about 110 MiB in incremental mode).** The output
  section's last island has the tail reserve: `.text`'s on this workload
  is 4.35 MiB, capped at `C`. That is room for about 350,000 thunks. The
  `.init`/`.fini` islands give `island-exhausted` for any need that has
  no in-reach thunk of its key elsewhere. A site in `.init` needs one
  only if it calls past 128 MiB, so reuse usually finds the `.text`
  island's.
- **Several parts (L-110: a body over S = 124 MiB − 32). This needs a
  ruling.**
  - `chunk.rs` `capacities` (~:994-1029) gives the tail reserve to the
    LAST chunk of each output section only. Every other island has
    capacity equal to its size.
  - So in a link with two `.text` parts, any new thunk or erratum patch
    for a site in part 0 is `island-exhausted`, unless an in-reach thunk
    of its key exists.
  - That is exactly the link where thunks matter. It affects WP-273's
    erratum appends too.
  - **Proposed IN-33 sentence:** "In incremental mode each island that is
    not its output section's last chunk gets capacity
    `min(C, size + max(4 KiB, part/16))`" (IN-33's tail formula, capped
    by L-112). For a 124 MiB part that is `C`.
  - Its costs:
    - up to 4 MiB of address space and file per extra part (zeros);
    - the parts after it move by that much in a full incremental link;
    - a plain link: nothing, since the slack is incremental mode's only;
    - L-112's bound: unchanged, since the island stays ≤ `C`;
    - L-110's cut: unchanged, since it uses sizes only.
  - Without it, the cut below still works, but on a multi-part link it
    gives `island-exhausted` for every new far call from a non-last part.

### 2.7 Stored tables and symbols

As WP-273 step 6:
- `PATCHES`, `REDIRECTS`, the islands' `SIZED` and `HOLES` rows are
  written whole;
- an appended thunk adds S-80's `$x` and `__<target>_veneer` (or
  `__<target>+0x<a>_veneer`, `@plt`) to the internal file's `.symtab`
  block, within its IN-49a capacity, else `symtab-exhausted`.

A thunk's symbols do not change when its target moves: the name is the
key's, and `st_value` is `Q`. A hole removes the row's symbols. So the
block is rewritten whenever a row is appended or removed.

### 2.8 What the judges check

| judge | what it catches for thunks | gap |
|---|---|---|
| fill (L-126, L-127) | a branch of B written out of reach: `relocation-out-of-range`, an error, never a mislink | a branch outside B is not written, so not checked (§2.2's argument; §2.10's compare) |
| the verifier, (b) `plumb --equiv` | stage 1 branch reach over EVERY relocation of the output: a missed thunk anywhere; W6: from each veneer the emulator must reach S+A, so a stale thunk reached from any branch, refilled or not, is caught | an unused stale thunk (nothing branches there) is not judged by W6; WP-272 judges it |
| WP-272's `islands` judge (`judge.py` `islands_check`, on `wp/272-island-judge`) | every thunk row's 12 bytes decode to `adrp/add/br x16` and to the key's target (`.symtab` value + addend, or the `slot plt` record); every `REDIRECTS` row's site word is `b`/`bl` to its row; every branch into an island has a row; no island word is uncovered; rows do not overlap | **it FAILs a thunk whose key is a LOCAL or versioned key, or whose name has two `.symtab` values** ("cannot be judged"; judge.py `islands_check` ~:121-132). C++ far calls to `static` and anonymous-namespace functions are local keys. WP-272 must decode those through `SYMBOLS`' place (section + value) before this package's scenarios can use them. Until then the scenarios use global targets. |
| (d0), state = capture (IN-78) | `SIZED`, `CHUNKS`, `SYMBOLS` and the `.symtab` block on every hop | `PATCHES`/`REDIRECTS` are excluded on every non-identity hop (R-2), so WP-272 stands for them |
| the dirty-range invariant (IN-75, against the previous output) | a byte the update changed outside its named ranges: a thunk written without its range named | a thunk NOT rewritten is not seen by it (unchanged bytes); W6 and WP-272 see it |
| (a) the run | a call that arrives at an old address, if the scenario executes it | only the paths run |
| (c) the two-full-link oracle (IN-63a) | the units a full link changes: the thunk's island and the referrers | it predicts; the update's write is judged by the others |

So each risk of §2.11 has at least two judges on every hop, both in the
lane.

### 2.9 Proposed rule text

**IN-72 item 9 (iv)**, replacing WP-271's v1 text:

> (iv) **thunks**: every `CALL26`/`JUMP26` site of a refilled exec
> section is judged at U7's addresses (arch.md §6 step 1, in step 3's
> order): no need keeps its redirect; a need reuses the in-reach thunk of
> its key with the lowest address in any island, else gets one appended
> to its part's island (L-111) within the island's capacity and `C`, with
> exact `s(28)` reach and the thunk's `s(33)`, else `island-exhausted`; a
> first chunk byte at an L-118 offset is `update-not-implemented (layout)`;
> every thunk row is rewritten (its bytes are a function of its address
> and its key's final target); a thunk whose key is gone becomes a `Fill`
> hole. A branch outside the refilled sections keeps its words, because
> its `P`, its `T` and its redirect are unchanged (IN-27). The RX
> `PT_LOAD` spanning ≤ 2^27 − 4 is reported as the fast path; it changes
> nothing judged.

- **IN-27, a new row**: "an island holding a thunk | every thunk row's
  12 bytes (IN-72 item 9 (iv))".
- **IN-34's thunks row**: "re-judged for the branches of refilled
  sections; every thunk row rewritten; new ones appended within capacity
  | `island-exhausted`".
- **IN-33** (if ruled, §2.6): the non-last island reserve.
- **L-113**, add: "In an update the islands are fixed at their capacity,
  which the RX `PT_LOAD` already spans; the fast path is the `PT_LOAD`'s
  span alone (IN-72 item 9)."

| # | wrong byte | how | caught by |
|---|---|---|---|
| 1 | a far call without a thunk | a branch whose `P`/`T` changed is outside B (an IN-27 row missed) | verifier stage 1 (every relocation); the lane-only full compare |
| 2 | a thunk branching to the old `T` | the thunk row not rewritten | W6 (used thunks), WP-272 (every row), (a) |

### 2.12 Cost

- Per update: O(|B| + thunks + P_touched + key look-ups). |B| is the
  branch relocations of refilled sections. A 1 MB translation unit holds
  ~10^4; not measured.
- The thunk rewrite is O(thunks) 12-byte writes.
- A plain link pays nothing: `replan` is called only from the update, and
  §2.6's reserve is incremental mode's.
- `--incremental=full` is unchanged unless §2.6 is ruled.

## 3. The short note (what keeps v1 honest until §2 lands)

- **When thunks matter**: an incremental-mode RX over 2^27 − 4, that is
  about 107 MiB of plain code (97 MiB under WP-273's form). This
  workload has 61.8 MiB (58.1 with `--gc-sections`).
- **The counted refusal**: `update-not-implemented (layout)` with "L-113's
  fast path" (WP-273 `replan::fast_path`), or "needs a thunk ... (v1
  judges no new thunk)". The lane's reason counter counts it.
- **The test that keeps it honest**: WP-273's
  `replan_fast_path_fails_refuses`, a unit test, plus the pipeline test
  above, expecting the refusal by name on a 2 × 64 MiB `.skip` program.
  That pipeline test does not exist yet: it is part of this package's
  cut, or WP-273's if the supervisor prefers.
