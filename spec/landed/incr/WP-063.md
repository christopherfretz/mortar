# WP-063 (M7 S3): change detection, the delta, the refill set, as a dry run

Record of WP-063. It covers change detection (`spec/incr.md`
IN-22..24), delta resolution (IN-25..29), the refill set with a reason
per unit, the dry run behind `--incremental-report`, and the
two-full-link oracle lane (IN-63a) with its mutation table (IN-63b).
There is still no update path: every `--incremental` link is a full
link, with the reason `update-not-implemented`. The dry run says what an
update would refill. The oracle checks that this is a superset of what
actually differs between two full links.

## 1. What landed, by crate

  - `cli.md` §3.13: the report's format (§3 below).

**The new side is the full link's layout.** The dry run compares the
old state with the state that the full link it is running would write.
So "what would an update refill" is answered against the layout that
an update must reproduce (IN-31's equality), not against a predicted
layout. Report units are matched to oracle units by (path, member,
shndx).

## 2. Fall-backs added, with their triggers

| reason | trigger in the dry run |
|---|---|
| `new-output-section` | the OUTSECS (name, ordinal) sets differ, or the segment count differs |
| `property-changed` | the size of the `.note.gnu.property` chunk differs. Only the size is checked, because the content is a synthetic chunk and is refilled. |
| `options-changed` | a changed path that is not a file of either link (a linker script). The state check already returns it, before the dry run, when the command line changes. |
| `inputs-reordered` | the relative order of two unchanged FILES rows changed. A change on the command line is caught first by the check, so only archive extraction order reaches this. |
| `tls-layout-changed` | any TP offset of a TLS unit differs |
| `symbol-kind-changed` | an attribute change (type, binding, `st_other`), or a change to or from absolute or common, on a key that an unchanged file mentions |
| `link-order-moved` | an `SHF_LINK_ORDER` section's `sh_link` target is unmapped, or its position differs |
| policy `too-much-changed` | more than 1/2 of the allocated bytes are refilled, or more than 1/2 of the live inputs changed (`TOO_MUCH`) |

## 3. The report's format

The full text is in `spec/cli.md` §3.13.

- The report starts with the existing first line:
  `incremental: full (<reason>) changed=<files> refilled=<units> bytes=<written> time=<ms>`.
- When the dry run ran, `delta` lines follow, in this order:
  - `inputs`, `path`, `stat-missed`, `file` and `probe`;
  - `symbols` and `symbol <what> <name>` (round 2: the new link's keys
    in its RESOLVED order, then the gone keys in the old link's; round 1
    sorted all keys by name);
  - `fallback <reason> <detail>`;
  - `policy too-much-changed <detail>`;
  - `refill units= holes= chunks= bytes=`;
  - `unit <reasons> <path> <member> <shndx> <name>`;
  - `hole <reasons> <path> <member> <shndx> <old address> <size> <name>`;
  - `chunk <reasons> <tag> <chunk> <output section>`;
  - `time detect= delta=`;
  - `end`.
- Free fields are percent-encoded, and an empty field is `-`.
- The reasons are `file`, `gone`, `global`, `comdat`, `comdat-file`,
  `slots`, `moved`, `moved-ref`, `moved-file`, `frag`, `synthetic`,
  `patch`, `liveness`, `liveness-file`, `eh-frame`, `eh-ref`, `headers`
  and `gaps`.
- A link without `--incremental-report` computes no delta. The old
  state is not even kept past the check.

## 4. The oracle lane

- **Pairs.** There are 164 pairs, run at O0 and O2, and all pass:
  - R3's 28 pairs (56 runs);
  - WP-063's own pairs, at least one per IN-27 row and per fall-back,
    on AArch64 and x86-64;
  - `pt` (AArch64 only), an erratum-843419 patch: an ADRP at page
    offset 0xff8 whose target is out of ADR's reach, behind padding
    that moves the site.
- **L10 steps.** There are none: WP-067 has not landed.
- **Quick subset.** `ci --quick` runs 22 pairs at O0 through
  `cargo test -p mortar --test incr_oracle`, in about 11 s.
- **Judgement.** A pair passes when every one of these is in the report:
  - every unit that differs in place or moved;
  - every unit that moved and also differs beyond its move, with a
    reason other than `moved`;
  - every unit that appeared;
  - every unit that vanished, as a hole;
  - every unit of a changed file;
  - every unit of a file that left, as a hole;
  - every output section whose bytes differ outside units, as a chunk.
    Bytes past the section's last unit need a chunk other than its
    body's fill, which is where patches and thunks sit.
  
  A fall-back, or a full link decided at the check, passes, and its
  ratio is `full`.
- **Ratio** is the refill set's size over the number of differing
  units, counting units of unchanged files and changed files together.
  Over the 114 pair runs that do not fall back:
  - minimum 1.00, median 1.15;
  - `inf` where nothing differs but the eh-frame prefix rule refills.

### Round 2 (the same-size edit, the delta's cost)

The table above is round 1's, kept for comparison. Round 2 changed two
rules (§4a below) and restructured the delta's passes (§6); the
restructuring changed no report: on protoc the three cases' reports are
line for line those of round 2's rules before it, and the oracle and
mutation tables of the rules alone (run `full4`) and of the final code
(`full5`) are identical.

- **Pairs.** 164, all pass.
- **Columns.** `differing` counts the units of unchanged files that
  differ; `changed` the units of changed files (refilled by row 1,
  never counted as differing by the oracle); `refill` the refilled
  units of unchanged files; `ratio` is `refill / differing` as in round
  1; `ratio-all` is all refilled units over `differing + changed`, the
  ratio a same-size edit has a finite value for.

  1.01 median, 12.0 maximum, `inf` in 20 runs (nothing of an unchanged

  unit on AArch64 is `crtbeginT.o`'s `.text`, whose reference into an

### 4a. The two rules round 2 changed

- **`.eh_frame` (IN-34a, `delta.rs`, "The suffix").** Round 1 kept only
  the records equal from the start. When the output `.eh_frame` keeps its
  address and size, the records equal from the end keep their offsets
  too, if each FDE there points to the same CIE in both links: its own
  CIE kept at or after the suffix's start, or its own CIE removed by
  S-44 while the new link keeps no CIE between the prefix and the
  suffix. A piece the new link's split does not know counts as a CIE.
  `eh_changed` holds only when something is between.
- **References into `.eh_frame` (S-50).** Round 1 refilled every one
  when anything in `.eh_frame` changed. Now one is refilled unless its
  section is empty and the chunk did not move (rule 1), or every piece of
  its section is kept and none is between the prefix and the suffix
  (rule 3's next record is then the same).

9 times, interleaved.

The 1-minute load was 13-14 throughout, on a shared 12-core host.
Times are wall-clock medians (min-max), and RSS is the median maximum
resident set. `main` is b096d06, built the same way.

What changed, per pass:
- **Nothing changed** (`nothing_changed`): no delta beyond detection.
  Exact: the link is a function of its options, target, inputs and
  their order, and the searches' answers, all of which detection
  compared.
- **Globals.** No sort and no map of every key. The candidates are the
  keys a file other than unchanged mentions (per file, its range of the
  sorted MENTIONS), on either side; the keys defined in a section that
  moved, flipped, or whose fragments or records moved; the layout's own
  kinds (internal, common, shared, absolute); and the keys of a flipped
  section. A key only unchanged files mention is resolved from the same
  mentions in the same order (IN-26; another order is
  `inputs-reordered`), so it is in both links with the same definer,
  kind, size and attributes, and its value moves only with its section.
  No rule of IN-25..29 needs a whole pass. The report's order is the new
  link's RESOLVED order (by SYMBOLS row), then the gone keys in the old
  link's (`cli.md`).
- **Pairing a candidate across the states** is the one pass over every
  key left (2.3 ms here): the state has no index by name, so each
  side's RESOLVED rows are walked once, each name hashed and looked up
  in a map of the candidates only. The options, not chosen (the
  coordinator's rule: no format change without asking):
  1. keep it: 2.3 ms on protoc, under 1% of a link;
  2. SYMBOLS (and so RESOLVED) sorted by key identity in the format: a
     candidate is a binary search, O(c log n); the sort moves to every
     incremental-mode link's capture (round 1's sort of every key by
     name, inside its 79 ms globals pass, is the order of magnitude),
     paid even when nothing changed;
  3. a stored hash index per side: about 8 bytes per key (0.55 MB more
     state on protoc), built at every capture.
  The recommendation is 1.
- **COMDAT keepers.** Only the groups of the sections of files other
  than unchanged, on either side, each looked up by binary search in
  RESOLVED's kind-6 block (sorted by signature).
- **Merged fragments.** Each side's FRAGS as one sorted list, walked
  once: a verdict per hash. The 12.9 ms is O(FRAGS) plus one lookup per
  `extra` fragment.
- **`extra`** (26-28 ms, the largest part left) walks every piece of
  every merged input section of the link (millions on protoc `-g`,
  `.debug_str`) to give each section's fragment hashes. Taking the
  live fragments' hashes from FRAGS instead of hashing them again was
  tried: 2 ms saved, removed as not worth the code. It is not a format
  question; it is O(pieces) in the link's own split.
- **`capture.rs:816`** (the linear search of an ordinal row) is in
  `replay`, not on the path of these links: not changed.

### Round 3: protoc with slack, and a real growth

**A correction to round 2.** Round 2's case "`main.o` +16 bytes" was
the object with 16 zero bytes appended to the file: its hash changed,
no section grew. Its report was the same-size edit's (753 units with
the round-2 code), and its numbers above are those of a changed file
whose sections keep their sizes, not of a growth. Round 3 measures a

## 7. Findings and open questions

- **IN-27 (the fragment's place).** A merged fragment's place is its
  merged chunk's base plus its offset in that chunk. FRAGS stores only
  the offset, so a moved merged chunk moves every fragment in it. The
  `os` scenario found this. Proposed text, after IN-27 row 6: "A
  fragment of a merged section moved when its merged chunk's address
  (allocated) or offset in its output section (non-allocated) changed,
  or its offset in the chunk changed; an output section with several
  merged chunks has no single base, and all its fragments count as
  moved."
- **IN-16 `inputs-reordered`.** A command-line reorder is
  `options-changed` at the check (the plan differs). Only an
  archive's extraction order reaches this reason. Recorded in §7 of
  `incr.md`.
- **IN-16 `property-changed`.** The trigger is the chunk's size only.
  The open question is whether a change in the property bits (BTI, IBT,
  SHSTK) without a size change should also fall back. The note is
  refilled either way. WP-064 should check whether anything else in
  the image (segment flags, PLT form) depends on the bits. If something
  does, the trigger becomes "the bits differ".
- **IN-63b.** The rows `eh-ref`, `inputs-reordered`, `options-changed`,
  `property-changed` and `symbol-kind-changed` are not caught by the
  two-full-link oracle (§5). Round 2: IN-63b now says a fall-back row
  may be not caught, conservative, with its reason; `property-changed`
  (size only) is `incr.md` §11's open question 11, for WP-064.

## 8. Follow-ups

- **A same-size edit over-approximated** (round 1: ratio `inf`, about
  350 refilled units). Done in round 2 (§4a): 1 unit on AArch64, none on
  x86-64.
- **The dry run's time on protoc** (round 1: about 0.3 s, most of it

  for an edit; the format options for the one whole pass left are in
  §6, not chosen.
- **`capture.rs:816`**, from before WP-063: for fragments with
  identical bytes, the search for an ordinal row is linear per
  fragment. It is in `replay`, off the path measured here: left.
- **`extra`** walks every merged piece of the link (26-28 ms on protoc
  `-g`): the largest part of the dry run left (§6).
- **The `.eh_frame`-reference row** has no pair that catches it (§5):
  WP-069's scenario. (Round 2's one refilled unit on AArch64,
  `crtbeginT.o`'s reference at `r = 0` into an empty section, is gone in
  incremental-mode layouts with per-file CIEs, round 3.)
- **The dry run compares with the new FULL link, for WP-064.** Since
  WP-062 a full link lays out its regions afresh from the new sizes, so
  a growth that would fit its region in an update still moves what
  follows it in the full link the delta compares with (protoc `main.o`
  `.text` +16 bytes: 22,827 units, §6 round 3). The refill set an update
  needs is the delta against the update's own layout (the old regions,
  the growth inside the slack): WP-064's to compute, with the same
  rules, once an update lays out. Until then the report's numbers for a
  growth are the full link's, an over-approximation of an update's.

  is left as it is: it decides from stat and stamps before the front
  runs, from the old state alone, and `detect()` compares two states,
  the new one captured after a link. Replacing it is not a few lines; it
  is WP-064's, when the update path has a new state to compare.

  ETXTBSY). Main's 0323cc0 retries a busy program and covers it.
