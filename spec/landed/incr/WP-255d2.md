## T3. Why a `SYMBOLS` row is not the link's `SymbolId`

By design of the capture, not of the test. The link's `SymbolId` is the
input phase's interning by first mention over EVERY file it loaded, in
load order (`Inputs::sym_map`, lazy archive members' symbol tables
included). The written state's rows are renumbered by the compaction
(`state5/compact.rs` ~354-385, IN-18e's one row order): live globals
sorted by (first LIVE mentioning file's rank, `at_index`) (IN-71: a key
first mentioned by an unextracted member sorts by its first live
mentioner), then the unmentioned keys (option roots) by name, then the
locals by (file rank, index); GONE keys and dead keys (`live_keys`,
IN-71b) are dropped, which shifts every later row. Any key whose first
mention is in a lazy member, or which follows a dropped key, sits at
another row. Example printed by `stored_rows_value_every_global` (now
matching by name): see §T3-example below.

### T3-example

The lane's fixtures (`rows_stored`, every `[wp255c]` line) show
`renumbered: 0`: they have no lazy member and drop no key. A link
with one does: `file_front_update::update_front_of_an_extracted_member`
prints, for the C++ program plus `lib2.a` with `m4.o` NOT extracted
(`renumbering`: each key of the old link's in-process front looked up
in its written state by `find_key(name, version)`):

```
aarch64 g++: the first renumbered key: _ZNSi6ignoreEl: SymbolId 52, SYMBOLS row 3993; 14014 of 14074 keys at another row, 4 without a row
x86-64 g++: the first renumbered key: _ZNSi6ignoreEl: SymbolId 52, SYMBOLS row 4520; 14904 of 14963 keys at another row, 5 without a row
```

`_ZNSi6ignoreEl` is first mentioned (key 52) by a file the input phase
loads early (libstdc++'s archive symbol table order); its first LIVE
mentioner ranks later, so IN-18e's order puts it at row 3993. The keys
without a row are mentioned only by members not extracted (dropped,
IN-71b), e.g. `m4.o`'s.

`crates/mortar/tests/rows_stored.rs`: the fixture path no longer asserts
`stored.name(key) == name` for `SymbolId(i)`; keys are matched by name
always (`globals_by_name`/`stored_id`), and in the fixture a key without
a single `GLOBAL` row of its name is an error (in the scale run it is
tallied, as before).
