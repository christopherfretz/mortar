## T3. Why a `SYMBOLS` row is not the link's `SymbolId`

By design of the capture, not of the test. The link's `SymbolId` is the
input phase's interning by first mention over EVERY file it loaded, in
load order (`Inputs::sym_map`, lazy archive members' symbol tables
included). The written state's rows are renumbered by the compaction
(`state5/compact.rs` ~354-385, IN-18e's one row order): live globals
sorted by (first LIVE mentioning file's rank, `at_index`) (IN-71: a key
first mentioned by an unextracted member sorts by its first live
mentioner), then the unmentioned keys (option roots) by name, then the
locals by (file rank, index); GONE keys and dead keys (`live_keys`,
IN-71b) are dropped, which shifts every later row. Any key whose first
mention is in a lazy member, or which follows a dropped key, sits at
another row. Example printed by `stored_rows_value_every_global` (now
matching by name): see §T3-example below.

### T3-example

The lane's fixtures (`rows_stored`, every `[wp255c]` line) show
`renumbered: 0`: they have no lazy member and drop no key. A link
with one does: `file_front_update::update_front_of_an_extracted_member`
prints, for the C++ program plus `lib2.a` with `m4.o` NOT extracted
(`renumbering`: each key of the old link's in-process front looked up
in its written state by `find_key(name, version)`):

```
aarch64 g++: the first renumbered key: _ZNSi6ignoreEl: SymbolId 52, SYMBOLS row 3993; 14014 of 14074 keys at another row, 4 without a row
x86-64 g++: the first renumbered key: _ZNSi6ignoreEl: SymbolId 52, SYMBOLS row 4520; 14904 of 14963 keys at another row, 5 without a row
```

`_ZNSi6ignoreEl` is first mentioned (key 52) by a file the input phase
loads early (libstdc++'s archive symbol table order); its first LIVE
mentioner ranks later, so IN-18e's order puts it at row 3993. The keys
without a row (printed by the same function): `_end`, `_DYNAMIC`,
`wp255d_nowhere` (mentioned only by `m4.o`, not extracted: dropped,
IN-71b) and `_ZN9__gnu_cxx21zoneinfo_dir_overrideEv` (both targets),
`__real_pthread_create` (x86-64): keys no LIVE file mentions in a way
the compaction keeps (`live_keys`, IN-71b); not traced further.

`crates/mortar/tests/rows_stored.rs`: the fixture path no longer asserts
`stored.name(key) == name` for `SymbolId(i)`; keys are matched by name
always (`globals_by_name`/`stored_id`), and in the fixture a key without
a single `GLOBAL` row of its name is an error (in the scale run it is
tallied, as before).

## D2-1. `Ids::Update { first_section, row }` (granted; F-1 closed)

`front_of(Ids::Update { first_section, row })` reads the changed file's
bytes at `row.base .. row.base + row.len` of `row.path` and checks them
against `row.hash` (IN-24), never the stored row's. `FileFront::row` is
that row. The row's `path` is read from the state's `STRINGS`: a `Str`
past them (an appeared file's new path, in `ChangedFiles::strings`) is
`update-not-implemented (resolve)` (finding F-5 below).

Test `update_front_of_edited_files` (AArch64, x86-64): the OLD state
(`m1.o` the C version), then `m1.o` replaced by the C++ edit (a renamed
function, a grown one, an added section, an added COMDAT group) and the
archive rebuilt (every member's `base` moves: `rows moved 3`). Each of
`m1.o`, `m2.o`, `m4.o` is opened through the OLD state with the row
`FileRow { base, len, hash, ..stored }`: `base`, `len`, `hash` from the
full link's capture of the new archive (the one producer of those
three; no second maker of a hash), the `Str`s the old state's. Equal to
the whole front of the new inputs: 40 sections (2 COMDAT anchors), 14 /
15 keys (3 new keys: `key: None`), versioned 2. The stored row for the
edited `m1.o` gives `input-changed`.

## D2-4. `front_of(Ids::Update)` takes the file as live (accepted)

The doc comment of `front_of` says the join calls it only for a file the
update's link keeps (a changed file, or a member `Extraction::extracted`
holds), never for a member that stays or becomes unextracted. NOT
written: a test that an unextracted member is not opened. `front_of`
opens what it is asked to; the decision is the caller's (the join's
adapter, not this package's), and no caller exists in this tree. The
test belongs with the adapter (the join's walk over `Extraction`,
asserting `FrontCache::opened()`): finding F-6.

## D2-5. The facts of a changed file's section: design note (STOPPED here)

What `split_of` needs per section index: `SectionFact { kind, kept, out }`.
The full link's values: `kind` and `kept` are resolve's `SectionRow`
(`mortar_resolve/src/resolve.rs` `section_rows`, line 890), `out` is
`Assignment::out` (`mortar_layout/src/assign.rs` `assign`, line 271).

1. **`kept`** — the keeper of the section's COMDAT group after the
   change. The update's producer is `mortar_incr::update::resolve`
   (`resolve.rs` `keeper_new`, line 340: `elected` for a group resolve
   re-elected, else `rows::keeper` over `view.group(sig)` with the
   CURRENT ranks; private, on the private `Ctx`). What the public
   `ResolveDelta` exposes (lines 43-75): `groups` (the `GROUPS` edits)
   and `reelected` (`(signature, old keeper, new keeper)`, only groups
   whose keeper CHANGED). For a group whose keeper did not change the
   answer is the stored keeper; for a NEW signature (a changed file's
   added group, as in `update_front_of_edited_files`) `reelected` has
   no row (no old keeper), so the only way to the keeper is to recompose
   `rows::keeper(stored GROUPS rows + delta.groups, rank)` with the
   update's ranks outside resolve: a SECOND composition of
   `keeper_new`. Needs: a field of `ResolveDelta` (shared type) giving
   the keeper of every signature a changed file has a copy of, e.g.
   `keepers: Vec<(Vec<u8>, Option<FileId>)>` filled from `keeper_new`.
   Ruling asked.
2. **`kind`** — NOT one function. `sections::classify` (`sections.rs`
   line 126, already `pub`) is the first step only; `section_rows`
   then changes the kind per file: (a) a refused section in a dropped
   COMDAT copy becomes `Regular` (line 934; depends on the keeper:
   item 1); (b) `-S` turns a refused `.zdebug`/compressed debug section
   into `Debug` (lines 938, 942; an option); (c) `relocated_containers`
   (line 775) turns a relocated `Meta` into `Excluded` (line 790);
   (d) S-6: a `Merge` section `placed_whole` becomes `Regular` (line
   965; needs `reloc_targets`' `row.reloc`, line 810); (e) the
   relocatable path (`relocatable.rs` lines 335, 344, `-r`). So
   `classify` alone gives a different kind than the full link for (a),
   (c), (d) (e.g. every `aM` section with relocations: `Merge` by
   `classify`, `Regular` in the full link; this is also why no link
   reaches `phase::units`' `Unit::Whole` for an uncompressed section:
   resolve made it `Regular` first). The producer is a pure move of
   `section_rows`' per-file body (lines 890-983) into a `pub` function
   over (machine, options, the file's `SectionInfo`s, `group_of`,
   `is_dropped`), which the whole-link `section_rows` calls; its
   `is_dropped` input is item 1's keeper. The move is within the
   original brief's grant ("the pure move in `crates/mortar_resolve`
   for the per-file section rows"), but its input from item 1 is not
   available; built alone it would take a dropped-ness the update
   cannot give. Not started.
3. **`out`** — `assign::fate` (line 107, private) gives `Fate::Out(name)`
   per section from (header, row, machine); the `OutSecId` is the
   whole link's interning of names in `FileId` order (lines 314-323).
   For a changed file: a `pub` on `fate` (or a wrapper) gives the
   name, and the id is the STORED `OUTSECS` row of that name (an
   unchanged layout); a name the state has no row for is an orphan
   placement (U-4's layout): `update-not-implemented (layout)`. One
   producer for the name; the name-to-row lookup is the state's
   (`OUTSECS`), not a second interning. Buildable, but only with
   item 2's row (`fate` reads `row.kind` and `row.state`).

So: `kept` needs a shared-type change (or a second producer), `kind`
needs `kept`. Per the brief, stopped here; nothing of D2-5 is built.

## The x86-64 member without `SECTIONS` rows (`FILES.flags`)

Printed by `file_front::file_front_equals_the_whole_front`'s comparison
(`[wp255d2]` lines): on x86-64, 253 files of the test link have no
`SECTIONS` rows and no `LAZY` flag; every one has `FILES.flags` = `0x1`
(`POSITIONAL` only), `kind` 1 (object), 0 mentions, and is an archive

`tinfo2.o`, ...; libm: `s_lib_version.o`, `w_*_compat.o`, ...). On
AArch64: none. Not established why (my unchecked guess: members that
the archive's symbol index names for no symbol, so they never become
extraction candidates; the capture marks them neither live nor `LAZY`).
`front_of(Ids::Stored)` gives them no section ids and their (empty)
keys, as for a `LAZY` member. Finding F-7: `LAZY` does not mean "not
extracted"; a reader that needs that must test "no `SECTIONS` rows".
