# WP-255a: the refill fills its dirty ranges; dirtied blocks checked against their stored leaves

The first package of WP-255's cut (`briefs/wp-255-rulings.md`, "The cut",
F1, F8; the review `briefs/reviews/review-255-lazy-link.md`, line 1 and
m3). Base 3534a506 (batch 16: main d7661317 + seams 9, 8, 8a). Linker
crates only: `mortar_image::update` and `mortar_image::link`; the
signature of `pub fn update::refill` and the public shape of every type
are unchanged.

## 1. What changed

**Range fill (I-95).** `update::refill` computed its `want` ranges, asked
the image for the whole 1 MiB windows holding them (`link::refill`,
whole plan jobs) and sliced the ranges out: O(window), not O(change).
It now calls `link::refill_ranges` (new, `pub(crate)`), which fills
exactly the normalized `want` ranges with `fill::fill_range` against the
WHOLE plan of the `Link` (`layout_plan::from_layout`, unchanged; no new
plan, that is 255c). Each range is cut at the plan's job boundaries
(I-31: the parallel unit, the pool's `map` over the pieces as before) and
a piece that touches a `Division::Whole` synthetic chunk is widened to
the chunk (I-104: one call writes it; such a chunk lies inside one job);
pieces of one job that then touch are merged. Every byte of a piece comes
from the same rows a whole fill uses: section bytes and relocations, the
`Gap` rows that carry I-41's pads (0xCC code gaps and the `.text` tail on
x86-64, AArch64's zero pattern, the `.init`/`.fini` no-op: every gap is a
row, I-42), merged fragments, synthetic chunks, headers, fixups. Review
F1 (pads left out) is a defect of a CLIP PLAN; the plan here is whole, so
it cannot occur, and `clip_fill_writes_pad_bytes` pins it for 255c.
`slice_of` finds a range's pieces by binary search (sorted, disjoint).
`Counts`: `windows` is now the number of 1 MiB blocks the ranges touch;
`jobs` the pieces; `filled` their bytes (the bytes wanted, plus a whole
chunk's widening). Nothing public was added.

`link::refill` (the window fill) is unchanged: it is the WP-061 floor's
(`mortar::image::refill`, `crate::floor`), which needs whole windows for
its leaves; the update no longer calls it.

**The pre-write leaf check (ruling F8).** Step 6 of `refill` (the
leaves) reads each block it rehashes ONCE, as long as the longer of its
old and new lengths (`Counts::build_id_read` counts those bytes). For a
block of the previous output (`k < leaf_count(previous size)`) it first
hashes the old range with the previous note's descriptor zeroed (I-72,
I-76: `mortar_digest::leaf` with the link's leaf function, the function
that made the stored leaf; the descriptor's bytes are put back after)
and compares the digest with `leaves[k]`; a difference is
`output-changed` with the detail `block k of the previous output (file
bytes [lo, hi)) is not the block its stored leaf hashes`. The new leaf
is then hashed from the same buffer with the overlay laid over it. The
blocks checked are those step 6 already rehashed: every block a dirty
range, the sealed note or a size change touches. Blocks the update
leaves clean are not read: m2 stays as recorded (IN-21's binding and
judgement (b)). The previous note's place is the new one moved with
`.note.gnu.build-id`'s section when a growth step moved it. `refill`
writes nothing; the check returns before its ranges exist, so before the
join's first write.

**The sentences.** `spec/image.md` I-95 (the update fills its dirty
ranges; the 1 MiB block is the unit of the leaf hash, not of the fill);
`spec/incr.md` IN-75 (the fill sentence, and "an update hashes every
block it will dirty against its stored leaf before its first write; a
difference is `output-changed`"), IN-21 (a pointer: the dirtied blocks
are also checked; every other block rests on the binding).

## 2. Tests (`crates/mortar/tests/update_image.rs`, AArch64 and x86-64)

- `refill_clips_equal_windows`: every refill of the file runs
  `clips_equal_windows` (from `run_refill_with`): the bytes of each
  returned range equal those of the whole windows that hold them, as the
  window path `mortar_image::link::refill` fills them; aside only the
  build id's descriptor (zeros in any fill, the id in the range) and a
  retired slot's words (zeros the update writes, asserted by its own
  test); and `filled` never exceeds the windows' bytes. The named test
  runs the five U-6 tests that refill (same-size edit and empty delta,
  symtab shrink, growth, build id, dead slot): 12 refills compared.
  **Why the window path and not a hook:** it is the floor's existing,
  unchanged fill of the same plan by the same `fill_range` over whole
  jobs; the shipped update calls only the range fill, so the comparison
  adds no second writer and no test switch to shipped code. The
  comparison is made on the returned ranges (after the copies, `.eh_frame`
  patches and symtab writes laid over the fill); on these fixtures those
  equal the full link's bytes, and `judge` compares the whole patched
  output with the full link besides.
- `clip_fill_writes_pad_bytes`: (A) U-6's growth: its ranges hold the
  `.text` tail after c.o's grown function (x86-64: 1,537 bytes of 0xCC,
  the review's F1 count; AArch64: 1,540 zero bytes); (B) a same-size edit
  with the `.text` chunk rewritten whole (a `RefillSet` chunk): 128 bytes
  of gaps between a.o's and c.o's functions and a 64-byte tail. Each
  byte is the arch's pad in the full link and in the update. Mutation:
  the range fill with every `Gap` row's bytes forced to zero (the
  review's `REV255_NOPAD` in this shape) fails this test, the growth
  test and `refill_clips_equal_windows` at the x86-64 tail (0x14367).
- `dirty_block_flipped_is_output_changed`: m3: on the big fixture's
  same-size edit (block 0 dirty), a byte at 0x80000 (block 0, outside
  every range) flipped in a copy of the previous output: `output-changed`
  naming block 0, the file unchanged. m2's counterpart: a byte in block 3
  (clean) flipped: the refill succeeds, reads one block, and the patched
  output differs from the full link by exactly that byte (IN-21).
- `leaf_check_reads_each_dirty_block_once`: a same-size edit of c.o
  (block 0) and of an 8-byte data section of b.o in block 2 (4 MiB of
  data around it not refilled): `leaves_hashed` 2, `build_id_read` equal
  to the two blocks' lengths (2 MiB), the new leaves the full link's.
- U-6's existing tests unchanged and green; the same-size edit's
  `build_id_read` is still one block.

## 3. Numbers

AArch64 host, release, the workspace (virtiofs). Model: the design's
`wp255_readset` test (`tests/incr-design/wp255/wp255_readset.patch` on
`wp/255-incr-lazy-link`, applied uncommitted and removed), with a
microbench of one leaf hash added; `libprotobuf.a`'s `strutil.cc.o`
edited same-size by `edit_member.py` (`.text` +0), the layout replayed.
Binaries built from 3534a506's `update.rs`/`link.rs` ("before") and this
package's ("after") in the same target directory, run interleaved
(before, after) x 3, 3 refills each: 9 samples a side. Load 11.3 to
11.9. Every run's patched output equals the full link's, and its leaves.

| protoc | `refill` before (median, range) | after | `filled` before | after | dirty bytes |
|---|---|---|---|---|---|
| no `-g` | 10.2 ms (9.6-11.1) | 8.1 ms (7.6-9.1) | 4,070,680 | 45,271 | 37,948 |
| `-g` | 16.8 ms (16.5-26.0) | 11.0 ms (10.6-13.9) | 7,549,496 | 149,529 | 37,948 |

(`with_link` + `refill` adds 1.2-1.4 ms to each. The first refill of
each `-g` run is the slow tail on both sides.) Both refills read 2
blocks for the leaves (`build_id_read` 2,097,152: the edit's block and
the note's); "after" includes the leaf check of those 2 blocks.

**The leaf check's cost** (one leaf hash of a 1 MiB block of protoc's
output, 21 runs per binary run; the range of the 12 runs' medians): SHA-1 0.87-0.89 ms
(protoc's `--build-id` is `sha1`, so the check of this edit costs about
1.8 ms, inside the "after" column), L128 (`fast`, bare) 0.041-0.044 ms,
SHA-256 2.07-2.11 ms. The review's 1.0 / 0.045 / 2.5-3.1 hold.

**A plain link pays nothing.** The plain path (`link::write`,
`with_image`, the plan) is not touched; `refill_ranges` is called from
`update::refill` only. The release `mortar` binaries differ in size by
8 bytes. Plain protoc links, 7 interleaved pairs, load 10.8 to 11.3
(`/usr/bin/time`, 10 ms precision): no `-g` before 0.11 s (0.11-0.13)
after 0.11 s (0.10-0.12), peak RSS 151 MB both; `-g` before 0.20 s
(0.20-0.22) after 0.21 s (0.20-0.21), RSS 255 MB both. `cargo xtask
static-identical`: §4.
