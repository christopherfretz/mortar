### 1.1 The stored form holds nothing of the invocation

**Invariant (proposed sentence for IN-75a):** "A `DIAGS` row stores the
warning's model (`mortar_diag::Diagnostic`: its kind's fields, its place
and its context lines, as `mortar_diag::subject::stored` writes them),
never a rendering: the program name, colour and the demangling hook are
the invocation's (`Style`, diag.md §5.1), not in the plan hash, and are
applied when the update renders its report; so a repeated row renders
under the update's `Style` as the full link's would."

Why the model and not a text without the program name: diag.md §5.4's
hook rewrites the kind's symbol and every symbol place at render time
(and adds `>>> mangled name:`), and §5.6 colours the severity word;
`--color-diagnostics=auto` resolves through the terminal, so one plan
renders two ways. Only the model is invariant under all three. The
severity is not stored: a state holds warnings only (IN-75a; an error
writes no state, IN-48; `--fatal-warnings` promotes at `emit`, so a
state written under it holds none, and the option is in the plan hash).

The row (format 5's `DIAGS`, unchanged in shape):

| field | type | who writes | who reads |
|---|---|---|---|
| `key.phase` | `u16` | capture (from the full link's `Key`), the update (fresh rows' `Key`) | U-9: the order (§1.3) |
| `key.unit` | `u32` | the same, **as the file's `FILES` row** for the phases whose unit is a `FileId` (model.md §8: 30, 40, 45, 50, 60, 70, 100); as is for 10, 15, 20 (argument index), 80, 90, 95, 110 (0) | U-9: mapped to the file's current rank at emission |
| `key.seq` | `u64` | the same | U-9 (§1.3: phases 20, 80, 90 need a rule) |
| `code` | `STRINGS` (UTF-8) | `Diagnostic::id()` | U-9 (`subjects(code)`, the per-code rule of §1.2); `from_stored` |
| `text` | `STRINGS` (UTF-8) | **`mortar_diag::subject::stored(&d)`** (the model; not a rendering) | **`mortar_diag::subject::from_stored(code, text)`** → `Diagnostic`, rendered by the update's `Report::render(&Style)` |
| `subjects` | `STRINGS` (`Subject`s, sorted) | capture (§1.4's derivation), U-8 (`Now::diag_row`), the update's steps for fresh rows | U-9: drop or repeat |
| `tomb` | flag | U-2 | U-2 |

The ONE pair: `stored(&Diagnostic) -> Option<String>` and
`from_stored(code, text) -> Option<Diagnostic>` (in `mortar_diag`,
which owns the model's private fields; `from_stored` returns `None` for
any text that is not exactly a stored form of the code: `state-corrupt`).
Over them, in `update/diags.rs` (my file), the two row functions capture
and update share (proposed names, §1.4): `row(key, &Diagnostic,
subjects) -> Option<DiagRow>` and `diagnostic(&DiagRow) ->
Option<Diagnostic>`. U-8's `Now::diag_row` calls `row` instead of
`render(&Style::plain("mortar"))`.

The form: tokens `<byte length>:<bytes>`; the kind's fields in
declaration order (numbers in decimal), the place (`-` or a tagged
form), then each context line (`n` note | `@` relation index, place).
Canonical (one text per model value: the decoder refuses leading zeros
and trailing bytes), so `text` stays a valid key column (IN-18e: the
key `(phase, unit, seq, code, text)`). Measured size: 97-99 bytes for
glibc's `gets`/`tmpnam` warnings with one `referenced by` place (the
rendered head line alone is 90).

### 1.2 Every warning code: who raises it, how an update recomputes it

unsupported`: no `-shared`, no dynamic executable, no PIE), so four
codes cannot be in a state; `incremental-unsupported` makes the link
plain (no state). "Key-implied files": every file the warning names or
that decides it mentions the key, so IN-71's affected set (every key a
changed, appeared, gone, drawn-in, extracted or no longer extracted file
mentions, old or new version) already contains the key whenever such a
file changes. "Datum": does a path, address, size or ordinal of the
text change without a subject changing.

How often a real update meets a fall-back: protoc (GCC `-g`, static,
AArch64): **0 warnings** in mortar's full link (and none in GNU ld's),
so never. A glibc static link that uses `getpwnam`-class functions: one
row per such key, each with its referrers; the fall-back is met only
when more than three places refer to one warned key and an edit touches
one of them (option A), or never (option B). `--warn-backrefs` and
`--version-script` are rare in static development links; under them
every update is a full link until a later package.

### 1.3 The order

diag.md §6.2: by `Key`, then the plain text, then the model (`Ord`).
The update sorts the union (repeated rows + fresh rows) by
`(phase, u(unit), s(seq), plain text, model)` where:

- `u`: for the phases whose unit is a `FileId`, the file's current
  `FILES.rank` (monotone in the full link's `FileId`, which is the
  position in rank order, IN-18e); no dense ordinal is needed, only the
  order. Otherwise the unit as stored.
- `s`: the seq as stored, except phase 80's `unknown-property` (its
  file's current rank, F-2) and phase 90 (F-3).

This is the Collector's own comparator over a monotone image of the
key; the join emits the sorted rows into the update's `Collector` with
`unit` replaced by the row's position among distinct `u` values (dense,
order-preserving), or `diags` returns them sorted and the join emits
them with consecutive keys. **Cost**: O(W log W) for W = stored + fresh
warnings, plus reading `DIAGS` whole (WP-213 F-3). This is accepted on
the numbers, and it is the floor in any case: every repeated row is a
line the update must print, so the output alone is Ω(W). No index makes
it O(change) without dropping that output. Measured (§1.6 b): W = 0 on
protoc; at most ~112 for glibc's whole `.gnu.warning` set; reading
10,000 rows costs 2.2 ms, 100,000 rows 23 ms.

### 1.4 What capture must do (and the seam change)

Capture today writes no `DIAGS` (WP-214 §9 b). It needs, for every
warning of the full link, its `Key` and its `Diagnostic`, but
**`Report` drops the keys at `finish`** (finding F-7). Proposed: one
accessor on `mortar_diag::Report`, `warnings(&self) -> impl Iterator<Item
= (Key, &Diagnostic)>` (the entries' keys kept; a plain link never
calls it, and `-w` has dropped them at `emit`), or capture takes the
`(Key, Diagnostic)` pairs before `finish`.

Then per warning: `row(key, &d, subjects_of(...))` with:

- `Key`: `Subject::Key(id)` of `Kind::symbol()` (the key of that name in
  the link's resolution) for the codes whose column has `key`;
- `File`: the files of the places (head and context) and of a kind's
  path field (`executable-stack`, `unknown-property`, `cet-report`),
  through the link's `FileRef` → `FileId` index (built only when there
  is a warning: a warning-free link pays nothing); the unit's file for
  phases 30-100; **key-implied files are not stored** (proposed IN-75a
  sentence, F-6: a key referenced by 1,000 files is one subject, not
  1,001);
- `Link` for the codes whose column has `link`.

### 1.5 Reference-site warnings (`.gnu.warning.SYM`, `undefined-symbol`)

The text is `with_refs`: the first three references in `RefId` order
(file, section index, relocation index) and "referenced N more times";
the key is the first reference's `(70, file, seq)`. Every referrer
mentions the key, so an affected key decides every hop; what the
recomputation needs is the places of the **unchanged** referrers.

- **Option A (O(change), no read; needs `refs`, `ref_count`)**: the
  stored row's listed places of unchanged files, merged by (rank, seq)
  with the changed files' new references to the key (U4/U-6's scan of
  the changed files). The rule: exact iff the stored row listed every
  reference (`ref_count` ≤ 3) or no changed file referred to the key in
  its old version (then no listed place can vanish, and the unlisted
  ones keep their count); else `update-not-implemented (diags)`.
- **Option B (exact always, reads)**: re-scan the unchanged referrers of
  the key (`KEY_REFS(key)`'s files) for their references to it, each
  read after IN-75's `STAT` check. O(the key's referrers' relocations);
  warned keys only.

I propose A for v1 (no unchanged file read, a named fall-back) and B
later. Undecided: which step produces the changed files' references to
warned keys (U-6's refill scans the changed files' relocations; U-9 can
take them as `fresh` rows with `refs` filled).

### 1.7 Findings (proposed text; rule files not edited)

- **F-1 `executable-stack`'s subjects** (diag.md §3.1): its existence
  depends on every file before it in load order (L-84 names the first
  exec-stack file). Proposed column: `file, link`, with IN-75a's per-code
  rule of §1.2.
- **F-2 phase 80's `unknown-property` key** carries the file's first
  `SectionId` (`mortar_synth::notes`), a per-link ordinal. Proposed for
  model.md §8: "phase 80: unit 0; seq the `SymbolId`, a count, or for a
  per-object finding the first `SectionId` of the object (an update
  orders those by the object's rank)".
- **F-3 phase 90's warnings are keyed by their position in the layout's
  list** (`front.rs`: `u64::MAX - 1000 + seq`): `entry-not-found` is seq
  0 or 1 depending on whether `executable-stack` was raised. A stored
  `entry-not-found` (seq 0) with a fresh `executable-stack` (seq 0) ties
  and sorts by text, `entry-not-found` first; the full link puts
  `executable-stack` first. Proposed (front's owner): a fixed seq per
  code (`executable-stack` `MAX - 1000`, `entry-not-found` `MAX - 999`).
- **F-4 phase 20's seq is a member offset**: an archive rewritten with
  another member changed moves it. Proposed IN-75a sentence: "a phase-20
  row's unit is its argument; the row is dropped when that argument's
  input is not clean (IN-22, IN-24) and recomputed by U2's walk".
- **F-5 `.gnu.warning.K`'s holder** need not mention K. Proposed IN-71
  sentence: "a changed, gone, drawn-in, extracted or no longer extracted
  file whose old or new version has a section `.gnu.warning.K` makes K
  affected".
- **F-6 key-implied files are not stored** (§1.4).
- **F-7 `Report` drops the keys** capture needs (§1.4).
- **F-8 `Now::diag_row` (U-8) stores `render(&Style::plain("mortar"))`**:
  to call `row` once ruled.

### 2.1 What `diags` does

`diags(view, changed, resolved, odr, fresh) -> Result<Vec<DiagRow>,
IncrReason>` reads `DIAGS` whole (as §1.3) and routes every stored and
fresh row by its code:

| route | codes | stored row | fresh row |
|---|---|---|---|
| fall back | `archive-backref`, `archive-choice`, `version-reassigned`, `version-script-undefined-name`, `versioned-definition-hidden`, `duplicate-soname`, `needed-not-found`, `incremental-unsupported`, `copy-of-locally-bound-definition` | `update-not-implemented (diags)` | the same |
| dropped | `incremental-not-reproducible` | dropped (U1 raises it afresh) | kept |
| probe | `skipped-incompatible` | kept unless a fresh row has its unit (argument) | kept |
| site | `undefined-symbol`; `gnu-warning` at phase 70 (incl. dormant rows, §2.4) | kept whole when its key is not affected and no `File` subject (the holder) is touched and there is no fresh row; else recomputed (§2.3) | merged (§2.3) |
| stack | `executable-stack` | F-1 / ruling 7 (§2.5) | the candidates |
| ODR | `odr-*` W1/W2 rows of a `Key` (no `OdrKey`) | kept unless the key is in `odr.keys` (U-8's rows replace them) | — (`odr.rows`) |
| subjects | every other code | dropped iff a `File` subject is touched, a `Key` subject affected, or it has an `OdrKey`, `OutputSection` or `Link` subject (IN-75a) | kept |

"Touched" is every `ChangedFile` (changed, appeared, gone, drawn-in,
extracted, no longer extracted); "affected" is `resolved.affected`.
Then `sort`: `(phase, current rank of unit for the FileId phases, seq
(phase 80's `unknown-property`: its file's rank, F-2), plain text,
model)`, equal rows deduplicated. `emit(view, changed, resolved, rows,
&Collector)` (a new `pub fn` in my file: **needs the supervisor's
word**, it is the join's call) maps each rank to its dense position
(the full link's unit is the file's position in load order) and emits;
dormant rows are skipped; `--fatal-warnings` and `-w` are the
collector's.

### 2.2 Ruling 4: a COMDAT copy killed or revived in an unchanged file

**The key is affected; no new rule and no `layout` parameter are
needed.** IN-71 (`spec/incr.md`, the affected set): "every global key a
changed, appeared, gone, drawn-in (IN-72 item 2a), newly extracted or no
longer extracted file mentions". IN-72 item 2a: "An unchanged file is
**drawn in** when the update must change its sections or its `.symtab`
block for a reason outside it: a section of it becomes live (IN-71a) or
kept (IN-71's election), or stops being so". The code does it:
`update/resolve.rs` re-elects a group and draws in both the old and the
new keeper (`for f in [old, new] … if self.cx.changed_file(f).is_none()
&& self.live_new(f)? { self.draw.insert(f) }`), and `affected()` adds
every key a drawn-in file mentions. A drawn-in file is "touched" for
`diags`: its stored references are dropped and its references are
re-read by the update's scan of that file (it is read anyway, IN-72 2a).
Test `gnu_warning_reference_in_revived_section` (AArch64, x86-64; GCC
C++ `inline` function calling the warned `extern "C"` symbol in `k.o`
and `o.o`): k.o drops its copy, o.o's copy is revived; the update draws
o.o in (the test asserts it), and its standard error names
`o.o:(.text._Z5use_wv+…)` as the full link's; the reverse hop (k.o's
copy back, o.o's killed) likewise. Proposed IN-75a sentence (F-6's
companion): "A reference-site row's references in a drawn-in file are
dropped and re-read: a section killed or revived by a re-elected group
is in a drawn-in file (IN-72 item 2a), whose keys are affected (IN-71)."

### 2.3 Reference-site rows (A+, rulings 3 and 5)

`DiagRef { file, seq, offset }`: the referring file's `FILES` row, the
scan's seq (section index << 32 | relocation index) and the
relocation's `r_offset`. **A place's text needs, beyond (file, section
index, offset): the file's display, from `FILES` (`odr::stored_display`,
WP-220 §K), and the section's NAME, from `SECTIONS.name` of row
`FILE_INDEX.ranges[Sections].first + section index`** (capture writes
one `SECTIONS` row per ELF section in index order, its name
`object.section(i).name()`, the very expression the scan's
`section_name` uses, `crates/mortar_incr/src/capture.rs` and
`mortar_scan/src/view.rs`). The state has both; no column is added.

Recompute of key K's row (stored `S`, fresh `F`):
- head: `undefined-symbol`: from `F` (no fresh row: the key is no longer
  warned: no row). `gnu-warning`: from `F` when it carries a holder
  `File` subject (the step read a holder); else from `S` when its holder
  is untouched; else no row (ruling 5: the holder gone, or changed
  without the section: dropped, exact).
- references of unread files: `S.refs` minus touched files when `S`
  holds every reference (`refs.len() == ref_count`); a capped `S`:
  `update-not-implemented (diags)`. No `S`: K's `KEY_REFS` must name no
  live unchanged file (else the places are unknown: a NEW holder, or a
  key newly undefined under `--warn-unresolved-symbols`:
  `update-not-implemented (diags)`, ruling 5).
- references of read files: `F.refs` (a capped `F` keeps the known
  prefix).
- merged by (current rank, seq); the first three listed (unread ones
  rendered by §2.3's rule, read ones taken from `F`'s listed places);
  "referenced N more times" from the total; key `(70, first.file,
  first.seq)`; subjects `Key(K)` (+ the holder); refs the first
  `REFS_CAP` in report order.

`REFS_CAP` = 64 (§2.6's numbers).

### 2.4 A finding of step 2: dormant rows (needs a ruling)

Ruling 5's "holder changed with the section: message from the new
section, references from the row" leaves a case no stored row covers:
**a key whose holder is linked but which no reference reaches** (glibc:
a member holding `.gnu.warning.K` extracted for another symbol; my
fixtures: `w.o` linked, no caller). When an update adds a reference in
a file it reads, the full link warns, but the update has neither the
message (the holder is unchanged and not read) nor even the knowledge
that K is warned. Without a remedy the update silently omits a warning
(`fatal_warnings_update_fails_like_full_link` and hop 2 of
`gnu_warning_reference_removed` failed exactly so). **Implemented**:
capture stores one **dormant row** per such `.gnu.warning.K` holder:
`dormant(&d, K, holder)` = `row((70, holder, u64::MAX), head without
places, [Key(K), File(holder)], [])`, `ref_count` 0; `diags` routes it
as a site row, keeps it while the holder is untouched, and turns it into
the warning when a read file references K; `emit` never prints it; a
warning whose last reference goes becomes dormant again. Cost: one row
per warned key in the link (≤ 112 for glibc's whole set, §1.6 b). It
also tells the producer of fresh rows which keys are warned (§2.8).
IN-75a's "holds every warning of the link" needs the sentence: "and one
row per `.gnu.warning.K` section of a linked file whose key no live
reference reaches (stored, never printed)".

### 2.5 `executable-stack` (F-1, ruling 7)

Least-ranked of the fresh rows and the stored row of an untouched file;
the stored row's file touched and no fresh row at or before it:
`update-not-implemented (diags)` (the next exec-stack file may be an
unchanged one the update does not read).

### 2.7 Ruling 11 against the rules (quoted, not followed beyond `diags`)

Ruling 11 (an update never prints an error of its own: any error, or a
warning under `--fatal-warnings`, abandons the update before its first
write and the full link runs) differs from three rules today:

- IN-5: "An update reports exactly the diagnostics a full link of the
  same inputs would: errors and warnings found in the changed files are
  found again; … On failure the update does what a full link does
  (image.md I-65, I-66: the output is removed) and also removes the
  state."
- IN-48: "The state is written only by a successful link (image.md
  I-100). A failed update removes the output (image.md I-66) and the
  state. … *Test:* an update that introduces an undefined symbol leaves
  neither file; the next `--incremental` link reports `no-state`."
- IN-70's table, row U9: "a block that fails its hash: `state-corrupt`
  (a refill error is the link's own diagnostic, IN-5)".

They describe an update that FAILS with its own errors (equal to the
full link's) and removes output and state; ruling 11 has it fall back,
and the full link then fails. The observable outcome agrees (status,
standard error, the output removed) if the fallen-back full link also
removes the old state (IN-48's `no-state` test); it differs in cost and
in who prints. The code decides nothing yet: the orchestration
(`crates/mortar/src/update/mod.rs`: "The orchestration itself … is
**U-10**'s and is not wired"). IN-75a's own test name says "(exit
status and no state written, as the full link)", compatible with both.
**For the coordinator to rule.** `diags` is the same under both: it
returns warnings only; `emit` under `Policy { fatal_warnings: true }`
yields a failed report equal to the full link's
(`fatal_warnings_update_fails_like_full_link` checks the text and the
status); the join then either falls back (ruling 11) or fails (IN-5).
