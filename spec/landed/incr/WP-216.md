# WP-216 (U-4): the delta layout

`mortar_layout::delta::layout(stored, changes, threads)` filled
(`crates/mortar_layout/src/delta.rs`); its tests in
`crates/mortar_layout/tests/delta.rs`, with the M.1 fixture
`tests/data/m1.txt` (extracted by `tests/data/m1_extract.py` from
review-in72's protobuf 3.21.12 `strutil` objects). No signature, shared
type, `mod` line or dependency edge changed. No link calls `layout`: the
update is not wired until U-10, so a plain link runs exactly as before.

## Q. Open questions (each needs a ruling; the code takes the named fall-back)

- **R-1 Items 5 and 6 have no input.** `SectionChange` carries a
  section's shape, not its merged pieces nor its `.eh_frame` records. So
  a live `.eh_frame` (or x86-64 `SHT_X86_64_UNWIND`) of a changed or
  drawn-in file, and a live `SHF_MERGE` section with contents and no
  placed previous version, end `update-not-implemented (layout)`. Every
  real GCC/Clang object has `.eh_frame` (and `.comment` is merged), so
  today no real object's update gets past U-4: the M.1 series runs with
  those sections ignored by the test's extraction, as WP-207's model
  ignored them. Proposed: add to the seam, per changed file, its pieces
  (merge class, content hash, size) and its CIE/FDE records (size,
  target section), or rule that U-4 receives `.eh_frame` and merged
  sections as packed sections rewritten whole by another package.
- **R-2 Item 11 has no input.** A winning common's SymbolId, size and
  alignment, and its winning file, are not in `SectionChange`; the full
  link places commons after `.bss` inputs from `sym_place`, outside any
  file's region. `LayoutDelta::commons` stays empty. Proposed: a
  `CommonChange { key, file, size, align }` list beside the changes, or
  that U-1/U-2 synthesise a `SectionChange` for each winning common
  (name `COMMON`, `SHT_NOBITS`, the file's next index).
- **R-3 The sparse placement.** `LayoutDelta::placement.place` is a column
  of length (largest id it places)+1, `NONE` where the section is "as
  stored"; `placement.holes` holds the holes of the touched chunks only
  (they replace those chunks' stored holes); `sized` is empty. The type's
  doc says "every hole of the output" and IN-18c speaks of the whole
  `Placement`. A whole placement would cost O(output), not O(change).
  Proposed text for the `LayoutDelta.placement` doc: "the places of the
  sections this update placed (`NONE`: as stored), every hole of every
  chunk it touched (they replace that chunk's stored holes), and every
  chunk; `sized` is empty".
- **R-4 Item 7 has no slot demand.** Nothing says which GOT/IPLT/TLS slots
  a changed file now needs, so nothing is appended; a stored slot keyed
  by a local of a changed file ends `update-not-implemented (layout)`
  (IN-28b's conservative branch). `LayoutDelta::slots_*` stay empty;
  `two_ifuncs_added_irelative_order` waits on this.

## F. Spec findings

- **F-1 (IN-72 item 3)** "opened in load order of the files": the update
  has no load rank, only FileId; regions open in FileId order. Proposed:
  "in FileId order (the load order of the first link; an appended file
  after every stored one)".
- **F-2 (IN-30, IN-72 item 2 Overflow)** "(O, c)'s tail reserve": the
  full link gives one tail per output section, not per category. The
  overflow region opens at O's last chunk. Proposed: "at O's tail
  reserve (shared by its categories)".
- **F-3 (item 9, arch.md)** on AArch64 `.text`'s tail is on the island
  chunk after it (and a `Merged` chunk can be O's last), so a `.text`
  overflow there is `reserve-exhausted`. Proposed: the full link puts
  O's tail on its last body chunk, or the spec says so.
- **F-4 (IN-32, IN-33)** the last `PT_LOAD` has no file reserve after it
  (the section headers follow), and the last chunk of each run and the
  chunk before `.pad.relro` have no tail (capacity = size). So any
  growth in the RW file part, and any overflow of `.data.rel.ro`, is
  `reserve-exhausted`. Proposed: say so in IN-33, or reserve there too.
- **F-5 (IN-72 item 3)** "their sections are moved sections of unchanged
  files": a growth step's followers are not listed in `moved`; they are
  in `growth_steps` and the moved chunks. Proposed: "listed by
  `growth_steps`; U-6 enumerates them by chunk".
- **F-6 (item 10)** "an output section left empty" is not detected: no
  member count is stored.
- **F-7 (item 4)** "rewritten whole in full-link order": there is no
  member index for a packed section; a packed section that changes is
  refused.
- **F-8 (item 2a)** a drawn-in file's merged sections are refused (R-1).
- **F-9 (item 1)** a gone merged section's fragments do not lose their
  reference (an over-count: a fragment stays live, safe).
- **F-10** `.note.GNU-stack` and `.note.gnu.property` changes are ignored
  here (they are U-2's `property-changed`).

## J. What U-10 must know to call `layout`

- Pass every section of a drawn-in file (`old == Some(id)`), and a gone
  file's rows with `live == false`; `changes` sorted by id.
- `regions_of` / `sections_of` must answer empty for a new FileId.
- The result's placement is sparse (R-3): `NONE` = as stored; its holes
  replace the stored holes of the chunks they name only; its chunks are
  every chunk.
- `growth_steps` lists the moved chunks; segments are re-derived and the
  `p_type` multiset is the stored one.

## G. Gate and what a plain link pays

Gate lines are in the hand-back. A plain link pays nothing: `layout` has
no caller outside its test (`grep -rn delta::layout crates xtask`), the
diff since 294101b1 touches only `delta.rs`, its test and test data, and
`cargo xtask static-identical` shows `0 differ`.

  output or run.
- The M.1 series keeps only each object's non-empty, non-merged
  PROGBITS/NOBITS sections of hole-tolerant output sections (as
  WP-207's model did; `.eh_frame`, merged, debug and packed sections are
  left out, R-1); real objects whole are refused today.
- The M.1 first link is the `World` harness's, not protoc's real link
  (main.o, strutil and a stand-in third file), so the absolute
  addresses differ from the model's; the moved counts match exactly.
- i386 and growth steps across a RELRO boundary on AArch64 were not run.
- Thunk fitting into an island (U-8/U-9).
