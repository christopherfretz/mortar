## F. Spec findings and their rulings

- **F-1 (IN-72 item 3), accepted.** Several files' new regions in one
  tail open in **FileId order** (the stored `FILES` order; an appended
  file after every stored one), not by rank. Sound: the order decides
  WHERE a region goes, never WHAT is linked (every section is placed
  either way, and IN-78 compares the update's placement with its own
  replay, not with a fresh link's addresses), and it is a function of the
  state and the inputs only (IN-6). Item 5's order is the full link's and
  is by rank (seam 4's `EhFile::rank`).
- **F-2 (IN-30, item 2 Overflow), accepted as text.** "(O, c)'s tail
  reserve" is O's tail, shared by its categories: the full link gives one
  tail per output section; the overflow region opens at O's last chunk.
- **F-3 (item 9) and F-4 (IN-32, IN-33), accepted as v1 behaviour.**
  On AArch64 `.text`'s tail is the island chunk after it (and a `Merged`
  chunk can be O's last), so a `.text` overflow is `reserve-exhausted`.
  On both targets the last `PT_LOAD` has no file reserve after it (the
  section headers follow) and the last chunk of each run and the chunk
  before `.pad.relro` have no tail (capacity = size), so a growth step in
  the RW file part and any overflow of `.data.rel.ro` is
  `reserve-exhausted`. **What can never succeed on AArch64 because of
  them**, row by row of the edit table (IN-73, which maps WP-064a's edits
  to IN-72's items):

  | edit (IN-73 row) | on AArch64 |
  |---|---|
  | weak made global or back (W1, W1b); a call bound elsewhere (W9); visibility (n2); a local made global (W10) | not affected (no section changes size) |
  | a definition moved inside its section (n1); a section's size, count, type, flags or alignment (`layout-changed`); a file named twice | succeeds only inside the file's own regions (keep, place, holes, region slack). A `.text` section that overflows its regions: never (F-3). A `.data.rel.ro` section that overflows: never (F-4). A `.data` (RW file part) overflow that needs a growth step: never (F-4); one that fits O's tail: succeeds where O's last chunk has a tail. New code with no `.text` region in the file: never (its overflow goes to `.text`'s tail) |
  | a `--gc-sections` liveness flip (W8) | the revived section as the row above; refused before that by `update-not-implemented (live)` (WP-215) |
  | a function made an IFUNC (n3) | `symbol-kind-changed` first; its IPLT slot is item 7 (refused wholesale) |
  | a common made a definition (n4) | the join's `update-not-implemented (common)` (R-2) |
  | merged contents changed (s4, W6); a GOT slot keyed by a section symbol (s3) | refused wholesale (items 6, 7) until WP-239 |

  On x86-64 the `.text` rows succeed into `.text`'s tail (no island);
  the `.data.rel.ro` and RW growth rows are the same as on AArch64. And on
  both, every real GCC/Clang object has `.eh_frame`, so until WP-239
  every real update ends `update-not-implemented (layout)` at item 5
  first; the go/no-go counts read against this table only after that.
- **F-5 (item 3), accepted.** A section moved only by a growth step is
  not in `moved`; it is in `growth_steps` and the moved chunks (an
  address = the chunk's new address + the place's offset; seam 4's docs).
- **F-6 (item 10), DETECTED.** An output section that lost a member in
  the update (a section of a file of the update placed in it before and
  not now, or an old version's row) and in which the update places none
  is `new-output-section` ("output section X left empty") unless one of
  its chunks still holds a live byte. No member count is stored, so the
  proof is by bytes: every byte of a body chunk is a live section's, a
  hole (slack, a dead section), or alignment padding before a member or
  region, shorter than the chunk's alignment; a run of non-hole bytes at
  least that long holds a live section, and a non-body chunk with bytes
  is live. Anything else is taken as empty and refused (so an output
  section left with only empty or short sections between holes is a
  refusal, never a kept empty section). It reads `HOLES` of the lost
  output section's chunks (key reads). Test:
  `output_section_left_empty_is_new_output_section`.
- **F-7 (item 4), accepted for v1.** A packed section is kept at the
  same place and size, else `update-not-implemented (layout)`.
- **F-8, F-9** are gone with seam 4: a drawn-in file's merged pieces and
  a gone file's fragments are item 6's, refused wholesale until WP-239
  (`FRAGS.refs` must be exact: S4-2).
- **F-10.** A changed `.note.GNU-stack` or `.note.gnu.property` is not
  placed (both are consumed: `fate` ignores them; the full link derives
  `PT_GNU_STACK` and the output's property note from them). The rule is
  IN-72 item 10's `property-changed` (the property note's size, §7; the
  stack: the `PT_GNU_STACK` flags would change, which no row names
  today) and, as ruled, **the join (U-10)** checks it, from the new
  versions' notes merged as the full link merges them against the stored
  output's. The open point of §11 item 11 (the bits at the same size)
  stays WP-064's.

### W.1 Item 6

- `FRAGS.refs` counts FILES (WP-239 S4-4), exact after the update
  (IN-78): per file of the update, its stored `FRAG_USE` range is −1 per
  key, its new version's distinct `(out, MergeClass::word(), hash)` keys
  +1 (a gone or not-extracted file: −1 only; an appeared or drawn-in
  one: +1 only). Only the keys whose net change is not 0 are read
  (`frags_of`) and written (`LayoutDelta::frags`, by key).
- Falls to 0: the row stays (offset kept, refs 0). A constant becomes a
  `Fill` hole of `entsize` bytes. A string is refused (finding C).
- Rises from 0: revives at its stored offset; its hole (`Fill` or
  `DeadFragment`, exactly the stored one) leaves `HOLES`. **How U-6
  learns of it**: the delta's `frags` row has `refs > 0` and the stored
  row (`frags_of`, still the old state when U-6 runs) has `refs == 0`;
  U-6 rewrites the bytes at `offset` from the piece. No new field.
- New key: appended at the merged chunk's tail, in `out` then
  first-occurrence order (files ascending, pieces in order), offset
  rounded up to the class's alignment. Past the chunk's capacity: an
  allocated merged chunk takes item 3's growth step (stage D gives the
  tail's capacity to the segment's reserve); a non-allocated one is
  `reserve-exhausted (<name>: merged tail)`. Growing a chunk whose end a
  `DEFINED` row names is refused (`end_symbol_refused`, finding G).
- `.debug_*` / `.zdebug*` pieces: `update-not-implemented (debug)` by the
  section's name, before any count (R-1). A merged section the join gave
  no pieces for, a piece of a section the update does not name, a piece
  of another file: `update-not-implemented (layout)`; a `FRAG_USE` row of
  another file, a key with no `FRAGS` row, a count below 0:
  `state-corrupt`.

### W.2 Item 7

- `SLOTS.refs` +1/−1 once per FILE per kind its flags need (WP-239
  S4-4): the old demand is the file's `KEY_REFS.demand`, the new is

- IN-28b: a local's slot is its file's alone. A CHANGED file's live

- What the seam carries: a slot at 0 is `slots_dead` (written 0, S-113).

### W.3 Findings (need a ruling)

- **A. No shared flags→kind function existed.** The table was inline
  in the private `mortar::front::slots_of` and copied in
  `Layout::check` §4.3. Commit "WP-242 finding A" adds
  `SlotKind::demand` in `mortar_core::layout`; both callers and item 7
  use it. If dropped, item 7 must stay refused.
- **B. `LayoutDelta` has no field for a live slot's new count, or a
  revived slot** (`slots_dead` / `slots_appended` only). Proposal:
  `slots: Vec<StoredSlot>`, every row whose `refs` changed. Until then
  refused.
- **C. A dead string's length is not stored**, so its `DeadFragment`
  hole cannot be made. Datum: `FRAGS.size` (u32): +4 B a row (protoc's
  ~1,554 rows ≈ 6 KB; clang's ~127,630 ≈ 510 KB). Until then refused.
- **D. A slot region's capacity is not stored** (S-63 at M1: capacity =
  count; R-M4's stored capacity is not built), so every append is
  `reserve-exhausted`.
- **E. A dead slot's GOT bytes**: IN-72 says "written 0 and a hole"; the
  delta gives the row only (`slots_dead`), no `HOLES` row for the slot.
  U-6 writes the 0; whether a hole row is needed is the supervisor's.
- **F. PLT/IPLT retirement** changes `.rela.plt`'s size (rewritten whole)
  and `__rela_iplt_end`; the delta gives neither. Refused.
- **G (the coordinator's question): `placement.defined` is WHOLE.**
  `layout` passes the stored `DEFINED` through whole and unchanged
  (`Base::read` → `stored.defined()`; `finish` →
  `base.rest.defined.clone()`). Values are `At { chunk, offset }`, so
  they follow a chunk a growth step moves. A row naming a chunk's END
  (`At { c, old size }`: `_end`, `_edata`, `__stop_*`, `*_array_end`,
  `__rela_iplt_end`, `etext`) goes stale when the update grows that
  chunk's size: item 6's append refuses it (`end_symbol_refused`);
  U-4's overflow regions grow chunks too (suspected from the code, not
  checked on bytes). Item 7 changes no chunk size:
  `_GLOBAL_OFFSET_TABLE_` (offset 0) is unaffected and the IPLT bounds
  are kept by refusing PLT/IPLT retirement (F). Nothing is added to
  `defined`.
  **Seam doc line owed** (`mortar_core::incr::LayoutDelta`, not edited
  here): "`placement.defined` is the stored `DEFINED`, whole and
  unchanged (chunk-relative values follow their chunks); a row whose
  value is a chunk's end is not moved when the update grows that chunk;
  the update refuses where it would grow one."

### W.4 F-6's corner

Constructed (`f6_corner_empty_region_between_paddings`, both 64-bit
machines, three cases): `.data` of 1 byte (align 1), an empty section
(align 8) and 8 bytes (align 16), one file each, so the empty section
sits between two paddings. When the live sections die, the output
section is always refused (`new-output-section`), never kept. The
argument (in `left_empty`'s doc): a run of paddings is shorter than the
largest alignment, which is at most the chunk's, so a chunk with no live
byte cannot look non-empty. The one code change: `placed` counts only
sections with `size > 0`. The exact datum that would make this a count
rather than an argument: an OUTSECS live-member count, u32 per `OUTSECS`
row (< 1 KB), ±1 per placed or killed section and per fragment 0↔>0.
Not added.
