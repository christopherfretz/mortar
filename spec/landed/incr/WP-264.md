## `REGIONS` (51)
- **Producer**: `capture::region_rows`, called in `state5_rows` after
  the `SYMTAB` check. It reads the full link's stored placement (the
  `SECTIONS` places, `CHUNKS`, `HOLES`) and rebuilds the regions where
  `mortar_layout/src/chunk.rs` made them (`plan_parts`, `close`,
  `region_key`): in a hole-tolerant (`slack::class == Tolerant`) body
  chunk, a region is a run of members of one (file, category) key, the
  category the section's text category under `SHF_EXECINSTR`, else 0;
  it starts at the run's first member and ends at the end of the `Fill`
  hole that is its slack (none: at the last member's end, the chunk's
  last region). A run breaks at a key change and at a `Fill` hole.
  Ordinals count each (file, output section, category)'s regions in
  address order.
- **Check** (`capture::regions_check`, every capture, `state-corrupt`
  words "REGIONS: ... (IN-30, IN-72 item 2)"): each region in a
  tolerant body chunk of its output section, inside it, no two
  overlapping; ordinals dense in address order; every member of such a
  chunk in a region of its own file and category; each region starting
  at its first section and holding one; its slack the `Fill` hole from
  its last section's end to its end (or none, as the chunk's last);
  every `Fill` hole some region's slack.
- **What it changes**: an unchanged file given to `delta::layout` as
  changed keeps every section in place and opens no region (both
  targets, `m1.o` and `m2.o`: 3 regions each). Before this package (the
  same state with `REGIONS` emptied) the same call refused
  `reserve-exhausted: .text: its tail is in a patch island chunk` on
  AArch64 and moved all three sections to 3 new overflow regions on
  x86-64.

## F-1: file 0's internal block
- File 0's `SYMTAB` range holds two rows: the global area, then the
  internal file's block (`incr_blocks`' `FileId(0)`, which WP-263 left
  without a row). `symtab_rows_check` requires exactly area, internal,
  then the files' blocks.
- Reader: `symtab_of(FileId(0))` is the area (first row) as before; a new
  `StateRows::symtab_internal` (view.rs; `Reader`, `&MemoryState`) is
  the second row; `LayoutOf::symtab_block(FileId(0))` answers it (it
  answered the area: F-1 below). Decode and the encoder (write.rs) admit
  two rows in file 0's range, one in every other.
- `map.rs`: WP-263 F-3's `retain` is removed; `update_map` states the
  stored internal block as `symblock -`.

## `DIAGS` (49): what an update loses today
No producer (ruling asked, below). `tests/state_producers.rs`
`diags_hold_no_warning_today` sees the gap: the full link prints the
reference-site warning; its state holds no `DIAGS` row; an update with
`m1.o` changed refuses `update-not-implemented (diags)` (path (A)'s
`image_link` falls back on any front diagnostic, `update/mod.rs`
~948-966), one with nothing changed refuses
`update-not-implemented (resolve)`. So **no warning is lost today; the
update is**: a link that warns never updates. Nothing in
`crates/mortar/src` calls `update::diags::diags` yet; once U-9's join
replays `DIAGS`, an empty table drops the stored warnings of unchanged
files (and `--fatal-warnings` would pass where the full link fails).

## `META.boot_id`; the clone probe
- `incremental.rs` `state5_bytes` sets `META.boot_id` from
  `update::write::boot_id()` (`/proc/sys/kernel/random/boot_id`, read
  safely); unreadable gives zero, which no boot matches (the update
  re-hashes). `canon` already zeroes it, so the static-identical and
  canon comparisons do not see it.
- `MetaRow.clone_probe` and `CloneProbe` are removed (never written nor
  read): `META` is 196 bytes (was 228); the probe's flag byte stays as a
  pad that must be zero.

## Findings
- **F-1** (fixed): before this package `LayoutOf::symtab_block(FileId(0))`
  returned the global area, so `symtab_incr::rewrite_file` for the
  internal file and `update_map` read the area as the internal block.
- **F-2** (for the join): `FileRanges::symtab` holds ONE row per file;
  a patch of file 0's range must write two (area, internal block).
  Nothing writes it today.
- **F-3** (IN-77c): the rule says a full link that cannot read the boot
  id `fdatasync`s `T` and writes `output-synced` 1 (form (a)); the
  capture writes the bit 0 always (only compaction and the patch write
  1). With zero for the boot id the update re-hashes, which is safe.
  Not verified whether `floor.rs`'s syncs implement form (a).
- **F-4**: a no-change `--incremental=update` of the warned line refuses
  `update-not-implemented (resolve)`, not investigated.
