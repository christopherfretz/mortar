### 0.1 The decision that needs a ruling first: what `Link` the refill gets

`mortar_image::update::refill` (`crates/mortar_image/src/update.rs:135`)
and `mortar_image::map::update_map` (`map.rs:922`) take the IMAGE's
`Link<'_, '_>` (`crates/mortar_image/src/link.rs:257`): `inputs` (every
file's parsed model), `resolution`, `assignment`, `liveness`, `split`,
`order`, `records`, `demands`, `layout`, `eh: (&EhPlan, &dyn EhSource)`,
`synth`, `facts`, `proof`, `recheck`, `fixups`, `args`. Every field is a
WHOLE-PROGRAM structure of a front; no function builds one from a
format-5 state plus the changed files. U-6's own tests
(`crates/mortar/tests/update_image.rs`) build it from "a second front
over the edited inputs" (its module doc), and WP-218 §C lists what the
image's table builders read of every unchanged file (every placed
section, symbol, fragment, fixup, the eh plan). So the callee FORCES a
whole front: IN-18c's defect class, and the largest one.

Two ways, both named so the ruling can pick:

- **(A) v1: the whole front over the new inputs, its layout replaced by
  the materialized `P_U`** (the front's replay hook, IN-61, `front::Env::
  replay`, `crates/mortar/src/front.rs:296/1189`; the floor's own
  architecture, `crates/mortar/src/floor.rs`). The U-steps run on the
  `StateView` as the cut says (they decide the placement, the refill
  set, the symtab plan, the patch); the front supplies the image's
  `Link`, and the per-file producers of U4 (0.3, G-2) read the changed
  files' rows from that front with the capture's own functions (one
  producer for a full link and an update: the stale-datum class is
  narrowed to the delta's own decisions). Correct soonest; every
  milestone M2-M5 is judged on it. **It cannot meet the go/no-go**: the
  front is most of a full link (spec/incr.md §1.5, protoc without `-g`,
  120.7 ms: input 57.7, resolve 8.4, assignment 4.1, split 3.5, scan
  4.4, synthetic 3.3, layout 21.8, image 13.5 ms; WP-244: plain protoc
  0.23-0.24 s), so an (A) update is a full front + the delta's steps +
  the materialization + the refill: above a plain full link. M6's table
  would record the miss as a FINDING with its phases, as the brief
  allows, but it is decided now by construction, not by measurement.
- **(B) the lazy `Link`**: a `Link` whose unchanged files are backed by
  the state's rows and parsed on demand (only the units the dirty
  windows reach: a window is filled whole, image.md I-95, so unchanged
  units overlapping a dirty window are parsed and relocated too), plus
  a per-file front (parse, split, scan of the files of the change
  alone, the scan's `KeyFacts` from `RESOLVED.facts` and the delta).
  That is a change of `mortar_image`'s `Link`/`LinkTables`/`layout_plan`
  and of the facade's front: not mine, and larger than the join (my
  estimate: L, design first).

**Proposal**: (A) for this package, with every U4 adapter and the
`Link` behind ONE function of `mortar::update` (`fn image_link(..)`),
so that (B) replaces that function and the U4 producers without
touching the orchestration's order; (B) cut now as its own package
(design step, then code) so the go/no-go is taken on (B). (A) also
gives an internal cross-check for free in tests: the whole front's
resolution against `ResolveDelta`, its capture against the update's
patch (the in-crate (d), 0.4 G-11).

## M2b-3 design (Part 1: the note; no code until it is ruled)

Base d2867b91 (batch 20 + WP-263). Read, not run: no build or
experiment was made for this note. "Front" is `crate::front::Front`;
"update ids" are the state's rows plus `ChangedFile::first_section + k`
(ruling 3 of M2b-2b: a changed or drawn-in file's sections take FRESH
ids); "front ids" are the front's `SectionId`, `ChunkId`, `OutSecId`,
`SymbolId`.

### D-1 The shape: a second front, only when the identity check fails

The delta needs the front: `changed_files` reads the changed files'
rows from `f`'s tables (`changed.rs:63-127`, `file_rows` over
`f.layout`), `u5` and `facts_into` judge against `f`'s capture. The
image takes a placement only inside a front, through `Env::replay`
(`front.rs:1220-1239`), called before `Layout::validate`. So one front
cannot both produce the delta and take it without moving U4-U7 into the
hook (they read `f.incr5`, `f.liveness` and the capture, which exist
only after the hook). The design:

1. Front 1, as today (`image_link(ctx, cwd, None, ..)`): U4-U7, the
   delta `d` (update ids), the identity check.
2. Identity case: unchanged (front 1's refill, capture and state; D-7).
3. Otherwise: `materialize` (D-2) turns `(stored, d, inputs.changes)`
   into `(L_U, d_F)` against front 1's link and computed layout: `L_U`
   a whole front-id `Layout`, `d_F` the delta in front ids (D-3).
   Front 1 is dropped (its `Layout` kept as `L_1`, O(sections)).
4. Front 2: `image_link(ctx, cwd, Some(&hook), ..)`. The hook checks
   `computed == L_1` (the front is a deterministic function of the same
   inputs, plan and store; a difference is `update-not-implemented
   (image)` with the first differing table named) and returns `L_U`.
   The front then builds every plan from `L_U` and checks them itself
   (`front.rs:1256-1376`: `.eh_frame` and `_hdr` from
   `slots.eh_records` and the `EhPad` holes, S-88's spans, `.shstrtab`,
   `.got` from the slot lists, AArch64's erratum fixes from the
   placement, the merged order from `merge`, every synthetic plan's
   size against `slots.sizes`), then `Layout::validate`.
5. Front 2's `refill(l, &d_F, &symtab, &set, ..)`, its capture (the
   state written: G-11's reference "the capture of a full link with the
   update's placement", by construction), the map, `write_identity`'s
   tail as today.

Cost: a non-identity update is two fronts (O(link) twice, three times
with the capture). It changes no answer of (A)'s go/no-go (record 0.1:
missed by construction until (B)). The identity case stays one front.

The hook returns `Err(String)` to the front, which emits `internal
"replay: .."` and fails; `image_link` then says `(diags)`. The hook
therefore keeps its `IncrReason` in a `Cell` it captures, and the
caller returns THAT reason. A front-2 failure with no reason in the cell
(a plan or `validate` refused `L_U`) is `update-not-implemented
(image)`, with the diagnostic's text recorded in
`MORTAR_UPDATE_FINDINGS` as a FINDING: the translation, or the delta,
broke a rule the full link keeps. In the tests it is a test failure,
never a quiet fall-back (D-8).

### D-4 The delta in the front's ids (`d_F`), for `refill` and `update_map`

`refill` reads the delta in FRONT ids: `layout.moved` through
`link.resolution.sh_index(s)` (`mortar_image/src/update.rs:563`,
`check_moved_code`) and `place(s)` (`:226`), `frags[..].out` as a front
`OutSecId` (`:545`), `eh.chunk` and `hole_chunks` against the link's
chunks. **Today's update ids there are a latent wrong answer**: a fresh
id `first_section + k` read as a front id names another section, so
`check_moved_code` can judge the wrong section (an exec section moved,
its file's FDEs not rewritten, would not be refused). Not reachable
today (no update is taken with a moved section). So `d_F` translates:
`files` (same numbers, D-2), `moved`/`revived` (by the changes'
`(file, index)`), `killed` dropped (old rows; `refill` reads their holes,
not their ids), `holes`, `hole_chunks`, `eh.chunk`, `regions_opened`'s
chunk and out, `growth_steps[..].out`, `frags[..].out`, the slot rows'
keys; `placement` = `L_U.placement`. `update_map` reads `slots_dead`
(kind, index) and `stored.symtab_block(file)`: unchanged by `d_F`.

### D-5 The refill set and refusals

- **Refill set (ruling R-3):** U-8 (`refill::refill_set`)
  is not wired; today's set is "every chunk that is not a body"
  (`update/mod.rs:317-324`). Once sections move, the unchanged
  referrers of a moved definition must be relocated again. Proposed v1:
  the set holds EVERY chunk in the non-identity case (front 2's image is
  a full image; `refill` drops each range equal to the previous output,
  IN-75), so no referrer can be missed. Cost O(output) bytes compared.
  `refill_set` is wired later, judged by IN-79 (c).
- **Refusals propagate** (ruling 2 of M2b-2b) in the commit that writes
  `L_U`: in `reference_of`, `Why::Refused` returns its reason. Open
  for the identity case (ruling R-2).
- Order: `materialize` runs before front 2. Each check above is a
  refusal by name before any byte or row is written; front 2 can only
  add `(image)` FINDINGS.

### D-8 The test that catches a wrong translation

1. **Identity first** (`crates/mortar/tests/update_placement.rs`, new
   test `materialize_equals_the_front_in_the_identity_case`, both
   64-bit targets): a first link, a same-bytes-in-place edit (the
   identity case), `d` from the join's producers, then
   `materialize(.., f.layout)` compared with `f.layout` TABLE BY TABLE
   (chunks, order, segments, place, sym_place, defined, patches,
   redirects, sized, tls, entry, holes, frag_off, each slot list,
   tls_ld, eh_records, symtab_locals, sizes, folds), each mismatch
   printed with its table and row. All equal. It needs `d` to keep the
   stored places in the identity case (M2b2b-3, M2b-2c's item 1: the
   test derives the regions test-only until `REGIONS` has a producer).
   A testhooks build runs the same comparison on every identity hop of
   the incr-update lane (a difference is a FINDING), so the lane checks
   the translation on every hop it takes today.
2. **Mutations** of that test: swap two stored section rows' places,
   shift one chunk row, drop a `FRAGS` row, give a slot list one key of
   another file: each is a refusal by name or a table mismatch, never
   an equal `Layout`.
3. **The non-identity case** (a body grown inside its region; one grown
   past it with a growth step): `L_U` against `f.layout` with every
   difference explained by `d` (a place of a `d.files` section; a
   chunk's `addr`/`offset`/`size` after a growth step; a hole of
   `hole_chunks`; a fragment of `d.frags`; `.eh_frame` ranges of
   `d.eh`); any other difference fails. Then front 2's capture against
   `d`: each changed section's `SECTIONS` place, `FILES` eh columns,
   `FRAGS` offsets and `SLOTS` refs equal `d`'s (the image-side check
   of D-3's `.eh_frame` row). Then the bytes: the updated output against
   a full link with `L_U` replayed (equal, byte for byte) and the lane's
   `plumb` judgement.

### The signature as built

`materialize(view, stored, d, changes, link, keys, computed, classes, eh)
-> Result<(Layout, LayoutDelta), (IncrReason, String)>`: the `Layout` in
the front's ids and D-4's `d_F`. Against D-2/D-3:

- the error carries a String naming the refusal (`(x)` has no detail);
  a FINDING (both answers known, they differ) starts `FINDING`;
- two front-side inputs the note did not name: `classes` (the fragment
  class word per `merge_of` row) and the front's `.eh_frame` runs
  (`capture::EhFile`, for the per-file `fdes` check);
- the brief's "EMPTY delta" is `unchanged_delta(stored)`.

### Rules changed against D-3 (each needs the ruling)

- `placement.sized` (D-10 asked whether a static 64-bit link has a row):
  EVERY AArch64 link has rows: the empty islands, one per code output
  section (aarch64 C: chunks 15, 22, 24, `Patches(Part{out 0/6/7})`,
  size 0). The note's rule (any row: `(layout)`) refuses every AArch64
  update. Built: the front's row is kept when the delta's chunk has its
  size, else `(layout)`. Equal size does not prove the size right at the
  delta's addresses (an island's need is a distance).
- `slots.symtab_locals`: S-88 in incremental mode makes the span
  `(first, capacity)`, not `(first, count)` (aarch64 C, file 1: stored
  block first 12 count 10 capacity 12; the front's span (12, 12)). Built:
  compared with `(first, capacity)`. A file with no `SYMTAB` row must
  have an empty span.
- `slots.eh_records`: a file of `d.files` with no `d.eh` range (its
  `.eh_frame` not rewritten) keeps its stored range; a count or `fdes`
  mismatch there is `(eh)` (an unchanged file's stays `state-corrupt`).
  The S-47 record-offset check is NOT done (D-10's question open).
