# WP-094: the change order, three escapes from the floor

Record of WP-094, the change order the operator chose after WP-061
stage B (option A, 2026-11-16): prototype the three escapes stage B
named, measure again on the same workloads and edit, and restate
`spec/incr.md` §1.5's rule at the scale the feature is for. The
contract does not move: an update is equivalent to an
`--incremental=full` link (IN-2) or falls back by name, and a plain link
pays nothing (IN-11).

Every prototype lives on the branch `wp/094-incr-change-order`. Section
9 says which commits are meant to merge.

## 1. Method

- **Host**: AArch64, 12 cores, shared. Two other packages compiled
  large programs under the jobserver for the whole session (WP-081's
  LLVM, WP-100). The 1-minute load was 7-16 for nearly all of it; it
  never stayed under 6. Every table below that was taken above load 6
  is **provisional** (the brief's rule). The tables were not repeated at
  a lower load because none came.
- **Harness**: stage B's (`scripts/incr-floor.py`, `mortar::floor`, the
  `incr_floor` example), with three additions (commit 86e8c73):
  `--interleave` (each round runs every series once, so that ratios are
  taken under the same load), series items `LABEL:KIND:BIN:MORTAR` (to
  compare binaries in one series), and `--extra`. Ratios between series
  of one interleaved run are what counts; absolute times move with the
  load by up to 2× between runs (g10x's plain link: 1.50 s in stage B
  at load 5.8, 2.1-4.8 s here at load 8-12).
- **Equivalence**: after each update series the update's output is
  compared **byte for byte** with a fresh `--incremental=full` link of
  the same edited inputs (`identical` below). Every update in this
  record was identical.
- **Binaries**: release builds copied to the scratch
  `/tmp/mortar-wp094-<pid>/bin`: `main` is the branch base 1d96204,
  `a`, `b`, `c` the prototypes as they were committed.
- **Workloads and edit**: stage B's, unchanged (WP-061b §1): protoc
  `-g` with thin archives, the edit in `importer.cc.o`
  (`0xa04: 00008052 -> 20008052`); `synthetic-objects-g10x` (8,150
  objects, 82 thin archives), the edit in `o00514.o`
  (`0x210: 931e0011 -> 93220011`).

## 3. Escape (a): unchanged files translated by position

**What it is** (commit 2f6e73a, with the degradations of section 9's
follow-up commit). The state gains two columns and one table (format
version 3, proposed as `spec/incr.md` IN-18a3): each `SYMBOLS` row
records where the key was read (`at_file`, `at_index`: a local's own
file and symbol index; a global's first-mention file and its position
among that file's non-local entries), and `FRAG_AT` keys every
fragment of a split section by (section, offset). The update
(`capture::replay_by_position`, IN-28a) then maps:
- a `FILES` row to the new file by file identity (path, member), as
  before: never by row number;
- for an unchanged file, its `SECTIONS` rows by arithmetic
  (`section_base[file] + index`), its locals to `(file, at_index)`, its
  globals through `sym_map(at_file)[at_index]` with the name and
  version checked, its fragments through `FRAG_AT` with the stored
  fragment hash checked;
- every other row through identities built from the files that are not
  positional only (`Keys::partial`); a global that partial lookup does
  not hold builds the whole lookup once.

**Conditions** (each checked; none assumed). A failed condition never
gives a different output: the row goes to the identities, which
translate it or fail by name as IN-28 does.

| condition | checked by | when it fails |
|---|---|---|
| the file is unchanged | IN-22: stamp clean, or the content hash equal (the test path hashes; step 3) | the file's rows go through identities |
| the file's new entry is the same range of the same file (`base`, `len`) | `FILES` row against the new `inputs.files` entry | the file goes through identities (a member moved inside a regular archive, an archive rewritten around an unchanged member) |
| the file has the stored number of sections | `section_base[file].len()` against the count of its `SECTIONS` rows | the file goes through identities |
| `SECTIONS` rows are contiguous per file, in file order | one pass over `SECTIONS` | no file is positional |
| a global at its position is the same key | name and version of `sym_map(at_file)[at_index]` against the row | that row goes through identities (the partial lookup, then the whole one) |
| a fragment at its position holds the same bytes | `FRAG_AT` by (section, offset), then the `FRAGS` hash | that fragment group goes through identities (`frags_by_identity`) |
| the file is in the same place on the command line | the plan hash (IN-18b) | `options-changed` before any of this |
| unchanged members are extracted in the same relative order | the delta (WP-063) | `inputs-reordered` (§7) as before |

Prototype limit: the test path builds the partial identities from the
changed file only, so an unchanged file that fails a per-file condition
fails the replay by name (`internal-error`, the test path's refusal)
instead of translating; the update (WP-064) must decide the positional
set before it builds the identities. No measured edit met that case.

**Measured** (protoc: `c0`/`a1` diagnostics, load 9-13, provisional;
g10x: the interleaved series of section 2, load 7.5-11.7, provisional).

## 4. Escape (b): per-file symbol tables and `.eh_frame`

**What was built** (commit 0aecc4b). The test path's dirty set takes
`.symtab`, `.symtab_shndx` and `.strtab` as the changed file's own
ranges (`SymtabPlan::file_entries`: its `Locals(f)` and `Demoted(f)`
segments, and its globals found from the 1,024-id checkpoints), and
`.eh_frame` as the range of the changed file's records (IN-34a: per-file
CIEs make it contiguous; an error if not); `.eh_frame_hdr` stays whole.
The writes cover the dirty ranges only, not whole windows (the windows
are still refilled whole, I-95, because a window's bytes are read from
the image). What was **not** built: slack (synth.md Q8's capacity) in
`.symtab`/`.strtab`. Without it, an edit that changes a file's number of
symbols or the length of its names changes every later range: the
prototype covers same-size edits only, which is all the floor measures.

**Dirty set per edit** (identical to the full link in every case):

| protoc, whole tables (before) | 15 | 15,333,160 | 7,317,983 (`.symtab`/`.strtab` 5,421,401; `.eh_frame` 988,464; `.debug_aranges` 681,872; the file 229,666) | 15,333,160 (windows) |

On g10x the per-file tables remove 147 of 172 windows and 99.7% of the
written bytes; the update's writes in place fall from 150 ms to 16 ms.
What remains is set by the 1 MiB window (13-26 MB refilled for under
1 MB dirty): `.debug_aranges` (rewritten whole, IN-54) and the changed
file's globals, which sit at their `SymbolId` places across 7 windows.
Per-file global ranges (the globals ordered by definer, not by id) would
make them one range.

**IN-2.** Without slack nothing changes in the bytes: every update was
byte-identical to the full link, so IN-2 holds and the verifier needs no
rule. With slack (Q8), it would not be byte-identical, and plumb.md §6.9
P-E3 would need a ruling (a **request**, not made here):
- P-E3 compares globals by name and locals as a multiset, so the
  **order** of a per-file layout is inside the rules already (P-E3:
  "their order and indexes may differ"); the full link in incremental
  mode would use the same per-file order anyway;
- a **hole** is an entry `F` does not have. P-E3 has no rule that passes
  one over; it would report it. The request: P-E3 passes over entries
  of `X` of one stated filler form (proposed: `STB_LOCAL`,
  `STT_SECTION`, `st_name` 0, `st_value` 0, `st_size` 0, `st_shndx`
  the index of a section of the output, before `sh_info`), and the
  `.strtab` bytes no entry names.
- In the global area no filler is invisible to the tools (below), so
  the proposal keeps the global area dense: a file's added globals go
  to a tail reserve after the last global, and a removed global's
  entry is taken by the area's last entry (order is free under P-E3).
- `.eh_frame_hdr`: P-E5 compares it as a set; a per-file `.eh_frame`
  refill rewrites it whole and stays inside that ruling.

**What the tools make of holes and of another order.** protoc `-g`'s
output, its `.symtab`/`.strtab` rewritten by a script
(`symtab-holes.py`, untracked notes) in seven forms, then asked by
gdb 16.3, lldb 19.1.7, binutils 2.44 (`nm`, `readelf`, `addr2line`,
`objdump`), elfutils' `eu-readelf`, LLVM 19.1.7 (`llvm-nm`,
`llvm-symbolizer`) and perf 6.12 (installed for this test, gone with the
container): `info symbol`/`image lookup` of a local and a global, a
breakpoint on `main` and on `CommandLineInterface::Run`, a backtrace
through `main`; `nm` against the original; `perf report` of one
`perf.data` against each variant at the same path, with a stripped
copy as the control.

| variant (8 entries each unless said) | nm / llvm-nm | readelf / eu-readelf | gdb, lldb, addr2line, llvm-symbolizer, objdump, perf |
|---|---|---|---|
| all-zero entries after each file's locals | each a nameless ` U` row | silent | unchanged |
| `STT_SECTION` locals (section 1, value 0) after each file's locals | invisible (`nm -a` shows them) | silent | unchanged |
| all-zero entries among the globals (gABI-invalid: local after `sh_info`) | ` U` rows | readelf warns `local symbol N found at index >= sh_info` | unchanged |
| `STB_GLOBAL` undefined, nameless, among the globals | ` U` rows | silent | unchanged |
| `STB_WEAK` undefined, nameless, among the globals | ` w` rows | silent | unchanged |
| the globals reordered (grouped by section) | no difference | no difference | unchanged |
| 64 unused `.strtab` bytes after each file's names | no difference | no difference | unchanged |

So: order is free; local-area holes are free if they are `STT_SECTION`
locals (nm hides them); there is no global-area filler that `nm` does
not print, hence the dense global area above. perf's reports were
identical across all variants (the stripped control differed).

## 5. Escape (c): the first incremental-mode link

**Where the time goes.** `--incremental=full` is a plain link plus one
phase, 110 "incremental state" (the layout with slack costs nothing
measurable: phase 90 is within 2 ms of the plain link's on protoc and
within the spread on g10x). Its parts, timed by the new laps
(`mortar: incremental: NAME: MS` under `--time-phases`), medians in ms:

| part | protoc, main (c0, load 7.5) | protoc, branch (c4, load 10.4-12.2) | g10x, branch (c3, load 9.7-10.9) |
|---|---|---|---|
| keys (`Keys::new` / `Keys::for_capture`) | 31.3 | 8.1 | 15.8 |
| file hashes (every input, parallel) | 8.8 | 14.0 | 510.6 |
| capture: sections | 70.9 | 19.6 | 59.0 |
| capture: fragments | 8.2 | 9.4 | 326.2 |
| capture: delta tables (`MENTIONS`, `RESOLVED`, `INDEX`) | 35.5 | 28.1 (c3) | 1,990.8 |
| stat rows | 4.3 | 4.1 | 114.2 |
| encode | 14.1 | 10.8 | 350.6 |
| write and `fdatasync` | 30.9 | 29.2 | 912.5 |
| **phase 110 whole** | **211.1** | **117.5** | **4,733.9** |

What was changed (commits d7cbcaf, d980d71, 1d9c0e2), none of it in a
plain link's path (a plain link writes no state):
- `Keys::for_capture`: the capture's identities read per file on the
  link's pool, without the symbol lookup the capture does not use
  (31 to 8 ms on protoc);
- `Ordinals`: each row's ordinal computed in one pass (it was two binary
  searches per row), which takes `capture sections` from 71 to 20 ms;
- `MENTIONS` and `INDEX` read per file in parallel with each key as its
  `SymbolId`; the ids become rows afterwards in file order, so the rows
  are numbered exactly as the serial pass numbered them;
- the capture's string pool and maps on the fixed hash (model §6 rule
  5) instead of SipHash, and the global rows found by a vector indexed
  by `SymbolId`, not a hash map.

|---|---|---|---|---|
| protoc `-g` | 205.8 ms | 394.9 ms (1.92×) | 364.6 ms (1.77×) | 10.4-12.2 |
| g10x | 5,813 ms | 15,746 ms (2.71×) | 9,508 ms (1.64×, c3) | 9.1-10.9 |

On `cxx-large-g` (c) gains nothing measurable (2.72× to 2.68×): its
state phase is file hashes 900.9 ms, capture 903.0 (fragments 454.1),

The second g10x series, at the session's lowest load, puts the first

**What could move off the critical path or be made proportional to the
inputs read anyway** (not built; *estimates* from the parts above):
- the **file hashes** read every input a second time (511 ms on g10x):
  the input phase already reads every byte; hashing there, on the same
  workers, makes it proportional to the bytes read anyway (cost: the
  hash rate, about 0.1 ms/MB at L128's speed, against the 0.3 ms/MB of
  the second read);
- the **delta tables** are now per-file parallel except the row
  numbering and `RESOLVED`; what remains serial is one pass over
  `MENTIONS` and `INDEX` rows (about 6 M rows on g10x). Numbering keys
  by first mention at the input phase (inputs rule 6 is already that
  order) would remove the pass;
- **write and sync** (0.9 s on g10x, 29 ms on protoc) can move off the
  critical path only by returning before the state is durable. IN-17
  makes the state the last write of a successful link, after the
  output; a background writer would have to leave the state absent or
  "updating" until it lands, and the next link would then fall back
  (`no-state`) instead of updating. That is a contract question, not
  built;
- the **state's size** drives encode, write, and the next update's
  read: 404 MB on g10x, of which `MENTIONS` 69.0, `STRINGS` 68.9,
  `RESOLVED` 66.1, `SYMBOLS` 59.2, `FRAGS` 52.7, `INDEX` 32.3,
  `FRAG_AT` 26.4, `SECTIONS` 14.0, `EH_RECORDS` 13.1 MB. Stage B
  measured 82 MB for the same link: the delta tables of format version
  2 (WP-063) and the holes (WP-062) multiplied it by 4.4 after stage B,
  and (a) adds 10.8%.

## 7. The rule restated (proposed text for `spec/incr.md` §1.5)

The proposal replaces §1.5's "Go/no-go rule" and the three paragraphs
before it; it applies WP-061b §7's corrections (the identity
translation's measured cost; the state's real size; g10x
over-representing globals; the copy's 0.98 ms/MB; update peak RSS not
verifiable before WP-064; the translation as a named part; the first
link's cost in §8.1).

> **Go/no-go rule (WP-094).** The rule is judged on the large workload
> only: `synthetic-objects-g10x` (8,150 objects, 757 MB plain output,
> 1.67 M symbols) until WP-081's `cxx-large-g` (clang 19, static, `-g`,
> 1.13 GB output) has been measured, then on `cxx-large-g`. protoc `-g`
> is reported, never gated: at 50 MB an update cannot be much faster
> than a 0.2 s link, and the rule below sends it to a full link.
>
> - **The update** (a one-function, same-size edit to the median
>   object, thin archives, in place) takes at most **1/3** of a plain
>   link of the same inputs, measured interleaved; by copy, at most
>   **1/2**. Measured as the design floor D of WP-061b §4.1 until
>   WP-064's update exists, then as the update itself.
> - **The first link** (`--incremental=full`) takes at most **1.5×**
>   a plain link, and its peak RSS at most **1.25×**.
> - **The fall-back** (a full link with a reason) takes at most a
>   `--incremental=full` link plus the state's read and the change
>   detection; `--incremental-report` is bounded (a count per kind and
>   at most 1,000 named items per kind).
> - **Full link below a size.** When the previous output (the one the
>   state describes) is smaller than **256 MiB**, mortar does not update
>   but links in full in incremental mode, reported as
>   `incremental: full (small-output)` (a §7 row); `--incremental=update`
>   still updates. Below that size a full link is short in absolute
>   terms and the update gains little: at 55 MB an update in place is
>   0.67-1.15 of a plain link (D, virtiofs and overlay; it saves at
>   most 124 ms), at 583-832 MB 0.70-0.94 (D) and 0.19-0.26 with the
>   state escape. No workload between 55 MB and 583 MB was measured:
>   256 MiB is a power of two between them, chosen so that a developer
>   can predict the mode from `ls -l`, not a measured crossover; WP-064
>   measures one workload in that range and moves it if the crossover
>   is elsewhere.
>
> **go** if the update and the first link meet their thresholds;
> **change order** if a miss is attributed to a named part (the state
> read and rewrite; the copy; the window refill; the identity
> translation; the first link's capture), each with one time-boxed
> prototype; **no-go** otherwise.

**The rule applied to WP-094's numbers** (nothing rounded in the
design's favour; provisional loads). The g10x rows are the final
binary's series (c4, load 8.0-9.5; plain 3,266.5 ms); the first
series (c3, load 9.1-10.9; plain 5,813) is given beside each where it

On `cxx-large-g` (the workload the rule names) the state's read
(387.3) and rewrite (522.9) are 910.2 ms of D in place's 1,497.8
(60.8%); without them D is 587.6 ms = **0.248 of plain, under 1/3**; by
copy 2,331.2 ms (0.984 of plain), over 1/2 by the copy's writes
(1,838.4 ms). Its first link misses by more than g10x's (2.68×): phase
110 is 2,320.4 ms, of which the file hashes 900.9 (2.3 GB of inputs
read a second time), the capture 903.0 (fragments 454.1, sections
210.4, delta tables 171.1) and the encode and write 611.7.

**Attribution** (c4, in place): D is 2,272.1 ms, of which the state's
read (1,040.1) and rewrite (612.5) are 1,652.6 ms, **72.7%**, a named
part. Without them D in place is 619.5 ms = **0.190 of plain: under
1/3** (first series: 0.238). By copy, without the state, D is 1,820.7
ms (0.557 of plain): over 1/2 by the copy's writes (1,241.0 ms against
7.2 in place), the second named part. The first link's miss (1.84×) is
the state phase 110 (2,331.7 ms in the c4 series: capture 1,049.5 of
which delta tables 804.8; file hashes 345.6; encode and write the
rest), the part named "the first link's capture". So the result is
**change order**: every miss is attributed to a named part, and
exactly one of them, the state's read and rewrite (§1.5's O(symbols)
row: "a ranged state read ... and a state patched in place or
journaled"), stands between the design and the update threshold in
place. That escape was not prototyped here (it is not one of the three
this package was cut for), and the first-link threshold is missed even
after (c).

## 8. What WP-064 should now be

Differences from `spec/incr.md` as it stands:

1. **IN-28 → IN-28a**: the update translates unchanged files by
   position under the conditions of section 3, and decides the
   positional set before it builds identities (only from the others).
   State format version 3 (IN-18a3).
2. **The state is read and written by range, not whole** (new, the
   largest term at scale: 1.65 s of a 2.27 s floor on g10x). The
   update reads the tables it needs by positioned reads (no mmap) and
   writes a patch (or a journal) with per-table hashes; IN-17/IN-18's
   "read whole and validated" becomes per table. Before that, the
   state should shrink: `MENTIONS`, `RESOLVED` and `INDEX` (168 MB of
   404 MB on g10x) repeat what `SYMBOLS` and the object files hold.
3. **`.symtab`/`.strtab` per file** (synth.md Q8 answered): locals per
   file with slack filled by `STT_SECTION` filler entries; the global
   area dense, ordered by definer, with a tail reserve; added globals
   to the tail, removed ones replaced by the area's last entry. Needs
   the P-E3 filler ruling (section 4) — a request to the supervisor.
4. **Writes of the dirty ranges only.** The 1 MiB windows (I-95) stay
   the unit of refill and build-id hashing; the write is the union of
   the dirty ranges (g10x: 475 KB instead of 26 MB).
5. **In place is the default for outputs above the small-output size**
   (the copy's writes cost 1.2-2.6 s at 832 MB on overlay, 1.5-3.1 ms/MB measured
   under load); copy stays for small outputs and the cases of IN-45.
6. **`small-output`**: a §7 row and the rule of section 7.
7. **The fall-back pays only detection**: the dry-run delta and the
   report run only when the update itself would run, and the report
   is bounded; the measured fall-back is 1.00-1.02× a full link without
   the report and 1.5-1.7× with it.
8. **The delta recognizes a changed thin-archive member** as an input
   (today it names `options-changed`, "is not an object or archive").
9. **The first link**: hash inputs as the input phase reads them
   (511 ms on g10x), and number keys by first mention at input time so
   the delta tables need no serial pass (2.0 s on g10x); both
   *estimates*.
10. **Split DWARF** (IN-55a `debug-unit-kind`): the floor with
    skeletons was identical on both split workloads, and gains less at
    scale (D in place: protoc split 0.81 of plain, g10x split 0.94, g10x
    0.70); whether to lift the fall-back is WP-065's question.
11. Update peak RSS: the test path's is 1.21× a plain link on g10x; the
    design's O(change) front is still unmeasured.
