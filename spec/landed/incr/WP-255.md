# WP-255: the update's `Link`: unchanged files from the state, a per-file front (design)

A design step: no code in shipped crates. It answers the seven questions of
`briefs/wp-255.md` with measurements on the real workloads. It follows the
whole-program `Link` finding of the join's Step 0 (WP-225). Base f69596c7.
The experiments are throwaway: `tests/incr-design/wp255/` holds their scripts
and their patches (`probe-and-clips.patch`, `wp255_readset.patch`,
`wp255_state.patch`). Restore them with `git apply` on f69596c7.

**What needs a ruling (details in §3, §2.3 and §7):**

1. **The shape: C', "the update builds its own `fill::Image` over clips".** The update
   does not build a `Link`. It assembles the `fill::Image` that `fill_range`
   already takes, over the dirty ranges only. Its tables come from the state,
   plus the changed files' own fronts. The three builders the whole link uses
   (the section-row maker of `layout_plan::from_layout`, the value formula of
   `LinkTables`, and the writers of `.eh_frame_hdr`, the headers and the
   structure) are split into one kernel each, generic over a row source.
   **A plain link pays nothing:** it monomorphizes over its own front, and no
   `dyn` is added inside a hot loop. Candidates A and B are rejected in §3.
2. **The rule sentences this needs:**
   - I-95: "the update fills clips (its dirty ranges), not whole windows; the
     1 MiB window is the unit of the leaf hash, not of the fill."
   - IN-75: "the inputs rechecked are those the update READ", not every input.
   Both were measured byte-identical on protoc, with and without `-g` (§1.3).
3. **Missing stored data (2(e)):** none for the static body-edit path that
   the join's v1 serves. The one exception is already filed: G-15's
   3-reference `Acc` cap (WP-256). A changed file that adds a new IFUNC, TLS
   or COPY consumer stays a named fall-back (§2.3).
4. **Trusted data that no judgement catches (§7):** none new. One datum is
   caught only by (b) and IN-21: **the previous output's bytes outside the
   dirty ranges.** Mutation m2 flipped one byte at 0x180000. Refill accepted
   it. The output differs from the full link by that byte, while the build id
   equals the full link's. Judgement (d) cannot see it, because C(U) hashes
   the same leaves. This is the existing trust (IN-21 binds the output's
   stat), not new to this design. It is listed so the ruling is explicit:
   either (b)'s content check stays mandatory on update outputs, or IN-21's
   stat binding is the whole defence.

## 1. The read set (measured)

### 1.1 Method

The probe is a feature-gated counter in `mortar_core::column`. It hooks
`get`, `range`, `iter`, `as_slice` and `Index`, and is keyed by
`(phase, column type, id)`. The phases come from `Steps::step`. The test
(`wp255_readset`) builds three fronts on the workload's response file:

- prev: the full link.
- want: the edited archive, with layout L0 replayed.
- the update front.

It calls `refill` inside `mortar::image::with_link`, asserts that the patched
prev equals want and that the leaves are equal, and classifies every read by
file class:

| class | meaning |
|---|---|
| C | the changed file |
| W | a file with a section in a refilled window |
| T | a file the fill touched outside C and W |
| U | any other file |
| global | per-symbol columns |
| WHOLE | `as_slice` and `iter` over a whole column |

The edit flips bit 0 of a relocation-free word in one code section of one
member (`edit_member.py`), so the change is same-size.

The probe counts `as_slice` as WHOLE even when the caller binary-searches
it. The WHOLE figures for `section_base` are therefore upper bounds.

### 1.2 protoc without `-g` (cxx-medium-static, `strutil.cc.o` edited)

The workload has 3,536 files, of which 784 are live, and 46,565 globals. In
window mode the refill covers windows 0, 4 and 8 (4.07 MB filled). The
windows hold 280 files and 8,004 sections of nonzero size.

| phase (the `Link` field it fills) | what it reads | files |
|---|---|---|
| `with_link` construction (`inputs`, `resolution`, `assignment`) | `FileLive` and `section_base` of every file; `SectionRow` and `OutOf` of 138K sections | all 3,536 |
| `tables` (`LinkTables`) | `Def` of all 46,565 globals; through `def_value`, the definers' section rows, `Place` and `OutOf` (23K sections) | 782 |
| `structure` | whole `Chunk`, `Segment` and `File` columns | all |
| `plan` (`layout_plan::from_layout`) | a row for every placed section, `proof` per relocated section (27.7K sections) | 783 |
| `fill` (window mode) | the readers of 403 files; `Def` of 30,690 globals | 403 |
| `after` (the IN-75 recheck) | every `File`, twice (7,072 calls) | all |

**Clip mode** fills only `want` (45,271 bytes) and touches 31 files:

- the changed file;
- the section rows of about 30 definer files, through the relocation
  targets;
- one other file's reader;
- 179 globals: `Def`, `SymProps`, `DemandFlags` and the redirect.

No other file's bytes are read.

### 1.3 protoc with `-g` (cxx-medium-g-static)

In clip mode the edit fills 149,529 bytes and touches 50 files. The refill
also covers the debug windows 28, 35, 36 and 38 (`.debug_info` and
`.debug_line` relocations of the edited function's file), and is
byte-identical to the full link. **Per-file debug refill for a same-size
edit works on today's `refill`.** In window mode the fill grows to the
whole debug windows.

### 1.4 What is O(program) today, per field

These are everything `with_link` builds before `refill` runs:

- `LinkTables::new`: every file's symbol table and every global's value.
- `structure`.
- `Chunks::new`: the synthetic chunks.
- `from_layout`: every placed section.
- `deferred_orders` and `file_fixups`.

The fill itself reads O(change) in clip mode. **The read set an update needs
is about 1% of what the `Link` builds:** 31 of 3,536 files, and 179 of
46,565 globals.

## 2. Where each datum of an unchanged file comes from

The update's id space is the state's rows: FileId is a FILES row, SectionId a
SECTIONS row and SymbolId a SYMBOLS row, with new ids appended. A per-file
front born in update ids (§4) removes G-3's translation.

Sources:

- (a) a format-5 table.
- (b) derivable in O(change) from (a).
- (c) the previous output.
- (d) parsed on demand.
- (e) missing.

### 2.1 Per datum

| datum | source | from |
|---|---|---|
| a target symbol's value (global) | (b) | model §4.5: `CHUNKS.addr + SECTIONS.place_offset + RESOLVED.value`; merge targets through `FRAG_AT`/`FRAGS`; commons through `SYM_PLACE`; internal symbols through `DEFINED` |
| a target's type, binding, size and facts | (a) | `RESOLVED` (`facts` = the scan's `SymFacts`), `KEY_REFS.demand` |
| a local symbol of an unchanged referrer | (d) | that file's symtab, parsed on demand (bounded by the refill set) |
| GOT, PLT and IPLT slots | (a) | `SLOTS (kind, symbol)` plus `CHUNKS` |
| TLS block and offsets | (a)+(b) | `SEGMENTS` (the TLS segment), `RESOLVED.value` |
| a section's place | (a) | `SECTIONS.place_chunk`/`place_offset`, `CHUNKS` |
| output sections and headers | (a)+(c) | `OUTSECS`, `CHUNKS`, plus the previous section header table (refill step 2 already reads it) |
| the bytes of an unchanged section in a clip | (c) | the previous output (refill step 5 already copies moved sections) |
| relocations of an unchanged referrer (IN-74) | (d) | parse and scan that file on demand; `INDEX` names which |
| `.eh_frame` records | (a)+(d) | `FILES.eh_offset`/`eh_capacity`/`eh_records`/`eh_fdes`; the changed file's records are parsed |
| `.eh_frame_hdr` | (c)+(b) | the previous table, re-sorted only over the changed file's FDEs |
| `.symtab`/`.strtab` | (a)+(c) | `SYMTAB_KEYS`, `NAMES`; the previous tables are patched in place; growth is a named fall-back |
| `.init_array`, fixups | (a) | `PATCHES`, `GROUPS`, the changed file's own rows |
| erratum sites (AArch64 843419 and friends) | (d) | rescanned for the changed file; a `PATCHES` difference is the named fall-back |
| build-id leaves | (a)+(c) | `LEAVES`, recomputed over the dirty windows from the patched output |
| proof (`layout_plan` per section) | (d) | computed for the changed file's sections only |
| the map | (a)+(b) | `update_map` already writes it from the delta |
| `.debug_*` relocations | (d) | the changed file's own; the referrers' through IN-74 |

| content | O(change)? | source |
|---|---|---|
| `.symtab`/`.strtab` | yes, while the names fit (`SYMTAB_KEYS`); growth falls back | (a)+(c) |
| `.eh_frame_hdr` | O(FDEs) when the changed file's FDE count or order changes; otherwise a patch of its rows | (c) |
| `.got`, `.plt`, IPLT | yes; a NEW slot is a fall-back today | (a) |
| TLS | yes | (a) |

### 2.3 Missing (e): seams to rule on

- **G-15's 3-reference `Acc` cap** (already WP-256): a symbol with more than
  three references of one class is not answerable from `KEY_REFS` alone.
- **A new IFUNC, TLS or COPY consumer in the changed file** needs a slot that
  is not in `SLOTS`. It needs a named fall-back (proposed:
  `update-not-implemented (slots)`; today only `(eh)` and `(image)` exist
  in refill). No new seam is proposed for v1.

Nothing else was found missing on the static body-edit path.

## 3. The shape

The deciding rule is ONE implementation of every byte-producing kernel.

### A: the `Link`'s tables behind accessors

`Link` keeps its fields, but each becomes a trait object or an enum over the
front or the state.

- **Cost to a plain link:** a `dyn` or enum dispatch on every `Def`,
  `SectionRow` and `Place` read inside the fill and the plan loops (the hot
  loops: 46K and 138K reads above). Rejected on "a plain link pays nothing".
- **Code with two paths:** the accessors only, about 15 methods.

### B: a sparse front of `Link`'s shape

The update builds a `Front` whose columns are dense over the program but
filled only for the files it reads.

- **Cost to a plain link:** nothing.
- **Cost to the update:** the columns must still be allocated at
  O(program): 138K sections and 46K globals of placeholders. The builders
  (`LinkTables`, `from_layout`) must become demand-driven anyway, or they
  read the placeholders. It keeps the O(program) terms §1.4 measured and adds
  a correctness trap: a placeholder read as data. Rejected.

### C': the update's own `fill::Image` over clips (recommended)

`fill::Image` is already the kernel seam. It holds:

- `plan: &Plan`
- `source: &dyn Source`
- `tables: &dyn Tables`
- `keys: &dyn RecordKeys`
- `records`
- `chunks: &[&dyn SynthChunk]`
- `merged`, `eh` and `fixups`

`fill_range(img, lo, out, errs)` fills any clip. The `dyn`s are per file or
per relocation section, not per relocation, and they exist today.

The update assembles an `Image` from:

- a `Plan` over the clip set's sections only (§4);
- a `Tables` over the state rows plus the changed fronts;
- a `Source` serving the previous output and the changed files;
- the chunks, re-created from the stored rows.

**Code that has two paths (the only part):**

- `layout_plan::row_for(section, place, out, proof)`: the per-section row
  maker factored out of `from_layout`. The full link calls it in its loop;
  the update calls it per clip section.
- `link_tables::value::<R: Rows>(sym)`: the value formula, generic over a
  row source. It is monomorphized for `FrontRows` (the full link, unchanged
  speed) and for `StateRows`.
- The `.eh_frame_hdr`, section-header and structure writers take data lists
  (one writer each). The full link builds the lists from its front; the
  update builds them from the previous output plus the delta.

**What does not get a second path:** every relocation kernel, the
`.eh_frame` rewrite, merge, GOT/PLT and TLS encoders, and the debug
relocations. They are all reached through `fill_range`.

**Cost to a plain link:** none. It keeps `Link` and `with_link`; the three
factored functions are called from the same loops, generic and inlined.

## 4. The per-file front

`front_of(file, state, ids)` runs input, scan and split for ONE file, with
ids allocated in the update id space:

- its FILES row;
- its SECTIONS rows (appended when the count grows);
- its symbols' SYMBOLS rows by key (`find_key`).

It yields:

- its section rows, `Place` (from `SECTIONS`, or U-4's new place), `OutOf`
  and readers;
- its relocations, scanned with the stored facts of its targets.

The same function is called on demand for an unchanged referrer that IN-74
names (`INDEX`) and whose relocations land in a clip. It is cached by
FileId, and the IN-75 recheck covers exactly the files it opened.

Measured cost of the parts (protoc, `wp255_state`, 9 reps, **load
13.5-14, above the brief's 12**: treat as upper bounds):

| primitive | no `-g` | `-g` |
|---|---|---|
| `state5::open` | 0.14 ms | 0.13 ms |
| FILES+STAT pass (3,536 rows) | 1.41 ms | 0.99 ms |
| the changed file's rows (407 sections, 334 mentions, 374 INDEX) | 1.17 ms | 1.04 ms |
| its 334 keys: SYMBOLS+RESOLVED+KEY_REFS (7,173 refs) | 5.5 ms | 4.7 ms |
| INDEX of the 387 mentioning files (117K rows; an upper bound) | 2.3 ms | 1.6 ms |
| CHUNKS, SEGMENTS, OUTSECS, SLOTS | 0.4 ms | 0.4 ms |
| LEAVES (15 / 54 leaves) | ~0 | 0.06 ms |

The state is 34.9 MB (no `-g`) and 35.0 MB (`-g`); the reads total
2.84 MB. Input of the changed member is taken from the full link's share:
`strutil` is 187 KB of 44 MB of live input in an 85 ms input phase, so
about 0.3 ms. The raw `mortar_elf` parse measured 0.004 ms, which is
meaningless because the parser is lazy.

### 5.2 The update under C', per edit

The edits:

- E1: a same-size body edit (measured).
- E2: a function added, so the file grows within its capacity.
- E3: a header-like edit touching many files (modelled, not measured).

Terms for E1 on protoc:

| term | no `-g` | `-g` | O(?) |
|---|---|---|---|
| stat every input + FILES/STAT pass | 1.4 ms + stat (~3.5K stats, ~2 ms) | 1.0 + 2 | O(inputs): **program** |
| change detection of a changed REGULAR archive (IN-24, §1.5 of `spec/incr.md`) | 15 ms (25 MB) | 50-70 ms (85 MB) | O(archive bytes): **program-ish** |
| changed file: input+scan+split | ~0.3 + ~1 ms | ~0.5 + ~2 ms | O(change) |
| its keys and referrers (state) | 5.5 + 2.3 ms | 4.7 + 1.6 ms | O(change × fan-in) |
| referrers parsed on demand (IN-74), clip-bounded | ~1-3 ms | ~2-5 ms | O(change × fan-in) |
| U-4 placement, U-5 symtab plan | not measured; estimate ~2-5 ms | same | O(change) |
| Plan over clips + Tables from state | <1 ms (the 31 touched files' rows) | <2 ms | O(change) |
| the fill (clips) | 0.30 ms | 0.71 ms | O(dirty) |
| leaves: hash dirty windows + fold | ~1 ms | ~1-2 ms | O(dirty) + O(output/1 MiB) |
| writes (in place, fdatasync; §1.5: 8.2 ms) | ~8 ms | ~8 ms | O(dirty) |
| process start, CLI, state open | ~5 ms | ~5 ms | constant |
| **total, regular archive** | **~45-55 ms** | **~85-110 ms** | |
| **total, thin archive or plain objects** | **~30-40 ms** | **~35-45 ms** | |
| gate: 1/2 of the full link | 95-100 ms | 155-165 ms | |
| ratio | ~0.25 (regular), ~0.18 (thin) | ~0.3 (regular), ~0.13 (thin) | |

**E1 meets the protoc gate in both configurations.** The deciding term on
`-g` is the regular-archive change detection (IN-24), not anything in the
`Link`.

- E2 (growth in capacity) adds U-4's shifts of the file's own chunk (moved
  bytes copied from the previous output, O(moved)) and the `.eh_frame_hdr`
  re-sort when its FDE count changes (O(FDEs): protoc ~12K FDEs, ~1 ms).
  Still under the gate.
- E3 (many files) scales the O(change) rows linearly. At about 50 changed
  files on protoc the per-file terms reach the order of a full link's input
  and scan. That is the natural fall-back point (WP-225's `full-relink
  cheaper`), not a gate case.

### 5.3 clang `-g` (the large workload)

Gate: 1/3 of 2.8-3.1 s, so about 0.95 s. Measured: see §5.4. Today's image builders cost tables 25-55 ms over
118,435 symbols and plan 71-157 ms over 211,134 rows. **They are the
O(program) terms the shape removes.** C' replaces them with the touched
files' rows.

Modelled E1 under C':

- change detection of libLLVMSupport.a, if regular: about 30-60 ms;
- stat pass: about 10 ms;
- the file and its keys: about 10-20 ms;
- clips and leaves (1.22 GB output means ~1,170 leaves to fold): about
  5 ms;
- writes: about 10 ms.

That totals about 0.1 s, roughly 1/30 of a full link: well under the 1/3
gate.

### 5.4 Measured on the large workload

The edit is `StringRef.cpp.o` of `lib/libLLVMSupport.a`, same-size; that
archive is named twice on the command line, and the live copy is used. Each
mode ran 3 reps, in-test. The windows run had load 10.9-12.8. The clips run
had load 11.6-14.0, which is above 12: its times are contended.

| | windows | clips |
|---|---|---|
| windows / jobs | 13 / 13 | 13 / 12 |
| bytes filled | 13,289,672 | 145,482 |
| dirty bytes (2 ranges) | 9,284 | 9,284 |
| inputs rechecked | 15,208 | 15,208 |
| image tables (118,435 symbols) | 26-49 ms | 60-180 ms (contended) |
| image plan (211,134 rows) | 104-167 ms | 304-677 ms (contended) |
| `with_link` + refill | 206 / 234 / 302 ms | 571 / 982 / 1,007 ms (contended) |

Both runs are **byte-identical to the full link, build id included.** The
test asserts it; the prev/want outputs differ in 21 bytes. Clip filling cuts
the fill by a factor of 91.

Inside today's `with_link` path, the refill is dominated by the two
O(program) builders (tables + plan: about 130-215 ms uncontended). These are
the terms C' removes. Even so, the uncontended windows run (about 0.23 s)
is already under the 1/3 gate of about 0.95 s for the image part alone. It
is not the whole update: the in-test front construction is 3.6-8 s, which
is the full link's front, not an update's.

### 5.5 The O(program) terms (named)

1. stat of every input, and the FILES/STAT pass (IN-24).
2. change detection of a changed regular archive: O(archive bytes). Thin
   archives remove it.
3. LEAVES fold: O(output / 1 MiB).
4. `.eh_frame_hdr`: O(FDEs), only when the eh order changes.
5. `.symtab` growth: a fall-back to a full rewrite of `.symtab`/`.strtab`.
6. today's `LinkTables` and `from_layout` builders, while the update goes
   through `with_link`. C' removes them.

Seam signatures (sketch):

```rust
pub trait Rows {            // monomorphized; no dyn in hot loops
    fn place(&self, s: SectionId) -> Option<Place>;
    fn out_of(&self, s: SectionId) -> OutOf;
    fn def(&self, k: SymbolId) -> Def;
    fn chunk(&self, c: ChunkId) -> Chunk;
    fn frag_at(&self, s: SectionId, off: u64) -> Option<FragId>;
}
pub fn row_for<R: Rows>(r: &R, s: SectionId, proof: &mut Proof) -> PlanRow;
pub fn value<R: Rows>(r: &R, k: SymbolId) -> Result<u64, ValueError>;
pub fn front_of<'s>(state: &StateView<'_>, file: FileId, store: &'s Store,
                    ids: &mut UpdateIds) -> Result<FileFront<'s>, UpdateError>;
```

**What the join's `image_link` changes:** it no longer constructs a `Link`
over the whole update front. It builds `Plan::for_clips(set)`,
`StateTables::new(view, delta, fronts)` and a `Source` over the previous
output plus the opened fronts, then calls `refill`. `refill`'s signature
changes from `&Link` to `&Image` (plus the stored layout and leaves it
already takes).

**v1 fall-backs (to `full-relink`; the names other than `eh` are PROPOSED):**

- `slots` (a new slot);
- `symtab` (growth past `.strtab` capacity);
- `eh` (any encoding but 0x1b/0x9b; already in WP-218);
- `patches` (erratum sites differ);
- `acc` (G-15's cap, until WP-256).

## 7. What could go stale

| trusted datum | written by | patched by | caught by (IN-79) | mutation |
|---|---|---|---|---|
| `RESOLVED.value`/`section` | full link (seam) | U-3 | (d) state equality; (b) the verifier's symbol values | not run (covered by the WP-225 rows suite) |
| `SECTIONS.place_*`, `CHUNKS` | full link | U-4 | (d); (b) relocations re-verified on the map | not run |
| `SLOTS` | full link | U-3 (refusal on new) | (b) GOT slots; (d) | not run |
| `KEY_REFS`, `INDEX` | full link | U-2 | (d); missing a referrer leaves a stale relocation that (b) catches on the map, (c) on dirty ranges only | not run |
| `FILES.eh_*` | full link | U-4 | (b) `.eh_frame`/`.eh_frame_hdr` contents; (d) | not run |
| `LEAVES` | full link | refill | **(d)**: C(U) recomputes them; (b) if plumb recomputes the tree | **m1: LEAVES[1] flipped; refill accepts it; 19 note bytes (the build id) differ from the full link. Caught by (d).** |
| **the previous output outside the dirty ranges** | the previous link | refill (clip bytes only) | **(b) content only; IN-21 stat binding. NOT (d)** | **m2: one byte at 0x180000 flipped; refill accepts it; 1 byte differs from the full link; build id EQUAL to the full link's. Not caught by (d).** |
| the previous section header table | the previous link | refill step 2 | (b) | not run |

C' adds no trusted datum that today's refill does not already trust. It
reads the same stored tables `with_link` reads, now without the front that
used to dilute the trust. Its new trust is the factored `value::<StateRows>`
against `value::<FrontRows>`, which WP-255c's differential test pins.
