# WP-061 stage B: the measured floor of an incremental update

Record of WP-061 stage B. `spec/incr.md` §1.5 rests on an emulated floor
and a scaling model. This package measures the floor with mortar's own
code: a test-only update path does every step of §5.2 for a same-size
body edit. It reports the numbers against the pre-registered thresholds
(§1.5 "Go/no-go rule": the update on the default write path at most 1/2
of a plain full link on protoc `-g`, at most 1/3 on the large workload).
The thresholds are not ratified (record WP-060 (a) 6). This record
measures against them as written and does not decide go, change order or
no-go.

## 1. The workloads and the edit, fixed before the first measurement

Both workloads were fixed, and this section written, before any number
below was taken. The first trial runs of protoc (section 3) checked the
test path and are not counted.

### 1.1 protoc `-g`, thin archives

- **Objects**: the bench's `protoc` workload, `-O0 -g`, static
  (`bench/workloads/manifest`). 168 objects, 194 MB on disk, copied into
  the scratch directory with their CMake paths.
- **Archives**: `libprotoc.a` and `libprotobuf.a` rebuilt thin
  (`ar qcTD`, then `ranlib`). The members are in CMake's own order, from
  each library's `link.txt`.
- **Link line**: the bench's recorded collect2 line without
  `-plugin*` and `--dependency-file`. It keeps `--build-id`,
  `--fix-cortex-a53-843419`, `-Bstatic`, crt files, and `-lgcc -lgcc_eh
  -lc` in a group.
- **Live input**: 164 MB, as §1.5 states. The output is 50.3 MB.
- **The edit**: `importer.cc.o` (1,085,592 B), the median live member
  of §1.5's emulation. The edit is in `IsWindowsAbsolutePath`: `return
  false` becomes `return true`. That is the word at `.text+8`, `mov w0,
  #0` becomes `mov w0, #1`, at file offset `0xa04`: `00008052` becomes
  `20008052`. The edit is the same size, and no definition moves (IN-27).

### 1.2 `synthetic-objects-g10x`, thin archives

- **Generator**: a bench workload of class `on-request`
  (`bench/workloads/manifest`). The class is skipped by a plain `cargo
  xtask bench` and runs only when named. It uses the `synthetic-objects`
  generator (`xtask/src/bench/synth.rs`) with N = 8,150 objects of 200
  functions, compiled by `gcc -O1 -g`, and `-static`.
- **How N was fixed**: N is the smallest round count whose user objects
  reach 10× protoc's live input (1,640,597,920 B). It was fixed from a
  40-object sample at N = 8,200, whose mean object was 201,602 B.
- **What was built**:
  - user objects: 8,150 of them, 1,642,902,000 B, plus `main.o` at
    2,073,192 B, for 1,644,975,192 B in all (10.03× protoc's live input);
  - `cargo xtask bench --prepare` reports 8,156 objects, 3 archives,
    1,653,848,958 B in, 1,673,936 symbols, and 757,096,432 B out;
  - the whole build directory takes 2.1 GB, under
    `/tmp/mortar-wp061b-7731/bench-work`.
- **Archives**: the objects `o00000.o`..`o08149.o` are put into 82 thin
  archives of 100 members each (`libg000.a`..`libg081.a`, `ar qcTD`,
  `ranlib`). They follow `main.o` on the link line. `main.o` names
  `function_00000` of every object, so every member is loaded.
- **Link line**: the recorded line without `-plugin*`, with the
  archives in place of the objects.
- **The edit**: `o00514.o` (201,672 B), the median object by size. The
  edit is in `mortar_bench_objects_o00514_function_00007`: `x + 7`
  becomes `x + 8`. That is `add w19, w20, #0x7` at `.text+0x1d0`, which
  becomes `#0x8`, at file offset `0x210`: `931e0011` becomes `93220011`.
  The edit is the same size, and no definition moves.
- **Shape**: the workload is C. Its objects are uniform, with no
  templates, no COMDATs and no shared `.debug_str`. As §1.5 says, it
  under-represents the O(symbols) terms of real C++.

        and removed files.

        (IN-61, `capture::replay`). The two parts of the replay are
        timed apart (`mortar: floor: replay keys/translate`).
      - 100: the dirty windows filled through the image phase. They

        - the ELF header;
        - `.symtab`, `.strtab` and `.symtab_shndx` whole (S-112);
        - `.eh_frame` and `.eh_frame_hdr` whole (conservative:

    - It refuses by name what it does not do:
      - no state, an invalid state or a changed plan;
      - zero or several changed files;
      - a dynamic executable;

      - a changed output size or leaf function.
  - `src/image.rs:319`: `image::refill`, the facade over

  - `src/incremental.rs`: `take_stamps` (line 241) split out of

  - `examples/incr_floor.rs`: `incr_floor copy|in-place -- LINK-ARGS`,

  - `tests/incremental.rs:1398`:
    `the_floor_update_is_the_full_link_of_the_edited_inputs`.
- **`xtask`, `bench/`, `spec/harness.md`**: the bench class

- **`scripts/incr-floor.py`**: the measurement. It runs medians of N
  runs, with wall time from the clock and peak RSS from `/usr/bin/time

  run and records that load. It also collects phase lines, toggles the
  edit, and checks each update series byte for byte against a plain
  link.
- No new dependency edge, no `unsafe`, no mmap.

## 3. Evidence

- **The test.** It links the C program (`support::C_PROGRAM`: TLS,
  IFUNC, static glibc) with `--incremental=full`. It then edits
  `impl_a` from `mov w0, #1; ret` to `#2`, and later to `#3`: two
  chained same-size edits, each written through a new inode. On each
  write path, each update must meet all of these:
  - its bytes equal a plain link of the edited inputs, build id
    included;
  - `mortar_plumb` accepts it (with the plain link's `--mortar-map`);
  - the program prints the new value;
  - the state's flag is clear afterwards.
  The in-place path must keep the inode, and the copy must replace it.
  Afterwards `--incremental=update` must still fail with
  `update-not-implemented`. Result: passes.
- **On the measured workloads**, every update run of every series
  (section 4) was compared byte for byte with a plain link of the same
  edited inputs: all identical. That is 9 + 9 runs on each protoc file
  system and 7 + 7 on g10x, chained (each update starts from the state
  the previous one wrote).

### 4.1 The test path against the design's floor (derived)

The test path's front parses, splits and scans every input, because the
v1 state has no per-file summaries. It also computes a whole layout
before the replay replaces it. The design does neither: WP-064 restricts
input, split and scan to the changed file and runs a delta layout. §1.5
bounds the delta layout and the split at 34.5 ms until S2.

The *derived* design floor, D, keeps each measured phase that the
design does as measured:
- state, stat and stamps, detection;
- resolve, assignment, liveness, synthetic;
- the dirty-window refill, the writes, the state rewrite;
- the process's start and exit (wall time minus the in-process total).

To that D adds:
- the identity translation as measured (replay keys + translate);
- the 34.5 ms bound;
- the changed file's share of input, split and scan, by bytes (≤ 0.4
  ms).

D′ is D without the identity translation, as if IN-28's translation
were made O(change). D″ is D′ with `.eh_frame` refilled only over the
changed file's range (IN-34a): the image phase is scaled by the
windows, and so are the writes in place. All three are **estimates**
built from measured parts.

| | plain | threshold | measured | D | D′ | D″ |
|---|---|---|---|---|---|---|
| protoc, copy | 131.5 | ≤ 65.7 (1/2) | 280.8 (0.47× speedup) | 235.0 (0.56×) | 161.1 (0.82×) | 159.9 (0.82×) |
| protoc, in place | 131.5 | ≤ 65.7 | 232.2 (0.57×) | 196.2 (0.67×) | 121.7 (1.08×) | 120.0 (1.10×) |
| g10x, copy | 1,495.9 | ≤ 498.6 (1/3) | 7,056.4 (0.21×) | 4,395.7 (0.34×) | 1,687.4 (0.89×) | 1,591.4 (0.94×) |
| g10x, in place | 1,495.9 | ≤ 498.6 | 4,112.8 (0.36×) | 2,888.3 (0.52×) | 632.2 (2.37×) | 552.9 (2.71×) |

## 5. The rule applied (not decided)

**Thresholds** (§1.5 as written: the update on the default write path,
the copy, at most 1/2 of a plain full link on protoc `-g`, at most 1/3
on the large workload; in place reported beside it):

| workload | write path | threshold | measured | met? | derived D / D′ / D″ |
|---|---|---|---|---|---|
| protoc `-g` | copy (default) | 65.7 ms | 280.8 ms | **missed** | missed / missed / missed |
| protoc `-g` | in place | 65.7 ms | 232.2 ms | **missed** | missed / missed / missed |
| `synthetic-objects-g10x` | copy (default) | 498.6 ms | 7,056.4 ms | **missed** | missed / missed / missed |
| `synthetic-objects-g10x` | in place | 498.6 ms | 4,112.8 ms | **missed** | missed / missed / missed by 11% |

On both workloads and both paths, the measured update is slower than a
plain full link.

**Attribution** to the named parts of the rule:

1. **An O(symbols) term above 25%: the state row, by way of the
   identity translation (IN-28).**
   - The replay's `Keys::new` re-reads every object's symbol table and
     section names. `capture::replay` then maps every state row (202 K
     sections on protoc) through string identities, single-threaded.
   - Measured: 74 ms on protoc, which is 31% of D (copy) and 38% (in
     place). On g10x it is 2,256-2,708 ms, which is 62% and 78% of D.
   - The state read and rewrite proper: 33.5-38.9 ms on protoc (24% of
     D′ by copy, 28% in place); 144.6-268.8 ms on g10x (16% of D′ by
     copy, 23% in place).
   - Note for the operator: the rule's O(symbols) table names "state"
     as "read whole and validated ... and rewritten whole". The
     translation appears in §1.5's omitted phases ("decoding the state
     and translating identities (IN-28)"), not in a table row. Whether
     it counts as the named "state" part is the operator's reading. A
     miss on a part not named is no-go by the rule.
2. **The copy** (g10x).
   - The writes take 805.6 ms by copy against 62.2 ms in place: 743 ms
     for 757 MB, or 0.98 ms/MB.
   - That is 48% of D′ by copy. In place, D′ = 632 ms, which still
     misses 498.6.
   - On protoc the copy costs 32.7 ms more than in place (25% of D′).
     That matches §1.5's 30-40 ms.
3. **Window refill** (g10x).
   - The refill takes 178.8 ms in place, 28% of D′, and 291.6 ms by
     copy. Of the 170 windows, 106 are `.symtab`/`.strtab`, rewritten
     whole: 111 MB.
   - The test path's 57 `.eh_frame` windows (34%) are its own
     conservatism, not the design's. D″ removes them.
   - On protoc the refill is 16.6-16.8 ms (10-14% of D′): 14 windows,
     6 of them `.symtab`/`.strtab`.
4. **The changed file's refill without `-g`** was not measured. Both
   workloads are `-g`. With `-g`, the changed file's own windows are 7
   of 14 on protoc and 7 of 170 on g10x. By windows, that is about
   8 ms on protoc (7% of D′ in place) and about 7 ms on g10x (1%).
5. **Regular-archive detection**: not measured, because both workloads
   use thin archives. It does not gate.
6. **Not named, but present in every number**:
   - Process start and exit: 11.6-12.8 ms on protoc and 50.6-86.5 ms on
     g10x, mostly freeing about 2.7 GB. A plain link pays its own
     (9.9 / 67.4 ms).
   - The CPU passes over all symbols (resolve, assignment, liveness,
     synthetic): 16 ms on protoc and 147-179 ms on g10x.

**Escapes that need a prototype** (not built). For each, what a
follow-up would measure and what I expect, all as *estimates*:

- **IN-28's translation made O(change).**
  - The idea: for a file whose content hash is unchanged, map its state
    rows to the new ids by position (file ordinal, section index), with
    no string identity. Only the changed file's rows go through
    `Keys`.
  - The follow-up would measure the replay's two timers with the
    positional map, on both workloads.
  - Expected: a few ms on protoc and tens of ms on g10x. That gives D′:
    122 ms on protoc in place (still above 65.7) and 632 ms on g10x in
    place (above 498.6).
- **Per-file `.symtab`/`.strtab` ranges** (synth.md Q8), together with
  `.eh_frame` per file (IN-34a).
  - The follow-up would measure the refill and the writes with 7-10
    dirty windows on g10x instead of 170.
  - Expected on g10x in place: 553 ms minus about 100 ms of refill and
    about 35 ms of writes, so about 420 ms, which **meets** 1/3 (2.9×).
    That holds only together with the translation escape.
- **protoc's 1/2.**
  - The design's fixed parts already sum to more than the threshold:
    - state read and written: 33.5;
    - CPU passes: 16;
    - process: 11.6;
    - refill: 16.8;
    - writes in place: 7.6;
    - delta layout: the 34.5 bound, or 20 ms if it costs what today's
      whole layout costs.
  - That sums to 106-120 ms against 65.7. Even with a ranged state
    read and a patched state (about 5 ms, an estimate), it is about
    80 ms.
  - A follow-up of one session cannot bring protoc under 1/2 on the
    data above, by my estimate. The full link it is measured against
    is 131.5 ms.
- **Smaller update windows** (a write-size change, I-75's leaf size
  kept).
  - The follow-up would measure the refill at 64 KiB windows. On
    protoc the changed file's 7 windows would become about 287 KB of
    units.
  - Expected: under 5 ms saved on protoc. On g10x the refill is set by
    `.symtab`, not by the window size.

## 6. What a plain link pays

Nothing by construction: `write_link`'s body moved into `with_image`
unchanged, and no other plain-link code changed. `static-identical` is
in the gate (section 8). The bench A/B result follows.
