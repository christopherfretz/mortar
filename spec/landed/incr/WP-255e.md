### The dirty set

Front 2 refills EVERY chunk (`front_two`, `:1065-1072`: R-3's scaffold) and
keeps only ranges that differ from the previous output. C' refills:
- the U-6 rules of `mortar_image::update::refill` over `d_F` (the changed
  files' sections, moved, revived, holes, fragments, slots, `.eh_frame`
  ranges, `.eh_frame_hdr`, grown tails, headers, the synthetic chunks when
  code moved: `update.rs:204-318`), ONE producer, unchanged;
- the non-body chunks (front 1's set, `:316-324`);
- **R-3's `refill_set`** (`mortar_incr/src/update/refill.rs:49`) units:
  IN-27's referrers of every key whose `RESOLVED` row changes, of every
  definition `defined::recompute` (`defined.rs:37`) moves, of moved,
  killed and revived sections, COMDAT re-elections and slots. They are
  state ids; they are mapped to front 2's ids by `(file, section index)`
  (D3-1: `StoredLayout::section` for a stored row, `first_section` for a
  changed file's row), never by number.

A range C' does not refill must equal the previous output. So the shadow
does NOT compare C''s ranges only: both refills are lists of ranges that
differ from the previous output, and they are compared as WHOLE outputs
(previous output overlaid with each list): equal lists of ranges and bytes,
equal leaves and build id. A first difference is reported at its file
offset, with the section, front 2's byte and C''s byte.

### The comparison

Always on in the shadow phase (no testhooks gate), in `front_two` after
front 2's `refill_capture`, on front 2's `Link`, before the first write.
It never writes the output and never changes the update. Two stages:

- **S1 (the dirty set).** `refill` with C''s set and `d_F` against
  front 2's every-chunk refill: `255e shadow: equal (N ranges, M bytes;
  U units, C' filled F of front 2's G)` or `finding: 255e shadow: first
  difference at 0x.. (section, front 2 .., C' ..)`.
- **S2 (the clip plan over the hop's real ranges).** `for_clips` over front
  2's `FrontRows` (`link::refill_clip_plan`, `link.rs:2237`) for the dirty
  ranges outside synthetic chunks, compared with S1's bytes there:
  `clip plan: equal (K ranges)`, a finding as above, or `refused NotYet(..)
  <chunk>`.

A refusal of `refill_set` (`too-much-changed`, a read) is recorded by name.

What the shadow does NOT yet prove: bytes from STATE rows. S1 and S2 both
read front 2's `Link`. The stage that replaces front 2 (S3: `UpdateImage`
over a `Rows` of P_U in state ids) needs the three MISSING rows above. It
is the blocker for the replacement, not for the shadow.

### S2-1 (x86-64 shrink, `clip byte 0x434fb written by no row`): bytes

`s21_evidence` (`update/mod.rs`, printed with the shadow's clip-plan
error) on `update_two_front.rs` x86-64 hop 2, chunk 15 (`.text`, file
offset 0x42880):

| what | value |
|---|---|
| REGIONS file 4 (unchanged) | [0xbf0, 0xc7b): `.text` 0x4b + `slack.region(0x4b, 0)` = 64, the full link's rule (`chunk.rs` `close`) |
| REGIONS file 5 (`c.c.o`, the changed file) | [0xc80, 0xd10) = 0x44 + `slack.region(0x44, 4)` rounded to 16 |
| `c.c.o` `.text` | hop 1 (GROWN): size 0x44, `sh_addralign` 16; hop 2 (SMALL): size 0x11, `sh_addralign` 1 (readelf) |
| x86-64 hop 1 | NOT taken by front 2 (no shadow line): a full link, so the state's region of file 5 starts at align_up(0xc7b, 16) = 0xc80 |
| the 5 bytes [0xc7b, 0xc80) | previous output `cc cc cc cc cc`, front 2 `cc cc cc cc cc` (trap pad) |

So the delta's region end for file 4 (0xc7b) equals the full link's
`slack.region` end; neither is wrong, and no byte is wrong. The 5 bytes
are the padding before a REGION's start that the previous full link chose
for a 16-aligned member; the update keeps the region's start (IN-33) and
places the 1-aligned SMALL there, so no member alignment explains the
padding any more. The gap rule refuses (the safe direction). A fix is NOT
in `crates/mortar_layout`. Two ways to close it, for the ruling: (a) the
gap rule takes a region's start (`REGIONS.offset`) as an item an
alignment gap may end at (a `ClipParts` field: a shared-type change), or
(b) the delta records `[previous region end, region start)` as a `Fill`
hole when the region's first member no longer needs it
(`mortar_layout/src/delta.rs:1268` `holes()`).

### c2b-3: `clip_plan::check_member_counts`

Before the first row: every in-file `Body` chunk a clip meets lists as
many members as an independent count gives, else `internal-error (image:
clip plan: chunk N: the member index lists n members, the independent
count m)`; no count is `(... no independent member count)`. The RESIDUE
fixture (`tests/clip_plan.rs` `residue_is_not_seen`) now also asserts the
dropped member is refused by the count (the full link's `clip_members`
as the independent source in the test).

The state has NO independent count: `CHUNKS` has no member column, and
`SECTIONS`' places are the member list's own source. The change to name
(`crates/mortar_incr`, not mine): a `CHUNKS.members` column (format-5
VERSION 12): the capture writes, per in-file `Body` chunk, the number of
sections `from_layout` makes an `Input` row of (`layout_plan::is_member`
plus `member_front`); `delta::layout` writes it for the chunks it
re-places (+1 per placed changed section, -1 per killed one), from its
own placement, never from `SECTIONS`. Until then a real update's S3 must
refuse `no independent member count` by name.

### The member index from the state (`UpdateRows::members`)

Every file's `SECTIONS` range (the stored rows; a changed file's
`ChangedFile::sections`), each section with a place in the update's
placement (`LayoutDelta::place_of`) in a chunk the clips meet, through
`clip_plan::is_clip_member` (the one rule). P-1: a file the delta
places, "the delta placed it"; any other, `SECTIONS.bits` (KEPT, not
COLLECTED) with the delta's `killed`/`revived` (a revived section of an
