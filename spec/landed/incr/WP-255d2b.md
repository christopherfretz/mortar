## Rulings needed

**R-1. A changed file's demoted globals.** S-74: a file's block is its
locals THEN its demoted globals (`Seg::Locals(f)`, `Seg::Demoted(f)`;
`plan`'s `GlobalKind::Demoted`: "the join gives it among its definer's
`FileSymbols::locals`"). The block is rewritten whole, so EVERY demoted
global the changed file defines (a hidden definition that stays hidden,
not only a `Demoted` change) belongs in `locals`. Which keys are demoted
is the resolution's (merged visibility, S-77, S-121: a default
definition here plus a hidden reference elsewhere is demoted), so
`file_symbols` cannot give them from the file. Proposal: `file_symbols`
takes the file's demoted entries from `global_changes`' producer
(below) and appends them in key order (`count`'s `demoted` order: by
`SymbolId`... of the FULL link, which is not the `SYMBOLS` row: the order
inside a file's demoted run is a second question, to be measured against
the full link's output).

**R-2. `global_changes` needs the full link's global rule, which is not
in a shared function.** `GlobalChange::kind` is not a field of
`ResolveDelta`: it is (stored entry, new entry) where the new entry is
`SymCtx::classify`'s answer over the new `RESOLVED` row (`Skip`: no
place, an unreferenced undefined; `Demoted`: hidden, internal or
`STB_LOCAL` and defined; else `Global`). `name`, `info` and `other` are
`CoreSyms::global`'s (`mortar/src/syms.rs`): the versioned name of a
`foo@@V` definition, `STB_GNU_UNIQUE` kept, `st_other`'s bits above the
visibility from the defining entry, the merged visibility. Writing these
in `file_symbols.rs` is a second copy of each. Proposal (two pure moves,
each with static-identical `0 differ` and a timing): (a) `classify`'s
binding/visibility rule as a `pub fn` in `symtab.rs` over a `GlobalIn`;
(b) the per-key part of `CoreSyms::global` (from a definition's symbol
entry and the key's props to `GlobalIn`) as a function the update calls
with the changed file's entry and `ResolvedRow`. `place`, `value` and
`size`: the new `RESOLVED` row (`section` in the update's ids, `value`,
`size`), whose producer for a changed definer is the file's symbol table
(`ChangedFile::values`); `stored` from `view.symtab_key`.

**R-3 (for step 4).** A key with no `SYMBOLS` row has no `GlobalChange`
(its `key` is a row). Its `.symtab` answer is the full link's only if the
update can name it: `_end`/`_DYNAMIC` are linker-defined
(`GlobalPlace::Linker`, the placement's `defined`), an undefined weak
with no definition is `GlobalPlace::Undefined`, a key only an unextracted
member names has no entry. Each needs a row (U-3's `new_keys`) before
`plan` can take it; not built here.

### Steps 3-4: `global_changes`, `demoted_run` (132ee164)

`global_changes(view, delta, fronts, merged) -> Result<Vec<GlobalChange>,
IncrReason>` in `update/file_symbols.rs`:

| field | producer |
|---|---|
| `kind` | the stored `SYMTAB_KEYS` row (global entry = index not `NO_ENTRY`) and `global_info` over the new `RESOLVED` row (`None` entry: a hidden/internal or unreferenced undefined); `ResolveDelta::gone` keys with a stored entry are `Removed` |
| `name`, `info`, `other` | `defined_global` over the chosen entry of the CHANGED definer (front + `ResolveDelta::key_ids`), then `global_info`; an undefined key: `STT_NOTYPE`, size 0, the row's binding and visibility |

## Findings and rulings needed (continuation)

**F-1 (R-4 asked). The merged visibility and `referenced` are not in
`ResolveDelta`.** A defined key's `RESOLVED.other` is the defining ENTRY's
`st_other` (capture `tables.rs` ~295, update `defined_row` ~854), not the
merged visibility (S-121); `referenced` is not stored at all (an undefined
row's `bind` is 2 for both a weak reference and none). `resolve`'s `vis`
and `referenced` (`update/resolve.rs` ~622, ~644) are private. So
`global_changes` takes them as a parameter (`merged`). Proposal: U-3
exports `(vis, referenced)` per affected key in `ResolveDelta` (mortar_incr,
not mine) or a pub fn; `vis_rank` collapses internal into hidden (rank 0 is
`STV_HIDDEN`), which changes `st_other` for an internal key.

**F-2 (blocking). No capture writes `SYMTAB_KEYS`.** Bytes: the old
output's global entries `_Z10wp255d_inli` 5714, `wp255d_m1` 5717,
`wp255d_m1_data` 5718 (AArch64) read back from the old state as
`SymtabKeyRow { index: 0xffffffff, strtab: 0 }`. `state5/write.rs` ~249
resizes the table with `NONE`; no producer fills it (grep: only
`compact.rs`/`write.rs` from a patch's edits, the test `MemoryState`).
With it, every surviving global is `Promoted` (appended twice) and no
`gone` key is `Removed`: `plan` would write wrong `.symtab` if it ran.
`global_changes` reads the row as the brief says; the capture's producer
is owed (not mine).

**F-3.** `changed_facts` gives a not-kept COMDAT copy's section an `out`
(the dropped `$x` mapped to `.text` in the mutation run). Harmless after
item 5; noted.

**R-1's order.** The update's rule as implemented: a file's demoted run is
its demoted keys in `SymbolId` (SYMBOLS row) order. Proposed IN-49a
sentence: "A rewritten block's demoted globals follow its locals in
`SYMBOLS` row order; this need not be a fresh link's order (S-74 holds:
locals, then demoted, per file)." The full link's own order inside a run
was NOT measured (one demoted key per file in the test). Whether the lane's
judges compare `.symtab` order: not checked.
