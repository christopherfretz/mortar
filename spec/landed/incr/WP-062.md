# WP-062: slack and dead ranges, the linker's side (M7 S2)

Record of WP-062. It lays out an incremental-mode link with the slack of
`spec/incr.md` §5.6 and §6 (IN-30, IN-32, IN-33, IN-34a, IN-50, IN-51b),
records it in the state (format 2) and the map (`incremental`, `hole`,
`dead`), and replays it. The verifier's side (IN-60's checks, reading the new map
records) is WP-091, merged into this branch with main 8b515d3: every
incremental-mode output here is judged by it, with the claim. A plain link's bytes do not change
(`static-identical: 0 differ`).

## 1. What landed

- **Amendments** A–E (`layout.md` L-141, L-142, L-144, L-147;
  `synth.md` S-110, S-111). `plumb.md` §3.2's incremental records are
  WP-091's text (the coordinator's ruling); this package writes them and
  leaves `plumb.md` as on main.
- **Policy** (`mortar_layout/src/slack.rs`): `Slack::NONE` (a plain
  link: every function returns 0) and `Slack::INCREMENTAL`; region
  slack for L-143 sections, tails, packed capacity, the PT_LOAD
  reserve, debug size classes `m·2^k` (m in 8..15, at least 32) with
  IN-51b's neutral minimums, and the 9-byte neutral abbreviation table.
- **Layout**: `Staged.holes` and `Placement.holes`, sorted by
  `(chunk, offset)`, empty without slack; `check` judges them (inside
  the chunk's size, no overlap with a placement or each other).
- **`.eh_frame`**: per-file CIEs in incremental mode (IN-34a), padding
  CIEs (length − 4, id 0, version 1, augmentation "", code alignment 1,
  data alignment −4, return register 30 on AArch64 (16 on x86-64,
  8 on i386), `DW_CFA_nop`s); a hole of 4, 8 or 12 bytes is absorbed by
  the record before it.
- **Image**: debug holes hold neutral DWARF units (`mortar_image`
  `neutral.rs`); the abbreviation table hole is zero-filled.
- **State format 2**: table `HOLES` (kind 39, 24-byte rows: chunk u32,
  kind u8, 3 pad, offset u64, size u64), written after `LEAVES`, before
  `STRINGS`. A format-1 state still reads, as no holes (its 23 tables).
- **Replay** restores the holes and capacities; a hand-made `HOLES`
  row of kind `dead-*` makes the image write the dead range and the map
  its `dead` line (the dead writer's only way in until WP-063).

## 2. Map grammar (WP-091's `plumb.md` §3.2, as written here)

```
incremental
hole <output-section> <offset> <size>
dead <output-section> <offset> <size> neutral|contribution|strings|cie
```

After the `define` records, before the dynamic records: `incremental`
first (exactly once in every map of an incremental-mode layout: linked
with `--incremental`, or replayed from a state, whose layout has holes;
none in a plain map, whose bytes are unchanged), then the `hole` and `dead` lines by output
section (header order) and offset. `<offset>` is from the output
section's start, hex as every other record. What each hole kind writes
(`mortar_image/src/link.rs` `dead_lines`):

| layout hole (`HoleKind`, state `hole_kind`) | map line |
|---|---|
| `Fill` (region slack, allocated; trap fill in code, zero in data, nothing in NOBITS) | `hole` |
| `EhPad` of 16 bytes or more (one padding CIE) | `hole` |
| `EhPad` of 4, 8 or 12 bytes (absorbed) | none: the record before it absorbs it, and its `piece` covers it (`EhPlan::record_span`) |
| `Debug` (an allotment's neutral form), `AbbrevTable`, `DeadDebug` | `dead … neutral` |
| `DeadFragment` (a dead merged string piece) | `dead … strings` |
| `DeadCie` | `dead … cie` |

Besides the layout's holes, an incremental-mode map lists as a `hole`
the L-118 start padding of a synthetic code chunk (the 843419 padding
before a `Patches` chunk on AArch64): fill that no item owns and no
alignment explains, from the end of the chunk before it in the same
section.

A first link writes `hole` and `dead … neutral` lines only; no
`contribution` is written by this package (WP-064 writes them), and a
dead constant fragment is meant to be a `Fill` hole from its writer.

## 3. Findings

1. **S-50 rule 1 vs the verifier (WP-091).** With per-file CIEs,
   crtbeginT.o's `__EH_FRAME_BEGIN__` (section-relative, value 0) and
   its two `R_AARCH64_ADD_ABS_LO12_NC` against `.eh_frame` resolve, by
   S-50 rule 1 ("whatever E holds"), to the start of the output
   `.eh_frame`: byte-checked, `__EH_FRAME_BEGIN__` = the output
   section's start. The verifier applies rule 2 and reports Y4 plus two
   R1 findings. This is the only verifier difference between plain and
   incremental-mode links of the aarch64 link-test corpus. It affects 50
   tests, and they all pass with `--no-plumb`. Still so with WP-091
   merged. Tests filter exactly these findings (`tests/support/plumb.rs`
   `s50_rule1_verifier_finding`). Proposed (plumb.md, Y4 and R1 on
   `.eh_frame`): "a section symbol or section-relative reference of value
   0 into `.eh_frame` is the output section's start (synth.md S-50 rule
   1), whatever record is first".
2. **IN-51b: the abbreviation table is 9 bytes, not 8.** It needs the
   terminating 0 code. readelf reports "section not zero terminated" and
   "abbreviation number 1 which does not exist" with 8. Proposed: "the
   neutral table is the 8 bytes above followed by a 0 (end of table): 9
   bytes".
3. **IN-18a: the kind order.** HOLES is kind 39 but sits before
   `STRINGS` (kind 23). "Kinds ascending, `STRINGS` last" therefore holds
   only as "file order is the writer's fixed order, `STRINGS` last".
   Proposed: state the order as a list, not by kind number, and say a
   format-1 state (23 tables, no `HOLES`) reads as having no holes.
4. **IN-33 / IN-34a: no per-range `.eh_frame` slack in a first link.**
   `.eh_frame` is packed in the policy: its growth is capacity at the
   section's tail, so a first link has no `.eh_frame` hole. Padding CIEs
   appear only through an update (WP-063) or a hand-made `HOLES` row.
5. **IN-2 item 5: per-file CIEs.** An equivalence check must pass over
   CIE pieces present in one output only, and over a record whose length
   grew by 4, 8 or 12. R13's `equiv.py` needed both, and three more
   fixes unrelated to slack: `.tbss` units (whose range overlaps the
   next section), thin archive members, and the AArch64 erratum 843419
   (which instruction moves into a veneer depends on addresses; an
   incremental link and a plain one patch different sites).
6. **Neutral units are DWARF 5.** The image writes version-5 neutral
   units, whatever the version of the units around them. readelf,
   `llvm-dwarfdump --verify`, gdb and lldb accept them.
7. **A capacity given back is invisible in the replay bytes.** Code
   slack is trap fill both ways (I-41, L-141), so a mutation that shrinks
   a capacity leaves the bytes unchanged. The replay test mutates
   capacity into the next chunk and capacity below the size instead.
8. **L-118 padding and P-I1.** The 843419 start padding (layout.md
   L-118) before a synthetic code chunk is not alignment padding, so the
   verifier's coverage (plumb.md §6.8 P-I1) reported it as covered by no
   line (`e843` in `tests/incremental.rs`). mortar now lists it as a
   `hole` in an incremental-mode map (it holds the fill). Proposed
   (plumb.md §3.2, after "All slack is listed as holes"): "so is the
   start padding of layout.md L-118". A plain map is unchanged.
9. **P-I3 and sections of size 0 (verifier finding).** P-I3 counts an
   input section of size 0 as one byte (`mortar_plumb` `dead.rs`
   `named_by_relocations`, `sh_size.max(1)`). libgfortran's
   `transfer.o` has `.bss.empty_string.0`–`.4`, NOBITS of size 0, the
   last sections of their `.bss` region: they sit at the region's end,
   which is the start of its slack hole, and every reference to them is
   a P-I3 finding (14 in `lang/fortran-c.test` on aarch64 and x86-64,
   and in `debuggers.rs` `incr_dwarf_fortran_gfortran`). They occupy no
   byte; their address is the boundary N3 already admits for `arr+size`.
   Output, map, inputs and the verifier's report are kept in
   `.build/wp-062-gate/findings/fortran-*`. Proposed (plumb.md §6.8,
   P-I3): "an input section of size 0 is in a dead range only when its
   address is strictly inside it; at a range's start or end it names
   the boundary (N3)". Tests filter exactly these findings, checking in
   the input that the named section has size 0
   (`tests/support/plumb.rs` `p_i3_zero_size_verifier_finding`).
10. **Three unruled WP-091 requests** (costs only, not implemented):
   - *A chunk line for linker-made NOBITS* (`.pad.relro`): `dead_lines`'
     sibling in `link.rs` (the chunk records) skips NOBITS synthetic
     chunks; about 3 lines to write one. Unconditional, a plain map
     gains one line in most outputs (bytes change); gated on an
     incremental-mode layout, no plain map changes.
   - *`chunk common` lines with the alignment*: a new optional token in
     the `chunk` grammar and one line per common symbol; an estimated 20 lines
     (the commons' addresses and alignments are in the layout). Plain
     maps change unless gated the same way.
   - *The copy's alignment in the `copy` record*: a field in `CopyHint`
     (`mortar_image/src/map.rs`) and the record, about 10 lines. Copy
     relocations exist only in dynamic outputs, which incremental mode
     refuses (`incremental-unsupported`), so only plain dynamic maps
     would change, and only if the field is written there.
