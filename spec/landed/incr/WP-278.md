# WP-278: a `-g` update of a real-sized object reads its debug sections from the staged store

LINKER package. Base 1bfce906 (main 2064dd12 plus WP-267 P-1c). Branch
`wp/278-staged-debug`. The finding: WP-274 §8 item 0 (an update whose
changed object is protoc's `-O0 -g` `main.cc.o`, 539 KB, refused
`debug-unit-kind: section 29: unreadable` under the default store).

## 0. What needs the supervisor's ruling

1. **The call site is in P-5's file.** The fix cannot work from
   `split.rs` alone: `classify_object(&Object)` has no way to the store,
   and the failing caller (`debug_placed`) holds the front's object over
   the parts view. The one-line change in `crates/mortar/src/update/mod.rs`
   is committed apart (3f7f7993, plus 8ec909c7: the same line without a
   needless borrow, for clippy). Take both with this package, or drop them
   and have P-5 carry the line (`split::classify_input(cx.link.inputs,
   c.file)` in place of `split::classify_object(o)` in `debug_placed`).
   Without them the package's update tests and the lane scenario FAIL.
2. **A new public entry point** `mortar_incr::update::split::classify_input
   (inputs: &Inputs<'_>, file: FileId) -> Result<Handled, IncrReason>`
   (no signature changed, no shared type, no `mod` line, no dependency
   edge: `mortar_incr` already uses `mortar_core::inputs`).
3. Named in other packages' files (census §3): C-16 (WP-277's
   `capture.rs`, a silent empty relocation list for a debug section on
   disk), C-4 and C-3 (P-5's `mod.rs`).

## 1. The cause (reproduced, then instrumented)

**Residency.** The staged store (`spec/input.md` §11.1 (b),
`mortar_input::staged::object_ranges`) keeps resident, in an object larger
than `staged::SMALL` (64 KiB): the headers, symbol and string tables,
groups, notes, the relocations of allocated sections, merge sections,
compressed sections, `.eh_frame`, and any section of at most 64 KiB.
Everything else stays on disk and is read with `Store::copy_to`. No knob
lowers the threshold (`SMALL` is a `const`; `StoreConfig` has `head`,
`tail`, `max_open`, `hashes`, `containers`; no testhook): the
reproduction uses an object above it.

**Reproduction** (scratch `w278/repro/`): `main.cc` plus a generated
`c.cc` (500 structs and functions), GCC 14 AArch64 `-O0 -g`, static;
`c.cc.o` 333 KB, `.debug_info` 0x175d6 (95.7 KB). `--incremental`, then a
same-size edit of `c.cc` (one immediate), `--incremental=update` with the
release binary of 1bfce906: refused `debug-unit-kind: section 4:
unreadable` (`G-3 fallback: file 5: ...`). With `MORTAR_STORE=resident`:
taken.

**Instrumented** (a scratch debug build: an `eprintln!` with a backtrace at
`split::classify_object`'s `s.data()` error, reverted after): 

    W278-INSTR classify_object: section 4 ".debug_info" size 0x175d6
      range Ok(Some(38108..133810)): NotResident { offset: 38108, size: 95702 }
      ... mortar_incr::update::split::classify_object
      ... debug_placed ... mortar::update::run_with ... mortar::update::run

So the refusal comes from the SECOND caller, `debug_placed` (U7,
`crates/mortar/src/update/mod.rs` ~:3586 at the base), which classifies
the FRONT's object: parsed over the store's parts view, where
`Section::data` is `NotResident` for a section on disk
(`crates/mortar_elf/src/section.rs` `data`). The first caller,
`debug_condition` (U2, ~:3405), passed: it reads the file whole with
`std::fs::read` and parses it whole. WP-274's "probable cause" is
confirmed, with the call site made precise.

## 2. The fix

`crates/mortar_incr/src/update/split.rs`:
- `units_by(len, at, h, v4)`: the unit-header walk over a reader (`at`
  fills bytes `p..p+n` of the section; at most 7 bytes per unit: the
  `unit_length`, `version`, DWARF 5's `unit_type`, at each unit's start).
  Its outer `Err` is a read that failed; the inner `Err` the rule's reason,
  exactly as before. `units(data, ..)` is `units_by` over a slice (the
  same answers; the existing unit test passes unchanged).
- `classify_input(inputs: &Inputs<'_>, file: FileId)` (new, public): IN-55
  and IN-55a on the front's object of `file`. A `.debug_info` that is
  resident is read in place; one that is `NotResident` has its unit
  headers copied by `Inputs::copy_to` (the full link's read of a section
  that is not resident: the store's parts, else one positioned read on
  the descriptor the store keeps; the same call as
  `capture::frag_hash`). Never the section whole, never the file whole:
  O(units) reads of 7 bytes, O(1) memory.
- `classify_object(object)`: signature and answers unchanged (for a
  caller holding the bytes whole). Over a parts view it still says
  `section N: unreadable (..NotResident..)`; the detail now names why.
- A copy that fails (the file changed, an I/O error) is `debug-unit-kind:
  section N: unreadable (copy: ..)`: conservative, as before.

The call site, in `crates/mortar/src/update/mod.rs` (`debug_placed`, NOT
this package's file: P-5 is in it), is ONE line, committed alone
(3f7f7993): `split::classify_input(&cx.link.inputs, c.file)` in place of
`split::classify_object(o)`. **It needs the supervisor's ruling** (take it
with this package, or have P-5 carry it).

What a plain link pays: nothing by construction, NOT timed. The diff
touches `split.rs` (whose functions are called only from the update's
`debug_condition` and `debug_placed`) and one call in `debug_placed`
(`--incremental=update` only); `cargo xtask static-identical` (the gate)
compares plain outputs. A timing would need a release build of the base
beside HEAD's (a second build tree, against the disk rule).

## 3. The class (census)

Every read of section CONTENTS (`Section::data`, and the readers built on
it: `rela`/`rel`, `group`, `strings`, `symbols`, `notes`, `merge`,
`compression`) in `crates/mortar_incr/src/update/`,
`crates/mortar/src/update/` and `crates/mortar_incr/src/capture.rs`,
greped at 1bfce906 (`grep -n '\.data()\|\.rela()\|\.rel()\|\.strings()\|
\.group()\|\.symbols()\|copy_to\|resident(\|Object::parse'`). Two kinds
of object reach them:
- the FRONT's (`cx.link.inputs`, `link.inputs`: the full link's `Inputs`,
  over the store's parts view): a section can be on disk;
- `FileFront`'s (`crates/mortar/src/update/file_front.rs` `read`: the
  store's whole file, or the member copied WHOLE into a kept buffer) and
  `debug_condition`'s (`std::fs::read`): whole bytes, never `NotResident`.

What can be on disk (§1): a non-merge, non-compressed section above 64
KiB that is not a symbol/string table, group, note, `.eh_frame`,
`.gnu.warning*` or the relocations of an allocated section, in an object
above 64 KiB: big `.text`/`.data`/`.rodata` (non-merge), `.debug_info`,
`.debug_line`, `.debug_abbrev`, `.debug_rnglists`/`loclists`,

## 5. protoc (WP-274's experiment, default store)

WP-274's `clock/g/link.rsp` (protoc 3.21.12 static, AArch64,
`cxx-medium-g-static`'s `-O0 -g` objects, `--gc-sections` added) and its
three `main.cc.o` variants (vA, vG grow, vS same size; one directory),
copied to `w278/protoc/`. The binary: this package's HEAD, DEBUG build
(no timing asked for), `MORTAR_STORE` unset. WP-274's order: full (vG),
update to vA (shrink), update to vG (grow), full (vA), update to vS (same).

| hop | at 1bfce906, default store (WP-274 §8 item 0) | HEAD, default store |
|---|---|---|
| shrink (vG -> vA) | refused `debug-unit-kind: section 29: unreadable` | **taken** (`update (InPlace) changed=1 ranges=5`) |
| grow back (vA -> vG) | refused (the same) | **refused `update-not-implemented (layout)`** by `delta::layout` ("not placed by the front: [.group size 12 kept false ..]"): WP-274 §8 item 0a, WP-279's; not this package's |
| same size (vA -> vS) | refused (the same) | **taken** (`ranges=2 bytes=4108`), **byte-identical** to `--incremental=full` of the same inputs |

The shrink's output, bytes compared (`w278/protoc/shrink.log`): the
update under the staged store is byte-identical to the same hop under
`MORTAR_STORE=resident`, with the debug binary and with the release
binary. (The log's label `resident-base` is WRONG: the release binary in
the target directory had been rebuilt at HEAD by the lane's run at 10:54,
checked afterwards by its behaviour on the repro; no binary of the base
was compared.) So the store does not change the update's bytes; the fix
lets the default store reach the path the resident store took. It is not byte-equal to a FRESH full link of vA (1,417,585 bytes
differ: `.text` 1.33 M, `.symtab`, the debug sections, `.eh_frame`, the
build id; the program headers and section sizes are equal): a
non-identity update keeps the stored placement where a fresh link packs,
so this is expected and not judged here (IN-78/IN-79 judge it against the
full link WITH the update's placement; the lane does that on its own
scenarios).

## 6. Spec findings (proposed text; not applied)

1. **IN-55a** (`spec/incr.md`, the rule's last paragraph) and §7's
   `debug-unit-kind` row ("an unreadable unit header"): say where the
   header is read from. Proposed sentence for IN-55a: "The unit headers
   are read from the file's bytes wherever the store keeps them (resident
   or on disk, `spec/input.md` §11.1): a section the staged store left on
   disk is read with the store's copy, never refused for its residency. A
   header that does not parse (a version outside 2..5, a length past its
   section) or that cannot be read (the file changed, an I/O error) is
   `debug-unit-kind`." And §7's row: "... or a unit header that does not
   parse or cannot be read from the file (IN-55a)".
2. **A class rule** (proposed for `spec/incr.md` §5.10, beside IN-18c):
   "An update reads input contents through the store's interface
   (`Inputs::resident`, then `Inputs::copy_to`), never through
   `Section::data` alone over the front's objects: the staged store keeps
   a section above 64 KiB of an object above 64 KiB on disk, and
   `NotResident` is the store's state, not the input's. A reader that maps
   `NotResident` to a refusal refuses every real-sized object; one that
   maps it to `None` computes a datum from nothing." The census (§3) names
   the sites left (C-4, C-16).
3. The lane (`spec/harness.md` "incr-update"): its objects are below 64
   KiB, so the staged store's on-disk path is covered by
   `g_large_debug_info` alone. A sentence: "At least one scenario's changed
   object is above the staged store's resident threshold (`-g`), so the
   update's reads of sections on disk are judged."

## 7. What this record did NOT verify

- Clang objects: the binary tests and the lane use GCC 14 and kiln; a
  Clang `-g` object of the same shape was compiled (its `.debug_str` and
  `.debug_line_str` are `MS`, entsize 1) but not linked or updated.
- i386 (not required): not run.
- DWARF 4 objects and objects with several units in one `.debug_info`
  (an `ld -r` output) on disk: the reader walk is unit-tested over three
  units; no real multi-unit object above the threshold was updated.
- The census's C-4 and C-16 cases were reasoned from the code and the
  staged rules, not reproduced (no non-merge `.debug_str` producer was
  found; no reference-site warning from a debug section was built).
- The cost of `classify_input` was not timed: by construction one
  positioned read of 7 bytes per `.debug_info` unit of each changed file
  with debug sections (one unit per GCC/Clang/kiln object), and nothing in
  a plain link (no caller there).
- `debug_condition`'s whole `std::fs::read` (C-3) was not measured.
- protoc: AArch64 only (WP-274's experiment); the shrink hop's output was
  compared byte for byte with the resident store's (equal) but not
  verified by `mortar_plumb` nor against a full link with the update's
  placement; no timing (debug binary).
