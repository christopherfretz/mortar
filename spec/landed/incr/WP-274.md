# WP-274: phase B of WP-267, C' on the real path (DESIGN)

A design record. It changes no code. Base 1bfce906 (main 2064dd12 plus
WP-267 P-1c). The update's code is read at P-5's head (`wp/267-p5`,
b2387960, `crates/mortar/src/update/mod.rs`), because phase B starts from
P-5's real path: `front_free` (U1-U7 without a front), then ONE front
(front 2, the update's placement replayed), then the write.

The words used here:
- **front 2**: the one full-link front left on the real path after P-5
  (`front_two`, its replay hook `hooked`).
- **C'**: the update's own image over clips (WP-255 §3, §9.5): a
  `fill::Image` over `RowTables<UpdateRows>` with an `UpdateSource`. It
  never builds a `Link`.
- **P_U**: the update's placement (the stored rows plus the delta `d`).
- **the patch**: a `StatePatch` (`mortar_incr::update::view`) applied by
  `state5::plan_patch` (U9) and `state5::patch` or `compact` (W5), IN-46b.

Status of each number: **measured** (with its source) or **estimate**
(with its model). Every name of a verifier check goes through
`spec/plumb.md` only.

## 0. Data phase B needs (committed early for WP-275)

step. "Source" says where it comes from without a front:
- **stored**: a state row that exists at VERSION 12;

  U6, U7) that today is dropped or recomputed by front 2, and that only

- **MISSING**: a stored datum that does not exist at VERSION 12 (WP-275's

**The note on D-8 (WP-275 item 1).** IN-49a rewrites a file's block only
for a file that is changed or drawn in; every other file's block is
remapped (`SymtabPlan::remap`, the values moved by the growth steps, the
rest of each entry read from the previous output), which reads nothing
of the state but `SYMTAB` and nothing of the file. A changed file and a
drawn-in file are opened anyway (IN-75; D-1 and the drawn-in fronts of
P-1c and U6). So `symtab_incr::plan`'s inputs exist in memory for every
file whose block it rewrites, and the "missing per-block symbol row" of
255e5 is a carry (P-5's `placement()` dropped them), not a stored datum.
A stored row would be needed only for a block rewritten while its file
is NOT opened. That happens when an unchanged file's sections move by
something other than a growth step: a packed chunk re-packed (WP-270,
D-7), or a chunk whose members reorder. For those, phase B v1 opens the
file (a symtab draw-in, O(that file)) or refuses `(symtab)` by name.
**Superseded by WP-275 §2.1** (accepted, §7): no row either way, and no
draw-in: an unchanged file's block keeps its entries, each moved by the
delta of the unit that holds it (found through `CHUNK_UNITS` and the
`FILES` eh columns). On the large build a re-pack of `.init_array` near
its start would have opened up to 403 files.

## 1. The real path after phase B, step by step

### 1.1 Where P-5 leaves it

At P-5's head the real path is:

```
U1-U3 -> front_free (m6, u4, u5, u6, u7: O(change))
      -> front_two: image_link (O(link) front)
           hook: debug_placed, judge, identity', materialize_in_hook (O(link))
           after: eh_runs_judged, marks_judged,
                  refill_capture (with_image: O(link) plan and tables; capture: O(state)),
                  u5_on_capture, facts_judged, identity_check (R-A1, O(state)),
                  [refill_capture again on a disagreement],
                  R-A2, facts_within_changed, debug_judged / debug_judged_moved
      -> write_identity: W1-W4, W5 = state5_encode of the WHOLE state + write_state_whole
```

`Planned` (`front_free`'s output) does not carry the `FrontCache` nor
the per-file facts and splits (`per_file` is dropped at :527 of P-5's
`mod.rs`, the cache at the end of `front_free`). Front 2 re-opens every
file of the link.

## 2. The judges

"Binding" means the real path refuses by name when it fails. "Shadow"
means it runs only under `MORTAR_UPDATE_FINDINGS`, against front 2 (and
front 1), after the decision, and never changes the outcome. "Refusal"
means the case is not judged but not taken: it falls back by name.

**The rule "no judge reads its own input"**: a binding judge's
reference must not be computed from the value it judges. A comparison
of the patch's `RESOLVED.facts` with the packed facts it was written
from is such a read (R-4a after phase B), and so is R-A2 over the
update's own rows (resolve only writes affected keys, so the check is
true by construction). A rule check (`Rule::Places`) has the rule as
its reference, which is allowed.

**R-8, in full.** Bit 24 of `RESOLVED.facts` (`dead`) must be written by
the update for (a) every key defined by a changed file, from its facts
after resolve, and (b) under `--gc-sections`, every key defined in a
section whose liveness flips (`now_live`, `now_dead`), found through
the flipped file's `MENTIONS` range (a file-keyed read of that file,
O(its mentions)). The full link's capture already writes the bit
(WP-275 §1.5, bytes), so (d0) compares the update's writer against it
on every flip; WP-275 §2.5 states the same key set (with the keys whose
definer changed, which (a) contains).

**Whole tables are the patch's O(table) terms.** IN-18e puts `CHUNKS`,
`SLOTS`, `SIZES`, `SYM_PLACE`, `DEFINED`, `LEAVES` in the whole class: an
update that changes one row rewrites the table. That is cheap when the
table is small. **Measured** on protoc `-g --gc-sections`
(`incr_state size`, §4.2's state): `CHUNKS` 42 rows (8 KB), `ORDER` 42,
`SEGMENTS` 8, `SLOTS` 544, `SIZES` 10, `DEFINED` 9, `SIZED` 3, `LEAVES` 53,
`PATCHES` 1, `REDIRECTS` 1; the state is 37.5 MB, a third of it
`SECTIONS` (158,821 rows) and a quarter `STRINGS`. A chunk is a part of
an output section, not an input section, so every whole table is a
constant-size write; on clang `SLOTS` is 4,688 rows (WP-255 §9.6) and
`LEAVES` ~1,170. No class change is needed.

**Compaction.** `plan_patch` chooses compaction when a range outgrows
its capacity. A compaction is O(state) (WP-255 §9.6: a whole rewrite is
23-57 ms on protoc and 195 ms on clang, measured). It is correct but it
is a slow update: the report must name it (`compact`), and the gate's
median and p90 count it.

### 4.3 What must hold to beat `--incremental=full` and a plain link

**Against `--incremental=full`**: every projection above is under it by
a factor of 2.5 or more on protoc and 20 or more on clang `-g`. Phase B

**Against the plain link on the operator's configuration** (the U-10
gate: 1/2 on protoc, 1/3 on the large workload, median and p90 over at
least 20 updates):

   identity hop is at the gate.** Measured on the operator's
   configuration (§4.2, with P-5's `u7`), phase B projects to

   kept terms are ~78 ms (outside ~50, `u1-u3` 2, `m6` 2, `u4` 5, `u5`

   identity hop against a ~90 ms gate (plain 176). It beats
   `--incremental=full` (465-537 ms) everywhere. The terms left are all
   named: the process's own ~41-85 ms outside the laps (measured, at
   bases that still build and drop a front), U6 (28-34 ms measured,
   with no flip), and C''s fill of the referrers' whole sections
   (8.5 MB on the `-g` shrink, whose objects have no
   `-ffunction-sections`: a changed `main` refills every referrer's
   whole `.text`). On 255e3's laps (no `-g`, plain 104 ms) the
   same two terms decide it: U7a's 47-48 ms and the 25 ms outside the
   laps. All of them must be explained and cut before the U-10

     the open part (B-1's package measures it).

4. **No whole table of the patch is O(link)**: met on protoc (every

5. **No compaction on the measured series** beyond its rate (§3).

   at 1bfce906 an update whose changed object is a GCC 14 `-O0 -g`

   unreadable` under the default store, with and without

   `split::classify_object` (`crates/mortar_incr/src/update/split.rs`)

   "unreadable". The lane's objects are small enough to stay resident
   whole, so the lane does not see it. On the operator's configuration
   (`-g` always) this refuses every update of a real-sized object, so it
   comes before any phase-B package's measurement. Its callers at P-5's
   head are `mod.rs` :4164 and :4345 (unchanged from the base).
