# WP-263: the capture writes `SYMTAB` and `META.symtab`; the orphan `.gnu.warning` count; the producer sweep

The record of the package (brief `briefs/wp-263.md`), written by its
agent. It is the third state package of its kind, after WP-261
(`FILES.round`) and WP-262 (`SYMTAB_KEYS`).

## Why
IN-49a's update plan (`mortar_synth::symtab_incr::plan`) reads the
stored global area and the tables' sizes (`symtab_tables`: `SYMTAB`'s
file-0 row and `META.symtab`) and each changed file's block
(`symtab_block`: its `SYMTAB` row). No full link wrote either: nothing
outside `mortar_synth` called `SymtabPlan::incr_blocks` or `incr_tables`.
The plan's first check (`area.first != tables.sh_info || entries == 0`)
would have refused every update's table `state-corrupt`.

## The producer
- **Route** (WP-262's): `crates/mortar/src/incremental.rs`
  (`Session::state`, the format-5 branch only, ~1438) calls
  `plan.incr_blocks()` and `plan.incr_tables()` beside WP-262's
  `incr_global_area()` and `incr_global_keys()`. `Link5::symtab` now
  carries all four answers of the plan, together or none (`None` under
  `-s`): `(area, keys, blocks, tables)`. This changes the type of
  WP-262's approved field (supervisor's word asked, below).
- `rows5` keeps the blocks and the tables in `Rows5`. `state5_rows` puts
  every input file's block in `MemoryState::symtab`, the global area in
  file 0's range (IN-18e; `StateRows::symtab_of(FileId(0))`), and the
  sizes in `META.symtab`. `compact::normalize` renumbers the files'
  ranges as it does for every file-keyed table.
- **The internal file's block has no row** (finding F-1 below):
  `incr_blocks` gives it as `FileId(0)`, and file 0's range holds the
  global area, one row at most (`read.rs` `symtab_of` refuses two).

## The check (every capture, `capture::symtab_rows_check`)
In `state5_rows`, after `symtab_keys_check` and before `check_capture`.
With a `.symtab`:
- the plan's blocks are in `FILES` order (the internal file's first, as
  file 0), each of a file with a `FILES` row that is not `LAZY`, with at
  least one entry and at most its capacity;
- they tile `[1, tail_first)`; the local tail reserve ends at `sh_info`,
  where the global area starts; the area is dense (capacity = count);
- the `.strtab` regions are each used at most to their capacity and
  tile from the first block's region to the area's names, which end
  `.strtab`;
- `(area.first + area.count) * entsize` (24 for ELFCLASS64, else 16) is
  `META.symtab.symtab_size`, and `META.symtab`'s two sizes are the
  `.symtab` and `.strtab` chunks' sizes (`CHUNKS`);
- `SYMTAB`'s rows are exactly the input files' blocks and file 0's area.

Without one (`-s`): no block, no row, `META.symtab` zero, no `.symtab`
chunk. A break returns `Err`: no state is written (as `file_round` and
`symtab_keys_check`). Unit test `capture::wp263::good_rows_pass_and_each_
break_is_refused` (18 breaks and 3 no-`.symtab` cases, each refused by
its words).

## Findings
- **F-1: the internal file's block has no `SYMTAB` row.** IN-18e says
  "`SYMTAB` (43: per file its local block and `.strtab` region; file 0's
  range holds the global area's row)", and `StateRows::symtab_of` admits
  0 or 1 row a file. But S-74's first block is the internal file's (the
  linker-defined keys written as locals and the patch symbols: 11
  entries on AArch64, 12 on x86-64 above), and `incr_blocks` gives it as
  `FileId(0)`. The capture checks it with the others and stores nothing
  of it; the plan never rewrites file 0's block today (only `files`),
  but an update that adds or removes a patch symbol or changes a demoted
  linker-defined key has no stored block to rewrite. Proposed (IN-18e's
  `SYMTAB` cell): "file 0's range holds two rows: the global area's,
  then the internal file's block (none when it has no entry)", with
  `symtab_of(FileId(0))` the first and a second accessor for the
  internal block; or the internal block in `META`. Not done here (the
  reader and the view are not this package's).
- **F-2: the sweep's "none"s** (below): `REGIONS`, `DIAGS` and
  `META.boot_id` are read by an update and written by no full link;
  `META.clone_probe` is written and read by nobody.

Each "none" with an update reader is a FINDING (F-2): `REGIONS`,
`DIAGS`, `META.boot_id`. Their consequence was not measured here: an
update that reads an empty `REGIONS` range, an empty `DIAGS` or a zero
boot id (every boot check then re-hashes the leaves, the conservative
path) behaves as if the link had none. Not fixed here (the brief).

and of head, 5 rounds interleaved (base plain, base full, head plain,
head full), the whole process timed, load 10.8 to 12.1 (the last round
just above 12):

branch only; the resolve counter is one add per `.gnu.warning.<sym>`
section with no key). The full capture's added work (copying the plan's
blocks and the check, linear in the files) is within the noise.
