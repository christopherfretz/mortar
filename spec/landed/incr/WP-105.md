# WP-105: the state by range and the first link's capture

Record of WP-105, the time-boxed prototype and measurement package that
WP-094 §8 items 2 and 9 asked for: shrink the state, read and write it
by range, take the first link's capture cost down, then re-estimate the
design floor D and apply WP-094 §7's rule. The contract does not move:
an update is equivalent to an `--incremental=full` link (IN-2) or falls
back by name, and a plain link pays nothing (IN-11).

Every prototype lives on the branch `wp/105-incr-state-by-range` (base
0fd00819). Section 9 says which commits are meant to merge.

## 1. Method

- **Host**: AArch64, 12 cores, shared. The 1-minute load was 7-26 for
  the whole session and never under 6: **every table below is
  provisional** (the brief's rule). Ratios between series of one
  interleaved run are what counts; absolute times moved by up to 2×
  between runs (g10x's plain link: 7.4 s, 8.5 s, 7.5 s
  medians in three runs of the same binary).
- **Harness**: WP-094's (`scripts/incr-floor.py --interleave`, series
  `LABEL:KIND:BIN:MORTAR`, `mortar::floor`, `incr_floor`, WP-094's
  `dfloor.py` for D), plus `--out-dir` (outputs and states on the
  scratch's overlay while the inputs stay where they are) and a new
  example, `mortar_incr/examples/incr_state.rs` (tables, whole read and
  write, the shrunk states, the format-4 prototype's ranged reads and
  patches).
- **Equivalence**: every update series was byte-identical to a fresh
  `--incremental=full` link of the same edited inputs; every format-4
  patch was compared with the format-4 encoding of the state the update
  wrote (`result is NEW's format-4 bytes: true`, every run).
- **Workloads and edit** (WP-094's): `synthetic-objects-g10x` (8,241
  inputs, 82 thin archives, inputs on **virtiofs** in this worktree's
  target directory, outputs and states on overlay), the edit in
  `o00514.o` (`0x210: 931e0011 -> 93220011`); `cxx-large-g` (a copy of
  WP-081's build tree on overlay, 2,358 inputs, thin archives), the edit
  in `CallPromotionUtils.cpp.o` (`0xc0c: 20008052 -> 00008052`). protoc
  was not set up (section 11).
- **Binaries**: `base` is 0fd00819; `p1` is b5668d2a (ranged prototype,
  the test path's STRINGS fix, delta laps, the resident store in
  incremental mode); `p2` is 763c7158 (the resident store reverted, the
  input stats on the pool).

**Which tables an update reads.** The test path's replay reads every
table but `MENTIONS`, `RESOLVED` and `INDEX`; the dry-run delta
(`delta::compute`) reads the old `MENTIONS` and `RESOLVED` and the new
link's `INDEX`. A design update needs, of the three:

- **`MENTIONS`**: the changed file's old mentions (what it used to
  define and reference: the old file is gone, so they cannot be derived
  from it), read by the file's range; and, when a key's resolution
  changes, every file that mentions the key (whose references to it are
  refilled), read by key. It stays.
- **`RESOLVED`**: the old resolution of the changed file's keys (to see
  whether it changed); derivable only by re-running resolution over
  every mention of each key, which needs `MENTIONS` by key and repeats
  extraction order. It stays, read by key (binary search: it is sorted
  by symbol row).
- **`INDEX`**: derivable on demand. Its intra-file rows come from the
  changed file's own relocations (read anyway for the refill); its
  cross-file rows (a file's references to a global) are needed only for
  keys whose resolution changes, and those files' relocations are then
  read for the refill anyway, so deriving their rows costs what the
  refill it triggers costs. **Proposed: `INDEX` goes** (−32.3 MB,
  −8.0% on g10x; −13.7 MB, −5.6% on `cxx-large-g`), replaced where the
  update needs "who mentions K" by a by-key order of `MENTIONS` (a
  `u32` per row: 17.2 MB on g10x, 1.2 MB on `cxx-large-g`) or by a scan
  of the mentioners' symbol tables. Not prototyped: the delta's code
  still reads `INDEX`.

What shrinking buys the update is small once the state is read by
range (section 4: the update reads 6-8 MB of it); it buys the first
link the encode and write of 32-167 MB.

## 4. Scope 3: the state read and written by range

**The prototype** (`mortar_incr::ranged`, "format 4", not wired into the
update; `incr_state` drives it):

- A header of 80 bytes (magic `MORTARSR`, format version 4, a flags word
  at 12 outside every hash, the table count, the block size, the file's
  length, the plan hash, the directory's L128, the header's L128); a
  directory of 29 entries of 56 bytes (kind, row width, rows, body
  offset and length, block-hash list offset and its L128); per table, a
  list of L128 hashes, one per block of the body, then the body (format
  3's rows, unchanged).
- A new table, `FILE_INDEX` (kind 41, 32 bytes a row, one per `FILES`
  row): the first row and count of the file's rows in `SECTIONS`,
  `MENTIONS`, `FRAG_AT` and `EH_RECORDS`, so a file's rows are a range.
- `Reader::open` reads and checks the header and directory (2 preads);
  every other read is a positioned read of whole blocks, each block
  hashed and compared with its list entry before any byte of it is
  used, and kept in a cache of verified blocks; every row index and
  string offset is range-checked. A failure is `state-corrupt`, never a
  panic: the unit test flips every byte of a small state and every flip
  outside the flags word is refused.
- `update_reads` reads what a same-size update of one file reads: the
  small tables whole (META ... LAYOUT, LEAVES, HOLES), STAT (every input
  is stat'ed), FILES (to find the changed file), the changed file's
  ranges of SECTIONS, MENTIONS, FRAG_AT, EH_RECORDS and its
  SYMTAB_LOCALS row, the SYMBOLS rows and names of the keys it
  mentions, their RESOLVED rows (binary search), and the SECTIONS rows
  of their definers. FRAGS and INDEX are not read.
- `patch` writes a same-length change in place: the updating flag set
  and synced; the changed blocks, their list entries, the directory
  entries and the header written; synced; the flag cleared and synced
  (3 syncs; 2 when step one shares IN-46's first sync).

**WP-094's three other edits were not measured** (section 11): the
test path refuses an edit that changes a size, and the largest-file
edit is on protoc, which was not set up. What they write, from the
tables' shapes (not measured): an added function adds a `SYMBOLS` row
(appended), a `MENTIONS` row in the file's range, a `RESOLVED` row
(sorted by symbol row: appended to the keys' part), a name in
`STRINGS`, and changes the file's `SECTIONS` rows and the layout
tables (`HOLES`, `SLOTS`, `CHUNKS`) where the slack absorbs it; a grown
function changes `SECTIONS` rows and the layout tables. Neither is a
same-length patch: rows are inserted.

**Compaction.** A row inserted inside a file's range (`SECTIONS`,
`MENTIONS`, `FRAG_AT`, `EH_RECORDS`) or a new key's rows need room. The
proposal: per-file ranges get slack like the output's (a file's ranges
end in reserved rows that a count excludes); keys' tables (`SYMBOLS`,
`RESOLVED`, STRINGS) append, with removed keys left as tombstones that a
count records. Compaction is a whole rewrite (format 3's encode and
write: 0.38-0.80 s on g10x, 0.27-0.47 s on `cxx-large-g`, measured
above), done by every full link (the state is rewritten whole anyway)
and by an update when a file's slack is exhausted or tombstones pass
25% of a table's rows; the journal never outlives one update (it is
the patch's blocks, applied before the flag clears), so nothing grows
without bound. Not prototyped.

**Proposed rule texts** (replacing "read whole and validated" in IN-17 /
IN-18; for `spec/incr.md`):

> **IN-18c [v1] The state read by range.** The state is block-hashed:
> its header (magic, format version, flags, table count, block size,
> length, plan hash) carries the L128 of a directory with one entry per
> table (kind, row width, rows, body range, and the L128 of the table's
> block-hash list), and each table's body is covered by a list of L128
> hashes, one per block of the body (4 KiB unless measured otherwise).
> A reader checks the header and the directory in full, then reads only
> the blocks it uses, by positioned reads (no mmap), and hashes each
> block against its list entry, and the list against its directory
> entry, **before** any byte of the block is used; every row index,
> range and string offset it follows is checked against the directory.
> A block or list that fails its hash, a range out of bounds, or a
> reference out of range is `state-corrupt` (§7) for the whole state:
> the link is a full link that writes a new state, never a panic and
> never an update from a partly trusted state. The checks of IN-18a2 /
> IN-18a3 that span a table (sortedness, the per-file ranges) are made
> over the ranges read; what an update does not read it does not trust
> and does not use.
>
> **IN-18d [v1] The per-file index.** `FILE_INDEX`, one row per `FILES`
> row: the first row and the count of the file's rows in `SECTIONS`,
> `MENTIONS`, `FRAG_AT` and `EH_RECORDS`; the reader checks that the
> ranges are in bounds, ascending and that they tile each table.
>
> **IN-46b [v1] The state patched in place.** An update writes only the
> blocks it changes: the updating flag set (outside the hashes) and
> synced with IN-46's first step; the changed blocks, their list
> entries, the directory entries and the header written; synced; the
> flag cleared and synced. A state whose flag is set is `state-corrupt`
> (a crash between the two syncs). A change that inserts rows uses a
> file's slack or a table's tail; when neither has room, or tombstones
> pass 25% of a table, the update rewrites the state whole (the
> compaction) and says so in `--incremental-report`.

Hashing at read removes the file hashes (568-963 ms) and takes phase
110 down by 0.9-1.2 s, but the resident store keeps every input's bytes

the staged store reads: a file's hash defined as L128 over the hashes of

version) and the detection's hash with it; not prototyped. Its bound is
the file hashes' 535-963 ms less the pieces the link never reads.

## 6. Scope 5: D re-estimated, and the rule

D is WP-094's (dfloor.py's phases, process start and exit, the
translation, 34.5 ms and 0.5 ms), with phases 15 and 106 (the state read
whole and rewritten whole) replaced by the measured ranged read and
patch at 4 KiB blocks (section 4: g10x 3.10 + 191.46 = 194.56 ms;
`cxx-large-g` 4.13 + 154.29 = 158.42 ms). By copy the old state must
stay valid until the new output is renamed into place, so the copy row
is given twice: with the state patched (a journal of the same blocks,

## 7. Scope 6: the directions not taken

**(i) A resident linker process** that keeps the state in memory
between links. What it removes that range I/O does not: almost nothing
of the state's cost. The ranged read is 3.1-4.1 ms; what is left of the
state is the patch's syncs (154-191 ms), which a resident process must
still pay if a crash is not to lose the state (IN-46's order is what
makes a crash safe), and the whole rewrite at compaction. It could
remove the input stats (phase 16: 829.8 ms serial on virtiofs, section
6 after the pool) only by trusting a file watcher instead of stamps,
which IN-22's racy-stamp rule exists not to trust (inotify does not see
writes through another mount, and virtiofs and NFS give no events for a
host's writes), and process start and exit (wall minus phases: about
120 ms on g10x). What it costs: the decoded state and the link's front
held between links, about a plain link's peak (1.97-2.47 GiB at
0.8-1.2 GB outputs) per output being developed, for as long as the
developer works. A crash or a stale process is a state that may not
describe the output on disk: the process must re-check the output's
identity and the inputs' stamps on every request anyway, which is the
update's detection; a process that answers from memory without it can
break IN-2 silently. Not worth it for v1; the measured remaining cost
is the syncs, which it does not remove.

**(ii) What kiln or hod could pass.** An object's own content hash (a
note section) **cannot** replace the linker's: a file edited by another
tool (`objcopy`, `strip`, a GCC or Clang object, a hand edit) keeps a
stale note, and trusting it makes a changed file look clean, which
breaks IN-2; verifying it reads the bytes, which is the cost it was to
save. So no request for a per-object hash. What is safe to take, as
concrete requests, each with its bound:
1. **Stable symbol and section order across recompiles** (an unchanged
   function keeps its symbol-table index and section index; new symbols
   appended, removed ones left as a section-index-0 filler like the
   P-E3 request): the changed file's own rows translate by position
   (IN-28a) and its `MENTIONS`/`SECTIONS`/`FRAG_AT` ranges keep their
   length, so an added or removed function is a same-length patch more
   often and the compaction of section 4 runs less. Bound: a changed
   file's translation and its rows' patch, tens of ms at most on these
   workloads (replay translate is 153-261 ms for **all** files); its
   value is that more edits stay updates, not the time of one.
2. **`-ffunction-sections`/`-fdata-sections` by default in
   `mason`-driven development builds**: a body edit then changes one
   section, so section-level detection (iii) can refill one section's
   windows. Bound: phase 100's refill (185-281 ms here).
3. **A change summary** (which sections changed since the last object
   at this path): useful only as a hint to order the work; mortar must
   still hash to verify. Bound: zero time saved, safely. Not requested.

**(iii) Per-section updates.** Today the changed file's every live
section is refilled, in 1 MiB windows: 25 windows, 26.2 MB refilled for
475 KB of dirty bytes on g10x; 17 windows, 17.8 MB for 1.49 MB on
`cxx-large-g`. Hashing each section (content and relocations) in the
state (16 B a row: +2.9 MB on g10x, +9.0 MB on `cxx-large-g`, plus the
first link's hashing of the section bytes it already reads) would let
the update refill only changed sections and their dependents. Bound:
phase 100 "image (dirty windows)", 185.4-235.1 ms on g10x and
166.8-281.0 ms on `cxx-large-g` (base series), so at most 10-13% of D
by range in place on g10x and 21-35% on `cxx-large-g`, less the
per-section hashes of the changed file. It also bounds the build id's
re-hash (the leaves of the dirty windows). Worth a prototype after the
update exists; not before.

**(iv) Other terms above 10% of the update** (the base series' D by
range in place, section 6: 1,850.3 ms on g10x, 801.9 ms on
`cxx-large-g`):
- **The input stats** (phase 16) on virtiofs: 829.8 ms serial, 44.8%
  of D by range on g10x; on the pool in `p2` (section 5): 102.4 ms.
- **The whole-program phases the D still counts**: resolve, assignment,
  liveness and synthetic (102.7 + 9.6 + 27.3 + 87.8 = 227.4 ms on g10x,
  12.3% of D by range; 163.4 ms, 20.4%, on `cxx-large-g`). D counts them
  as measured over every input (WP-061b §4.1); an O(change) resolve
  (re-resolving only the changed file's keys from `RESOLVED` and
  `MENTIONS` by key) would remove most of it. That is WP-064's delta
  resolution, which this measurement makes the next largest term.
- **Replay translate** (195.7 ms on g10x, 10.6%; 153.5 on `cxx-large-g`,
  19.1%): the positional translation of every unchanged file (IN-28a).
  A translation computed only for what the update reads (the changed
  file's keys and their definers) would be O(change); it is O(files)
  today because the test path replays the whole layout.
- **The copy's writes** (by copy only): 1,140.9 ms on g10x, 3,960.4 ms
  on `cxx-large-g`; the reason in place is the default above the
  small-output size (WP-094 §8 item 5), unchanged.
