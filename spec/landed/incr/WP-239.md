## 1. S4-1: fragment identity

- **Datum.** `FRAGS` (key-keyed, 37 B in format 5): key `(out u32, ordinal u32 := class word, L128)`, plus `offset` and `refs`.
  - The class word is `strings << 31 | align_log2 << 24 | entsize` (entsize ≤ 2^16, S-6).
  - The only writer is the capture (`capture.rs`, frags), from `MergeMeta`. The update writes the same rows from `MergedPiece`.
- **Why it is the identity.** S-13's `MergeMeta` is (out, strings, entsize, align) plus the bytes, with one `FragId` each.
  - There is no tail or suffix merging (S-23, `merge.rs`). So two pieces with equal bytes and class share one fragment and one offset, and no piece lies inside another fragment.
  - `cut::cut` cuts a section by its own bytes only (S-9/S-10), so a file's pieces do not depend on other files.
- **Experiment.** `wp239_probe` runs the full link's function (`mortar_merge::merge::merge`) over every split section of an object set. For each section it compares `cut::cut` offsets with `piece_off`, and checks that `(out, class, L128)` maps one-to-one to `FragId`.

  |---|---|---|---|---|---|---|
  | GCC AArch64 M.1 o0g | 16 | 25,860 | 3,376 | 3,376 | 0 | 0 |
  | GCC AArch64 M.1 o2fs | 16 | 25,966 | 3,275 | 3,275 | 0 | 0 |
  | GCC x86-64 stubs o0g | 10 | 13,659 | 3,367 | 3,367 | 0 | 0 |
  | protoc -g (main.cc.o, libprotoc.a, libprotobuf.a) | 168 | 1,011,939 | 95,977 | 95,977 | 0 | 0 |

  Independently, `frags.py` counted `(out, class, L128)` over the links' own inputs, from the map plus a cut of the inputs. It equals the state's `FRAGS` rows: o0g 4,905, protoc 1,554, g10x 1× 1,007, protoc -g 79,044, cxx-large-g 127,627 + 3 `.comment` = 127,630.
  - So the cut, the class and L128 reproduce the capture exactly on 5 links.
- **Collision.** L128 is also `FILES`' content hash. The capture sorts `FRAGS` by key, so two different `FragId`s with an equal key are adjacent: one compare per row, which it already does. The link must not be wrong because of it, because the full link merged by bytes.

- **Fall-back.** Only the collision; never seen.

## 2. S4-2: what a file's old version named

**`FRAG_AT` is broken.** It has one row per fragment at its first occurrence, so it cannot give the old version's references.
- On the M.1 series it names 1,586 of strutil.o's 2,288 old fragments (o0g), 1,432 of 2,150 (o2fs), and the same on x86-64 (1,586 of 2,288; 1,443 of 2,158).
- Its `frag` column is a `FRAGS` row number, which a key-keyed insert renumbers.

**Datum.** `FRAG_USE`:
- File-keyed. One row per (file, fragment the file's live split pieces name): `{file u32, out u32, class u32, L128}` = 28 B.
- It refers to the fragment by its identity (the `FRAGS` key), never by row number, and to the file by `FILES` row (file-keyed blocks; "first" is by `FILES.rank`).
- `FRAGS.refs` is the number of distinct files with a `FRAG_USE` row for the fragment.

**Writer.** The capture writes it from the merge's `piece_frag` per section, deduplicated per file. The update writes the changed file's rows from `MergedPiece`.

**Maintenance per file whose contribution changes:**
- Changed, gone, no longer extracted, or a COMDAT copy losing its keep: read the file's old block. For each row, decrement `refs`; at 0 the fragment is dead (its bytes stay as a hole, IN-56 style, or the section is refilled, which is U-4's choice).
- Changed, appeared, newly extracted, or a copy becoming the keeper: write the new block. For each row, increment `refs`, inserting the `FRAGS` row at refs 1 (offset from U-4's placement).
- Compaction rewrites both tables from the capture of the same rows, with no renumbering because of the identity reference.

**The `-g` explosion decides the scope.** Pieces, (file, fragment) pairs and fragments per output section (`frags.py`; alloc pieces come from the link's map, non-alloc ones from cutting the linked inputs):

- **Today**, an incremental-mode link captures **every** split section into `FRAGS` and `FRAG_AT`, debug included: 2.21 M fragment rows on clang, about 124 MB of U-2's 279 MB format 5. Nothing reads them in v1, because any changed or appeared file with debug sections is `(debug)`.

**Experiment.** `model.py` over the M.1 series (base, grow1, grow2, rmfn + an appearing `stub.o`, addfn + `stub.o` gone, base).

- It also compares the fresh fragment count with the new state's `FRAGS`.
- Result: equal on all 5 hops, o0g and o2fs, AArch64 and x86-64 (4 series). Fragments whose `refs` fell to 0 per hop: 1–6, and rose from 0: 1–6.

**Fall-back.** `.debug_*` (as §7's `(debug)`, widened by P-3).

## 3. S4-3: `.eh_frame`

**U-4's claim checked on the bytes.**
- `ehmap.py` reads the map's eh pieces; `ehbytes.py` walks the output's `.eh_frame`.
- On the incremental-mode full link the records are contiguous with no pad, grouped in one run per file, in file order, with the terminator last. Every FDE's CIE is in its own file's range.

| link | files with records | records (FDE/CIE) | bytes | range median / p90 / max | FDEs with CIE in another range |
|---|---|---|---|---|---|
| M.1 o0g AArch64 | 562 | 5,659 | 237,816 | | 0 |
| M.1 o0g x86-64 | 637 | 6,108 (5,411/697) | 232,680 | 80 / 496 / 11,992 | 0 |
| M.1 o2fs x86-64 | 635 | 5,925 | 228,784 | 80 / 496 / 11,992 | 0 |
| protoc | 735 | 28,935 (28,032/903) | 988,460 | 104 / 2,252 / 100,328 | 0 |
| g10x 1× | 1,352 | 202,305 | 7,281,268 | | 0 |
| cxx-large-g (`--strip-debug`) | 2,783 | 164,606 | 8,379,812 | | 0 |

**Encodings** (every CIE, all links):
- FDE `0x1b` (pcrel | sdata4), LSDA `0x1b`, personality `0x9b` (indirect pcrel sdata4).
- Augmentations `zR`, `zPLR`, and once `zRS` (the x86-64 glibc signal frame).
- The walker knew every field.

**So U-6 moves an unchanged range by Δ from the previous output's bytes alone.** Walk the records by their length words, then subtract Δ from each FDE's `pc_begin` and from the LSDA (`0x1b`) and personality pointer (pcrel `0x9b`) fields. The CIE pointer is relative within the range and does not change. A range holding any other encoding is not movable this way, and the update falls back by name (`update-not-implemented (eh)`): it is never seen in these inputs.

**Datum.** Three `u32` columns on `FILES` (12 B per row):
- `eh_offset`: from the `.eh_frame` chunk start.
- `eh_capacity`: bytes including pad.
- `eh_records`: the count.

Not a `REGIONS` row (U-4's proposal): `RegionRow` is keyed `(out, category, ordinal)` and has no file column, so a file's range could not be found in O(1).
- Record sizes and `EH_RECORDS` are not needed to move a range, and a changed file re-derives its own (S-47) from its new bytes.
- Whether anything else reads `EH_RECORDS` was not examined (§12).

**Writer.** `EhPlan` in the incremental-mode full link with `per_file` pads (today `from_records` adds no pads; the pads exist only on replay). This is the first change U-6 or the join makes.

**Pad.** max(16, ceil4(size·f)), so a padding CIE always fits (IN-34a's ≥16, and its 4/8/12-byte absorption covers the rest). Output bytes:

| pad | protoc | g10x 1× | cxx-large-g |
|---|---|---|---|
| 1/16 | 67,400 | 458,980 | 535,232 |
| **1/8** | **127,272** | **913,448** | **1,055,484** |
| 1/4 | 248,768 | 1,823,268 | 2,099,776 |

**Overflow frequency** (`model.py`; capacity persists across hops). The changed strutil.o's range size per hop:
- o0g AArch64: 7936 → 7936 → 7936 → 7936 → 7960 → 7936.
- o2fs AArch64: 4704 → 4712 → 4712 → 4640 → 4728 → 4704.
- x86-64: o0g 8296 → … → 8328 → 8296; o2fs 6416 → 6344 → 6432 → 6408.

Pad 0 overflows in 1/5 (o0g) and 2/5 (o2fs) hops on both targets; pad 1/8 in 0/20. Untouched ranges kept their size on every hop.
- **The appearing `stub.o` lands between two stored ranges in rank order on every series.** That forces the whole rewrite whatever the pad (R-3).

**Whole rewrite cost, g10x 1×:** 7.28 MB + 0.91 MB pad written, 1,352 range rows read, previous-output bytes read; no input is read for unchanged files.

**Fall-back.** Overflow (0/20 with pad 1/8) and appearing files (R-3) give a whole rewrite, not a refusal. An unknown encoding gives `(eh)` (0 seen).

## 4. S4-4: slots

**What `INDEX` kind `SLOT` is.** It is set from the relocation classifier (`uses_slot(classify)` in `tables.rs`), not from the scan's demand.

**The refutation (slot series, `slotseries.sh`).**
- Setup: a.c is edited; b.c shares `gx`; c.c defines ifuncs f1/f2; d.c defines `__thread` tx/ty. Compiled with `-O2 -fPIC -ftls-model=initial-exec`, static.
- On AArch64 the model with demand = INDEX `SLOT` ∪ GLOBAL references to IPLT keys passes all hops (GOT gy retired and gz added; IPLT f1 → f2; TLS IE tx retired).
- On **x86-64 it fails on every hop**. GOTTPOFF is relaxed to LE in a static link, so `INDEX` names `__libc_errno`, `__libc_tsd_CTYPE_B` and `__libc_dlerror_result` as slot users with no slot (and `tx` never gets one).
- The same 3 extras appear on the x86-64 M.1 series (FAIL 5/5).
- Conversely, IPLT slots (an ifunc reached by a call) have only GLOBAL rows, and TLS IE slots on locals (`.LANCHOR0`) are `LOCAL_SLOT` rows.
- So `INDEX` is not the demand in either direction. The demand is `arch.scan`'s `DemandFlags`, after relaxation decisions and with resolution facts.

**Measured** (format 4 state, AArch64):

| workload | GOT | IPLT | TLS IE | `SLOTS` | `INDEX` SLOT rows | keys' file users (sum) | unit users (sum) |
|---|---|---|---|---|---|---|---|
| protoc | 688 | 5 | 23 | 716 | 3,179 | 1,615 | 3,179 |
| g10x 1× | 110 | 5 | 21 | 136 | 432 | 432 | 432 |
| cxx-large-g | 4,658 | 5 | 25 | 4,688 | 30,033 | 13,183 | 28,682 |

The x86-64 rows of the three big workloads were not linked (§12); x86-64 was measured on the slot series and M.1 only (553 `SLOTS`).

**Datum.**
- `KEY_REFS` (key-keyed by (key, file), 12 B, the `flags` byte has no spare bit) gains `demand u16` = the OR of the file's `DemandFlags` on that key. That is 14 B per row: +162 KB protoc, +618 KB clang.
- `SLOTS` gains `refs u32` = the number of files whose `demand` needs that slot kind: +19 KB / +35 KB with IN-18e's minimum append area.

**Counted per file, not per unit**, so that the capture and the update agree. Without `--gc-sections` every unit of a live file counts, and the join scans whole files. WP-238 will need it per unit (28,682 vs 13,183 rows on clang) and should add it then.

**Writer.** The scan through S4-5's recording sink, in the incremental-mode full link, and in the join for changed files.

**Maintenance.** For a changed, gone or appearing file: subtract its old rows' demand (from its `KEY_REFS` rows), add its new.
- A slot whose `refs` reaches 0 is retired. A new demand appends a slot.
- The IPLT and IRELATIVE order follow `SLOTS`' order (`two_ifuncs_added_irelative_order`; not examined, §12).
- IN-28b's local slots stay per file in `LOCAL_SLOT` as today, and go with their file.

**Stale case.** `arch.scan`'s flags depend on the target's resolution (`Ifunc`, absolute, undefined weak). If a changed file changes such a fact of a key that unchanged files reference, their stored demand is stale. The join detects it from `ResolveDelta` (the resolution kind of a key changed) and either falls back by name (`update-not-implemented (slots)`) or rescans the referrers that `KEY_REFS` lists (R-4).

## 5. S4-5: one per-file demand producer (design, no edit)

`Sink::raise` today ORs a global demand into `&[AtomicU16]` and keeps locals. The factoring:

```text
pub trait GlobalDemand { fn raise(&mut self, id: SymbolId, flags: DemandFlags); }
impl GlobalDemand for Shared<'_>    // today's body: load, fetch_or if new bits
impl GlobalDemand for Recording<'_> // Shared's body + push (id, flags) to self.file
fn run_unit<G: GlobalDemand>(.., g: &mut G) -> UnitOut   // Sink<'u, G>
```

- The plain link instantiates `Shared`, which is the same code as today after monomorphisation, so its cost is nil.
- The incremental-mode full link instantiates `Recording`. The caller, per file, sorts its units' `(id, flags)` by id and ORs them, which gives `FileDemands` and the `KEY_REFS.demand` column.
- The join calls the same `run_unit::<Recording>` over a changed file's units, with no link-wide column (`Recording { cells: None }`).
- The full link pays one `Vec` push per record that raises a global demand, plus a per-file sort. That is not measured; the `INDEX` GLOBAL rows, 67,661 on protoc, bound the entries.

## 6. Seam 4's inputs against their producers

**Pieces (`MergedPiece`): run, equal.**
- `cut::placed_whole` + `cut::cut` per file give exactly the full merge's pieces on the four GCC sets above: 0 offset differences, 0 identity conflicts, 1.01 M pieces.
- kiln (`kiln++` k3c + hod a68, `-O0 -g`, 5 protobuf stubs per target): 0 offset differences and 0 conflicts on AArch64 (5,041 pieces) and x86-64 (5,018). kiln emits no duplicate piece within a file (pairs = pieces).
- `cut::placed_whole` placed 0 split sections whole in these sets. `SHF_COMPRESSED` sections (`-gz`) are placed whole (S-5) and were not in the inputs.

**`EhPlan::select_in(per_file)`: NOT RUN, and not reachable from a test without a `src/` edit (finding).**
- An `EhSource` needs `EhFrames` from `mortar_merge::eh::parse` with `EhReloc`s carrying resolved `Target`s.
- `MergeEh` needs a `phase::Link`, which only the front builds.
- Instead, the bytes-level checks of §3 hold on the full link: one contiguous run per file, CIEs local to a range. Those are the properties the per-file selection relies on.
- The equality "per-file selection = the full selection restricted to the file" stays **argued, not run**. The join's first test should be it: a test helper in `mortar_synth` (a `#[cfg(test)]` constructor) is the smallest way in.

## 7. What breaks in U-4's proposals

1. **S4-4, "slot kinds as `INDEX.kind` values"**: refuted on x86-64. Relaxed IE gives 3 phantom users per link. IPLT slots have no `SLOT` row, and TLS IE on locals are `LOCAL_SLOT`. `refs` per `SLOTS` row alone cannot be decremented without the old version's per-file demand.
2. **S4-3, "one `REGIONS` row per file, ~32 B, 784 files"**: `RegionRow` has no file column (keyed by out, category and ordinal), so a file's range cannot be found by file. The measured count is 735 files with records on protoc, not 784.
   - "Record offsets from S-47 sizes of the file's own records" holds only for changed files. Unchanged ranges are moved from output bytes, which is safe only because the encodings are `0x1b`/`0x9b` (now measured).
   - Appearing files force a whole rewrite whatever the pad (not stated in U-4's proposal).
3. **S4-2, "+16 B per extra row"**: the identity reference makes the row 28 B. On `-g` inputs it explodes (2.0× and 2.85× the gate), so the proposal holds only with the `.debug_*` exclusion. Today's capture already stores 2.2 M debug fragments on clang that v1 never reads.
4. **§7's `(debug)` clause** covers "changed, appeared or newly extracted" files with debug sections. A **gone** or no-longer-extracted file with debug sections, or a changed file whose **old** version had them, is not named.
   - Under IN-56 its dead strings may stay, but this must be said, or the clause widened (P-3).
5. **S4-1** survives as proposed.
6. **S4-5** survives as a finding. The factoring is in §5.

- `StoredFrag { out, class: u32, hash: L128, offset, refs }`: `ordinal` renamed to `class` (the class word).
- `StoredFragAt` is deleted. In its place: `StoredFragUse { file: FileRow, out, class, hash }`, read per file (`frag_uses_of(file)`).
- `StoredEhRange { offset: u32, capacity: u32, records: u32 }` per file (`eh_range_of(file)`). `EhRange { file, offset, capacity, records }` (output) is unchanged.
- `StoredUse { key, slot }` becomes `StoredKeyRef { key, file, …, demand: DemandFlags }`. `StoredSlot` gains `refs: u32`.
- `FileDemands` is as seam 4 has it, filled by S4-5's `Recording` sink; `SlotDemand { key, flags }` is unchanged.
- `MergedPiece`, `MergeClass`, `EhRecordIn` and `EhFile` are unchanged (§6 run for pieces).
