# WP-238 — liveness under `--gc-sections` in an update (IN-29, IN-71a)

Branch `wp/238-incr-live`, base ffdda274. Step 1 only: the design, backed by
experiments. No step-2 code. The experiment probe (`mortar_live`'s feature
`wp238-probe`) and the scripts under `tests/incr-design/wp238/` are
experiment code. The probe is deleted in step 2.

## Step 1

### 0. What needs a ruling

1. **R-1. Two new row kinds, not `SECTIONS` columns.**
   - Today IN-29 says `linkorder` and `group` are "columns of the sections table".
   - `format::SectionRow` has no such columns; it has no `sh_link` and no group.
   - Proposed: `LINK_ORDER` (7) and `GROUP` (8) become `EDGES` kinds. `GROUP` is stored as a ring, one row per member.
   - Also proposed: `ROOT` (9) and `NAMED` (10) as row kinds (§2).
   - All four are made by the one enumerator, so no second derivation exists anywhere.
   - The alternative is wider `SECTIONS` rows, which every link pays for.
2. **R-2. Narrow `EdgeRow` from 17 B to 13 B** (`offset: u64` becomes `u32`, with `u32::MAX` meaning "every piece").
   - Nothing is lost: a split section's piece offsets are `u32` in `mortar_core::split`, and the mark's `To::Section` offset is `u32` too.
   - It saves 24% (cxx-large-g: 21.5 MB becomes 16.5 MB).
   - No state holds `EDGES` rows yet, so nothing migrates. IN-18e's "17-byte rows" changes.
3. **R-3. The old live set comes from a second walk, not from a stored bitmap.**
   - The second walk runs over the stored rows and the stored `RESOLVED`, before `ResolveDelta`.
   - It needs no format change and gives the old marks at piece level.
   - It costs one more walk: 37.7 ms on cxx-large-g.
4. **R-4. `LiveDelta` gains two fields** (`drawn_in`, `pieces`; diff D3).
   - Rule: **a file with a section or piece flip and no byte change is read as drawn in**. This widens IN-72 item 2a from "election" to "election or liveness".
   - Every consumer then sees only the cases it already handles: changed and drawn-in files.
   - The rows of an unchanged file are the same when fresh (stale rows: 0 on every emulated update, §6), so reading such a file does not feed back into the walk. No fixpoint is needed.
5. **R-5. `OptionKeys` has no `--gc-keep-exported`** (D4). `live` cannot see the flag, so an update under it is silently wrong as soon as gc is enabled. Proposed:
   - add the field;
   - v1 refuses `update-not-implemented (live)` when it is set;
   - the rooted keys then come from `entry`, `undefined` and `require_defined` only. `RefFlags::EXPORTED` cannot occur, because the update already refuses dynamic tables.
6. **R-6. Under gc, `KEY_REFS.demand` and `FRAG_USE` must count live units only.**
   - Keep WP-239's row shape, one row per (key, file) and per (file, fragment).
   - The value counts only the units that are live, from `LiveDelta`, in both the capture and the update.
   - This needs a sentence in IN-18e, P-2 and WP-239's datum.
7. **R-7. The new mod line `#[cfg(feature = "wp238-probe")] mod probe;` in `gc.rs`** (experiment only, off by default).
   - Its feature line `[features] wp238-probe = []` is in `mortar_live/Cargo.toml`.
   - Asked for: keep it until step 2's tests replace it, then delete both.

### 1. One edge enumerator, and what it costs a plain link

- **The enumerator** (committed in d46d3550): `crates/mortar_live/src/gc.rs`, `Walk::edges(unit, sink: FnMut(Via, To))`.
  - For one unit of a section it yields every I-7 edge:
    - `Via::Record`: relocation records, both `reloc` and `local`, chosen by the target;
    - `Via::Frame`: the FDE edges of a code section, through its CIE's personality;
    - `Via::LinkOrder`: the `SHF_LINK_ORDER` dependents of the section;
    - `Via::Group`: the other members of its group.
  - The target is either `To::Key(SymbolId)`, after `sym_map` and an undefined mention's `redirect` but not resolved, or `To::Section(SectionId, offset | WHOLE)`.
  - The plain mark resolves `To` at walk time (`Walk::resolve`). That is the update's rule too, so the plain link and the update share one producer.
  - `record_target` (which resolved through `defs`) became `record_to`, which does not resolve. `eh_edges` no longer takes `defs`.
  - The round-0 roots are one closure, shared by the mark and the probe.
  - The `SHT_REL` implicit-addend re-read now applies only to `To::Section(s, WHOLE)`. A key's piece is chosen by the key's value, not by the addend, so this is equivalent; the replay below shows 0 differences.
- **The row kinds** (`probe::kind_of`) come from `(Via, To)`, the source's alloc flag and the key's name:
  - `reloc` / `startstop`: a key, split by its name;
  - `local`: a section;
  - `fde_section` / `fde_key`;
  - `nonalloc_key` / `nonalloc_section`: the source is not allocated;
  - `linkorder`;
  - `group`.
- **Cost to a plain link** (`plaincost.sh`):
  - Interleaved runs of ffdda274's release binary (base) and this branch's (new), on the bench's captured links plus `--gc-sections --time-phases`, at a 1-minute load below 12.
  - Medians (wall from the shell, ms; phase 50 from `--time-phases`, ms; peak MiB), base / new:

    | link | runs | wall | phase 50 | peak |
    |---|---|---|---|---|
    | protoc `-g`, default threads | 10 + 10 | 275 / 272 | 12.5 / 14.6 | 245.8 / 244.4 |
    | protoc fs, default threads | 10 + 10 | 185 / 176 | 12.1 / 11.6 | 159.1 / 157.9 |
    | protoc `-g`, `--threads=1` | 10 + 10 | 631 / 636 | 18.8 / 19.1 | 211.3 / 211.2 |
    | protoc fs, `--threads=1` | 10 + 10 | 299 / 302 | 17.6 / 17.6 | 142.1 / 142.1 |
    | cxx-large-g, default threads | 5 + 5 | 5,942 / 5,666 | 139.0 / 132.3 | 1,960.7 / 1,955.8 |

  - **Nothing measurable.** The differences go both ways and are within run-to-run spread (the host is shared, at a 1-minute load below 12). Every phase-50 median is within 2.1 ms. The `--threads=1` rows, which are the least noisy, differ by at most 0.3 ms.
  - Outputs: base and new byte-identical on every run of every series (`cmp`: 0 `OUTPUTS DIFFER` in `cost-*.log`).
  - `cargo xtask static-identical`, the standard way (the release build, byte-identical to `mortar-new`; `MASON_KILN`/`MASON_HOD` set): **3,493 links of 495 tests, 0 differ**.
    - Run through `--mortar <copied binary>`, both ffdda274's binary and this branch's give the same 678 stderr-only differences on the links they share; this is the invocation, not the change.

### 2. The stored form

`EDGES` (kind 42, file-keyed, `--gc-sections` only). One row per distinct `(kind, source, target, offset)`, written for every **kept** section of the file (a dead section's rows are needed when it revives).

| kind | name | source | target | offset | writer | reader |
|---|---|---|---|---|---|---|
| 0 | `RELOC` | `SECTIONS` row | `SYMBOLS` row | 0 | capture; U-2 (the join's fresh rows) | `live` |
| 1 | `START_STOP` | `SECTIONS` row | `SYMBOLS` row of `__start_N`/`__stop_N` | 0 | same | `live`: the key's def if defined, else every `NAMED` section named `N` |
| 2 | `LOCAL` | `SECTIONS` row | `SECTIONS` row | piece offset, or `u32::MAX` (every piece; `SHT_REL`) | same | `live` |
| 3 | `FDE_SECTION` | the code section | `SECTIONS` row (LSDA's) | 0 | same | `live` |
| 4 | `FDE_KEY` | the code section | `SYMBOLS` row (personality, through `DW.ref.*`) | 0 | same | `live` |
| 5 | `NONALLOC_KEY` | non-alloc, non-debug section | `SYMBOLS` row | 0 | same | `live` |
| 6 | `NONALLOC_SECTION` | non-alloc, non-debug section | `SECTIONS` row | piece offset or `u32::MAX` | same | `live` |
| 7 | `LINK_ORDER` (new) | the `sh_link` target | the `SHF_LINK_ORDER` dependent | 0 | same | `live` |
| 8 | `GROUP` (new) | a member | the next member of its group (the last names the first) | 0 | same | `live` |
| 9 | `ROOT` (new) | a root section (I-6's section rules: `keep`, notes and non-alloc not grouped with an alloc member, `.eh_frame`, no place, start-up tables; never `SHF_LINK_ORDER`) | 0 | 0 | same | `live` (the walk's start) |
| 10 | `NAMED` (new) | a kept section whose name is a C identifier | its name's `Str.off` (= `SECTIONS.name.off`) | its name's `Str.len` | same | `live` (`START_STOP`'s targets, without scanning `SECTIONS`) |

How keys and sections are named:
- Sections are `SECTIONS` rows and keys are `SYMBOLS` rows, as `EdgeRow` already does and as `INDEX` does.
  - capture writes them through `sec()` (state5/write.rs).
  - Compaction remaps them through `per_file` (compact.rs).
  - The two lists of "target is a section" kinds (write.rs:203, compact.rs:557) gain `LINK_ORDER | GROUP`.
  - `EdgeRow::ok` becomes `kind <= edge_kind::LAST`.
- In `ChangedFile.edges` (the join's fresh rows), ids are "as `index`": sections in the new id space, keys as positions in `keys`. This is unchanged.
- I considered naming sections by in-file index instead. I dropped it: it would differ from `INDEX` for no gain, since compaction remaps both.

**Roots: a row kind, decided with the reason.**
- Every section rule of I-6 is a function of the file alone: its headers, its group sections, its kept bits and the fixed script (`keep`, `out_of`; a script change is `options-changed`). See `file_facts` in gc.rs.
- So the rule is recomputed per file, by the enumerator's own `file_facts`, for changed and drawn-in files, and stored as `ROOT` rows for the others.
- A `SECTIONS` flag would be a second writer of the same fact, and `SECTIONS` has no spare bit.
- All root sections are stored, debug ones included. Storing only the walkable ones (alloc, or with edges) would need a second rule ("a non-alloc kept section with no rows is live") and save only 0.2 MB on the largest link.
- The rooted keys are not stored: `entry`, `undefined` and `require_defined` come from `OptionKeys` through `find_key`. `--gc-keep-exported` is R-5.

**Group as a ring.**
- Liveness of a group is symmetric (any member live means all are live), so a ring of n rows reaches what n(n-1) pairs reach.
- Measured, distinct pair rows against ring rows:

  | link | pair rows | ring rows |
  |---|---|---|
  | protoc fs | 10,531 | 4,989 |
  | protoc `-g` | 4,521 | 2,075 |
  | cxx-large-g | 3,524 | 1,614 |

**Pieces of split sections.**
- `LOCAL` and `NONALLOC_SECTION` rows carry the offset the record names.
- A key defined in a split section marks the piece at its `RESOLVED.value`. There are 11 such keys on all three bench links (51 rows).
- The walk records, per split section, the offsets it marked or `u32::MAX`. The piece containing an offset is found where the file's bytes are read (the drawn-in or changed file), so the update stores no piece boundaries.
- Replay at piece level: 0 differences on every link (§6).

**Sizes** (`.sum` files: distinct rows over the kept sections; ring and `ROOT` counted as proposed):

| link | output | rows (proposed form) | at 17 B | at 13 B (R-2) | IN-29's estimate |
|---|---|---|---|---|---|
| protoc `-g` (bench `cxx-medium-g-static`, `-O0 -g`, no function sections) | 49.4 MB | 120,428 − 4,521 + 2,075 + 2,426 + 2 = **120,410** | 2.05 MB | **1.57 MB** | 59,971 rows, 0.48 MB at 8 B |
| protoc fs (`cxx-medium-gc-static`) | 10.0 MB | 153,983 − 10,531 + 4,989 + 1,554 + 2 = **149,997** | 2.55 MB | **1.95 MB** | — |
| cxx-large-g (clang 19 `-O2 -g`, static, the largest link) | 1,120.7 MB | 1,244,166 − 3,524 + 1,614 + 23,588 = **1,265,844** | 21.5 MB | **16.5 MB** | +9.9 MB (17.5 B a section) |

**IN-29's estimates are corrected.**
- protoc `-g` has 2.0x its rows (4.3x its bytes at 17 B).
- The estimate counted only distinct (source section, target section) pairs whose source is live. Stored rows must also cover dead kept sections: 15,026 rows on protoc `-g` have a dead source.
- Stored rows also keep key targets as keys, without collapsing to the section, so that a moved definer is followed.
- cxx-large-g is 2.2x the §5.5 row of +9.9 MB: 37.6 B a section at 17 B, 29 B at 13 B.
- Per GB of output on cxx-large-g: 14.7 MB at 13 B.

### 3. The walk in an update

**Inputs.**
- The stored `EDGES` rows of every file not in `changed`; the fresh `ChangedFile.edges` of changed and election-drawn files.
- `RESOLVED`, stored for the old walk; for the new walk, stored rows overridden by `ResolveDelta.resolved` (affected keys).
- `OptionKeys`' rooted keys.
- `SECTIONS`, only to translate `NAMED` names. Kept bits are implicit: rows exist only for kept sections, and a file whose kept set changes is drawn in (IN-72 item 2a).

**Output.**
- The new marks, per section and per split-section offset.
- The old marks from the same walk over stored data (R-3).
- `LiveDelta` = their difference, plus `drawn_in` and `pieces` (D3).

**Does `live`'s signature carry it?**
- `view`, `changed`, `resolved` and `options` carry every input above, except `--gc-keep-exported` (R-5).
- `LiveDelta` does not carry what the consumers need. By consumer:

| consumer | datum it takes | in `LiveDelta` today? |
|---|---|---|
| the join (U-10) | which unchanged files to read as drawn in (their bytes, fresh rows, `SectionChange::live`) | no: `drawn_in` (D3) |
| U-4 `layout` (IN-72 items 1, 2a; WP-216) | sections now live (placement or revival at the stored offset) and now dead (holes) | yes |
| U-4 item 6 (merged; WP-239 `FRAG_USE`) | per live split section of a changed or drawn-in file, the live pieces | no: `pieces` (D3) |
| U-3 `refill_set` (IN-27's liveness row) | sections now live; referrers of globals defined in sections now dead | yes (the referrers come from `KEY_REFS`) |
| U-5 `symtab` (WP-217) | the files whose locals change: changed plus drawn-in | yes, if `drawn_in` is included in `plan`'s `files` |
| `.eh_frame` (WP-216 item 5, WP-239) | FDEs of code sections now live or now dead | yes (the sections); the file's records come from its bytes (drawn in) |
| U-6 map | `place` versus `discard … gc` lines of the flipped sections | yes |
| ODR (WP-220) | the files whose live units' rows change | yes, if `drawn_in` (WP-220 does not say whether gc-dead units count: §5) |

**Cost, measured.**
- On the update's path, the probe's `stored-form` line: encode the rows as 17-B `EdgeRow`s, then decode, index by source and walk; one thread, best of 3, at a load of about 10.
- The update runs this twice (R-3).

| link | output | rows | one decode + walk | per GB of output, two walks |
|---|---|---|---|---|
| protoc `-g` | 49.4 MB | 2.05 MB | 2.65 ms | 107 ms/GB |
| protoc fs | 10.0 MB | 2.62 MB | 2.07 ms | 414 ms/GB (a small output with many sections) |
| cxx-large-g | 1,120.7 MB | 21.2 MB | 37.7 ms | **67 ms/GB** |

- Reading the rows from the state, about 21 MB from the page cache, is not included.
- The walk alone, without decode, on in-memory rows is 2.3, 1.5 and 36.5 ms.
- The cost is O(stored rows), as IN-71a says.
- Phase 50 of the full link of cxx-large-g is 793 ms, so the update's liveness is about 1/10 of the full link's.

### 4. Whether the common update can skip the walk

**Rule.** Skip both walks, and return `LiveDelta` empty with `pieces` taken from the stored marks, when all of these hold, compared by identity (file by path and member; section by (file, index); key by name):
1. no file appeared, went or changed extraction;
2. `ResolveDelta.reelected` is empty (no election draw-in);
3. each changed file's fresh rows, `ROOT` and `NAMED` included, equal its stored rows;
4. no affected key's definition moved (its `(file, section index)`, and its value when the section is split);
5. the rooted keys are the same.

The check is O(change): the changed files' rows and the affected keys. Condition 5 is the options' (`options-changed`) except for keys that become defined or undefined, which condition 4 covers.

**Proof sketch.**
- The live set is the least fixpoint of (roots, rows, resolve), and the walk is a function of exactly those inputs.
- Unchanged files' rows and roots are unchanged by construction: each is a function of the file alone, given the kept bits, which condition 2 fixes.
- Conditions 1-5 make every remaining input equal by identity. So the fixpoint is the same, at section level and at offset level.
- `NAMED` belongs to condition 3 and changes only with a file.

**Refuting experiment.** `emulate.py` evaluates the rule on every emulated update. Where it holds, it checks that the old full link's live set equals the new one's. Result: the rule holds on 124 of the 336 L10 emulated updates, and on **all 124 the old live set equals the new one** (0 counterexamples). It holds on none of the 16 g-scenario updates, which all change rows.

**How often L10's edit shapes meet it.** 124 of 336 (37%: 6 configurations, 28 edit rows, forward and back). Among the 212 updates where it fails, the reasons counted (an update can have several) are: rows 204, defs 142, roots 96, election 36, appeared/gone 12. The rule fails on:
- "rows": any edit that changes a call, a reference or a constant;
- "defs": a definition moves inside its section;
- "election", "appeared/gone".

**The fall-through** costs the two walks of §3: 2.7 to 38 ms on these links.

### 5. A section of an UNCHANGED file that dies or becomes live

**Measured.** 40 of the 352 emulated updates have a section flip in an unchanged file: the 2 `gc-*` rows of L10 × 6 configurations × 2 directions, and all 16 g-scenario updates. The flips seen were:
- `gc-kill-revive` and `gc-revive-first`: a `.text` helper of an archive member;
- the g scenario: `.text.dropf` and its `SHF_LINK_ORDER` section `.meta_d` in u.o.

Piece-level flips in unchanged files: 0 in all 352.

Under R-4 such a file is **read as drawn in**. Every part of the update that must act on it:

| layout hole or placement | a section now dead becomes a hole; one now live is placed or revived at its stored offset | WP-216: item 1 and item 2a (drawn-in), `gc_section_dies_then_revives`. A dead section's hole is refilled by its kind. It never names a liveness flip as the cause: it acts on what U-4 gives, so it is covered through `drawn_in`. - `(live)`: `--gc-keep-exported` (R-5);
- `(live)`: a demand change of a drawn-in-by-liveness file until R-6;
- `(live)`: `.mason.meta` units in such a file until WP-220 says.

## Step 2: the design after the review

This section replaces Step 1's §2 to §5 and §7 where they differ. The rulings are `briefs/wp-238-rulings.md` ("After the review" wins). There is no skip rule (F5). The oracle's results are §S6.

### S1. The stored form

`EDGES` (kind 42, file-keyed, written only under `--gc-sections`). Each row is 13 bytes: `kind u8, source u32, target u32, offset u32`.

**Who writes the rows.** There is one producer, `mortar_live::stored_edges`. It is the enumerator `Walk::edges` (the full mark's only walk, IN-29) plus `file_facts`/`section_groups`. It is called by the capture for every file and by the join for changed and drawn-in files. Rows are made for every **kept** section of a file, live or dead, and sorted and deduplicated by `(source, kind, target, offset)`.

**Ids.** In the state, `source` and a section `target` are `SECTIONS` rows, and a key `target` is a `SYMBOLS` row. `ChangedFile.edges` uses the same id spaces as `ChangedFile.index`.

**F8's normalisation (the producer; one rule for capture and join).** A row whose section target is not kept is dropped. A section target that is split (it has a `SPLIT` row) keeps the offset the record names, or `u32::MAX` (every piece). Any other section target gets offset 0, and a non-split self-edge is dropped. A key target gets offset 0. `u32::MAX` cannot be a real offset (R-2's rule): a split section of 4 GiB or more is already refused as `feature` (`spec/model.md` §3.5, `mortar_merge` `What::SectionTooLarge`), so every real offset is at most 2^32 − 2.

| kind | name | source | target class | offset after F8 |
|---|---|---|---|---|
| 0 | `RELOC` | kept allocated section | key (`SYMBOLS`) | 0 |
| 1 | `START_STOP` | kept allocated section | key named `__start_N`/`__stop_N`, N a C identifier | 0 |
| 2 | `LOCAL` | kept allocated section | section of the same file (local or section symbol), kept | split: offset or `u32::MAX`; else 0, and no self-edge |
| 3 | `FDE_SECTION` | the FDE's code section | section (LSDA, CIE-named data) of the `.eh_frame`'s file, kept | as 2 (this drops the FDE's own initial-location self-edge) |
| 4 | `FDE_KEY` | the FDE's code section | key (personality through `DW.ref.*`, a global LSDA) | 0 |
| 5 | `NONALLOC_KEY` | kept non-allocated section | key | 0 |
| 6 | `NONALLOC_SECTION` | kept non-allocated section | section of the same file, kept | as 2 |
| 7 | `LINK_ORDER` | the `sh_link` target | the `SHF_LINK_ORDER` dependent | 0 |
| 8 | `GROUP` | a kept member of a group with two or more kept members | the next kept member in section order; the last names the first (a ring, re-made whenever the file's kept set changes, which draws the file in) | 0 |
| 9 | `ROOT` | a root section (I-6's section rules: `file_facts`' `ROOT` bit) | none: 0 | 0 |
| 10 | `NAMED` | a kept section whose name is a C identifier | none: 0 (the walk reads the source's `SECTIONS.name`; F4) | 0 |
| 11 | `SPLIT` (proposed) | a kept split section (`Split::merge_of`) | none: 0 | 0 |
| 12 | `REFUSE` (proposed) | the section the refusal is about | the reason code: 1 `fde-global` (F3), 2 `def-dropped` (F6) | 0 |

The **rule for kind 1** is unchanged: it records where the row came from. It no longer says how the key is read (F2; see S2).

**Why `SPLIT` is a row.**
- The walk must know whether a target is split. That decides whether it records a key's `RESOLVED.value` or an offset, whether R-4's piece flip in an unchanged file can occur, and what the live-set hash covers.
- `SECTIONS` cannot tell. A split section is `Split::merge_of`'s choice, which uses `sh_entsize` and the merge rules, and `SECTIONS` has neither.
- It is the same fact the full link uses (`MERGE` bit), written by the same producer.
- Cost: protoc fs has 1,554 split sections and cxx-large-g has 23,588 (Step 1 §2).

**Why `REFUSE` is a row.**
- It is per file. A file that stops having the defect clears it by changing (its rows are fresh), with no full link in between.
- Every update reads it, because the old walk reads every stored row and the new walk reads every fresh one.
- A `META` flag would be sticky until the next full link, and would need a second writer.
- The probe's prototype also has a code 3 (relocations that cannot be read). It is not proposed: the full mark fails the link on such a section first (I-4), so no state could carry it.

### S2. The ONE key reader (F2)

Every key-target row (kinds 0, 1, 4 and 5), and every rooted key, goes through the same reader. The row's kind is not read. The reader does what the full link's `def_target` does (gc.rs), on the key's `RESOLVED` row:

| `RESOLVED.def_kind` | the reader marks | the full link's `def_target` |
|---|---|---|
| `UNDEFINED` 0 | nothing | `Def::Undefined`: `None` (a definition in a dropped COMDAT copy is demoted to a reference, resolve.md §6.2; a withdrawn conditional symbol is `Undefined` by `Assignment::def`) |
| `SECTION` 1 | `RESOLVED.section`. If it has a `SPLIT` row, the piece at `RESOLVED.value`: a value of 2^32 − 1 or more is `state-corrupt`. Otherwise the whole section. | `Def::Defined` in a section: `Target::At(section, st_value)` |
| `ABSOLUTE` 2, `COMMON` 3, `SHARED` 5 | nothing | `None` |
| `INTERNAL` 4, name `__start_N` or `__stop_N`, N a C identifier, the name not a `--defsym` name (`OptionKeys.defsym`) | every section with a `NAMED` row whose `SECTIONS.name` is N, whole (`u32::MAX`) | `Provide { conditional: true }`, start/stop and C identifier: the `named` sections |
| `INTERNAL` 4, a `--defsym` name whose operand names a symbol | not reached: v1 falls back (F9, `briefs/u-10-notes.md`) | `Alias` / `Assign::Offset`: one step to the base |
| `INTERNAL` 4, any other name | nothing | `None` (a `--defsym` number; `_end`, `__bss_start` and the other linker-defined keys) |
| `COMDAT` 6, `LIVE` 7 | `state-corrupt` (these are not key rows) | — |

**Why the name test is exact.**
- In a static link, an `INTERNAL` key named `__start_N` comes only from the conditional start/stop rule, a `--defsym`, or a script assignment.
- Script assignments are refused (`spec/script.md` §2.10, shown by input in S6).
- `--defsym` names are excluded by the table above.

**F6's kept test.** The mark tests the kept bit of what it marks (`Marks::section`). `SECTIONS` has no kept bit, so the stored form guarantees by construction that every target the walk can reach is kept:
- **Section targets** are always in the source's own file: a local or section symbol, an LSDA of the same `.eh_frame` file (F3 refuses the other case), a link-order dependent, or a group mate. The producer drops a row to a section that is not kept. A file's kept set changes only through election, which draws the file in (IN-72 item 2a), so its rows are then fresh.
- **Key targets**:
  - A definition in a COMDAT copy that lost its election is demoted to `UNDEFINED` in `RESOLVED`, so the walk marks nothing for it (shown by input in S6).
  - A non-local symbol defined in a section dropped for any other reason (`SHF_EXCLUDE`, `.note.gnu.build-id`, `.gnu.lto_*`, consumed, stripped, `/DISCARD/`) gets a `REFUSE` row with code 2 on that section. The walk would find such a key's `RESOLVED` row naming a section the mark never marks, and the state cannot tell it from a kept, dead one.
  - The full link refuses a relocation to such a symbol (`relocation refers to a symbol in a discarded section`, S6), so only rooted keys and non-allocated references reach one.

### S3. The rooted keys (F1)

Rooted keys are taken from `OptionKeys`, not enumerated a second time. The list is `OptionKeys::live_roots()`: `roots()` (resolve's order) followed by `init` and `fini`.

| rooted key | where it comes from | in the update |
|---|---|---|
| entry | `OptionKeys.entry`: `-e`, else the last script `ENTRY`, else `_start` (`option_keys`, resolve tables.rs:670) | rooted |
| `-u` and `EXTERN` | `OptionKeys.undefined` | rooted |
| `--require-defined` | `OptionKeys.require_defined` | rooted |
| `--defsym` bases | `OptionKeys.defsym[].value.base()` | v1 falls back for any `--defsym` whose operand names a symbol (F9); a numeric `--defsym` roots nothing |
| `-init`, `-fini` | **new** `OptionKeys.init` / `fini`, filled from `plan.dynamic.init` / `fini` (only when given; the defaults `_init`/`_fini` are not roots, as in `Outcome::roots`) | rooted |
| `--gc-keep-exported` | **new** `OptionKeys.gc_keep_exported` | R-5: `update-not-implemented (live)` |

**The test (Part 2).** On a link that uses entry, `-u`, `EXTERN`, `--require-defined`, a `--defsym` base, `-init` and `-fini`, `live_roots()` mapped through `find_key` must equal `Outcome::roots`, element for element. The order is the same by construction: resolve appends `-init` and `-fini` after `opts.roots()`. The next root added to `resolve` then fails this test, not an update.

### S4. The live-set hash (F7, R-3)

**Where it lives.** `META.live_hash: [u8; 16]`, after `versioned`. `MetaRow::WIDTH` goes from 208 to 224. It is all zeros without `--gc-sections`.

**What is hashed.** For each file f with at least one live section, the encoding `enc_f` is:
- `u32` length and the bytes of the `FILES.path` string;
- `u32` length and the bytes of `FILES.member_name` (empty for none);
- `u32` `member_ordinal`;
- then, for each live kept section of f in ascending `sh_index` (= its `SECTIONS` row minus the file's first row):
  - `u32` `sh_index`, `u32` n, then n `u32` marked offsets in ascending order;
  - n = 0 for a section without a `SPLIT` row; `[u32::MAX]` when the whole section is marked; otherwise the distinct offsets the walk marked.

`H` is the wrapping 128-bit sum (little-endian) of `mortar_digest::L128` (`new`, `update`, `finish`) over the `enc_f`.

**Why this form.**
- Files are named by identity, not by row. The sum is order-free, so compaction (which renumbers `FILES` and `SECTIONS` and drops gone files, whose sections are not live) leaves `H` unchanged. Compaction copies it.
- No `SECTIONS` row or `SymbolId` enters the hash.

**Who writes it.**
- **The capture** computes it from the full mark: `Liveness`' live bits, plus the marked positions projected from the producer's rows. For a split section t, those positions are:
  - the offset of every row from a live source to t;
  - `RESOLVED.value` of every key read from a live source's row, or rooted, whose definition is in t;
  - `u32::MAX` if t is a root, or reached through `NAMED`, `GROUP` or `LINK_ORDER`.

  This does not walk the stored form. Its section part is the full mark itself, which is what the old walk is checked against.
- **Every update** writes the new walk's `H`.

**The check.**
- In `live`, before anything is written, the old walk's `H` is compared with `META.live_hash`.
- If they differ, the update falls back with **`state-corrupt`** (the existing class; detail `META.live_hash: the stored rows do not give the stored live set`), since the state is not trusted.
- In `incr-update` and in the tests, this fall-back is a failure.
- It does not catch F3, which is why S5 is needed.

### S5. F3's refusal

**What is detected.** An FDE (not a CIE) of a kept `.eh_frame` section has a relocation at byte 8 of its piece (the initial-location field; S-37, DWARF64 refused) whose symbol is non-local (`r_sym >= first_global`) and not `STT_SECTION`. `mortar_merge::eh` resolves such an FDE's code through the resolution, so its code section, and the source of its rows, can be in another file.

**Where it is detected.** In the producer (`stored_edges`), per kept `.eh_frame` section, over its relocations. That is at the capture, and in the join's fresh rows for changed and drawn-in files.

**How the state says it.** A `REFUSE` row with code 1 (`fde-global`), whose source is the `.eh_frame` section.

**What happens.**
- The full link still links (a plain link accepts the input), and the state is written.
- Every update that sees a `REFUSE` row, stored or fresh, falls back with **`update-not-implemented (live)`** (the existing class, `Unimplemented::Live`). The detail names the reason and the file: `fde-global: an FDE of <file> names its code through a non-local symbol`, or `def-dropped: <file> defines a non-local symbol in a section that is not kept`.
- In tests, the reviewer's `fdeglobal.sh` (S6) must be refused this way.

**Independent of `--gc-sections`.** The predicate reads only the `.eh_frame` section's relocations and the file's symbol table: no liveness, no resolution. It runs inside `stored_edges`, which only a gc link calls, but the same function can be called by the capture without gc for the `.eh_frame` question in `briefs/u-10-notes.md`.

## Step 2 Part 3: the update's walk (`live`)

### P3-0. What needs a ruling

1. **FINDING: the capture writes `META.live_hash` = 0 on every link.**
   `Session::state5_bytes` hashes the `MemoryState` of
   `capture::state5_rows`, whose `FILE_INDEX` ranges are not filled yet
   (the encoder fills them, `state5/write.rs`), so every file's body is
   empty and the sum is 0. Shown on bytes: the decoded `out.mortar-state`

   the state's `SECTIONS` rows are NOT the link's `SectionId`s (file-keyed

## Step 2 Part 3b: the written `META.live_hash`

### P3b-1. The cause (by experiment)

At the hash's call in `Session::state5_bytes` (a temporary probe, first
scenario `calls`, AArch64), `m.view().file_index(f)` answered
`ranges = [0; 8]` for EVERY file (0 of 2439 files with a `SECTIONS`
range; file 1 has 14 rows in `m.sections`), with `first_global` set,
while `MemoryState::from_format4(state)` on the same `state` gave file 1
`SECTIONS {first 0, count 14}`: `capture::state5_rows` returns
`compact::normalize(&m)`, which builds `FILE_INDEX` afresh with
`first_global` and `locals` only (`..FileIndexRow::default()`; the ranges
are the encoder's), so S4's sum saw no file with a section and was zero.
Part 3's "the encoder fills the ranges" is the encoder's side; the
defect is that the hash was taken over `normalize`'s range-less rows.

### P3b-2. The fix

`MemoryState::index_sections` (testing.rs, narrow: `index_rows`' rule
for the `SECTIONS` table, the shared `note_ranges`, other fields kept)
sets the ranges on the normalized rows before `live_hash`; the encoder
keeps each file's rows in their order (`by_file`) and S4's sum is by
file identity and position in the file, so the value over the in-memory
rows is the one over the written rows. Shown by
`the_written_live_hash_is_the_full_marks` (un-ignored): on all 4
scenarios x 2 targets the DECODED `META.live_hash` is non-zero and
equals the full mark's hash over the decoded rows (a link section =
its file's first `SECTIONS` row + `sh_index`, the reader's numbering,
`state5::read` `sections_of`). The encoder ignores the ranges of `m`
(it reads `gone`, `first_global`, `locals`): the bytes but META are
unchanged. Not touched: `normalize` (compact.rs, not mine); proposed
for its owner: `normalize` could fill the ranges itself, then
`index_sections` goes.

### P3b-3. The oracle judges the bytes (P3-1a)

`live_check(f, m)` now takes a DECODED state; the capture's hook calls
its body on `state5::read::open_bytes(<the encoded bytes>)` (the
update's own reader) after encoding, before the write; a DISAGREE still
fails the link and writes no state. Link sections are mapped to rows by
the reader's numbering (above), back-mapped for the pieces; a live row
of no link section, a live link section past its file's rows, and a
zero stored hash with a live section are differences. Hook
`testhook::live_hash_mutated` (`MORTAR_INCR_LIVE_HASH=zero|flip`): the
capture writes a wrong hash; `live_rows.rs`
`the_capture_oracle_judges_the_written_hash` (testhooks binary, both
targets) sees agree / `DISAGREE META.live_hash is zero` / `DISAGREE
META.live_hash: the stored rows ...` and no state. `live_rows.rs` reads
the written state (decoded) instead of the rows sink;
`a_state_without_the_live_hash_is_refused` uses a state linked without
`--gc-sections` (hash zero, no `EDGES`).
