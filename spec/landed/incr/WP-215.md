## Q. IN-71b against `spec/resolve.md` §4.1 as it reads on the base

### Q.1 Can an update follow an iteration in O(change)? No.

§4.1 step 3: `L_{i+1}` is the closure under `T_{i+1}` **from the roots and
every file live in `L_i`**; "an extracted member stays extracted". So the
final member set is not a closure under one target function: a member
extracted in iteration `i` through an edge to `first_i(K)` (a file whose
copy iteration `i`'s keepers then drop) stays live although no edge of
the final targets reaches it. IN-71b's support property (a round, an edge
from a smaller round) is stated over ONE edge set. To keep it over an
iterated link the state would need, per member, the iteration it entered
and the targets `T_i` of that iteration (per key, per iteration), and an
update would have to replay the iterations from the changed keys; a
change can move a member from one iteration to another, so there is no
recurrence over the delta. **The update does not iterate; it decides the
trigger and falls back by name.**

### Q.2 Deciding the trigger from the state, in O(change)

Claim. If the previous link ran ONE iteration, the update's link runs
one iteration unless a mention `(F, K)` feeds back with `K` an
**affected key** of IN-71 (after the extraction and the re-election).
Proof sketch: a feed-back `(F, K)` needs (i) `F` live, a relocatable
object, (ii) `F`'s mention of `K` defined in a section of a COMDAT copy
the keepers drop, (iii) `F = first(K)` or `cfirst(K)`. If `K` is not
affected, no file that mentions `K` changed, appeared, went, flipped or
was drawn in, so `KEY_REFS(K)` and therefore `first(K)`/`cfirst(K)` (over
members whether extracted or not) are the stored ones, and `F` is
unchanged and was live before. (i)-(iii) held before unless (ii) is new:
`F`'s copy was kept and is now dropped, so `F` was the keeper and stopped
being it: `F` is drawn in (IN-72 item 2a "kept ... or stops being so")
and its keys are affected. Contradiction. ∎

The check, per affected key `K`, once extraction and re-election are
done (the old link not iterated):
1. `F = first(K)` and `G = cfirst(K)` from `KEY_REFS(K)` and the changed
   files' rows (IN-71b's "Edges of a key"; members' rows, `LAZY` or not).
2. For each of `F`, `G` that is live after the extraction and a
   relocatable object (`FILES.kind`, `LAZY`): its mention of `K` is
   `def = SECTION` (`KEY_REFS`); its section is the mention's `SECTIONS`
   row; the section is in a COMDAT group iff `SECTIONS.anchor_kind` is 1
   (COMDAT; the capture takes it from the resolution's group,
   `capture.rs` `file_keys`), the signature its anchor; the copy is
   dropped iff the group's new keeper is not `F`.
   Cheap path: when `F` is the stored definer (`RESOLVED(K).section`'s
   file), unchanged, and its group was not re-elected, its section was
   kept and still is: one `RESOLVED` row and one `SECTIONS` row. Else
   `F`'s `MENTIONS` range is read once per `F` (a file-keyed range).
3. Any feed-back: `extraction-changed`, before anything is written.

**How often.** The model's series (`model_extract.py`,
`extract_amended.py`) has no COMDAT (its header says so), so it cannot
say. A feed-back needs a dropped copy defining a key that no lower file
defines: mismatched symbol sets of one group's copies (WP-200: "a link
with no mismatched copy runs one iteration"). Measured here: protoc
(`cxx-medium-static`, release build of the base, `MORTAR_STEPS=1`): one
`resolve.closure` step, i.e. one iteration, with 785 live files, 26,776
signatures and 56,185 group sections; WP-200 §8 found the same. The
large workload (`cxx-large-g`, output > 1 GB) was not run.

### Q.4 The rule text this changes

IN-71b gains, after "Edges of a key": "**Iterations** (resolve.md §4.1,
WP-200). An update never iterates the closure. A link whose closure ran
more than one iteration (`META.iterations`) is not updated: every update
of its state is `extraction-changed`. Otherwise, after the extraction and
the re-election, for every affected key `K` and each of `first(K)`,
`cfirst(K)` that is a live relocatable object whose mention of `K` is
defined in a section of a COMDAT copy the new keepers drop, the update
ends with `extraction-changed` (the full link would iterate). Only an
affected key can start an iteration (WP-215 §Q.2)." IN-18e: `META`'s
column, and D2-D7's rows as ruled. §7 `extraction-changed`'s "when":
"..., or the full link of the update's inputs would iterate §4.1's
closure, or the stored link did (IN-71b)".

### R.2 Named fall-backs `resolve` adds (all `update-not-implemented (resolve)` unless said)

- two live strong definitions (a clash, or `--allow-multiple-definition`,
  which the update does not see);
- TLS and non-TLS mentions of one key (the full link's error);
- a key that is undefined and referenced now, unless the stored row is
  undefined and was referenced as strongly (§8's candidacy is a name
  table the update does not have: the stored link answered it);
- a shared object's mention or a stored `SHARED` row (R.4 (c));
- an extracted member that is not a changed file (`debug_assert!`; the
  join's contract);
- a second `DrawIn` (`input-changed`, after a `debug_assert!`: R.4 (a));
- `symbol-kind-changed`: IFUNC or TLS flipped, absolute <-> section, or
  the `other` bits beyond visibility changed, while an unchanged live file
  mentions the key;
- `closure-iterated`: §Q.2.

### R.3 The model is checked against `mortar_resolve`

`feedback_check_is_sound_random` builds a `mortar_resolve::View` of each
model link and runs `mortar_resolve::resolve`: on every link (old and
new) the iteration agrees; on every non-iterating link the live files and
every key's definer and class (strong, weak, common, undefined weak or

rule on those shapes, not only my reading of resolve.md.

### R.4 Conditions of seam 3's review

(a) The second `DrawIn`: `debug_assert!(false, ...)` before the
`input-changed` fall-back (`Res::run`). Every test runs it (debug).

(b) `resolve_random_series` (above). `resolve` is never called a third
time (the join asserts `calls < RESOLVE_CALLS`).

(c) What a `DrawIn` names: an unchanged live relocatable object (an
object named on the line, or an archive member extracted before: yes,
the same; a member is drawn in by the same rule). Never a member the
update does not keep live, never file 0, never a shared object: a
shared object is never drawn in, because every key a shared object
mentions (stored or fresh) is `update-not-implemented (resolve)` before
any draw-in (`shared_definer_is_not_implemented`). Settled: a `SHARED`
row needs only the symbol's index (`value`), which `MENTIONS` gives by
position, so a drawn-in shared object is never needed for its values;
what is NOT settled is the dynamic stage (spec/dyn.md D-11's `bind`,
`--as-needed`, the needed list), which the update does not run.
Incremental mode is static-only today (`incremental.rs`), so no state
holds a shared object. **For U-10:** when dynamic outputs come under
incremental mode, a key whose definer is or becomes a shared object
needs the dynamic stage's rows; until then it is the fall-back.

Condition 2: a winning common NEVER needs a draw-in. Its row is
`(kind COMMON, size = max over the live common mentions, value = the
winner's alignment, typ/bind/other the winner's)`; `COMMONS` holds each
live file's (size, alignment) per key, and `MENTIONS` the winner's
typ/bind/other; a newly extracted member's common is a changed file's
fresh row. Nothing is drawn in for a common
(`common_first_referenced_by_changed_file` asserts it). IN-72 item 2a's
list names "the winning common's file": ruled: dropped (R.6 1).

Condition 3 (`-u foo@V`, D8): `OptionKey::name` is split as
`InputsView::key_of` splits it (`extract.rs` `split_version`): `foo@V`
is the key `(foo, V)`, `foo@@V` is `foo`. Static only, nothing defines
`(foo, V)`: it is an undefined key the root refers to, unaffected by an
edit of `foo`'s definer (updated). A shared object's `foo@V` (rows forced:
kind-2 file, `SHARED` row): an edit not naming the key updates; the
shared object's own change is `update-not-implemented (resolve)`.
`undefined_versioned_root` pins both.

### R.6 Rulings (wp-215-rulings-3, applied)

1. IN-72 item 2a: "never for a common" (the rows give a winning common's
   `RESOLVED` row whole; v1 places none, item 11). Written in item 2a
   and IN-71 "Values".
2. IN-71 "Values": "its keys are affected; no candidate or winner
   changes, so the second call asks for nothing". Written.
3. **Live keys** (IN-71b "Stored", new paragraph; IN-78's `canon`: dead
   keys removed). A key is live when a stored row gives it a mention by
   a live file or a `LAZY` definition (a `KEY_REFS` row), or an option
   names it; else dead. The argument that no reader of U-3 treats a
   dead key as live:
   - **affected**: a key is affected only when a changed, appeared, gone,
     drawn-in or (no longer) extracted file's old or new rows mention it
     (`KEY_REFS` / the changed files' keys); a dead key has no stored
     mention, so only a new mention makes it affected, and then it is
     live;
   - **undefined report** (the `update-not-implemented (resolve)` of a
     key undefined and referenced): decided only for an affected key,
     from live mentions;
   - **draw-in**: only a live definer, a keeper or an S-74 crossing of a
     live mention is drawn in;
   - **re-election**: `GROUPS` rows by signature, never a key's rows;
   - **extraction**: roots are `OptionKeys`; edges come from `KEY_REFS`
     rows (a dead key has none);
   - **refill_set**: a key's referrers are its non-tomb `KEY_REFS` rows.
   A dead key that gets a mention again is found by name (`find_key`
   over `NAMES`, which indexes `GONE` keys too) and its row reused.
   Test: `dead_key_is_inert_and_reused` (a key dead in the stored state;
   an edit elsewhere, an edit of the `LAZY` member, a live definition of
   it, and the same from a `GONE` row). The random series and every
   named test now compare **through the rule**: `same_as_full` drops the
   dead keys on both sides (`canon_live_keys` / `is_live_key` in
   `tests/support/resolve_model.rs`, named so that U-2's `canon`
   replaces them: it is not on this branch), checks that every key the
   update calls gone is dead and that a dead key it leaves is undefined;
   the tolerated-key lists are gone. The capture's filter is the next
   format package's.
4. `at`: IN-71's text; the capture changes (U-2, F-12). Nothing here.
5. **The alignment-0 common: settled (ruled).** The full link writes a
   common's `RESOLVED.value` as `max(1, st_value)`

6. Seam 4 cherry-picked (1c690a82, clean). `refill_set` reads the

7. U-8's two answers:
   - **Rank**: `ChangedFile.row.rank` is read by U-3 ONLY for an
     `Appeared` file (`extract::Ctx::facts`); the JOIN (U-10) sets it
     (IN-18e's midpoint) before the first `extract`. A newly extracted

     ignored). `ChangedFile::row`'s doc ("`rank` and `round` are U-2's

### R.7 Findings for U-2

- `at` (IN-71): the code reads "the first **live** mentioner by current
  rank" (IN-71's words). The capture (`capture.rs` `first_mentions`)
  writes the first mentioner among **all** inputs by `FileId`, LAZY
  members included. `at_is_first_live_mentioner` fails under the
  capture's reading (a LAZY member before the live file). One of the two
  must change; the update follows the rule text.
- A common winner that becomes an unchanged file: `RESOLVED.value` is
  its `COMMONS.align`; the capture writes `st_value` raw (0 stays 0)
  while `COMMONS.align` is `max(1)`: an alignment-0 common gives 1 in the
  update and 0 in a full link. U-2 should store the raw value or the
  rule say `max(1)`.
- A new local key's `SymbolRow.ordinal` is written 0 (the update has no
  local numbering); U-2 decides it when it writes `SYMBOLS`.
- The old local keys of a changed file are not listed as gone by
  `resolve` (they are the file's range; U-2 replaces it).

### R.8 Findings for U-10 (the join)

- The `extract` loop: call `extract` again with every newly extracted
  member read (`Change::Extracted`) until it adds none; then `resolve`.
- The `DrawIn` loop: at most two `resolve` calls; add every named file
  as `Change::DrawnIn` with fresh rows (new section ids past the last),
  call once more; a second `DrawIn` is `input-changed`.
- Ranks of appeared files: the midpoint rule (IN-18e) BEFORE `extract`;
  every "first", "least", "lowest" is by `(rank, FileId)`.
- `recompute` assumes `layout.placement.defined` is the update's whole
  `DEFINED` set, keyed by the `SYMBOLS` rows of the update's id space
  (new keys numbered past the stored count, as `ResolveDelta::new_keys`).
  Against seam 4 this is STILL an assumption: `place_of` gives section
  places only, and `LayoutDelta`'s doc lists the whole tables as chunks,
  segments, TLS template and entry, not `defined`. U-4 must give
  `defined` whole (or the doc say so); `recompute` reads only `defined`
  and `chunks`, never a place.
- Shared objects: R.4 (c).
- **Seam doc lines owed** (the supervisor's one commit; not edited here):
  - `ChangedFile::row`: the join sets an appeared file's `rank` by
    IN-18e's midpoint before the first `extract`; every other file keeps
    its stored rank (`round` is U-3's, `Extraction`).
  - `ChangedFile::mentions`: section ids are in the update's id space,
    `first_section + k`, `k` by position in `ChangedFile::sections` (not
