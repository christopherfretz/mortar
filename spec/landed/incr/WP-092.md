# WP-092: `mortar_plumb --equiv`, the independent equivalence check (M7)

Record of WP-092. It closes WP-091's two missing models (`tests/dead.rs`:
a PIE, Clang DWARF 5; all 7 survivors of WP-091's mutation run caught,
`plumb.md` §9.5), writes IN-2's items 1 to 6 as rules (`plumb.md` §6.9,
P-E1 to P-E6; item 7 is the harness's, IN-63) and implements them
(`crates/mortar_plumb/src/equiv.rs`, `cargo xtask plumb --equiv`). It
reads no linker crate; the pairs below are judged from files.

## 1. What WP-064 runs

```text
cargo xtask plumb --equiv <X.map> <F.map> <X> <F>
```

from the directory the maps' relative paths are relative to (the link's
directory). Exit 0: both sides verify and no P-E finding; 1: a finding
(each side's prefixed `X:`/`F:`, then the P-E ones, then one summary line
per side and for the pair); 2: a usage error (an argument missing or
extra, an option, an unreadable or non-ELF output, a map that is not a
mortar map, an `X` map that claims no coverage: §8). In a test, the
library call is

```rust
mortar_plumb::equiv::check(&x_out, &x_map, &f_out, &f_map, &inputs) // -> Equiv
```

with `inputs` the files both maps name (`Equiv::clean`, `Equiv::with(n)`
for the P-E findings of rule `P-E{n}`, `x`/`f` the side reports). `F` may
be a plain link (IN-8's pair) or `--incremental=full`; any map format is
accepted by the library for `F`.

`--equiv` costs about two verifier runs plus 2-3 s of comparison; nothing
in it is quadratic except greedy matching among items whose first
identities differ (few: the boundary labels of question 10). L10 can run
it on every pair of the link-test corpus (each well under 0.1 s); on
protoc-sized pairs a nightly lane, about 5 s and 1.9 GB each.

## 4. What it does not cover

- the program's behaviour (L10 runs it); diagnostics (item 7, IN-63);
- the meaning of a table word or linker symbol whose address has two
  identities (a unit's end and the next one's start);
- a record neither side's engine checks: refused, not judged (P-E4 1;
  the AArch64 glibc records of question 8 are judged since 092b, §6);
- `.eh_frame` CIEs' order (per-file CIEs); thunks' and patches' places
  (only the values through them); local symbols' order;
- the x86-64 `ET_DYN` side of `GOTPCRELX` and the TLS must-not-differ
  cases are covered by the form table's unit test only (§6: no honest
  mortar pair exists for them yet); the range-thunk and erratum-843419
  pairs are real mortar pairs since 092b, not tests;

## 5. Questions for the spec (ruled 2026-11-16; `plumb.md` §6.9 "Rulings")

`plumb.md` §6.9 "Questions for the spec", 1 to 10: `.symtab` locals as a

## 6. 092b

**What changed.**

- Question 8 closed: an AArch64 thread-local undefined weak in a static
  output is judged (`plumb.md` §4.7 T1w/T2w; `reloc.rs` `weak0_tls`).
  Measured on a static glibc `setlocale(LC_ALL, "")` program, at
  `setlocale.o`'s IE pairs (`_nl_current_LC_COLLATE`, `_NAME`, ...):

  | linker | AArch64 | x86-64 (`GOTTPOFF`) | i386 (`TLS_GOTIE`) |
  |---|---|---|---|
  | GNU ld 2.44 | IE kept, GOT entry `0 − tls.start + 16` | `mov $TpRel(0)` (−(tls.start + memsz)) | `mov $TpRel(0)` |
  | lld 22 | LE `movz/movk` 0 | `mov $0` | `mov $0` |
  | mold 2.37 | IE kept, GOT entry `0 − tls.start + 16` | `mov $TpRel(0)` | IE kept (GOT) |
  | mortar | IE kept, GOT entry 0 (plain and `--incremental=full`) | `mov $0` | `mov $0` |

  mortar agrees with lld (a64.md §7: `T = A`; x64.md X-18, x86.md
  X86-23); GNU ld and mold agree with each other. No ABI text fixes the
  value. The plain verifier now reports, for mortar's AArch64 output, 0
  records not checked (was 20 `tls`); for GNU ld's, lld's and mold's on
  all three targets, 0 `tls` (the x86 records were judged already).
  mortar keeps IE where a64.md §7 says R3 relaxes it to LE `T = 0`; both
  forms compute `TP + 0` and are accepted (a remark for the linker's
  owner, not a mislink).
- `--equiv` traces a GOT group's member by the outcome its group gives
  (`got-unpaired` was traced as a plain record), and passes over the
  local symbols of a thunk or patch chunk (P-E3), which a real W6 pair
  showed.
- `incr.md` IN-62 and IN-2 item 4 name the command and the `GOTPCRELX`
  ruling; `plumb.md` §6.9 records the rulings (question 11 is the name).

Not made, and why (each covered by the unit table
`p_e4_forms_that_may_differ` only):

- a W6 pair with the thunk in `F` and not in `X`: `X`'s slack only
  lengthens distances, so a full link never needs a thunk the
  incremental-mode link of the same inputs does not;
- x86-64 `ET_DYN` `GOTPCRELX` by distance: mortar's incremental mode is
  static only (`-pie --no-dynamic-linker` with `--incremental` warns and
  links without a state; `-shared` is refused), so no `ET_DYN` pair
  exists before incremental PIE;
- the TLS must-not-differ case: a TLS relaxation depends on the symbol
  and the output kind only, which two links of the same inputs share; a
  pair that differs would be a forged `X`, which is what the unit table
  is.
