Every other kind is an error only (relocation kinds, `refused`,
`internal-error`, the rest): `—`. `meta-version` is an error (only
`--odr=strict` reads containers). No code's text depends on the layout
today, so none takes `output section`.

**How the table tells a warning from an error: it does not** (F-1).
`warning_kinds_have_subjects` therefore holds the list
(`WARNING_KINDS`, 36 kinds) and checks: each is a kind; each has
subjects, all from the set, none twice; a row with `—` is not in the
list; a row with subjects is in it. Mutated by hand: `executable-stack`
set to `—` fails ("can be a warning: it needs subjects"), set to `file,
section` fails ("'section' is not a subject").

## 4. Findings

- **F-1 (diag.md §3.1, R.7).** "every warning code ... gains subjects":
  the table has no severity (severity is not part of a kind, §2.2; §3.2
  says it in prose, kind by kind). A new warning kind with `—` passes
  the test unless `WARNING_KINDS` is edited. Proposed: a `severity`
  column, `error`, `warning`, or `error; warning under <option>`, which
  `spec_tables` compares with `WARNING_KINDS` (or, once U-9 lands, with
  `mortar_diag::subject::subjects`). Not added (no word for it).
- **F-2 (R.12, file names).** "Names follow IN-78's `canon` (a file by
  rank position)": a map's file ids are its own (live files only,
  `FileId` 0 without a record), so a map id is not a rank position.
  Applied: `<file>` is the map id (§3.2's token rule), H-1 maps it to
  the rank through the `file` record's identity and `C(U)`; the internal
  file is `-` in `symblock`.
- **F-3 (R.12, slots).** `slot <kind> <key> <addr>` has no form for a
  slot keyed by a local (IN-28b) or for the keyless module slot.
  Applied: `slot <kind> <file> <index> <addr>` and `slot tls-ld <addr>`
  (told apart by the field count).
- **F-4 (R.12, redirects).** `redirect <from> <to>` written as `redirect
  <file> <section> <offset> <addr>` (the site; the patch by its
  `chunk` record's address).
- **F-5 (R.12, fragments).** `FRAGS` has an ordinal column (IN-18a3's
  table) that `frag <out> <class> <hash> <offset>` cannot carry:
  several records of one identity are its fragments in `FragId` order.
  `<class>` is `<flags>,<entsize>,<align>` (hex), `<hash>` 32 hex digits.
- **F-6 (R.12, place).** "after the allocation records": `copy` is an
  allocation record in the dynamic group, so the records go after
  `incremental`/`hole`/`dead` and before the dynamic records.
  `capacity`'s `<ordinal>` is the creation (`ChunkId`) order within the
  output section and `order` lists them in file order; `<part>` is
  `b<k>`/`p<k>`/`m`/`s`; a non-allocated chunk's `<addr>` is `-`. Record
  names checked: none collides with mortar's format (`file`, `place`,
  `piece`, `nplace`, `merged`, `discard`, `fold`, `chunk`, `common`,
  `define`, `incremental`, `hole`, `dead`, the dynamic and `-r`
  records), and the foreign formats (§3.4-§3.6) are tables read only
  under their own headers.
- **F-7 (IN-72 item 11 vs plumb.md §3.2; no block).** IN-72 item 11
  says "the map's `common` line names the file" and WP-211 §C gives U-6
  "the `common` line's file", but `common <name> <addr> <size> <align>`
  has no file field and no block changes it; a verifier following
  §3.2 refuses a fifth field (`MapError`). Proposed: `common <name>
  <addr> <size> <align> [<file>]`, `<file>` (an earlier `file` record)
  written in an incremental-mode map only, and P-E2 compares it.
  **Needs a ruling** (it binds U-6 and V-1).
- **F-8 (R.8 vs IN-77e).** The block's I-66 covers the in-place path
  only; IN-77e also says "Before C2 (copy): `T` is removed; `P` and `S`
  are left; from C2 on, by copy, `P` is the old or the new file and is
  kept". incr.md's reading applied.
- **F-9 (R.9 vs resolve.md §2).** §2 defines a lazy file as "not live
  yet ... an archive member, or an object in a `--start-lib` region
  (M4)". The §4.1 sentence (a member whether or not extracted) is
  applied as the update's reading; a full link is unaffected (§4.1 says
  "live or lazy"). `--start-lib` objects are lazy files but not
  members: IN-71b does not say what an update does with them (M4;
  conservative: a full link).
- **F-10 (R.4, sizes).** S-108's table gave `.symtab` = `entsize × (1 +
  locals + globals)` and `.strtab` without slack: amended for
  incremental mode (fillers, tail reserve, region slack).
- **F-11 (layout.md L-145; no block).** L-145 ("Step 4 reruns stage D
  ... the fixed point starts from the previous patches") predates
  §9's text C (step 4 is now a full link, `reserve-exhausted`) and
  IN-72 item 9 (islands keep the first link's capacity, nothing moves
  after U7). Proposed: replace L-145 by "An update's delta layout is
  `spec/incr.md` IN-72; its islands keep the capacity the first link
  gave them (IN-72 item 9)".
- **F-12 (IN-75a, WP-211 §C `DiagRow`).** `DiagRow`'s key subjects are
  "`SYMBOLS` rows", but the one-definition rule's kinds are about ODR
  keys (types, not symbols; `ODR_CLASSES`' key). Proposed: a key subject
  is a `SYMBOLS` row or an ODR key (U-8/U-9).
- **F-13 (IN-75a, `link`).** "an output section or the link (these are
  recomputed from the update's `Placement` every time)": the warnings
  given `link` here are the front's (search, options, scripts), which
  the `Placement` does not give. Proposed: "... recomputed every time:
  from the update's `Placement`, or by the update's own front (U1-U4)
  for a warning the front raises".
- **F-14 (R.6).** The `incr-update` lane does not exist yet: the section
  says so and `ci`'s step table does not list it until H-1 adds it.
- **F-15 (R.6 vs today's tests).** "other outputs of mortar need none":
  the link tests hold one `check elflint` (a dynamic test, allows for
  lld and mold only), so nothing measured contradicts it; the four
  patterns are T-1's measurement, not re-run here.

No disagreement between a block and `spec/incr.md` other than F-8 and
the WP-211 amendment R.5b's L-88 predates (applied as WP-211 says).

`static-identical` line is the proof that no output byte moved). Not
verified: the decision records' forms against a writer (U-6 has not
