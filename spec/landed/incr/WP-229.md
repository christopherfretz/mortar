# WP-229 (G-2): split DWARF in incremental mode

IN-55 option (A): an incremental-mode output leaves the GNU name index
(`.debug_gnu_pubnames`, `.debug_gnu_pubtypes`) out. IN-55a: the unit kinds
of a changed file are detected for an update. Brief `briefs/wp-229.md`;
rulings `briefs/wp-229-rulings.md`. Scripts are in
`tests/incr-design/wp229/`. The scratch was `.build/target-wp-157/wp229`.
Workloads are AArch64 unless a row says x86-64.

Tools: GCC 14.2.0 (`g++`, `x86_64-linux-gnu-g++`), Clang 19.1.7 and
22.1.8, kiln++ (`target-kiln-next`), gdb 16.3 (and `gdb-multiarch` 16.3
for x86-64), lldb 19.1.7, llvm-dwarfdump 22, llvm-dwp 22, qemu-x86_64
10.0.13.

## 0. What needs a ruling

1. **Skeletons handled (IN-55a narrowed).** Accept §11's spec text 1-5.
   Ruling 8's experiment passed (§4): 108 transcript comparisons SAME,
   verify 0, with one exception that was not run (GCC DWARF 5 after dwp;
   see 4. below).
2. **The verifier row.** M10 needs a row for the GNU sets of an
   incremental-session link (§6). This is the supervisor's package. Until
   it lands, `split/incr-gnu-index.test` stays `xfail(mortar)` (L3, both
   targets: 6 PASS, 2 XFAIL; with `--no-plumb`, 8 PASS). Ruling 6 says G-2
   is not merged before then.
3. **`DEBUG_EXPORTS`.** Adopt the stored bit of §9, or leave the
   argument? No compiler output, `ld -r` product or protoc object (526
   objects) can make a `classify_rows` miss wrong. Only hand-written
   assembly can.
4. **GCC DWARF 5 after dwp is not verified.** llvm-dwp 19 and 22 do not
   finish on GCC 14's DWARF 5 `.dwo` (alone, with no linker involved), and
   there is no binutils `dwp` here. Accept as not verified, or name a dwp?
5. **The DWARF 4 address base.** Keep `DW_AT_GNU_addr_base` in the block
   (one rule for both versions, §11 item 2), although dropping it measured
   harmless.
6. **A seam accessor for the join.** U2 needs a file's stored `SECTIONS`
   rows. `view.sections_of(file)` in §8 is a placeholder, and the seam
   (`update/view.rs`) is not mine. Its name and shape are for the seam's
   owner (G-3).

## 2. Option (A) as built

**What goes and what stays.** Only the two GNU sets go. The other name
indexes (`.debug_pubnames`, `.debug_pubtypes`, `.debug_names`) stay in the
output and still make a changed file fall back (`debug-name-index`,
IN-55). `.gdb_index` is built from the GNU sets (S-G6), but `--gdb-index`
is already refused in incremental mode (IN-58, `incremental.rs`). So an
incremental-mode link never has both, and nothing else reads the sets.

**The map.** Each dropped set is one I-78 line
`discard <file> <section> unspecified`, the same line `-S` gives.

**Diagnostics.** None is added. None counts the dropped sections (below).

**Lane test** `tests/link/split/incr-gnu-index.test`, AArch64 and x86-64,
GCC 14, mortar and the three reference linkers. It gives 8 PASS without
L3 (`--no-plumb`). With L3, mortar FAILS on M10 (§6), as expected until the
verifier rule lands. What it checks:

- `--incremental=full`, DWARF 5 and DWARF 4 `-gsplit-dwarf`: no
  `.debug_gnu_pub*` in the output, `.debug_addr` kept, the skeletons still
  name their `.dwo`, `llvm-dwarfdump --verify` clean, the program runs,
  the map has the `discard * unspecified` line. A plain link keeps both
  sets.
- **The named test (ruling 1).** `-Wl,--sort-common -Wl,--incremental`
  warns `--incremental is not supported with --sort-common; linking
  without a state`, keeps `.debug_gnu_pubnames`, and `check cmp` says
  `identical` with the link without `--incremental`.
- **The edge cases (ruling 4)**, from a hand-written `x.S`:

  | case | incremental-mode result | why |
  |---|---|---|
  | GROUP: the set is a member of COMDAT group `xgrp` with an allocated member `.text.xg` | The set alone is dropped (map: `discard * unspecified`). The group's other member and `xg` are kept, and the program runs. | The group's keeper is decided in resolve (§6.1) before `discard` runs. `discard` changes one row's state and does not touch the group. Nothing counts a group's members after resolve, so a dropped member does not unbalance it. `-S` does the same today. |
  | ALLOC: a section named `.debug_gnu_pubnames` with `SHF_ALLOC` | Kept. | It is not debug information (`discard` tests `SHF_ALLOC == 0`, the way `-S` does). |
  | RELOC: `.data` relocated against the set | The link fails: `relocation refers to a symbol in a discarded section: .debug_gnu_pubnames` (`discarded-section-reference`). `-S` fails the same way. The plain link links. | The full link's rule for a relocation in a live section that is not debug, against a symbol of a section not in the output: the scan's event `DiscardedSection` (`spec/arch.md` §3.4), reported as `discarded-section-reference`, "relocation refers to a symbol in a discarded section: {name}" (`spec/diag.md`; `spec/image.md` I-46: "Any other non-alloc section: the scan reported `discarded-section-reference` (§4.4) and fill never runs"). A COMDAT copy's or `-S`'s drop gives the same refusal. |
  | DINFO: `.debug_info` relocated against the set (a `DW_FORM_sec_offset` attribute) | It links. The attribute is the tombstone `0xffffffff`. | `spec/image.md` I-45: "Referring section with a GNU ld debug name [...]: the tombstone of I-47, whatever the addend"; I-47: all ones in `.debug_info` on ELFCLASS64. |

  No compiler writes RELOC or DINFO. Over the 190 objects of §3 and two
  `ld -r` products, no relocation in any section targets a GNU set (xref.py).

**Readers of `Dropped(Stripped)` (ruling 2).** Each reader, and what it does
with a set left out:

| reader | what it does | behaviour beyond the map line and the absence |
|---|---|---|
| `mortar_image/src/link.rs:2517` (the map) | `Excluded \| Stripped` give `discard ... unspecified` | none: this is the map line |
| `mortar_resolve/src/sections.rs:283` `reloc_fate` | `Comdat \| Stripped`: native form Applies, other form Nothing | none: `reloc_fate` is computed in resolve, BEFORE `discard` runs, so the sets' referrers keep the fate they had as Kept. A plain-link refusal stays a refusal. |
| `mortar_resolve/src/sections.rs:318`, `resolve.rs:939/943` | the writers under `-S` | not reached: these write the state, they do not read it |
| `mortar_core/src/place.rs:41` `NoPlace::describe` | "a stripped section", in a diagnostic naming a target with no place | the RELOC row's error names the section, not "-S". No text says that -S was given. |
| `mortar_layout/src/relocatable.rs:125` (`-r`'s `.eh_frame` removal) | `Comdat \| Stripped` FDEs removed | not reached: `-r` is never incremental (IN-12) |
| generic `Dropped(_)` / `is_kept` readers (assignment, image, layout) | not placed, no bytes | the absence |
| the capture (`capture.rs`) | stores the placement only: `place_chunk` NONE for an unplaced section | none. A dropped section round-trips as "no place", the same as for every other `Dropped` reason. |

No diagnostic counts `Stripped` sections (`grep` of every crate outside
`mortar_plumb`). Nothing concludes that `-S` was given from this state.
Only the verifier says so, by rule M10 (§6). The plain `static-identical`
rows are `0 differ` (§7).

answer:

- It is in no DWARF 4 object that is not split (it IS in Clang's and

- One DWARF 4 split object has no `.debug_addr`: g++ on a unit with no

- So `dwarf4_split` (a DWARF 2-4 unit and a non-empty `.debug_addr`) is
  exactly "the neutral unit must keep `DW_AT_GNU_addr_base`".

## 4. Experiments that could refute (A), and ruling 8's skeleton experiment

`skel.sh WORK MORTAR a64|x64` covers g++ 14 and clang++ 22, each with
DWARF 4 and DWARF 5, `-O0 -g -gsplit-dwarf -ffunction-sections
-fdata-sections`, static, `--gc-sections`. On x86-64 the program runs
under `qemu-x86_64 -g PORT`, and `gdb-multiarch` (`target remote`) and
lldb (`gdb-remote`) attach to it.

Two units are linked. `m.cc` holds `main`. `u.cc` holds `u_f`, the
class `UOnly` (defined only in `u.cc`) and a static `uo`. Version 2 of
`u.cc` adds a line and the member `int z` to `UOnly`. Four outputs per
configuration:

| output | inputs | what it stands for |
|---|---|---|
| plain | m.o u.o (v2), no `--incremental` | the GNU index kept |
| full | m.o u.o (v2), `--incremental=full` | the index left out (option (A)) |
| emul | m.o dead.o u.o (v2), `--incremental=full`, then `neutral.py` | an update's picture of the edit v1 -> v2 (ruling 8 (a)). `dead.o` is v1's `u.o` with its symbols renamed, so `--gc-sections` collects its code. `neutral.py` makes v1's skeleton contributions dead in place: the unit becomes IN-51's block form (DWARF 5: `DW_UT_skeleton` becomes `DW_UT_compile`, and the 8-byte dwo_id goes into the block); its abbreviation table becomes the block abbreviation plus zeros; `DW_AT_addr_base` (DWARF 5, 0x73) or `DW_AT_GNU_addr_base` (DWARF 4, 0x2133) is kept, aimed at the dead `.debug_addr` table; `.debug_aranges` is rewritten without the dead set (IN-54). The other dead contributions (`.debug_line`, `.debug_addr`, `.debug_rnglists` / `.debug_ranges`, `.debug_str_offsets`, strings) are left as the compiler wrote them and tombstoned by the link (IN-53). v2's contributions come last, at the section tails. |
| emuldrop | the same, with the address base dropped | a dead `.debug_addr` table nobody names (ruling 8's question) |

Each output gets a gdb session and an lldb session:

- gdb: `break u_f`, `break u.cc:7` (the edited file), `run`, `bt`,
  `info source`, `list u_f`, `ptype UOnly` (a class defined in the edited
  file's `.dwo`), `ptype Pt`, `print uo`, `continue`, `info locals`,
  `info functions u_f`, `info functions ^hin`, `info scope u_f`;
- lldb: the same questions (`breakpoint set -n` / `-f -l`, `bt`,
  `frame variable`, `image lookup -t`, `image lookup -r -n ^hin`,
  `source list`, `target variable`).

Addresses, pids, ports and the output's name are masked, and so are the
uninitialized locals at the first stop. The sessions are compared with
the `.dwo` files present, and again after `llvm-dwp-22 -e <output>`
packs them with the `.dwo` files moved away.

**Item 4's (A) question.** Leaving the GNU index out changes no answer of
gdb or lldb, on either target, for either compiler, DWARF 4 or 5, with the

reads the skeletons instead.

**llvm-dwp and GCC 14 DWARF 5.** `llvm-dwp-22` (and `llvm-dwp-19`) do not

killed after 6 min 28 s of CPU; the others stop at `timeout 60` or 20. This happens with `m.dwo` alone, with no linker
involved, and with the GNU ld output (`-e`). `u.dwo` alone packs in under
a second. No binutils `dwp` is installed (gold's `dwp` is not in the
container). So "dwp still works" is verified for g++ DWARF 4 and for
clang++ 22 DWARF 4 and 5, and is **not verified** for g++ DWARF 5. The
two `dwp` rows of g++ DWARF 5 compare sessions without debug information
(SAME, but empty of meaning).


## 5. gdb start-up without the index (protoc)

`protoc.sh WORK MORTAR gcc|clang` builds protoc 3.21.12 (the bench's
source) static with `-O0 -g -gsplit-dwarf` (DWARF 5, the compilers'
default), using GCC 14 or Clang 19. mortar then relinks it from cmake's
own link line, twice: plain (index kept) and `--incremental=full` (index
left out). A third copy, `gdb-add-index` on the incremental one, carries
a `.gdb_index` for reference. 168 objects are compiled, and 125 skeleton
units reach the output (the archive members that are linked).

gdb 16.3 and lldb 19.1.7 run on AArch64, `-readnow` off, `-batch -nx`.
gdb start-up is timed as `break main` + `info line main`. "cold" is the
first run right after the link: the page cache is not dropped (that
would be a global change), so cold means gdb's own caches only. "warm" is
7 interleaved runs, given as median (min-max). The GCC series was run
again at load 5 and the Clang series ran its last 3 rounds at load 6.6.
The numbers below are from those quiet runs; the first GCC series, at
load 11, is in `protoc-gcc-load11.log`, with the same ordering and about
1.3x the times.

| | size (bytes) | GNU index bytes | gdb cold (s) | gdb warm (s) | gdb `info functions DebugString$` (s) | lldb `breakpoint set -n main` (s) |
|---|---|---|---|---|---|---|
| GCC plain | 32,332,576 | 16,481,027 | 0.182 | 0.202 (0.193-0.225) | 0.544 (0.525-0.558) | 0.227 (0.221-0.233) |
| GCC incremental (no index) | **18,303,824** | 0 | 0.202 | **0.202 (0.183-0.203)** | 0.537 (0.527-0.556) | 0.229 (0.225-0.245) |
| GCC incremental + `.gdb_index` | 24,841,144 | 0 | | 0.138 (0.126-0.141) | | |
| Clang plain, load 6.6 | 26,801,704 | 11,923,281 | 0.287 (load 11.7) | 0.128 (0.126-0.132) | 0.325 (0.321-0.326) | 0.163 (0.162-0.166) |
| Clang incremental, load 6.6 | **17,412,216** | 0 | 0.259 (load 11.7) | **0.127 (0.120-0.127)** | 0.318 (0.317-0.337) | 0.165 (0.161-0.167) |
| Clang incremental + `.gdb_index`, load 6.6 | 23,773,136 | 0 | | 0.110 (0.109-0.111) | | |

**Verdict.** On protoc, gdb 16.3 starts up as fast without the GNU index
as with it: 0.202 vs 0.202 s (GCC), 0.127 vs 0.128 s (Clang). Within
noise, gdb does not use the sets at start-up. A `.gdb_index` saves 0.06 s
(GCC) or 0.02 s (Clang). The incremental-mode output is **14.0 MB
(GCC) and 9.4 MB (Clang) smaller** than the plain one, because the index
is 51% and 44% of the plain output, more than the incremental slack
adds. That much less is written per full link.

The gdb transcripts (`break main`, `run --version`, `bt`, `info source`,
`ptype google::protobuf::FieldDescriptor::Type`, a type of another unit
than `main`'s, `info functions ^google::protobuf::DescriptorPool::generated_pool`,
`info line google::protobuf::FileDescriptor::DebugString`) are SAME,
plain vs incremental, for both compilers (20 lines each).

**Per 1,000 units** (an extrapolation, not a measurement). protoc is the
largest build here, with 125 skeletons. Assume gdb's start-up is linear
in the skeletons, the worst case, since gdb 16 indexes them in
parallel. Then without the index: 0.202 s / 125 = 1.6 ms per unit, so
about **1.6 s per 1,000 units** (GCC) and 1.0 s (Clang). With the index
the plain output gives the same figures, so the difference that
option (A) makes is ~0 per 1,000 units. That is the number IN-55's (B)
clause asks for ("neutralized sets only if that start-up is measured
too slow"). A `.gdb_index` would save about 0.5 s per 1,000 units (GCC).
A build of 10,000+ units was not run (§12).

## 8. What G-1 and G-3 need (rulings 5, 11)

**The full link and the capture.** Nothing to call. `discard` runs in the
full link (the front, keyed off the session), and the capture reads the
resolution's states as it does for every `Dropped` section
(`place_chunk` NONE). IN-78 holds as long as the update writes the same
rows.

**The join (G-3 / U-10).** The calls and their order. Any `Err` ends the
update before its first write.

1. **U2**, for each changed file, in `FileId` order:
   `split::classify_rows(&view, &changed, old_rows)?` on the stored
   `SECTIONS` rows of the OLD version. Then, for each changed, appeared,
   drawn-in or newly extracted file,
   `split::classify_object(&object)?` on the NEW bytes. The same applies
   to gone and no-longer-extracted files (`classify_rows`) and to
   appeared and newly extracted files (`classify_object`). Name index
   before unit kind (ruling 7); the function returns the first reason.
2. **U4**, the new version's sections: before IN-72 places them, give
   every new section row that is kept, of kind `Debug` or `Merge`,
   non-allocated, and with `incr_discard::left_out(name)` true the state
   `Dropped(Stripped)`. This is the same test as `discard`, and it is the
   only test (IN-78: the state the update writes must equal the capture of
   a full link of the new inputs). A changed file's old GNU sets were
   never placed, so there is nothing to neutralize for them.
3. Hand `Handled` (`compile_units`, `skeletons`, `dwarf4_split`) to G-1:
   a DWARF 5 skeleton is neutralized as a compile unit (§4); a
   `dwarf4_split` unit or a DWARF 5 one with `DW_AT_addr_base` keeps its
   address base (§4).

The exact lines (G-3 writes them; `mortar_incr` cannot name
`mortar_layout`, so the join passes the test in or repeats the two names
as `split.rs` does):

```rust
// U2
let _old = split::classify_rows(&view, &changed, view.sections_of(file))?;
let new = split::classify_object(&object)?;
// U4
for (row, h) in new_rows.iter_mut().zip(new_headers) {
    if row.state == SectionState::Kept
        && matches!(row.kind, SectionKind::Debug | SectionKind::Merge)
        && h.flags & SHF_ALLOC == 0
        && left_out(h.name)
    {
        row.state = SectionState::Dropped(DropReason::Stripped);
    }
}
```

(`view.sections_of` stands for however the seam names a file's
`SECTIONS` range. I did not add it.)

## 9. What `classify_rows` cannot see (ruling 9)

Without the old bytes, `classify_rows` sees names, flags, types, sizes and
COMDAT anchors. It does not see unit headers. So it misses, in the OLD
version:

- a `DW_UT_partial` (or any non-compile, non-skeleton) unit in a
  `.debug_info` that is not in a COMDAT group;
- a DWARF 5 type unit (`DW_UT_type`) in a `.debug_info` that is not in a
  COMDAT group. GCC and Clang always put them in groups (§3), and so does
  `ld -r` on them (it keeps the groups);
- an unreadable header.

The new version is always read by `classify_object`. So a miss needs the
old version to have such a unit and the new version not to have it.

**Can a miss produce a WRONG output?** The old version's contribution is
dead in either case. G-1 neutralizes each dead unit in block form (IN-51)
whatever its type: a partial or type unit becomes a block-form compile
unit, which is just as dead. Neutralizing is wrong only if a unit that
stays live refers INTO the dead one:

- a `DW_TAG_imported_unit` to a partial unit, `DW_FORM_ref_addr` or
  `DW_FORM_ref_sig8` to a type unit, or a `.debug_str_offsets` /
  `.debug_addr` base in another file.

Within one file the old version's referrers die with it. Across files, a
relocation in file B can name file A's debug section only through a
GLOBAL or WEAK symbol that A defines in that section, since an object's
relocations name its own symbols. `DW_FORM_ref_sig8` is not relocated, but
it names a type by signature, and an unchanged referrer of a signature
found in another file's type unit is the same question.

Measured (`xref.py`):

| object set | objects | symbols defined in debug sections | GLOBAL/WEAK among them | debug relocations naming an undefined symbol |
|---|---|---|---|---|
| §3's objects, both targets, all compilers and configurations | 188 | 1,888 (all LOCAL) | 0 | 0 |
| `ld -r` products (g++ DWARF 5 split, clang DWARF 4 split) | 2 | LOCAL only | 0 | 0 |
| protoc `-g -gsplit-dwarf` objects, GCC 14 | 168 | 1,657 (all LOCAL) | 0 | 0 |
| protoc `-g -gsplit-dwarf` objects, Clang 19 | 168 | 2,974 (all LOCAL) | 0 | 0 |

**Verdict.** No compiler output, and no `ld -r` product of one, can make a
miss wrong. A miss can still be wrong for objects that DO define a
global symbol in a debug section (hand-written assembly; a tool like dwz
does not run on objects). Type units by signature (`ref_sig8`) fall back
in v1 anyway (§10). If the supervisor wants that case closed rather than
argued, the proposal (NOT made) is a stored bit:

- **What.** `FILES.flags` (`format.rs` `file_flags`, byte 2 of the row;
  only `POSITIONAL` = 1 is used) bit 2 `DEBUG_EXPORTS`, written by the capture per
  file: set when the file defines a GLOBAL or WEAK symbol in a
  non-allocated `.debug_*` section, or has a relocation in such a section
  whose symbol is undefined in the file.
- **Who reads it.** The join at U2: a changed or gone file with the bit
  set, or any file with the bit set whose referenced symbol is defined by
  a changed file, falls back `debug-unit-kind (cross-file debug
  reference)`.
- **Cost.** 0 bytes: a free bit of an existing column. The capture already walks every
  file's symbols and every relocation section. I did NOT measure the
  added time on protoc `-g`, which would need a `capture.rs` edit (not
  mine). On protoc `-g` the bit is 0 for every file (the table above).

## 10. Falls back in v1 (ruling 10)

| case | reason it gives | what lifting it needs |
|---|---|---|
| `-gsplit-dwarf=single` (Clang; the `.dwo` sections inside the object) | `debug-unit-kind (<name>.dwo)` | The `.dwo` sections are not linked (they are `SHF_EXCLUDE`), but the skeleton's `DW_AT_dwo_name` names the object itself. An edit must keep the object's `.dwo` sections readable at their old offsets for gdb. Lifting it needs a transcript experiment like §4 with the object as the `.dwo`. |
