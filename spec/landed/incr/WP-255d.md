### Who allocates ids today (a CHANGED file)

- **Sections**: the join (U-10) gives each `ChangedFile` its
  `first_section`, "past the state's `SECTIONS` count, in
  `ChangedFiles::files` order" (`view.rs:413-416`); `refill.rs:63`,
  `resolve.rs:310`, `odr.rs:339` read it.
- **Keys**: a changed file names keys by position in `ChangedFile::keys`
  (`KeyName`); U-3 (`mortar_incr::update::resolve`) maps each by
  `find_key` or allocates a new row `cx.symbols + i` (`resolve.rs:1106`
  `new_keys`).
- `front_of` therefore allocates nothing: for a changed file it yields
  sections relative to a `first_section` the caller passes (the join's)
  and keys as `KeyName`s with `find_key`'s answer where there is one. No
  second allocator.

## M2. `front_of`

In `crates/mortar/src/update/file_front.rs` (see the file's docs):
`front_of(&mut FrontCache, &StateView, FileId, Ids) -> Result<&FileFront,
IncrReason>`. The cache holds the store, pool and cwd (the brief's
`store`), so the signature differs from the brief's
`front_of(view, stored, file, store, ids)`: no `StoredLayout` is read (the
place comes from `SECTIONS`).

Findings while building it:

- The section ids are `FILE_INDEX.ranges[Sections].first + k` in the
  on-disk state (`state5::read`), but the normalized `MemoryState`
  (the rows sink, `compact::normalize`) leaves `FILE_INDEX` ranges at 0:
  a `StateView` over a `MemoryState` cannot give a file's section ids.
  The test therefore reads the written state (`state5::read::open_bytes`).
- A file whose state holds no `SECTIONS` rows (members not extracted)
  gets no section ids: its keys are read, its sections are not. On
  x86-64 one libstdc++ member (`FileId` 8 of the test link) has no
  `SECTIONS` rows; whether its `FILES.flags` has `LAZY` was not checked
  (the first version keyed the rule on `LAZY` and failed there). The
  whole front's `file_rows` also gave it no sections.
- §6.5's `SHF_LINK_ORDER` inheritance (a section outside the groups whose
  linked section is dropped takes that group) depends on the keeper
  (whole-program). For an unchanged file `front_of` takes it from the
  stored row's anchor; a changed file's case is not handled (no such
  section in the test links).
- COMDAT anchors apply only to a live file (resolve fills
  `SectionRow::comdat` for live objects alone): `front_of` keys this on
  `FILES.flags & LAZY == 0`.
- The relocation table is given for PLACED sections only (the image reads
  no other); the first `SHT_RELA`/`SHT_REL` naming a target wins, without
  resolve's `reloc_fate` (an `Excluded`/dropped target has no place).

## M3. The test

`crates/mortar/tests/file_front.rs`: the C++ program of `support` (static
libstdc++/libc) plus `lib2.a` (two members, both extracted by `-u`), on
AArch64 and x86-64: every object file of the link (3371 and 4119 files,
3364/4112 members of which 2937/3638 have no sections) equals the whole
front's `capture::file_rows` (header fields, name, anchor, ordinal,
place), the stored `SECTIONS` rows, the front's relocation section of
each placed section, and its mentions (key names, `find_key` = stored
`MENTIONS.symbol`, values). 862/857 COMDAT anchors, 958/1069 relocated
sections, 4807/4977 keys, 1/2 locals whose name is a key. The two
`input-changed` tests (a rewritten object; `lib2.a` rebuilt with its
members swapped) pass on both targets.
