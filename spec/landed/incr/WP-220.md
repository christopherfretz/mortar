# WP-220 (U-8): the ODR checks in an incremental update, design

Step 1 of U-8 (`briefs/u-2-to-9.md`): how an update recomputes
odr.md's findings for the ODR-affected keys only (IN-71d) and gets the
same text and order as the full link (IN-78, IN-75a). This settles
WP-213's F-5 (the ODR keys have no numbering; `ODR_CLASSES` and
`ODR_REFS` are PROVISIONAL). Nothing here is code. Every new table,
field, argument and dependency edge below is a **proposal** awaiting the
supervisor's word. `spec/incr.md` is not edited; §H gives the proposed
text.

**Ruled 2026-11-18** (`briefs/wp-220-rulings.md`): step 2 is R-1 (a)
only, W1 and W2 exact in an update, with ONE new table, `COPIES` (55,
§E). §B-§D and their tables are **proposed, not ruled (WP-236)**: an
adversarial review with experiments comes before any code. Until then
the update falls back with `update-not-implemented (meta)` decided from
the switches alone (`mortar_odr::register::update_fallback`). R-2 is
accepted for (a): `ChangedFile::odr: OdrRows { copies }`, `odr()` takes
`&Odr`, the edge `mortar_incr -> mortar_odr` with one comparator
(`mortar_odr::foreign::compare_copies`). R-6: no record table is
written; an `--odr` mode change is `options-changed`.

## R. What needed a ruling (as asked)

- **R-1 What the update must do under each mode.** The finding in §A
  decides this. In the default `--odr=warn` NO record check runs (O-42,
  O-47's register: every record check, ENFORCE, isa and vtable-rtti is
  `strict` only). Only **W1** (`odr-size-mismatch`) and **W2**
  (`odr-symbol-type-mismatch`) run, and they read symbol tables
  (`foreign.rs`), not `.mason.meta`. I propose this order:
  - **(a)** W1 and W2 are exact in step 2. They are what the operator
    runs, on every input including GCC and Clang objects.
  - **(b)** The record families (kinds 2, 3 and 5, internal references,
    O-32, ENFORCE) are exact under `--odr=strict` too, from the stored
    rows of §B-§D. The fall-backs in R-4 cover the rest.
  - **(c)** U-2 fixes the bytes of every table below now, so (b) never
    reopens the format.

  The alternative: step 2 does only (a), and an update under `--odr=strict`
  whose ODR-affected keys are non-empty gives `update-not-implemented
  (meta)` until a later package. That is about half the work, and the
  brief's three-hop test then covers only W1 and W2 (plus the strict
  K's refused by name). I recommend the full form (a)+(b)+(c). Yours to
  pick.
- **R-2 Signatures and shared types** (`briefs/u-common.md`: a signature
  that lacks what a rule needs).
  - **`ChangedFile`** carries `meta_units: u32` only. It has no ODR
    rows, and its `MentionRow`s carry no `st_size` and no symbol-table
    index, which W1 and the diagnostic key need. I propose one new field,
    `odr: OdrRows`, a new shared type in `update/view.rs`:

    ```rust
    pub struct OdrRows {
        /// One per (ODR key, row) of the new version's live units:
        /// (family, name bytes, OdrVariant, line, unit).
        pub records: Vec<OdrRecord>,
        /// Its COMDAT copies' global definitions (§E), position in
        /// `keys` as `mentions`.
        pub copies: Vec<CopyRow>,
    }
    ```

    The join (U-10) fills it with the capture's function, so a full link
    and an update produce the rows from the same code.
  - **`odr()`** takes `mode: OdrMode`. It needs `&mortar_core::plan::Odr`
    (`check_archives`, `table`, `runtime`, `stats`), which decide R-4's
    fall-backs. Proposed: `fn odr(view, changed, resolved, odr: &Odr) ->
    Result<Vec<DiagRow>, IncrReason>`.
  - **`mortar_odr`** must export two things:
    - the rows a full link's capture stores (§B-§E), as a new
      `Outcome::rows: Option<OdrStateRows>` filled when the link
      captures a state;
    - each diagnostic's subject (family and name bytes, or the symbol),
      so that capture and the update assign the same `Subject`s (§C).
  - **A dependency edge `mortar_incr → mortar_odr`.** The update must
    call the full link's comparator, not a copy of it. I propose that
    `mortar_odr` exposes `records::compare_key(rows: &[KeyRow], units:
    &[UnitCtx]) -> Vec<Finding>` and `foreign::compare_copies(..)`, pure
    functions over a key's rows. `check` calls them per key, and the
    update calls them per affected key. `mortar_odr` already depends only
    on `core`, `diag`, `elf` and `meta`, so the edge creates no cycle. The
    other form, a trait `mortar_incr` defines and `mortar_odr`
    implements, adds an indirection for nothing.
- **R-3 New tables and changed tables** (U-2 fixes the bytes):
  - `ODR_KEYS` (53, key-keyed, new);
  - `ODR_FILE_KEYS` (54, file-keyed, new);
  - `COPIES` (55, key-keyed, new);
  - `ODR_CLASSES` (47) redefined as per-key variants;
  - `ODR_REFS` (48) widened to 16 B;
  - `odr_class` extended into families.

  Widths are in §F. Three new kinds go into `FileTable`/kinds 53-55. They
  are new `mod`-free items, but they are new shared rows.
- **R-4 Named fall-backs** (each `update-not-implemented (meta)`, as for
  `--keep-mason-meta`). Each applies only when its check runs AND the
  update touches it:
  1. W3 and W4 (strict).
  2. O-23 `--odr-check-archives`.
  3. O-24 shared-object inputs (strict).
  4. A type finding whose O-19 details note needs the details area of an
     unchanged file's unit. The details are not stored (§D); the other
     form is an input reader argument to `odr()`.
  5. `--odr-table`/`--odr-runtime` when a changed file has meta units.
     The `.note.mason` table is a whole-output contribution; it is
     unchanged when no changed file carries units, so
     `odr_runtime_note_under_update` holds for such an update and
     falls back otherwise. G-1's contributions can lift this.
  6. `--odr-stats` (whole-link counts).
  7. O-31 isa and O-25 vtable-rtti for an affected COMDAT group that
     defines no global symbol, when the live units' kind-1 values for
     the name are not all one value (§D.4).
  8. `odr-internal-reference` when its check needs the symbol map of an
     unchanged file (not checked, §J).
- **R-6 The record tables are written only under `--odr=strict`** (§F);
  a mode change is then `plan-changed`. Recommended; the other form costs
  every default-mode kiln link about 65 MB at 1,000 TUs.
- **R-5 Findings in today's spec and seam**:
  - IN-18e says "`ODR_*` are zero for GCC and Clang objects". That is
    wrong for W1 and W2 in default mode. They read every COMDAT copy's
    `st_size` and `st_type`, so their rows (`COPIES`) exist for GCC
    objects too (protoc: 55,866 definitions, §F).
  - A file can define one key in two COMDAT groups. `KEY_REFS` (one row
    per (key, file)) cannot show this, and `foreign.rs` groups copies by
    group, so `COPIES` is keyed by (key, file, symbol index).
  - Today the `odr-abi-mismatch` subjects are the file only. Its key
    (an `ENFORCE` name) must be a subject too, or a stale finding
    survives when another file changes the value. §C gives every ODR
    diagnostic its key subject.

## A. What the full link computes, and what an update must reproduce

The full link (`mortar_odr::check`) produces one sorted list of
`(mortar_diag::Key, Diagnostic)`. The keys are §9.1's: phase 40; unit =
the `FileId` of the first file of the second class; seq = that file's
symbol-table index, or 2^40 + row index (types, unanchored), or 2^41 +
group (O-25, O-31); a record check's tag sits at `<<44`. Its inputs fall
into three families:

| family | grouped by | inputs | runs |
|---|---|---|---|
| W1/W2 | global symbol, then COMDAT group (W1) | every COMDAT copy's global definition (file, sym index, `st_type`, `st_size`, group) and the resolved definition | default (on) |
| records (kinds 2, 3, 5; internal; O-32; O-11 schemes) | ODR key (O-4: name + class), then O-20's partition | the live units' rows, the unit's scheme, layout scheme, `-std`, language | strict |
| unit values (ENFORCE O-30, isa O-31, vtable-rtti O-25) | kind-1 name across units; COMDAT group over the copies' files | each live unit's kind-1 rows | strict |

Every finding is a function of one group (one key, one symbol, one
name, one COMDAT group) and of the unit context of the files in it.
So IN-71d's scheme holds per family. Recompute the affected groups from
their stored rows plus the changed files' new rows. Drop the stored
`DIAGS` rows of those groups by subject (IN-75a). Keep every other
group's stored findings.

## B. ODR key identity in the state (`ODR_KEYS`, kind 53) — proposed, not ruled (WP-236)

An ODR key is **(row kind, class, name bytes)** (O-4). The name bytes
decide; MT-13's FNV-1a 64 (the meta row's `key`) is an index only.
`ODR_KEYS` is key-keyed and sorted by `(hash, kind, class, name bytes)`.
One row per key that some live unit's row names:

| field | type | |
|---|---|---|
| `hash` | u64 | MT-13's FNV-1a 64 of the name, as the `.mason.meta` row carries it (the kind-1 names are hashed the same way) |
| `name` | `Str` | the name bytes in `STRINGS`, appended once when the key first appears |
| `id` | u32 | the key's number: a full link (and a compaction) numbers keys by position in this order; an update appends `count`. `ODR_CLASSES`, `ODR_REFS` and `ODR_FILE_KEYS` name keys by `id` |
| `class` | u16 | the row's class (kind 2's `class`; 0 for kinds 1, 3, 5) |
| `kind` | u8 | the row kind (1, 2, 3, 5) |
| `flags` | u8 | `TOMB` |

A lookup reads every row of the hash and compares kind, class and name
bytes, the same rule as `NAMES`. A gone key (no ref left) is a
tombstone. Its `id` is never reused before compaction. The key keeps
its `Str`, so if the key comes back it takes the old row and the old
`Str`.

## C. What `Subject::OdrKey` carries — proposed, not ruled (WP-236; W1/W2's subjects are ruled: `Subject::Key` and the files named)

The type is unchanged: `OdrKey { name: Str, class: u8 }`.
- **`name`** is the `ODR_KEYS` row's own `Str` (for O-25/O-31, the
  `GROUPS` row's signature `Str`). One key has exactly one `Str` in the
  state, so equality of subjects is equality of keys without a string
  compare.
- **`class`** becomes the family. `odr_class` is extended to:
  `FUNCTION 0`, `VARIABLE 1`, `TYPE 2`, `DECLARATION 3`, `SUMMARY 4`
  (a kind-1 name: ENFORCE), `GROUP 5` (O-25 and O-31's COMDAT group),
  and `KIND2 6 + c` for any other kind-2 class `c`.

W1 and W2 findings take `Subject::Key(SymbolId)` (their group is the
symbol). Every ODR finding also keeps `Subject::File` of each file it
names, as today. The full link's capture gets the subject from R-2's
new `Outcome` field (family plus name bytes, mapped to the `Str`
through `ODR_KEYS`/`GROUPS`), so a full link and an update store the
same subjects.

## D. The record rows, and how a changed file's OLD keys are found — proposed, not ruled (WP-236)

### D.1 `ODR_FILE_KEYS` (kind 54, file-keyed): the answer to F-5

One row per (file, ODR key the file's live units name), 4 bytes (`id`),
in the file's range through `FILE_INDEX`. A changed, gone or
no-longer-extracted file's **old** keys are its range: O(that file's
rows). The new version's keys come from `ChangedFile::odr.records`. The
ODR-affected record keys are the union of the old and new keys, plus
(IN-71d) the keys whose COMDAT keeper changed (`ResolveDelta.reelected`
and `groups`, mapped to the keys their copies define through §E). Its
patch rule is the file-keyed class's.

### D.2 `ODR_CLASSES` (kind 47, redefined): the key's variants

One row per **distinct comparator input** of a key. A variant is
everything `records.rs` compares, without `line` (per ref, §D.3) and
`details` (an offset into the unit, read only for a finding's note):
- the row's hash, flags, layout, size, align, `ty`, and the `file` and
  `type_name` strings;
- plus the unit context the comparator reads: scheme (O-11), layout
  scheme, `-std` and `SYSTEM` (O-32), language.

Each row also has `count`, the refs that fall in this variant.

| field | type |
|---|---|
| `id` | u32 (key) |
| `variant` | u16 (key; position among the key's variants, append) |
| `flags` | u16 (the row's flags; `TOMB` in the high bit) |
| `count` | u32 |
| `context` | u32 (scheme u8, layout scheme u8, std u8, language u8) |
| `hash` | [u8; 16] |
| `layout` | u64 (kind 3's layout; kind 5's `ty`) |
| `size` | u64 (kind 5's size; kind 3's size) |
| `align` | u32 (kind 3) |
| `text` | `Str` (kind 2/3's `file` string; kind 5's `type_name`; kind 1's value) |

That makes 64 bytes. A **key with one variant has no record finding**,
and this is decided in O(1). This matters most: a header's inline
function is in every TU, with identical rows (measured, §G), and a
changed TU that keeps its row only moves a count. Only a key with two or
more variants (or a ref count above one in a unit, `one_per_unit`) runs
the comparator over its refs.

### D.3 `ODR_REFS` (kind 48, widened): who holds which variant

Key-keyed by `(id, file, unit)`. One row per row of a live unit, 16
bytes: `id` u32, `file` u32, `line` u32, `variant` u16, `unit` u8 (the
unit's position in the file; `-r` merges more than one), `flags` u8
(`TOMB`). It lists a key's files in `FileId` order, which is what a
finding's classes, its §9.1 key (first file of class 2) and its
`file:line` sources need. It is read only for a key the comparator
runs on.

### D.4 Unit values (ENFORCE, isa, vtable-rtti)

Kind-1 rows are keys of kind 1 (name = the summary name; the variant's
`text` = the value). So ENFORCE (O-30, "per kind-1 name across units")
is the same machine. A file's unit values are its kind-1 keys from
`ODR_FILE_KEYS`.
- O-31 and O-25 compare the values of the files of a COMDAT group's
  copies. When a kind-1 name has one variant over all live units, no
  group can differ on it: O(1).
- Otherwise, a group's finding changes only when one of its copies'
  files changed (its values or its copies) or when its keeper changed.
  So the affected groups are the changed files' groups (old: the
  anchors of their grouped `SECTIONS`; new: `ChangedFile::sections`)
  and `ResolveDelta.reelected`. That is O(change). A group's other
  files are the `COPIES` rows of a key the group defines. A group that
  defines no global symbol has no such rows, and that is R-4 item 7's
  fall-back.

### D.5 How a finding's text is rebuilt when the changed file's row is gone

It never needs the gone row. An affected key is recomputed from its
**current** rows only:
- the changed files' new rows (`ChangedFile::odr`);
- the unchanged files' rows (variants + refs + `line`);
- the names (`ODR_KEYS`, `FILES`), the unit context (the variant) and
  the summary notes (kind-1 variants of the file's keys).

The old version is used only to find WHICH keys to recompute (§D.1) and
to drop their stored `DIAGS` rows by subject. A finding whose classes
included the old row disappears or changes with the recomputation. The
text equals the full link's because it is the full link's function
(R-2) over the same rows. The exception is the O-19 details note of a
type finding, which needs an unchanged unit's details area (R-4 item
4).

## E. W1 and W2: `COPIES` (kind 55, key-keyed)

One row per COMDAT copy's global definition. Key-keyed by
`(key, file, index)` so that a file defining one key in two groups has
two rows. 24 bytes:

| field | type |
|---|---|
| `key` | u32 (`SYMBOLS` row) |
| `file` | u32 |
| `index` | u32 (its symbol-table index: §9.1's seq, W's `At`) |
| `size` | u64 (`st_size`) |
| `typ` | u8 (`st_type`) |
| `flags` | u8 (`TOMB`) |

- **Group.** A copy's group comes from its `MENTIONS` row's section and
  that section's `SECTIONS.anchor`. **Checked (step 2's first act)**:
  `capture.rs`'s section keys take `Anchor::choose(comdat, ..)` with
  `comdat` = `inputs.comdats[resolution.sections[s].comdat].name`, and
  `anchor_row` writes `Anchor::Comdat` as `anchor_kind` 1. So a section
  is in a COMDAT group exactly when its `anchor_kind` is 1, and then
  `anchor` is that group's signature: the same `ComdatId` (one per
  signature) `foreign.rs` groups copies by. No column is added. The
  order of groups differs (the full link sorts by `ComdatId`, an update
  meets signatures); it does not reach the output, because W1 runs per
  group and the diagnostics are sorted by their §9.1 key.
- **Affected symbols.** These are every key a changed file's copies
  define (old: `MENTIONS` of its range whose section is grouped; new:
  `ChangedFile::odr.copies`), plus every key whose resolved definition
  changed (`ResolveDelta.resolved`, `reelected`).
- **Recomputation.** Per affected key, `foreign::compare_copies` runs
  over its `COPIES` rows (with the changed files' rows replaced) and its
  `RESOLVED` row (`st_type`, size, common) under the full link's `agree()`
  fast path.

## F. Widths and the state's size

The record tables exist only when some unit has `.mason.meta` and
`--odr` is not `off`. One more choice (R-6): write them only under
`strict`, the one mode whose checks read them, so that a default-mode
link pays nothing for them; a change of `--odr` mode is then a full link
(`plan-changed`). I recommend that. The other form writes them in every
mode, so that a mode change needs no full link, at the cost below in
every kiln link.

`COPIES` exists for every input, and its rows are written whenever W1
and W2 run (every mode but `off`).

| table | width | rows |
|---|---|---|
| `ODR_KEYS` | 24 B + name in `STRINGS` | distinct keys D |
| `ODR_CLASSES` | 64 B | distinct variants (≈ D, measured §G) |
| `ODR_REFS` | 16 B | rows of live units R |
| `ODR_FILE_KEYS` | 4 B (+12.5% slack) | (file, key) pairs ≤ R |
| `COPIES` | 24 B | COMDAT copies' definitions |

**Heavy link: 1,000 TUs** (*estimate*). Assumptions:
- R = 1,563 rows a TU, WP-071's measured heavy TU (kinds 1/2/3/5 =
  6/594/302/661), which is close to O-21/O-22's "about 1,600". That
  gives R = 1.56 M.
- D: header entities repeat across TUs. At 15% distinct, D = 234 k. Type
  names average 51 B (measured §G).

| | MB |
|---|---|
| `ODR_REFS` 16 B × 1.56 M | 25.0 |
| `ODR_FILE_KEYS` 4.5 B × 1.56 M | 7.0 |
| `ODR_KEYS` (24 + 51) B × 234 k | 17.6 |
| `ODR_CLASSES` 64 B × 234 k | 15.0 |
| **records** | **≈ 65** |
| `COPIES` 24 B × ~1.04 M (§G's 1,042 definitions a kiln TU) | 25.0 |

- **Records against IN-71d.** IN-71d's estimate (19 MB + 28 B a key)
  had no `line`, no file-keyed old-key index, no names and no
  comparator input. Without these an update could not find old keys or
  write the text without re-reading inputs.
- **Worst case: no sharing at all (D = R).** The records cost about
  160 B a row, 250 MB for 1,000 TUs. A code base like that has few
  repeated keys, so a cheaper form is possible: store the variant
  inline in `ODR_REFS` when the key has one ref. I did not design it in
  full.
- **GCC and Clang links** have no record rows. `COPIES` measured on
  protoc (`cxx-medium-static`, `--odr-stats`, this branch's debug
  mortar): 221 files with copies, 21,643 groups, 46,495 copies, 55,866
  definitions. That is 55,866 × 24 B = **1.34 MB**. g10x was not
  measured. U-2's 1.15 × gate (465 MB against format 5's estimated
  442.5) leaves 22.5 MB. If `COPIES` on g10x exceeds that, the compact
  form is the fall-back: one summary row per key whose copies agree
  (size, type, count), with per-copy rows only while copies disagree.
  An agreeing key's copies all have the summary values, so expanding
  a key back into per-copy rows is exact.

## G. Measured: a kiln full link's O-20 (the test producer's units)

Four near-identical libstdc++-heavy TUs plus `main`, kiln + hod (the
pinned `kiln++`, `hod`), linked by this branch's debug mortar with
`--odr=strict --odr-stats`:
- **rows:** 4,401 (kind 1 76, kind 2 1,628, kind 3 1,268, kind 5
  1,429). Per TU that is about 407 kind 2, 317 kind 3 and 357 kind 5, so
  1,100 a TU: 70% of O-21/O-22's 1,600, and below WP-071's 1,563.
- **distinct keys:** kind 2 407, types 317, declarations 359. Distinct
  variants (all fields but `line`/`details`, from `xtask meta dump`)
  equal the distinct keys: rows of one key are identical across TUs.
- **W:** 80 files with copies, 3,277 groups, 4,734 copies, 5,210
  definitions (1,042 a TU).
- **findings:** 2 record findings (`odr-internal-reference`, strict).
- **names:** type names average 51 B.

A real 1,000-TU code base was not linked, so the D/R ratio of 15% is an
assumption, not a measurement.

## I. Rejected alternatives

- **Widening `KEY_REFS` with the copy's `st_size` and index.** It has
  one row per (key, file), so it cannot show one file's two copies in
  two groups (R-5). It would also add 12 B to every mention (51.7 MB on
  g10x) to serve COMDAT copies only.
- **Reusing `SYMBOLS` keys for ODR keys.** O-4's keys are source names
  and classes (types, declarations, kind-1 names), not linker symbols.
  Most have no symbol.
- **Keying `ODR_CLASSES`/`ODR_REFS` by `(fnv64, Str)` instead of an
  `id`.** That gives 12 B more per ref and no stable number. Rejected.
- **Storing only "first three files a class + count".** The comparator
  needs every row's variant to partition. After a removal, the fourth
  file becomes one of the first three, and its `line` is needed.
- **Re-reading unchanged inputs' `.mason.meta` for every affected
  key.** A header key in 1,000 TUs would read every container on every
  update (WP-071's heavy unit is 112 KB: about 112 MB a
  touch). That is not O(change), and `odr()` has no input handle. It is
  kept only as R-4 item 4's alternative, for a finding's details note.
- **Hashing the variant to one 16-byte digest per ref, with no
  `ODR_CLASSES` fields.** That decides "all agree" but cannot write the
  text, which prints hashes, sizes, layouts and type names.
