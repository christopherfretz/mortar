## 2. The cause

- **Front 2** (`update/mod.rs` `front_two`): its replay hook `hooked`
  calls `materialize_in_hook`. `materialize` gives every island its
  STORED size (`materialize.rs` `sized`, WP-273 R-1: "front 2's re-plan
  sizes it"). Then `crate::front::front`, once the hook returns, runs
  `replan_islands` on the replayed placement (front.rs ~1552,
  `if let Some(rules) = target.islands.filter(|_| env.state5)`). That
  appends the patch and sets the island's size from `Replan::sized`
  (front.rs ~698-704). `tables_resized` (~1626) then resizes
  `.symtab`/`.strtab`. `front_two` records `seen.lu = Some(f.layout
  .clone())` (mod.rs ~2194), the layout AFTER all of that.
- **Front 1** (`reference_of`, mod.rs ~1147): `one.materialized` is
  `materialize_on`, which is `materialize_in_hook` over front 1's own
  view. Front 1 is a plain front (`image_link(.., None, ..)`): no replay,
  so no re-plan and no table resize.
- The shadow's `materialize` check (`first_difference(lu1, lu2)`)
  therefore compared front 1 BEFORE the re-plan with front 2 AFTER it.
  WP-273 was built on 1bfce906, before P-5 existed. There front 1's
  layout was the replay input of the old path's front 2, and nothing
  compared it with front 2's final layout. The two packages met only in
  the merge.

## 3. The fix (dbed2d76)

`update/mod.rs` only, in front 1's materialize path:

- `replanned_on(ctx, cwd, lu)`, a new private function. A layout with
  no `Patches` chunk is returned as it is. `replan` returns an
  island-less placement's rows unchanged, so `replanned` stays false and
  `tables_resized` does not run: the early return is exact. Any other
  layout is replayed through `crate::front::front` with a hook that
  returns `lu`. It uses the same `Env` as `image_link` (`slack`,
  `state5`) and its own `Collector`. Front 1's own front then runs the
  same re-plan and the same table resize on front 1's layout. The answer
  is that front's `layout`. A diagnostic, such as a re-plan refusal, is
  an `Err` with the rendered text (`front 1's re-plan: ..`), which the
  shadow reports as `refused: ..`.
- `reference_of`: `one.materialized` is the materialization above,
  passed through `replanned_on`. `d_F` is still materialize's, as front
  2's `h.df` is the hook's.

Front 2's layout is never read. No new `mod` line, no shared type, no
change to an existing signature, no dependency edge. The update's
outcome is unchanged: the result goes into `one.materialized` only, and
that value is read only by the shadow's comparison.

## 7. B-7's note (front 1's refill on a non-identity hop)

Front 1's materialize DOES take the delta on a non-identity hop:
`placement` passes `d` from `delta::layout` to `materialize_on`, which
returns `(lu, d_F)`. Front 1's REFILL does not. `reference_of` (~1031-1047)
refills, on every hop, with `LayoutDelta { files, ..default }` (empty)
and the non-body chunks of front 1's COMPUTED layout, against the
previous output. That refill is the identity case's reference (WP-271
ruling item 8: "the identity reference (M2a, front 1's computed layout
with an empty delta, judged AFTER by R-A1's identity check)"). On a
non-identity hop its bytes are those of a placement that is not the
stored one, so an `.eh_frame` walk over them can read a stale CIE
pointer. Nothing writes it. G-4 (`debug_judged_moved`) does read its
ranges on a non-identity hop. This fix does not touch that path: it
changes `one.materialized` only, and `gc_comdat_last_use_dies` has no
island, so `replanned_on` returns early there. The cause is different,
so it is named here and left alone.
