# WP-060: the design of incremental linking (`spec/incr.md`)

Record of WP-060, a design package: it wrote `spec/incr.md` (draft,
awaiting review) and no code. This record says how the draft was made
and what it rests on; the draft itself carries the numbers.

## 1. Method

- **Sources.** mortar's own specs (`model.md` §4, §5, §7, §8;
  `layout.md` §18; `image.md` §7, §12; `synth.md` §11; `resolve.md` §13;
  `dyn.md` §14; `arch.md` "Incremental links"; `input.md` §4.6, §9.4,
  §11.6), kiln's and hod's specs (`kiln/spec/driver.md`,
  `hod/spec/object.md`, `hod/spec/dwarf.md`, `hod/spec/eh.md`), read
  only. Prior art (MSVC, gold, Zig, wild, mold, lld, ld64, hot
  patching) from public documentation as the author knows it, marked
  "not verified here" in `incr.md` §2; none could be run (no `ld.gold`
  on the host).
- **Experiments.** E1–E6 of `incr.md` §12, with scripts in the
  workspace's `.build/review-incr/` (uncommitted; `run-all.sh WORK
  MORTAR`). Every number in the draft is one of: measured by them,
  derived from mortar's specs (cited), an *estimate* (a sum of measured
  parts, labelled), or "not verified here".
- **Order.** Census first (what an edit changes), then the shape of a
  big link (what an index costs), then write costs, then the debug
  experiment; the rules were written after the measurements, and three
  of the architecture's starting positions changed because of them
  (`incr.md` §2.7).

## 2. What the measurements decided

| decision | evidence |
|---|---|
| the unit of change is the file | E1: every edit that adds or removes a symbol or section reorders the object's symbols and section indices and rewrites 99–100% of its `.debug_info` |
| a unit-level index, not field-level | E3: 118,145 (unit, target) pairs against 1,776,710 relocations on protoc |
| no indirection; patch through the index | E3: fan-out of one file's globals is 3 units at p50, 533 at p99 (1.35 MB) |
| debug relocations need no index | E3: 104 of 170,477 debug pairs name a global |
| neutralize dead compile units, not only tombstone | E6/E6b: tombstoned units are enumerated by gdb and lldb (lldb picks a stale type); neutralized ones are invisible |
| zero the whole dead abbreviation table | E6b's first attempt: lldb lost line information of a live unit |
| stat, then content hash | E2: reading protoc's inputs costs 120–220 ms of a 560 ms link; `stat` 4.3 µs |
| regular archives dominate the floor | E2: 80–160 ms to read `libprotoc.a` |
| in place by positioned writes; copy on the exceptions | E5: positioned writes of MiBs cost ms; `ETXTBSY` on a running executable; copy of 1 GiB 1.8–2.9 s; no reflink on the overlay |

## 3. What could not be checked here

- Any incremental linker's behaviour (prior art not runnable).
- The floor of an update as a whole: §1.5 is a sum of measured parts;
  WP-064 measures it.
- The state's size as written: IN-19 is derived from E3's counts.
- Neutralized type units and split-DWARF skeletons (IN-51 falls back on
  them until WP-065 tests them); name indexes (IN-55).
- `ETXTBSY` on kernels newer than 6.8 (`incr.md` §11 Q2).
- Durability across power loss (IN-46's `fdatasync`s are by argument).

## 4. Incidents

Recorded in `incr.md` §12: the bench cache's GNU-ld-built static protoc
was overwritten by an early E2 run and rebuilt with the cache's own GNU
ld command; an early build wrote some artifacts into the main
checkout's cargo target directory.
