# WP-060: the design of incremental linking (`spec/incr.md`)

Record of WP-060, a design package: it wrote `spec/incr.md` and no code.
Revision 1 answers an adversarial review (the context repository's
`briefs/reviews/review-060-incr.md`) under the coordinator's rulings.
This record says how the draft was made, what changed in the revision,
what is still unverified, and ends with what the operator decides (a),
the cut (b) and the requests to kiln and hod, ready to send (c).

## 1. Method

- **Sources.** mortar's own specs (`model.md` §4, §5, §7, §8;
  `layout.md` §18; `image.md` §7, §12; `synth.md` §11; `resolve.md` §13;
  `dyn.md` §14; `arch.md` "Incremental links"; `input.md` §4.6, §9.4,

  only. Prior art (MSVC, gold, Zig, wild, mold, lld, ld64, hot
  patching) from public documentation as the author knows it, marked
  "not verified here" in `incr.md` §2; none could be run (no `ld.gold`
  on the host).
- **Experiments.** The first draft's E1–E6 and the revision's R1–R13
  (one per experiment the reviewer required, numbered as the review's §6
  list), all in `incr.md` §12, with scripts in the workspace's
  `.build/review-incr/` (uncommitted; `run-all.sh WORK MORTAR`). The
  reviewer's scripts were copied there from `.build/review-incr-adv/`
  and not edited; edited copies carry a new name (`regions2.py`,
  `corpus2/`). Every number in the draft is measured by them, derived
  from mortar's specs (cited), an *estimate* (a sum of measured parts,
  labelled), or "not verified here".
- **Helpers.** Three measuring subagents, one at a time, each with a
  brief kept beside the scripts (`BRIEF-corpus2.md`, `BRIEF-dwarf.md`,
  `BRIEF-oracle.md`): the corpus extension (R2-A..C, drift for R8), the
  DWARF dead ranges (R9–R11), the oracle and its mutation table (R3,
  R13). Their numbers were checked against their scripts' outputs
  before entering the spec.

## 3. What is still unverified

- Durability across a power loss: IN-46/IN-47's order is argued, not
  tested (no `dm-flakey` here).
- LLVM libunwind's `.eh_frame` walker (not installed, not in
  `scripts/provision.sh`).
- The cost of a `/proc/*/fd` scan (only `/proc/*/maps` was measured).
- The floor on a workload larger than protoc (none in the bench); the
  scaling model's projections (§1.5: 500 MB to 10 GB of output) are
  linear *estimates*, and so is the update's peak RSS at every size
  (3 × the state, not measured). The omitted phases are charged as whole
  full-link phases (≤ 55 ms), an upper bound.
- Stamps on ext4, xfs, btrfs and NFS: not measured here, so off the
  allow-list (IN-22a); FUSE, sshfs, vfat and exFAT are untrusted by
  argument, not reproduction.
- How often `symbol-kind-changed` and `link-order-moved` fire (not
  measured; 0 times on the corpus's edits for the first, derived).
- IN-31's native cost (Python stood in; 13–33 ms is an *estimate*).
- Reflink: no file system here clones, so copy-by-reflink is untested.
- Any incremental linker's behaviour (prior art not runnable).
- `ETXTBSY` on kernels newer than 6.8.
- The TLS row's mutation test on AArch64. Every TP-offset change R3
  produced there also moved an address. (The x86-64 programs now run
  under `qemu-x86_64`.)
- The oracle and the equivalence check exist only as Python prototypes.
  Their cost in mortar's own harness is an *estimate* (IN-63).
- **Open from the by-value oracle**: with every row in place 6 of 36
  pairs fail: `-O2` l (allocated merged `.rodata.str*` fragments whose
  owner or position changes; no row covers it) and x86-64 lx (a
  `crtbeginT.o` field to an unplaced section). A missing refill row or
  an oracle gap; WP-063 resolves both before the oracle gates.
- **N2 pending**: dedicated gc scenarios for
  `startstop`, `linkorder`, `group`, `nonalloc`, `local`; what mortar
  does with a non-alloc non-debug section's relocation target.
- **Split DWARF not measured** (`.build/review-incr/BRIEF-split.md`).
- Clones: `std`'s copy reaching `copy_file_range`, and the kernel
  cloning, are read, not run (no reflink here).
- PIE tombstones (R11): mortar refuses `-pie` on this branch. Until
  WP-066 runs R11, IN-53 rewrites dead address-bearing contributions in
  a PIE to their neutral form.
- A dead `.debug_loclists` or `.debug_frame` range in the middle of a
  section. R9 tested them appended only, so IN-51b allows only appends
  in those two sections until S5 tests them.
- Neutralized type units and split-DWARF skeletons (these fall back,
  IN-55a).
- The `.eh_frame_hdr` size at scale (≈ 8 B per FDE, *estimate*; the
  bench's static protoc has none). `.debug_aranges` is now measured
  (0.68 MB, IN-54).

## (a) Operator decisions

Each with options, measured costs and a recommendation.

**1. The write path (M4).**

| option | cost per update (protoc, 50 MB) | what can go wrong |
|---|---|---|
| (a) copy and rename always | 18–27 ms at low load (first run 40–58 ms), 52–76 ms at load ~20; ~0.4–1.5 s per GiB; 0 where the file system clones (none here) | nothing torn is ever visible; a running process and a debugger keep the old inode and see the old program consistently until restarted |
| (b) in place, guarded by `ETXTBSY` and a `/proc/*/maps` scan | saves the copy; scan 1.0 ms at 57 processes, 5.6 ms at 575, 55 ms at 5,083; four `fdatasync`s (~8.2 ms overlay, 2.3 ms virtiofs) | the scan sees only its own pid namespace and (unprivileged) its own user's processes: a program started through `ld.so` or qemu outside that view runs a mix of old and new code (measured: it printed the new function's output); lldb with the file loaded crashed after an in-place write |
| (c) **copy by default; in place on request** (`--incremental-write=in-place`, with (b)'s guards and a note naming what the scan cannot see) | (a)'s cost unless asked; (b)'s when asked | (b)'s hazards, only for users who opted in |

Constraint: no `unsafe` and no third-party crate. That rules out an
explicit `FICLONE` ioctl, `fanotify`, and `mmap`-based writes. `std::io::copy`
uses `copy_file_range`, which clones on file systems that support it
(not verified here). **With clones on the operator's target** (the operator: the file system
will be reflink-enabled): the copy path's `copy_file_range` clones
(IN-47; *estimate*, not verified here: this host's overlay and virtiofs
refuse reflink), so (a) costs O(extents) instead of 0.6–0.8 ms/MB, the
sync count is unchanged and writes only the dirty windows and extent
metadata, and a running process or debugger keeps the old inode's bytes.
On the target, copy by default is then no longer a speed trade-off; (b)
remains for file systems without clones. **Recommendation: (c).** It is
correct by default.
The copy is a fixed cost that grows with the output (0.6–0.8 ms/MB with
its sync; 0.35 s of a 0.83 s update at 500 MB of output, *estimate*,
§1.5's scaling model), and §1.5's go/no-go rule names it if it decides
the result: then in place, measured in WP-061, re-opens this decision.

**2. Section-level refill (M12): second or first.**

| option | cost | benefit |
|---|---|---|
| (i) **second**: WP-068 after WP-065 | none until then | v1 is simpler; under `-g` the factor is 1.0–3.3, and dirty windows dominate the floor (§1.5) |
| (ii) first: WP-068 before WP-065 | the same package earlier (2,000–3,000 lines, *estimate*); in incremental mode only: +0.44 MB state (5.4%), 13–33 ms CPU, 2–5 ms wall per full link (*estimate*); a plain link pays nothing | with `-ffunction-sections` and no `-g`: refill 2.6–316× smaller for most edits, 1,692–4,483× for a same-size constant (§1.2) |
| (iii) never | — | — |

**Recommendation: (i), with §1.5's trigger.** Move it first if WP-061's
measured update on the large workload, without `-g` and with
`-ffunction-sections`, spends more than 25% of its time refilling the
changed file's units.

**3. The slack overhead.** Output growth of an incremental-mode link on
protoc (`regions2.py`, IN-33). The debug tail sets the compaction rate
(IN-57):

| debug tail | protoc `-g` output | `-g` updates before compaction (max / p99 / p90 / p50 file) |
|---|---|---|
| `size/8` | +17.2% | ≥500 / ≥500 / ≥500 / ≥500 |
| `size/16` | +12.4% | 227 / ≥500 / ≥500 / ≥500 |
| **`size/32`** | **+10.0%** | 227 / 297 / ≥500 / ≥500 |
| none | +7.6% | 88 / 18 / 19 / 121 |

Without `-g` the output grows +20.1%, mostly from fixed minimums: four
`PT_LOAD` reserves of at least 64 KiB, 4 KiB section tails, and 64-byte
region minimums. These shrink relative to the output on bigger programs.
Under edits that keep growing (synthetic drift of 1–5% per update),
every tail compacts within 3–88 updates. **Recommendation:**
`size/32` plus size classes. Revisit the allocated fractions with
WP-064's measured `reserve-exhausted` rate.

**4. kiln's development profile passing `--incremental` by default.**
Options: (i) now; (ii) **after §1.5's go result and S6 (WP-066)**; (iii)
never by default. The promised speedup for a one-function edit on
protoc `-g` (`incr.md` §1.5, measured floor plus the omitted phases as
an upper bound, so an *estimate*): 1.3–2.5× by copy with thin archives,
1.5–3.5× in place, 0.9–1.5× with a regular archive (which can be slower
than a full link). Projected 2.3–2.5× by copy and 4.0–4.5× in place at
0.5–10 GB of output (*estimate*). Until WP-061 measures it and L10
measures the fall-back rate, the default would add +10–20% output size
and the state file (16% of the output on protoc) for a gain not yet
measured. **Recommendation: (ii).**

**5. Old bytes kept until a full link** (the re-review's n8). An update
leaves the bytes of old versions in dead ranges (IN-3a): a removed
function's code is trap-filled (IN-3), and a dead constant fragment is
zero-filled, but a removed **string literal** stays in allocated
`.rodata.str*` (suffix sharing, L-147), and every old debug contribution
(names, `.debug_str` strings, whole dead `.debug_line`/`.debug_addr`
contributions, IN-53) stays until a full link or compaction. A developer
removing a secret from source has not removed it from an incrementally
linked output.

| option | cost | what it buys |
|---|---|---|
| (i) **keep them, say so** (`docs/`, the `--incremental` help text, and a note in `--incremental-report`) | none | nothing; the user is told that a full link (`--incremental=off` once, or deleting the state) removes them |
| (ii) IN-3b scrubbing of non-allocated dead ranges | the writes of the whole dead contribution on each update of a file: p50 210 KB, p99 823 KB, max 1.50 MB on protoc (§1.4), against today's unit and abbreviation rewrite only | no old debug bytes; still not removed strings in `.rodata.str*` or `.debug_str` fragments shared by suffix |
| (iii) refuse `--incremental` for outputs marked sensitive | an option and a check | no old bytes at all, by a full link every time |

**Recommendation: (i).** No scrub can remove a string a live one may
share a suffix with (IN-3b), so (ii) gives a false assurance; a full
link is the remedy and costs one link.

**Recommendation: (i).** It can say no (no-go after the named parts are
measured), and it asks the large workload for the gain that justifies

**7. `SOURCE_DATE_EPOCH` with `--incremental`** (IN-7). An incremental
output's bytes depend on the edit history (slack used, holes, dead
ranges, region order), so equal inputs give equal bytes only after the
same history.

| option | cost | effect |
|---|---|---|
| (i) **warn** (`incremental-not-reproducible`, once per link) | none | a reproducible-build pipeline that sets the variable and passes `--incremental` gets history-dependent bytes with a warning |
| (ii) refuse | a pipeline that sets the variable everywhere (some distributions' build environments do) cannot use `--incremental` until it unsets it | no history-dependent output under the variable |
| (iii) ignore `--incremental` and do a full link, with a note | the full link's time | reproducible bytes, the option silently weakened |

**Recommendation: (i).** The development profile is the only user of
`--incremental`; a reproducible build is a release concern, and the
warning names the conflict. No byte-identity test links with
`--incremental` (IN-7).

## (c) Requests to kiln and hod, ready to send

*Ranking after the operator's sizing (`incr.md` §1.5, reference
configuration): with 1,000–3,000 small archives, request 1 saves at
most 0.4–5 ms per update and adds 8–77 ms of `stat`s, so it is **not
sent as a default**; it is kept, conditional, for builds with a few
large archives. Request 2 is the first to send.*

**To kiln (1, conditional): thin archives in the development profile.** "mortar's
incremental mode (spec/incr.md, M7) detects a changed object in a
*thin* archive with one `stat` per member. In a regular archive built by
deterministic `ar` (`D`, the Debian default), a same-size member edit
changes only that member's bytes: no header field and no offset. mortar
must then read and hash every member, which costs 50–70 ms of a
107–178 ms update on protoc `-g`. Please make the driver's development
profile (and its build examples) create thin archives (`ar rcsT`), or
link objects directly. No change is needed for release builds."

**To kiln (2): a switch to omit `DW_LNCT_MD5`, on in the development
profile.** "Under kiln `-g`, a header edit changes every object that
includes it (40 of 40 in a 40-unit corpus). For the same edits GCC
changes 13 or 34. The 27 (e5) and 6 (e6) extra kiln objects differ only
in the edited header's DWARF 5 MD5 in `.debug_line`'s file table.
Clang 19 behaves the same as kiln when every file of a unit has an MD5.
It drops all of a unit's MD5s when one file lacks one, so in the corpus,
where every unit includes libstdc++, its objects did not change
(`incr.md` §1.1, R2-B and R2-B'). GCC 14 emits no MD5s. Today
`-gdwarf-4` is kiln's only way to drop them. For mortar each such
object is a changed input. In incremental v1 it is refilled whole: its
allocated units plus its debug contributions, about 210 KB of debug at
the protoc median. That is 27 extra whole-file refills of 40 in e5. Please
add a switch that omits `DW_LNCT_MD5` (a DWARF 5 line-table header has
one file-entry format, so it is all files or none), and turn it on in
the development profile. Its cost: with it on, debuggers lose source
checksums, so they cannot tell a source file edited since the build
from the one compiled. It matters most
until mortar's section-level refill (WP-068) exists, which would refill
only those objects' `.debug_line`."

**To hod (3): notice before name indexes or type units.** "mortar's
incremental mode v1 falls back to a full link when a changed object has
`.debug_names`, `.debug_pubnames`/`.debug_gnu_pubnames`, type units
(`DW_UT_type`, `.debug_types`) or split-DWARF skeletons (`incr.md`
IN-51, IN-55). hod emits none today. Please tell mortar before it starts
to, so that WP-065 tests them first."

**To kiln (4), later: `-gsplit-dwarf` in the development profile**,
once WP-065's skeleton tests pass. Please measure its effect on kiln's
own test links first.

**To kiln (5), later: `--incremental` in the development profile**,
when mortar is the linker. Only after §1.5's go result and WP-066
((a) 4).

**Withdrawn:** the first draft's request to hod for a guarantee that "an
edit outside a function does not change the function's bytes". No
compiler gives that guarantee (`__LINE__`, `assert`, inlining, and
assembler-resolved branches all break it, `incr.md` §1.1), and mortar
does not need it (IN-31 hashes sections itself).
