# WP-277: a repeated archive on the command line no longer stops the state

The record of the package (brief `briefs/wp-277.md`), written by its
agent. LINKER package, incremental capture. The finding was WP-276's
§1.4-§1.5: every `--incremental=full` link of `cxx-large-g` ended with
`incremental: no state written: DIAGS: a warning gnu-warning: it names
FileRef { path: "lib/libLLVMSupport.a", member: Some("DynamicLibrary.cpp.o") },
which is not one file of the link (IN-75a)`.

## 1. The cause, from the code and the run
Small reproduction (`w277/r1/repro.sh`, AArch64; the same shape runs on
both 64-bit targets in the tests below): `main.o liby.a libw.a libb.a
liby.a libw.a`. `c.o` (in the repeated archive) calls `foo`, and `libw.a(w.o)`
warns about `foo` with glibc's `link_warning` form. `b.o` calls back into `c.o`.

- **The member is not loaded twice.** The map lists `c.o` once, `nm` shows
  one `cfun`, and the verifier (`xtask plumb`) finds 0 problems on both the
  plain output and the `--incremental=full` output.
- **`inputs.files` holds the members of both mentions.** input.md §9.1
  makes each mention its own input: two `ArchiveId`s, two sets of member
  `FileId`s, and two `FILES` rows that differ only in `mention`. Only one
  of them is extracted: the first mention's, by resolve.md §4.1's
  first(K), the first lazy definition by `FileId`. That holds even for
  `main2.o liby.a libb.a liby.a libw.a`, where GNU ld would take the second
  mention's copy (resolve.md §4.3 documents the difference). The second
  mention's copy stays `Dead`/`LAZY`.
- **The refusal.** `diag_rows_named` built a display -> `FileId` map that
  gave `None` for a display two files share, and it refused any warning
  that names such a display. A member does not play two roles here: one
  copy is lazy and was never read past its symbol table, and the other is
  live.
- **What the linkers print**:

  | Linker | Output |
  |---|---|
  | GNU ld | `ld.bfd: libc.a(c.o): in function 'cfun':` / `c.c:(.text+0x10): warning: foo is deprecated`, once |
  | lld, mold | nothing (they do not implement `.gnu.warning`) |
  | mortar | `warning: foo is deprecated` / `>>> referenced by libc.a(c.o):(.text+0x10)`, once |

  The full link was correct before the fix and is unchanged by it.

## 2. The fix (`crates/mortar_incr/src/capture.rs` only)
The private `diag_rows_named` takes `in_link: &dyn Fn(FileId) -> bool`.
`Rows5::capture_diags` passes "the row is not `LAZY`" from its own file
columns. `diag_rows` (the tests' entry) passes "has `SECTIONS` rows".
Neither public signature changes, no type changes, and there is no
VERSION bump.
- `named_files(ids, in_link)`. When one file has the display, the result
  is that file (unchanged). When several do (an archive or an object given
  twice), the result is those of them in the link: a warning about a file
  of the link names a file the link reads. If several are in the link
  (`a.o a.o`), the result is all of them (IN-75a, plural): both mentions
  are the same bytes and are touched together. If none is in the link, the
  result is `None`. Which file the warning is about is then unknown, so no
  state is written (the conservative path; no case is known).
- `reference_of(found, prev)`. A listed `referenced by` place is a
  relocation in one of `named_files`' files (at most one per file, as
  before). The scan lists the three least `RefId`s in (file, section,
  record) order, which is `DiagRef`'s (file, seq) order
  (`mortar_scan::events::Acc::keep`). So the place is the least match
  after the previous listed reference. The first one is still checked to
  be the key's `(unit, seq)`.
- **The other mention is not a subject.** The rule picks the file the
  warning depends on. The second mention's copy can become extracted only
  if the first one stops being extracted. Both are one path with one set
  of bytes, so an edit touches both rows, and first(K) always takes the
  first mention. Any extraction flip of either row also touches it, and
  the key subject (`affected` through `KEY_REFS`) recomputes the site row.
- **The update side** (`update/diags.rs`) is unchanged. Its rows hold
  `FILES` rows (`FileId`s). `Site::place` renders from the `FILES` row's
  display, and `Site::unchanged` skips `LAZY` rows of `KEY_REFS`. The
  `hop` tests check that the update drops and recomputes the row as the
  full link of the new inputs stores it, in the same order.
- **A plain link pays nothing.** The changed code runs only in an
  incremental-mode capture that has a warning. The displays map was built
  there before too.

**What the real updates do.** Every hop after the first falls back with
`update-not-implemented (diags)`, which shows the state was there.
Before the fix those hops would say `no-state`. Without testhooks the
small outputs say `small-output`. Under testhooks the incr_diags hop
that removes the call says `update-not-implemented (resolve)`.
`(diags)` is the join's path A (`crates/mortar/src/update/mod.rs`
`image_link`): front 2 over the whole new input set says something, so
the update is left to the full link ("M2a updates silent links only").
The stored `DIAGS` rows are not used by the binary yet. That is outside
this package (§5).

## 4. The large workload (AArch64, `cxx-large-g`)
Run from `inputs/` with `@response.txt` UNCHANGED. `-o` and
`--dependency-file` come after it and point into the scratch; the
workload directory is read-only. Release build, one link at a time,
`/usr/bin/time -v` over the whole process, load 7.7-11.8, at least 9 GB
available. Scripts: `w277/large.sh`, `large2.sh` (the same again) and
`large3.sh` (the line without `--dependency-file`).

**The state is written: 195,717,490 B.** WP-081's was 209,791,911 B. With
the second `libLLVMSupport.a` removed it was 195,628,530 B, so the repeat
adds 88,960 B: the second mention's 24+1 archives' member rows, `LAZY`.
The output is 1,226,586,552 B. The three warnings are glibc's `dlopen`,
`getpwnam_r` and `getpwuid_r`, as before.

| Run | Wall | Max RSS |
|---|---|---|
| `--incremental=full`, `large.sh` | 18.79 s | 2,786,956 KB |
| `--incremental=full`, `large2.sh` | 16.53 s | 2,869,604 KB |
| `--incremental=full`, `large3.sh` | 26.55 s | 2,775,636 KB |

**The one no-op update (the same line, `--incremental`) is NOT taken.** It
falls back to the full link (rc 0), and its standard error equals the full
link's outside the `incremental:` line:
- With the real line: `incremental: full (update-not-implemented (image))`.
  `crates/mortar/src/update/mod.rs` ~:200 (G-7) refuses before reading
  anything, because the line has `--dependency-file` and there is no
  update producer of the dependency file yet. clang's CMake link line
  carries `--dependency-file`, so every update of the operator-shaped
  link stops here first. 27.08 s and 17.08 s wall: the process falls back
  and links in full.
- Without `--dependency-file` (`large3.sh`; the line otherwise
  unchanged): `update-not-implemented (resolve)`, from mod.rs ~:210
  "Nothing changed: no update to make". Detection read the state and found
  no changed file, the 25 repeated archives' rows included. 21.63 s wall.

The next refusal on a real edit of this link is not measured. The lane
scenario's hops answer `update-not-implemented (diags)` (path A's
`image_link`: front 2 over the whole input set prints the warnings, and
"M2a updates silent links only"). Every glibc static link prints
`dlopen`'s warning, so the operator's link would meet the same refusal.

## 5. Census of the class (`capture.rs`: lookups by display, path, name)
| Shape | Before (reading) | Now (run, `w277/r2/census.sh`, a64) |
|---|---|---|

| the warned holder's archive twice (`libw.a ... libw.a`) | holder by `FileId` (`Front::gnu_warnings`): fine | written |

Other lookups in `capture.rs`:
- File identities (`keys.identities.file`/`file_id`, `file_identity`)
  include the mention ordinal (`mortar_core::identity::FileIdentity`), so
  they are unique per mention.
- The holder of a warned key is found by `SymbolId`.
- `resolve_diag_keys` works per key (one `SYMBOLS` row per key).
- `interned` and the option-name sets do not depend on files.

None of these meets this refusal.

GNU ld prints the `a.o a.o` warning once. mortar lists both references,
in diag.md's `referenced by` form, as before this package.
