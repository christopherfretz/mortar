# WP-219 (U-7): the incremental update's writes and the crash protocol

`mortar::update::write::write` fills IN-77's W1..W6 (in place) and
C1..C5 (by copy), IN-77a's checks, IN-77d's leftovers, IN-77e's failures
and IN-45/IN-76's choice of path; `mortar_incr::ops::RecordingOps`
replays every power loss. W5/C4 call U-2's `state5::patch`/`compact`,
which still return their "until it lands" value: `write` writes the
output, then fails at W5 as IN-77e says (flag set, our file removed).
The tests drive the protocol through `write_with` (doc-hidden: `write`
with W5's writer given) against a stub state (the supervisor's ruling).

## Q. Findings for a ruling

- **S-1 the new size is not an argument.** W3 "truncate or extend" needs
  the new output's size; `write` has the ranges and `META` (the old
  size) only. Until it does, the size is `max(META.file_size, end of the
  last range)`: a growing output is extended, a shrinking one is NOT
  truncated (its tail is stale bytes past every segment). Proposal: a
  `size: u64` (the new placement's file size) on `Pair` or as an
  argument.
- **F-1 "the report says which" (IN-76).** `Written` has no field for the
  IN-45 condition that forced the copy path; `in_place_blocked` computes
  the sentence and drops it. Proposal: `Written::copy_because:
  Option<&'static str>`. The `incremental-in-place-unchecked` note is
  the join's to print.
- **F-2 IN-77b "a hard-linked snapshot keeps its bytes" is not quite
  true.** W1/C2 sets the flag through `S`'s descriptor, the snapshot's
  inode, so the snapshot keeps its blocks with its flag word set (read
  as a state it is `output-torn`; safe). Proposed text: "keeps its
  blocks; its updating word is set by W1, so as a state it is
  `output-torn`".
- **F-3 W4's `EEXIST` is `Failed`, not `Fallback`.** "the link fails
  with `output-changed` and nothing more is written": `WriteFailure::
  Failed { step: "W4", error }` (kind `AlreadyExists`, text
  `output-changed: ...`); the join must not run a full link after it.
  W2's foreign file (put back) is `Fallback(output-changed)`.
- **F-4 IN-77e "from W1/C2 the flag stays set" cannot hold when W6's or
  C5's sync fails** (or the compaction's directory sync after its
  rename): the cleared word (the new state) is already live. The next
  link sees the new pair (copy) or `P` removed (`output-changed`):
  never a trusted mix. Proposed text: "...the flag stays set, except
  when W6/C5's (or the compaction's) final sync fails: the state is then
  the new one as the kernel holds it".
- **F-5 not reachable from the seam**: IN-77b's lock acquisition and
  "renamed while waiting", IN-77c's boot-id check, the flag-first
  reader are U1's; no entry point exists for U-7 to test them
  (`two_updates_one_output_serialize`, `state_renamed_while_waiting_retries`,
  `boot_id_changed_checks_leaves` not written). Proposal: a
  `pub fn lock_state(path, ops) -> Result<File, IncrReason>` in U1.
- **F-6 a plan that patches a shared `S`** (hard-linked or symbolic,
  IN-77b) is refused before W1 with `update-not-implemented (write)`: no
  §7 name fits.
- **F-7 IN-77a's check is by tuple.** A foreign same-inode, same-size
  write between U1's check and `write`'s start is not seen (the
  descriptor's tuple is taken at `write`'s start, after the leftovers);
  from then on the whole tuple is compared.
- **F-8 the floor's state temporary** (IN-77d) is now pid-free,
  `File::create`d and not locked: two unlocked full links share it, and
  the lock holder's leftover removal can remove a live floor's
  temporary (its `try_lock` succeeds). Outside "that line only".
- **F-9 the format-5 flag** must stay at `format::FLAGS_OFFSET` (12):
  W1/W6 write it there; W5 writes 16.. (U-2, the join).
- **F-10 a held leftover `A`** keeps the update off in place (the copy
  path): IN-45 does not list it; W2's `rename(P, A)` would replace a live
  link's file.

## V. H-1's virtiofs report, against this protocol's calls

Run on the workspace mount (virtiofs), in one scratch directory under
`.build/target-wp-156/scratch-219/` (removed by its literal path
afterwards), with Python's `os` calls, which are the same syscalls:

1. **The protocol's sequences, 3000 iterations, twice** (once with a
   second process doing `stat` and `open` on every name in a loop, once
   alone). Each iteration ran W2 (`rename(P, A)`, zero `e_ident`,
   `fdatasync`), W3, W4 (`pwrite`, `fsync`, `link(A, P)`, `fsync(dir)`,
   `unlink(A)`, `fsync(dir)`), the compaction (`O_EXCL` create, write,
   `fdatasync`, `rename(C, S)`, `fsync(dir)`), H-1's case (`link(P, L)`,
   then `rename(Z, P)` over `P`, then `open(L)`), and a leftover second
   name removed (`link(P, A2)`, `unlink(A2)`, `open(P)`). After every
   call, every name was checked by `stat`, by `open` and read back, with
   `fstat`'s `(dev, ino)` compared and `listdir` consulted on a failure.
   **0 failures in 6000 iterations.** H-1's case (`open(L)` after `P`,
   L's other name, was renamed over) never failed in that process.
2. **The observing process** saw `open(S)` give `ENOENT` once in 20664
   tries. `S` is only ever renamed over (`rename(C, S)`), so it should
   never be absent. `stat(S)` never failed.
3. **A focused loop**: one process ran `rename(C, S)` (C created,
   written and synced first) and `rename(Z, P)` 20000 times with `L` a
   second name of the first `P`. A second process looped on `open` and
   `stat` of `S` and `L`. Result: **`open(S)` gave `ENOENT` 12 times in
   42738 (about 1 in 3600), and each time `listdir` showed `S`;
   `stat(S)` 0 failures in 42738; `L` 0 failures** (open and stat).

What that is: on this mount, while one process renames a file over a
name, another process's `open` of that name can see `ENOENT`, and the
name is still listed. `stat` did not see it in these runs. I did not
reproduce H-1's exact sentence (a hard link's other name failing after
the first name was renamed over).

Where it touches U-7 (none of these is a step of the protocol failing;
they are what other processes see):

- **C3's `rename(T, P)` and the compaction's `rename(C, S)`**: while
  either runs, another process's `open(P)` (make, a debugger, `exec`)
  or `open(S)` (a second link's U1) can see `ENOENT`. POSIX says the
  name is never absent. For the protocol's outcome rule this is only a
  reader seeing no file: no pair is ever made of mixed bytes. For U1
  (not U-7's), an `open(S)` `ENOENT` while another link compacts reads
  as `no-state` and starts a full link. Whether that full link takes
  IN-77b's lock before it writes `S` is **for the supervisor or U1 to
  rule**; I did not test it.
- In U-7's own code nothing opens `S` by name after a rename. The names
  U-7 opens are the leftovers (IN-77d: `File::open(A|T|C)`); an
  `ENOENT` there leaves the leftover in place, and a left `A` sends
  the update down the copy path.

**Each `WriteOps` call's unexpected `ENOENT`/`ESTALE`/`EEXIST`**, and
what is at `P` afterwards (from the code; the injected-failure tests
cover `EIO`/`ENOSPC` at every call, `EEXIST` at W4's link, and a foreign
file at W2, and they all end the same way):

| step | call | outcome | `P` |
|---|---|---|---|
| before W1 | leftover `flock`/`unlink` | ignored; a leftover still there is left; a left `A` means the copy path | untouched (old) |
| W1 | `pwrite`/`fdatasync` of the flag | `Failed W1` | old (flag clear: old pair; set: `output-torn`) |
| IN-77a check | `stat(P)` errors | `Fallback(output-changed)` | as found, not written |
| W2 | `flock(P)` | `Failed W2` | old |
| W2 | `rename(P, A)` | `Failed W2`, nothing removed | old, or absent with A the complete old file if the rename happened (flag set: `output-torn`) |
| W2 | `stat(A)` is `ENOENT` after the rename | treated as foreign: nothing put back, `Fallback(output-changed)` | absent, flag set: `output-torn` |
| W2, W3 | `fsync(dir)`, `pwrite`, `set_len`, `fdatasync` | `Failed W2/W3`, `A` unlinked if it names our inode | absent: `output-torn` |
| W4 | `link(A, P)` `EEXIST` | `Failed W4` (`output-changed`), `A` removed | another link's file |
| W4 | `link(A, P)` `ENOENT`/`ESTALE` | `Failed W4`, `A` removed if ours | absent: `output-torn` |
| W4 | `fsync(dir)`, `unlink(A)` | `Failed W4`, `P` and `A` removed if ours | absent, or the complete new file if its `stat` failed; flag set: `output-torn` |
| W4 | `bind` (stamp create/remove) | `Failed W4`, `P` removed if ours | absent: `output-torn` |
| W5, W6 | any | `Failed W5/W6`, `P` removed if ours | absent: `output-torn` (W6's sync: F-4) |
| C1 | `create_new(T0)` `EEXIST` | `T0.<pid>` instead (I-59) | old |
| C1 | any other | `Failed C1`, `T` removed if ours | old (old pair) |
| C2 | flag | `Failed C2`, `T` removed | old |
| C3 | `stat(P)` errors | `Fallback(output-changed)`, `T` removed | as found |
| C3 | `rename(T, P)` | `Failed C3`, `T` removed if ours | old (or the new file, if the rename happened) |
| C3..C5 | `fsync(dir)`, `bind`, W5, flag | `Failed`, `P` kept | the new file: `output-torn` (C5's sync: F-4) |

In every row `P` is the old output, the new output, absent, or (W4
`EEXIST`) another link's file, and the state's flag is set in every row
from W1/C2 on, so no row can be trusted as a mix. No step depends on
`open` by name after a rename, so H-1's behaviour as reproduced
(`open` → `ENOENT` while another process renames) does not break a
step. As H-1 reported it (a second name gone after the first is
renamed over), it would hit only an `A` that is a second name of `P`
(W4 between the link and the unlink), and every use of `A` there goes
through `unlink` and `stat`, which end in the rows above.
