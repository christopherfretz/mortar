# WP-219 (U-7): the incremental update's writes and the crash protocol

`mortar::update::write::write` fills IN-77's W1..W6 (in place) and
C1..C5 (by copy), IN-77a's checks, IN-77d's leftovers, IN-77e's failures
and IN-45/IN-76's choice of path; `mortar_incr::ops::RecordingOps`
replays every power loss. W5/C4 call U-2's `state5::patch`/`compact`,
which still return their "until it lands" value: `write` writes the
output, then fails at W5 as IN-77e says (flag set, our file removed).
The tests drive the protocol through `write_with` (doc-hidden: `write`
with W5's writer given) against a stub state (the supervisor's ruling).

## Q. Findings for a ruling

- **S-1 the new size is not an argument.** W3 "truncate or extend" needs
  the new output's size; `write` has the ranges and `META` (the old
  size) only. Until it does, the size is `max(META.file_size, end of the
  last range)`: a growing output is extended, a shrinking one is NOT
  truncated (its tail is stale bytes past every segment). Proposal: a
  `size: u64` (the new placement's file size) on `Pair` or as an
  argument.
- **F-1 "the report says which" (IN-76).** `Written` has no field for the
  IN-45 condition that forced the copy path; `in_place_blocked` computes
  the sentence and drops it. Proposal: `Written::copy_because:
  Option<&'static str>`. The `incremental-in-place-unchecked` note is
  the join's to print.
- **F-2 IN-77b "a hard-linked snapshot keeps its bytes" is not quite
  true.** W1/C2 sets the flag through `S`'s descriptor, the snapshot's
  inode, so the snapshot keeps its blocks with its flag word set (read
  as a state it is `output-torn`; safe). Proposed text: "keeps its
  blocks; its updating word is set by W1, so as a state it is
  `output-torn`".
- **F-3 W4's `EEXIST` is `Failed`, not `Fallback`.** "the link fails
  with `output-changed` and nothing more is written": `WriteFailure::
  Failed { step: "W4", error }` (kind `AlreadyExists`, text
  `output-changed: ...`); the join must not run a full link after it.
  W2's foreign file (put back) is `Fallback(output-changed)`.
- **F-4 IN-77e "from W1/C2 the flag stays set" cannot hold when W6's or
  C5's sync fails** (or the compaction's directory sync after its
  rename): the cleared word (the new state) is already live. The next
  link sees the new pair (copy) or `P` removed (`output-changed`):
  never a trusted mix. Proposed text: "...the flag stays set, except
  when W6/C5's (or the compaction's) final sync fails: the state is then
  the new one as the kernel holds it".
- **F-5 not reachable from the seam**: IN-77b's lock acquisition and
  "renamed while waiting", IN-77c's boot-id check, the flag-first
  reader are U1's; no entry point exists for U-7 to test them
  (`two_updates_one_output_serialize`, `state_renamed_while_waiting_retries`,
  `boot_id_changed_checks_leaves` not written). Proposal: a
  `pub fn lock_state(path, ops) -> Result<File, IncrReason>` in U1.
- **F-6 a plan that patches a shared `S`** (hard-linked or symbolic,
  IN-77b) is refused before W1 with `update-not-implemented (write)`: no
  §7 name fits.
- **F-7 IN-77a's check is by tuple.** A foreign same-inode, same-size
  write between U1's check and `write`'s start is not seen (the
  descriptor's tuple is taken at `write`'s start, after the leftovers);
  from then on the whole tuple is compared.
- **F-8 the floor's state temporary** (IN-77d) is now pid-free,
  `File::create`d and not locked: two unlocked full links share it, and
  the lock holder's leftover removal can remove a live floor's
  temporary (its `try_lock` succeeds). Outside "that line only".
- **F-9 the format-5 flag** must stay at `format::FLAGS_OFFSET` (12):
  W1/W6 write it there; W5 writes 16.. (U-2, the join).
- **F-10 a held leftover `A`** keeps the update off in place (the copy
  path): IN-45 does not list it; W2's `rename(P, A)` would replace a live
  link's file.

## S. Shape changes (need the supervisor's word)

`write_with` and `StateWriter` (doc-hidden, `mortar::update::write`);
`mortar_incr::ops`: `Op::CreateNew { path, file }` (the file's id),
`RecordingOps` performs through `StdOps` and records only successful
calls, `RecordingOps::file_of`, `RecordingOps::power_loss`, `Disk`.
`write`'s signature is unchanged.
