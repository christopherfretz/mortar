# WP-262 — the full link's capture writes `SYMTAB_KEYS`

The record of the package (brief `briefs/wp-262.md`), written by its
agent.

## Why
IN-49a's update plan (`mortar_synth::symtab_incr::plan`, WP-217) finds
each global it moves, removes, demotes or promotes through the state's
`SYMTAB_KEYS` (IN-18e, key-parallel: per `SYMBOLS` row a `.symtab` index
and a `.strtab` offset, `NONE` without a global entry). No full link
wrote it: `state5/write.rs` resized the table with `NONE`, so on
255d2b's AArch64 bytes `_Z10wp255d_inli` (entry 5714), `wp255d_m1`
(5717) and `wp255d_m1_data` (5718) were all stored
`{ index: 0xffffffff, strtab: 0 }`. An update would have taken every
surviving global for an added one and appended it again.

## The producer (one walk)
- `SymtabPlan::incr_global_keys(&self, cx, pool)` (the one new `pub fn`,
  `crates/mortar_synth/src/symtab.rs`): `None` unless the plan has
  IN-49a's form (`facts.room`). Per `SymbolId`, `(entry, st_name)` of its
  global entry, `(u32::MAX, 0)` otherwise. It is the writer's own walk:
  `classify` per key in S-75's `SymbolId` order, from each checkpoint of
  the global segment (one pool task per `CHECKPOINT` block), the names'
  offsets by `fixed_name` / `region_len`, as `Walk::next` gives
  `st_name`. Each block must end where the next checkpoint (or the area)
  starts, else an internal error.
- `NONE` follows from the walk: a local key, a hidden/internal/
  `STB_LOCAL` global (`Class3::Demoted`, written in its file's block), a
  key the table does not write (no place: gc'd, an unreferenced
  undefined, a withdrawn key), a key of an unextracted member.
- Routing: `crates/mortar/src/incremental.rs` (`Session::state`, the
  format-5 branch only) computes `(incr_global_area(), keys)` through
  `Front::with_sym_cx` and passes them in the new field
  `Link5::symtab: Option<(SymtabBlock, &[(u32, u32)])>` (`None` under
  `-s`). `rows5` maps each `SymbolId` to its `SYMBOLS` row (the same
  `syms.row` loop that fills `SYMBOLS.at_*`) into `Rows5::symtab_keys`;
  `state5_rows` puts them in `MemoryState::symtab_keys`; the rows added
  there for options' names get `NONE`. `compact::normalize` carries them
  with their rows (`compact.rs` ~499).
- **Order:** the plan is final before the capture. The front builds it in
  phase 80 (`front.rs:887`, replanned `:1110-1124`, patches
  `:1280-1291`); `lib.rs:495` writes the image from it; then
  `lib.rs:503` `Session::finish` -> `incremental.rs:1123`
  `Session::state` -> the capture. An update's state is the same
  `Session::state` (`update/mod.rs:353`), so it runs the same producer.

## The check (every capture)
`capture::symtab_keys_check`, in `state5_rows` before
`check_capture`: with the plan's global area `[first, first + count)`
(= `[sh_info, entries)`), every entry named by exactly one row; every
non-`NONE` row inside it; each row's `strtab` equal to the `st_name` that
S-86 lays for its entry (the area's names in entry order from its first
byte, `name\0` each, the fixed table's names at 0/1/4/7), the names
ending at the area's last byte. Without `.symtab` every row is `NONE`. A
failure returns `Err`: no state is written (as `file_round`). Unit test
`capture::wp262::a_good_table_passes_and_each_break_is_refused` (seven
breaks, each refused by its words).

## VERSION
`state5::VERSION` 7 -> 8. A version-7 state has `NONE` everywhere and is
refused `state-version` (reader and end to end: `symtab_keys`
`version_7_state_is_refused`).

## Proposed for IN-18e (the key-parallel row) and IN-49a
"The full link's capture writes `SYMTAB_KEYS` from the symbol table
plan's own walk of the global area: per key its entry's index and that
entry's `st_name`, and `NONE` for a key with no global entry (a local, a
hidden, internal or `STB_LOCAL` definition written as a local, a key the
table does not write). A capture whose rows do not name each entry of
`[sh_info, entries)` exactly once, with the `st_name` S-86 lays for it,
writes no state."
