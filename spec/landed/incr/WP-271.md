# WP-271: patch islands at the update's addresses (DESIGN)

Branch `wp/271-islands-design`, base 1bfce906 (int/batch-26 + WP-267
P-1c). No linker code is changed. Evidence: `.build/target-wp-140/w271/`
(`island-bytes.txt`, `f1/*.txt`, `f1.log`, `keep.log`). The rule text
below is PROPOSED. The supervisor writes it at the spec commit.

## 0. What needs a ruling

1. **Option (a), the one-round re-plan at fixed islands, is recommended.**
   - The update re-scans only the dirty 843419 windows at U7's final
     addresses. It judges thunk need, appends new patches inside the
     island's fixed capacity, rewrites patches whose words changed, and
     turns patches whose key is gone into `Fill` holes.
   - Overflow is `island-exhausted`.
   - **The datum it needs: none.** `PATCHES`, `REDIRECTS`, `SIZED`,
     `HOLES`, `CHUNKS` and the chunk capacity already carry everything.
     So there is **no new column and no VERSION bump**, and the bump
     WP-270 shares with 255h is not touched.
   - A plain link and `--incremental=full` stay byte-identical, because
     the full link's fixed point is not changed.
2. **L-115 must be scoped to a full link.** An update appends patches,
   so an island is no longer in key order. The verifier does not check
   key order, and `check.rs` does not either. IN-78 holds because the
   placement is data. The alternative, inserting at the key's position,
   moves later patches and refills their sites' units (§2, option a2).
3. **Thunks, v1.** The update takes a link only when L-113's fast path
   holds at the update's addresses: the RX `PT_LOAD` span, islands at
   capacity, is ≤ 2^27 − 4. Otherwise it refuses with
   `update-not-implemented (layout)`.
   - The per-branch judgement over refilled `CALL26`/`JUMP26` sites is
     designed (§2 a, "thunks") but cut as a follow-up.
   - **This matters for the operator's target.** A large static
     executable with more than 128 MiB of RX would fall back on every
     update. Rule whether the follow-up is cut now or after the
     large-workload measurement.
4. **The 843419 judge must read pre-fix input words.** It must never
   read the previous image. Every section that holds a word of a dirty
   window joins the refill set. This adds a row to IN-27's refill set
   (§3, IN-27 row).

## 1. Today's model, with bytes

### 1.1 Where island sizes are decided

These are full links (`mortar_layout/src/fixed.rs`, arch.md §6, layout
§14).

- **Rounds.** `fixed_point` loops rounds at addresses A_k. Each round
  lays out each island in L-115 key order (`lay_out`), then runs stage D
  (`address`), then `needs`.
- **What `needs` judges.**
  - Every branch's target. A thunk is needed when T − P ∉ s(28); none is
    needed when L-113's fast path holds.
  - Every 843419 window over every code output section's words
    (`Sites::code`).
- **Where a new patch goes.** `island_of_section` puts it in the island
  of its site's part. Patches are only added. Stale erratum redirects are
  dropped at the end, and their patches stay unused (L-116).
- **Island size and start.** The island's size is the end of its last
  patch (L-115, L-121), and the island is in `sized`. Stage D pads a
  non-empty island's start off page offsets 0xFFC, 0x000, 0x004 and
  0x008 (L-118). An empty island gets no padding.
- **What is stored** (`spec/incr.md` table 18-20):
  - `PATCHES` holds one 32-byte row per patch: chunk, kind (0 thunk,
    1 PLT thunk, 2 erratum), offset, key (`SYMBOLS` row for kinds 0
    and 1, `SECTIONS` row for kind 2), and addend or site offset.
  - `REDIRECTS` holds (section, patch row, offset).
  - `SIZED` holds (chunk, size).
- **The image.** The image writes thunks from `PATCHES`. Erratum patch
  words and the site's `b` (or the ADR) come from `Link::fixups`, which
  `sites.rs` `erratum_fixes` computes over ALL exec words at the final
  placement. A site that needs a patch and has no redirect is an
  internal error.
- **The island's capacity** is its size plus stage C's capacity. As
  `.text`'s last chunk it holds `.text`'s whole tail reserve
  (`chunk.rs` `capacities`). That is why WP-216 F-3 refuses a `.text`
  overflow: "its tail is in a patch island chunk".

### 1.2 What the update does today

These are in `mortar_incr/src/update/materialize.rs`.

- **`patches()`** refuses if the computed placement has an erratum
  patch or redirect in a changed file, or if a stored row names a
  changed file. Otherwise it translates the stored rows unchanged.
- **`sized()`** refuses a size that differs from the computed one. It
  then applies **F-1's bound** (WP-225): an equal-size address-dependent
  row is taken only when no exec section is moved or revived and no exec
  chunk moved (`moves_code()`).

So no update ever adds, drops or rewrites a patch, and none moves code
on AArch64 while an island exists.

## 2. Options, each costed

Notation:

- R is the refill set's exec bytes (changed, revived, placed, moved,
  referrers).
- W is the dirty windows, about R/4096 + one per refilled range.
- P is the patches of the touched islands.
- D is the redirects of refilled sections.
- B is the branch relocations in refilled sections.

**The property every option rests on.** U7 places islands with fixed
capacity (IN-72 item 9). Adding a patch inside that capacity moves no
other address. So needs judged at U7's final addresses are final, and
the update's fixed point is ONE round with no iteration.

| | (a) re-plan at fixed islands (RECOMMENDED) | (a2) as (a), keeping L-115 key order | (b) veneer-slot reserve inside the island | (c1) page-congruent moves | (c2) no 843419 in incremental mode |
|---|---|---|---|---|---|
| idea | scan W at U7's addresses; append new patches in capacity; rewrite D; stale ones become `Fill` holes | insert at key position; later patches move | the island's size = capacity; unused room is a `Fill` hole (map `hole`) | move code only by multiples of 4096, so windows keep their sites | refuse the option in incremental mode |
| stored datum | none (PATCHES, REDIRECTS, HOLES, SIZED, CHUNKS) | none | `HOLES` row per island (exists); no column | none | none |
| VERSION bump | no | no | no | no | no |
| update cost | O(W + D + P_touched + 1) | O(W + D + P + redirects of every moved patch), plus refills of those sites' units | as (a) | O(1) per move, but up to 4 KiB of slack per moved run, and changed code still needs (a) | O(1) |
| verifier already judges (plumb.md only) | C1 (site with no fix), C2, C3 (redirect at a non-site), C4, C5 (chunk start), C6, W7/W8 (patch meaning), stage 1 (reach), P-I1 (holes covered by the map `hole` line) | same | same, plus P-I1 for the in-chunk hole | same | C6 refuses it, rightly |
| plain link byte-identical | yes (the fixed point is untouched; the replan is called only from the update) | yes | yes for plain; **`--incremental=full` changes** (`.text`'s `sh_size` grows by the reserve) | yes | yes |
| WP-269's tail | fits: the body's trailing `Fill` hole grows; the island stays fixed after it, with its own reserve as slack after `sh_size` | fits | fits, but duplicates the reserve the slack already gives | does not address it | n/a |
| verdict | take it | rejected: more refills for no gain, since key order is checked by no judge | rejected: (a)'s capacity is already slack outside `sh_size`; (b) only spares `.text`'s `sh_size` change, which the section headers absorb | rejected: does not cover edited code, and wastes address space | rejected: breaks "correct or refused by name"; Debian's GCC passes the option on every link |

### Option (a) in detail

The steps below run after U7 (addresses final) and before U9's refill.

1. **Dirty windows.**
   - For every refilled exec range [s, e), the windows are the 4096-page
     ends p with [p − 8, p + 12) meeting [s, e). A site's W1 is at
     p − 8 or p − 4, and F is at most W1 + 12.
   - Every section that holds any word of such a window **joins the
     refill set** (the neighbour across a section boundary). Its words
     are then the pre-fix input words, not the previous image's.
   - **Why not the image.** The image's F may hold an old `b patch`, or
     W1 an old ADR. Those would hide a site, or make a non-site look
     like one.
   - **Further dirty windows.** Every redirect in `REDIRECTS` whose
     section is refilled makes its window dirty. A redirect whose
     section is moved or gone is re-judged or dropped.
2. **Judge each dirty window** by a64 §11:
   - the words must be `$x`, from the refilled sections' mapping
     symbols;
   - the opcodes decide: W1 ADRP, W2 load/store, F load/store unsigned
     immediate with base Xn. Relocation does not change opcodes or
     registers, so the site predicate is a function of the addresses
     and the input words only;
   - the fix is ADR in place when Page(V) − Q ∈ s(21); otherwise a
     patch.
3. **Patches.**
   - **A site that needs a patch** reuses the patch of the same key
     (SectionId, offset of F) in its part's island, if one exists. That
     happens when its section is unchanged and unmoved, or moved within
     the part with reach checked. Otherwise a new patch is **appended**
     at `align_up(island end, 4)`.
   - **Padding for the first patch.** If the island was empty and its
     start is at a forbidden page offset (L-118), the chunk's start
     moves forward by the L-118 padding, at most 16 bytes, inside its
     capacity. The full link's padding has the same shape: a `hole`
     before the chunk. Nothing points into an empty island, so nothing
     else moves.
   - **Reach.** It is exact: the patch reach [F − 2^27 + 4, F + 2^27 − 4]
     and the patch's `b F+4`. L-112 guarantees it when the site's
     section is in the island's part.
   - **Overflow.** If the island end passes its capacity, the update is
     `island-exhausted`. The `.fini` island's capacity 0 and `.init`'s
     3 make any site there `island-exhausted`.
4. **Patch words.**
   - Every patch whose redirect's section is refilled is rewritten:
     W4' is the relocated F, and the `b F+4` follows. This is an 8-byte
     dirty range in the island.
   - A redirect whose site is no longer a site, or now takes an ADR, is
     dropped.
   - A patch whose key's section is in a changed or removed file (its
     `SECTIONS` row is no longer that section) becomes a `Fill` hole in
     the island chunk (a `HOLES` row and a map `hole` line), and its
     `PATCHES` row is removed. Patches that are merely unused stay
     (L-116).
5. **Thunks.**
   - v1: the fast path of L-113 at U7's segments, O(1). If it holds, no
     branch inside RX needs a thunk. A stored thunk whose target symbol
     moved is rewritten (12 bytes, from its `PATCHES` key).
   - If the fast path fails, the update is `update-not-implemented
     (layout)`.
   - The follow-up judges every `CALL26`/`JUMP26` in a refilled section
     (B). Every branch whose target moved is in a refilled section by
     IN-27's referrer rows. It reuses the island's thunk of the same key,
     else appends one, else `island-exhausted`.
6. **The stored tables.**
   - The rows are written whole: `PATCHES`, `REDIRECTS`, the island's
     `SIZED` row, its `HOLES` rows, and the island's `CHUNKS` start when
     padded.
   - The internal file's `.symtab` block gets the patch symbols (S-80:
     a `$x` and an `__erratum_843419_veneer` per patch, in `PATCHES`
     order, S-74) within its IN-49a capacity. Past it, the block moves
     to the local tail reserve, else `symtab-exhausted`.
   - `.text`'s `sh_size` changes; the section header table is rewritten.
7. **IN-78.** The state written equals the capture of a full link given
   this placement. The placement includes the patches (arch.md §6 "What
   `Placement.patches` records"), so the appended order is part of it.

**Cost.**

- O(W + D + P_touched + 1): a window is 5 words, and D and P are
  in-memory row scans of whole tables. These are tables of a few rows
  on protoc (2 redirects); on a large workload they are thousands of
  rows, microseconds.
- The neighbour refills add at most 2 sections per refilled range.
- A growth step that moves the rest of a part by a non-multiple of
  4096 makes all the moved code's windows dirty. That is O(moved),
  already paid by refilling the moved code.

**Where it runs (WP-267).**

- **Phase A.** It runs in front 2's replay hook. The replay's
  `LinkSites` already holds every exec word at L_U, so the window words
  come for free. The phase A hook can also run, under a lane-only
  switch, the FULL window scan and compare it with the dirty-only scan.
  That is an oracle for a missed dirty window, available before phase B
  removes the full words.
- **Phase B.** C' supplies the pre-fix words of the refill set.
- The function takes an abstract provider of window words, so both
  phases call the same code.

## 5. Risks: where a wrong byte could get past the update, and its judge

| # | wrong byte | how | caught by |
|---|---|---|---|
| 1 | a site left unfixed | a dirty window missed (a neighbour, a moved run, a referrer refill) | verifier C1; the phase-A full-scan compare (lane switch) |
| 2 | a site judged on the previous image's words | an old `b patch` at F or an ADR at W1 hides or fakes a site | C1 or C3; prevented by the neighbour-refill rule |

### What needs a ruling

1. **Phase A has no delta at the call.** The replay hook
   (`front::ReplayHook`) returns a `Layout` only; the update's refill set
   (`df`) lives in `crates/mortar/src/update/mod.rs` (not this package's).
   So `replan_islands` (front.rs) passes the WHOLE exec extent as the
   dirty set (`replan::full_dirty`), and `branches_in` (WP-276 ruling 3:
   only the branch sites of the dirty ranges) then picks every branch.
   Consequences:
   - the lane's "dirty-only vs full scan" compare is the same scan twice
     (always `equal`): it checks nothing until the call gets a real dirty
     set;
   - each AArch64 update costs O(all windows + all branches) in the
     re-plan, and `LinkSites::targets` is computed for every branch
     (front 2 already walks every word, so it is the same order as front
     2's own cost, not an added order);
   - the dirty-only path IS unit-tested (`replan_dirty_only_against_full`,
     `branches_in` asserts in `replan_fast_path_fails_refuses`).
   Proposed: the join (U-10, or WP-267 P-5) hands the refill set to the
   hook (a `Replay` field), and the call passes its exec ranges plus the
   window neighbours.
2. **A re-plan refusal is named `(image)` in the report.** The refusal
   is a diagnostic of front 2 (`incremental-update-failed`,
   `island-exhausted: ...` or `update-not-implemented (layout): WP-273
   replan: ...`); `update/mod.rs`'s `front_two` turns any front-2 failure
   into `update-not-implemented (image)` plus a `finding:` line that
   carries the real reason. Naming it `island-exhausted` / `(layout)` in
   the report needs a change in `update/mod.rs` (not mine). The scenario
   `e843419_init_island_exhausted` expects `(image)` until then.
3. **A changed file's patches become `Fill` holes, always.** The record
   (§4, `e843419_site_disappears`) said "the old patch stays unused".
   Built: a patch whose key is a section of `d.files` has an old
   `SECTIONS` row, so materialize turns it into a `Fill` hole (zeros,
   R-6; `replan::hole_gone`) and the re-plan appends a new patch if the
   new version still has the site. A patch of an UNCHANGED file whose
   site went away (moved) stays unused (L-116).
4. **A kept redirect is kept even where an ADR would now fit** (its
   patch in its island and in reach). A full link would choose the ADR,
   so such an update is equivalent to the full link, not byte-equal.
   Dropping it for the ADR is one line; I kept the redirect to write
   fewer bytes. Rule which.
5. **The first patch of an EMPTY island at a forbidden page offset
   (L-118) is refused** (`update-not-implemented (layout)`), not padded:
   the padding moves the island's start, and R-1 keeps islands fixed.
   The proposed L-118 sentence (§3) is therefore not built.
6. **A `Fill` hole in an island is zeros, not a trap pattern** (§4's
   table said the trap pattern; R-6 rules zeros, as the full link's
   image writes every byte of an island no patch owns:
   `mortar_image` `link.rs` `patches()` starts each island zeroed).
7. **x86-64 scenarios are `not x64`.** `--fix-cortex-a53-843419` is
   refused on x86-64 by the command line, so the six scenarios cannot
   run there. x86-64's no-op is shown by the lane's unchanged x86-64
   counts and `replan_without_islands_changes_nothing`.
8. **R-3 is judged only for a refill planned at the link's own
   placement** (`planned_here`: the delta's chunks at the link's
   addresses and offsets). Two callers in `update/mod.rs` refill at a
   placement that is not the delta's: the identity reference (M2a,
   front 1's computed layout with an empty delta, judged AFTER by R-A1's
   identity check) and the 255e shadow (C' over front 1's link). Judged
   there, R-3 failed 3 `update_debug_join.rs` growth tests (a moved
   section's fix at front 1's addresses, file offset 0x60ff8, over the
   previous output's `cmp`), on a refill the identity check then throws
   away; as an error it turned the whole update into a failure. And in
   phase A front 2 refills EVERY chunk (`want` is the whole output), so
   R-3 holds by construction there: it is built and unit-tested
   (`r3_a_fixed_word_outside_the_refill_is_an_internal_error`), but it
   judges a real update only from phase B (C') on. The M2a identity case
   that IS written (front 1's layout equal to the stored one) is not
   judged by R-3: nothing moved, so every fix outside the changed files'
   sections is the previous output's (the slack guard keeps a window in
   one file). Rule whether the join should pass the materialized
   placement to every refill so that R-3 judges all of them.
9. **front.rs order.** The erratum fixes and the final GOT plan of a
   replay are now made before `Layout::validate` (they were made after
   `.shstrtab`), so that the checks judge the re-planned rows. A plain
   link's fixes are the computed ones, unchanged.

### For WP-272's judge (its rulings)

- **A dropped erratum (kind-2) patch is 8 ZERO bytes in the update's
  output, in both of its forms.** (i) Its key's section is in a changed
  file: its `PATCHES` row is removed and its 8 bytes become a `Fill`
  hole of the island (a `HOLES` row, a map `hole` line). (ii) Its site
  went away but its key's section is unchanged (the redirect dropped by
  the re-plan): the `PATCHES` row stays, unused (L-116), with no hole.
  Either way the image writes zeros there: `mortar_image` `link.rs`
  `patches()` starts every island zeroed and leaves erratum patches to
  `Link::fixups`, and `sites.rs` `erratum_fixes` writes a patch's
  `W4'` and `b F+4` only for a patch that a `REDIRECTS` row uses. Never
  full words. (Phase A refills every chunk, so the island is rewritten;
  phase B must refill the island chunk when a patch is dropped, else the
  previous words stay: a note for C'.)
- **Every `b` into an island has a `REDIRECTS` row.** The only `b patch`
  the update writes is `erratum_fixes`' at a redirect's `F`. A redirect
  is dropped only when its `F` lies in a dirty range (the re-plan
  re-judged that window and found no site) or its section has no place,
  so the old `b patch` at `F` is overwritten by the refill of `F`'s
  section (phase A: every chunk). No thunk is created or kept by v1
  beyond the stored ones, and no `bl` into an island is written by the
  re-plan. The islands column was NOT run here: WP-272
