## 3. The cause (bytes and code)

The `.group` sections in the refusal's words ("not placed by the front:
[.group size 12 kept false ..]") are a red herring: they are the
diagnostic's list of the changes the full link does not place (SHT_GROUP
is never placed); they are not the refused section.

**The state's bytes** (`incr_state compare`, the full link's state
against the shrink's; protoc `plain`):

```
REGIONS 04000000 00000000 05 00000000 0e000000 e025000000000000 c00f000000000000: only in the first
REGIONS 04000000 00000000 05 00000000 0e000000 e025000000000000 ac0c000000000000: only in the second
REGIONS 04000000 00000000 05 01000000 0e000000 8c32000000000000 1403000000000000: only in the second
```

(file 4 = main.o, output section 0 = `.text`, category 5, ordinal,
chunk 14, offset, capacity.) The full link writes ONE region
`[0x25e0, +0xfc0)`: `.text` 0xcac, the eight COMDAT `.text.*` sections up
to 0x33e0, the slack `[0x33e0, 0x35a0)` (0x1c0 = max(64, 0xe00/8)). The
shrink's state has TWO: ordinal 0 `[0x25e0, +0xcac)` and a new ordinal 1
`[0x328c, +0x314)`. The same split is in `gc` (ordinal 0 0xfc0 -> 0xdc4)
and `g` (0xfc0 -> 0xcac), from temporary `eprintln!`s in `Update::file`
(reverted).

**Who splits it.** The shrink's delta is right: `.text` keeps its start
(IN-72 item 2, keep), the 0x18 bytes it freed are a Fill hole
`[0x2674, 0x328c)` (IN-3a: a section's freed tail exactly like slack), the
file keeps its region. The update's new state is front 2's capture with
the update's placement, and its `REGIONS` come from `capture.rs`
`region_rows` (WP-264), whose rule is "a run ends where the key changes
**or a `Fill` hole starts**" (:1631 at the base: `next_hole(r.3)
.is_some_and(|h| h.0 < off)`). A full link never has a hole between two
members of one region (`chunk.rs` `plan_parts` closes a run only at a key
change, and adds the slack after it), so on a full link the rule is
harmless; on an update's placement a freed tail (or a gone section,
IN-72 item 1) between two sections of one region ENDS the region there,
and the rest becomes a new region of the same file, category and chunk.
`regions_check` (same file) requires it: every `Fill` hole must be one
region's slack (from its last section's end to its end) or a pad, so a
hole between a region's sections would refuse the state.

**Why the grow back refuses and the shrink did not.** After the shrink,
ordinal 0 `[0x25e0, 0x328c)` holds `.text` (0xc94) and ends at the freed
tail's hole: invariant I holds. The grow back places `.text` (0xcac) at
its old address (IN-72 item 2 place (i): free to its new end, inside
ordinal 0): it now fills ordinal 0 EXACTLY, and ordinal 0 is followed by
ordinal 1 with no hole at its end. `region_pads` (:1436) refuses that
case by design (a later pad at ordinal 1's start could be computed from a
hole inside ordinal 0 and cover a live byte). Before 4552368a there was
no such check and the hop was taken (255e3, d3977a2c, 8cb0fb97).

**The rules it breaks.**
- `spec/incr.md` IN-72 item 2: "The file keeps every region it has had in
  `(O, c)` until the next compaction". The shrink's state shrinks the
  region to 0xcac and invents ordinal 1.
- IN-78: `REGIONS` is a decision row of `P_U` ("`P_U`'s `region` record,
  plumb.md §3.2"), and `P_U` is read from the update's map. The map's
  `region` records (`mortar_image` `map.rs` ~:712-746) are runs of one
  (file, category) with no split at a hole, so by that code the map of
  the shrink says ONE region `[0x6686e0, +0xfc0)` where the state says
  two: the state is not `P_U`'s record. (Read from the code only: an
  update refuses `-Map` here, `update-not-implemented (image)`, and the
  full link's `-Map` of this run has no `region` records, so no map was
  compared.)
- IN-3a / IN-30: the hole a shrinking file leaves is a hole of its region
  ("a region's slack and the hole a shrinking file leaves are holes"),
  not the end of the region.

## 4. The proposed change (ruled to this package; section 7)

In `crates/mortar_incr/src/capture.rs`:
1. `region_rows`: a run ends only where the key `(file, category)`
   changes (as `plan_parts` and the map's `region` records do); its
   capacity runs to the end of the `Fill` hole that starts at its last
   member's end, as now.
2. `regions_check`: a `Fill` hole that lies between a region's first
   section's start and its last section's end is that region's (a freed
   tail or a gone section's bytes, IN-3a, IN-72 item 1).

A full link's `REGIONS` are unchanged by (1) (no hole lies between two
members of one run in a full link), so a plain or full link pays nothing.
In the one other case where two runs of one key meet in a chunk (an
overflow region opened at the tail right after the same file's last
region), (1) gives one region where the base gives two; that is what the
map's `region` record already says for such a placement, so the state
then agrees with `P_U` there too.

The alternative inside `delta.rs` (accepting "a region filled to its end
followed by its own file's next region of the same `(O, c)`" in invariant
I, and no pad at such a region's start) would touch the guard WP-273
relies on, and would keep the split state (IN-72 item 2 and IN-78 still
broken, the regions fragmenting at every shrink). Not proposed.

**Measured as an experiment** (the two edits above, temporary, reverted;
`experiment-capture.patch` in the scratch):
- protoc `plain`, `gc`, `g` (resident): full, shrink, grow back, shrink
  again: **all taken**; the stored region stays `[.., +0xfc0)` (one row)
  after every hop.
- protoc `plain`, bytes: the grow back's output equals a fresh
  `--incremental=full` link of vG byte for byte (`cmp`, 14,749,784
  bytes); its state equals the full link's (`incr_state compare`: 2
  differences, both `STAT` rows, the output's own stat).
- the lane: §5 (the two grow scenarios only, not the whole lane).

## 7. The fix (5bd3573f, bbd0388d)

In `crates/mortar_incr/src/capture.rs`, the two functions ruled, nothing
else in the file:
- `region_rows`: a run ends only where the key `(file, category)`
  changes. Its capacity runs to the end of the `Fill` hole at its last
  member's end, as before (`close`'s `slack_at`).
- `regions_check`: a `Fill` hole inside a region, from its first section
  to its last section's end, is that region's (a freed tail, IN-3a). The
  chunk's holes are sorted and each region takes its holes with one
  `partition_point`, so the check stays linear in holes. It still
  refuses a hole that is no region's slack, interior hole or pad.

`delta.rs` is unchanged; its slack guard (:1437, WP-273) is untouched.

**IN-78: the map and the state now agree (from the code).** The map's
`region` records (`mortar_image` `map.rs` ~:712-746) are runs of one
`(file, category)` over a chunk's members, sorted by offset, with no
split at a hole, extended by the `Fill` hole that starts at the run's
end. `region_rows` now has the same rule: a run of one key, ended only
at a key change, with the `Fill` hole at its last member's end as its
slack. So the shrink's state says ONE region `[0x25e0, +0xfc0)` for
protoc's main.o, as the map's rule does. No map was compared: an update
refuses `-Map` (`update-not-implemented (image)`), and the machine map's
`region` records were not read against the state.

One difference between the two remains, and WP-279 did not change it:
the map gives a member a category only in a chunk named `.text`
(`text && flags & SHF_EXECINSTR`), while `region_rows` gives one to any
`SHF_EXECINSTR` member of a hole-tolerant chunk. They differ only for an
executable member of a hole-tolerant output section other than `.text`.
Whether that case occurs was not checked.
