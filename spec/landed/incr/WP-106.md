# WP-106: five small defects of the incremental code (M7)

Record of WP-106. WP-094 found five defects in the incremental code on
main (c5409aa): a changed thin-archive member named `options-changed`
by the dry run; an unbounded `--incremental-report`; the dry-run delta
computed on links that could never update; `small-output` missing from
`spec/incr.md` §7; one stale number in WP-061b §7. Each was reproduced
by a test before its fix. No command-line option and no option value was
added or renamed. `crates/mortar_plumb/` and `spec/plumb.md` are
untouched.

## 1. A changed thin-archive member (item 1)

**Test, failing on main:** `tests/incremental.rs`
`a_changed_thin_member_is_a_changed_file`. On main the report said
`delta fallback options-changed lib/m1.o changed and is not an object or
archive`.

**Cause.** A thin member is read from its own file, so the state has a
`STAT` row for the member's path (`lib/m1.o`), while its `FILES` row
names the archive (`lib/libt.a`) with the member name `m1.o`. Detection
treated a changed `STAT` path that is no `FILES` path as a linker
script (`detect::detect`, `script_changed`), and the delta then fell
back with `options-changed`.

**Fix.** `crates/mortar_incr/src/detect.rs:267` and `:289`
(`thin_member_paths`): a `STAT` input path read and hashed whose length
and hash are a member row's (object, base 0), and whose last components
are that row's member name, counts as the member's file. Its change is
judged by `FILES`, as a regular archive member's is.

**Only the label was wrong.** The delta itself was right on main: `delta
file changed lib/libt.a m1.o` was there and the three refilled units
were the right ones. The extra `options-changed` fall-back hid them
behind a reason that is not the real one.

**Cases the test runs** (thin `rcsT`, and regular `rcs` as the control,
each from a fresh state): m1 edited (and edited back with the same size
and mtime); m3 removed; m3 and m4 added; m2 replaced by m5 (`delta file
gone` and `appeared`); the archive inside `--start-group`; the link run
from `run/` with `../lib/...` paths. `--start-lib` is refused by the
command line (`docs/status/options.md`), so the group case uses
`--start-group`.

**Spec:** `spec/incr.md` IN-24 (a paragraph on thin members) and the
`options-changed` row of §7 (a thin member's file is not a script).

## 2. The report is bounded (item 2)

**Test, failing on main:** `the_report_is_bounded` (one object of
100,000 sections, each with its global, all moved by one instruction),
and `delta::tests::the_report_bound`.

**Cause.** `delta::report` wrote one line per item of every kind with no
limit. WP-094 measured 801,742,419 B (12,924,615 lines) for one g10x
fall-back.

**Fix.** `crates/mortar_incr/src/delta.rs:1526` (`REPORT_BOUND` =
10,000) and `:1560` (`Bounded`). Each kind of listing line (`path`,
`stat-missed`, `file`, `probe`, `symbol`, `fallback`, `unit`, `hole`,
`chunk`) is written for its first 10,000 items. The rest are counted but
not formatted, and the kind ends with `delta elided <kind> listed=10000
total=<n>`. `delta listed bound=10000 elided=<n>` comes before `delta
time` (`:1782`). The count lines (`delta inputs`, `delta symbols`,
`delta refill`) are never bounded. The oracle lane
(`tests/incr-oracle/oracle.py`) fails a pair whose report elided lines,
naming the kind, so the bound cannot cut what it judges without anyone
noticing.

**Why 10,000 and not WP-094's 1,000.** At 1,000 the oracle lane failed 12
of its 22 quick pairs. Static `-g` links with crt objects list
1,167-2,137 units or symbols (the largest is `ovx`'s 2,137 units).
10,000 keeps every one of them whole. It caps a report at 90,000
listing lines, against WP-094's 12.9 million.

**Measured** (AArch64 shared host, load 1.2-2.0; release builds of this
branch; the 100,000-section link; 7 interleaved runs, median; the
unbounded build is this branch with `REPORT_BOUND = usize::MAX`):

| link | wall s (min/med/max) | peak RSS MiB | report |
|---|---|---|---|
| plain | 0.050/0.050/0.050 | 66.2 | — |
| `--incremental=full` | 0.080/0.080/0.090 | 105.4 | — |
| `--incremental` + report, unbounded (main's behaviour) | 0.140/0.140/0.140 | 125.8 | 11,845,581 B, 300,023 lines |
| `--incremental` + report, bounded | 0.110/0.110/0.120 | 105.2 | 1,135,524 B, 30,022 lines |

The report is 10.4 times smaller. Formatting nothing past the bound
saves 30 ms and 20 MiB on this link.

**Determinism.** Two links of the same history give the same report
bytes, except `time=` and the `delta time` line (`the_report_is_bounded`
masks those two). Proposal: move both times to `--time-phases` so that
the report is byte-reproducible.

**Spec:** `spec/incr.md` IN-10 (the report row) and the new IN-10b;
`spec/cli.md` §3.13 (rows for `delta elided` and `delta listed`, and
"The bound").

## 3. The delta only where an update could run (item 3)

**Test, failing on main:** `a_target_change_at_the_same_path_is_options_changed`.
On main, a state of another target at the same path got `options-changed`
and then a dry run: the link compared an x86-64 state with an AArch64
link and reported `refilled=6`.

**Cause.** `incremental::start` kept the old state for the dry run
whenever `--incremental-report` was given, whatever the reason was. The
target check runs later, in `Session::finish`, and did not drop the old
state either.

**Fix.** `crates/mortar/src/incremental.rs:341` (`dry_run_wanted`: the
reason is `update-not-implemented` or `small-output`), `:242` (the old
state is kept only then), and `:477` (it is dropped after the target
check finds `options-changed`).

**The rule (IN-10a).** A delta is computed only for a state an update
could start from: one that passed every §7 check before the delta.
`no-state`, `state-corrupt`, `state-version`, `options-changed`,
`output-changed`, `output-torn`, `--incremental=full` and shared-object
inputs report the reason alone.

**Decision: the dry run also runs under `small-output`.** That reason is
a policy on the output's size, which `--incremental=update` does not
apply. The oracle lane's links are all small; without this they would
have no delta. A fall-back that the delta itself finds does not stop the
listing either, since its refill set is IN-63b's evidence. The bound
limits the size.

**Plain links.** `a_plain_link_touches_nothing_of_incremental_mode`
puts FIFOs at `p.mortar-state` and at a `--incremental-state` path
(`p.st`), and an older state beside them. A plain link neither blocks on
nor opens a FIFO. The old state keeps its bytes and metadata. The
directory gains only the output. The next `--incremental` link says
`output-changed`. A plain link returns at the first line of
`incremental::start` (`let Some(mode) = ... else { return Start::Plain }`),
before any code this package changed.

**Spec:** `spec/incr.md` IN-10a (new); IN-11's test sentence.

## 4. `small-output` (item 4)

**Test, failing on main:** `a_small_output_is_linked_in_full_by_name`.
`fall_back_reasons`, `a_compiler_driver_link_twice_finds_its_state` and
the target test now expect `small-output` where main said
`update-not-implemented`.

**Cause.** WP-094 §7 proposed the rule but nothing implemented or
specified it.

**Fix.** `crates/mortar_incr/src/lib.rs:18` (`SMALL_OUTPUT: u64 = 256 <<
20`, the one constant), `:22` (`small_output`), and
`crates/mortar/src/incremental.rs:236`. After every other check, a state
whose `META` output size is below the bound gives `small-output`, except
with `--incremental=update`. The test reads the bound from
`mortar_incr::SMALL_OUTPUT`.

**Spec:** a `small-output` row in `spec/incr.md` §7. It says the 256 MiB
is a policy constant, not a measured crossover. It is set from one
workload's measurements: 55 MB, and 583-832 MB, with nothing measured in
between. It is a power of two between those, so the mode can be read
from `ls -l`. WP-105 measures a workload in that range. The
`update-not-implemented` row now says it applies from 256 MiB.

## 7. Not verified

- That a plain link makes no `stat` call. There is no strace on the
  host. The FIFO and byte/metadata checks show only that a plain link
  does not open or write a state, and the code path returns before any
  of it.
- The `small-output` boundary end to end at exactly 256 MiB (that needs
  an output of 256 MiB). The unit test covers the constant's edges, and
  the link test covers a small output.
- Nested thin archives (a thin archive whose member is another archive).
  They stay `options-changed`, which is conservative.
- The O2 (nightly) oracle set under the 10,000 bound. Only the quick O0
  set was run (22 pairs, 0 failed; largest kind 2,137).
- The report size on g10x itself. The 100,000-item synthetic link stands
  in for it.

## 8. Findings

- IN-10 / `docs/cli.md` §3.13: the report's two time fields are its
  only non-determinism. Move them to `--time-phases` (follow-up;
  `crates/mortar/src/incremental.rs:713`, the `delta time` line, and `:511`,
  the summary line's `time=`).
- WP-094 §7's proposed text says "at most 1,000 named items per kind".
  The bound is 10,000 (§2 above), and IN-10b is the rule.
