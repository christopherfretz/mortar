# WP-261 — the full link's capture writes `FILES.round` and `META.iterations`

This is the record of the package (briefs `briefs/wp-261.md` and
`briefs/wp-261-cont.md`; rulings in `briefs/wp-225-rulings.md`, "After
WP-261's first hand-back" and "After WP-261's second hand-back"). The
supervisor wrote it from the two agents' reports
(`briefs/handbacks/wp-261.md`, `wp-261-cont.md`).

## Why
IN-71b's removal cone reads each extracted member's stored ROUND, the
breadth-first round of resolve.md §4.1's closure in which the full link
pulled it in. M2b-1 showed on the bytes (ruling M2b1-5) that no capture
wrote it: every stored member had round 0. `extract` read every
extracted member as a `--whole-archive` one (`Ctx::facts`: `member !=
0 && (LAZY || round > 0)`), and on a real state it never dropped a
member that was no longer needed. The join's guard fell back by name.
Without the guard, the result would have been a wrong program.

## The producer (one walk)
- `mortar_resolve::live::closure` keeps a per-file atomic minimum,
  `round`, filled in the same loop that tracks the pulling reference.
  An edge from a file of round `r` offers `r + 1` to its target.
  - Files on the line are round 0.
  - A root option's target, and a lazy file live from the iteration
    before (`prior`), start at 1.
  - Only an `Extracted` file keeps its round; every other file is 0.
- **Determinism:** a file of frontier `i` has a round of at least `i`,
  so an edge out of frontier `i` offers at least `i + 1`, and a file's
  round is fixed before round `i` reads it. The minimum therefore
  depends on no thread order.
- The round travels as `Closure::round`, then `Resolved::file_round`,
  then `mortar_core::Resolution::file_round` (`Box<[u32]>`; empty from
  `Resolution::empty`). The capture's `FileCols.round` writes it into
  `FILES.round`.
- `capture::file_round` refuses, on every capture, an `Extracted` file
  of round 0 and any other file with a round. When it refuses, no state
  is written.
- `META.iterations`: `Resolution::iterations` comes from
  `Resolved::iterations`, and the capture writes it (it refuses 0).
  Before this, no capture wrote it (the `rows.rs` default was 0; the
  format-4 bridge set 1), so `extract`'s `closure-iterated` fall-back
  never fired on a real state. **Owed (ruling item 3):** the value is
  the last stage's. It must be the MAXIMUM over the stages, so that an
  iterated `--as-needed` stage is not lost.
- The state `VERSION` goes from 6 to 7. A version-6 state holds round 0
  for every extracted member and is refused (`state-version`), never
  read as `--whole-archive`.

## The check
- The canonical form (`state5/canon.rs`) still sets the round to 0, for
  WP-214's reason. An update keeps rounds that are supported but not
  breadth-first (review-wp207 M-1, R2-1), so canonical equality cannot
  compare the value.
- The support property is checked by an independent walk over the
  stored `KEY_REFS`, in `crates/mortar/tests/rows_round.rs`.
- `extract`'s `Ctx::facts` answers `state-corrupt` for a member that the
  update's changed row has as lazy, whose stored row is not `LAZY`, not
  `GONE`, and of round 0. This check is a MODEL-LEVEL guard only
  (ruling item 2). On a real update the join's adapter copies the
  stored round into the changed row (`crates/mortar/src/update/
  changed.rs:124`), so the check cannot fire there. The real guards are
  the capture's write-time refusal, `VERSION` 7, and the state's
  integrity checks.

## F-7, from the bytes
- **The 253 x86-64 members** stored with flags `0x1` and no rows are
  objects WITHOUT a `.symtab`. `readelf -S` of libstdc++'s `tinfo2.o`
  shows 7 section headers (null, `.text`, `.data`, `.bss`,
  `.note.GNU-stack`, `.note.gnu.property`, `.shstrtab`). Of
  `libm-2.41.a`'s members, 119 have none (for example `w_exp_compat.o`,
  6 headers).
- **Why AArch64 has none:** its `tinfo2.o` has a symbol table.
- **The cause:** such a member has no mention, so no edge reaches it
  and it is never extracted. But `capture::file5`'s early return gave
  `File5::default()`, whose `lazy` is false, so the member was stored
  without `LAZY`.
- **The fix**, in the same producer: the early return gives
  `lazy: !live` and `object_flags`. After it, all 253 members (263 on
  AArch64) without a mention are `LAZY`.

## Proposed for IN-71b (the supervisor places it in the spec commit)
"The full link's capture writes each extracted lazy member's round
(resolve.md §4.1's closure: one more than the least round of a file
with an edge to it, a root counting as round 0, so at least 1) and 0 for every other file, from
the closure's own walk. It writes `META.iterations` as the closure's
iterations (the maximum over the stages). A capture whose rounds break
this writes no state."
