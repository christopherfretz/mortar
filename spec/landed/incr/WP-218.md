# WP-218 (U-6): refill, image, and the update's map

The update's image (`spec/incr.md` IN-75) and its map (IN-75, IN-79 (b),
`spec/image.md` I-78a, `spec/plumb.md` §3.2): `mortar_image::update::refill`
and `mortar_image::map::update_map`, and the decision records every
incremental-mode map now carries. Base a828a3de.

## A. What refill does (IN-75)

`refill(link, layout, symtab, set, previous)` (and `refill_counted`, the
same with its [`Counts`]) returns sorted, disjoint dirty ranges and their
bytes; an empty delta returns none. In order:

1. Every input rechecked (the store's `fstat` against the file it read);
   a difference is `input-changed` (`path: error`). Again after the fill.
2. The previous section header table read from the previous output, the
   new one from the placement; a class, count or name difference is
   `update-not-implemented (image)`.
3. The moves of the growth steps (`Shift`): the sections whose address or
   offset changed, and the address map of the previous output's
   allocated sections.
4. `.eh_frame` walked (only when U-4 gave `layout.eh` or a section moved),
   BEFORE any byte is written (U9 before W1): any pointer encoding but
   0x1b/0x9b is `update-not-implemented (eh)`. A code section of a file
   whose `.eh_frame` range is not rewritten that is in `moved` is `(eh)`
   too (its FDEs' old target is a stored row, not an input of refill).
5. Moved sections' bytes copied from the previous output.
6. The image fills: the units and chunks of the set, the sections of
   `layout.files`, moved and revived sections, the holes of `hole_chunks`,
   fragments with references, the slot chunks when slots changed, the
   rewritten `.eh_frame` ranges (or the section) and `.eh_frame_hdr`
   whole, every synthetic chunk that can hold a moved address when
   anything moved, the gaps around moved sections, the grown tails, and
   the header chunks (ELF header, both header tables) whole.
7. The unchanged `.eh_frame` records moved (IN-34a "pad and move"): each
   FDE's `pc_begin`, LSDA and each CIE's personality re-targeted through
   the move map, from the previous output's bytes alone (WP-239 R-3).
8. `.symtab`/`.strtab` from U-5's plan: moves, remapped values (shndx 0,
   >= 0xff00 and `STT_TLS` not remapped), fillers, entries, names.
9. The build id: the tree of I-76 over the whole new output (the previous
   output overlaid with the writes, the note zeroed), written in the note.
10. Ranges whose bytes equal the previous output's are dropped.

The new output's size: `mortar_image::update::output_size(link)` (the end
of the last in-file chunk); U-7 takes it as `Pair::size`.

## B. The map

- Every incremental-mode map (a full link's included) carries the
  decision records of I-78a after the `hole`/`dead` lines: `region`,
  `capacity`, `order`, `slot`, `redirect`, `frag`, and `common`'s fifth
  field. A plain map does not change by one byte
  (`i78a_plain_map_unchanged`, the static-identical gate).
- `update_map(link, layout, symtab)`: the full link's map of the update's
  placement, `incremental`, the `hole .symtab`/`.strtab` lines of the
  plan's slack, `dead .strtab <off> <size> strings` of its dead names,
  and the `symblock` of every block the plan places. A default plan
  leaves the full link's lines.
- `frag`'s class is `<flags>,<entsize>,<align>` with `flags` =
  `SHF_MERGE` (+ `SHF_STRINGS`) and `align` in bytes (finding F-4).
- `delta cause` lines: no rule defines them (IN-79, WP-213 §J); none are
  written.

## C. Findings (for the supervisor's ruling)

- **F-1 refill has no stored layout.** `refill` and `update_map` take a
  `LayoutDelta` but no `StoredLayout`, so they cannot call
  `place_of`/`holes_of` for a section outside `layout.files`. Both read
  `link.layout.placement` as the join's MATERIALIZED `P_U` (every place
  filled). `update_map` cannot state the `symblock` of an unchanged
  file's block (the stored `SYMTAB` rows are not passed). Alternative:
  an extra `stored: &StoredLayout` argument.
- **F-2 the build id is O(output).** IN-75 says the leaves of unwritten
  blocks are the state's (`LEAVES`); refill has no `LEAVES` input and
  hashes the whole new output (`Counts::build_id_read`). Proposal:
  leaves in, new leaves out.
- **F-3 image granularity.** The image fills whole jobs (`IMAGE_BLOCK`
  windows); a small edit fills its window, the dirty ranges are cut to
  the bytes that differ. On the test fixtures one window is the whole
  output (`filled` = output size).
- **F-4 `frag`'s alignment.** I-78a does not say whether `<align>` is log2
  or bytes; bytes are written (the stored class has log2).
- **F-5 regions** are derived from the Fill holes of body chunks
  (members keyed (file, category), skipping members of another output
  section placed beside a neighbour, L-159). They must agree with U-2's
  `REGIONS`; folded sections are not handled.
- **F-6 `.eh_frame` who-has-what.** Moves come from the section tables;
  the padding CIE is written by the image's `EhPlan` (the join builds it
  from `EhLayout`); `.eh_frame_hdr` is filled whole from the image:
  O(`.eh_frame`). On a real link (kiln++): `.eh_frame_hdr` 156,948 B,
  `.eh_frame` 1,336,152 B, `.text` 16,071,012 B, rewritten on every
  update that touches `.eh_frame`.
- **F-7 a changed file's FDEs.** refill rewrites `.eh_frame` only where
  U-4's `EhLayout` says; a changed file whose code moved inside its own
  sections needs its range in `layout.eh` (the growth test gives it).
