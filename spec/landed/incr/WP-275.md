# WP-275: the state-format change for phase B, in ONE VERSION bump (DESIGN)

A design record of stored state. It changes no code. Base 1bfce906
(main 2064dd12 plus WP-267 P-1c), branch `wp/275-state-format`. The
brief's five data, by the brief's numbers:
1. the update's `.symtab` plan from rows (255e5);
2. the chunk -> (file, region) index (255e4 rulings items 4/5);
3. WP-270: packed chunks' members (`Why::Packed`);
4. 255h: a `RESOLVED` row in a merge section -> its `FRAGS` fragment
   and offset;
5. R-8: `RESOLVED.facts` written by the update itself.

Status of each number: **measured** (with its source) or **estimate**
(with its model). The verifier is named through `spec/plumb.md` only.

`seq` is a position key with gaps (the capture writes `k << 32` for the
k-th unit of a chunk in offset order; an update inserting between two
rows takes their midpoint, IN-18e's rule for `FILES.rank`; no midpoint
left: compaction). No row holds an offset: a unit's offset is read from
its `REGIONS` or `SECTIONS` row, so a growth step (which shifts offsets
and keeps the order) rewrites no `CHUNK_UNITS` row.

Not new rows, answered in this record: WP-274's D-14 (a merged chunk's
fragments) is a carry (`LayoutDelta::frags` plus the changed files'
pieces), because no fragment of an unchanged file ever moves (IN-72
item 6); see §2.6.
