# WP-255c2b: the clip's section list from one producer, the gap rule, merged chunks

Base 5799e5d7 (`int/batch-17`). Rulings "After 255c2a" item 2 (i)-(iii),
"After 255c3" items 1-2. Design: `spec/landed/incr/WP-255.md` §9.1.

## What was built

- `clip_plan::sections_in(rows, members, chunk, range)`: every placed
  input section of `Body` chunk `c` that meets `[a, b)` (chunk offsets),
  in offset order. Where each one is and its size come from `Rows::place`
  and `Rows::section_size`; WHICH sections a chunk has comes from the
  narrow index `Members` (below). O(log members + members met): a binary
  search over the index, each visited member checked against the rows
  (placed in `c`, in order, disjoint). `frags_in` is its twin for a
  `Merged` chunk.
- `for_clips(rows, clips, members, front, parts)`: the caller no longer
  passes `sections`. It passes the index and `front`: the bytes and
  relocations of a section the function returned (`SectionFront`, keyed by
  `(SectionId, (chunk, offset))`); a section `front` cannot supply, or
  supplies at another size, is `internal-error`, not an omission.
- **The gap rule** (always on, before any row is made; O(members and
  fragments under the clips)). Inside a `Body` or `Merged` chunk, every
  gap that meets a clip between consecutive items (before the first, after
  the last up to the chunk's size) must be explained exactly: from the end
  of the previous item, holes that start exactly there (each one ending
  where the next starts or within the gap), then the next item at the
  end of the last hole rounded up to the next item's alignment (`n ==
  align_up(p, align)`, stricter than "smaller than the alignment"); the
  chunk's tail after its last item needs no padding (alignment 1);
  `[size, capacity)` is the slack, the same `Chunk::capacity` that
  `pad_views` reads. Anything else is `internal-error (image: clip byte
  {offset:#x} written by no row)` at the first unexplained byte in the
  clip, and `for_clips` returns `ClipError::Internal` (255e: the named
  fall-back `(image)`).
  The region slack of an incremental-mode link is NOT a `Chunk` field: it
  is the placement's `Fill` holes, one right after each member that has
  slack (the C++ link's `.rodata`: `Input`, `Fill` hole, `Input`, ...).
  This is why a hole has to start EXACTLY where the previous item ends: a
  first version that allowed less than the chunk's alignment of padding
  before a hole let a 13-byte member be dropped unseen (it lay between two
  holes).
- `Merged` chunks (`NotYet::Merged` removed): a clip that meets a merged
  chunk gets the whole plan's row there (one `Merged` unit, the fragment
  order's chunk index and the output section's name, from the index) and
  the `merge_source` of every section a fragment in the clip is copied
  from (`ClipParts::merge_source`, the caller's). The fill still reads the
  fragments through `Image::merged` (the order and split), as for the
  whole plan; the gap rule runs over the index's fragments.
- `link.rs` (test path, beside 255c2a's): `clip_members(link)` (the
  index of a full link: `from_layout`'s member rule `is_member` +
  `member_front`, the input header's `sh_addralign`; the merged chunks
  from `order.chunks`/`order.order` and `layout.merge`), `clip_model`,
  `refill_clip_plan_with(link, ranges, members_edit, edit)` (the drop
  hook; `refill_clip_plan` calls it), `clip_sections_for_test`,
  `clip_frags_for_test`.
- `layout_plan.rs`: the body of `merged()`'s per-section loop moved,
  unchanged, into `pub(crate) fn merge_source(m, s)`; `merged()` calls it
  (the `continue`s became `return Ok(None)`).

## The index a state must store (for the supervisor's ruling)

`Members` is what `sections_in`/`frags_in` read besides `Rows`:

| datum | for | the state's source (255e; assumed, not built) |
|---|---|---|
| per in-file `Body` chunk, the member `SectionId`s in offset order | which sections a clip meets | a by-chunk table over `SECTIONS` rows (kept, placed, live, not folded, with file bytes); `StoredSection` has the place, not the per-chunk order: a stored table (or a sort at load, O(sections)) |
| each member's alignment | the gap rule | the input header's `sh_addralign` (not in `Rows`; `StoredSection` holds `sh_flags`/`sh_type`: one more column) |
| per merged chunk, its fragment order index and output name | the `Merged` row | `CHUNKS` + `OUTSECS`, and the position of the chunk's output section in the fragment order's chunk list (`Order::chunks`, by `out`): stored or derived, not verified |
| per merged chunk, every placed fragment in offset order, with its section, size and alignment | the fragments a clip meets, the gap rule, the merge sources | the fragment table (`Rows` gives place and liveness, not section, size or alignment) |
| the holes of the chunks a clip meets | the gap rule | `HOLES` (already in `ClipParts`) |

## The residue of the gap rule (ruling 2(iii))

A member D dropped from the index is NOT seen when, after removing it, the
next item is still exactly where the previous item's end (past its holes)
rounded up to the next item's alignment puts it: D lies wholly inside the
padding the next item needs anyway, and no slack hole follows D.
**Bound: D's size plus its own leading padding is less than the next
item's alignment, so D.size < align(next) <= the chunk's alignment**
(and the same for a dropped fragment, under the next fragment's
alignment). Shown by `RESIDUE` (a 4-byte `.text.b`/`.data.b` before a
64-aligned member): the clip plan is built, and its bytes differ from the
whole plan's in exactly D's bytes (trap or zero where they were). On the
C++ link 1 of 1292 (AArch64) and 1 of 1424 (x86-64) members are in the
residue, each 1 byte. What sees it: the rows-equal test in the lane, and
in production IN-79's judgements (the ruling's name; I did not read or
run `mortar_plumb`). A per-chunk count or checksum of members in the
state would close it, at O(members of the chunk) per clipped chunk.

## Tests (`crates/mortar/tests/clip_plan.rs`, AArch64 and x86-64)

- `clip_sections_equal_the_whole_plan`: for every body chunk of U-6's
  fixtures (pad 0 and 0x3000) and of a static C++ link (`-O1
  -ffunction-sections -fdata-sections`, libstdc++ and libc: 13/12 body
  chunks, 1292/1424 sections), `sections_in` over the chunk's whole range
  and 24 random sub-ranges equals the whole plan's `Input` units there,
  section for section with their ranges; then one clip over every body and
  merged chunk at once (15 chunks, 2/3 merged on the C++ link) passes the
  gap rule and fills `refill_ranges`' bytes.
- `clip_plan_refuses_a_missing_section`: on the C++ link one member
  dropped from the index in the exec `.text` chunk and in a non-exec chunk
  (`.rodata`) is refused at the member's first byte; every member's drop
  is classified (refused or residue, above); then `RESIDUE`.
- 255c2a's two tests, extended: b.o gains `.mycst` (a merge section of
  its own output section, two 8-byte constants); the cases add clips
  inside, across the edge of and covering the merged chunk of `.rodata`
  (the strings and b.o's `.rodata.cst8`) and `.mycst`: rows equal, bytes
  equal; one fragment dropped from each is refused at its first byte. The
  test's `View::Merged` resolves the plan-local index (the fragment
  order's chunk and the name).

## Not built (`NotYet` stays)

`Synth`, `Relocatable`, `Patches` and `EhFrame`: Milestone 3 was not
started (budget). For `Patches` the data `Rows` lacks is the patch
islands' contents (`PATCHES` rows: each patch's kind, target and place);
for an input `.eh_frame` placed in a body chunk, the `.eh_frame` plan's
pieces (the `eh_sections` rows), neither verified.

## A plain link pays nothing

`for_clips`, `sections_in` and the gap rule are reached only from
`refill_clip_plan` (a test path). `from_layout`'s path changes by one
function boundary (`merged()` calls the moved `merge_source`).
