# WP-255c2c: the clip plan's `Synth`, `Patches` and body `.eh_frame` arms

Branch `wp/255c2c-clip-synth`, base `int/batch-23` (eb4db957). The
clip plan (`crates/mortar_image/src/clip_plan.rs`, `for_clips`) now plans
the synthetic chunks every taken lane hop dirties, the patch islands, and
an input `.eh_frame` in a body chunk. Inside the clips its bytes are the
whole plan's bytes.

## Design

### What the clip plan does with a synthetic chunk

A synthetic chunk is ONE row of the whole plan, `Unit::Synth`
(`layout_plan.rs:248-259`). Its bytes come from the chunk object at fill
time, `fill.rs:506-525`: `chunk.write(range)`, then the `.eh_frame`
relocations, then the build id's descriptor set to zeros. The plan holds no
bytes for it, only the index of the chunk object in the list the fill is
given (`Image::chunks`, `fill.rs:182`). So the clip plan does not write
these bytes. It routes them:

- For a chunk a clip meets, it emits the whole plan's row:
  `SynthUnit { chunk, id, name, whole, eh }`, at the chunk's whole extent.
- The row data comes from a new `ClipParts::synth`: chunk id to
  `(SynthKind, SynthRow)` (`clip_plan.rs:153`).
- In the full link this map comes from the whole plan's `Synth` units
  (`link.rs` `refill_clip_plan_with`). In an update it comes from the
  chunk list that the update's `Image` fills with.
- Then the fill writes the chunk's bytes over the clip, as it does for the
  whole plan.
- A chunk written whole (`Division::Whole`, I-104) is widened by
  `clip_jobs` to the whole row. This is unchanged.

The planned kinds are `clip_plan::PLANNED` (`clip_plan.rs:177`):
`.symtab`, `.strtab`, `.symtab_shndx`, `.eh_frame`, `.eh_frame_hdr` and
the build-id note. Any other synthetic kind under a clip, or a synthetic
chunk the map does not hold, is `NotYet(Synth, chunk)`. That covers
`.got`, `.got.plt`, `.plt`, `.rela.plt`, `.shstrtab`, `.comment`, the
property note, `.mason_meta`, `.gdb_index` and the dynamic chunks. The
check is `synth_row`, `clip_plan.rs:498`. A planned kind whose name is not
the chunk's name is an internal error: the caller's map is not this
placement's.

### Notes on each arm

- **A body `.eh_frame` cannot be built today.**
  - Resolve gives every section named `.eh_frame`, and every
    `SHT_X86_64_UNWIND`, the kind `EhFrame` (`mortar_resolve/src/sections.rs:205-207`).
  - `SectionKind::is_placed` excludes `EhFrame` (`mortar_core/src/resolution.rs:254-258`).
  - So no member list holds one, in the full link (`is_member`) or in a
    stored index (same rule).
  - The old refusal (`clip_plan.rs` before this package) was therefore
    dead. It is removed: if a later rule placed one, the clip plan would
    make the whole plan's row with the same maker.
  - `NotYet::EhFrame` and `NotYet::Patches` stay in the enum, documented
    as no longer produced.
- **What is not the clip plan's.** Building the chunk objects (the
  `SymtabPlan`, `EhPlan`, `HdrPlan` and `BuildIdPlan`) from state rows for
  an update belongs to whoever builds the update's `Image` (255e2, then the
  join's package). The clip plan only needs their index in that list.

### Needs a ruling (shape)

- **R-c1: `ClipParts` gains four fields** (`clip_plan.rs:146-172`):
  `synth`, `eh_sections`, `patches` and `sealed`.
  - It is not a new type: `ClipParts` is constructed only in
    `link::clip_plan_of`.
  - Each field is a debt of the update's `Image` builder, with a named
    state source:
    - `synth`: the update's chunk list, plus `CHUNKS` rows of tag
      `Synthetic` (WP-255 §9.5 #10);
    - `eh_sections`: `LayoutDelta.eh` and `StoredLayout::eh_range_of`,
      plus the fronts' tables;
    - `patches`: `PATCHES` rows plus `value::<R>`;
    - `sealed`: `META.sealed_start` and `META.sealed_end`.
- **R-c2: an `.eh_frame` section left out of `eh_sections` is a
  relocation that is not applied, and nothing sees it.**
  - `eh::relocate` skips a kept record whose section `Plan::eh` does not
    list (`eh.rs:55`, `continue`).
  - Test `an_eh_section_left_out_is_not_seen_by_the_fill`: drop one
    section and fill the whole `.eh_frame`.
    - AArch64: first difference at file offset 0x1294, clip 0x00, whole
      plan 0x3c.
    - x86-64: at 0x1298, clip 0x00, whole plan 0x48.
    - In both cases it is the FDE's `pc_begin`, left at the input's zero.
    - The fill gives no diagnostic.
  - In the full link this cannot happen, because `eh_sections` lists every
    live section with relocations. In an update it is a wrong byte if the
    caller's producer misses one.
  - Proposed rule for `spec/image.md`: "In a clip plan, every kept
    `.eh_frame` record that a fill piece meets, whose input section has
    relocations, has its section in `Plan::eh`. A record whose section is
    missing is `internal-error (image: .eh_frame record at {offset:#x}:
    its section's relocations are not in the plan)`, never skipped."
  - Its check belongs in `eh::relocate`, behind a "has relocations" bit in
    the `EhSource` frames. That is not this package's file, so it is not
    built.

## What was built

- `clip_plan.rs`:
  - the `Synth` arm: `synth_row` and `synth_rows`;
  - the `Patches` arm: one `Bytes` row through `fixed`, which is the old
    `structural` with the map as a parameter;
  - the body `.eh_frame` refusal is removed;
  - `PLANNED`;
  - the new `ClipParts` fields;
  - `Plan::sealed` is set from `ClipParts::sealed`.
- `layout_plan.rs`: `eh_part`, a pure move out of `eh_sections` (the same
  checks in the same order).
- `link.rs`:
  - `clip_eh_sections`;
  - `clip_plan_of` takes `synth` and `sealed`, and builds the patches'
    bytes (`patches()`) and the `eh_sections` closure;
  - `refill_clip_plan_with` builds the clip plan inside `with_image`. The
    synthetic rows are the indices of the whole plan's `Synth` units,
    because the fill's chunk list is `with_image`'s.
- The plain link's path changes only by `eh_part`'s function boundary.

The tests are in `crates/mortar`, not `crates/mortar_image`: they need a
`Link`, and only the driver (`mortar::front`) makes one.

## Not done

- **The holes a real update leaves**, from `update_two_front.rs`'s
  fixtures with a `FrontRows` built from front 2 in a test.
  - Front 2's `Link` exists only inside `crates/mortar/src/update`
    (`shadow_255e`), which is not this package's.
  - A test cannot make one without a hook there, such as a
    `#[doc(hidden)]` function that runs front 2 for a test.
  - 255e's S2 already runs `for_clips` over front 2's rows on every taken
    lane hop, but it leaves out the synthetic chunks.
  - Proposed: 255e2, or the supervisor, removes the skip in
    `shadow_255e` (`update/mod.rs`, the `synth` list and the `skipped`
    branch). S2 then judges the synthetic arms on real hops.
- **An input `.eh_frame` in a body chunk** is not tested: no link can make
  one (see the Design notes).
