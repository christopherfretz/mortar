# WP-023 — `mortar_arch` and `mortar_a64`

`mortar_arch` is the trait and vocabulary of `spec/arch.md`. `mortar_a64`
is its AArch64 instance (`spec/a64.md`). This record covers stage A: the
pure functions and the writers. Stage B is `scan` in full, the
relaxations of §8, IRELATIVE, static TLS, and the need functions.

## Deviations from `spec/arch.md`, to be reflected there

- **§3.7 `erratum_sites`** takes `&Code` (bytes, address, proof runs)
  and returns `Result<(), Unproved>`. The spec's signature has no way to
  give the proof, or to report the condition-5 refusal.
- **§3.7** has no writer for the ADR fix or for the `b patch` at `F`. They
  are the free functions `mortar_a64::erratum_adr` and `erratum_branch`.
- **§3.5** `ScanError::Internal` was added, for a class outcome the table
  calls impossible.
- **§3.5** `field_window` gives a marker (`Field::None`) the window the
  howto names, so that a TLSDESC_CALL overlapping another field is
  caught.
- **§3.6** `Records` is implemented for `&[Reloc]` and `Vec<Reloc>`.

## Decisions and readings of `spec/a64.md`

- **§3.1:** values are computed in wrapping `i64` arithmetic, not
  mathematical integers. Every check is at most 48 bits wide (s(33) for
  ADRP), and the inputs are 64-bit addresses and addends, so a wrapped
  value never passes a check that the mathematical value would fail.
  The exception is `Unchecked` 64-bit data, where the two are equal mod
  2^64.
- **§3.2:** the `mov/k` masks admit `opc = 01`, which is unallocated.
  `requires` does not reject it, because AAELF64 lets a MOVW_*_NC
  relocation sit on any MOVZ/MOVN/MOVK.
- **§5 `tls_local`** is `local` or `abs`.
- **§6.1 status gating:** `classify` refuses a row whose status is above
  `A64.max`. `A64::M1` is the shipped value, and tests use `M2`.

What the "not compared" columns mean:

- **relaxed:** the reference rewrote the instruction (IE → LE; GNU ld's
  `nop` for some GOT loads). M1 applies IE unrelaxed, which mold confirms
  (3539 ok); R3 is stage B.
- **ifunc:** the target is an `STT_GNU_IFUNC`. The IPLT is stage B.
- **doc:** a difference the spec already records:
  - GNU ld's weak branches (§7);
  - mold's R1 order, `nop; nop; movz; movk` (§8.1);
  - mold's ADRP against `weak0`, which addresses page 0.
- **emit:** the emitted record does not describe the field, so it is
  not compared:
  - lld's records against section symbols, and lld's records in
    `.eh_frame`, which lld rewrites;
  - lld's and mold's records whose symbol was dropped (index 0).

  GNU ld and mold agree with mortar on the same inputs.
- **refused:** a TLS reference to an undefined weak symbol (§7). See the
  first spec error below.

### (ii) 843419 against GNU ld 2.44 and lld 22

The input is 640 generated sequences, one per page. The sequences vary:

- the start offset: FF8, FFC, or the non-site offsets FF4 and 000;
- the form: 3 or 4 words;
- the second word: 12 load/store groups and 2 words outside them;
- the third word: 5 kinds;
- the final word: 9 kinds, 6 of them sites;
- data: 162 sequences have one or all words written as `.word`, which
  gives them `$d`.

Each linker linked the input with and without the fix, and the fixed
sites were read off the difference. mortar ran over the unfixed image,
with the proof from the image's mapping symbols.

| reference | fixed by it | mortar sites | missed by mortar | mortar only |
|---|---|---|---|---|
| GNU ld | 177 (134 patches, 43 ADR) | 214 | 0 | 37 |
| lld | 147 (147 patches) | 214 | 0 | 67 |

No mortar site has a word in a `$d` range, and neither reference fixed
one.

### Performance

`cargo run --release -p mortar_a64 --example apply_bench`, on one thread:

- 2^20 relocations with a static-C++ mix: **59.6 M relocations/s**;
- 2^22 relocations: **57.2 M/s**;
- machine load average during the runs: 29.4 on 24 CPUs (shared host).

`apply` does not allocate and has no loops. Its branches are the
dispatch on class and form, and the error paths.

## Spec errors and ambiguities found

1. **a64 §7, "TLS classes: `E`" is wrong for static glibc.** glibc's
   `libc.a` references `_nl_current_LC_COLLATE` (and the other
   `_nl_current_LC_*`), which are `STT_TLS STB_WEAK STV_HIDDEN` and
   undefined. The references are `TLSIE_ADR_GOTTPREL_PAGE21` and
   `TLSIE_LD64_GOTTPREL_LO12_NC`, guarded at run time by a test of
   `_nl_current_LC_COLLATE_used`. The corpus had 100 such records per
   linker.
   - GNU ld keeps the IE pair, and its slot holds `TPREL(0)`
     (`0 − tls.start + 16`). lld and mold link the same inputs without
     complaint.
   - With §7 as written, mortar refuses every static C link that pulls in
     the locale code (all of the corpus's C and C++ links). This blocks
     M1.
   - Proposal: for `weak0`, IE takes a slot holding `TPREL(0)` (that is,
     `S = 0`), with no refusal. LE and the other TLS classes stay `E`.
   - The refusal is `mortar_a64::WEAK_TLS`; the decision belongs to the
     spec owner.
2. **a64 §14, row "TLSDESC in exec", mold column:** "→ IE (nops first)"
   is wrong for a static link. mold writes LE, `nop; nop; movz; movk`.
3. **a64 §7 and §14** do not mention that mold resolves ADRP against
   `weak0` to page 0 (§7 has `S = P`, as GNU ld and lld do).
4. **a64 §6.1, 570 and 571** are M1, but no producer or reference linker
   handles them. Either mark them `later`, or accept them with only
   unit-test coverage. Stage A accepts them.
5. **arch §3.7 erratum signatures:** see the deviations above.
