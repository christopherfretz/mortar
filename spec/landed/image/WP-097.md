# WP-097 — `--gdb-index`: a complete index, or the link refused by name

`--gdb-index` now writes a `.gdb_index` section (version 7). The rules
are `spec/synth.md` §17 (S-G1 to S-G9), taken from WP-080 stage B's
proposal (`spec/landed/image/WP-080-stage-b.md` §4). gdb trusts the
index it is given: a name the index leaves out is a name gdb does not
find. So mortar writes the index only when every unit with debug
information has its GNU name sets, and otherwise refuses the link,
naming the object (`gdb-index-incomplete`). lld and mold write the
incomplete index without a warning.

Tools: GCC 14.2; Clang 19.1.7 and 22.1.8; kiln++ with hod 1.0.0; lld
19.1.7 and 22.1.8; mold 2.37.1; gdb 16.3 (with its `gdb-add-index`);
lldb 19; readelf 2.44; llvm-dwarfdump 22. The host is AArch64, and the
other two architectures use the cross toolchains and qemu.

## 1. What is written

- **The chunk.** It is S-3 row 28: `.gdb_index`, `SHT_PROGBITS`, not
  allocated, alignment 4. It is placed after the `.debug_*` sections.
- **The CU list.** It holds every unit of every live `.debug_info` input
  section, in output order. Type units, partial units, DWARF64 units and
  `.debug_types` are refused by name.
- **The address area.** It is built from each root DIE:
  - the forms read are `low_pc`/`high_pc`, `DW_AT_ranges` into
    `.debug_rnglists` (by offset or `rnglistx`) or `.debug_ranges`, and
    `.debug_addr` through `addr_base`/`GNU_addr_base`;
  - every address is read through its relocation;
  - empty ranges are left out, and so are ranges whose section is not in
    the output: a discarded COMDAT copy, or code that `--gc-sections`
    collected.
- **The symbol table and the constant pool.**
  - The names come from `.debug_gnu_pubnames` and then
    `.debug_gnu_pubtypes`, in CU order. Each name is held once.
  - Each CU vector is sorted and unique.
  - The table size is `max(1024, the smallest power of two above
    ⌊4N/3⌋)`, and names are placed with gdb's hash and probe.
  - The input sets are consumed: they become `Dropped(Consumed)` and are
    not copied (S-G6).
- **The refusals:**

  | name | when |
  |---|---|
  | `gdb-index-incomplete` | a unit with debug information and no GNU pubnames or pubtypes set |
  | `gdb-index-type-unit` | a type unit, or `.debug_types` |
  | `gdb-index-malformed-unit` | a unit, range list or address that cannot be read |
  | `gdb-index-malformed-name-set` | a name set that cannot be read |
  | `gdb-index-orphan-name-set` | a name set whose unit was dropped |
  | `gdb-index-too-large` | 2^24 units or more, or a section of 4 GiB or more |

  `INCOMPLETE` in `mortar_synth::gdbindex` is the one switch for the
  supervisor's ruling. It is set to refuse.
- **The options.**
  - `--no-gdb-index` and `--no-debug-names` are no-ops, and the last of
    `--gdb-index` and `--no-gdb-index` wins.
  - `--debug-names` stays refused. Its diagnostic gives the reason: gdb
    16 ignores a `.debug_names` it did not write.
  - `--gdb-index` with `--incremental` follows IN-12, as IN-58 always
    said: a warning, then a plain link with the index and no state
    file. With `--incremental=update` it is an error. The brief
    described this case as "refused"; the existing IN-12 behaviour is
    what ships, and `spec/synth.md` S-G8 now says so.
  - With `-S` or `-s` no index is written.

One rule changed while testing. Clang 22 writes an empty name (`""`) for
the unnamed `DW_TAG_variable` of a string literal. lld and mold index it
as an empty name. mortar first refused it as a malformed set; it now
indexes it as they do.

through the verifier (L3).

**`--gc-sections` and the dead-unit rule (S-G5a).** `unused_fn` is
collected, so its range is left out, but its name stays in the index.
This is checked in `gdb-index-gcc.test`, `gdb-index-clang.test`,
`gdb-index-pubnames.test` and `gdb_index.rs`, which also compares these
outputs with lld's and mold's.

**A COMDAT function kept from another unit.** `twice<int>` is defined in
units 0 and 1. Its CU vector names both units, as lld and mold do, and
only unit 0's range is in the address area (`gdb_index.rs` checks the
vector `[0, 1]`).

## 3. Against lld and mold

`crates/mortar/tests/gdb_index.rs` covers three architectures and eight
forms, each plain and, for the `-O0` forms, with `--gc-sections`: 36
comparisons in all. It reads all three indexes with its own reader,
which shares no code with mortar's writer, and requires each of these to
be equal between mortar and each reference:
- the CU list's lengths;
- every unit's ranges, compared by length;
- every name and its CU vector.

mortar's own index must also pass these checks:
- gdb's probe reaches every name from its hash;
- every vector is sorted;
- the size follows the rule in §1;
- readelf and llvm-dwarfdump read it without a warning.

All 36 comparisons are equal, apart from these differences:

| difference | lld | mold | mortar | why it is right |
|---|---|---|---|---|
| a value repeated in one name's vector | written (`ns::OnlyInC 2:1 2:1`: GCC's pubtypes names the struct from two DIEs) | once | once | `gdb-add-index` writes each value once (`tests/gdb_add_index.rs`); gdb's lookup is a set |
| slots | 1024 | 64 for 34 and 37 names | 1024 (the size rule in §1) | gdb accepts any power of two; mortar's rule is gdb's own writer's (2048 for 1303 names in the fixture) |
| alignment | 1 | 4 | 4 | gdb reads u32 fields |
| Clang `-gsplit-dwarf -gpubnames` | empty symbol table (lld 19 and 22) | empty symbol table | refused, with a note naming `.debug_names` | stage B's "30 symbols" did not reproduce with these tools; an empty table makes gdb miss every name |
| a unit without sets (mixed build) | indexed without its names | the same | refused at the object | stage B §2.1 and §4 below |

The kiln check was done by hand: kiln++ `-g -O1 -gsplit-dwarf` and
`-O2 -gsplit-dwarf`, three units, linked by all three linkers and dumped
with `.build/target-wp-097/notes/gisym.py`. mortar's index equals lld's
exactly, and mold's except for the slot count. gdb gives the same
`ptype`, `print`, `break` and `bt` answers with mortar's index and with
lld's.

`gdb-add-index` writes version 9 and builds its index from the DWARF
itself, not from pubnames. So it is a check of the format, not of the
content:
- it merges adjacent ranges;
- it spells base types its own way (`long` where GCC's pubtypes says
  `long int`);
- it lists `tl_count` in both units.

The fixture `crates/mortar_synth/tests/data/gdb-add-index-v9.bin` holds
its bytes for 1303 names (25 KB).

## 4. gdb with the index

- **The same answers, from the index.**
  `debuggers.rs::gdb_index_is_used_and_answers_the_same` runs on GCC and
  Clang `split-d5-O0` and `split-d4-O0`:
  - the full split sessions are run twice, on mortar's output with and
    without `--gdb-index`: breakpoints by line and by function, `bt`,
    `print`, `ptype`, `info scope`, `step` into another unit, and a
    catchpoint on a throw;
  - the gdb transcripts are equal, and so are the lldb ones;
  - with the index, `maint print objfiles` prints `.gdb_index: version
    7`;
  - without it, it prints `Cooked index in use`.
- **Stage B's failure case.**
  `debuggers.rs::gdb_index_of_a_mixed_build_is_refused` builds two GCC
  split units and one `-g` unit without pubnames:
  - on lld's `--gdb-index` output, gdb says `No symbol "ns" in current
    context` and `'g_only_c' has unknown type`;
  - without an index, gdb prints the type and `{a = 4, b = 2}`;
  - mortar refuses: `gm_c.cpp.o: unsupported feature:
    gdb-index-incomplete`.

gdb gave no wrong answer on any mortar index.

## 5. Cost

Measured on the AArch64 host (12 cores) on 2026-11-16. The machine was
shared, with a 1-minute load of 8 to 11. That inflates every wall time
alike, so compare rows within one workload rather than with stage B's
absolute numbers.

**Method.**
- Each link was run through `g++ -static -no-pie` (with `-B` naming the
  linker), with 1 warm-up and then 5 timed runs. The tables give the
  median wall time and the median peak RSS (`/usr/bin/time`).
- gdb 16.3 was run with `-batch -nx`, 1 warm-up and then 3 runs:
  - *start* is `-ex quit`; gdb waits for its index before quitting;
  - *bp* is `-ex 'break <function>'`.
- mold's RSS is not shown, because mold hands the link to a forked
  child that `time` does not see.
- Sizes are in MB (10^6 bytes).

**Inputs.**
- *syn-gcc* is stage B's 4000-unit input: the bench's `objects` shape at
  4000 × 200, as C++ (`.build/target-wp-097/notes/syn.py` ports
  `xtask/src/bench/synth.rs`), built with GCC `-O1 -g -gsplit-dwarf`.
  It was about 1.2 GB on disk with sources and `.dwo` files, and was
  deleted after the measurements.
- *protoc* is protobuf 3.21.12's protoc built as the bench builds
  `cxx-medium-g-static`, but with `-O0 -g -ggnu-pubnames`. The bench's
  plain `-g` objects carry no GNU name sets, so mortar refuses them
  (`gdb-index-incomplete`); lld and mold index their address ranges
  only.

**What the index costs.**
- **syn-gcc, link.** The index costs mortar +89 MiB of RSS, against
  +137 MiB for lld. Its wall-time cost (−0.09 s) is inside this loaded
  machine's noise; lld pays +0.15 s and mold +0.12 s.
- **protoc, link.** It costs mortar +0.05 s and +18 MiB.
- **Index size.** mortar's index is lld's size on syn-gcc. On protoc,
  lld's is 0.18 MB larger because of its repeated vector values (§3).
- **Output size.** The output still shrinks on protoc (−10.8 MB),
  because the consumed GNU name sets were 16.5 MB.
- **gdb.** With mortar's index gdb starts 10× faster and in a third of
  the memory at 4000 units: 0.40 s / 384 MiB, against 3.95 s /
  1135 MiB without an index on this loaded machine. This is the same
  gain lld's index gives (0.32 s / 384 MiB). On protoc gdb's memory
  halves.
- **Implementation.** As the brief asked, there is no optimisation beyond
  this:
  - the input files are read in parallel (`Pool::map`);
  - each name is held once, in the pool's bytes, and the sets are
    borrowed from the inputs;
  - the vectors are built by one sort of the (name, value) pairs;
  - placement is linear probing;
  - nothing is quadratic.

## 6. A link without the option pays nothing

- **Nothing runs without the option.** Phase 80 builds the plan only
  when `plan.shaping.gdb_index == Some(true)`. Resolution consumes the
  sets only under the same condition. No other code path changed.
- **Byte-identical lane (AArch64 host).** After merging main `ea9b94f`
  (WP-093's 898 links), every one of the 898 existing rows is unchanged.
  The 84 rows added are this package's four tests: 982 links of 221
  tests. The x86-64 rows were pasted from the hosted lane's printout
  (run 43867770098). That lane, too, reported only these 84 rows as
  differing, so none of the 898 existing x86-64 rows changed either.
- **Bench.** `cargo xtask bench --linker mortar` ran on all 13 static
  workloads, once with main `ea9b94f`'s mortar and once with this
  branch's, then twice more interleaved (three runs each). Results:
  - every output hash is the same on both sides, in every run, and for
    the ten dynamic workloads of the first run as well;
  - peak RSS is within 3 MiB on every row;
  - medians are noise in both directions. The host load was 8-11, and
    each side's fastest run sits within the other side's range. For
    example, `cxx-medium-g-static` at default threads gave 186-199 ms
    on main and 182-212 ms on the branch.
  - "REGRESSED (memory) synthetic-objects-static threads 1" is printed
    against the recorded baseline for main's binary too, so it is not
    this package's.
  - No bench workload with `--gdb-index` was added (the cost is in §5).

## 7. For WP-098 (the verifier)

The map needs nothing new (`spec/synth.md` §17.7). The verifier gets
everything it needs from records it already reads:
- the option, from `arg`;
- the output offsets of the `.debug_info` input sections, from `nplace`;
- the code addresses, from `place`;
- the chunk, from `chunk synthetic .gdb_index`.

Today's verifier already accepts these outputs. It found nothing in any
mortar output of the four link tests or of `gdb_index.rs`, including
the consumed pubnames sections and the new chunk. It does not judge the
index's content: `spec/plumb.md` still says `.gdb_index` is not judged,
and changing that text is WP-098's.

To judge the content, WP-098 must:
- re-read the name sets and range lists of the inputs;
- recompute the index from §17's rules;
- compare the result as a set, since slot order follows the size rule
  and the probe.

`gdb_index.rs`'s reader can serve as a model.

## 8. Not verified

- Type units (refused), `.dwp` inputs, and DWARF64 (refused).
- `--gdb-index` with `-r`, which is refused as a whole.
- Inputs with compressed debug sections: the reader decompresses through
  the input layer, but no test feeds it one.
- kiln on x86-64 and i386 (kiln is AArch64-only), and kiln in CI: the
  kiln check was by hand.
- gdb sessions off an AArch64 host.
- Scale beyond 4000 units, and `gdb-index-too-large` (2^24 units).
- Whether gdb accepts a version-7 index from mortar when an input also
  carries `.debug_names`: Clang `-gpubnames` is refused before that
  question arises.
- Cross-project: kiln++/hod write no GNU pubnames without
  `-gsplit-dwarf`, even with `-ggnu-pubnames`, so `--gdb-index` refuses
  kiln at `-O0` and every non-split kiln build. Asking hod to emit the
  sets is the way to lift this.
