# WP-026h — `mortar_digest`: SHA-1, SHA-256, `L128`, the build-id tree

Implements `spec/image.md` §8.2–§8.3 (I-69, I-70, I-72, I-73, I-114) as
the crate `crates/mortar_digest`: no dependencies, `forbid(unsafe_code)`,
no hardware instructions. Parsing `--build-id` and refusing `md5` (and
`uuid` in M1) stays in `mortar_cli`; reading `/dev/urandom` and writing
the note stay in `mortar_image`.

## API

```rust
// FIPS 180-4, one-shot and streaming.
pub const SHA1_LEN: usize = 20;
pub fn sha1(data: &[u8]) -> [u8; 20];
pub struct Sha1;   // new(), update(&mut self, &[u8]), finish(self) -> [u8; 20]
pub const SHA256_LEN: usize = 32;
pub fn sha256(data: &[u8]) -> [u8; 32];
pub struct Sha256; // new(), update, finish -> [u8; 32]
// I-114.
pub const L128_LEN: usize = 16;
pub fn l128(data: &[u8]) -> [u8; 16];
pub struct L128;   // new(), update, finish -> [u8; 16]

// I-72, I-73.
pub const IMAGE_BLOCK: u64 = 1 << 20;            // B
pub const TREE_TAG: &[u8; 18] = b"mortar-build-id-2\0";
pub enum TreeFn { L128, Sha1, Sha256 }           // leaf_len(), root_len()
pub const fn leaf_count(file_size: u64) -> u64;  // m
pub fn leaf_range(file_size: u64, index: u64) -> Range<u64>;
pub struct LeafHasher;                            // new(TreeFn), update(&[u8]), update_zeros(u64), finish() -> Leaf
pub fn leaf(f: TreeFn, data: &[u8]) -> Leaf;
pub struct Leaf;                                  // tree_fn(), hashed_len(), as_bytes()
pub struct LeafColumn;                            // new(TreeFn, file_size) -> Result<_, TreeError>,
                                                  // set(index, &Leaf) -> Result<(), TreeError> (any order),
                                                  // root() -> Result<Root, TreeError>, len, is_complete, …
pub struct Root;                                  // tree_fn(), as_bytes()
pub enum TreeError { TooLarge, Index, WrongFn, WrongLength, Duplicate, Missing, WrongRoot }
pub fn tree_root(f: TreeFn, file: &[u8], zeroed: Range<usize>) -> Root; // one thread, the reference

// I-69, I-70.
pub enum TreeStyle { Default, Fast, Sha1, Sha256 } // tree_fn(), id_len(), id(&Root) -> Result<&[u8], TreeError>
pub const fn uuid_v4(random: [u8; 16]) -> [u8; 16];
pub fn parse_hex(digits: &str) -> Result<Vec<u8>, HexError>; // the digits after `0x`
```

How the image uses it (I-33 step 4, I-73): one `LeafColumn` per link
(behind a `Mutex`, or leaves sent back to the coordinator: one `set` per
MiB); a worker makes a `LeafHasher` per window, feeds it the window's
bytes in as many pieces as it likes (the descriptor already zero, as the
synthetic chunk wrote it, I-107), and `set`s the `Leaf` at the window's
index. `set` checks the function, the index, that the leaf hashed exactly
`leaf_range`'s length, and that no window is set twice. After the last
job, `root()` and `TreeStyle::id` give the `L` bytes for the sealing
write. `tree_root` is the same function over a file in memory, for tests
and for `mortar_plumb` (R-8).

## Tests (`cargo test -p mortar_digest`)

- `tests/vectors.rs`: FIPS 180-4 / RFC 3174 vectors (empty, `abc`, the
  448- and 896-bit messages, RFC 3174 TEST4, one million `a` in one call
  and in 997-byte pieces); §8.4's `L128` and tree vectors; the styles'
  lengths and prefixes (`fast` = bare's first 8); `uuid_v4` bits; I-70's
  hex values.
- `tests/tools.rs`: SHA-1/SHA-256 equal `sha1sum`/`sha256sum` (coreutils)
  on random bytes of every length 0..=300 and of `2^20 − 1`, `2^20 + 55`
  and `3·2^20 + 7` bytes (one tool run over all files, through
  `mortar_testutil::run_with`; skipped with a note when a tool is
  missing, a failure under `MORTAR_REQUIRE_TOOLS=1`).
- `tests/streaming.rs`: pieces == one call for all three functions, at
  every split point of every length 0..=200, every pair of split points
  of 15 lengths around the 32- and 64-byte boundaries, byte at a time,
  random pieces up to 70 KB; `LeafHasher::update_zeros` == zeros fed.
- `tests/tree.rs`: leaves set in 12 orders (L128; 2 for SHA) each fed in
  random pieces, and by 1/2/3/8 threads from an atomic counter, give
  `tree_root`; flipping either of two bits of each of 300 bytes changes
  the id, except inside the zeroed range; bytes at every leaf boundary;
  the length (zeros of 11 lengths, all different ids); the style; every
  `TreeError` of `LeafColumn`; zeroed ranges clipped.
- `src/tests.rs`: SHA-256's `K` and `H0` re-derived from the primes'
  cube and square roots; the root depends on `n`, `B` and the leaves.
- `tests/l128_quality.rs`: avalanche (quick: 14,336 flips, mean within
  0.005 of 0.5, worst output bit within 0.03) and collisions (quick:
  2^14 counter leaves of 1 KiB, 20,417 sparse leaves). `#[ignore]`d full
  variants with E23's sizes (`--release -- --ignored`, under a second):
  118,272 flips, mean 0.5002, worst |p − 0.5| = 0.0041; 2^20 counter
  leaves of 4 KiB: 138 low-32-bit collisions (128 ± 11 expected), 0
  full; 81,857 sparse leaves: 0 collisions.

The whole suite takes about 4 s in a debug build.

## Measurements (`examples/digest_bench.rs`)

`cargo run --release -p mortar_digest --example digest_bench [MiB] [threads…]`;
1 GiB of splitmix64 bytes, 1 MiB leaves, disjoint leaves from an atomic
counter under `std::thread::scope`, AArch64 host (24 CPUs, shared), load
46. Best of 3 for `L128`, one run for SHA. Ids equal at every thread count.

| function | threads | time | aggregate | per thread |
|---|---|---|---|---|
| `L128` tree | 1 | 82.0 ms | 13.1 GB/s | 13.1 GB/s |
| `L128` tree | 2 | 42.5 ms | 25.3 GB/s | 12.6 GB/s |
| `L128` tree | 4 | 24.4 ms | 43.9 GB/s | 11.0 GB/s |
| `L128` tree | 8 | 19.0 ms | 56.4 GB/s | 7.0 GB/s |
| SHA-1 tree | 1 | 1.385 s | 775 MB/s | 775 MB/s |
| SHA-1 tree | 2 | 0.724 s | 1.48 GB/s | 742 MB/s |
| SHA-1 tree | 4 | 0.492 s | 2.18 GB/s | 545 MB/s |
| SHA-1 tree | 8 | 0.293 s | 3.67 GB/s | 459 MB/s |
| SHA-256 tree | 1 | 3.742 s | 287 MB/s | 287 MB/s |
| SHA-256 tree | 2 | 1.995 s | 538 MB/s | 269 MB/s |
| SHA-256 tree | 4 | 0.989 s | 1.09 GB/s | 271 MB/s |
| SHA-256 tree | 8 | 0.546 s | 1.97 GB/s | 246 MB/s |

Against the spec: `L128` matches I-74 (85/28/17 ms); SHA-1 is about 3×
E6's 260–279 MB/s and SHA-256 1.5× E23's 195 MB/s. What was tried
(SHA-256, 256 MiB, one thread): the straightforward FIPS loop shifting
eight variables per step, 280 MB/s; the shipped form (16-word rolling
schedule, eight steps per macro expansion with the variables' roles
rotating instead of their values) 297 MB/s; a 64-word schedule computed
before the rounds 219 MB/s (reverted); `Maj` as `(a & b) | (c & (a |
b))`, no change (reverted). SHA-1 uses the same shape (five steps per
expansion, one loop per group of 20 with its `f` and `K`). `L128` is
bound by each lane's multiply-rotate-multiply chain; the loop keeps the
four lanes in locals over `chunks_exact(32)`.

## Changes to `spec/image.md`

1. I-72: the exact bytes of the root's input (tag = 17 ASCII bytes and a
   zero byte; `le64`; leaf digests in their functions' byte order,
   concatenated in index order); the `n = 0` coincidence of the bare and
   `sha256` roots (no leaves; harmless, no ELF output is empty).
2. I-114: how to read the definition (operator precedence, `n` as
   `u64`, `0 − P1`, argument order of the nested `round`, stripe order
   and the padded tail, `a` before `b`; the lanes and `round` are
   XXH64's at seed 0, the finish is not). The definition was complete:
   the independent Python implementation of the text agreed on every
   vector at the first attempt; the paragraph removes the readings a
   second implementer could still doubt.
3. I-114's quality bullet: `mortar_digest`'s re-measurement added (worst
   |p − 0.5| 0.0041 against E23's 0.0205 with comparable sizes; E23's
   input sampling is not recorded, so the two are not reconciled).
4. I-74: `mortar_digest`'s table added (SHA-1 1.39 s and SHA-256 3.74 s
   per GiB on one thread instead of ≈4 s and 5.51 s); the whole-file
   SHA-1 figure annotated.
5. New §8.4: the vectors (`L128` of 15 inputs, the three trees for 7
   files, `uuid_v4`).
6. §16.1 `build_id_vectors`: points at §8.4 and this crate's test, and
   says what the image's own test still checks (its output's id against
   `tree_root` with the descriptor zeroed).

## Follow-ups

- `crates/mortar_cli/src/grammar.rs:891`: the `0xHEX` check accepts `0X`
  (I-70: `0x` is case-sensitive) and an odd number of digits (I-70:
  `invalid-option-value`, note `expected an even number of hexadecimal
  digits`); it could call `mortar_digest::parse_hex` (that would add the
  dependency to `mortar_cli`), or check the parity itself. The image
  must not be the first to notice.
- `mortar_image` (WP-026s or later): hold one `LeafColumn`, hash each
  window before writing it (I-33 step 4), and test the linked output's
  id against `tree_root` (§16.1).
- I-76 (M7): `LeafColumn` has no way to replace a leaf or to be rebuilt
  from a stored column; add `replace(index, &Leaf)` and a constructor
  from the digests when incremental linking needs them.
