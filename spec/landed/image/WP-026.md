# WP-026 (code), stage A: `mortar_image`

This package implements `spec/image.md` §5–§11 and §13 in
`crates/mortar_image`. The crate covers:

- fill: windows, clips, record search, padding, NOBITS, and errors reported once;
- tombstones, including I-112;
- the output file protocol of §7;
- the `mortar-map 1` map file;
- per-worker 1 MiB buffers written with `write_all_at`;
- the `--time-phases` lines and the memory formula;
- the §13 synthetic-chunk interface.

It also adds `Kind::CannotWriteOutput` to `mortar_diag` (R-7).

**Stage reached: A, plus WP-023b's half of stage B.** Main has been merged twice:

- 0a5fc21 brought in WP-026h (`mortar_digest`);
- 157adee brought in WP-023b.

Fill now uses `mortar_arch`'s real pieces:

- the clipped `SectionOut::new`;
- `Facts.max_reach`, `code_fill` and `code_nop`;
- `dead_reference` and `Arch::tombstone`;
- `RelocAt.leads`.

What remains of stage B is WP-025 (`mortar_synth`), which is not on main.

- **The shifted site.** `Site` is "the input section". So that a clip does not have to read its whole section, each record sees `[r−16, r+32)` shifted to 0, with `Shifted` records and proof runs and a `redirect` fix-up. `SectionOut::new` then carries the clip in that shifted view.

## End to end (`tests/e2e.rs`, glue in `tests/support/reflink.rs`)

GCC 14 compiles and GNU ld links static AArch64 executables with `-static -no-pie -Wl,--no-relax -Wl,-Map`:

- **C**: one unit, `-g -O1 -fno-pie`. It has constructors, function pointer tables, string tables and a 8 KiB `.bss`.
- **C++**: two units at `-g -O0` that share template instantiations, so GNU ld drops COMDAT copies. It has exceptions, virtual calls, `thread_local` and the STL.

`reflink::ref_world` places every input section of the user objects at the file offset that GNU ld's map and the executable's section headers give it. A section is placed if it has file bytes, is not a merge section and is not `.eh_frame`. Each record gets its `S` from the reference:

- globals come from the executable's `.symtab`;
- locals and section symbols come from the map placement;
- a section dropped by the reference is a dead target.

A cross-check asserts that every global the objects define has the same value by map placement and in `.symtab`.

The image fills the plan at W = 1 MiB and at W = 4 KiB (so sections straddle windows), with 1 and 4 workers.

**What is compared.** Every byte of every placed section must equal the executable's byte at the same offset, except for:

- **left out, field masked**:
  - GOT types (300–313);
  - TLS types (≥ 512; the reference relaxes them, and a64's differential test covers them);
  - targets in merge sections (`.rodata.str*`, `.debug_str`, `.debug_line_str`: rewritten by the reference);
  - `STT_GNU_IFUNC` targets (IPLT);
  - targets undefined in the executable (weak).
- **dead targets**: the field, and for `.debug_aranges` the tuple length, is checked against the I-47/I-112 values instead. GNU ld redirects such a reference to the kept copy, which is the documented difference in §15's table.

**Not compared:**

- archive members (libc, libstdc++);
- `.eh_frame`;
- headers;
- padding;
- every synthetic section.

Result, with none different:

| program | units | bytes compared | records applied | dead-target records | tombstones checked | left out |
|---|---|---|---|---|---|---|
| C | 9 | 2 337 | 63 | 0 | 0 | ifunc 1, merge 48 |
| C++ | 377 | 187 242 | 2 686 | 519 | 641 | TLS 6, ifunc 2, merge 7 492, undefined 1 |

The test found that GNU ld writes the kept copy's address into `.debug_info`/`.debug_aranges` for references into dropped COMDAT copies, where mortar writes the I-47 values. This is the documented difference (§15, row "debug reference into a dropped COMDAT copy"), and the test asserts mortar's side of it.

`reflink` is meant for WP-027: `parse_map`, `RefExe` (sections, symbols, `PT_TLS`), `ref_world`, `compare` and `check_tombstones`.

**Against the review's `wr.rs` at 8 threads** (review: staged 31 ms / 90 ms / 0.88 s; resident 72 / 138 ms / 1.45 s, with the input read included):

- **Resident.** Adding the ≈ 45 ms input read, mortar takes ≈ 70 / 135 ms / 0.79–1.2 s against `wr.rs` res's 72 / 138 ms / 1.45 s. That is parity at 48 and 200 MB, and faster at 2 GB (the existing output is set aside, I-113). The goal "at least as fast as `wr.rs res`" is met within noise at load 35–42.
- **Staged.** mortar takes 28 / 93–122 ms / 1.07–1.37 s against 31 / 90 ms / 0.88 s. That is equal at 48 MB and 5–35% slower at 200 MB and 2 GB. Three costs explain the gap:

  3. Thread scaling flattens above 4 workers on this host (P5). Every configuration plateaus at about 2 GB/s.

  The first version read one site per record with `pread`. That cost 12 s for the 2 GB plan, flat across thread counts, with CPU rising as threads were added. It was fixed in 00be328. The fix is the measurement above.

## Spec fixes made in `spec/image.md` (this WP)

1. **I-31.** "a whole synthetic chunk *larger than W*" is now "*touching more than one window*". A small whole chunk can straddle a window boundary, and without the change it would be filled twice, once per job, by a chunk that cannot fill part of itself.
2. **I-59.**
   - `T0` is opened `create_new`, falling back to opening the existing file. A stale `T0` (lock acquired) is removed and created again, not truncated with `set_len(0)`, because a truncated file keeps the killed link's mode.
   - The new inode is locked before the old one is released.
   - A lock on an inode that `T0` no longer names counts as `WouldBlock` (an inode check: without it, two links racing on a stale `T0` could both win).
   - A `T0` created on a file system that does not enforce locks is removed again.
3. **I-60.** Rename, then close. The lock must cover the rename, or another link could take `T0` as stale between the close and the rename. A close error cannot be observed through `std::fs::File`, so it is not reported.

## Ambiguities and errors (not changed in the spec)

1. **The reason text for a FIFO, socket or block device (I-58).** It is "not a regular file", with the note "output is a FIFO/socket/block device". The spec names the diagnostic but not the reason.
2. **I-112's "the next field".** "the next field is there" is approximated as "no record has `r_offset` in `[r+w, r+2w)`". This holds for the aranges tuples GCC and clang emit.
3. **I-66 and symbolic links.** A symbolic link to an input is kept, which is the conservative choice. The spec speaks only of "the output".
4. **I-38.** A fragment run that crosses input sections cannot be one input unit. `layout_plan` writes merged fragments as `Bytes` rows.
5. **The OS/ABI byte.** `EI_OSABI` is 0. The spec does not say.
6. **Records.** Records are decoded at plan time (memory ∝ records). This stands in for the scan's `RecIndex` (I-29). I-82's "read twice" budget is not yet met.
7. **Random worlds after WP-023b.** The new `apply` makes an alloc reference to a dead target an internal error ("no live target"), because the scan's `DiscardedSection` stops such a link first. The test generator now makes dead targets only from debug sections and `.gcc_except_table`.
8. **The staged store and record sites.** The site bytes of the records in a clip are read once, as the union of their sites. This is in addition to the clip read, so the overlap is read twice. The bench measured this before the WP-023b merge; a check after it is below. Reading each record's site separately (the first version) cost one `pread` per relocation: 12 s for the 2 GB plan. The spec does not say how sites are read in the staged store.
