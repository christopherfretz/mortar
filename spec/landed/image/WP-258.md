# WP-258: dropped COMDAT copies at address 0 (x86-64, DWARF 5) and a `--verify` that never ends

An investigation, no product change. Scripts: `tests/image-design/wp258/`
(README there); every number below comes from their output (scratch
`.build/target-wp-143/wp258/`, runs `r3` and `vl`). Tools: g++ 14.2 (native
AArch64, `x86_64-linux-gnu-g++-14`), clang++ 19.1.7 (`--target=`), GNU ld
2.44, lld 19.1.7 and 22, mold 2.37.1 (gold is not installed), gdb 16.3
(gdb-multiarch for x86-64), lldb 19.1.7, llvm-dwarfdump 19 and 22,
llvm-symbolizer-22. mortar at 04346e34, `cargo build --release -p mortar`,
plain (non-incremental) static link through `g++ -B`. kiln/hod was not run.

## 1. The coordinator's first finding: `--verify` does not terminate (not a linker defect)

`llvm-dwarfdump-22 --verify` on `a64-gcc-dw4-o2/mortar` ran 98 minutes at
97% CPU. Measured (`links.sh`, `timeout 120` each):

| configuration (a.cc + b.cc, `-O2 -DWP258_O2`) | mortar | GNU ld | lld 19 | lld 22 | mold | ones-rng probe |
|---|---|---|---|---|---|---|
| AArch64 g++ DWARF 4 | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | |
| AArch64 g++ DWARF 5 | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT |
| x86-64 g++ DWARF 4 | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | |
| x86-64 g++ DWARF 5 | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT | TIMEOUT |
| clang++, both targets, DWARF 4 and 5 | 0 s | 0 s | 0 s | 0 s | 0 s | 0 s |

It also does not terminate on the compiler's own `a.o` (`timeout 30`,
llvm-dwarfdump 19 and 22), before any linker has run, while `b.o` verifies
in 0 s. Reduced by hand (`bis/`) to `src/loop.cc`:

    int g(int);
    int main() { { int x = g(1); return 1 + x; } }

GCC 14 `-O2 -g` puts the call site INSIDE the lexical block
(`DW_TAG_subprogram > DW_TAG_lexical_block > DW_TAG_GNU_call_site` in DWARF
4, `DW_TAG_call_site` in 5); Clang puts it under the subprogram
(`DW_TAG_subprogram > DW_TAG_call_site`, its block holds only the
variable). `verifyloop.sh`: GCC's `loop.o` and its links by all five
linkers, both targets, DWARF 4 and 5, both dwarfdump versions: TIMEOUT;
Clang's: rc 0 in 0 s.

The field, by patching bytes (`bis/` probes, then `retag.py` in
`verifyloop.sh`). These do NOT stop the loop: the block's ranges made
`[0, 0x1c)`, empty, or only `[0, 0)`; the variable's location list made
empty, one entry, base address only, overlapping. -fno-var-tracking (no
call sites) makes it stop, and so do these:

| patch (one byte of `.debug_abbrev`) | `--verify` |
|---|---|
| none | does not terminate |
| the block's tag `0x0b` -> `0x1d` (`DW_TAG_inlined_subroutine`) | ends in 0 s: `error: Call site entry nested within inlined subroutine` |
| the block's tag `0x0b` -> `0x2e` (`DW_TAG_subprogram`) | ends in 0 s: `Subprogram with call site entry has no DW_AT_call attribute` |
| the call site's tag `0x48` -> `0x0b` | ends in 0 s, rc 0 |

So the verifier's call-site check loops when the call site's parent is
neither a subprogram nor an inlined subroutine. That fits a walk up the
parents that never moves past the first parent. I did not read LLVM's
source, so that last part is an inference from the bytes, not a quote. The
same retag on mortar's and GNU ld's `a64-gcc-dw4-o2` outputs makes
`--verify` end in 0 s with that error (the "smallest patch": one byte per
lexical-block abbreviation). It makes the output's DWARF wrong, so it is a
probe and not a fix.

The bytes that the brief asks about, for this configuration
(`a64-gcc-dw4-o2`, the relocations of `b.o` into its dropped
`.text._ZN5wp2585twiceEi`; `a.o` has none: its copies are the kept ones):

| field (reloc `R_AARCH64_ABS64`) | mortar | GNU ld | lld 19 / 22 | mold |
|---|---|---|---|---|
| `.debug_info` 0x123 `DW_AT_low_pc` (`DW_FORM_addr`; `high_pc` is `data8` 0xc) | all ones | kept (0x4007a0) | 0 | 0 |
| `.debug_loc` 0x7d..0xc0, six begin/end words (`[sec]+0, +8, +8, +0xc, +4, +0xc`) | 1 each | kept + addend | 1 each | 1 each |
| `.debug_ranges` 0x10, 0x18 (`+0`, `+0xc`) | 1, 1 | kept, kept + 0xc | 1, 1 | 1, 1 |
| `.debug_aranges` 0x20 address / length | all ones / 0 | kept / 0xc | 0 / 0xc | 0 / 0xc |
| `.debug_line` 0x8c `DW_LNE_set_address` | all ones | kept | 0 | 0 |

Each mortar value is the I-47 row for its section (§2). The loop is
outside all of them: it is in `a.o`'s unit, whose call site lies in kept
code, and it happens with GNU ld's redirect as well. x86-64
(`x64-gcc-dw4-o2`, `-dw5-o2`) does the same; Clang does not.

Consumers on that output (`timeout 120`, by hand and in `consumers.sh`):
gdb 16 ends in 1 s. `break wp258::twice` gives one location, `info scope
wp258::twice` gives `v` and `r` as multi-location, and `info address` gives
the function at the kept copy's address. Running, it stops twice (callers
`a_f`, then `b_f`), the same as GNU ld and lld. lldb 19 ends in 0 s, and
`image lookup -v -n` gives one function (`range = [0x438020-0x43802c)`).
gdb's one complaint particular to the tombstone, `DW_AT_call_target target
DIE has invalid low pc`, is printed for lld's output too.

**Consequence:** `llvm-dwarfdump --verify` cannot be an unbounded step of
any harness that sees GCC `-O2 -g` objects: every caller needs a timeout,
and a timeout must be recorded as "did not terminate", never as a count.
This is not mortar's to fix.

## 2. The report: overlapping ranges `[0x0, 0xe)` and `[0x0, 0x11)`

### 2.1 The rule and the bytes

`spec/image.md` I-47, ELFCLASS64: `.debug_ranges` and `.debug_loc` take 1;
`.debug_rnglists`, `.debug_loclists` and `.debug_addr` take **0**;
`.debug_aranges` takes all ones **and the tuple's length 0** (I-112);
`.debug_info`, `.debug_line` and every other debug name take all ones.
I-47a (redirecting into a kept non-alloc group member) does not apply,
because the targets are `SHF_ALLOC` code. The text of I-47 already says
"`llvm-dwarfdump --verify` reports `DIE has overlapping ranges` for a CU's
several `[0, len)` entries (lld and mold: the same); the debuggers are the
oracle."

`fields.py` gives the value written for each of `b.o`'s 164 references per
linker into its dropped copies, in all 24 configurations. One value per
linker per section, with no exceptions:

| section, form | compilers | mortar | I-47 | GNU ld | lld 19/22 | mold |
|---|---|---|---|---|---|---|
| `.debug_info` `DW_AT_low_pc` `DW_FORM_addr` | GCC 4/5, Clang 4 | all ones | all ones | kept | 0 | 0 |
| `.debug_line` `DW_LNE_set_address` | all | all ones | all ones | kept | 0 | 0 |
| `.debug_ranges` begin/end pairs | GCC 4, Clang 4 | 1 | 1 | kept + addend | 1 | 1 |
| `.debug_loc` begin/end pairs (`-O2`) | GCC 4, Clang 4 | 1 | 1 | kept + addend | 1 | 1 |
| `.debug_rnglists` `DW_RLE_start_length` | GCC 5 | 0 | 0 | kept | 0 | 0 |
| `.debug_loclists` `DW_LLE_base_address` (`[sec]+3`), then offset pairs (`-O2`) | GCC 5 | 0 | 0 | kept | 0 | 0 |
| `.debug_addr` entries (used by `DW_RLE_startx_length` and `DW_FORM_addrx`) | Clang 5 | 0 | 0 | kept | 0 | 0 |

### 2.2 Why the targets differ

They do not differ in form or relocation. Both targets use the same
references: GCC 5 writes `DW_RLE_start_length` with an `ABS64` start in
`.debug_rnglists`, and Clang 5 writes `DW_RLE_startx_length` through
`.debug_addr`, with `DW_FORM_addrx` low_pc. The only difference is the
**sizes** of the two dropped functions. On AArch64 at `-O0`, `twice` and
`Box<long>::get` are both 0x18 bytes, so their two entries are the same
range `[0, 0x18)` twice, and `--verify` does not report identical ranges.
On x86-64 they are 0xe and 0x11 bytes, which overlap. The `ne` variant
(`twice` grown by an add) flips it: AArch64 becomes 0x1c and 0x18 and is
reported, while x86-64 becomes 0x11 and 0x11 and is clean. This holds for
all four linkers that write 0.

### 2.3 Consumers (consumers.sh, 14 configurations)

mortar's outputs and lld's and mold's give the same results, apart from
the binary's name. In each case gdb `break wp258::twice` gives ONE
location; `info line` and `info line *kept` give the same line; and the
complaint count is equal (DWARF 5 `-O0`: GCC 6, Clang 7; `-O2`: 3, 4): `.debug_rnglists entry
has start address of zero`. On AArch64, running the program stops twice,
with callers `a_f` and `b_f`. lldb `breakpoint set -n` gives one location
at the kept copy, and `image lookup -v -n` gives 2 `Function:` lines.
`llvm-symbolizer` on kept and on kept+4 gives `wp258::twice(int)` with the
right line. GNU ld's redirect gives lldb 3 `Function:` lines (b's DIE of
the dropped copy is attached to the kept address) and 0 gdb complaints;
otherwise it is the same.

The all-ones alternative (the `ones-rng` probe: mortar's output with all
ones in the dropped entries of `.debug_rnglists`, `.debug_addr` and
`.debug_loclists`) makes `--verify` clean, because LLVM skips a tombstone
start. gdb 16 then complains `Invalid .debug_rnglists data (inverted range)`
(3 complaints instead of 6 zero-start ones, GCC; 4 instead of 7, Clang).
This is the wrap `[2^64-1, len-1)` that I-47 gives as the reason for 0.
In THIS program the breakpoints, the two stops, `bt`, lldb and the
symbolizer are the same as with 0. The probe did not step into `b.cc`'s
code, so E16's measured failure (`pc ... in read in CU, but not in symtab`
after gdb drops the CU's whole range list) was neither reproduced nor
refuted here. The rejection of all ones rests on E16.

## 3. Verdict and proposal

**As specified, and equal to lld 19/22 and mold in every DWARF 5 field: no
change to I-47.** The overlap report is a `--verify` artefact of several
`[0, len)` entries in one CU, and I-47 already names it. No consumer
measured reads it wrongly. The only value that silences it without
redirecting, all ones, breaks gdb's reading of the CU's range list, which
is the reason I-47 rejected it (E16's step failure; here only the
complaint is reproduced, §2.3). Redirecting (GNU ld) silences it
too, but I-47 rejects that for code: it asserts that the two copies are the
same code.

What a change would need, if `--verify` cleanliness were ever wanted (not
proposed): rewrite DWARF, not relocations. For example, a dropped copy's
`DW_RLE_start_length` length ULEB could be set to 0, padded to the same
width (a 1-byte `0x0e` becomes `0x00`, and an n-byte ULEB stays n bytes as
`0x80.. 0x00`). That needs a `.debug_rnglists` parser in fill, which I-47
avoids on purpose ("No DWARF is parsed"). Clang's `.debug_addr` entries
are shared through an index and have no length to clear.

Proposed spec text (a clarification of I-47's `--verify` sentence, no
change of value): "the report appears when the dropped copies' lengths
differ; two dropped copies of equal length give the same `[0, len)` twice,
which `--verify` does not report (WP-258: AArch64 `-O0` `twice` and
`Box::get`, both 0x18), so its absence on a target is not evidence of a
difference." And for the harness (VALIDATION, not image.md): "`llvm-dwarfdump
--verify` does not terminate on GCC `-O2 -g` objects with a call site inside
a lexical block (WP-258 §1, LLVM 19 and 22, the compiler's object alone);
every use runs under a timeout, recorded as `TIMEOUT`."

Test that would guard it: `crates/mortar/tests/update_debug_bytes.rs` (or a
`tests/deferred.rs` neighbour) checks the bytes of fields.py's rows for
`.debug_rnglists`/`.debug_addr` (0) and `.debug_aranges` (all ones, length
0) on the x86-64 fixture. Any `--verify` assertion there must allow the
overlap error and run under a timeout.
