# WP-080 — split DWARF as a first-class configuration (stage A)

mortar has linked split-DWARF objects since M1 (WP-060 R14 measured
protoc), but nothing tested that configuration. Stage A records what a
split object carries, what GNU ld 2.44, lld 22, mold 2.37.1 and mortar do
with each section, the tombstones a collected or losing function gets,
and how gdb 16.3 and lldb 19 read the result. It adds link tests, debugger
sessions, byte-identical rows and one rule, `spec/image.md` I-49a. No
linker code changed: mortar was already right everywhere this package
looked.

Reproduce the census with
`scripts/split-census.py --work <dir> --mortar <bin> --xtask <xtask>
[--kiln <kiln++> --hod <hod>]`. It writes one TSV row per (unit, linker,
mode, kind, section).

## 1. The census

The program is two C++ units. `main.cc` has `twice<int>` (a COMDAT that
both units instantiate), `thread_local int tl_count`, a global and `main`.
`b.cc` has `helper`, which calls `twice`, and `unused_fn`, which
`--gc-sections` collects. Each unit is compiled with
`-ffunction-sections`, on AArch64, x86-64 and i386.

The producers are:

- GCC 14.2 (the cross compilers on this host);
- Clang 19 and Clang 22 (`--target`);
- kiln++ 1.2.1 with hod (`KILN_HOD_STRICT=1`). kiln is AArch64-only, so
  it runs on that host only.

The forms are:

- `-gsplit-dwarf` at DWARF 5 (`d5`) and DWARF 4 (`d4`, the GNU extension:
  `DW_AT_GNU_dwo_name` skeletons);
- `-gsplit-dwarf=single` at DWARF 5 and DWARF 4;
- with `-ggnu-pubnames`, `-gno-pubnames` and `-gpubnames`
  (`.debug_names`);
- with `-fdebug-types-section`;
- at `-O2`.

That makes 15 forms. There are 128 units, and each is linked `-static
-no-pie` plain and with `--gc-sections`, by each of the four linkers: 256
links per linker.

Every link was then checked four ways:

- **Run**: the program ran, and its output equals GNU ld's output.
- **Verifier**: `xtask plumb` with mortar's map judged mortar's output.
- **Sections**: each output section's fate (kept, merged, dropped,
  refused) and its size.
- **Addresses**: `llvm-dwarfdump-22` counted the entries of
  `.debug_addr`, `.debug_line`, `.debug_ranges` and `.debug_aranges`.

**Producers' refusals**: GCC 14 has no `-gsplit-dwarf=single` (it is an
error). kiln++ refuses `-gsplit-dwarf=single` and
`-fdebug-types-section`. These cells do not exist.

Sections of the relocatable objects. The table is the same on all three
architectures unless a cell says otherwise. Abbreviations: `addr` is
`.debug_addr`, `str_offs` is `.debug_str_offsets`, `gnu_pubn/t` is
`.debug_gnu_pubnames`/`pubtypes`, `names` is `.debug_names`. `.dwo` is
the number of `SHF_EXCLUDE` `*.dwo` sections that the `=single` form
leaves in the object.

| producer | form | sections (besides `.debug_abbrev`, `.debug_info`, `.debug_line`, `.debug_str`) | `.dwo` in the object |
|---|---|---|---|
| GCC | d5, d5-O2, d5 ± gnu-pubnames, d5-types | addr aranges gnu_pubn/t line_str rnglists | - |
| GCC | d4, d4-O2, d4-gnu-pubnames, d4-types | addr aranges gnu_pubn/t ranges | - |
| GCC | `-gno-pubnames`, `-gpubnames` at d5 | as d5 (GCC still writes gnu_pubn/t) | - |
| Clang 19, 22 | d5, d5-O2, d5-gnu-pubnames, d5-types | addr gnu_pubn/t line_str rnglists str_offs | - |
| Clang 19, 22 | d5-no-pubnames | addr line_str rnglists str_offs | - |
| Clang 19, 22 | d5-pubnames | addr **names** line_str rnglists str_offs | - |
| Clang 19, 22 | d4, d4-O2, d4-gnu-pubnames, d4-types | addr gnu_pubn/t ranges | - |

The `*.dwo` sections, by producer and form:

- **Clang `=single`**: `.debug_info.dwo`, `.debug_abbrev.dwo`,
  `.debug_str.dwo` and `.debug_str_offsets.dwo`.
- **`-O2`**: also `.debug_loclists.dwo`.
- **DWARF 4, or DWARF 5 with types**: `.debug_line.dwo`.
- **DWARF 4 with types**: also `.debug_types.dwo`.

What the linkers do. Each cell counts outputs over the 256 links per
linker; a section appears only in the units that carry it.

|---|---|---|---|---|---|

| `.debug_str` | merged 256 | merged 256 | merged 256 | merged 256 | I-38 |
| `.debug_line_str` | merged 154 | merged 154 | merged 154 | merged 154 | I-38 |

The results were:

- **No refusals.** No linker refused any cell.
- **Fates and sizes.** mortar's section fate and size equal at least one
  reference's in every one of the 256 × 2 cells. In fact all four agree on
  every fate.
- **Runs.** Every program runs as GNU ld's does.
- **Verifier.** The verifier is clean on all 256 mortar outputs. On
  x86-64 and i386 the output was judged without being run.
- **`.debug_addr`.** Compared symbolically (each entry as section +
  offset), mortar's `.debug_addr` equals lld's in all 256 links. GNU ld
  and mold differ only by A15 (below) and GNU ld's COMDAT redirect.

**Finding F1: no rule said what a split object becomes.** I-49 calls debug
sections ordinary units, but it says nothing of skeletons, `.debug_addr`,
the name indexes, `DW_AT_dwo_name`, or the `SHF_EXCLUDE` `.dwo` sections.
mortar's behaviour was right (it is all three references' behaviour), but
it was unstated. The proposed text is now `spec/image.md` **I-49a**.

## 2. `--gc-sections` and the losing COMDAT copy: tombstones

Each cell below is `tombstones/entries`, summed over the forms and both
Clang majors under `--gc-sections`. A tombstone is I-47's value for the
section and class. "wrong" counts dead entries with another value: the
references' choices that I-47 rejected. A TLS entry's `DtpRel` of 0 also
counts as a zero in `.debug_addr`. That is why GNU ld's and mold's x86
counts are lower: they write the template address (A15).

|---|---|---|---|---|---|---|
| GCC | ELF64 | `.debug_addr` (0) | 44/232 | 78/232 | 68/232 | 78/232 |
| GCC | ELF64 | `.debug_aranges` (all ones, length 0) | 0/116 (20 wrong) | 0/116 (40 wrong) | 0/116 (40 wrong) | 40/116 |
| GCC | ELF64 | `.debug_line` (all ones) | 0/116 (20 wrong) | 0/116 (40 wrong) | 0/116 (40 wrong) | 40/116 |
| GCC | ELF64 | `.debug_ranges` (1) | 8/46 | 16/46 | 16/46 | 16/46 |
| GCC | ELF32 | `.debug_addr` | 18/107 | 38/107 | 28/107 | 38/107 |
| GCC | ELF32 | `.debug_aranges` | 0/58 (10 wrong) | 0/58 (20 wrong) | 0/58 (20 wrong) | 20/58 |

The tombstones:

- **mortar.** mortar has no wrong entry anywhere. Each dead `.debug_addr`
  entry (the collected `unused_fn` and the losing `twice<int>` copy) is 0,
  as I-47 says.
- **GNU ld.** GNU ld has fewer zeros because it redirects the losing COMDAT
  copy to the kept one (rejected in I-47).
- **Skeletons.** The DWARF 5 skeleton's `DW_AT_ranges` goes through
  `.debug_rnglists` with `DW_RLE_startx_length`, so its dead range is a
  `.debug_addr` 0. The DWARF 4 skeleton's goes through `.debug_ranges`,
  so its dead range is a 1.

What the debuggers show for these (`crates/mortar/tests/debuggers.rs`
`split_gc_sessions_*`, and the gc rows of `tests/link/split/debuggers.test`)
is the same on GNU ld's and mortar's outputs, for GCC and for Clang:

- **gdb:**
  - `break b.cc:3` (in `unused_fn`) gives "No compiled code for line 3",
    then the pending-breakpoint question.
  - `break gc_unused` and `info scope gc_unused` find nothing, and
    they print the same thing on both outputs.
  - A backtrace through the kept `twice<int>` from `helper` shows both
    frames with arguments.
- **lldb:** `breakpoint set -f b.cc -l 3` moves to `helper`'s line 4 on
  every linker's output. lld's and mold's give the same lines.

**Finding F2 (not mortar's): `llvm-dwarfdump --verify` "overlapping
ranges".** Under `--gc-sections`, `llvm-dwarfdump-22 --verify` reports
`DIE address ranges overlap` / overlapping ranges in 77 of 128 outputs.
It does so for lld's, mold's and mortar's outputs alike. The cause is
the 0 tombstones of two dead functions in one unit. GNU ld's outputs are
clean, because its redirect makes the ranges distinct. Plain links verify
clean on all four linkers. The link tests check `--verify` on plain links
only. The debugger test allows these lines under gc, citing I-47. I-47
has already accepted this trade (the lldb rows of its table).

The last run gave 48 results: 48 PASS, 0 FAIL, 0 ORACLE. That is, per
linker: aarch64 5, x86_64 4 and i386 3 tests. Every unit checks:

- the run (`5 10 8`);
- that `readelf -SW` has `.debug_addr` and no `.dwo` section;
- `readelf --debug-dump=info`: the skeleton (`DW_UT_skeleton` and
  `DW_AT_dwo_name`, or `DW_AT_GNU_dwo_name`) and "Found separate debug
  object file" for both units' `.dwo`;

- the L3 verifier.

The declared anomalies, all already in `spec/plumb.md` §10.2:

- **A15** (GNU ld and mold, x86-64 and i386): GCC's `.debug_addr` entry
  for `tl_count` holds the template address where X-53/X86-62 want the
  DTP offset.
- **A30** (GNU ld, AArch64 static-pie).
- **A31** (GNU ld, x86-64 static-pie, crtbeginS's `.plt.got`).

`llvm-dwarfdump` is a new `check` tool (`spec/harness.md`; `Feature::
LlvmDwarfdump`, `requires` word `llvm-dwarfdump`). `llvm-dwp` joins
`scripts/ci-tools.sh`; both come from the image's `llvm-22`.

## 4. Debugger sessions (`crates/mortar/tests/debuggers.rs`, split section)

Each session is a pair: mortar's output against GNU ld's, from the same
objects, run under gdb 16.3 and lldb 19 on AArch64 (named skip
elsewhere). gdb's session does:

- `tbreak` by line in the other unit (`dx_b.cpp:7`) and by function
  (`level2`);
- `catch throw`;
- `bt` with arguments, `print` a local and a global, `ptype` a class,
  `info scope`;
- `step` into a function of another unit;
- `continue` through the throw.

lldb's session is the same, in lldb's commands. The transcripts are
compared after masking addresses, the same as `cxx_sessions_*`.

| form | GCC 14: gdb / lldb | Clang 22: gdb / lldb | `.dwp` (llvm-dwp-22) |
|---|---|---|---|
| d5 -O0 | equal / equal | equal / equal | Clang equal; **GCC: llvm-dwp hangs** (F3) |
| d4 -O0 | equal / equal | equal / equal | equal (both) |
| d5 -O2 | equal after `@entry` masking (F4) / equal | equal / equal | - |
| d5 + `-fdebug-types-section` | **not run: gdb cannot read GCC's `.dwo`** (F5) | equal / equal | - |
| single d5 -O0 | (GCC has no `=single`) | equal / equal | Clang equal |
| d5, d4 -O0 under `--gc-sections` | equal / equal | equal / equal | - |

The `.dwp` row runs `llvm-dwp -e <program>` on both outputs, then hides
the `.dwo` files. The `.dwp` transcripts equal the `.dwo` ones. GNU
`dwp` (binutils-gold) is not in the image, so that row is **not run**
(request R1).

- **F3 (llvm-dwp, not mortar's).** `llvm-dwp-22` and `llvm-dwp-19` do not
  finish on the two `.dwo` files GCC 14 writes at DWARF 5 (`main.dwo
  b.dwo`). Each file alone packages, and GCC DWARF 4 and Clang's files
  package. The hang is independent of the linker (the `.dwo` files are
  the compiler's). The `.dwp` row skips GCC d5.
- **F4 (I-47 at work).** At `-O2`, gdb prints `twice<int> (x=x@entry=2)`
  on GNU ld's output and `(x=2)` on mortar's. gdb finds the entry value
  through the call site's `DW_AT_call_origin` in the caller's unit,
  which names the DIE of `b.cc`'s discarded copy of `twice<int>`. GNU
  ld's redirect gives that DIE the kept copy's address. mortar's
  tombstone gives it none: `CALL_TARGET_DEAD`, which the non-split
  `cxx_sessions_*` already allow. The comparison masks `name@entry=`
  (`entry_values_masked`, I-47).
- **F5 (GCC and gdb, not mortar's).** gdb 16.3 says "DWARF Error: wrong
  version in compilation unit header (is 0, ...)" on the `.dwo` that
  GCC 14 writes for `-gsplit-dwarf -gdwarf-5 -fdebug-types-section`. It
  does so on GNU ld's output as on mortar's. That form links, runs and
  verifies (census, `gcc.test` `d5t`), and the session is Clang-only.

## 5. Byte-identical rows

`static-identical` covers every `tests/link` test except `dyn/`, so the
five split tests joined it as they are, with every link at
`-fno-use-linker-plugin`. That gives 65 new rows in each baseline, for
the same links:

- `tests/identical/baseline.on-aarch64.tsv`: cut with `--update` after
  merging main at 61e806c, which includes WP-059's `.symtab` bits;
- `baseline.on-x86_64.tsv`: from the printout of hosted run 43839082260.

No existing row changed. Two runs after `--update` gave 0 differ.
WP-059 changed 39 of the 65 rows that had been cut before the merge.

- **F6 (GCC, not mortar's).** GCC 14's `DW_AT_dwo_id` (the skeleton's
  DWO ID) at `-gsplit-dwarf -gdwarf-5 -O2` differs between two compiles
  of the same source with the same output name, even with
  `-frandom-seed`; at `-O0` the object is stable. Its link therefore
  changed between runs (output digest only; the map was equal), and it
  was taken out of `gcc.test`. The census and `debuggers.rs`
  `split-d5-O2` still link it. A build that wants reproducible split
  objects from GCC at `-O2` does not get them, whatever the linker.

## 6. The Mason lane with split DWARF

The lane's compiler wrapper (`tests/mason/lane/kiln++`) already passes
`MASON_CFLAGS` to every command, so no kiln change was needed. kiln++
compiles and links each test in one command. Like GCC, it then writes
`<output>-<source>.dwo` beside the program and a `DW_AT_dwo_name`
skeleton that points at it; this was checked on a one-file program.

The command was:

    cargo xtask mason libcxx --full --shard 1/46 --cflags "-g -gsplit-dwarf" \
      --plumb --baseline tests/mason/baseline-mortar.tsv

That ran modes bfd and mortar with hod as the back end.

`libcxx`), sorted by path, is every 46th test: 202 tests. It is a

## Requests and open questions

- **R1 (image).** GNU `dwp` (Debian `binutils-gold`, or binutils' `dwp`)
  is not installed, so the `.dwp` row runs with `llvm-dwp` only.
- **R2 (verifier, a question).** This package did not read the verifier.
  Whether it judges `.debug_addr`'s dead entries against I-47, as the
  census's `addresses()` counts did here, is a question for its owner.
  If it does not, split DWARF's addresses are checked only by these
  tests.
- **Q1.** I-54 leaves `.debug_names` and `.gdb_index` to M4. Producers'
  per-unit `.debug_names` (Clang `-gpubnames`) are concatenated, and gdb
  and lldb accept that. Whether mortar should merge them is stage B's
  question.
