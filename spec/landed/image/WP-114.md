# WP-114: a link replaced the container's `/dev/stdout` with a regular file

`spec/image.md` I-58b (new), I-66, I-79a, §15; `spec/diag.md` §3.2;
`spec/incr.md` IN-17; `docs/AGENTS.md` ("Shared machine"). On
2026-11-16, during a `cargo xtask ci --quick` gate in this container
(processes run as root; `/dev` is a writable tmpfs), `/dev/stdout`
stopped being the symbolic link to `/proc/self/fd/1` and became a
regular file holding a GNU-style link map of `ok.o` (945 bytes). From then
on `streams::written_files_to_a_broken_stdout` and
`written::dev_null_and_dev_stdout_keep_working` failed in every worktree.

## The cause

**The first actor was not mortar** (found by the coordinator, checked on
a private link). At 15:50:05 local time another agent ran
`objcopy -O binary --only-section=... <file> /dev/stdout` from Python
(`capture_output`, so descriptor 1 was a pipe) over AArch64 and x86-64
outputs. The native objcopy cannot read an x86-64 file ("Unable to
recognise the format", status 1), and a FAILING GNU objcopy unlinks its
output path when it is a regular file or a symbolic link (libiberty's
`unlink_if_ordinary`). After status 1 the link was gone; after status 0
it was kept. GNU ld does the same after a failed `-o` (measured below).

**Then mortar re-created it as a regular file.** With `/dev/stdout`
missing, the next `-Map=/dev/stdout` saw no file: `lstat` gave `ENOENT`,
so `write_whole` took the ordinary protocol. The syscalls were
`openat(AT_FDCWD, "/dev/.stdout.mortar-tmp", O_WRONLY|O_CREAT|O_EXCL)`,
`flock`, `write`, `rename("/dev/.stdout.mortar-tmp", "/dev/stdout")`.
From then on `/dev/stdout` was an ordinary existing output for every
later link, which replaced it again (I-113's aside, then the rename), and
every program in the container that wrote to `/dev/stdout` wrote into
that file. The 945-byte map was written at 15:59:42 by an agent's
hand-run probe with a reader-less pipe. Each later writer made a new
inode, so the map the supervisor saw is the last one written, not the
first. `strace` is not installed in this container; the syscall sequence
is read from the code (`Output::create`, `Output::temp`, `commit`).

**Two mortar defects of the same class**, measured on private links
(`L -> /proc/self/fd/1`, `L2 -> /dev/stdout` in the scratch directory),
fixed here:

- **A: descriptor 1 of no file type.** When descriptor 1 is an eventfd,
  an epoll or a pidfd, `stat("/proc/self/fd/1")` gives an `st_mode` with
  no `S_IFMT` bits. `stream_target` and `Output::create` checked for a
  character device, a FIFO, a socket, a block device and a directory, and
  let anything else through to the ordinary protocol:
  `open(.L.mortar-tmp, O_CREAT|O_EXCL)`, `rename(L, .L.mortar-old)`,
  `unlink(.L.mortar-old)`, `rename(.L.mortar-tmp, L)`. The link became a
  regular file holding the map, and the link exited 0. This happened for
  -Map, --mortar-map, --dependency-file and -o, through both L and L2:
  48 replaced out of 48 runs, a 100 % rate. The same fall-through was
  reached by any symbolic link whose `stat` failed.
- **B: `--incremental-state` through a descriptor link.** The state's
  own writer (`write_atomically` in `crates/mortar/src/incremental.rs`)
  renamed a temporary over the path. It replaced L and L2 in every
  descriptor state: file, append, deleted, `/dev/null`, closed, socket.
  With descriptor 1 a pipe it hung instead, because the link read its
  own standard output as the old state (`fs::read` on the pipe, whose
  writer is the link itself). With `/dev/full` it read zeros forever.

**What did not replace the link.** The descriptor states of the tests
never replaced it: 0 of 18,000 runs. Those states were a pipe whose
reader has gone, `/dev/full`, closed by the shell (`>&-`, which Rust's
start-up reopens as `/dev/null`, S-4), closed by the parent (the same),
and a pipe with a reader. That is 200 runs each for -Map, --mortar-map
and --dependency-file, through L and L2, 12 links at a time. A regular
file and an `O_APPEND` file also never replaced it: 0 of 3,600 runs at
300 each, 16 at a time. The existing code is deterministic for those
states. A deleted file on the workspace's FUSE share fails the open
(`ENOENT`), not the stat, and is refused by name.

## What the references do (measured, private links, 3 runs each)

Descriptor 1 in each state; `L -> /proc/self/fd/1`. "replaced" means L
is now a regular file; "unlinked" means L is gone.

| state | GNU ld 2.44 `-o L` | lld `-o L` | mold 2.37.1 `-o L` | `-Map=L` (all three) |
|---|---|---|---|---|
| regular file, `O_APPEND` | written in place | **replaced** | written in place | written in place |
| closed (a C program: no reopen) | `cannot open output file` | **replaced** | **replaced** | error, `ENOENT` |
| deleted file (FUSE) | error | **replaced** | **replaced** | error |
| `/dev/null` | written | written | written | ld: "not a regular file", written; others written |
| `/dev/full` | **unlinked**, `final close failed` | error, kept | written, status 0 | ld status 0; lld error; mold status 0 |
| pipe with a reader | **unlinked**, `Illegal seek` | written | written | written |
| pipe, reader gone | **unlinked** | status 74 | status 0 | ld 0, lld 74, mold killed by `SIGPIPE` |
| socket | error `ENXIO` | error | error | error |

A failing GNU ld therefore removes a `/dev/stdout`-style link, as GNU
objcopy does. lld and mold replace it in some states. That is why
`docs/AGENTS.md` now forbids naming a descriptor path as any tool's
output.

An ordinary dangling link (`out -> target.bin`): GNU ld and mold
create `target.bin` for both `-o` and `-Map`. lld replaces the link for
`-o` and creates the target for `-Map`. mortar replaces the link for
both, and keeps doing so (I-58b gives the reason).

## The rule (`spec/image.md` I-58b) and the one function

`mortar_image::output::disposition(path, Use::{Output, Whole})` returns
`Replace`, `InPlace { truncate }`, `Refused` (`cannot-open-output`:
I-57, I-58) or `Forbidden` (`cannot-write-output`: I-58b). Its table is
total over `lstat(P)`, the walk of P's chain of symbolic links and
`stat(P)`:

- A link through a descriptor table (decided by walking the chain with
  `readlink`, each name judged by its directory's `realpath` before the
  name itself is examined, so a closed descriptor's absent
  `/proc/self/fd/1` is still an alias) is handled in one of four ways.
  It is written in place (truncated for a regular file). It is refused
  as a FIFO, socket or block device output. It is forbidden when it does
  not resolve or resolves to a file of no type. It is never replaced.
- A chain that cannot be walked (`EACCES`, `ENOTDIR`, more than 40
  links) is forbidden. An ordinary link whose `stat` fails other than
  `ENOENT` is forbidden too.
- A file of no type is forbidden.
- A name in a system directory is forbidden from the replace protocol.
  A system directory is `dir(P)` after `realpath`, when it is exactly
  `/dev` or is under `/proc` or `/sys`. This means a missing
  `/dev/stdout` is now `cannot-write-output /dev/stdout: a system
  directory`, not a new regular file. `/dev/shm` stays an ordinary
  directory: this repository's stamp tests create files there
  (`crates/mortar/tests/incremental.rs`, `stamp_dirs`), and builds use
  it as a tmpfs. Nothing in the real-build results writes outputs there.
  Safe Rust's `std` has no `statfs`, so the test is by path.

Every site that creates, renames over or removes a path the command line
named goes through it:

| site | verdict |
|---|---|
| `Output::create` (`-o`; `write_whole`'s replace case) | through `disposition`; the I-113 aside and the I-60 rename exist only in its `Replace` branch |
| `write_whole` (`-Map`, `--mortar-map`, `--dependency-file`) | through `disposition` (`stream_target` removed) |
| `remove_stale_output` (I-66) | removes only a regular file or a symbolic link that `may_replace` allows |
| I-113's aside `.<base>.mortar-old` | inside `Replace` only; the name is mortar's own |
| the incremental state (`incremental.rs`: `start`, `write_atomically`, the two `remove_file`s; `check`'s read) | refused by name at `start` unless absent or a regular file the link may replace; the writer calls `may_replace` before its rename; the removals go through `remove_if_replaceable`; a state that is not a regular file is never read |
| `--incremental-report=FILE` (appended) | refused at `start` when `disposition` refuses it; appended in place otherwise (no rename) |
| the in-place update's copy (`floor.rs` `by_copy`, IN-47) | `may_replace(out_path)` before the copy and rename |
| the in-place update (`floor.rs` `in_place`, IN-46) | writes in place after an `fstat` check (a regular file with one link); no rename or unlink: unchanged |
| the stamp files (`mortar_incr::stamp`, `.mortar-stamp-<pid>`, created and removed) | mortar's own names, not a path the command line named; `take_stamps` (facade) drops system directories from the list, so no stamp is created in `/dev`; `crates/mortar_incr` untouched |
| `-M` | writes standard output, no path |
| `--gdb-index`, split DWARF | sections of the output; no side files |
| `--why-extract` and other path-valued writers | refused options; nothing is written |

## The tests

- `crates/mortar_testutil/src/dev_stdout.rs`: `Guard`. A test that
  names the real `/dev/stdout` holds one. It checks the link when it is
  created and again in `Guard::check`. If the link is not a symbolic
  link to `/proc/self/fd/1`, it restores it with
  `ln -sfn /proc/self/fd/1 /dev/stdout` and FAILS the test, saying a
  tool or the linker replaced or removed it, so one defect cannot
  cascade into every later test. `Drop` restores it too, for a test that
  failed earlier. Used by `streams::written_files_to_a_broken_stdout`
  and `written::dev_null_and_dev_stdout_keep_working`.
- `crates/mortar/tests/descriptors.rs` (new):
  - `a_link_through_a_descriptor_table_is_never_replaced` runs 11
    descriptor states × 6 written options (-Map, --mortar-map,
    --dependency-file, -o, --incremental-state, --incremental-report) ×
    {L, L2}. The states are a regular file, `O_APPEND`, deleted,
    `/dev/null`, `/dev/full`, a pipe, a pipe whose reader is gone, a
    socket, a directory, closed, and an eventfd made by `python3`. Eight
    links run at a time. After each link, L is still the same link and
    nothing else is in its directory, the link exits with status 0 or 1
    (never a signal or a hang), and the state's own outcome holds: no
    type and the incremental state refused by name; closed and
    `/dev/null` succeed; a regular file is written in place.
  - `the_state_that_replaced_the_link_is_refused_every_time` runs the
    eventfd state 100 times with -Map and 100 times with -o, and the
    closed state 100 times, in parallel.
- `crates/mortar_image/tests/output.rs` has two new tests.
  `i58b_every_outcome_of_resolving_a_path` covers the table row by row,
  on links to `/proc/self/fd/N` of a file the test holds open (also
  through `/dev/fd/N` and a chain of two), a descriptor the process does
  not have (forbidden; not removed by `remove_stale_output`), a pipe, a
  loop (`ELOOP`), `ENOTDIR`, and dangling and ordinary links.
  `i58b_system_directories` covers `/dev`, `/dev/fd/..`, `/proc/self`,
  `/sys`, `/dev/shm` (not one) and a name under `/proc` (forbidden,
  nothing created).
