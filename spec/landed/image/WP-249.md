GNU ld's condition is `_bfd_elf_check_kept_section`'s: a member of the
kept group whose LOCAL SYMBOLS match the dropped section's (names and
count; AArch64's `$d` and the section symbols count; no symbols on one
side: no match) and whose size is equal. The NAME and the BYTES are not
compared: C4 writes a `.debug_types` offset into a `.debug_macro` field.
mold never deduplicates `wm4.*` groups (it keeps every copy; the import
names the importer's own copy). The plumb.md §5.8 description of GNU
("same name and size") is not GNU's condition.

## 3. Proposed rule (for the supervisor to apply; not edited here)

New I-47a, after I-47 (exact text proposed):

> - **I-47a [M1] [C] A debug reference into a dropped copy of a debug
>   group** (WP-249). A relocation in a live non-alloc section with a
>   debug name (I-45) whose symbol is a section symbol or a local symbol
>   defined in a section D, where D has no `SHF_ALLOC` and is not live
>   only because its COMDAT group copy is dropped (`spec/resolve.md`
>   §6.2), is filled against the kept copy instead of the tombstone when
>   the group's keeper (`spec/resolve.md` §6.1) has, in its copy of the
>   group, exactly one section K with D's name, no `SHF_ALLOC`, D's
>   `sh_size`, and K is live: `S` is K's address plus the symbol's
>   `st_value` (K's offset in its output section, as for any non-alloc
>   target), and the field is written as for a live target (range checked,
>   I-43). Otherwise I-47's tombstone. No DWARF is parsed and no bytes
>   are compared. GCC's `-g3` puts each header's macros in such a group
>   (`wm4.<file>.<line>.<md5>`) and imports it by offset
>   (`DW_MACRO_import`); the tombstone there crashes gdb 16 and loses the
>   unit's macros in lldb 19, and 0 (lld) names the output's first macro
>   unit, so both debuggers give wrong answers silently (WP-249 §2.3).
>   The redirect asserts that the two copies of non-alloc group data are
>   the same, which the group's signature states (GCC's is the contents'
>   MD5) and which the keeper's own references already rely on; for code
>   (an `SHF_ALLOC` target) I-47 stands. GNU ld redirects on a weaker
>   condition (matching local symbols and size, any name: WP-249 §2.1),
>   mold keeps every `wm4.*` copy.

I-47's paragraph "GNU ld's redirect to the kept copy was rejected: it
asserts that the two copies are the same code" gets: "(for code; a
non-alloc member of a debug group is redirected, I-47a)".

§15 table, new row after the first:

| subject | GNU ld 2.44 | lld 22 | mold 2.37.1 | mortar | rule |
|---|---|---|---|---|---|
| debug reference into a dropped COMDAT copy of a NON-ALLOC group member (GCC `-g3` `DW_MACRO_import`) | a kept member with matching local symbols and equal size, of any name (+ st_value + addend), else 0 | 0 | none dropped for `wm4.*` (every copy kept); else 0 | the keeper's same-named, same-size, live non-alloc member + st_value + addend, else the tombstone | I-47a |

Why every class and not only `.debug_macro`: the rule is a function of
the resolution and the section headers, so it needs no list of DWARF
forms; the only class any producer emits is the macro import (§1), and
for a hypothetical `DW_FORM_ref_addr` into a dropped type unit the
tombstone is the same out-of-range offset into `.debug_info`.

Why the tombstone, not 0, for the fall-back: no measured producer reaches
it (every one of the 2228 references meets the condition); 0 is silently
wrong in both debuggers, the tombstone is loud (gdb) or a loss (lldb).
Alternative for the supervisor: refuse the fall-back by name (it needs a
new diagnostic kind: not proposed without your word).

**`--gc-sections`** (modes.sh, u.o first: its only function is collected,
it keeps every shared group): the kept copies stay in every linker's
output (keeper_bad=0; mortar 31 units as GNU, lld), because a group with
no alloc member is a root by type (`mortar_live` `section_groups`: only
a group with an alloc member lives and dies with it). The patched redirect
under gc: gdb right (2 of 2), mortar today: crash. A group with an alloc
member whose code is collected makes K not live: the fall-back.

**`-r`**: mortar refuses groups at `-r` (RL-8, AArch64) and x86-64 `-r`
(RL-9): nothing changes; references stay relocations, I-47a is a fill
rule. GNU ld -r deduplicates and rewrites b's import relocations to the
kept copy's section symbol (52/54 relocations all `kept` in its output);
RL-8 may do the same or keep both: either is consistent with I-47a.

**Incremental** (WP-228 §4, §7.1): with I-47a every importer names the
keeper's copy by offset, so the keeper's macro group must not move in an
update, or every importer refills ("a keeper's macro group never moves";
a growth that does not fit falls back), and a keeper whose new version
drops the group is WP-228's `debug-comdat-keeper` fall-back. Nothing in
I-47a contradicts it: an update that refills an importer computes the
value from the keeper's unchanged placement in the state. Measured:
`--incremental` full link equals the plain link (ones today); the second
link was a full one (`small-output`), so an update was NOT exercised.

## 4. Where the value is chosen

`LinkTables::sym_value_of` (`crates/mortar_image/src/link.rs:756`), the
`SymKind::Local` arm: `facts.dead` gives `Valued::Missing` there, which
fill turns into I-47's tombstone (`mortar_a64/x64/x86` `apply.rs`,
`DeadRef::Tombstone`). The redirect: when the place is `Section(D)`, D is
dropped for its group (`resolution.sections[D].comdat`, state
`Dropped`), D has no `SHF_ALLOC`, the keeper `resolution.comdat[G]` has
exactly one kept, live, non-alloc section of D's name and size in group
G (scan of the keeper's `section_base` range), return
`self.value_in(K, st_value)`. A private helper in the same file; no new
type, `mod`, signature or dependency edge; only the dead path pays.
To confirm in step 2: that an incremental update fills through the same
`LinkTables`, and that the scan's deferred check (I-14) passes the now-live
target.

## Step 2: I-47a in the linker

### S2.1 What landed

- `crates/mortar_image/src/link.rs`: `LinkTables::sym_value_of`, the
  `SymKind::Local` arm (line 843): when `facts.dead`, a place `Section(D)`
  asks the new private `LinkTables::kept_copy_value` (line 644) and keeps
  `Valued::Missing` (I-47's tombstone) when it answers `None`. The helper
  checks I-47a's condition: D is `Dropped(Comdat)` and placed whole,
  without `SHF_ALLOC`; the keeper (`resolution.comdat[G]`) has exactly one
  section of D's name in group G (scan of its `section_base` range), and
  that section has no `SHF_ALLOC`, has D's `sh_size`, and is kept and
  placed. The value is then `value_in(K, st_value)`, which also requires
  K to be live (P-1). There is no new type, `mod`, signature or dependency
  edge. A live or alloc D pays nothing new: the first test is the existing
  `facts.dead`, then one state and flag test.
- The scan's deferred check (I-14) is not involved: it returns early for
  debug-named referrers before it reads the target's liveness, so a target
  that is now valued needs no change there.
- `Merge` and `.eh_frame` kinds are refused by `is_placed()`, because their
  value is not K + offset. They keep the tombstone.

### S2.6 Findings for the supervisor

1. The ORACLE rows of S2.3: verifier attribution of same-named sections in
   foreign maps. They need a ruling: a WP-250 item, a marker, or keeping
   the four tests out of L3.
2. The helper does not see the referring section. A `.gcc_except_table`
   field (I-46: 0), or a dead FDE's field, whose target is a non-alloc
   member of a dropped group, would get the redirect instead of 0. No
   producer emits this. A fix needs the referrer's name at the
   `except_table` path in `reloc.rs`.
3. Proposed text for I-47a: "K and D are placed whole (neither
   `SHF_MERGE` nor `.eh_frame`)". The linker falls back to the tombstone
   for those kinds.
