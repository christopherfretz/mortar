# WP-200: a strong reference extracts the member past a dropped COMDAT copy's definition

`gcc -static -no-pie wu.o wa.o wb.o libhx.a`: wu.o references `hx`
strongly; wb.o's copy of group `g` is dropped (wa.o keeps it) and also
defines a weak `hx`; libhx.a's member defines `hx`. resolve.md §6.2 makes
wb.o's `hx` a demoted mention, an undefined weak mention, so wu.o's
strong reference extracts the member and the program exits 15. mortar
refused it (`comdat-mismatch`). Measured against GNU ld 2.44, lld 22 and
mold 2.37.1 on AArch64 (natively), x86-64 and i386 (cross, qemu).

## 1. The cause

The order of events in `mortar_resolve` before this package:

1. `live::targets_with` computes `first(K)` and `cfirst(K)` once, over
   every file's mentions, before anything is live. wb.o's `hx` is a
   defined weak mention in a section, so `first(hx)` = wb.o (a named
   object, lower `FileId` than the member).
2. `live::closure`: wu.o's strong undefined `hx` is an edge to
   `first(hx)` only when that is a lazy file. wb.o is not lazy, so the
   edge has no target and the member is never reached.
3. `comdat::keepers`, over the closure's live objects: wa.o keeps `g`;
   wb.o's copy is dropped.
4. D1 demotes wb.o's `hx` (`effect`: `Ref { weak: true }`): `def[hx]` is
   `Undefined`, and the scan reports `comdat-mismatch`.

The keeper was chosen after the closure, and §4.1 said so ("COMDAT does
not feed back: extraction treats a definition in a group section as a
definition whichever copy is kept"). So the strong reference was never
seen as unsatisfied: at extraction time `hx` had a definer, the one that
is dropped one step later. §6.2's text ("the binding counts for ...
archive extraction") contradicted §4.1's bullet; the brief directs §6.2.

## 2. The fix

The closure is **iterated** (`resolve.rs` `resolve_stage`, `live.rs`):

- After a closure and the keepers over its live objects, D1 (which
  already demotes per file) checks every demoted mention:
  `live::feeds_back` (its definition is `first` or `cfirst` of its key,
  `K` or the `foo@V` row) and `live::would_pull` (it is not weak and
  `first` of its key is a lazy file the closure left out; the key gets
  `flags::PULLS`, masked out of `props`).
- If one feeds back, or one pulls for a key no live object defines
  outside a dropped copy (`open`: the class minima `strong`, `weak`,
  `common` of D1 all empty), the closure runs again (`live::Prior`: the
  previous live files with their pulling references, the keepers,
  `open`), with `live::next_targets`: the targets recomputed without the
  definitions the keepers demote (never lower than before, so a
  `--defsym` key keeps no target). In it the demoted mentions of the
  previous live files are undefined mentions with their binding: a
  non-weak one of an `open` key is an edge to `first` of its key, a weak
  one none.
- It stops when an iteration changes nothing (targets, live set,
  keepers and `open` equal to the previous one's), or when no mention
  feeds back. The live set and the dropped copies only grow, the targets
  only rise: it ends.
- `live::oracle` (the sequential reference the tests compare with) runs
  the same iterations, with the same predicates, sequentially.
- `Resolved.iterations` counts them; `Resolved.targets` stays the
  targets before the closure (what the oracle is given).

The same edges serve every kind of lazy file (an archive member, a
`--start-group` member, a `--start-lib` object). The needed set (D-11)
needed no change: it is decided after the closure from `def` and the
object references' flags, where wm.o's strong reference already counted
(mortar linked `comdat-mismatch-strong-needed.test` before this package:
§3).

**Why `open`.** The first version had a demoted non-weak mention
extract whenever `first` of its key was a lazy file left out, as §4.1
has an ordinary strong reference do. `mortar_resolve`'s differential
tests caught it on i386: every object there has a COMDAT copy of
`__x86.get_pc_thunk.*` defining a global (hidden) symbol, so every live
object's demoted thunk mention pulled the first archive member with a
copy (libgcc.a's `_absvdi2.o`, `bid128.o`, ...; libm.a's `*f128.o`): 3
to 51 members GNU ld does not load (`chello32`, `mth32`, `spie32`,
`tpl32`). A demoted mention binds to the keeper's definition (§6.2), so
when a live object defines the key it extracts nothing: GNU ld's
behaviour (a key already defined extracts nothing), and the unit test
`s6_2_wp200_demoted_mention_of_a_defined_key_extracts_nothing`. This is
narrower than §4.1's rule for an ordinary strong reference (finding 1:
`first(K)` is extracted even when a later file defines `K`): question 2.

**Cost.** A link with no mismatched copy runs one iteration, as before:
`feeds_back` is two loads per demoted mention in D1; `would_pull` one
more; a link whose demoted non-weak mentions pull (i386's thunks, when an
archive member before the keeper has a copy) adds one pass over the keys
(`open`) and no iteration. A second iteration redoes the closure from all
live files, the keepers and D1: only for a mismatched copy. Timing was
not measured on the bench.

**Bytes.** A link that ran one iteration is unchanged.

**Can a copy read first be dropped (§6.1)?** Yes, under mortar's rule:
the keeper is the lowest live `FileId`, not the first loaded; wb2.o,
named and read before libwa2.a's member is extracted, loses its copy to
the member (keeper-later). GNU ld and lld keep the copy loaded first and
bind `hx` to its definition (80); that is §6.1's recorded difference.

**`-j1` and `-j8`.** The unit tests run every case under 1, 2, 7 and 64
threads and seeds (`check_schedules`) with the oracle; the lane cell
links with `--threads=1` and `--threads=8` and compares the bytes
(identical).

## 4. The verifier

The verifier (`mortar_plumb`, L3) still models §4.1 before this package:
its M12 finds every member mortar now extracts past a dropped copy
unreachable, e.g. `ext: M12 libhx.a(hx.o) is in the link and no root or
live reference reaches it (resolve §4.1)`. mortar's outputs were shown
correct by their runs (every mortar run of the table: `--no-plumb`, all
pass) and by their bytes (AArch64 `ext`: `main` and `Y` both `bl` the
member's `hx`, `mov w0, #7`; `g` is wa.o's `mov w0, #1`; wb.o's copy is
absent; exit 15). So these tests are committed as `.test.pending` with
the finding in their first line, to be renamed when the verifier follows
§4.1's iterations:

- `comdat-mismatch-weak-archive-extract` (its `xfail(mortar)` removed),
  `comdat-mismatch-extract-orders`, `comdat-mismatch-member-copy`,
  `comdat-mismatch-keeper-later`, `comdat-mismatch-strong-demoted`,
  `comdat-mismatch-unique-demoted`.

Live tests: `comdat-mismatch-archive-first` (no feedback; all four
linkers but mold link) and `comdat-mismatch-strong-needed` (mold's
`libw.so` an `xfail(mold)`, the verifier's R5; lld an `xfail(lld)`).
The existing `comdat-mismatch*` tests keep their verdicts (the whole
lane).

## 5. Spec edits

- `spec/resolve.md` §4.1: the bullet "COMDAT does not feed back" is
  replaced by "A dropped copy's definitions stop counting when it is
  dropped" with the iterations (the brief's reading of §6.2; question 3).
- §6.2: the binding counts for extraction "from the moment its copy is
  dropped"; a demoted `STB_GLOBAL` or `STB_GNU_UNIQUE` mention extracts
  as a strong undefined mention; the same for a lazy object or a group
  member.
- §12.1 (`first`, `cfirst` row), §12.2 (the COMDAT bullet: each
  iteration unique, the sequence monotone, the oracle iterates), §13
  (the graph depends on the keepers of the live set).
- §4.1 and §6.2, a precision (question 2 asks to confirm it): a
  demoted non-weak mention is an edge only when no live object defines
  its key outside a dropped copy (the `open` condition, §2).

## 6. Questions

1. A demoted `STB_GLOBAL` / `STB_GNU_UNIQUE` mention of a key only an
   archive member defines: by §6.2 it extracts the member and the
   program links (Y reads the member's definition, exit 8). GNU ld, lld
   and mold all refuse (every order). Keep mortar's extraction, or
   refuse as the three do?
2. A demoted non-weak mention whose key a live object defines (the
   keeper's copy) extracts nothing in mortar now (GNU ld's behaviour;
   otherwise every i386 link loads members GNU ld does not, through the
   pc thunks), although §4.1 has an ordinary strong reference extract
   `first(K)` even when a later file defines `K`. Written into §4.1 and
   §6.2 as a precision; please confirm.
3. §4.1's "COMDAT does not feed back" is reversed by the iterations: a
   meaning change of §4.1 the brief's reading of §6.2 requires; please
   confirm the text.
4. The verifier's M12 (and its model of `first`) must follow §4.1's
   iterations for the six pending tests to run.
