# WP-004: the relocatable-object reader

`spec/elf.md` §1 to §4: `mortar_elf`'s constants and relocation names, and the
reader for relocatable objects of both classes (AArch64 and x86-64 in
`ELFCLASS64`, i386 in `ELFCLASS32`).

## What it does

- **Allocation-free.** It is a zero-copy, allocation-free reader over `&[u8]`.
  `Object::parse` costs constant time and checks identification, the section
  header table and the name table. Everything else is checked by the accessor
  that reads it.
- **Class-generic.** Each on-disk record widens into one type (`Shdr`, `Sym`,
  `Rela`, `Rel`, `Chdr`, `Nhdr`, `Word`, `Ehdr`) through the `Record` trait.
  `Table<T>` is a `Copy` array of records whose iterator branches on the class
  once per `fold` and once per `next`. No other code branches on the class,
  except the `r_info` split and the note/property padding.
- **Coverage.** Extended section numbering (count, name-table index and
  `SHT_SYMTAB_SHNDX`), `SHT_REL` and `SHT_RELA`, groups, notes and GNU program
  properties, compression headers and mergeable sections.
- **Errors.** Every malformed shape is a `Copy` `Error` value whose one-line
  `Display` names the section or symbol.
- **Names.** Name functions for every constant, and relocation names for the
  three machines: 248 types are named.

## Decisions the spec records

- **Refusals.** ELF32 x86-64 (x32), ELF32 AArch64 (ILP32), ELF64 i386,
  big-endian files and non-`ET_REL` files are each refused by name (§3.1).
  The AArch64 ILP32 relocation types are therefore not named (§2.3).
- **The count escape** (`e_shnum` 0) is taken at its word: `sh_size` 0 means no
  sections (§3.2).
- **`SHT_RELR`** is named but its records are not read (§3.6).
- **Merge entry size.** A `SHF_MERGE` entry size of 0 is reported, not refused
  (§3.10).
- **Group signatures.** The reader returns them as stored. An unnamed
  `STT_SECTION` signature is left for `resolve.md` (§3.7).

The relocation-type sweep compares every type from 0 to 1100 (plus four
larger values) on the 64-bit machines, and every type from 0 to 255 on i386.

L1 found no reader bug. It found five ways the tools' output differs from the
bytes; `elf.md` §4.3 lists them.

A mutation check confirmed that L1 catches changes to the decoders: an
`r_offset` off by one fails seven tests. It also found a gap. Narrowing the
ELF32 type mask went unseen, because no corpus object has an i386 type of 128
or more, so the sweep now also checks the reader's decoded type numbers.

## Open questions

- **Signatures that are section symbols.** A group signature that is an
  unnamed `STT_SECTION` symbol (GCC emits them for `.stapsdt.base`): BFD takes
  the section's name. `resolve.md` must decide what mortar does.
- **Tool versions.** The §2.3 pins name binutils 2.44 and LLVM 22. A tool
  upgrade will fail the test until the pins are revisited.
- **Compression headers.** L1 compares them with readelf only.
  `llvm-readelf -t` prints them and could be the second oracle.
- **`stapsdt` notes.** Their descriptors are not compared.
- **i386 Fortran.** No i386 gfortran is installed, so there are no i386
  Fortran objects in the corpus.
