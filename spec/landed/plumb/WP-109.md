# WP-109 — the verifier at the reference scale

Branch `wp/109-plumb-at-scale`. Only `crates/mortar_plumb/`,
`xtask/src/plumb.rs`, `spec/plumb.md` and this record. The verifier was
written from the specs and the outputs; no linker crate was read.

Measured on the AArch64 development container (12 CPUs, 17 GB, shared;
load 5 to 9 throughout). mortar is this branch's release build; the
verifier is `cargo xtask plumb` in the dev profile (`mortar_plumb` and
`mortar_elf` at `opt-level = 2`), as the bench and CI run it, from the
inputs' directory. Every large run is under `prlimit --as=8589934592`
(8 GiB of address space), `nice -n 10`, one at a time, after `uptime`
showed a load under 10 and `free -g` 9 GB or more available. A run that
hits the cap aborts (`memory allocation of N bytes failed`, signal 6).

**A run killed at the cap dumps core into its working directory** (the
container's `core_pattern` is `core`, `ulimit -c` unlimited): the first
capped run wrote 5.4 GB of core into `cxx-large-g/inputs/` over FUSE
before it was stopped (deleted). Every later run has `ulimit -c 0`.

## 1. Where the memory goes (before any change)

The profile: `MORTAR_PLUMB_PROFILE=<file>` (`mortar_plumb::prof`):
`/proc/self/status` `VmRSS` and `VmHWM` at each phase boundary, the
peak reset at each by `clear_refs` (5), and the size of the large
structures by their lengths and element sizes (heap of strings inside
the elements not counted). Lines are appended to the file as they are
made, so a run killed at the cap keeps them. No new dependency.

What this says:
- **The inputs are not the main cost; the deferred piece references
  are.** Every `.debug_info` reference to `.debug_str` (a mergeable
  section) is a record whose target is decided by content (§5.6): it is
  queued as a `Pending` (the record, its `Site` with three `String`s,
  the symbol's name: 208 B inline plus some 150 B of heap) until every
  section has been read. On opt `-g` 10.5 M are queued after a fifth of
  the objects, on protoc 3.8 M (three quarters of its peak). The split
  build has few (its strings are in the `.dwo` files), which is why it
  fit in 2.2 GB.
- The bytes held whole are the output plus every input file: 1.6 GB on
  opt `-g`, 3.4 GB on clang `-g` (2.4 GB of inputs, 1.6 GB of which is
  `.debug_*`). That alone is 1.7x the linker's peak on clang `-g`
  (1,958 MiB, WP-081 §4.2).
- Nothing else is large: the map's rows, the located sections and the
  symbol cache are under 200 MB together on clang `-g`.

## 2. Where `--equiv`'s time goes (clang split, before)

Two `--incremental=full` links of clang split (byte-identical outputs,
641 MB each).

- Each side runs a full engine (11.5 s: 6.7 s of it the dead-range
  rules §6.8, which the plain pass also pays on a map that claims
  coverage) and builds its units and forms (1.3 s).
- **Superlinear term 1, `equiv::reform`**: a GOT group member's outcome
  (§6.9 P-E4) replaced the traced one found by a backward scan of the
  whole trace (`iter().rev().find(p)`). GOT groups are decided after
  every section, so each scan walks most of the 3.5 M traced records,
  once per member (93 K members on clang split): about 1.6e11 steps.
- **Superlinear term 2, `match_items`** (P-E5): every item was matched
  by a linear search among the other side's items with the same exact
  part. `.eh_frame_hdr`'s 161 K entries all have the empty exact part,
  and GOT words all have `address`: quadratic in the table.
- After these two the check ran in 50.7 s (peak 4.7 GB) and gave one
  P-E3 finding on two byte-identical links, a false one (§3.3). A flat
  profile (`perf record -F 49`) then named three more terms:
- **Superlinear term 3, `Side::ids_open`** (45 % of the run): an
  address's identities were found by walking back from the spans that
  start before it while the running maximum of their ends reached it. A
  long span keeps that maximum up, and on a `-g` link thousands of spans
  overlap (the non-allocated contributions by offset, empty sections at
  one address: 6,995 levels of 550 K spans on clang split), so each of
  the 390 K symbol and 166 K table lookups walked most of the spans
  (`symbols` 15 s, `tables` 14 s).
- **Superlinear term 4, the dead-range rules' `DeadSet::in_memory` and
  `over`** (§6.8; 20 %, and the plain pass pays it too on a map that
  claims coverage): every symbol, table word and placed input section was
  compared with every range of the map (17 K on clang split), 5.5 s of
  the 6.7 s of each side's dead-range phase in `named_by_relocations`.
- **The forms' keys** (memory, not time): each side kept a
  `BTreeMap<((path, member, n), section, offset), Form>` with the path
  and member strings cloned per record: 1.3 GB a side on opt `-g`'s 9.2 M
  records, which put opt `-g`'s `--equiv` at 6.97 GB.

## 3. After

### 3.1 What changed

| change | where | effect |
|---|---|---|
| a piece group (§5.6) whose section no other object can name is decided once the objects are read past its own (`plumb.md` §5.6) | `reloc.rs` | the members are held per object, not to the end: opt `-g` from > 8 GB to 1.80 GB |

### 3.3 The false P-E3

On two byte-identical clang split links, P-E3 said glibc's
`__nptl_version` (`pthread_create.o`, `.rodata.str1.8`, input offset
0x1c8) "names another definition or place". The piece before it is one
byte, merged elsewhere (at 0xcd02b0); `def_addr` looked for a piece with
`offset <= value <= offset + size`, end included, and so found the
one-byte piece's end first: the address after the merged byte, not the
definition's. It now prefers the piece that holds the value, and takes a
piece's end only when none does (an end symbol). The P-E3 on that pair
is gone; no other verdict of the tree moved (§5).

## 4. The budget

Stated in `spec/plumb.md` §8.1: the verifier's peak at most twice the
linker's on the same link, and at most 4 GB on clang `-g`; `--equiv`
within the same 4 GB; time linear, `--equiv` about two plain passes and a
linear comparison. Measured against it:

| link | mortar's peak (plain link, default threads) | 2x | verifier peak | within |
|---|---|---|---|---|
| clang `-g` | 1,960 MiB (WP-081) | 3,920 MiB | 3,850 MiB | yes, by 2 % |
| opt `-g` | 953 MiB (WP-081) | 1,906 MiB | 1,799 MiB | yes, by 6 % |
| clang split | 779 MiB (WP-081) | 1,558 MiB | 1,833 MiB | **no**: 2.35x |
| protoc `-g` static | 249 MiB (the bench baseline's median) | 498 MiB | 365 MiB | yes |
| `--equiv` clang split | | 4,096 MiB | 3,481 MiB | yes |
| `--equiv` opt `-g` | | 4,096 MiB | 3,363 MiB | yes |

clang `-g` and opt `-g` are inside the budget by the width of the
host's noise, and clang split is outside it: on all three, what remains is
the output and the inputs held whole (3.4 of clang `-g`'s 3.85 GB; 1.4 of
clang split's 1.8, where the linker reads little of its `.debug_*`-poor
inputs). §6 is the design that takes it down, waiting for WP-102 (it
changes `lib.rs` and `dynverify.rs`, where the inputs are held).

## 6. The inputs: positioned reads (design; after WP-102)

What is left of clang `-g`'s 3.85 GB: the output (1,076 MiB), the inputs
held whole (2,289 MiB, 1.6 GB of it `.debug_*`), and 500 MB of map rows,
located sections and engine state. The design, inside the crate's two
dependencies and without `unsafe` or mmap:

- An input is opened, not read: `mortar_elf::View::parts` already gives
  an object a view of parts (`Part { offset, bytes }`), with
  `Section::is_resident` and `Error::NotResident` for the rest. Each
  object keeps its skeleton resident: the ELF header, the section
  header table, `.shstrtab`, `.symtab`, `.strtab` and `SHT_GROUP`s
  (some 8 % of clang `-g`'s input bytes).
- A section's bytes and its relocation section are read with
  `FileExt::read_exact_at` when a rule needs them, object by object in
  the engine's order, and dropped when the object's rules are done; an
  archive member is read from its offset in the archive, never the whole
  archive.
- The rules that read input bytes after the engine (S12 content, the
  `.eh_frame` rules, the `.gdb_index` and the dead-range DWARF checks)
  read again by position, object by object; no rule needs two objects'
  bodies at once except the content of mergeable pieces, which is read
  by the piece.
- `verify(&[u8], &[Input], &Map)` stays for the tests; a `Files`-like
  source (already a trait of the crate, `line::Files`) gives the
  positioned reads.
- Expected: clang `-g` at the output (1.1 GB) plus 0.2 GB of skeletons
  plus the engine's state: 1.5-2 GB, under 1x the linker's peak.

## 7. The command defects

- **No input resolved** (`spec/plumb.md` §8): a map naming files none
  of which can be read from the current directory (and `--inputs-from`'s
  choice) is a usage error naming the first file and the directory, plain
  and `--equiv` (`s8_no_input_resolved_is_a_usage_error`). The map has
  no `cwd` record to resolve against (`plumb.md` §3.2: none of the four
  formats records the link's directory).
- **Linker-script libraries** (`spec/plumb.md` §8): a file of the
  response file, or a library found, that is neither ELF nor an archive
  is read as a linker script: `INPUT`, `GROUP` and `AS_NEEDED` of plain
  file names, found as GNU ld finds them (absolute as is; otherwise the
  current directory, then the library directories), `OUTPUT_FORMAT`
  passed over; any other command, an `-l` name, unbalanced parentheses
  or nesting past 8 are a usage error naming the script
  (`s8_linker_scripts_are_followed`). On opt `-g` with `--inputs-from
  cxx-large-g-opt/response.txt`: 0 findings (WP-081: E4/I1/P-I1 on
  `libm-2.41.a`, `libmvec.a`).
