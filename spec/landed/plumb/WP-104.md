# WP-104 — a non-alloc word against a name only a shared library defines

Branch `wp/104-debug-word-shared`, cut from main at dd7fe7d. The RB-1
defect of WP-100 (`spec/landed/harness/WP-100.md` §5): the verifier
reported R1 on every linker's output for a `.debug_addr` word against
`_ZTVSt9bad_alloc`, because it expected the loader's address of the
library's definition in a section nothing relocates at run time.

Touched: `crates/mortar_plumb/` (`src/dsoword.rs` new; `src/reloc.rs`,
`src/dynverify.rs`, `src/anomaly.rs`; `tests/dyn.rs`), `spec/plumb.md`
(§5.8, §10.2 A37–A43, §10.6, §12.1 "The views"), the test moved from
`tests/realbuild/defects/RB-1.test` to
`tests/link/dyn/reloc/debug-word-shared.test` (extended) and a new
`tests/link/dyn/reloc/debug-word-shared-tls.test`, the static-identical
baseline, this record. The verifier was written from the specs, the
psABIs and the outputs; no linker crate was read.

## 2. The rule (`spec/plumb.md` §5.8, "A target only a shared library defines")

For a record in a section without `SHF_ALLOC` of a dynamic output, whose
symbol is global, weak or unique, not defined by the output's `.symtab`
nor placed by an input, and defined visibly by a shared object of the
loader's order: S is the copy (the output's `.dynsym` defines the name),
else the canonical PLT entry (`ET_EXEC`, an undefined `.dynsym` entry with
a non-zero `st_value`), else 0. X = S + A (absolute), S + A − P
(PC-relative), 0 + A (DTP offset against an `STT_TLS` definition, with
or without a `PT_TLS`). An absolute or PC-relative word against an
`STT_TLS` definition is P-D12, refused by name. The verifier reads copy
and canonical PLT from the output's `.dynsym`, not from its own
D-43/D-44 decision, because P-D7, P-D9 and P-D11 already hold the output
to that decision. An undefined weak no library defines stays §4.4. The
code: `crates/mortar_plumb/src/dsoword.rs`, called from
`Engine::record` for non-alloc records before the general procedure.

View 3 (every `WeakDyn` key given a preloaded definition) no longer
judges non-alloc uses (`dynverify::names_any`): they are not relocated
at run time, and lld's exported `nowhere` gave P-D9 view 3 on a debug
word (the same class of false positive; `spec/plumb.md` §12.1).

**The sentence for `spec/image.md`**: written as I-48a after WP-113
merged, checked against `spec/arch.md` §4.3 "Non-alloc places" (the
same S table). Its first form: "I-xx
[M2] A word in a section without `SHF_ALLOC` against a symbol only a
shared library defines holds the symbol's link-time value: the copy's
address when the output copies it, the canonical PLT entry's address
when an `ET_EXEC` gives it one, else 0; so S + A, or S + A − P for a
PC-relative type. An ordinary PLT entry, an IPLT entry, a GOT slot and
the library's `st_value` are never written there. A DTP-offset word
(`R_X86_64_DTPOFF64`/`DTPOFF32`) against the library's TLS symbol holds
0 + A, with or without a `PT_TLS`; an absolute or PC-relative word
against it is refused by name (`spec/arch.md` §4.3, `spec/a64.md`
§13.2)."

## 5. Debuggers and the tombstone

gdb 16.3 and lldb 19.1.7 on AArch64; `v.cc` (a class deriving
`std::bad_alloc`) by Clang 22 `-g -O2`, the only setting where Clang 22
emits the `.debug_addr` entry of `std::bad_alloc`'s `_vtable$`
(`DW_OP_addrx 0x2` → `_ZTVSt9bad_alloc`; Clang 19 emits no `_vtable$`).
Linked `-pie` by each linker; the entry holds 0 (GNU ld, lld, mortar),
0x2569a8 (mold: `st_value` in libstdc++), and 0x990 in a copy of GNU
ld's output patched to `std::bad_alloc::what()`'s PLT entry (the stub).
All five programs run and print the same.

- **gdb** (stopped in `puts` from `main`): `print m` gives `{<std::bad_alloc>
  = {<No data fields>}, static _vtable$ = <optimized out>}`; `print b`
  `<incomplete type>`; `print 'std::bad_alloc::_vtable$'` "No symbol";
  `info vtbl m` reads the object's vtable pointer (`vtable for 'my_alloc'
  @ ...`). Identical for 0, `st_value` and the stub.
- **lldb**: `frame variable m b` gives `(my_alloc) m = (std::bad_alloc =
  <incomplete type>)`; `target variable my_alloc::_vtable$` "can't find
  global variable". Identical for all five. `image lookup -a 0x990` on
  the stub output answers "symbol stub for: std::bad_alloc::what()
  const"; `0x2569a8` (mold's) resolves to nothing.

Neither local debugger reads `_vtable$` (lldb 20+ uses it to find an
object's dynamic type; only lldb 19 is installed here). **Recommendation:
keep 0 + A** (GNU ld's and lld's value, the rule). A consumer that reads
the word can tell 0 from an address (it is DWARF's "no address" in
`.debug_addr`, I-47's tombstone for the section); mold's `st_value` reads
as an address of the executable that holds something else or nothing,
and a PLT entry reads as code ("symbol stub for ..."), so a dynamic-type
lookup would match a vtable pointer against a stub. Tuck should treat 0
in a `_vtable$` entry as "defined in a library" and resolve the name
through the library's `.dynsym` at run time.

before WP-113): every reference PASS or its recorded XFAIL/SKIP, 0
ORACLE, 0 new findings; mortar failed exactly WP-113's lines

entry + A (`.quad dfunc+8`, `dfunc+8 - .` in the non-PIE) and a

start with a `PT_TLS`; mortar at c5409aa writes 0 + A there (the rule;
`debug-word-shared-tls.test` lines 31 and 34 check it).
