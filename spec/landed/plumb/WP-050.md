# WP-050 — the verifier's stage 3: dynamic executables

`spec/plumb.md` (§3.2 step 0d, §12.1 new), `crates/mortar_plumb` (new
`src/dynout.rs`, `src/line.rs`, `src/dynmodel.rs`, `src/loader.rs`,
`src/dynverify.rs`, `src/dyncheck.rs`, `src/dynmutate.rs`; `tests/dyn.rs`,
`tests/dyn/`), `xtask/src/plumb.rs` (`--line FILE`; `--mutate` runs
stage 3). `mortar_plumb` still depends on `mortar_elf` and `mortar_diag`
only, reads no linker code (written from `spec/dyn.md`, `spec/plumb.md`
§12, the psABIs and the reference linkers' outputs) and is
`forbid(unsafe_code)`. The P-D rules are `spec/plumb.md` §12 since
WP-040r; `spec/dyn.md` keeps the D rules they cite.

## What was built

- **Step 0d** (03d2154, on main as d3bde0d): the map's dynamic records
  (`plumb.md` §3.2; `map::DynRecords`; writer side
  `mortar_image::map::DynRecords`).
- **Entry** `mortar_plumb::verify_with(output, inputs, map, &Ctx)`: a
  `PT_DYNAMIC` output goes to stage 3; `Ctx` carries the line (the
  linker's words) and a `Files` reader for shared objects and scripts.
  Without a line, a mortar map's `arg` records are the line; with
  neither, P-D2 and nothing else. `verify` (no context) is unchanged for
  static outputs.
- **The line** (`line.rs`): D-1's kind, `-dynamic-linker`, `-z
  now/lazy/relro/norelro`, `-E`, `--allow-shlib-undefined`, new dtags,
  `-rpath`, `-L`, `-l` search, `--as-needed` / `-Bstatic` /
  `--push-state` state per file, GNU ld scripts (`GROUP`, `AS_NEEDED`,
  `INPUT`), `-u`, `-e`. `-shared` is refused by name (M4).
- **The model** (`dynmodel.rs`): every shared object read with
  `mortar_elf` (`.dynsym`, versym, verdef, verneed, `DT_NEEDED`,
  `DT_SONAME`, segments); D-11's needed set, D-12's used set and
  `DT_NEEDED` closure, D-19a's order (GNU ld, mortar) and the
  first-mention order (lld, mold, §13.1), every key's view from the
  placed objects (`Key`: defined, weak, referenced by the program or by a
  library, version asked).
- **Static checks** (`dyncheck.rs`): P-D1, P-D4..P-D8, P-D10..P-D13 and
  P-D9's record order (D-40) and text relocations (D-47).
- **The loader model** (`loader.rs`): the output's records applied as
  ld.so applies them, library `i` at `0x7f00_0000_0000 + (i << 32)`,
  lookups in the executable then the needed objects breadth-first
  (`COPY` skips the executable, `JUMP_SLOT` skips a canonical PLT),
  glibc's version matching; TLS with fake library blocks (§12.1).
  `plt_entries` decodes each PLT entry to its slot (AArch64: GNU ld,
  lld, mold forms; x86-64: the three forms, IBT and lazy stubs).
- **The views** (`dynverify.rs`): stage 2's engine re-judges every input
  relocation against the loaded bytes in view 1 (bias 0), view 2 (bias
  `0x5555_5a5a_0000`, every absolute word re-checked) and view 3 (every
  `WeakDyn` key at a fresh address), GOT, PLT and TLS indirections
  followed through the records. Exported IFUNCs (D-23, W13).
- **Mutations** (`dynmutate.rs`, `mutate::run_with`): 16 dynamic classes
  appended to the harness's table; `xtask plumb --mutate --line` judges
  each mutant with stage 3.
- **Tests** (`tests/dyn.rs`): 20 tests, fixtures compiled and linked at
  test time with GNU ld, lld and mold on AArch64 and x86-64 (recording
  `ld` wrappers write each link's words), 21 sources in `tests/dyn/` plus
  inline ones; 42 unit tests in the crate.

## Reference outputs flagged outside the list

Each decided by experiment (the binary run, or the bytes read by hand):

- **W3 is F3, not P-D9.** Stage 2's IFUNC rule (F3, two addresses for one
  function) sees it inside view 1 before P-D9's comparison would; it
  fires on x86-64 PIE (GNU ld, mold) and on AArch64's mixed PIE (GNU ld,
  mold).
- **H1 on every lld and mold output with an IFUNC and a PLT**, E1 and
  the W3/W13 links included: `IRELATIVE` sits in `.rela.dyn`, before
  `.rela.plt`'s `JUMP_SLOT`s (D-41: their known hazard).
- **E1 x86-64 PIE, GNU ld and mold: F3** (the IFUNC in E1's `ifunc.c`,
  W3's form).
- **mold's A-list** in every dynamic output (A1 also for IFUNC symbols'
  S8, A2, A3, A9 — globals `STB_LOCAL` in `.symtab`, A13); GNU ld A10.
- **W10 on GNU ld AArch64**: flagged though GNU ld's built-in default
  interpreter is right (the line names none; proposal 3).
- **W13 AArch64 no-PIE, GNU ld: P-D9**: the executable's own uses take
  the IPLT entry while the library's reference binds the exported
  `STT_GNU_IFUNC` implementation (two addresses).

Every survivor, with its reason (all are equivalent or masked):

- **`dyn-rel-addend`, 11, x86-64 `GLOB_DAT` addend + 8**: equivalent.
  The x86-64 psABI computes `GLOB_DAT` as S, without the addend; glibc
  ignores it.
- **`dyn-rel-symbol`, 3, a `JUMP_SLOT` given another symbol**:
  equivalent; the PLT entry is dead. GNU ld's AArch64 PIE keeps
  `fb@plt`/`fc@plt` (the names are used only by `ABS64` data words, which
  get symbolic records) and its x86-64 output keeps `__tls_get_addr@plt`
  after relaxing every GD sequence; no branch reaches those entries.
- **`dyn-rel-order`, 3, an `IRELATIVE` swapped with a `COPY`** (lld,
  mold): masked. The output already carries H1 at that `IRELATIVE`
  (P-D10, D-41: every `IRELATIVE` after every symbolic record), and the
  mutant's finding is the same.
- **`versym`, 4, 0 → 1 on an undefined weak import nothing defines**
  (lld writes 0): equivalent. glibc reads 0 and 1 alike for a
  reference: no version.

Holes the table found and closed in this package: P-D5 now checks the
chains' shape (12 end-bit survivors before); P-D8 checks exported
definitions' versions (a copy's index naming another version makes
glibc's versioned lookup skip the copy: a split) and that an import
nothing defines carries no version; H1 covers `GLOB_DAT`, `COPY` and
absolute records, D-41's reason.

Not mutated: `DT_FLAGS`'s `DF_BIND_NOW` (`dyn-tag` flips `DT_FLAGS_1`'s
`DF_1_NOW`); swaps of two `DT_NEEDED` entries (`dyn-needed` replaces a
name; the swap is the committed dupdef test).

## Spec proposals (rule text for the `plumb.md` §12 owner)

1. **P-D9, the W table: W3 → "F3 (stage 2, in view 1), P-D9".**
2. **P-D10, last sentence:** "IPLT words have one `IRELATIVE`; every
   `IRELATIVE` is applied after every `JUMP_SLOT`, `GLOB_DAT`, `COPY`
   and absolute record (D-41; H1)." Also say in §13.1 that lld and mold
   show H1 in every output with an IFUNC and a PLT.
3. **P-D4, W10:** "its string is the command line's `-dynamic-linker`;
   when the line names none, a reference output is compared with that
   linker's built-in default (GNU ld: the target's; lld and mold: no
   `PT_INTERP`, P-D1), and a mortar output is P-D4." Today GNU ld's
   right default is flagged.
4. **P-D6, `DT_RELACOUNT`:** "ld.so applies the first `DT_RELACOUNT`
   records as `RELATIVE` whatever their type: the count is at most the
   leading `RELATIVE` run (every linker) and equal to it (mortar)."
5. **P-D4, RELRO:** "covers" is measured with `PT_GNU_RELRO`'s end
   rounded down to the page, as `_dl_protect_relro` does.
6. **P-D9, view 3:** "every use of the key reaches the fresh definition,
   except a use whose field cannot hold a library address (an input's
   32-bit absolute use in a no-PIE executable, R2), which fails only
   when another use of the key does reach it (a split: W12, F2)."
7. **P-D8, add:** "an exported definition whose index is 2 or more names
   a version under which a needed library defines the name (glibc's
   versioned lookup skips it otherwise); an import nothing defines has
   index 0 or 1."
8. **P-D5, add for the references:** "each bucket's entries are
   contiguous, the bucket word is the first, the chain's end bit is set
   exactly on the last, and each chain word is the name's hash with bit
   0 cleared" (mortar is already word for word).
9. **P-D2, add:** "stage 3 judges nothing further once an input is
   unreadable."
10. **P-D7/P-D9, W13 on AArch64:** an exported `STT_GNU_IFUNC` is P-D7 on
    x86-64 (the loader refuses a library's reference) but on AArch64 is
    judged by P-D9: accepted when every use of the executable is the
    `IRELATIVE` slot, P-D9 when its own uses take an IPLT entry.
11. **Stage 2 inside a dynamic output** (§12.1 lists them):
    `__rela_iplt_start == __rela_iplt_end`; GNU ld's AArch64 `-z now`
    `_GLOBAL_OFFSET_TABLE_` is the `.got` word holding `_DYNAMIC`; GNU
    ld's x86-64 `.eh_frame` FDE over `.plt` is the linker's; lld's
    `PT_PHDR` reserves room for one more header (`p_filesz` ≥ the table;
    mortar exact).
12. **P-D12, references:** a TLS record with symbol 0 against the
    executable's own block is accepted from the references; D-48
    forbids it to mortar only.

## What a mortar output's map needs for stage 3 (WP-053)

Stage 3 runs with the map alone when it carries the line:

- **`arg <word>`, every word of the link in order** (response files
  expanded, program name left out): the line is the source of D-1's
  kind, the interpreter, `-z now`/`relro`, `-rpath`, `-L` and every input
  with its `--as-needed`/`-Bstatic` state. Paths must be readable from
  the directory `xtask plumb` runs in (or absolute): the shared objects
  and scripts are read from them (P-D2).
- **`output`, `interp`, `runpath`/`rpath`, `bind`, `relro`**: facts,
  each checked against the `arg` words (P-D3); optional, but a written
  one must agree.
- **Hints** (`needed`, `copy`, `export`, `plt`, `iplt`): optional; stage
  3 recomputes all of them and does not read them today.
- The ordinary M1 records (files, places, pieces, defines) as for a
  static link: stage 3 re-judges every input relocation through them.

## Integration with WP-051's harness (`tests/link/dyn`)

After main brought WP-051's dynamic link tests (80 cases), stage 3 judges
every reference output of them on AArch64 and x86-64.

**The probe.** `mortar_plumb::STAGE: u8 = 3` (lib.rs);
`engine::stage3_present()` is `mortar_plumb::STAGE >= 3`. S1's "not
ET_EXEC" finding is no longer read.

**The line.** The `ld` wrapper also writes the words the linker got, one
per line, to `.linktest-ld-status-<line>.line`; a reference output is
verified with them (a `link ld` step with its own words). A mortar output
gets no line from the harness: its map's `arg` records are the line, and
a map without them is P-D2 "a dynamic output and no command line", a
failure. A mortar dynamic output therefore never passes unjudged; at the
join (WP-053, WP-055) the map must carry what "What a mortar output's map
needs" above lists, with paths readable from the link's directory (the
harness's base). The "outside stage 3" findings below fail a mortar
output like any other.

**Outside stage 3** (new P-D1 finding, `OUTSIDE`): a link stage 3 does
not model is named and nothing of stage 3 is judged: `--hash-style` other
than `gnu`, `--copy-dt-needed-entries`, `-shared`, static-pie (WP-052),
an output with `DT_VERDEF` (M4), a closure object no search finds. The
harness counts a reference's such output as not judged, `outside stage
3` (26 outputs in `tests/link/dyn`), and still judges its other findings.

## Not verified

- `-shared` (M4) and static-pie (S1) are refused by name.
- The loader model is glibc's; musl's or another loader's lookup rules
  are not modelled.
- A `DT_NEEDED` object not on the line is searched in `-rpath-link`,
  `-rpath`, the needing object's `DT_RUNPATH`/`DT_RPATH` (`$ORIGIN`
  expanded), its directory and `-L`; `ld.so.conf` and `LD_LIBRARY_PATH`
  are not read.
- Stage 2's classes on dynamic outputs were run but not re-tabled here.
- The ELF32 (i386) dynamic forms: no M2 target.
