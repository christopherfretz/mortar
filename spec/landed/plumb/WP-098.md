# WP-098 — the verifier judges `.gdb_index`

Branch `wp/098-plumb-gdb-index`. The rules are in `spec/plumb.md` §6.10
(P-G1 to P-G9), written before the code; the code is
`crates/mortar_plumb/src/gdbindex.rs` (the format rules, the output's
reading), `gdbnames.rs` (mortar's rules, the inputs' reading) and
`gdbdwarf.rs` (the DWARF reading both use: units, abbreviations, every
form's size, root-DIE ranges through `.debug_rnglists`, `.debug_ranges`
and `.debug_addr`). They run in the plain pass after the relocation
engine. The coverage report gains a `gdb index:` line.

Independence: the writer (`mortar_synth/src/gdbindex.rs`, `gdbread.rs`),
its tests and `crates/mortar/tests/gdb_index.rs` were not read. The
sources were gdb's manual (appendix J, "`.gdb_index` section format"),
`spec/synth.md` §17, `mortar_elf`, `mortar_diag`, `mortar_plumb`, and the
outputs of `mortar --gdb-index`, `ld.lld-22 --gdb-index`, `mold
--gdb-index` and `gdb-add-index` (gdb 16.3).

## 1. The rules

| rule | kind | one line |
|---|---|---|
| P-G1 | format | the header: not allocated, version 7-9, offsets in order, CU list at the header's end, each area whole entries |
| P-G2 | format | the CU list is the output `.debug_info`'s non-type units, `(offset, 4 + unit_length)`, in order |
| P-G3 | format, plus a mortar bound | an entry's `cu` is a unit, `low < high`, inside one allocated section; for mortar also inside its unit's merged live claimed ranges |
| P-G4 | format | the table is a power of two with an empty slot; offsets and names inside the pool, NUL-terminated; gdb's probe reaches each slot; no name twice |
| P-G5 | format | vectors: count ≥ 1, unit below CU+TU count, bits 24-27 zero, kind not 5-7 (kind 0 accepted) |
| P-G6 | mortar | presence (S-G1, S-G6, S-G8): the option, the chunk and its size, the section header and its place, the sets consumed |
| P-G7 | mortar | the inputs' units and name sets (S-G2, S-G3, S-G3a, S-G4a): the CU list is the placed input units; every debug-bearing unit has both sets (the silent `gdb-index-incomplete`) |
| P-G8 | mortar | complete (S-G4, S-G5): each name's value set and the address area equal what the inputs give |
| P-G9 | mortar | the bytes are S-G7's (version 7, the table size, name order, sorted vectors, the pool), naming the first differing area |

**What the format rules found on the references.** On lld's and mold's
indexes: nothing. On `gdb-add-index`'s (version 9): two things, both the
rule's error and both fixed in the rule, not declared as anomalies:

1. gdb writes adjacent ranges of a unit as one entry (unit 0's
   `[0x237d20, 0x237da8)` and `[0x237da8, 0x237dc0)` as one
   `[0x237d20, 0x237dc0)`). P-G3 now merges a unit's ranges where they
   touch.
2. On clang's split-DWARF units, gdb writes an entry `[a, a + 1)` for the
   global variable `g_total` (`.data`), outside every range the unit's
   root DIE states. P-G3's bound by the unit's own ranges is therefore not
   a format rule: it holds mortar's output only (where P-G8's exact
   comparison holds it too). The format part keeps `cu` in range,
   `low < high`, inside one allocated section (now including `NOBITS`:
   a variable may be in `.bss`).

No §10.2 anomaly was added (none is needed: zero P-G findings on lld,
mold and `gdb-add-index` outputs).

## 4. The sweep

`.gdb_index` joins `sweep::SECTIONS`, with field names (header word, CU
offset/length, address low/high/cu, slot name/vector offset or empty
slot, vector count/value, name, NUL). New case `gdbindex` of `cargo
xtask sweep` (full lane, not `--quick`): hello.c `-fPIE -g
-ggnu-pubnames`, `-pie -Wl,--gdb-index -Wl,--build-id=none`, sweeping
`.gdb_index` only (`run_sections`; `--case <name>` selects cases).
**8441 bytes, 0 survivors** on AArch64 (local, 51 s on 4 threads; hosted
20 s) and x86-64 (hosted, 27 s).

**Finding for the supervisor (not this package's to fix): the sweep's
other cases measure B1.** Their outputs carry mortar's build id, and the
sweep does not reseal it (the mutation tool does, §9.5): every flip
changes the id, B1 reports it, and the byte counts as caught. The same
`-pie` hello linked with `--build-id=none` and swept (`xtask plumb
--sweep`) leaves 33 survivor ranges (`.dynsym` `st_size` of 7 entries,
`st_info`/`st_other` bytes, `.gnu.hash` bloom word, `.gnu.version`
indices, `.got` words with `RELATIVE`/`GLOB_DAT` records, `.dynamic`'s
`DT_NULL` tail, `.plt` bytes, one `RELATIVE` record's offset and addend,
`.eh_frame_hdr` header bytes); with the id, 0. So WP-082/WP-088's "0
survivors" is B1's, not the field rules'. The `gdbindex` case links
without the id for that reason.

## 6. Spec findings against synth.md §17

1. **§17.7, the option.** "`arg` records give `--gdb-index`": a static
   link's mortar map has no `arg` record (plumb.md §3.2 puts them in the
   dynamic records), and every link of the gdb-index tests is static.
   P-G6 reads the option from `arg` words when the map has them, else
   from the presence of the `chunk synthetic .gdb_index` record, so in a
   static link "the option was given and the index is missing" is not
   distinguishable from "the option was not given". Proposed: write the
   `arg` records for static links too (a map change: a request to the
   supervisor, not made here).
2. **S-G5 and gdb's own index.** gdb 16's `gdb-add-index` puts a unit's
   variable addresses in the area (§2 item 2). S-G5's area (the root
   DIE's ranges) loses nothing gdb needs (the witness answers the same),
   but S-G5 should say it is narrower than gdb's own.
3. **Kind 0.** The manual calls kind 0 reserved; GCC writes it and S-G4
   copies it. P-G5 accepts it; S-G4 could say so.
4. **One value per use.** The manual: "one CU index+attributes value for
   each use"; S-G4 dedups and sorts. gdb reads either; noted for §17.8.
5. **Canonical names.** The manual says C++ names in the table are
   canonicalized; S-G4 copies the compiler's spelling, as lld and mold
   do. Not judged; the witness found no lookup that fails on it.
6. §17.8 could add: mold places `.gdb_index` after `.symtab`.
