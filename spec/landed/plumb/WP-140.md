# WP-140: stage 3's `bind(k)` over N alone in `Shared` (landed)

Follow-up of WP-137, which amends `spec/dyn.md` D-10 (`bind(k)` in
`Shared` ranges over N, not N ∪ U), a D-27 bullet and D-111 item 3: a
weak-only key whose every definition lies in an object that is not
needed stays undefined, `WEAK NOTYPE UND`, unversioned, the object
neither `DT_NEEDED` nor a `Verneed` (GNU ld; lld writes `FUNC`, mold
keeps the object needed and the version).

## The false finding

mortar's AArch64 `libcx.so` (WP-137, `g++ -shared` with the driver's
`--as-needed`: `libstdc++.so.6` and `libgcc_s.so.1` needed, the C
library dropped; crtbeginS's `__cxa_finalize` `WEAK NOTYPE UND`,
unversioned) got two P-D7 findings under mortar's rows: "an import's
type is not its definition's (D-23)" and "the import '__cxa_finalize'
has type 0 (D-23: 2)" (and the same for `vfn` in the C twin). mortar's
bytes are D-111 item 3's; the verifier was wrong.

**Cause.** `Model::bind_in` (stage 2's `bind(k)`) ranged over every
member of C in the loader's order, so the used C library still gave
`__cxa_finalize`'s `STT_FUNC`; `dynfields::imports` then fell back to
the loader's lookup (closure files included) when nothing bound it.
GNU ld's identical library was clean only because P-D7's type rows are
mortar's alone.

**Fix.** `Model.shared` (the line's kind); in `Shared` `bind_in` takes
members of N only, and `dynfields::imports` (P-D7 mortar's D-23 type)
does not fall back to the loader's lookup (input §8.6 searches nothing
in `Shared`): a key N does not define is `STT_NOTYPE`. `Exec` and `Pie`
are unchanged.

## Spec edits (`spec/plumb.md`)

- P-D19: imports are P-D7's import rule and P-D8 except that `bind(k)`
  ranges over N alone (D-10 as WP-137 amends it); the reference forms
  are judged as before; the loader's run-time lookup (P-D9, P-D17) still
  reaches the object through a needed object's `DT_NEEDED`.
- P-D7 (mortar), D-23 (§12.3): `STT_NOTYPE` also in `Shared` when no
  member of N defines the import.

## Other rules that consult a `Shared` key's binding (item 2)

- P-D7 (import set, `pd7`): `bind_in` over N ∪ U's order, now N alone in
  `Shared` through `bind_in`. The import branches report only strong
  references, so a weak-only key unbound is no finding.
- P-D8 unversioned imports (`pd8`): `bind_in`, now N alone; an unbound
  weak key asks for no version (GNU ld's, lld's index 1 clean). P-D8
  versioned imports keep the loader-lookup fallback: mold's `GLIBC_*` version
  is checked against the library that defines it, as before.
- P-D8 `vn_file` a `DT_NEEDED` name: unchanged, and it is what catches a
  `Verneed` of the object that is not needed.
- P-D6 (`DT_NEEDED` set, D-19a order, `model.needed`): ranges over N
  already; `pd6_shlib_undefined` ranges over N ∪ U by D-13 and runs
  only under `--no-allow-shlib-undefined` (existence of definitions, not
  binding): unchanged.
- P-D5 (hash lookup by name and version in the output): no binding.
- P-D9, P-D17 (views A and B), P-D11..P-D13, P-D24: the loader's
  run-time lookup (`Loader::bind`, `Model::lookup`), which rightly
  reaches the C library through `libstdc++.so.6`'s `DT_NEEDED`;
  view A's host imports are decided from the inputs (`Sets`, WP-121
  part 2). No change.
