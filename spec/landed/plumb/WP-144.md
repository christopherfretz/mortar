# WP-144: stage 3 on TLS in a shared object, four findings on correct libraries (landed)

Four findings of stage 3 (§12.5) on libraries whose bytes are right: three
on x86-64 (WP-127 part 2's), one on AArch64 (WP-124's). None was a
mislink; each was the verifier.

## Finding 2: x86-64 TLSDESC kept in a shared object (R1)

`__thread int t` read through `-mtls-dialect=gnu2`, `-shared` by GNU ld,
lld and mold: "R1 a TLS descriptor is not the local-exec form ... nor,
in a dynamic output, kept or the initial-exec mov (X-58)".

**Cause.** `x64rec.rs`'s kept branch compared the whole window
`x64_window` returns, which ends with the relocated 4-byte field: the
link writes the displacement to the GOT pair, the input holds 0, so a
kept `lea x@tlsdesc(%rip),%rax` never matched. Executables never showed
it (every reference relaxes there). **Fix.** Kept means the
instruction's three bytes are the input's (X-61); the field is the
link's and R4 checks the pair it reaches. `_TLS_MODULE_BASE_`'s
descriptor (`r_sym` 0, addend 0) holds the module's block start, not
X-47's relaxed T = 0 (an R4 that remained after the first fix).

**Measured placement of the descriptor** (`R_X86_64_TLSDESC`): GNU ld
in `.rela.plt` with `DT_TLSDESC_PLT`/`DT_TLSDESC_GOT`; under `-z now`
still in `.rela.plt`, without those two tags (eager). lld and mold in
`.rela.dyn` either way.

**Every form checked.** `tests/shared.rs` builds `tls.c` (a preemptible,
a hidden, two static and an imported thread-local) in the desc, gd and
ie dialects, `-shared` by each reference (`p_d26_x64_tls_libraries_verify_clean`;
mold only A3), and `p_d26_x64_tls_records_are_checked` mutates every
TLS record (`DTPOFF64`, `TPOFF64`, `TLSDESC` addend + 8; `DTPMOD64`
retyped `TPOFF64`), every static DTPOFF word beside a `DTPMOD64` with
`r_sym` 0 (+ 8) and every descriptor's `lea` (+ 16): each gives a new
finding (66 mutants at landing).

## Finding 3: `_TLS_MODULE_BASE_` in GNU ld's gnu2 shared object (Y5)

"expected 0xc, found 0x0": Y5 expected GNU ld's x86-64 executable value
(TP, the end of the block) in a shared object too. Measured (a gnu2
local-dynamic object, `PT_TLS` memsz 0x30, align 0x10):

| linker | shared object | `-pie` | `-no-pie` | static |
|---|---|---|---|---|
| GNU ld | 0, `STT_TLS` LOCAL in `.tdata` | 0x30 | 0x30 | 0x90 (align_up(memsz 0x88, 0x10)) |
| lld | 0, LOCAL HIDDEN, absolute | 0 | 0 | 0 |
| mold | the block start's address (A3) | same | same | same |

X-47 states the executable kinds; X-61 does not state the shared
object's value, so the sentence is the measurement: Y5's row in
`spec/plumb.md` now says GNU ld's executable value is TP and its shared
object's 0 (`symbols.rs`: `!e.shared`).

## Finding 4: mortar's x86-64 local GD static DTPOFF word (P-D9, D-46)

mortar's `l0.mortar.so` (WP-127 part 2): `DTPMOD64` `r_sym` 0 at 0x29a0
and the word 4 at 0x29a8 with no record, lld's word for word: correct.
**Cause.** AArch64's `tls_slot` puts a GD pair in `got_demands`; x86-64's
kept GD/LD sequence did not, so the constant word was "asked by nothing".
**Fix.** `SeqX::Kept(module, offset)` carries the pair to the caller,
which demands it (P-D9's D-46 sentence names it). Fixtures of mortar's
libraries (`tests/shared/x64tls/`, built by `gen.sh` with WP-127 part 2's
mortar at 3ae1238): `gd0` (the reproduction), desc, gd and ie judge
clean and every `tls_mutants` mutation is caught
(`p_d26_mortar_x64_tls_libraries`).

## Finding 1: GNU ld's spare `R_AARCH64_NONE` (anomaly A46)

Measured with `-nostdlib -shared` of N static thread-locals in the
traditional dialect: GNU ld writes exactly N records of type 0 with
`r_sym`, `r_offset` and `r_addend` 0 (N = 1, 2, 3, 5; the same with an
exported one beside them, with `-z now`, and with two functions using
one local: one record per local pair, i.e. per `DTPMOD64` with `r_sym`
0). They follow the `RELATIVE` records in `.rela.dyn` at index
`DT_RELACOUNT` onwards, inside `DT_RELASZ`; under `-z nocombreloc` they
sit in `.rela.got` and no `DT_RELACOUNT` is written. None for the
TLSDESC or initial-exec dialects; none from mold, none from lld (no
traditional dialect; desc and IE give none); none from any reference on
x86-64 (GD, gnu2, IE, nocombreloc) or i386. Outside A46: GNU ld's
`-nostdlib` AArch64 PIE that leaves `__tls_get_addr` undefined writes
one in `.rela.plt` for the PLT entry it dropped (no link test has it).

**The anomaly.** A46 (GNU ld, AArch64): P-D25 gives the exact shape its
own message, from a reference's AArch64 output only: `DT_RELA` records
(not `DT_JMPREL`'s) of type 0 with `r_sym`, `r_offset`, `r_addend` 0, at
an index not below `DT_RELACOUNT` (the count of leading records glibc
applies as `RELATIVE` without reading their type), no more of them than
`TLS_DTPMOD64` records with `r_sym` 0. Classified for GNU ld:
"A46: GNU ld writes a spare R_AARCH64_NONE record (all fields 0) in
.rela.dyn for each local general-dynamic pair of an AArch64 shared
object; glibc skips type 0 (spec/plumb.md §5.8)". Anything else of type
0 keeps P-D25's plain message; a type-0 record that names a key is now
reported in every output. `tls-shared-gd.test` loses `xfail(bfd)` and
declares `anomaly(bfd): A46`.

**Tests** (`tests/shared.rs`): `a46_aarch64_gd_libraries_verify_clean`
(GNU ld only A46, mold only A3); `a46_accepts_only_its_shape`: for each
of the three spare records, `r_offset` 8, `r_sym` 1 and `r_addend` 8 each
give a finding no anomaly names; so do the last record zeroed (one
type-0 record more than local pairs) and `DT_RELACOUNT` raised over the
spare records; and the clean library judged as mortar's output keeps
P-D25's plain finding.
