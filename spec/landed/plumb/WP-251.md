Verifier package after WP-229 (G-2; `spec/incr.md` IN-55 option (A)).

`spec/landed/incr/WP-229.md` §2 and §6, `spec/landed/plumb/WP-222.md` and

## 0. What needs a ruling

1. **How the mode is told (new sentence of M10), and a linker hook that
   contradicts it.** Incremental mode is the map's `incremental` record
   AND the line's words: `--incremental` last over `--no-incremental`,
   and none of IN-12's options that its words alone show (`-r`,
   `--emit-relocs`, a `--compress-debug-sections` other than `none`,
   `--gdb-index`, `--debug-names`, an `--icf` other than `none`,
   `--sort-common`, `--sort-section`, `--start-lib`, `-shared`). The
   output cannot show it (IN-17; measured, §2). When map and line
   disagree the output is judged as a plain one (a left-out set is M10).
   I first made the disagreement itself an M10 finding; the quick gate's
   `cargo test --workspace` then failed three of mortar's own tests
   (`crates/mortar/tests/incremental.rs` `a_kept_equal_cie_is_followed`,
   `padding_cies_and_dead_ranges_through_the_replay`,
   `replay_reproduces_and_each_table_matters`): their "replayed" links
   write a map that says `incremental` while the map's `arg` records are
   `a.o b.o -static --eh-frame-hdr -o .../replayed
   --mortar-map=.../replayed.map`, with no `--incremental` (measured by
   printing the verifier's input; I did not read the linker crate, so I
   do not know how the replay enters incremental mode). So the
   disagreement is NOT a finding now. Rulings asked: (a) is a map that
   says `incremental` from a line without `--incremental` legitimate
   (then IN-10/IN-11 and §3.2a should say how, and the verifier should
   know the switch), or should the replay's map carry the real switch, so
   that the disagreement can become a finding again? (b) accept "judged
   plain on disagreement" as the rule.
2. **`--icf=none` and `--compress-debug-sections=none`** are taken as not
   making the link plain (IN-12 names "`--compress-debug-sections` other
   than `none`" but just "`--icf`"). Proposed IN-12 text: "`--icf` other
   than `none`" (or tell me mortar's `--icf=none` is plain too: then the
   verifier must change). Measured: the verifier's option table reads
   `--icf=all` in a mortar map as M9 (no option mortar accepts spells
   it), so today only `--icf=none` can reach this row.
3. **A set with no record.** The new row needs the `discard ... unspecified`
   line (the brief's (a)); a set with no record in an incremental-mode
   output is M10. The older `-S`/`-s` and `--gdb-index` rows also accept a
   debug section with NO record (`fate.rs`'s absent branch calls the
   same row table). Not changed here; say if they should require the
   record too.
4. **The `--gdb-index` row has no `SHF_ALLOC` test** (an allocated
   `.debug_gnu_pubnames` left out under `--gdb-index` is accepted). The
   new row has one. Not changed here (not this package's row): fix?
5. **IN-12's output-kind clause** still reads "(until WP-066) an output
   kind other than a static executable", while IN-12a says WP-066 lifted
   it for executables. The verifier does not derive the output kind, so
   this does not change its judgement; the text is ambiguous for anyone
   who does. Proposed: strike "(until WP-066) ... linked)," from IN-12 and
   leave IN-12a as the rule.

## 1. The rule (spec/plumb.md §3.3 M10, the new row)

In an incremental-mode output, a non-allocated `.debug_gnu_pubnames` or
`.debug_gnu_pubtypes` input section, not in a COMDAT copy that is not
kept, has a `discard ... unspecified` record and is not in the output:
that is its reason. Both directions: such a set placed (`nplace`,
`merged`, `place`) in an incremental-mode output is M10 at the record
unless `-S`/`-s`; a non-allocated output section of either name with
bytes, when no record places a set, is M10 once per section. In a plain
output a left-out set is M10 as before. An allocated section of the name
is not debug information (placed right, left out M10). Any other name
(`.debug_pubnames`, ...) left out is M10. The full text, with the mode
sentence, is in `spec/plumb.md`.

Code: `src/opts.rs` (`Options.incremental`, `Options.in12`,
`incr_plain()`, `incremental_by_words()`), `src/fate.rs`
(`incremental_mode`, `gnu_index_set`, the `Unspecified` arm of
`judge_discard`, the placed arm and the output-section check of
`check`), `src/lib.rs` (passes the image to `fate::check`). A plain map
(no `incremental`) runs one boolean test per section more.

Finding texts:
- `section '.debug_gnu_pubnames' is placed in an incremental-mode output: incr.md IN-55 option (A) leaves the GNU name index out`
- `the incremental-mode output has section '.debug_gnu_pubtypes' (0x.. bytes): incr.md IN-55 option (A) leaves the GNU name index out`

## 2. What shows the mode

mortar's `inc5` (WP-229's lane test, AArch64, `--incremental=full`)
against `plain5` (mortar's plain link of the same inputs): the same
section names and types but for the two sets, the same 4 program
headers; sizes and addresses differ (IN-72's slack). A
`<output>.mortar-state` file is beside it, but the verifier is not given
it and IN-77b's full link may write none. So the mode is the map's word
checked against the line, never the map's word alone.
