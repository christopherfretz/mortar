# WP-166: the linker-defined export ruling (verifier)

Follow-up to WP-150 (dyn.md D-110 item 2 and D-21 item 2, record
`spec/landed/dyn/WP-150.md` §3a). The verifier derives the export of the
seven linker-defined names (`_etext etext _edata edata __bss_start _end
end`) the one way the ruling states, holds mortar to it, and names each
reference's other form. The `xfail` lines of
`dyn/shared/linker-defined-export` (mortar's) and
`dyn/dynsym/linker-defined-export-exec` (`xfail(bfd,aarch64)`) are gone.

## The rules as written

- **Shared (D-110 item 2; `shared.rs`, `compute`).** A name of the seven
  that no input defines, that a live object references (an undefined
  reference in the import set, `STV_DEFAULT`) and that the script does
  not make local is an export: `GLOBAL NOTYPE DEFAULT`, size 0, the
  script's version, preemptible by `line_preempts` as a `NOTYPE` key. It
  leaves the import set. The derivation is "an object references it",
  nothing else. P-D19 reports one missing ("... is in the export set and
  not defined in .dynsym (D-110)") and one extra ("... is in .dynsym and
  not in the export set"); P-D25 and P-D17 follow from the preemption.
  GNU ld's `-Bsymbolic-functions` cell (it binds a `NOTYPE` key there)
  is `line_preempts`' format rule, already measured: no anomaly.
- **Exec and Pie (D-21 item 2; `dynverify.rs`, `dynmodel.rs`,
  `dyncheck.rs` `pd7`).** The seven are file 0's definitions whatever a
  needed library defines: a `DT_NEEDED` object's `char _end[1]` does not
  make `_end` an import (so P-D11 does not ask a `COPY` of it, and P-D7
  no import). A name of the seven no input defines becomes file 0's
  when an object references it, a needed or used object references or
  defines it (`ref_dynamic`/`def_dynamic`), or `.dynsym` defines it
  (whatever `.symtab` reads). `Key.linker` marks such a key; the
  file-0 pass runs before the dynamic list, so a list may name one. It
  is exported iff `ref_dynamic`/`def_dynamic` holds it (the
  `defined_dynamic` clause), or an object references it and the line
  has `-E` or a `--dynamic-list` naming it. P-D7: the missing export
  ("... is defined by the program and referenced by a needed or used
  object, and is not exported", or "... an object references it and the
  line's -E or --dynamic-list exports it, and it is not exported (D-21
  item 2)"), and the converse ("'K' is exported[ under -E], and no needed
  library references or defines it and no object's reference under -E
  or --dynamic-list exports it (D-21 item 2)"), not judged when the line
  has `--export-dynamic-symbol`.
- **One past the end (P-D9 view 2; `reloc.rs` `internal_value`, also
  `x64rec.rs`).** A `RELATIVE` record or an absolute word whose value
  `s` is in `[E, align8(E)]`, E a `PT_LOAD`'s end, is an address of the
  output when the input symbol is a global or weak segment-end key
  (`_end end __end__ _bss_end__ __bss_end__ _edata edata __bss_start
  __bss_start__ _etext etext __etext`) no input defines and an output
  symbol of that name (any binding, defined, not a section symbol) has
  the value `s`. The window is Y5's (GNU ld's `_end` is the end rounded
  up to 8). It serves the abs-words site and the GOT-slot site.
- **A30/A34** (`anomaly.rs`): the static-pie and `-pie` forms now need
  `DF_1_PIE`. GNU ld libraries' GOT slots of `_end`/`__end__` were
  undeclared A30/A34 before: the same cause as the one-past-the-end
  record, which P-D9 now accepts.

## Judged per linker

| | mortar | lld | GNU ld | mold |
|---|---|---|---|---|
| Shared, the seven | strict | strict (clean) | strict, plus A58 for its other names | A57 |
| Exec/Pie, the seven | strict | strict (clean) | A59 (library defines them: `STT_OBJECT`, its size), A60 (`-E` with no reference) | A57 |
| one past the end | strict | strict | strict | strict |

- **A57 (mold).** No linker-defined export at all: P-D19 missing, P-D7
  missing, P-D17 view B, on one of the seven.
- **A58 (GNU ld).** A shared object exports `__etext` and the AArch64
  `__end__`, `__bss_start__`, `__bss_end__`, `_bss_end__` an object
  references, preemptible (P-D19 extra, P-D25, P-D7 "which does not hold
  it"), on an output without `DF_1_PIE`.
- **A59 (GNU ld).** Against a library defining the seven, the program's
  own `_end`, `_edata`, `__bss_start` take the library's `STT_OBJECT` and
  size 1, one byte past its section (S8 "... is outside its section").
  The value is right (the runs agree).
- **A60 (GNU ld).** Under `-E` the executable exports `_edata`,
  `__bss_start`, `_end` with no reference. Matched on the `-E` message
  only, so a GNU ld export without `-E` is a plain finding.

## Mutations (`crates/mortar_plumb/tests/ldef.rs`, `mutations`)

On both 64-bit targets, mortar's outputs and every reference's the
mutation applies to; each must draw the named finding, none of it an
anomaly.

| Mutation | Cells | Caught by |
|---|---|---|
| `_end` out of `.dynsym` (name `Xend`) | `sh` | P-D17 view B on `_end` |
| the same, an executable whose library references `_end` | `exref-pie`, `exref-nopie` | P-D7 "... referenced by a needed or used object, and is not exported" |
| `_end`'s `GLOB_DAT` replaced by a `RELATIVE` of its value | `sh`, `shfn` | P-D17 view B on `_end` |
| `-Bsymbolic`: the `RELATIVE` of `_end` replaced by a `GLOB_DAT` (moved last, `DT_RELACOUNT` lowered) | `shsym` (mortar only) | P-D25 "names '_end', which the line binds" |
| `end` exported, referenced by no object (`_end`'s value) | `sh` | P-D19 "'end' ... is in .dynsym and not in the export set" |
| the same, an executable | `exref-pie`, `exref-nopie` | P-D7 "'end' is exported, and no needed library ..." |
| `_end` exported though `local: *` hides it | `shloc` | P-D19 "... (a version script ... makes it local)" |
| `__etext` exported (mortar: no reference makes it one) | `shx` | P-D19 (mortar); P-D7 "a name twice in .dynsym" (references, which define it already) |
| `__executable_start` exported | `shx` | P-D19 |
| the one-past-the-end `RELATIVE` moved 2 bytes further | `shsym`, `shloc`, `pie-e` | P-D9 "a RELATIVE record on a .got slot ... which no GOT-indirect reference ... asks a slot to hold"; GNU ld R4 |

The `-Bsymbolic` swap is mortar's only: a reference's `DF_SYMBOLIC`
library may name a bound key (glibc binds it to the library's own
definition; P-D25's GNU ld form), so that swap is no fault there.
x86-64's `-pie -E` program has no record for `_end` (a PC-relative
use), so item 3's mutation is AArch64's in `pie-e`, both machines'
in `shsym` and `shloc`.

`clean`: every fixture's findings are nothing (mortar, lld), A58, A59,
A60 (GNU ld), A3, A9, A57 (mold).

## Tests

- `crates/mortar_plumb/tests/ldef/` (`gen.sh`, about 1.4 MB): `-nostdlib`
  links by mortar, lld, GNU ld and mold of the cells `sh shsym shfn
  shloc shx exref-pie exref-nopie exdef-pie exdef-nopie exdefr-pie
  exdefr-nopie pie-e`, AArch64 and x86-64.
- `tests/link/dyn/shared/linker-defined-export.test`: mortar passes;
  mold is `xfail` (A57: its library binds `_end` to its own, so mortar
  hosts no mold library).
- `tests/link/dyn/dynsym/linker-defined-export-exec.test`: anomaly
  A57 (mold), A60 (GNU ld).
- `tests/link/dyn/dynsym/linker-defined-def-exec.test` (new): a library
  GNU ld links (`shlib`; mortar refuses an object's `_end`, resolve
  §8.2) defines the seven; `-pie` and `-no-pie` programs, with and
  without a reference, run `api_end() == _end` (1; mold 0, A57).
- `tests/dyn.rs` W13E and `tests/shared.rs` `optail` (`e-plain`,
  `e-ex`): GNU ld's `-E` outputs now name A60.

## Unsaid by the specs

- D-21 item 2 under `--export-dynamic-symbol` (its patterns): not judged.
- Whether a needed library that DEFINES one of the seven makes the
  program's definition the library's type and size (GNU ld, A59) or
  `NOTYPE` 0 (lld, mortar): D-21 item 2 says "exported", not the fields.
  The verifier holds mortar to `NOTYPE` and names GNU ld's.
- mold's `-shared` link of an object that defines `_end` gives the
  linker's value (Y1 on mold's output); resolve §16/E14 says GNU ld does
  too and mortar refuses (§8.2). The lane avoids the cell (`shlib`).

## Not verified

- i386: stage 3 does not model i386 dynamic outputs (P-D1, one finding)
  and mortar refuses them, so neither rule is judged there; GNU ld's and
  lld's i386 forms were not measured.
- Y5 picks the first `NOBITS` section for `__bss_start`, mortar's
  `.pad.relro` or lld's RELRO padding, on an output with no `.data`: a
  false Y5 finding outside this package (the fixtures keep `int one = 1`).
