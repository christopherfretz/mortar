## 1. The rule (spec/image.md I-47a)

Where the record's section has a debug name, its symbol is a section
symbol or `STB_LOCAL`, and the symbol's section D has no `SHF_ALLOC` and
is in a COMDAT copy the verifier's keeper drops, the expected value is
K's place + `st_value` + A. K is the one member of the keeper's copy
with D's name and D's `sh_size`, no `SHF_ALLOC`, in the output. By the
supervisor's amendment (ruled during this package), K and D must also be
placed whole: neither may be `SHF_MERGE` or `.eh_frame`. In every other
case the expected value is I-47's tombstone, and the message names the
failed branch. The referring section is binding: a record of an
`SHF_ALLOC` section, or of a non-alloc section without a debug name,
that points at D keeps its old column (I-47's 0 for
`.gcc_except_table`, R5 for any other name, I-46). The keeper is §5.7a's (resolve.md §6.1, the one M10
holds the map to), derived from the inputs: the line's order when the
caller gives a line, `FileId` order otherwise. The map is not asked
which copy it kept. The map needs no new sentence: `nplace` gives K's
place, and `discard ... comdat` gives D's fate, which M10 already judges
against the keeper. K placed in pieces or ambiguous is
`section-not-locatable`, not a guess.

## 2. Two attribution defects found on the way (§3.3)

On real GCC `-g3` links, the verifier's rows of one file's many
same-named `.debug_macro` sections were wrong in GNU's, lld's and
mold's maps:

1. Step 3 (bytes) read a non-alloc row's bytes at an image address, not
   in the output section of its name, so it never matched. The rows fell
   to M3 ("placed with size ..., its input size is ...") and R1 cascades.
   It now reads the file bytes at the row's offset (§5.8's offset; mold's
   cursor).
2. GCC's `-g3` groups of one file can be equal outside their relocated
   words (a 0x10-byte unit of two `DW_MACRO_define_strp`). AArch64, C,
   DWARF 4, `src/{a,b,c}.c`: c.o had five such 0x10 sections, four of
   them dropped copies. They were ambiguous, so 20 records were
   `section-not-locatable` and 9 imports were not judged. The new step 4
   picks the one copy §5.7a's keeper does not drop. After it, the GNU and
   lld links of that case have 0 not-checked records and 43 kept-copy /
   43 tombstone records, one per import.

Step 4 ranks in `FileId` (map) order, because `locate` has no line. For
a foreign map whose file order differs from the line's, it could pick a
copy the engine's line-ordered keeper drops. That case was not seen; it
would show as findings, not as a silent pass.

## 3. The reference columns, measured

- **GNU ld.** Its condition is `_bfd_elf_check_kept_section`: the first
  member of the keeper's copy whose sorted (name, `st_info`, `st_other`)
  list of defined symbols equals D's, then an equal size. The name is
  not compared. On WP-249's probe (`gnu/k.s`, `gnu/d.s`, with and without
  `KREF`, AArch64 and x86-64) GNU's map verifies with 0 findings,
  including C4 (a `.debug_types` offset written into a `.debug_macro`
  field). C4 is judged, not left "not judged": the condition can be read
  from the inputs alone. The old (name, size) set accepted C4 only by
  coincidence.
- **lld**: 0, or 1 in `.debug_ranges`/`.debug_loc` (unchanged).
- **mold**: on the probe it writes 4 at `.Ld + 4`, i.e. 0 + A, for a
  dead target without `SHF_ALLOC`, and 0 for an `SHF_ALLOC` one. The
  column is now "0, or A". mold keeps a second copy of every `wm4.*`
  group (macros.py: `copy=` equals the import count), so its `-g3`
  imports have live targets.

## 4. Measured on GCC 14 `-g3` with glibc (scratch `probe.sh`)

AArch64 and x86-64; C and C++; `-O0 -g3` and `-O2 -g3
-ffunction-sections -fdata-sections`; DWARF 4 and 5 (32 variants). Each
variant was linked by the driver with GNU ld, lld 22, mold, and mortar.
mortar's output was also patched by WP-249's `macros.py` to the
redirect and to 0. On every variant:

- GNU: `kept-copy` equals macros.py's `redirect=` count (39 to 63). It
  has 0 findings on x86-64 and only Y3 `__TMC_END__` (A10) on AArch64.
- lld: 0 findings; its `tombstone` count equals the imports.
- mortar as linked today: one R1 per import (39 to 54), "...; it holds
  a tombstone".
- mortar patched to the redirect: B1 only (the patch changes the bytes
  under the build id).
- mortar patched to 0: B1 plus one R1 per import.
- mold: only S8/Y1/Y3/Y5 (and one S11 on x86-64), with no R1. On the
  freestanding links of `reference_columns_on_gcc_g3`,
  `anomaly::classify` accepts every mold finding. On the glibc links the
  findings were read by rule letter only, not classified one by one.

WP-249's probe (`rprobe.sh`, 8 links): GNU and lld have 0 findings;
mold has S8 and Y3 only (A3, A9). mortar has 10 R1: C1, C1+4, C3, C8,
C9, C10, C11, C13, C14 and I1, every one expecting the kept copy. C2
and C4 are accepted as tombstones (no member of the name; another
size).

## 6. The questions of the linker's hand-back

- **M3 on GNU's and mold's maps of GCC `-g3` links** ("a4.o
  '.debug_macro' is placed with size 0x10, its input size is 0x51").
  Yes, I judged GNU ld, lld 22 and mold outputs of GCC `-g3` objects,
  and before §2's fixes I saw exactly these M3 findings and the R1
  cascades behind them. It is the defect of §2, and this branch fixes it
  in `locate.rs` (§3.3 steps 3 and 4). The name alone does not settle
  it: one file has dozens of `.debug_macro` sections, so a map row is
  matched by size, then by bytes, then by fate. A wrong early match
  takes the section a later row needs, and that row then fails the size
  rule (M3). After the fixes: no M3 on any of the 32 glibc variants for
  any of the three linkers, nor in `reference_columns_on_gcc_g3`. The
  linker's four lane tests (`debug/macro-import-*`) were not run here:
  they are on the linker's branch.
- **`split/gdb-index-refused.test` line 81.** The generic rule covers
  it, with no special case. On this branch the lane test fails because
  mortar's base output holds all ones; the verifier expects 0x0 at both
  words. Checked on the bytes: a link of the test's `x.S` (GROUP and
  GROUP+ORPHAN) with today's mortar has `.debug_gnu_pubnames+0x24` and
  `.debug_gnu_pubtypes+0x24` = 0xffffffff, and the verifier expects 0x0,
  the offset of x-group1's kept `.debug_info` (size 0x19). So the
  linker's GNU-equal value 0x0 is the expected one. The hand-made case
  of that shape is I in the test above.
