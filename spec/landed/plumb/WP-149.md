# WP-149: version definitions in a shared object (verifier)

Follow-up to WP-125 part 2 (`spec/dyn.md` D-114, D-115; `spec/resolve.md`
§9.7). Four false findings on versioned libraries are fixed and their
markers removed. A new rule, P-D27, checks the version definitions and
the `.gnu.version` of a shared object. WP-147 (M10's line roots, P-1's
placeless exports) is merged in, and the export set has one derivation
that M10, P-1 and P-D19 all ask.

## The four false findings

1. **P-D7 "a name twice in .dynsym"** (mortar: `interpose-default`
   `libi.so`, `symver-old-and-default` `libs.so.1`).
   - Cause: the duplicate check was mortar-format only, and it keyed by
     name alone. GNU ld's library of the same shape had no such check.
   - Rule as amended (every format): STB_LOCAL entries aside, a name may
     stand twice exactly when the entries' version indices (masked with
     0x7fff) differ and at most one is not `VERSYM_HIDDEN`.
   - Markers removed: `xfail(mortar)` in both tests.
2. **P-D7 "'foo' is exported with size 48 (.symtab 8)"** (mortar and mold:
   `symver-hidden-by-own-node` `libh.so`).
   - Cause: the rule compared the export with the first `.symtab` symbol
     named `foo`. mortar and lld write `foo@V1` and `foo@@V2` both as
     `foo`, and the first one was the dropped `foo@V1`.
   - Rule as amended: the `.symtab` entry is the first non-local defined
     one whose name is the export's and whose value is the export's.
     The name is `foo`, or GNU ld's `foo@V1`/`foo@@V2` by its
     `.gnu.version`. With several candidates, the first at that value is
     taken. With none, the first global of the name is used (as before).
   - Markers removed: `xfail(mold)` and `xfail(mortar)`.
3. **R1 on the call to `foo@plt`** (GNU ld: `interpose-default`
   `libi.so`).
   - Cause: the loader model's dynbind keyed every defined `.dynsym`
     entry by its bare name. GNU ld writes `foo@V1` (hidden) before
     `foo@@V2`, so `foo` was bound to the hidden entry.
   - Rule as amended: a hidden entry is bound as the key `foo@V1`. An
     unversioned lookup never finds it (glibc's `check_match`). This
     covers the TLS branch too.
   - Marker removed: `xfail(bfd)`.
4. **Y3 "'foo@V1' has another binding"** (lld: `symver-hidden-by-own-node`
   `libe.so`, `--export-dynamic`).
   - Cause: the verifier applied mortar's §9.7 rule 12 to every format.
     lld makes `foo@V1` local when a `local:` entry of V1 matches `foo`
     and no exact `global:` entry of V1 names it, whatever `-E` says.
     mold never makes a `.symver` key local; that per-format rule also
     clears mold's P-D19 on `libh.so`.
   - Rule as amended: rule 12 is each format's, as measured (dyn.md
     §17.8). A hidden key the script makes local is the local key
     `foo@V1`, not the plain `foo`.
   - Marker removed: `xfail(lld)`.

`tests/link/xfails` had no `dyn/version` line. No finding was true on a
reference's bytes, and no anomaly was added.

## P-D27 (new)

The rule is in `spec/plumb.md` §12.5, P-D27; the code is
`shared::pd27`. The old DT_VERDEF line of P-D22 now points to it.

**Inputs.** The script's text is read from the files that the map's
`version-script` records name. For a reference, the files come from
the line's `--version-script`. The map's `version-script` record plus
the line's `arg` records are enough: no new map record is needed.
`-soname` and `-o` come from the line (`SharedLine.output` is new).

**What it checks:**
- `DT_VERDEF` is present exactly when the script names a node.
- `DT_VERDEFNUM` equals the nodes + 1, and equals the chain length.
- Each Verdef:
  - `vd_version` is 1 and `vd_ndx` is its position + 1.
  - `vd_flags` is `VER_FLG_BASE` exactly on the first Verdef.
  - `vd_hash` is the ELF hash of its name.
  - Its names: the base is the soname, else the output's name. Each
    node is followed by its parents, last-written first (mortar and GNU
    ld).
  - `vd_cnt`, the last `vda_next` and `vd_next` are consistent with
    the chain.
- The `.gnu.version_d` header: `sh_info`, `sh_link` (`.dynstr`) and
  `sh_addr`, plus mortar's `sh_addralign` 4.
- `vna_other` is above the definitions' indices: one index space,
  definitions first.
- `.gnu.version`, for each `.dynsym` entry:
  - a local entry: 0;
  - an import: 0, 1 or a need's index, never hidden, and never a
    definition's index;
  - GNU ld's node symbols: their node's index;
  - each defined export: one of the indices that the export set gives
    its name, each consumed once, with the hidden bit exactly for
    `foo@V`.

**Measured** (all four linkers, AArch64 and x86-64):

| fact | GNU ld 2.44 | lld 22 | mold 2.37 | mortar |
|---|---|---|---|---|
| first `vna_other` | defs + 1 | defs + 1 | defs + 1 | defs + 1 |
| base name without `-soname` | basename of `-o` | `-o` as written | basename | basename |
| parents written | yes, last-written first | no (`vd_cnt` 1) | no | yes, as GNU ld |
| a node with two parents (`V3 {..} V1 V2;`) | accepted | refused (`; expected`) | refused (`expected ';'`) | accepted |
| `.gnu.version_d` `sh_addralign` | 8 | 4 | 4 | 4 |
| unversioned weak import's versym | 1 | 0 | 0 | 1 |

GNU ld's AArch64 libraries also keep nameless STB_LOCAL section
symbols in `.dynsym`, with versym 0.

**Judged.**
- mortar: every item.
- References: every item except those listed below.

**Not judged for a reference:**
- lld's and mold's parents, which they do not write;
- lld's base name, beyond equality with the `-o` as written;
- the references' `sh_addralign`.

**Not judged for anyone:**
- the layout of `.dynstr` (D-116);
- i386 (P-D1).

## The export set, one derivation (with WP-147)

`shared::ExportRule` decides whether a key (`foo`, `foo@V`, `foo@@V`)
of default or protected visibility is exported, and at which version.
It takes the script, `-E` and the format. Three things ask it:
- P-D19's export set;
- P-1's placeless keys: a key with no place is placeless only when
  the rule exports it, and one the script makes local is local;
- M10's export roots (`fate::line_roots`), through
  `Engine::exports`. Stage 3 sets it from the shared set's rule, or
  `ExportRule::plain` for an executable with `-E`.

A name that a version script's `local:` takes out is not a root, so
mortar may collect its section under `--gc-sections`. A `.symver` key
is a root when its node exports it. WP-147's text "mortar refuses
version scripts" is corrected.

Without `PT_DYNAMIC`, stage 3 does not run; this is WP-147's test
shape, a map that says `output shared` on a static output. In that
case the line's files are not read:
- without a script, every default global is a root, as WP-147 had it;
- with a script, no export is taken as a root.

Measured (`dyn/version/gc-local-unreferenced`, both arches): GNU ld,
lld, mold and mortar all collect the sections of `gone` and `data_gone`
when `loc.map` makes them local. All four keep them, exported at V1,
under `exp.map`. mortar writes `discard ... gc` for both under
`loc.map`, and `place` for both under `exp.map`. mortar did not
collect a section that the script exports: no mislink.

## `.symtab` of a version-local symbol (WP-150's)

**Today.** Y3's binding and visibility rows are dropped for every key
in the set's local keys (`filter_view1`, by the full key and by its
base name). Y3 therefore accepts both forms for every format: mortar's
`STB_GLOBAL`, and GNU ld's and lld's `STB_LOCAL`. It still judges the
value, section, type and size. It is not a finding now.

**After WP-150.** Once WP-150 decides mortar's form, mortar's map is
held to it: the rows are dropped only for a reference, and a non-LOCAL
mortar entry of a local key becomes Y3's binding finding.

The `.symtab` name of a `.symver` key matches in both forms (P-D7)
until WP-150 decides that too.

## Tests

`crates/mortar_plumb/tests/shared.rs`:
- `p_d27_verdef_libraries_verify_clean`: the new case `verdef`. It
  builds `vd.c` under `vd.map` (with `-soname`) and `vd3.map` (no
  soname; lld and mold get `vd31.map`, with one parent), with the
  import `ext@X1` from `libvdx.so`, by each reference on both arches.
- `p_d27_verdef_mutations_are_caught` and `p_d27_mortar_libraries`
  (fixtures `tests/shared/verdef`, `gen.sh`). Each mutation is a new
  P-D27 finding, on every library:
  - a wrong `vd_hash`;
  - `VER_FLG_BASE` cleared on the base, and set on V1;
  - V1's and V2's `vd_ndx` swapped;
  - `DT_VERDEFNUM` ± 1;
  - the last node missing;
  - the base's name wrong, and V1's name wrong;
  - a wrong parent, where the library has one;
  - `vd_cnt` ± 1;
  - `bar`'s and `baz`'s indices swapped;
  - the hidden bit cleared on `foo@V1`, and set on `bar` and on
    `foo@@V2`;
  - `bar`'s index set to 0, and to 1;
  - the import's index set to 2.
- `p_d27_mortars_alignment_only`: GNU ld's library judged as mortar's
  is `sh_addralign 8`.
- `m10_export_roots_follow_the_version_script` (fixtures
  `tests/shared/gcver`):
  - mortar's `loc`/`exp` libraries: clean;
  - the `loc` records under `exp.map`: M10 for `gone` and `data_gone`;
  - the `loc` records with no script: M10 for both.
- `tests/placeless.rs wp147_gc_of_a_line_root_is_m10` still passes.

Link test: `tests/link/dyn/version/gc-local-unreferenced.test` (new).

## Not verified

- i386: there are no versioned libraries in stage 3.
- The `.dynstr` layout (D-116).
- `--exclude-libs` in `ExportRule`. mortar refuses the option, and P-D19
  reads it per object.
- An executable's version script: WP-150's.
- With a script and no `PT_DYNAMIC`, M10's export roots are not
  derived.
