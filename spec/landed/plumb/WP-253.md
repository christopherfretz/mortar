# WP-253: P-I2's neutral list and P-I6's grammar of IN-51/IN-51b

Verifier package after WP-228 part A (the one 38-byte table, IN-51b's
table of exact bytes). Written from `spec/incr.md` IN-51, IN-51b,
`spec/landed/incr/WP-228.md` §A.2-A.6, `spec/plumb.md` §6.8 and from
mortar's outputs. No linker crate was read (not `mortar_image`'s
`neutral.rs` either): the forms in `src/neutral.rs` are typed from
IN-51b's table. Base e14dd5f4, + 0592b43d (batch 15's AArch64
`static-identical` baseline, cherry-picked as the supervisor asked).

## 0. What needs a ruling

1. **The table's place and when it is required.** IN-51 says "at the end
   of `.debug_abbrev`". mortar's map names it as its own line,
   `dead .debug_abbrev <size-0x26> 26 neutral`. Measured on real links:
   a separate line, ending at the section's end. The rule: the table is
   the section's last 38 bytes, inside one `neutral` line that ends at
   the section's end. `T` is its offset. It is required when the map
   says `incremental`, or when there is a `neutral` line in
   `.debug_info`/`.debug_types` (a unit must name a table), and the
   output has a `.debug_abbrev`. A plain map's dead lines with no
   neutral unit do not need it. A second copy anywhere before `T` is a
   finding (non-zero bytes).
2. **`.debug_info` versions 2 and 3.** IN-51b's v2-v4 row writes
   `04 00`. IN-51 says a neutral unit has "the same version" as the
   contribution it replaces. I accept `V` 2 to 4 with the v4 layout and
   code 1. Code 4 (`DW_FORM_sec_offset`) is accepted with `V` 2 or 3
   too, although that form is not defined before DWARF 4. Ruling: allow
   only `04 00` (then IN-51's "same version" needs a v2/v3 sentence), or
   keep 2-4.
3. **A base must name a neutral form.** A code-3 base names
   `D + 8` where `D` starts a v5-header form of a `neutral`
   `.debug_addr` range. A code-4 base names the start of a headerless
   one. A dead `.debug_addr` left as compiled (an IN-53
   `contribution` line) is not accepted as a base target. Separately,
   `contribution()` (unchanged here) still rejects a headerless GNU
   table: WP-229 left those as compiled. Say whether either should be
   accepted.
4. **A v5 `.debug_addr` table no code-3 unit names is accepted.**
   IN-51b does not say that a v5 form must be named. IN-51 says "a dead
   table stays named by its neutral unit". WP-228 §A.3 measured
   readelf's "Corrupt .debug_addr" for this case. A **headerless** zero
   range that no code-4 unit names is a finding: it reads as a v5
   header of length 0, below the minimum 8. That is what §4 below finds
   in 48 emulated outputs. Ruling: make the unnamed v5 table a finding
   too (IN-51's sentence), or accept it.
5. **`B` must be the exact smallest width.** IN-51b: "the ULEB length
   in the smallest width `k`" that ends the block at the unit's end. A
   wider (still valid) ULEB is a finding.
6. **Little-endian only.** Every multi-byte field is read and
   compared as little-endian (both targets of the brief). A big-endian
   output's neutral ranges would be findings. No big-endian target
   exists today.
7. **Live `.debug_types` units are not walked by P-I4.** Only the
   neutral ranges are judged here.
8. **The fixtures were converted, not relinked.** The incremental-mode
   outputs checked in under `tests/symfill`, `tests/symnames` and
   `tests/gnuindex` predate the 38-byte table. A relink with this base's
   mortar changed other bytes that `symfill`'s `edit.py` depends on. So
   `tests/retable.py` rewrites each one in place: the old 9-byte table
   becomes the 38-byte one at the same offset, and the later
   non-allocated sections and the section headers move by 32. None of
   these outputs has a build id. `symnames`' external evidence (WP-140's
   `t1/inc`, another agent's directory, read-only) is converted the
   same way in its scratch copy, and its build id is resealed
   (`buildid::reseal`). Ruling: accept, or have the fixtures relinked
   (and `edit.py` updated).
9. **The WP-228 harness and the decision records.** `place.py` writes
   its `dead` lines just before `end`, which is after mortar's decision
   records (WP-212). `spec/plumb.md` §3.2 says decision records follow
   the `dead` records, so the map parser refuses every emulated map:
   816 of 886 outputs were not judged on the first run. I judged them
   through a wrapper (`xtask` replaced in `forms.sh`'s
   `CARGO_TARGET_DIR_WP`) that moves those lines to just before the
   first decision record, and changes nothing else. `place.py` is not
   mine: it should insert before the first decision record.

`spec/incr.md`: nothing in it was wrong for this package. The
ambiguities are 2, 4 and 5 above.

## 1. The rule text (spec/plumb.md §6.8)

- P-I2: `neutral` is allowed in the 13 sections IN-51b gives a form
  (`.debug_types`, `.debug_loc`, `.debug_macro` and `.debug_macinfo`
  are new). It is not allowed in `.debug_aranges`, `.debug_str` or
  `.debug_line_str`.
- P-I6: a neutral range is a tiling of exact IN-51b forms. The full
  text is in §6.8. In short:
  - **The one table.** It is required, at its place, as in §0.1.
    Every other neutral `.debug_abbrev` byte is zero.
  - **`.debug_info`.** Either version's form may appear in any range,
    with `A` equal to the output's and `T` equal to the table. Code 1
    is accepted in both versions. Code 3 is v5 only and code 4 is
    v2-4 only, with bases as in §0.3. `B` is exact.
  - **`.debug_types`.** v4, code 2, signature
    `0xdead << 48 | offset`, `type_offset` 23.
  - **`.debug_line`.** The v4 and v5 headers byte for byte, then
    `0x06`.
  - **Lists.** The v5 header with `A`, then zeros.
  - **`.debug_str_offsets`.** The v5 header, then zero entries.
  - **`.debug_addr`.** Headerless exactly at a code-4 base, otherwise
    the v5 header.
  - **`.debug_ranges`, `.debug_loc`.** Zeros, at least `2·A`.
  - **`.debug_macinfo`.** Zeros.
  - **`.debug_frame`.** A v1 CIE with alignment factors 1/-4 and
    column 30, then zeros.
  - **`.debug_macro`.** `u16(V) 00 02 00 x… 00 00`, with `V` 4 or 5.
- **Newly findings.** Other fixed fields in line headers, v2/v3 line
  tables, other CIE factors or columns, a unit address size that is
  not the output's, list headers with another address size, a
  non-minimal `B`, a unit naming another table, and the per-file
  tables.
- **Newly accepted.** A v5 `.debug_addr` with `A` = 4 in ELFCLASS32,
  and an 8-15-byte `.debug_ranges` range in ELFCLASS32.

Reasons: IN-51b's table is exact bytes, so anything else is a
different form. "Either version in any range" is the spec's own
sentence. A table no unit names is IN-51's "stays named".

Code: `crates/mortar_plumb/src/neutral.rs` holds the pure judgement
`judge(&View) -> Vec<Bad>` and the forms. `deaddwarf.rs` builds the
`View` from the image and map, and maps each `Bad` to a P-I6 finding
at the range's start and the first differing offset. `dead.rs`'s
P-I2 list is `neutral::SECTIONS`.

## 4. Real outputs (`tests/incr-design/wp228/forms.sh`)

All 12 batches ran: base, o2, frame, types, macro (gcc and Clang),
split × AArch64, x86-64. That is 886 outputs: 816 emulated plus 70
reference full links. Every one was judged, through §0.9's map fix.

| WP-228 §A.4 row | before | after |
|---|---|---|
| 1 the one table | 886 | 0 |
| 2 `.debug_info` codes 3/4 | 116 | 0 |
| 3 `.debug_loc` P-I2 + P-I6 | 144 + 144 | 0 |
| 4 `.debug_macro` | 88 + 88 | 0 |
| 5 `.debug_macinfo` | 48 + 48 | 0 |
| 6 `.debug_types` | 60 + 60 | 0 |
| 7 `.debug_addr` named by a v4 unit | 64 | 0 (`addrbase`: 0 of 16) |
| P-I3 `$d` (emulation artefact, stays) | 1,784 | 1,784 |

Other findings:

- **48 × P-I6 `.debug_addr`: "a form of 4 bytes is below the minimum
  8".** These are DWARF 4 `-gsplit-dwarf` (GCC 14, Clang 22), AArch64
  and x86-64, in the `plain`, `pieces` and `v4` variants (S2-S5). WP-228
  counted them in its row 7. **The output is wrong by IN-51**,
  confirmed by the bytes:
  - `gcc14-a64-dw4-split` `s2plain`: `.debug_addr` 0x50..0x88 is 56
    zero bytes. The units' `DW_AT_GNU_addr_base` values are 0, 0x18
    and 0x88. The neutral unit at 0x68 is code 1, so nothing names
    0x50.
  - `clang22-x64-dw4-split` `s2v4`: 0x68..0xa8, the same.
  - In the `addrbase` variant of the same link, the neutral unit has
    `DW_AT_GNU_addr_base: 0x68`, and 0 findings.

  So a headerless dead table no unit names is not a form. G-1's writer
  must keep the base (the `addrbase` form) whenever the dead file has a
  `.debug_addr`.
- **1,344 × Y6/Y7 on `b.cc`** (768 outputs: every emulated output but
  kiln's, whose objects have no STT_FILE). `.symtab` keeps the dead
  file's STT_FILE `b.cc` (st_info 0x4) after `place.py` drops the file
  from the map. This is the same emulation artefact as `$d` (the old
  file's locals stay), from WP-246's rules, which WP-228's verifier
  predated. It is not a neutral form. An update drops the symbol.

Evidence (small) is in the scratch `wp253/evidence/`: the hex dumps,
the base lists and the per-batch summaries.
