# WP-020b: `mortar_core`, part 2: `par`, `hash`, `intern`

`spec/model.md` §6 (the deterministic parallel helpers and the scheduling
seed), §6 rule 5 (the fixed hash), and the numbering of §2.3 with the
interner it runs on. Safe Rust, `std` only. `lib.rs`, `id.rs` and the
manifest are unchanged (they belong to WP-020a).

## What it does

- **`par`.** `Pool` is the thread count (`--threads`) plus an optional
  scheduling seed. It is `Copy` and holds no threads. The helpers are
  `for_each`, `for_each_init`, `for_each_part` (rule 1: the caller passes
  disjoint parts, e.g. from `split_offsets`, `split_ranges` or
  `chunks_mut`), `for_each_mut`, `for_each_block` and `blocks` (rule 6),
  `map`, `map_collect` (flat rows plus offsets) and `map_collect_vecs`
  (rule 3), `prefix_sum`, and `sort_by` / `sort_by_key` (rule 4). With one
  thread and no seed, everything runs inline on the caller and nothing is
  spawned. Test support is `check_schedules`, `TEST_THREADS` = {1, 2, 7,
  64} and `TEST_SEEDS`.
- **`hash`.** `hash_bytes`, `hash_u64`, `combine`, `FixedHasher` /
  `FixedState` (a `BuildHasher`), and `HashMap` / `HashSet` aliases.
- **`intern`.** It has:
  - `InternKey`, implemented for `&[u8]`, `u64` and `SymName`;
  - `SymName { name, version: Option<&[u8]> }`, with `parse` for a
    relocatable object's `foo` / `foo@@V2` / `foo@V1`;
  - `Interner`, `Inserter`, `Frozen`, `Mention`, `Slot`;
  - `number::<K, I>(pool, counts, keys) -> Numbering { map, offsets,
    names }`, which serves both `SymbolId` and `ComdatId` (and any key);
  - `Names`, which looks up by key and gives each id's key, hash and first
    mention.
- **Tests.** 33 tests in `tests/par.rs`, `tests/hash.rs` and
  `tests/intern.rs`, named after their spec sections. Two deliberate
  mutations were checked against them: a merge that takes ties from the
  later run, and a first mention without its minimum. The sort test and
  three numbering tests failed on them.
- **Benches.** Run by hand: `examples/{intern,hash,par}_bench.rs`.
  `tests/intern_support/` holds the realistic workload: mangled C++ names
  with long shared prefixes, heavily shared among files, and one string
  table per file as real inputs have.

## The interner: designs measured

The workload: 2500 files and 1,506,043 non-local mentions of 523,005
distinct keys, with average names of 66 bytes. 75 % of mentions go to
150k shared names with a cubic skew towards the popular ones; 25 % are
the file's own. Times are medians of 7 runs per configuration, over 3
runs of the program. The host is a 24-core aarch64 VM shared with other
agents, at load average 27-39 throughout, so **the numbers are noisy**:
read them to about ±20 %, more at 8 threads.

| configuration | 1 thread | 2 | 4 | 8 | bytes/key |
|---|---|---|---|---|---|
| baseline: `std` `HashMap<&[u8], u32>` + SipHash, sequential | 227-243 ms | | | | |
| baseline: same with `FixedState` | 139-149 ms | | | | |
| **chosen: lock-free, entries inline in `OnceLock` cells** (`number`, all passes) | 253-273 ms | 133-174 | 75-96 | **40-60** | 106 |
| lock-free, `AtomicU64` tag+index cells, entries in lazily allocated `OnceLock` segments | 299-433 | 165-217 | 90-113 | 55-66 | 80.5 |
| 256 shards behind `Mutex`es (the first design) | 286-376 | 253-314 | 155-288 | 123-316 | 95.3 |

The rejected rows were measured on an earlier layout of the same
workload, partly or entirely. In that layout every file referenced one
shared copy of each name, so a mention's own bytes were a cache miss
too. It slows every configuration, the baseline included (170-200 ms
there). The conclusions below rest on comparisons made within the same
runs.

- **Throughput.** The chosen design reaches 25-37 M mentions/s at 8
  threads, against 10-11 M/s for the best sequential `HashMap`. Pass 1
  alone (inserts only) takes 32-41 ms at 8 threads. That matches the
  control of 8 threads each with a private table (48-62 ms), so sharing
  the table costs nothing measurable.
- **Why the mutex design was rejected.** It lost its scaling, erratically:
  8 threads took 115-262 ms where the private-table control took 42-50 ms
  in the same runs. The cost was in sharing the locks, not in the table.
  On an oversubscribed host (which a developer's machine running a build
  is), a lock holder that gets preempted stalls every thread wanting its
  shard. Cache-line transfers of the lock word on every insert add to
  that.
- **Why the segmented layout was rejected.** It costs one cache miss more
  per lookup (cell, then entry, then key bytes; hashbrown has two misses).
  Putting the entry in the cell recovered single-thread insert speed:
  inserts alone run at 160-164 ms for plain names against hashbrown's
  139-149 ms for the whole baseline.
- **Where the single-thread time goes.** The chosen `number` at one
  thread is about 1.7 times the `FixedState` baseline:
  - the `HyperLogLog` sizing pass, about 33 ms (it parses and hashes every
    mention);
  - pass 1, about 210 ms. The baseline does not split names at `@`; that
    split costs 15-50 ms of it here;
  - passes 2 and 3, about 25 ms (a random read of each mention's entry,
    then of its id).

  From 2 threads on, `number` is faster than the sequential baseline.
- **Bytes per distinct key: 106.** `5/3` cells per estimated key at 56
  bytes each (`OnceLock<Entry<SymName>>`: key 32, hash 8, first mention
  8, the `Once` state and padding 8) make about 93 bytes. The slot-to-id
  map (4 bytes per cell) adds 6.7, and the id-to-slot map adds 4. The map
  (`sym_map`) is the spec's 4 bytes per mention on top; pass 1 buffers
  nothing per mention.
- **The `@` split.** A byte loop (`iter().position`) cost about 110 ns per
  66-byte name, more than the hash. It is now an 8-bytes-at-a-time
  zero-byte test (SWAR, safe Rust).

How the chosen table works:

- **Cells and probing.** One table of `OnceLock<Entry>` cells, probed
  linearly from a multiply-shift reduction of the hash (any table size,
  using the hash's high bits).
- **Inserting a new key.** `OnceLock::set` writes the new key's entry.
  When two workers race for one empty cell, the loser reads the winner's
  entry and continues probing if the keys differ. A reader waits only
  while a cell is being written at that instant, never on a lock held
  across a probe.
- **First mention.** It is updated by `fetch_min`, after a relaxed load
  shows the new value would lower it (§6 rule 2: commutative and
  idempotent).
- **Sizing.** The table cannot grow while shared, so `number` sizes it
  from a `HyperLogLog` estimate (2^12 registers, standard error 1.6 %).
  Workers keep local registers and merge them by maximum when they are
  dropped; mold sizes its symbol table the same way.
  - The table is sized for the estimate plus 16 keys, holds 5/3 cells per
    key, and is full at 3/4 of its cells, i.e. 25 % above the estimate.
  - If it fills, pass 1 runs again with twice the size; the result is the
    same either way (`s2_3_numbering_survives_an_estimate_that_falls_short`
    starts from a size of 1).
  - Workers count new keys in batches of 64 against the limit. A probe is
    bounded by the table size, so even an over-full table terminates.

## The hash

- **Construction.** It follows wyhash, final version 4 (Wang Yi, public
  domain):
  - 16 bytes or fewer are read as overlapping 4-byte words;
  - longer input is folded 16 bytes at a time, in three independent lanes
    of 16 while 48 or more bytes remain, with `mix(a, b) = lo(a·b) ^
    hi(a·b)` over the 128-bit product;
  - the last 16 bytes are read overlapping and finish the hash;
  - the seed is 0 and the secret is wyhash's published default.
- **Provenance of the vectors.** It was written from scratch and **not
  checked bit for bit against the reference** (no reference was
  available offline). The frozen vectors in `tests/hash.rs` are therefore
  this implementation's own, produced by `examples/hash_bench.rs
  --vectors` when it landed.
- **Host independence.** Words are read with `from_le_bytes`. Integers go
  through `FixedHasher` by value, so `usize` and `u64` agree and
  endianness does not matter.
- **Speed.** On the workload's names (65 bytes average): 9.7-9.9 ns per
  name (6.6 GB/s) against `std` SipHash-1-3's 28 ns (2.3 GB/s), 3 runs of
  9. A `u64` takes about 0.4 ns against 6.5 ns.
- **Spread.** χ² over 1024 buckets from six bit ranges (low tag, middle,
  the high bits the home cell uses) stays within 7 deviations on 200k
  mangled names, with no 64-bit collision. Every byte of every length up
  to 130 changes the hash.

## `par`: design and cost model

- **Scheduling.** One atomic cursor over items. A worker takes the next
  item when it finishes one; there is no work stealing.
  - Units are batched into `units / (threads·16)` consecutive units per
    item. This is not observable: no result depends on it.
  - The calling thread works too.
  - `min(threads, items) − 1` scoped threads are spawned per call and
    joined before it returns.
  - A thread that cannot be spawned (a resource limit) leaves its share
    to the others.
- **Seed.** With a seed, items are single units in a splitmix64
  Fisher-Yates order, and every worker yields after each unit.
  `MORTAR_SCHED_SEED` is read once (`OnceLock`); `Pool::with_seed`
  overrides it without touching the environment.
- **Panics.** A guard sets a stop flag when a worker unwinds. Every
  handle is joined, and the first payload is resumed on the caller with
  its message. Tested at 1, 2, 7 and 64 threads, after which the pool
  still works.
- **Per-call cost.** Each extra worker costs one spawn: about 65-80 µs
  per thread on this host. That equals a bare `std::thread::scope` spawn
  of the same threads (560-670 µs for 7), so the helpers add nothing to
  it. Each call also allocates the handles vector; with a seed, it also
  builds a permutation of the items (one `usize` per unit).
- **Allocations per helper.** Beyond the result:

  | helper | allocations |
  |---|---|
  | `for_each`, `for_each_init`, `for_each_block` | none |
  | `for_each_part` | one `Mutex<Option<part>>` per part (not when inline) |
  | `for_each_mut` | one `Mutex` per batch |
  | `map`, `map_collect` | one buffer per batch and one copy into the result (none inline), plus `units + 1` offsets for `map_collect` |
  | `prefix_sum` | none up to 2^16 elements; beyond, one sum per 2^16 block |

- **Sort.** Inline, or up to 2^13 elements, the sort is `slice::sort_by`.
  Beyond that:
  - runs of `max(2^13, ⌈n/64⌉)` elements (a function of the length) are
    sorted in parallel;
  - then at most 6 rounds merge neighbouring runs. Each merge is cut into
    output blocks of 2^14 elements, whose input split points are found by
    binary search ("merge path"), so every round is parallel to the end;
  - the cost is one scratch copy (`T: Copy`: rows are plain data, §1) and
    a copy back after an odd number of rounds.
  - **Tie rule:** stable. Rows that compare equal keep their order in the
    input, so the result is exactly `slice::sort_by`'s. When the input
    order itself comes from a schedule, the key must be total.
  - Measured on 4M `(u64, u32)` rows, clone included: `slice::sort_by_key`
    120-122 ms; the pool's sort 117 ms at 1 thread, 93-94 at 2, 54-59 at 4
    and 39-48 at 8.
- **The small-work pitfall.** `map_collect` of 10k units of 400 rows
  takes 0.9 ms at 1 thread and 2.0-2.4 ms at 8: spawning dominates.

## Safe Rust: what it cost

- **No persistent thread pool.** Work that borrows a phase's data cannot
  be handed to threads that outlive the call without erasing lifetimes,
  which takes `unsafe` (rayon does it). Every parallel helper call
  therefore pays the spawns: 65-80 µs per thread here; bare metal is
  typically several times faster.
  - A link that makes ~30 parallel calls at 8 threads would pay about
    15 ms on this host. That is the one measurable cost, and the first
    candidate if the operator ever weighs `unsafe` for `par` (a scoped
    pool with persistent workers).
  - Until then, phases should make few calls with substantial work each.
- **`OnceLock` per cell.** It costs 8 bytes per cell for its state and
  padding, about 13 bytes per key, plus an acquire load per probe. An
  `unsafe` table with a state bit in the cell would save the bytes. The
  throughput difference was not measured and is likely small: the probes
  are memory-bound.
- **Elsewhere.** Nothing measurable: the hash's `copy_from_slice` word
  reads, `split_at_mut` chains, the sort's `to_vec` scratch.

## Where the spec was unclear or silent, and what was chosen (most important first)

1. **§2.3 pass 3 needs a join.** "(3) per file, give those entries their
   ids and rewrite `sym_map`" cannot be one parallel pass. An id is
   written by its key's first-mention file and read by every file, so the
   reads must wait for all the writes. Implemented as (3a) ids by slot
   (pass 2's concatenation *is* the id-to-slot list), a join, then (3b)
   the map rewritten per fixed block. *Proposal*: say so in §2.3.
2. **§2.3 packs `FileId << 32 | st_index`.** The implementation packs the
   mention's **ordinal** among the file's non-local entries instead. The
   order is the same, since the entries are in table order. So the
   numbering needs only the keys, in order, and `Names::first` gives
   `(unit, ordinal)`. *Proposal*: allow "or the entry's ordinal among the
   file's non-local entries".
3. **Sizing the concurrent table is not in §2.3.** The `HyperLogLog` pass
   adds one extra pass over every key. `number` therefore calls `keys(u)`
   twice per file (three times if the estimate falls short), so the input
   phase must make key extraction repeatable and cheap: it is a read of
   the input bytes. *Proposal*: mention the sizing pass in §2.3's cost
   statement.
4. **The key of §2.3.**
   - `SymName::parse` splits at the **first** `@`; `@@` makes the
     unversioned key.
   - `foo@` is the key (`foo`, version "") and differs from `foo`.
   - A shared object's version comes from its version tables, so it is a
     separate borrowed slice (`SymName::versioned`), with no allocation.
   - Hidden versions and version scripts remain `spec/resolve.md`'s
     (§12).
5. **The limit of §1.** Slots are cell indices in `u32`, with at most
   2^32 − 1 cells, each table full at 3/4. The numbering is therefore
   refused (`TooManyKeys`) at about 3.2·10⁹ distinct keys rather than
   2^32 − 1. That is unreachable in memory (about 340 GB of table), but
   it is a stated difference.
6. **A malformed `MORTAR_SCHED_SEED` is not specified.** `Pool::try_new`
   returns `BadSeed`, whose message names the variable, for the driver to
   report. `Pool::new` panics with the same message.
7. **The seed with one thread.** The units still run on the caller (no
   thread is spawned) in the permuted order, with yields: "one thread"
   tests the order independence too.
8. **Rule 2 has no helper.** `std`'s atomics are the helper, tested in
   `s6_rule2_…`.
9. **Rule 6 and internal partitions.** The batching of units and the sort's
   runs could depend on the thread count without being observable. The
   sort's do not (they are a function of the length); the batching does,
   being invisible.

## What later packages must know

- **Use `check_schedules` in every phase test.** Wrap the phase in it: it
  runs 1, 2, 7 and 64 threads, each with no seed and with three seeds,
  and requires the sequential result.
- **Few calls, real work.** Each parallel call costs a spawn per thread.
  Below a few thousand cheap units, a phase should run inline
  (`Pool::sequential()` or `pool.with_threads(1)`) or fold the steps into
  one call.
- **Disjoint writes.** Use `split_offsets(column, &offsets)` (offsets from
  a prefix sum, e.g. `Collected::offsets` or `Numbering::offsets`) with
  `for_each_part`. Never share `&mut` through a `Mutex` for that.
- **`for_each_init` state is dropped.** It must not carry a result, unless
  its `Drop` merges commutatively into shared state, as the interner's
  `HyperLogLog` sketch does.
- **Slots are not observable.** Never store one in a table, the link
  state or a diagnostic. Store ids, which `number` gives.
- **`hash::HashMap` is for lookup only** (§6 rule 5). Iterate a sorted or
  id-ordered view.
- **The hash is frozen.** Changing `hash_bytes` breaks
  `s6_rule5_frozen_*` on purpose, and is a change of `spec/model.md`.
- **One numbering function for everything.** `number` is generic over the
  key: `FragId` (§3.5, "by the method of §2.3") can use it with a key
  type `(OutSecId, &[u8], align)` implementing `InternKey`, unit = file
  and ordinal = the running piece index over its sections, which is
  monotone in `(sh_index, piece)`.
- **`Names` is the `symbols[SymbolId]` column's source.** It gives each
  id's name bytes, version, hash and first mention, and the lookup by key
  for `--defsym`, `-u` and the linker's own symbols.
- **The jobserver.** The product takes no jobserver tokens; threads come
  from `--threads` (`Pool::available()` by default). No client is
  implemented.

## Evidence

- **The gate.** `source scripts/env.sh && set -o pipefail &&
  MORTAR_REQUIRE_TOOLS=1 cargo xtask ci --quick` printed `[ci] ok`, twice.
- **Flakiness.** The three test binaries ran 15 times in a loop with no
  failure.
- **Benches.** `cargo build --release -p mortar_core --examples`, then
  `intern_bench` (with `CONTROL=1` for the private-table control),
  `hash_bench` and `par_bench`, each run three times, with the numbers
  above. The sharded-mutex and segmented designs are in this branch's
  history (commits 942239a and the one after it).
