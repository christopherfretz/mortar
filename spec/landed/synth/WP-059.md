# WP-059 — `st_other` bits, unique symbols, unread GOT slots: what landed

Three places where a static link's bytes were not the references'. Each
item was measured first (GNU ld 2.44, lld 19 and 22, mold 2.37.1), the
rule written where the references disagree from what a consumer needs,
then coded, then the baseline re-recorded and shown to be that item
alone. A and B landed; C landed for i386; C for x86-64 is **not
landed**: it meets the brief's stop condition (section 3.4 has the
options and their costs).

Commits (branch `wp/059-symtab-bits`):

| commit | item |
|---|---|
| `6860610` | A: `.symtab` keeps the `st_other` bits above the visibility |
| `15de784` | A2: a `WeakDyn` `.dynsym` entry carries `STO_AARCH64_VARIANT_PCS` (beyond the brief, see 1.4) |
| `31f9fea` | B: a static `.symtab` keeps `STB_GNU_UNIQUE` |
| `9ab85d9`, `711767d` | C x86-64: the scan-time slot drop, and its revert (kept for the decision) |
| `15d17db` | A: two existing tests read the bit (1.3) |
| `8fd87d7` | C: the x86-64 test's non-static links without gcc's plugin (F4) |
| `8907e0a` | C: an i386 `GOT32X` that relaxes demands no slot; X-19's slot written down |

No interface change remains on the branch (the reverted C x86-64 commit
added `SymFacts::large` to `mortar_arch`). No item changes what an
incremental state holds: A and B change `.symtab`/`.dynsym` field

(`RefFlags::VARIANT_PCS` is a new bit of an existing per-key byte); C
i386 changes which keys demand a slot, which `Slots` already records.

## 1. A — `STO_AARCH64_VARIANT_PCS` in `.symtab`

### 1.1 Measured

AArch64; `main.c` / `refs.c` / `defs.c` of
`tests/link/resolve/symtab-variant-pcs.test` (the same sources in
`tests/link/dyn/dynsym/symtab-variant-pcs.test`): variant-PCS
(`aarch64_vector_pcs`) definitions local, hidden, global, weak and
protected; `plain_def` defined without the bit and declared with it;
`marked_def` the opposite; undefined weak `wref` (bit on every mention)
and `wref2` (bit on the second mention only).

| case | GNU ld | lld | mold | mortar before |
|---|---|---|---|---|
| variant-PCS definition, static/PIE/static-pie | bit kept | bit kept | bit kept (entries `LOCAL`, A9) | bit kept on locals only, dropped on every global |
| hidden definition | static: `GLOBAL HIDDEN [VARIANT_PCS]`; PIE: `LOCAL DEFAULT [VARIANT_PCS]` | `LOCAL HIDDEN [VARIANT_PCS]` | as lld | `LOCAL HIDDEN`, no bit |
| `plain_def` (definition plain, a declaration marked) | bit (OR of mentions) | no bit (definition's) | no bit | no bit |
| undefined weak, bit on the second mention (`wref2`) | static, static-pie: no entry; PIE: bit (OR) | first mention's (none) | first mention's (none) | no bit |
| undefined weak, bit on every mention (`wref`) | PIE: bit | bit | bit | no bit |

gdb 16.3 behaves the same with and without the bit (`break`, `bt`
through a vector-PCS frame).

### 1.2 The rule

synth.md **S-127** (new), resolve.md §3.7 (paragraph after "An
undefined key that no live relocation uses"): a global's bits above the
visibility are the **defining entry's** (lld, mold: a property of the
code at the address, which only the definition knows); an undefined
entry carries `STO_AARCH64_VARIANT_PCS` when **any** live reference has
it (GNU ld: independent of mention order, and it is what the loader
needs on a `.dynsym` entry, 1.4). Resolution records the reference bit
as `RefFlags::VARIANT_PCS` (`mortar_core/src/resolution.rs`, bit 6;
resolve flag bit 10 in `mortar_resolve/src/resolve.rs`; `Mention.other`
in `view.rs`). `SymProps` stays 6 bytes. synth.md §13 has a row.

### 1.3 Code, baseline, tests

`crates/mortar/src/syms.rs` (`global`): the defining entry's
`st_other & !3` (also for a common), and for an undefined referenced
entry the bit from `RefFlags::VARIANT_PCS` on AArch64.

`static-identical` on AArch64: **70 links changed**, each only in two
`.symtab` entries (libgcc's hidden `__arm_tpidr2_save` and
`__arm_za_disable`, `st_other` 0x2 → 0x82) and the build-id note;
175 identical; 1 row added. With A, mortar's entries are lld's.

Two existing tests followed (`15d17db`): eu-elflint reports "unknown bit
set in st_other" for the two libgcc entries (it knows no
processor-specific bit; GNU ld's and lld's outputs draw the same two
lines), now in `crates/mortar/tests/support/plumb.rs` `ELFLINT_KNOWN`;
and the pipeline map test's `readelf -sW` parser skips the bracketed
`[VARIANT_PCS]` column.

Tests: `tests/link/resolve/symtab-variant-pcs.test` (static, every row
of 1.1, per linker; fails with the old mortar), and
`tests/link/dyn/dynsym/symtab-variant-pcs.test` (PIE and static-pie;
GNU ld's static-pie carries A30).

### 1.4 A2 (beyond the brief): the `.dynsym` entry of a `WeakDyn` key

Found while measuring: in a mortar PIE a weak undefined vector-PCS
function that is tested and called (`if (vweak) vweak(1)`, a `WeakDyn`
key, D-25) had neither the bit on its `.dynsym` entry nor
`DT_AARCH64_VARIANT_PCS`; GNU ld and lld write both (mold makes the key
0). Without the tag glibc binds the `JUMP_SLOT` lazily through a
resolver that saves only base-PCS registers: a possible wrong program
when a later library defines the function. Fixed in D-23's `WeakDyn`
row and D-30 row 25: `mortar_synth/src/dynsym.rs` (`Form::WeakDyn`),
`mortar/src/dynlink.rs` (`variant_pcs_jump_slot`). Test
`tests/link/dyn/dynsym/weak-undef-variant-pcs.test` (no library:
`none`; `LD_PRELOAD` of one defining it: `42`). No static byte changes.

## 2. B — `STB_GNU_UNIQUE` in a static `.symtab`

### 2.1 Measured

`u.cc`/`u2.cc` (a template static member `S<int>::v` and an inline
function's static `counter()::c`, both GCC `STB_GNU_UNIQUE`), all three
targets (i386: static and `-r`; it has no dynamic outputs here):

| output | GNU ld | lld | mold | mortar before |
|---|---|---|---|---|
| static | `UNIQUE`, `EI_OSABI` 3 | binding 10, `EI_OSABI` 0 | `LOCAL` | `GLOBAL` |
| static-pie, PIE | `UNIQUE`, 3 | binding 10, 0 | `LOCAL` | `UNIQUE` (WP-054) |
| `-r` | `UNIQUE`, 3 | binding 10, 0 | binding 10, 0 | refused (`unsupported option: -r`) |
| `-nostdlib` static, the unique symbol the only GNU one | `UNIQUE`, 3 | binding 10, 0 | `LOCAL`, 0 | `GLOBAL`, 0 |
| GNU ld `-s` | `EI_OSABI` 0 | | | |

So `-r` is not in play in mortar. `EI_OSABI`: GNU ld sets 3 from the
symbols it writes (with `-s` it writes 0); lld and mold never. mortar's
existing rule (a64.md Q11, x64 X-49, x86 X86-64, D-23: `ELFOSABI_GNU`
when `.symtab` or `.dynsym` holds IFUNC or UNIQUE, or there is an
`IRELATIVE`) is GNU ld's, and needs no change. gdb 16.3 and lldb 19
answer the same for all four outputs (`print 'S<int>::v'`, `image lookup
-s`); `nm` prints `u` for GNU ld, lld and mortar after B, `D`/`B` for
mortar before, `d`/`b` for mold.

### 2.2 The rule

resolve.md §3.7 (table row and a new paragraph), one rule with D-23
and synth.md S-75 (whose citation X-17 was wrong and now names this):
a unique definition is `STB_GNU_UNIQUE` in `.symtab` of every output
kind. Argued: glibc reads the binding only from `.dynsym`, so a static
`.symtab` has no loader consumer; the debuggers treat it as a global;
`nm`'s `u` says the definition was vague-linkage and deduplicated,
which an ODR diagnosis and Tuck need and which `STB_GLOBAL` and mold's
`STB_LOCAL` erase; one rule keeps static, static-pie and PIE outputs of
the same objects alike.

### 2.3 Code, baseline, tests

`crates/mortar/src/syms.rs`: `CoreSyms::dynamic` and `keep_unique`
removed (the four callers in `front.rs`, `image.rs`, `dynlink.rs`
updated).

`static-identical` on AArch64: **36 links changed**, each only in
`.symtab` `st_info` of its unique definitions (0x11 → 0xa1: 1, 5, 83,
106 or 107 entries) and the build-id; `EI_OSABI` was already 3 (glibc's
IFUNCs); 210 identical; 7 rows added. The changed tests:
`identical/{clang-cxx,cxx-large,gc-debug}`, `lang/cxx-exceptions`,
`lang/cxx-iostream`, `odr/k9-inline-variable`, `resolve/comdat-inline`,
on three architectures. All pass `linktest` with the verifier
(`tests/identical` run through `cargo xtask linktest --linker mortar
tests/identical/...`: 24 outputs clean).

Tests: `tests/link/resolve/symtab-unique.test` (all three targets:
binding per linker, `nm`, and the `-nostdlib` link's `EI_OSABI`; fails
with the old mortar on all three), `tests/link/resolve/symtab-unique-debuggers.test`
(AArch64: gdb, lldb).

## 3. C — GOT slots of relaxed GOT loads

### 3.1 Measured, x86-64

`x.s` of `tests/link/reloc/x64-gotpcrelx-slot.test` (`-nostdlib`): keys
`allr` (two relaxable `mov`), `some` (a relaxable `mov` and a
`GOTPCREL` `movq` to `%xmm0`), `none` (`GOTPCREL` only), `bin` (a G5
`add`); `big.s` (target in `.ldata`); `far.s` (target 2.5 GiB away in
`.bss`). `.got` bytes / `RELATIVE` records:

| input, kind | GNU ld | lld | mold | mortar |
|---|---|---|---|---|
| `x` static, `exec` | 16 (`some`, `none`) | 16 | 40 | 32 |
| `x` `pie`, static-pie | 24 / 3 (`bin` kept: G5 is not relaxed in a PIE) | 24 / 3 | 40 / 4 | 32 / 4 |
| `big` (large data) | 8, not relaxed (GNU's `mov`) | 0, relaxed (`lea`) | relaxed, slot kept | relaxed, slot kept |
| `far` | not relaxed, slot | not relaxed, slot | not relaxed, slot | not relaxed, slot |

GNU ld writes `mov $imm` for the relaxable `mov` in static and `exec`
(X-20 notes it), `lea` in a PIE; lld and mortar `lea`. With
`--section-start` moving the target out of range after its estimate,
GNU ld refuses: "failed to convert GOTPCREL relocation against 'allr';
relink with --no-relax" (lld and mold fail on other records; mortar
refuses `--section-start`). GCC's medium-model PIC reads extern data
with `big@GOTPCREL`, so large targets are real input.

### 3.2 Measured, i386 (static)

`x.s` of `tests/link/reloc/x86-got32x-slot.test`: the same four keys
with `GOT32X` (`mov`, G2 `add`) and plain `GOT32` (`movd`):

| | GNU ld | lld | mold | mortar before | mortar after |
|---|---|---|---|---|---|
| relaxed | G1, G2 | none | G1 to `lea` off the GOT base | G1, G2 | G1, G2 |
| `.got` | 8 (`some`, `none`) | 16 | 20 | 16 | 8 |

On a glibc `-static` link (`C/m32.c`): GNU ld 20 bytes of `.got`,
mortar 0x1c8 before and 24 after; the remaining difference is one word
holding an IFUNC's IPLT entry address (X86-28), which GNU ld's `.got`
does not have; not looked into further.

### 3.3 The rules

- **i386, X86-25** (paragraph "The GOT slot"): the relaxation is kind 1
  (no address in the condition, X86-10), so scan decides it with the
  same predicate as fill (`mortar_x86/src/apply.rs` `got_relaxable`,
  `relaxes`), and a relaxing record demands no slot. Scan takes it only
  where the place's `SHF_EXECINSTR` is known and the operand has a form
  (X86-13 step 1), so `i386_cells` has nothing to say. GNU ld's result.
- **x86-64, X-19** (paragraph "The slot stays"): unchanged behaviour,
  written down with the measurements.

### 3.4 x86-64: why it is not landed, and the options

Whether every use of a key relaxes depends on each relaxed field
fitting (s(32) for G1–G4, `S` < 2^31 for G5/G6), which is an address.
The scan has no address. The brief's condition (decided before layout
from facts the scan already has) does not hold.

Option (b) was built and is on the branch as `9ab85d9` (reverted by
`711767d`). Scan decides from input facts: a `local` target, not large
data (a new `SymFacts::large` from the defining section's
`SHF_X86_64_LARGE` or an `SHN_X86_64_LCOMMON` common), `A = −4`, the
bytes of G1–G4, or G5/G6 in a non-PIE output. Such a record demands no
slot. At fill, a record whose field does not fit and whose key has no
slot is `relocation-out-of-range` on the relaxed field. It reproduces
GNU ld and lld exactly on `x` (16 bytes, 24 and 3 `RELATIVE` in a PIE)
and keeps `big`'s slot. But on `far` it refuses ("relocation truncated
to fit: R_X86_64_REX_GOTPCRELX against 'far': 2684358693 is not in
[-2147483648, 2147483647]"), a link all three references accept.

| option | what it costs | what it gives |
|---|---|---|
| (a) keep the slot (landed) | 8 bytes per all-relaxed key; in a PIE one `RELATIVE` (24 bytes) per key too | nothing to build; correct |
| (b) drop at scan, refuse a misfit (`9ab85d9`) | `SymFacts::large` (an `mortar_arch` interface change, about 12 construction sites); a new refusal of links whose code and small data span more than 2 GiB, which GNU ld, lld and mold link (a `-fPIC` small-model program with more than 2 GiB of default-visibility `.bss` is one) | GNU ld's and lld's bytes on every program that fits |
| (c) drop at scan when a bound proves the fit | (b)'s field, plus one pre-layout number: the size of all live small allocated input sections plus an upper bound on the synthetic chunks and the padding; below 2^31 (and, for G5/G6, image base + bound below 2^31) every relaxed field fits. One sum over live sections before scan; a strict bound on the synthetic chunks needs each chunk's worst case. In incremental mode the decision flips when the image crosses the bound (a full relink then) | (b)'s bytes, no new refusal; the slot stays only for images over the bound |
| (d) lld's way: relax, then a pass after layout that reverts misfits and adds their slots | a second layout pass and a slot table that can grow after layout (the brief's "second pass") | the references' bytes everywhere |

My recommendation is (a) for now, with (c) as the follow-up if the 8
bytes matter. (c) is the only option that is both correct without a
new refusal and single-pass. Its cost is the bound, which layout's
synthetic plans can give before scan only if they are sized
pessimistically.

## 6. Findings

- **F1 (verifier or layout, not this package's).** A `-nostdlib`
  static link whose writable segment is `.bss` alone: mortar on x86-64
  gives a `PT_LOAD` with `p_filesz` 0 whose `p_offset` falls inside
  `.comment`'s file range, and the verifier reports S17 ("non-allocated
  section '.comment' lies in a PT_LOAD's file image"). The same happens
  with main's binary. GNU ld's AArch64 output of the same link draws S2
  (`PT_LOAD` file image past the end of the file). Reproducer:
  `inline int &counter() { static int c = 0; ... }` with an `_start`,
  `gcc -static -nostdlib`. Either the verifier should accept an empty
  file image anywhere, or layout should give such a segment an offset
  past the non-allocated sections' bytes.
- **F2.** `nm` and readelf name binding 10 `UNIQUE` only under
  `EI_OSABI` 3 (`<OS specific>: 10` under 0, lld's output).
- **F3 (a flake, not this package's).** One local gate run failed
  `crates/mortar/tests/incremental.rs` `stamp_rule_b_own_output_is_clean`:
  `race-out-<pid>.bin`, which the test had just created in one of its
  stamp directories (the scratch, `/tmp` or `/dev/shm`), was gone at
  the next open (`NotFound`, line 1031). The test passed alone twice and
  in the next gate. No other test in the binary uses that name. Something
  outside the test removes files in a shared temporary directory.
- **F4 (harness).** The first test of the static-identical corpus
  with a successful gcc link that is not `-static` (`x64-gotpcrelx-slot`'s
  `-pie`, `-static-pie`, `-no-pie`) had a map digest that changed per
  run. Without `-static`, gcc passes its LTO plugin and
  `-plugin-opt=-fresolution=/tmp/ccXXXXXX.res`, a new name per link, and
  the map records every argument. The test passes
  `-fno-use-linker-plugin` (`8fd87d7`). The digest's normalisation
  (`xtask/src/linktest/engine.rs` `digest_row`) could drop that argument
  instead, so that a later test need not know this.
