# WP-025 stage 1 — `spec/synth.md`: method and evidence

This document backs `spec/synth.md` (draft). It gives the method, the
experiments the non-obvious rules rest on, the library scan, and what
could not be checked. The `X-n` labels are the ones `synth.md` cites.

## 1. Method

- **Sources.** The gABI ("Section Attributes", "Symbol Table", "Note
  Section", "Extended Section Indices"), the Linux gABI extensions
  ("Program Property"), AAELF64 (mapping symbols, IRELATIVE), the x86-64
  and i386 psABIs, the LSB's "Exception Frames" (`.eh_frame` and
  `.eh_frame_hdr`), DWARF 5 §6.4, the GNU ld manual (`-O`, `-x`, `-X`,
  `--build-id`, `--eh-frame-hdr`), and the documented behavior of
  glibc's static start-up (`__rela_iplt_start`) and libgcc's
  `__register_frame_info`. No linker source was read; nothing was copied
  from one.
- **Oracle.** The observed output of GNU ld 2.44 (`ld.bfd`, and the cross
  `x86_64-linux-gnu-ld`, `i686-linux-gnu-ld`), `ld.lld-22` (22.1.8) and
  `ld.lld-19` (19.1.7), and mold 2.37.1, on an AArch64 Debian host. lld
  was driven through GCC with a `-B` directory holding an `ld.lld`
  symlink. x86-64 and i386 objects came from the Debian cross GCC 14 and
  from Clang (`--target=x86_64-linux-gnu`); in the first round those
  outputs were inspected with readelf only. In round 2 (§10) static x86
  programs were run under `qemu-x86_64` and `qemu-i386`, and gdb 16 was
  used on AArch64 outputs.
- **Tools.** binutils readelf 2.44, `llvm-readelf-22 --unwind` (it
  decodes `.eh_frame_hdr`), and three small Python readers written for
  this package (an ELF and archive reader, the library scan of §2, a
  `.strtab` statistic), kept out of the repository.
- **Programs.** Hand-written assembly for every malformed or unusual
  construct (generated by a shell function that writes a CIE and FDEs
  with chosen fields); small C and C++ programs for the merge,
  `.symtab`, IFUNC and TLS cases; a static C++ program with COMDAT
  inline functions and exceptions (two files sharing a header) for
  `.eh_frame` and the merge-size measurements.
- **Limits honored.** No package installs. Programs were built and run
  in one directory under `/tmp`, removed at the end; scratch scripts in
  the workspace's `.build/` scratch directory, removed at the end.

## 2. The library scan (X-1)

Every object in the static libraries and start files of the three
targets: `crt1.o`, `crti.o`, `crtn.o`, `crtbegin*.o`, `crtend*.o`,
`libc.a`, `libm.a` (and `libm-2.*.a`, `libmvec.a` where present),
`libpthread.a`, `libc_nonshared.a`, `libgcc.a`, `libgcc_eh.a`,
`libstdc++.a`, `libsupc++.a`, `libgfortran.a` (AArch64 and x86-64; not
installed for i386), `libatomic.a`, `libgomp.a`. AArch64 from
`/usr/lib/aarch64-linux-gnu` and `/usr/lib/gcc/aarch64-linux-gnu/14`;
x86-64 and i386 from the cross sysroots (`/usr/x86_64-linux-gnu/lib`,
`/usr/i686-linux-gnu/lib`, `/usr/lib/gcc-cross/*/14`).

The scan classifies every `SHF_MERGE` section, every relocation whose
target symbol is in an `SHF_MERGE` section with `sh_entsize > 0`, every
symbol defined in one, every `.eh_frame` record, every note, and
symbol-table statistics. For a reference, `r = st_value + A` for a
section symbol and `st_value` for a named symbol; on x86 the PC-relative
bias of the addend was allowed for when deciding whether a named
symbol's addend stays within its piece.

## 3. Merge experiments (AArch64, bare `ld -static`)

### X-2 Section symbol plus addend at and beyond the end

An object with a small `.rodata.str1.1` (a few strings) and data words
`.8byte .rodata.str1.1 + K` for K at piece starts, inside pieces, equal
to the section size, beyond it (the size plus some bytes: 13 in the
run below) and −1, linked after another object holding some of the
same strings, so that the pieces move:

```text
K inside [0, size)  all three: out(piece containing K) + (K - start(piece))
K == size           GNU: no message; value = the end of the whole output
                         .rodata.str1.1 (not this object's last string)
                    lld: error: ...: offset is outside the section
                    mold: the end of this input's last piece
K = 13, K = -1      GNU: warning: ...: access beyond end of merged section (13) / (-1);
                         value = the end of the output section
                    lld: error: offset is outside the section
                    mold: no message; an address unrelated to the input
```

### X-3 Named symbol plus addend

A local label at the start of an interior string, referenced with
addends that stay within its piece, that point one past its end, and
that cross into the neighbouring pieces in both directions: all three
write `out(piece of the label) + (label − start(piece)) + A`, i.e.
symbol-relative, even where the result lies in no piece of the output.

### X-4 Unterminated string section

`.section .rodata.str1.1,"aMS",@progbits,1` with `.ascii "abc"` (no
NUL):

```text

lld:  error: a.o:(.rodata.str1.1): string is not null terminated
mold: fatal: a.o:(.rodata.str1.1): string is not null terminated
```

### X-5 What compilers emit for one-past-the-end and before-the-start

`const char *p = "abc" + 4;` and `"ijk" - 1` (UB), at `-O0`/`-O1`:

```text
GCC aarch64/x86-64/i386: .LC0 + 4 and .LC1 - 1 through local symbols
clang x86-64, i386:      local symbols (.L.str + 4)
clang aarch64:           "ijk" - 1 as .rodata.str1.1 + a (section symbol;
                         maps into the previous piece; UB in C)
clang x86-64 "abc"+4:    .rodata.str1.1 + 0 with R_X86_64_PC32 (the -4 bias
                         cancels +4); correct under piece mapping
```

### X-6 Order, de-duplication, tail merging and -O

Three objects with overlapping strings, one a suffix of another, linked
with each linker, and with `-O0`, `-O1` and `-O2`:

```text
GNU  any -O:  identical outputs, .rodata.str1.1 0x20: de-duplicated and
              tail-merged; surviving strings in first-occurrence order
lld  -O0:     no merging;  -O1: 0x2b, de-duplicated, in shard/hash order;
     -O2:     de-duplicated and tail-merged
mold any -O:  0x2b, de-duplicated, not tail-merged, in hash order
```

### X-7 Aligned string sections and the merge class

The same string in a 1-aligned and in an 8-aligned string section: all
three keep two copies, and every piece of the `.rodata.str1.8` input is
8-aligned in each output. (A string and a constant of equal bytes were
not linked; S-13 keeps them apart because their pieces are cut
differently, S-9 against S-10.)

### X-11 Two personality CIEs

Two `zPLR` CIEs, byte-identical, whose personality pointers are

### X-12 `crtbeginT.o` and `__EH_FRAME_BEGIN__`

`crtbeginT.o`'s `.eh_frame` is 0x88 bytes (a CIE and four FDEs), with
the local `__EH_FRAME_BEGIN__` at offset 0; its CIE equals `crt1.o`'s,
which comes first. gdb at `__register_frame_info`, argument (GNU):
`0x48e3a8`, the first record GNU kept from `crtbeginT.o` (the CIE was
de-duplicated away). GNU's `.symtab` gives `__EH_FRAME_BEGIN__`
`0x48e358`, 16 bytes before `.eh_frame`'s start, in no section. lld
passes `.eh_frame`'s start and gives the symbol that value
(`__FRAME_END__` too); mold drops both symbols (it always writes
`.eh_frame_hdr`). The static binary has `_dl_find_object` and no
`dl_iterate_phdr` reference from libgcc's static path.

## 8. What could not be checked

- x86 outputs were run only for X-25 (qemu); the other x86 rules,
  IFUNC (X-27) included, rest on readelf of the outputs and the psABIs.
  gdb was run on AArch64 outputs only.
- gdb and lldb behavior with mortar's thunk symbols (S-80) and with
  `.symtab` lacking section symbols was not exercised; that gdb needs no
  section symbols in an executable rests on lld's outputs, which gdb
  debugs routinely.
- perf and valgrind were not run; §12 rests on their documentation.
- `SHN_XINDEX` (S-85) was not exercised with any linker (it needs an
  output of more than 65279 sections).
- S-30's figures are measured with a safe-Rust prototype (X-29), but on
  a host at load 29 to 34, so they are upper bounds; S-89 remains an
  estimate. The bench harness must replace both with mortar's.
- The x86 `FEATURE_2_USED` was not linked; its rule follows the range
  X-20 tested for `ISA_1_USED`. (`STACK_SIZE` and
  `NO_COPY_ON_PROTECTED` are now X-33.)
- `MEMORY_SEAL`'s kernel and glibc semantics were not checked; S-95
  only fixes when the property is written.
- lld 19 was not rechecked in round 2; every lld result there is 22.1.8.
- The libitm-linked transactional-memory program (X-31) was built with
  GNU only; that S-123's aligned start matches libitm's expectations
  rests on GNU's layout of it, not on a run.
- Writable or executable `SHF_MERGE` sections and merge sections with
  relocations (S-6) were not linked with the references; mortar's rule
  (place whole) is safe by construction.
- `--eh-frame-hdr` behavior for the GCC driver is now taken from its
  spec string (`gcc -dumpspecs`: `%{!static|static-pie:--eh-frame-hdr}`),
  not from a test note.
- How lld and mold choose a CIE among equal ones (S-44) was not
  observed beyond the counts.
