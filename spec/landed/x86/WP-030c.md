# WP-030c: i386 joins the pipeline

Branch `wp/030c-x86-joined`, cut from main at 86d5439. main was merged
twice: at 27e9992 (WP-032g, plus the two early commits as main
cherry-picked them) and at db9f0ad (main 266e16b: WP-032f and WP-028e).
The second merge conflicted only in `mortar_image/src/reloc.rs`, at the
two `split_target` calls. They keep main's `memo.split_target` and pass
the REL-aware `addend`, which on RELA is `rec.addend`, as on main. The two early commits on the branch are 4681e52
(the spec rulings on WP-030b's findings) and 10e5f46 (`PlaceFacts.exec`).

mortar now links static non-PIE i386 executables (`EM_386`,
ELFCLASS32, REL). Their output under `qemu-i386` matches GNU ld's
output for every program in the matrix below. Everything else on i386
is refused by name; `docs/status/i386.md` lists what is refused.

## Timing

The program has 160 C++ units plus `main`, compiled `-O1 -g`. Objects:
87 MB for i386 and 123 MB for x86-64, with about 0.96 M relocation
records each.

The link is static, on a shared 12-core AArch64 host. Each figure is
the median of 7 runs (wall and max RSS), or of 9 runs for the phases.

| link | wall | max RSS | scan | image (fill) |
|---|---|---|---|---|
| mortar i386 | 0.16 s | 115 MiB | 10.2 ms | 28.8 ms |
| mortar x86-64 (same program) | 0.22 s | 130 MiB | 4.2 ms | 42.2 ms |
| ld.lld i386 | 0.09 s | 220 MiB | | |
| mold i386 | 0.09 s | (forks; parent 10 MiB) | | |
| GNU ld i386 | 0.38 s | 118 MiB | | |

- All four i386 outputs print the same thing.
- **Scan:** i386 scan costs 2.4× x86-64's per record. The profile puts
  the time in `mortar_x86`'s `classify`, `scan`, `unit_window` (the
  R-13 overlap windows) and `forms::form`. That cost belongs to stage A,
  not to the REL plumbing (see Follow-ups).
- **Fill:** i386 fill is faster than x86-64's, because there are fewer
  output bytes.

## Findings (rule id, proposed text)

1. **R-13 (b), arch.md §3.3 (NONE).** An `R_386_NONE` record has an
   empty read window, so it may share an `r_offset` with another record
   (a width-0 marker reads and writes nothing). The rule as written refuses two
   records at one offset. Proposed: "…unless they are members of one matched
   sequence, or one of them is a marker (width 0), which reads and
   writes nothing." Implemented that way; `x86_5_overlapping_*` tests
   both sides.
2. **L-101 (`_GLOBAL_OFFSET_TABLE_` named but not referenced).** gas
   writes the symbol into `.symtab` beside `@ntpoff` code with no
   relocation against it. mortar used to fail with an internal error
   (a definition with no `GOT_BASE` demand). GNU does not define the
   symbol in that case. Proposed L-101 text: "a definition of the
   symbol demands `GOT_BASE`, as a reference does" (the `.got.plt`
   header then exists). Implemented in `front.rs:898`; tested by
   `x86_got_symbol_named_without_a_reference`.
3. **layout.md L-73 (ELFCLASS32 `PT_TLS`).** X86-45 bounds `PT_TLS` at
   2^31 (TP offsets are `s(32)`), but L-73 names only the image end and
   the file size. Proposed L-73 text: "ELFCLASS32: `PT_TLS` `p_memsz` ≥
   2^31 is `output-too-large`". It is implemented in `front.rs:676` for
   now, and belongs in `mortar_layout`'s L-73 check once that text
   lands.
4. **arch.md §3.1 / x64.md X-2 (the other relocation form).** An
   `SHT_REL` section in a 64-bit input used to be accepted with A = 0,
   which wrote wrong bytes. It is now refused at resolve as
   `unsupported section type: SHT_REL`. This change affects AArch64 and
   x86-64.
5. **X86-59 (tombstones).** `.debug_ranges` entries of dead COMDAT
   members get (1, 1) as X86-59 says. GNU points them at the kept copy.
   Both are valid; the `-g` runs above behave the same in gdb. No change is
   proposed.

## Verifier

With WP-028e merged, `mortar_plumb` judges i386, and it finds nothing
in any of mortar's i386 outputs. `tests/x86.rs` holds every output it
links to zero findings with mortar's own map. That covers the matrix,
both outputs of each `--gc-sections` size check, the determinism
link, the merge-piece link and the `_GLOBAL_OFFSET_TABLE_` link. The
gate's linktest stage 3 judges the `--arch i386` rows. No finding needed
a fix or an xfail.

  The site always covers the field (the snapshot margins are
  `MAX_REACH`), so 0 is unreachable; make it an internal error.

  `mortar_x86`'s `classify`/`unit_window`/`forms::form`.
