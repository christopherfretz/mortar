# WP-030d: a verifier false positive on ELFCLASS32 I-112; the missing tests

Branch `wp/030d-i386-tombstone`, cut from main at e539ecc. main was
merged twice: at 825bbf9 (WP-041, M2 step 0 and `static-identical`; the
cherry-pick 7b18cc4 of this package's verifier fix) and at 635b291
(WP-051).

## The report, and what it was

The verifier reported rule S12 in `.debug_aranges` of i386 outputs with
`-g -ffunction-sections` and `--gc-sections`: the word after an
`R_386_32` record against a collected section was 0, not the input's
value. The report suspected an 8-byte tombstone over a 4-byte REL field.

It was not a mislink. Reproduced with i686 GCC 14, one unused function:
mortar writes the field at the tuple's address `ffffffff` (4 bytes) and
the tuple's length after it `00000000` (4 bytes), and leaves the next
tuple alone. That is what `spec/image.md` I-112 prescribes ("the
class's address-sized absolute type (`ABS64`, `R_X86_64_64`,
`R_386_32`) ... fill also writes 0 into the `width` bytes that follow
the field"), and what I-47's ELFCLASS32 column says for the address.
The same program on x86-64 had the same pattern at 8 bytes and no
finding.

The verifier's acceptance of the zero length was 64-bit only:
`mortar_plumb/src/debug.rs` keyed it on `is_abs64` (`R_AARCH64_ABS64`
or `R_X86_64_64`) and on `class64`, following `spec/plumb.md`'s I-112
bullet, which named only "(`ABS64`)".

## The fix (561d5c7; on main as 7b18cc4)

- `debug.rs`: `is_abs_addr(e_machine, r_type)`, the output machine's
  absolute address-sized type (`R_AARCH64_ABS64` on `EM_AARCH64`,
  `R_X86_64_64` on `EM_X86_64`, `R_386_32` on `EM_386`), from
  image.md I-112's text; the `class64` condition is gone; the length is
  checked at the field's width.
- `spec/plumb.md` §5.8, the I-112 bullet: the three types and the width.
- `crates/mortar_plumb/tests/aranges.rs` (`tests/x86/aranges.s`), on
  i386 and x86-64: lld's `--gc-sections` link of a hand-written object,
  read as mortar's link with I-47's and I-112's bytes written, is clean;
  a kept (9) or other non-zero length after the tombstone is the I-112
  finding; a zero length after the tombstone of a target that is not
  `SHF_ALLOC` (a dropped non-alloc COMDAT copy) is S12; 0 over the
  record right after the field is a finding. On the old verifier the
  i386 test fails with the reported S12; the x86-64 one passes on both.

No linker code changed: `git diff main...HEAD -- crates` touches only
`crates/mortar/tests` (and the plumb commit, which main has).

## Why the gate missed it

`tests/x86.rs` and `tests/x64.rs` judge every output with the verifier,
but no link there combined `-g`, `--gc-sections` and a collected function
with debug information (`x86_gc_sections_c_and_cxx`'s `-g` set collects
only code of the C library and libstdc++, which have no debug
information: it passed on the old verifier). AArch64's
`tests/debuggers.rs` has such links, and its I-112 was accepted.

## Two disagreements found, not fixed (outside this package's plumb mandate)

Both are in `.debug_aranges`, on every class, and neither occurs in
compiler output (GCC's tuples point at code and are back to back):

1. **A collected merge piece as an aranges target.** `.debug_aranges`
   `addr dead_s` (a collected piece of a live `SHF_MERGE|SHF_ALLOC`
   section): mortar writes the tombstone and, by I-112, the length 0
   (I-45 makes it "a reference to a section that is not live"); the
   verifier accepts the tombstone but not the length (S12). Reproducer:
   `crates/mortar/tests/debug_gc_fields.s` with `fields 1` in
   `.debug_aranges`.
2. **A record inside the length but not at its start.** An address
   followed by a 4-byte word and a record at +4 (x86-64: `.quad dead+1;
   .long S; .word dead`): mortar leaves the length as relocated (I-112
   "unless a relocation record has its field there"); the verifier wants
   0 (R1), reading plumb.md's "no record has its field right after this
   one" as a record exactly at the end of the field.

Proposal: image.md I-112 to say "a section, or a merge piece, that is not
live" and "a record whose `r_offset` lies in those `width` bytes";
plumb.md's bullet to match; the verifier to follow.
