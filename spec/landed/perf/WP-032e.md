### The erratum window bug (found while profiling)

`sites.rs` built one proof window `(q, q+4)` per 0xFF8 inside the section
and tested relocations against `[q, q+16)`. That missed two cases:

- a site's last word at 0x1008, when `W1` is at 0xFFC;
- every window whose head lies in the previous section.

Those words were read unrelocated, which broke both fixes:

- **Patch path.** The patch held `W4'` with its `lo12` still zero. Repro:
  `adrp` at 0x…ffc and `ldr x1,[x0,#:lo12:sym]` at 0x…008. The veneer held
  `ldr x1, [x0]` where `#32` was needed; lld gets it right.
- **ADR path.** An `adrp` at a section's own 0xFFC was rewritten as an
  `adr` computed from its zero immediate. On the `sections` workload,
  main writes `adr x1, 0x93d000` for an `adrp x1, 0xaf8000`, a silent
  wrong load (lld agrees with the fix).

The fix is `erratum_windows(addr, len)`: the `[P+0xFF8, P+0x100C)` of every
page `P`, the page before the section's included. Tests:
`sites::tests::windows_cover_every_word_the_scan_reads` and
`pipeline.rs::an_erratum_site_across_the_page_takes_its_relocated_word`
(runs the program, exits 42, with ld.bfd alongside). Debian's aarch64 GCC
passes `--fix-cortex-a53-843419` by default, so this affected ordinary
links.

## `par` and the persistent pool

Measured with temporary instrumentation, reverted. protoc has **106
regions per link**. Spawns per link are 106 / 279 / 575 / 843 at 2 / 4 / 8
/ 12 threads. At 8 threads the caller spends 9–12 ms spawning and 17–54 ms
waiting in joins; at 12 threads, 13–16 ms spawning. The largest regions:

| region | time |
|---|---|
| fill | 50 ms |
| input store | 18.7 + 15.6 ms |
| scan | 11.7 ms |
| erratum `code()` (nested) | 9.1 ms |

Microbenchmark, per region with no-op work:

| threads | 2 | 4 | 8 | 12 |
|---|---|---|---|---|
| scoped spawn+join, wall | 96 µs | 108 µs | 281 µs | 390 µs |
| scoped spawn+join, CPU | 45 µs | 145 µs | 360 µs | 730 µs |
| persistent pool (condvar) wake | 5 µs | 35 µs | 78 µs | 141 µs |

Over 106 regions a persistent pool would save **~21 ms wall / ~30 ms CPU
at 8 threads** and ~26 ms wall / ~62 ms CPU at 12. That is most of the
CPU that grows with the thread count outside the phases' own work.

A safe pool does not work. `std::thread::scope` workers take `'scope`
jobs, and every phase's data is created inside the link, so it is shorter
than any link-long scope. A per-phase scope already is what `par` does.
"Data jobs" (owned inputs, `Arc`) would rewrite every call site and
copy. So `par` is unchanged.

The gain is minor faults. protoc at 1 thread goes from 61.8k to 8.7k
faults (8 threads: 70k → 23k), and nog from 40k to 9k. Effect of the THP
setting:

- **`never`**, simulated per process with `PR_SET_THP_DISABLE`, which
  exec inherits: the tunable does nothing (same faults, same wall within
  noise, on all four workloads).
- **`always`** could not be set: it is host-global. Anonymous regions
  would then get huge pages without the tunable, so most of the gain would
  arrive by default. The tunable adds `madvise`, which under `defrag
  [madvise]` also allows direct compaction.

Which buffers fault (protoc, 1 thread, `perf record -e page-faults`, by
first mortar frame):

| source | share of faults |
|---|---|
| input store copies (`Store::read_batch`, `Reader::read_into_own`) | 63 % |
| `object_ranges` | 5 % |
| `LinkSites::new` | 5 % |
| merge | 4 % |
| fixed point | 3 % |

The output image does not appear. Safe code cannot reach the same effect
without the re-exec:

- under `madvise`, only `madvise(MADV_HUGEPAGE)` (`unsafe` libc) or the
  tunable gives anonymous memory huge pages;
- the input copies live for the whole link, so reusing buffers saves
  nothing;
- mmap of inputs is WP-032a's `unsafe` row.

The re-exec (`main.rs` `hugepages()`, glibc on Linux only):

- The driver executes `/proc/self/exe`, with the same `argv[0]` (`arg0`)
  and the same `args_os`. `/proc/self/exe` is the real binary through
  `-B` directories and `ld` symlinks; `argv[0]` keeps the diagnostics
  name.
- It appends `glibc.malloc.hugetlb=1` to an existing `GLIBC_TUNABLES`.
- It does nothing when that variable already names the tunable (a user's
  `=0` wins) or when `MORTAR_HUGEPAGES_EXEC` is set (the guard).
- If the exec fails (no `/proc`), the link runs in the first process.
- On musl and other platforms it is a no-op.
- Cost: `--version` 0.34 → 0.53 ms, a hello-world link 1.9 → 2.1 ms.
- `strace -f` and debuggers see two execs of the same image. `--time-phases`
  starts in the second.

Test: `cli.rs::the_hugepage_exec_keeps_the_name_and_the_arguments`.

## The process around the phases

The gap between the `--time-phases` total and the process wall time is
4.5 ms at 1 thread and 7.3 ms at 8 (protoc):

| part | time |
|---|---|
| process start and `--version`-level work | 0.4 ms |
| `drop(front)` | 0.3 ms |
| `drop(store)` | ~1 ms |
| the rest: kernel `exit_mmap` of ~230 MB | ~3–6 ms |

Skipping destructors is not worth it. A mold-style early return (the
parent exits once a child signals the output is complete) could hide the
~4–7 ms teardown and could share the re-exec. It is not done.

## `unsafe` table (for the operator; nothing here is implemented)

| change | saving (protoc) | `unsafe` | alternative |
|---|---|---|---|
| A persistent worker pool for `par`: workers live for the link; each region publishes a lifetime-erased `&(dyn Fn(usize) + Sync)` and blocks until all workers have left it, panics included, like rayon's `scope` | ~21 ms wall / ~30 ms CPU at 8 threads; ~26 / ~62 at 12 (from 106 regions × (spawn+join − wake)) | one block: the lifetime erasure, ~150 lines around it | rayon (a third-party crate, itself `unsafe`) |

## Interface changes

- `mortar_layout::place_again(link, assignment, range, entry_def, pool,
  prev: Option<&Placed>)`, newly exported. `place` calls it with `None`.
- `mortar_layout::fixed::refix`, public. `fixed::needs` takes a `Steps`.
- `mortar::sites::SynthIds` derives `PartialEq, Eq`.
- Environment:
  - `MORTAR_TIME_STEPS` is removed; use `MORTAR_STEPS` (a new format for
    input and resolve's lines). The WP-032a record still names the old
    variable.
  - New: `MORTAR_HUGEPAGES`, and `MORTAR_HUGEPAGES_EXEC` (internal guard).

## What remains, ranked (protoc, head)

1. The persistent pool (`unsafe` table): `mortar_core/src/par.rs:201`
   (`drive`). This is the biggest CPU-growth item.
2. Hugepages by default, or the input copies' faults
   (`mortar_input/src/store.rs:1091` `read_batch`, `:1457`
   `read_into_own`; WP-032a's crate). They are 63 % of faults.
3. Layout `place` / fixed point: 8.6 ms (1T) and 5.9 (8T) over 2 rounds
   (`mortar_layout/src/fixed.rs:549`). The first round has no previous
   placement to reuse.
4. `LinkSites::new`: 10.3 ms (1T), 5.5 (8T) (`crates/mortar/src/sites.rs:109`).
   A walk of every code section's relocations, needed once per link.
5. Validate: 2.9–3.3 ms; it does not scale (`mortar_core/src/check.rs:266`).
6. Erratum needs and fixes: 2.3 + 1.8 ms (1T). `code()` still runs once
   per round and once at the fixes (`sites.rs:222`); a cache keyed by
   placement would remove one run. The walk could also be limited to the
   window span.
7. A safe region-size threshold in `par`, so tiny regions run inline. It
   needs per-call work sizes, and therefore every call site's numbers.
8. The early-return parent/child for the ~4–7 ms exit teardown.

## Spec findings

- a64.md §11.1–11.2 and the verifier: `mortar_plumb` passed both
  erratum mislinks. It should check every erratum fix semantically:
  - a patch's `W4'` equals the relocated word at `F`;
  - an ADR's target equals `Page(V)` of the relocated ADRP.
- a64.md §11.1 should state that the bytes a site reads are `[0xFF8,
  0x100C)` of a page, and may begin in the section before.
- `refix` relies on L-72 (non-alloc chunks after all alloc chunks). A
  change to L-72 must revisit `fixed::refix`, whose debug assertion
  compares it with the full fixed point.
