### 1. Wave A (`store.rs` `make_room`, `prefault`)

Cause, established with a throwaway program that replays wave A's
syscalls on synthetic-objects' 999 files over 68 KiB, at 1–12 threads:

- open + fstat alone scale (2.6 → 1 ms).
- Reads into fresh buffers anti-scale: 25–30 ms at 1 thread, 40–60 ms
  at 8–12. The fault is taken inside `read()`'s copy, in kernel mode,
  and on Linux 6.8 AArch64 a kernel-mode fault skips the per-VMA lock
  and takes `mmap_lock`, so every reader serializes on it. Touching each
  page in user mode first (`prefault`, one byte per 4 KiB) makes the
  same reads scale: 27 → 5 ms.
- Keeping ~1000 files open costs 25–40 ms by itself. A staged batch
  ((max_open / 4) clamped to 16..1024 files, 1024 here) holds its files
  from wave A to wave D. The kernel grows the descriptor table 64 → 128
  → ... → 1024 as they open, and `expand_fdtable` waits for an RCU grace
  period whenever the process has more than one thread. `make_room`
  grows the table before the batch's region starts, while the process is
  single-threaded: it opens `/dev/null` once, duplicates it `n + 16`
  times and closes them all (0.9 ms). A failure only stops the
  pre-growth; nothing read depends on it.

Wave A (`read.a`) median ms on synthetic-objects, load 13–15:

| threads | base | `make_room` only | both |
|---|---|---|---|
| 8 | 66–90 | 50 | 11–16 |
| 12 | 73–103 | 58 | 8–17 |

Input walk at 8 threads 112 → 59 ms; objects wall at 8 threads
313 → 265 ms; protoc at 8 threads input walk 54.7 → 39.2 ms, wall
225 → 195 ms (load 13). 1 thread unchanged (no regions, nothing to
serialize). RSS unchanged (the touched pages are the ones read anyway).

### 2. The gc mark (`gc.rs`)

Profile of `collect` on protoc `--gc-sections`, 1 thread, before:
facts 3–4 ms, defs 0.3, frames 1.9, round 0 0.6, rounds 9–13.5 (20
rounds, 23,186 units, 166,652 relocation records). A second warm walk
of the same records costs ~1.5 ms, so the rounds were cold misses and
per-unit overhead: three `partition_point`s per section (FDEs,
`SHF_LINK_ORDER`, groups), one binary search into `merge_of` per
reference, a swap per reference (a cache line taken exclusive even when
the section was marked long ago), and a barrier per round.

- **Facts bits** `MERGE`, `FDES`, `LINKED`, `GROUPED` say which lookups a
  section needs; most need none.
- **Load before swap**: a reference to a marked section (most of them)
  only reads the cell.
- **Continuation (I-8 amended below)**: a worker walks its unit, then
  depth first the sections its own swaps marked, up to `CONTINUE` =
  16,384 records per unit (no limit at 1 thread). It leaves to the next
  round what is past the budget, and any section of more than
  `SCAN_BLOCK` records (which the next round cuts into blocks). protoc
  marks in 3 rounds at 8 threads instead of 20.
- **Unit costs**: facts 800 ns/file, defs 7 ns/key, frames 2.5 µs/row,
  rounds 400 ns/unit, so a small link's mark stays on the caller.
- **Failures**: the closure is completed and every failure is collected.
  If any failed, the mark is run again with budget 0 (exactly the old
  breadth-first rounds, stopping after the first failing round), so the
  diagnostic reported is the one main reports. That costs time only on a
  link that fails anyway.

Rounds: 1 thread 9–13.5 → 5.5 ms; 8 threads 9.8 → ~5 ms. Phase 50
(liveness), `--time-phases`, n = 15, load 7:

| | 1 thread | 8 threads |
|---|---|---|
| phase 50 | 19.8 → 15.7 ms | 10.9 → 9.8 ms |
| wall | 559 → 525 (min 454 → 449) | 185 → 177 (min 168 → 158) |
| RSS | 207.8 → 207.9 MiB | 230.5 → 230.6 MiB |

`i8_the_mark_is_schedule_independent` and the other 12 tests of
`crates/mortar/tests/gc.rs` pass. The `--print-gc-sections` list is
identical on the gc links at every thread count, seed and store.

Not done: (b) caching per-file symbol lookups in `record_target`. Once
the binary searches went behind bits, the rounds were ~5.5 ms for
166,652 records (33 ns/record), and what remains is mostly the cold
first touch of each record. A cache would save the `sym_map` hop of
repeated symbols only; estimated < 1 ms.

### 3. Worker cap by input size (`front.rs` `capped`)

After phase 20, without `--threads` (any `--threads` form keeps the pool,
`--threads` alone meaning all) and without a scheduling seed, the
phases run on `min(threads, ceil(resident input bytes / 4 MiB))`
workers. Resident bytes are the store's count after input, a function of
the inputs; no clock is read. The input phase itself is not capped: its
sizes are not known until it ends, and on hello-c it is no slower at
default threads (walk 6.9 vs 7.3 ms).

### 4. Small costs

- **Branch needs** (`fixed.rs` `needs`): a result per branch site was a
  fresh 121,683-entry buffer per round, paid in page faults in the first
  round. `map_collect` keeps only the needs and failures, in branch
  order. protoc: 3.0 → 0.8 ms per link at 1 and 8 threads (both rounds);
  phase 90 35.2 → 33.3 ms at 1 thread, 24.6 → 22.6 at 8. RSS at 1 thread
  210.4 → 209.0 MiB.
- **Erratum `code()` twice** (`fixed.rs:423`, per output × erratum):
  reading each output's code once for both errata measured 4.7 → 4.9 ms
  (1 thread) and 2.6 → 2.8 ms (8). The code fill is not the cost.
  Reverted.
- **`validate`** (`check.rs:266`, 3.5 ms on protoc): 60% of its samples
  are sorts (the overlap checks' `taken`, `runs`, `memory`). A
  run-adaptive stable sort gave 3.5 → 3.5 ms. Reverted.

## Archive members resident as symbol tables (measured, not done)

Design: keep an unextracted member's ELF header, section headers,
`.symtab` and `.strtab` resident, read its other sections only when
resolution extracts it, then parse it again from the full parts. Upper
bound on hello-cxx (1 thread), from the map and the members' headers:
archive members 14.77 MB, of them 12.57 MB resident; the unextracted
members' resident bytes are 7.25 MB. Most of that is their symbol and
string tables or small members, which the archive chain's window reads
fetch anyway. A symbol-table-only design saves 1.15 MB (2.09 MB if small
members were split too). At `walk.read`'s 0.56 ms/MB that is 0.7–1.2 ms
of a 41 ms link, well under the 3% bar, and WP-032g's ≤ 5 MB estimate
was too high. Not implemented: it needs a second read after resolve and
a re-parse of each extracted member.

## Proposed amendments

**`spec/image.md` I-8**, replacing the paragraph:

> - **I-8 [M2] The algorithm.** A least fixed point. `live` is a column
>   of atomic booleans marked with `swap(true)` (model §6 rule 2:
>   idempotent, commutative); the worker whose swap returned `false` owns
>   the section and walks its edges, every live section exactly once.
>   The work is handed out in rounds: round 0 is the roots; a round's
>   units are the sections the round before left, partitioned by section
>   and, for a section with more than `SCAN_BLOCK` records, by
>   `SCAN_BLOCK` records (rule 6). A worker continues, depth first, on
>   the sections its own swaps marked until it has walked `CONTINUE`
>   records for the unit (no limit when the pool runs inline). It leaves
>   the rest, and any section of more than `SCAN_BLOCK` records, to the
>   next round, and the leftovers are concatenated in unit order (rule
>   3). The rounds only balance the load: the resulting *set* is the
>   least set closed under I-7 containing the roots, whatever the
>   schedule. Which round walks a section, and the order of a round's
>   list, may differ between schedules and are never observed (no id,
>   diagnostic or byte depends on them). A failure to read a section's
>   relocations is reported after the closure: the least-keyed failure
>   of the first breadth-first round (round `k + 1` = the sections first
>   marked by round `k`'s edges) that has one, found by marking again
>   breadth first.

## What remains, ranked (protoc, 1 thread unless stated)

   13–14 ms, 29 ms in one loaded run. Out of this WP's files (WP-030c).
2. Erratum needs, ~4.7 ms (`fixed.rs:423`, `sites.rs:248`). `code()`
   allocates and zero-fills the whole output section (`vec![0u8;
   size]`) per output × erratum × round, plus once in `erratum_fixes`.
   The windows touch every 4 KiB page, so each call faults the whole

   cost is the scan or the faults; next step: perf on that step alone.

   places could be checked in chunk order without sorting if the
   placement kept them so.

   3,536 files at 1 thread. It re-reads every file's section headers,
