# WP-032b — split, merge and scan: profile and first fixes

Branch `wp/032b-perf-scan`, cut from main d7a12b9, main 78dd0f9 merged
once. Crates: `mortar_merge`, `mortar_scan`, the scan/table side of
`mortar_a64`, `mortar_live`. No `unsafe`, no new dependencies, no
signature another crate calls changed.

## Method

- **Host.** 12 cores, shared; the load average was 7–12 during every run
  (stated per table). Wall times are therefore noisy; every before/after
  is interleaved (A B A B …, 9 runs) on the same inputs in the same
  minute, and CPU (user+sys from `wait4`) is given beside wall.
- **Inputs.** Copied once to one `/tmp` directory (removed at the end):
  `cxx-medium-g` (static protoc with `-g`: 3536 files incl. members,
  1.78 M relocation records, 804 k merge pieces, 52 MB mergeable bytes),
  `cxx-medium` (the same without `-g`), `synthetic-sections` (80 707
  relocated sections, 334 k records) and `synthetic-strings` (4.39 M
  pieces, 71 MB of strings). Static links, the `cargo xtask bench`
  command lines.
- **Sub-step timers.** `MORTAR_STEPS=1` (new,
  `mortar_core::wp032b_steps`) prints one line per sub-step of split,
  merge, order and scan to standard error with its count of work; off,
  one branch on a cached flag. It never reaches the output, the map or a
  diagnostic.
- **perf.** `apt-get install -y linux-perf` worked in the container;
  sampling (`perf record -g`, 20 kHz) was used to find the costs below.
- **Byte identity.** A golden script links all four workloads at
  `--threads=1`, `--threads=8` and `--threads=8` with
  `MORTAR_SCHED_SEED=977`, with `-Map`, and hashes output + map + stderr +
  exit status. The reference hashes were taken from the d7a12b9 build
  (protoc 5daca038a7f15f22, protoc-nog 070db282acb77342, sections
  9e729253145cd606, strings 004a0afca69f7353). Every commit below, and the
  final head after the merge of main, reproduces all twelve. The gate
  (`cargo xtask ci --quick`) runs the pipeline, determinism and link
  tests.

### Where the time goes, and what mold does differently

- **The scan walk** is 98% of the scan. On protoc 86.5% of the records
  (1.54 M of 1.78 M) are the relocations of non-alloc (`.debug_*`)
  sections; about 28% of the scan CPU at 1 thread is reading them and the
  debug bodies through the staged store's `copy_to` (read syscalls and
  page faults), the rest is per record: decode, `key_of`, the symbol's
  facts (a read of the defining file's symbol table), `classify`,
  `arch.scan` (fields, events), the window. mold's `--perf` has no scan
  row for debug sections: it scans the relocations of alloc sections only
  (from first principles: a non-alloc relocation cannot need a GOT, PLT,
  copy relocation or dynamic relocation; its checks can be done when the
  record is applied).
- **The merge** is 92% of split on protoc. intern is a hash table per
  shard probed once per occurrence with a byte compare against the
  representative: 804 k probes over 52 MB of `.debug_str`; mold's split
  is 2 ms for the same link because it hashes once per piece into one
  concurrent table and compares by hash only after a full-width match
  (from its row: inference, not fact).
- **eh parse** cost 6.2 µs per section with two binary searches over a
  section's relocations per record; it is now a running cursor.

### The two questions

- **44–177 ns/record against I-16's 3.5 ns: which is wrong?** Neither
  measurement; the model is. I-16's 3.35–3.68 ns timed a scan-like walk of
  decode + `sym_map` + one class-table lookup, with nothing else per
  record. The scan does more per record by specification: the symbol
  facts (a lookup in the defining file's symbol table, plus liveness for
  locals), the instruction and field checks and their events, the window
  and overlap bookkeeping, and — the largest single item — reading the
  86% of records that are debug relocations, and the bodies under them,
  through `copy_to` because the staged store does not keep them resident.
  Measured now: 31 ns/record at 1 thread on protoc (37 before), 21–68
  ns/record across the workloads; the higher numbers come from many
  small sections (per-unit overhead: open, symbol table, marks). I-16
  should be restated as a per-record budget per component (finding 1).
- **Does `mortar_live` cost anything?** No: 1.0–1.7 ms on protoc at every
  thread count, 4–6 ms on strings, ≤ 0.5% of any link measured. Nothing
  in it was changed.

## Fixes (largest first in effect; each its own commit)

Before/after are interleaved, 9 runs, median (min); CPU is the whole
process.

1. **9fe02ad — scan units from section headers.** The unit list opened
   every relocated section on the calling thread (records, symbol table,
   contents, mapping marks) only to count records: 3.8–4.9 ms serial on
   protoc (≈ 200 ns × 18 789), 8.8 ms on sections. A section of
   1..=`SCAN_BLOCK` records is now one unit from `sh_size / sh_entsize`;
   its walk opens it and reports what the open finds at the same key, as
   non-resident sections already did. protoc 8 threads: scan 15.0 → 11.8
   ms; 1 thread unchanged (the work moved into the walk, now parallel).
   RSS unchanged.
2. **9fa820a — merge: tagged table over one counting-sorted column.** The
   partition is a counting sort by (shard, range) into one `u64` column
   instead of `Vec<Vec<Vec<_>>>` buckets; intern probes an open-addressing
   table whose slots carry the hash's low half as a tag and whose entries
   hold (row, offset, length), so a candidate is compared without further
   lookups; entry ids and then `FragId`s are written over the column in
   place (no `entry_of` atomics), representatives marked in one bit set.
   protoc: intern 32.7 → 28.1 ms (1 thread), 11.1 → 8.4 ms (8); split
   60.5 → 57.0 / 21.4 → 18.9 ms. strings: intern 84 → 59 ms, split 173 →
   152 ms (1 thread); 8 threads split 49.2 → 47.6 ms, **RSS 256 → 237
   MiB**. partition and resolve became slightly slower (see remaining 3).
3. **e220887 — eh: relocation spans by cursor, CIE by binary search.**
   sections: eh 7.74 → 2.94 ms, split 10.5 → 5.6 ms, CPU 347 → 333 ms (1
   thread); eh 8.22 → 3.78 ms, split 13.0 → 8.4 ms (8). protoc: eh 4.69 →
   2.17 / 1.89 → 1.02 ms. The CIE search was quadratic in the records of
   a section whose CIEs are not all first (an `ld -r` object); now
   logarithmic. RSS unchanged.
4. **ff95a4d — scan: a local's symbol read once; overlaps skipped for
   disjoint in-order windows.** `View::facts` read a local's symbol twice;
   `overlaps()` (a sort and a sweep per unit) now runs only when the
   windows are not already in order and disjoint (checked in one pass).
   protoc scan 1 thread 58.4 → 51.5 ms, 8 threads 11.1 → 10.3 ms.
5. **1c6f16f — mapping marks indexed by section.** `View::marks` binary
   searched all of a file's marks per call; the scan, `LinkSites` and the
   layout fixed point call it per code section (some many times): 6.9% of
   the 1-thread sections link. Now a per-section start index. sections 1
   thread: CPU 355 → 339 ms, layout 126 → 113 ms (the driver's callers
   gain most); protoc within noise.
6. **c92d0d3 — a64 classify by a compile-time table.** `table::howto` is a
   `const` match evaluated per call; `classify` now loads the row from a
   static array of `howto(t)` for `t < 1030`. scan 1 thread 51.5 → 50.6
   ms. The classify test checks `lookup(t) == howto(t)` for every `t ≤
   0xFFFF`.

## Interface changes

- **Made (additive, prefixed):** `mortar_core::wp032b_steps` (`Steps`,
  `enabled`, `STEPS_VAR`). Reconcile with any step timer WP-032a adds.
- **Made (inside my crates):** `mortar_a64::table::lookup(r_type) ->
  Option<&'static Howto>` (new, beside `howto`); `mortar_scan` internal
  `FileMarks`; `UnitOut::nonalloc`.
- **Proposed (not made): `Arch` says whether a howto reads its site's
  bytes** (or `Site` carries the section length beside the bytes), so the
  scan need not copy a non-resident debug body only to bound-check a
  data relocation. A prototype that skipped the copy saved 3–5 ms CPU at 1
  thread and ~0.6 ms wall at 8 on protoc; output identical. Owner: WP-029b
  (`mortar_arch`).

## What remains, ranked by estimated saving (protoc unless named)

1. **Scan of non-alloc records** (`crates/mortar_scan/src/driver.rs:516`
   the walk loop; 86.5% of records): do the debug relocations' checks at
   fill, or give `Arch` a non-alloc fast path that only resolves the
   symbol and the howto's range check. ~35–45 ms CPU at 1 thread, ~7 ms
   wall at 8. Needs the spec change of finding 2.
2. **Non-resident reads** (`crates/mortar_scan/src/view.rs:512`
   `contents`, `:533` `rec_table`): the `Arch` proposal above (bodies),
   then batched/coalesced `copy_to` per file for `.rela.debug_*` (one
   read per file range instead of one per section). ~5–10 ms CPU.
3. **Merge partition/resolve** (`crates/mortar_merge/src/merge.rs:333`–
   `:465`): resolve reads `column[cursor[s]]` across all shards (cache
   misses over a 35 MB column on strings: 4.0 ns/piece, was 2.6), and the
   fresh column page-faults. Writing `piece_frag` per shard by scatter
   (shard-major, sequential reads) and reusing the cut's vectors should
   recover 5–10 ms on strings at 1 thread and fix its scaling past 4
   threads.
4. **Merge intern byte compares** (`merge.rs:390`–`:416`): 33 ns/piece on
   protoc is dominated by comparing duplicates' bytes with the
   representative's (52 MB, random). Compare a 64-bit second hash first,
   bytes only on a full match: ~8–12 ms CPU at 1 thread.
5. **Image phase lookups into the split** (not my phase, my crate):
   `crates/mortar_merge/src/refs.rs:28` `section_symbol` / `:42`
   `named_symbol` binary-search `Split::merge_piece_at`
   (`crates/mortar_core/src/split.rs:122`) per reference: 11.7% of the
   1-thread link in perf. A per-section bucket index (like the marks fix)
   would cut most of it: ~40–60 ms CPU at 1 thread, ~6 ms wall at 8.
   Ranked here by phase ownership; by saving it is first.
6. **Per-unit scan overhead on many small sections**
   (`driver.rs:486` `walk_unit`: `Sec::open`, five `Vec`s per unit):
   sections 63 ns/record vs strings 21. Reuse the vectors in `Bufs`:
   ~3–5 ms at 1 thread on sections.
7. **eh parse within a section** (`crates/mortar_merge/src/eh.rs:634`):
   parallel by section only; sections has 3 large `.eh_frame`s, so eh is
   ~3 ms at every thread count. A length-only pre-walk then FDEs in
   parallel chunks: ~2 ms wall at 8 threads on sections, < 1 ms on protoc.
8. **split units** (`crates/mortar_merge/src/phase.rs:257`): parallel by
   file, 2 ms on sections (few files, many sections). < 2 ms.

## Spec findings

1. **I-16 (`spec/image.md` §4.2) is not a model of the scan.** It costs
   one decode, one `sym_map` and one table lookup (3.5 ns); the scan as
   specified does several table reads, checks and events per record, and
   reads non-resident data. Proposed restatement: a budget per component
   (decode 1, key 2, facts 5, classify 1, arch scan 8, window 2 ns; plus
   the non-resident read cost per byte), checked by `MORTAR_STEPS`.
2. **Scanning non-alloc relocations is the scan's largest cost (86% of
   records on a `-g` link).** No consumer of the scan (GOT, PLT, dynamic
   relocations, copy relocations, TLS) is reachable from a non-alloc
   section. Proposed rule: the scan visits alloc sections only; the
   checks a non-alloc record needs (symbol resolves, type allowed in a
   non-alloc section, range) are fill's, with the same diagnostics at the
   same key. Diagnostics order would need restating for these records.
   I-14 (debug records' fast path) is not implemented.
3. **S-28's shard walk is fine; its resolve is not cache-friendly at scale**
   (remaining 3): no rule change, an implementation note.

## Bench

No harness code was added: `cargo xtask bench` already links all four
workloads (`cxx-medium-g`, `cxx-medium`, `synthetic-sections`,
`synthetic-strings`). Proposed for the next harness change: run each
mortar link once more with `--time-phases` and `MORTAR_STEPS=1` (outside
the timed runs, so they are not slowed) and record per phase and per
sub-step the median ms and the unit cost; report them under the
workload's row. Proposed thresholds: no CI gate on wall time (noise on
this host is ±10–25%); a soft alarm on the **1-thread unit costs** (CPU,
not wall) when a sub-step's ns/unit grows by more than 15% against the
baseline over 9 runs, and the existing 2% RSS gate.
