# WP-032f — performance: the fill (image phase), second pass

Branch `wp/032f-perf-fill`, cut from main 543fd4e; main a7fda39 (WP-027e)
and main 86d5439 (WP-031 `--gc-sections`, WP-028d) merged. Crates: `mortar_image` (fill, `reloc.rs`, `link.rs`'s
tables, `source.rs`), the image-side lookups of `mortar_merge/src/refs.rs`
(additive). No `unsafe`, no new dependencies, no signature another crate
calls changed.

## Method

- Inputs copied to one `/tmp` directory (removed at the end): protoc
  static AArch64 with `-g` (`cxx-medium-g`: `main.cc.o`, `libprotoc.a`,
  `libprotobuf.a`), the same without `-g` (`cxx-medium`),
  `synthetic-sections`, `synthetic-strings`, and an x86-64 `-g` link (41
  C++ units written for this package — templates, virtuals,
  `thread_local`, exceptions, iostreams — `x86_64-linux-gnu-g++ -g -O1`,
  static, runs under qemu-x86_64). Link lines: `g++ -static -###`'s.
- Byte identity (WP-032c's method): output, `-Map` and stderr+status
  hashed (sha256, 16 digits) for the five workloads at threads 1, 8 and 8
  + `MORTAR_SCHED_SEED=977`, under `MORTAR_STORE=resident` and staged: 30
  links per binary. Every commit before the merge reproduces the base
  543fd4e's hashes (protoc 5ebf458fb3b7aa73, nog 6791fa06223b3be8,
  sections 2e2c0af8abc6ff58, strings 0ccc0ad759628c7c, x64
  add3c2cf28ac5474). After the merge (WP-027e changes every output's
  `.comment`, and `-Map` became the text map) the head is compared with
  main a7fda39 built separately from `git archive`: all 30 identical
  (protoc 75278a0928ee1b74, …). After the second merge the set has two
  `--gc-sections` workloads more (the 41 C++ units above compiled with
  `-g -O1 -ffunction-sections -fdata-sections`, static, `--gc-sections`,
  for AArch64 with `g++` and for x86-64; both run and print the
  reference's output), 42 links per binary, and the head 70d93d3 is
  identical to main 86d5439 built from `git archive` on all 42 (protoc
  75278a0928ee1b74, nog e86db48539434fa7, sections d2b58c211126ff45,
  strings 2c4a4a444e908b2c, x64 ae45af86d051544c, gc-a64
  7975fbb02edfde87, gc-x64 91e6dfb3589b6412).
- Timers: `MORTAR_STEPS=1` now also prints fill's sub-steps summed over
  the workers: the jobs' fills, the copies from the store (bytes and
  reads) and the sink's writes (bytes). `perf record -g` (20 kHz) on the
  1-thread link; samples under `fill::write_checked` folded by leaf.
- The host: shared, load 6–21 during this package (stated per table).
  Interleaved A/B runs (A B A B …), medians (minima) of 9–15. Hardware
  counters are not available in this VM (`perf stat` reports
  instructions and cycles as not supported), so sample shares from
  `perf` back the wall numbers where the host was too loaded.

## Item 5: kernel time in fill, and the `unsafe` estimates (not written)

Where it is (protoc, staged store, head): copies from the store 36 ms at
1 thread (72.9 MB, ~2 GB/s through `pread` of page-cached archives on
overlayfs), writes 15 ms (50.3 MB). At 8 threads the writes sum to 48 ms
for the same bytes: `pwrite` to one file serializes on the inode, so
workers wait (about 4 ms of wall per worker). Page faults on the window
buffer are not a cost: the 1 MiB buffer is reused per worker.

Safe options measured or reasoned: (a) the resident store removes the
copies (jobs 159 → 131 ms) but is the store's policy (`mortar_input`, not
mine); (b) `table_order`'s 8 MB re-read could go if clips verified the
order of the records they read and a violation re-ran the section
(about 4 ms at 1 thread; changes I-14's procedure, not done); (c) a
single writer thread fed by the workers (double buffers, +1 MiB each)
would hide the write serialization (~4 ms wall at 8 threads, 2–3 % of
the link) — needs a thread outside `par`, so proposed, not done.

| site | safe cost now (protoc) | estimated saving | invariant to audit |
|---|---|---|---|
| inputs by `mmap` instead of the staged store's `pread` (`source::read` → `Store::copy_to`, `mortar_input/src/store.rs:626`) | 36 ms CPU at 1 thread (73 MB copied) | 25–30 ms at 1 thread (faults remain, ~16 k pages), ~4 ms wall at 8 | no input truncated or rewritten while mapped (SIGBUS); the store's change detection (input.md §11.5) kept |
| output by `mmap` instead of a reused buffer + `pwrite` (`fill.rs` `run_job`) | 15 ms at 1 thread; 48 ms summed at 8 threads (inode lock) | 5–10 ms at 1 thread; 4–6 ms wall at 8 | no truncation or other writer of the output while mapped; workers' ranges disjoint |
| unchecked indexing in the record loop (WP-032c's estimate) | bounds checks ≤ 2–3 % of fill | ~5 ms at 1 thread | each field window proved inside the clip |

## What remains (ranked by estimated saving, protoc 1 thread)

1. Kernel copies and writes (item 5, above): 25–40 ms at 1 thread, only
   with `mmap` (operator) or a resident store policy (`mortar_input`).
2. The record loop itself (`reloc.rs` `relocate`, 31 % of fill, about
   25 ns per record): `classify`, `arch.scan` + `unit_window` for the
   deferred check (about 18 ms of fill at 1 thread, measured by switching
   it off), `apply`, each a dynamic call with a `Howto` by value and a
   `RelocAt` built per record. The next step needs `mortar_arch`'s
   design: e.g. an `Arch` statement that a type's scan at a non-alloc
   place depends only on (type, target facts, place) so that fill can
   memoize the check per (key, type), or a batched `apply` of plain data
   fields. Est. 15–25 ms. **This is where I stopped: the next fix needs
   `mortar_arch`'s interface.**
3. Piece lookups for split targets (`refs.rs` `PieceIndex::at`, 7.4 % of
   fill): cache misses over each file's `.debug_str`; a memo does not
   help (5 % repeats). A table of output offsets per input piece would
   save one dependent load per record for 3–6 MB of memory. ≤ 8 ms.
4. Write serialization at 8+ threads (a writer thread): ~4 ms wall.
5. `table_order`'s whole-table read for deferred sections in several
   clips (8 MB): ~4 ms at 1 thread; needs an I-14 procedure change.
6. Decode (`RecordKeys::locals`, measured 1.3 %): ~5 ms, under the bar.
7. Fix 4 on its own under `--gc-sections` was not measured apart from the
   rest (the gc links' fill fell 16–23 % in all). The memo respects
   liveness: it caches `SymValue.live` (which WP-031 made include a named
   symbol in a collected piece) per key, and a split target's piece
   liveness (`frag_live`) is checked per record in `split_at`, so a dead
   target's field is the tombstone, never an address; the gc links are
   byte-identical to main.
