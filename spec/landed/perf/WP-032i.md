# WP-032i — performance: the ranked safe remainder

Branch `wp/032i-perf-remainder`, cut from main 2297dac, merged with main
31d9575 (WP-041 step 0, WP-030d) once. Crates: `mortar_arch` (`need`),
`mortar_scan` (driver, walker, view), `mortar_synth` (`symtab`),
`mortar_x86` (`classify`), the driver (`sites.rs`, `front.rs`). No
`unsafe`, no new dependency.

## Method

- Workloads as WP-032h (static protoc `-g`, nog, `synthetic-{objects,
  strings,sections}`, hello-c, hello-cxx, protoc `--gc-sections`, the
  three-file C++ gc program for AArch64, x86-64 and i386, and the same
  program `-g` without gc on i386), plus a 101-file synthetic C++ program
  (284k records) built for i386 and for x86-64, for item 6. Interleaved
  runs (A B A B ...), one warm-up, n = 9 unless stated; the load is stated
  per table (the host was at load 9-35 throughout; 12 CPUs, shared).
- Byte identity at every commit: output, `--mortar-map` map, stdout,
  stderr and exit status of 78 links hashed together (10 workloads x
  {1, 8, 8 + `MORTAR_SCHED_SEED=977`} x {staged, resident}; hello-c and
  hello-cxx x {1, 8, 8 + seed}; 12 workloads at default threads). The gc
  links' stderr is the `--print-gc-sections` list. Before the merge every
  commit hashed as 2297dac: `64c89cf1e44a38d7`; after it, as main
  31d9575: `0c44e634c40253b3` (main's outputs differ from 2297dac's by
  WP-041 and WP-030d). All 78 statuses 0. `cargo xtask static-identical`:
  167 links, 0 differ.
- Verifier: each of the 14 distinct outputs (8 threads) through
  `cargo xtask plumb <out> --map <map> --map-format mortar`, run from the
  link's directory: 0 findings on all 14 (i386 included; WP-030d's
  aranges fix is merged).

Item 6: on the synthetic pair the i386 scan cost is 1.0-1.3x x86-64's per
record, not 2.4x. Of what was left, 6 % of a 1-thread link was `classify`,
mostly the mispredicted indirect jump of `table::howto`'s `match` over
i386's mix of `PC32`/`PLT32`/`GOTPC`/`GOTOFF`/`32`. A table read and
skipping `read_window` for the 13 types that have no window took it to
3.8 %.

Item 3a: in `PieceIndex::at`, 42 % of its samples are the `piece_frag`
load and ~30 % are the bucket search on `piece_off`. Both are first-touch
misses on 3.2 MB columns (804,257 pieces). A per-piece output-offset table
would also be 3.2 MB, touched in the same pattern. It would remove only
the frag-indexed loads (79,044 frags, L2-resident) inside `split_at`'s
~5 ms self time, less the cost of building the table. Estimate: <= 2 ms at
1 thread, ~0 at 8, for +3.2 MB of RSS. Not worth doing.

Item 4: `validate`'s sorts are of unsorted lists (frag runs, section
`taken`), so they are needed. On strings, 503,507 frags sort in ~13 ms.
Allocation and faults dominate, and the three rewrites gave nothing
measurable.

Item 5a: `file_facts` runs at ~15 ns per section (226k sections). Taking
the bits from the input walk would need new per-section columns in
`mortar_input` and `Resolution`. That saves ~3 ms at 1 thread and ~2 at
8. Left for a package that owns those crates.

Item 5d: at 8 threads, protoc's workers spend 59.5 ms of CPU in `pwrite`,
against 15.8 ms at 1 thread (inode lock). A writer thread fed by double
buffers would serialize those 15.8 ms behind fill's ~30 ms wall. Estimate:
3-5 ms wall at 8+ threads, for +2 MiB per worker of RSS.

## Remaining, ranked (protoc, 1 thread unless stated)

1. fill's relocation loop: `relocate` 11 % self plus `apply`/`scan` 4.4 %,
   ~70 ms of ~2.2 M records (`crates/mortar_image/src/reloc.rs`
   `relocate`). A batched or memoized `apply` (a howto and class per run
   of same-type records, no `dyn` call per record) could take 15-20 ms at
   1 thread and 2-3 ms wall at 8. That is the largest safe item left.
2. Scan walk cost of item 1: 3 ms on protoc and 6-15 ms on objects
   (`crates/mortar_scan/src/driver.rs` `walk_unit`, the
   `branch_candidate` call). `consumed` runs `gd_lead` a second time per
   `CALL26`; the arch's own scan has already decided R4 for the record.
3. `PieceIndex::at` (`crates/mortar_merge/src/refs.rs:204`), item 3a:
   <= 2 ms.
4. gc facts (`crates/mortar_live/src/gc.rs:257`, `file_facts` :472),
   item 5a: ~3 ms at 1 thread.
5. Writer thread (`crates/mortar_image/src/fill.rs` `run_job`), item 5d:
   3-5 ms wall at 8+ threads.
6. The walker's first use in erratum needs (`View::marks`,
   `crates/mortar_scan/src/view.rs:118`): ~4 ms on sections. It could be
   shared with the scan's `View`, which would need a `scan_with_walker`.

## `unsafe`

None added. Kernel time was measured as `ru_stime` from `wait4` over 5
runs, with the per-thread CPU timers of the fill and input steps beside it.
On protoc at 1 thread with the staged store: user 384 ms, sys 117 ms;
`input walk.read` 84 ms, `fill reads` 17.6 ms, `fill writes` 12.8 ms. The
resident store reads everything up front (sys 200 ms). Only mapped input
and output, which need `unsafe` (`memmap`) or a dependency, could remove
these:

- input: the copy in fill reads (~15 ms), `table_order` (~1.3 ms), and
  the copy part of the input walk's reads (~30-40 ms);
- output: the per-window buffer and `pwrite` (~10 ms at 1 thread, plus
  the inode-lock contention at 8 threads).

Together that is ~55-65 ms CPU at 1 thread and ~8-12 ms wall at 8. As
WP-032c/f found, it has to be weighed against page faults and the SIGBUS
risk of a truncated input.
