# WP-078: the verifier's rules for the one-definition-rule metadata

Landed record. The rules are `spec/plumb.md` §13 (stage 4, P-M1 to
P-M3), which implement `spec/odr.md` §12.5 (amendment A-7) over the
container of `spec/meta.md`. This file gives what landed (§1), the rules
(§2), the corpus (§3), the mutants (§4), the sweep (§5), the cost (§6),
Q11's answer (§7), the map request (§8), the spec findings (§9) and what
was not verified (§10).

The verifier was written from the specs, the ELF and outputs of mortar
and `cargo xtask meta` only: no linker crate was read for how anything
is computed. Where the spec did not say, the behaviour was **measured**
(a link run and its output read) and the reading is a spec finding
below, not a guess written into a rule.

## 1. What landed

- `crates/mortar_plumb/src/meta.rs`: a second reader of the container
  (MT-1 to MT-14, MT-35), on `mortar_elf` alone; its tests read the test
  producer's units (one unit; two units with padding between them),
  every MT-14 malformation (named, the unit skipped), and hostile
  containers (no panic).
- `crates/mortar_plumb/src/odrtable.rs`: stage 4, run by `verify` and
  `verify_with` on every output before stage 3's early returns.
- `report.rs`: `Rule::Meta(n)` (`P-M1` to `P-M3`), `Coverage.meta`
  (`MetaCoverage`) and the summary's `ODR metadata` line.
- `line.rs`: `--odr-table`, `--odr` take their argument in the next word.
- `sweep.rs` (the verifier's): `.note.mason` and `.mason.meta` are swept;
  each note byte is named by field.
- `xtask/src/sweep.rs`: cases `table` (`-pie -rdynamic
  -Wl,--odr-table=exported`) and `table.full` (`=full` and
  `--keep-mason-meta`), each with a test-producer unit (`lang=c++`, a
  vague exported definition, a hidden one, two types).
- `crates/mortar_plumb/tests/meta.rs` with fixtures under
  `crates/mortar_plumb/tests/meta/{aarch64,x86_64}` (made by `gen.sh`:
  three units over two objects, a shared library, a static initialiser;
  3 table rows, 3 `=full` rows, 888 kept bytes each).
- `spec/plumb.md`: §13 rewritten; §1, §7.1, §7.2, §12.3 point to it.

## 2. The rules

- **P-M1 (containers in outputs)**: no input container placed in an
  executable or shared object (MT-31); the kept `.mason.meta` is
  `PROGBITS`, flags 0, alignment 8, and byte-equal to MT-32's (the units
  that parse, in FileId, section and offset order, each padded to 8),
  present exactly with `--keep-mason-meta` and a unit; an ordinary
  `.mason.meta` (encoding K) is legal without the option, refused with
  it when the kept section exists.
- **P-M2 (`.note.mason`)**: place (section and `PT_NOTE` attributes,
  whole notes owned by `MasonMeta`, the two types), presence (a table
  exactly when due, `=full` exactly when asked), header and shape, order,
  key (FNV-1a 64 of the `.dynsym` name), version, row set (O-50 over the
  keeper's row), hash and flags (the keeper's row, with
  `NONPREEMPTIBLE` in an executable), and `=full`'s note (header, order,
  definition rows, one type row per kind 3 group).
- **P-M3 (no code)**: in an output with a table or with the option, the
  initialiser arrays hold only placed input sections of their type and
  no linker chunk; every relocatable input is on the command line.

Every finding's message starts with the sub-rule's name, so a mutant is
caught by rule and field.

**WP-099 §8's list**, against these rules:

- MT-1 exactly: a section is a container only by MT-6 (name,
  `SHT_PROGBITS`, flags exactly `SHF_EXCLUDE`), so `SHF_GNU_RETAIN`,
  `SHF_GROUP` or `SHF_X86_64_LARGE` make it not one; a container with
  alignment other than 8 or non-zero entsize, link or info is not read
  and is counted malformed (`meta: malformed`). Both as measured on
  mortar.
- MT-2a: a container a relocation section applies to is not read and
  not kept.
- MT-32: P-M1 above. One difference from §8's sentence: an ordinary
  `.mason.meta` (no `SHF_EXCLUDE`, encoding K) in an output without the
  option is legal (MT-6, measured), not a finding.
- A near name (`.ldata.mason.meta`): **not implemented**. It breaks no
  rule (it is not a container, MT-6), and the verifier reports findings,
  not notes; a producer-side warning would be the place for it.

## 4. The mutants

`tests/meta.rs`, on both fixtures (aarch64 and x86-64). Each mutant is
caught by the rule and sub-rule named.

- **P-M1** (8): a byte, the size, the flags, the alignment and the type
  of the kept section; `--keep-mason-meta` dropped from the map; the
  map's `chunk synthetic .mason.meta` dropped (all `kept section`); an
  input container placed (`container`).
- **P-M2, the first note** (26): section alignment, type and flags; the
  owner, `n_namesz`, `n_type`, `n_descsz`; `PT_NOTE`'s `p_align` and
  `p_filesz` (`place`); version, count, `row_size`, reserved, a row's
  reserved (`header`); two rows swapped (`order`); a key (`key`); a hash
  (`hash`); `NONPREEMPTIBLE` cleared, `VAGUE` and `SYSTEM` flipped
  (`flags`); a `.dynsym` index past the end; a row moved to an exported
  definition O-50 gives none, with its key made to match, which is
  caught twice: the extra row and the missing one (`row set`);
  `--odr-table` dropped, `=exported` for `=full`, `--odr=off` added
  (`presence`).
- **P-M2, `=full`'s note** (18): header version, definitions, `row_size`,
  types; a definition's key, hash, layout, size, alignment, flags and
  `NONPREEMPTIBLE`; a type's key, hash, layout, size, alignment and
  flags; two type rows swapped (all `full`).
- **P-M3** (3): `.init_array` one entry longer than its inputs and a
  linker chunk in it (`init array`); an input not on the line (`input`).
- **Hostile**: every single-byte change of both notes and the kept
  section of one fixture is judged without a panic.

**Not mutated**: `version` (the fixtures have no `.gnu.version`; the
sub-rule ran on the corpus's versioned outputs, with no finding).

case 0 survivors, the two new ones included:

| case | bytes swept | survivors |
|---|---|---|
| `table` (`=exported`) | 1822 | 0 |

13075 bytes in 166 s. The new cases' bytes include every field of both

`nopie`).

## 6. The cost

Release build, 108 corpus outputs, host load about 11: stage 4 takes a
median **0.42 ms** per output (p90 0.72 ms, max 0.84 ms), against about
28 ms for the whole `xtask plumb` process. Its work is one read of each
live object's containers and symbol tables (which stage 1 reads anyway)
and an index of the live definitions built only when a unit exists: an
output with no metadata pays the container scan alone.

## 7. Q11: should the verifier re-run the comparison itself?

**Answer: not now.** Costed:

- **What it takes.** Grouping every live kind 2 row by key and name;
  partitions by hash and by layout; the schemes (O-11), rows set aside,
  the modes; kind 1's `ENFORCE` (O-30); kind 5 with the C rules (O-33);
  archives (O-23); W1 to W3. About 800 to 1200 lines and 1.5 to 2 weeks,
  a second implementation of `spec/odr.md` §3 to §8.
- **Runtime.** About one more pass over rows stage 4 already reads:
  under 1 ms per output on this corpus.
- **What it could catch.** The verdict lives in diagnostics and the exit
  status, not in the output. Without a new map record carrying the
  link's findings, the verifier could catch only "an error-mode link
  produced an output despite a violation". With the findings in the map
  it would catch missed and spurious verdicts, and liveness or anchoring
  bugs that leave the table unchanged.
- **What already exists.** The independent oracle for the verdict is
  `model/odrmodel.py` and the `odr_model-*` tests; stage 4 already
  checks every byte the verdict leaves in the output.

So a second verdict would mostly duplicate the model, and would need a
map change before it can see anything. Worth it once the model stops
covering the corpus (M7, Tuck), with the map record requested first.
`odr.md`'s recommendation (kind 2 at L11 only, compare hashes per key)
is the cheap half of this: it is still gated on the same map record.

## 8. Map request

A static link's map has no `arg` records (§3.2), so on a static output
the options are unknown: `--keep-mason-meta`, presence and P-M3's input
check are not judged there (53 of the 106 corpus outputs). Requested:
`arg` records in every mortar map, or one record giving the ODR options.

## 9. Spec findings

1. **O-50's "has a kind 2 row"** is the keeper's row (measured: a
   keeper without a unit gives no table row even when a losing copy's
   unit has one). The spec should say so.
2. **`=full`'s "live definition"** includes definitions `--gc-sections`
   collected (MT-21: liveness is per file). Measured; the spec should say
   whether that is intended.
3. **MT-35**: units of another major are not kept by MT-32 (measured).
   MT-32 says "the units"; it should say "the units that parse".
4. **`n_descsz`** must be exactly the header plus rows; O-52 says only
   that the descriptor holds them.
5. **C units**: mortar ignores the kind 2 and 3 rows of a unit whose
   kind 1 `lang` is `c` (measured). O-33 states only the producer's
   side; the reader's is unwritten.
6. **MT-14's tie-break** for anchored rows ("then name bytes" when a row
   has no name) is unclear; the verifier checks only ties of two named
   rows.
7. **MT-1's attributes** (alignment exactly 8, `sh_entsize`, `sh_link`,
   `sh_info` 0) are "checked by the reader", but MT-14 does not list
   them; measured: such a container is not read, and not kept.
8. **`lang` values** other than `c` and `c++` are unspecified.
9. Whether rows set aside within a unit appear in the table was not
   determined (no corpus output has one).
10. **A table with no units.** A dynamic executable linked with
    `--odr-table` and no `.mason.meta` input at all gets a count-0
    table (and with `=full`, an empty second note). O-50 as written
    allows it (a table of "one row per definition" that has a qualifying
    row: none). The verifier first required a unit (an unconfirmed early
    measurement); the variant corpus (§3) caught that on 88 outputs and
    the rule now follows O-50. Worth one sentence in O-50 either way: a
    loader-side reader (O-24, WP-077) will meet many such tables.
11. Observation, outside this package: mortar with `-export-dynamic` and
    no shared input exported nothing.

## 10. Not verified

- P-M1's option and P-M2's presence on static outputs (§8).
- Shared-object tables (M4; held to "no table"); `-r` outputs.
- Kinds 4 and 5 beyond their framing.
- MT-2a and MT-1's attribute rule: measured on WP-099's corpus links,
  no committed test of the verifier's own.
- i386 tables: the corpus's i386 outputs are static or carry no table.
- The hosted lanes: run after this record was written (the id is in the hand-back).
