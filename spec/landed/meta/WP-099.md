# WP-099: hod as a second producer of `.mason.meta`

Landed record. The rules are `spec/meta.md` MT-1, MT-2, MT-2a (new),
MT-4, MT-6, MT-10, MT-14, MT-32 and `spec/odr.md` §11 ("hod"). This file
gives the environment (§1), the answer to the package's question: what
of the container only an object writer knows (§2), what landed (§3), the
equality of the two producers (§4), what a code generator puts around
the section (§5), the tests (§6), the cost (§7), what kiln's hod route
and WP-078 need (§8), the findings for kiln and hod (§9) and what was
not verified (§10).

## 1. Environment

The host of `WP-070.md` §1 (aarch64, 12 cores shared with other agents;
GCC 14.2, binutils 2.44, LLVM 22). hod at `a598555f` (release build,
package `hod_cli`), kiln++ at the workspace's kiln submodule commit (its
release build). x86-64 objects are linked on this host (mortar is a
cross linker); the x86-64 programs of the link tests run under
qemu-user. **i386 is not covered**: neither kiln nor hod targets it
(`kiln++: unsupported target 'i686-linux-gnu'`, `hod: unsupported
construct 'unsupported-target'`), so no i386 Mason object exists; the
producer modes leave i386 out by name.

## 2. What only an object writer knows (item 1)

The answer, from `meta.md` and confirmed on hod's objects: **nothing in
the record kinds the test producer writes** (kinds 1 to 5). MT-2 and
MT-12/MT-15 forbid a record to hold a section index, a symbol index, an
offset or an address; every reference is by name or by FNV-1a key of a
name, and a row is anchored (`odr.md` O-4) to a GLOBAL symbol the file
defines, found by name when the link reads it. What the writer of IR
must therefore know is only what IR already states:

- the **symbol names** of the definitions it anchors to: IR names are
  ELF symbol names (no mangling step in the code generator). A `private`
  or `internal` definition has no global symbol and cannot be anchored,
  exactly as in the ELF form (a row anchored to it is unanchored, O-4).
- the **section's identity**: name, type and flags (MT-1, MT-6). IR
  states the name; hod's rule 9.7.4 gives `SHT_PROGBITS` with `E` from
  `!exclude !{}` (§5 says what else it can add).

One thing a future kind could need is not expressible: **kind 0x10**
(reserved by MT-16, unspecified, not written by the test producer, not
in kiln's K-1..K-6) names sections by (name, group signature, ordinal);
the ordinal of a section among those of one name and group is the
object writer's choice unless the IR pins every such global's
`section`. Smallest example: two `linkonce_odr` functions of one comdat
with no `section` attribute; IR cannot say which `.text.*` section is
"ordinal 1". So kind 0x10, when it is specified, must name sections by
something IR can pin (an explicit `section` name per global), or be
written by the code generator itself. This is a note for MT-16's future
author, not a blocker: no kind in use has the problem.

Also stated by IR's form, not by hod: several description sections
(MT-4) become ONE section (all `@__mason_meta*` globals of one section
name share it, initializers in order); MT-4 reads several sections as one
sequence of units, so the reader's answer is the same.

`cargo xtask meta write <description> --ll <out.ll>` writes the unit as
IR (one `private constant [N x i8] c"..."` per description section,
every byte outside printable ASCII, `"` and `\` as `\XX`; `section
".mason.meta"`, `align 8`, `!exclude !{}`; all in one
`@llvm.compiler.used`); `--into-ll <in.ll> -o <out.ll>` adds it to a
module (merging into an existing one-line `@llvm.compiler.used`;
refusing a module that already has `@__mason_meta`). No definitions are
written: the producer's ELF form has none of its own either (the
records talk about the definitions of the object it is added to).

## 4. Equality through two producers (item 2)

`cargo xtask mason producers` links every mortar link step of
`tests/link/odr` and `tests/link/dyn/odr` (43 tests, 57 link steps per
target) on AArch64 and x86-64, each with the test's own line and with
`--odr=strict`, `--odr-check-archives`, `--odr-table=full`,
`--keep-mason-meta` added: 570 links, four times:

- **gcc**: the tests as written (GCC/Clang objects, the test producer's
  container by objcopy).
- **hod-objcopy**: C++ by kiln and C by clang to IR (the step's
  options), objects by hod; the test producer's container by objcopy.
- **hod**: the same objects, the container written into the IR and made
  by hod (H-1).
- **mixed**: GCC/Clang objects; the first, third, ... `meta` step through
  hod (the object then hod's, from kiln's IR), the others by objcopy: one
  unit from each producer in every test with two units, a hod unit
  beside GCC and Clang objects without records, and (k17-archive-*)
  hod units inside an archive.

Checked, per link: **hod against hod-objcopy**, the same end and the
same standard error byte for byte (the objects differ only in who wrote
the container: a difference is the stop condition); **hod against gcc**
and **mixed against gcc**, the same end, the same diagnostics (kind and
files) and the same number of `meta-malformed`; **no output without
`--keep-mason-meta` on its line has a section `.mason.meta`**.

| target | variant | links | hod = hod-objcopy (byte for byte) | hod = gcc | mixed = gcc | explained |
|---|---|---|---|---|---|---|
| aarch64 | the test's line | 57 | 57 | 56 | 56 | 1 (model-f3) |
| aarch64 | `--odr=strict` | 57 | 57 | 56 | 56 | 1 |
| aarch64 | `--odr-check-archives` | 57 | 57 | 56 | 56 | 1 |
| aarch64 | `--odr-table=full` | 57 | 57 | 56 | 56 | 1 |
| aarch64 | `--keep-mason-meta` | 57 | 57 | 56 | 56 | 1 |
| x86_64 | (the same five) | 5 x 57 | all | 56 each | 56 each | 1 each |

278 of the 570 links report at least one diagnostic (16 kinds, among
them `odr-violation`, `odr-type-mismatch`, `odr-declaration-mismatch`,
`odr-archive-shadow`, `odr-vtable-rtti-mismatch`, `odr-contents-mismatch`,
`odr-size-mismatch`, `odr-strong-and-comdat`); all are the same through
hod. **No finding of the stop condition.** The one difference,
**explained to the object**: `odr/model-f3.test` (W3, strong and comdat)
needs a C++14 out-of-line definition `constexpr int A::n;` to be strong;
kiln at `-std=c++14` emits `@_ZN1A1nE = linkonce_odr ... comdat` (clang
22: `@_ZN1A1nE = dso_local constant i32 3`), so hod's a14.o has no
strong copy and W3 has no pair; mortar's answer follows the objects.
That is a kiln finding (§9), recorded as the row's explanation in the
baseline. Outside the comparator, the link tests run as tests with
`--producer hod` (`cargo xtask linktest --producer hod`): 78 pass, 4 fail
(model-f3 on both targets, above; `dyn/odr/o24-silent.test` on both:
its run step prints `1 4` where GCC's objects print `1 1`, because clang
at `-O1 -fPIC` inlines `f` into `fc` (clang's default
`-fno-semantic-interposition`), so libc0's `fc` no longer calls the
interposed `f`: the C compiler's semantics, not a link answer; its
link steps are the same).

## 5. What a code generator puts around the section (item 3)

From the fixtures' `.ll` through hod `a598555f`, both targets (the x86-64
large name only differs). "Now" is after WP-099.

| case | hod writes | meta.md before | mortar before | now (rule) | new or existing |
|---|---|---|---|---|---|
| the container | `E`, align 8, no group, no rela | MT-1 | read; kept | handled: MT-1, MT-6 | existing |
| `@llvm.used` | `RE` | MT-6 (flags not exactly `E`) | warned once, dropped, not read | same: refused as a container by name (`meta-malformed`, MT-6) | existing (MT-6 names it now) |
| comdat | `GE`, group of the comdat holding the section | MT-2, MT-6 | warned per file whatever the election, not read | same; MT-2 now says what two units' groups of one signature mean: neither is a container, no record depends on an election | existing rule, new sentence (MT-2) |
| two globals | one section, both initializers in order | MT-4, MT-10 | both units read and kept | handled: MT-10's framing (a sequence of units) | existing |
| two units of one file disagreeing | one section, two units | MT-4, `odr.md` | `odr-violation` under strict between the two units of one file | handled: each unit is a translation unit (what `-r` makes) | existing |
| pointer initializer | `E` and `.rela.mason.meta` | MT-2 (forbids it), "nothing is reported" | **accepted silently**: read as a container, relocation ignored, kept with the bytes the relocation would fill as zeros | refused as a container by name: MT-2a (kind `Excluded`, not read, not kept, `meta-malformed` "a relocation section applies to it") | **new** (judgement call) |
| no `!exclude` | `A` | MT-6 | copied as an ordinary section, warned; with `--keep-mason-meta` and a unit: refused by name; with the option and no unit: copied, warned | same; MT-32's sentence now says "when the output gets the kept section" | existing behavior, sharpened text (judgement call) |
| large name (x86-64) | `.ldata.mason.meta`, `lE` (AArch64: `E`) | MT-1 (the name) | dropped by `SHF_EXCLUDE`, nothing said | handled: not the container's name, so no container (MT-1; MT-6 says so now); hod never adds `l` to `.mason.meta` itself (`-code-model=large/medium` add nothing) | existing |
| alignment 4 | `E`, align 4 | MT-14 | default: nothing read; strict: error `sh_addralign is 4, not 8`; keep: the unit dropped silently | same | existing (keep's silence flagged, §8) |
| empty | `E`, size 0 | MT-10 | zero units; keep: no section | handled: MT-10 | existing |

None panics; none is read with its records silently ignored except the
one flagged under §8 (keep without strict drops a malformed unit, as
MT-32 says).

## 7. Cost

`cargo xtask mason producers -j 6` (four linktest digest runs of the 43
tests, 2280 mortar links, every C/C++ compile also through kiln or clang
and hod): 2 min 31 s wall, 330 s user + 84 s system, peak resident 320 MB
(the xtask process; `-j 6`, 1-minute load 5 at the start, this host).
The Mason step runs it at `-j 4`. `hod_meta.rs`: 0.3 s. MT-2a adds one pass over a file's
sections in resolution only when the file has a container
(`SectionKind::Meta` rows), so a link without containers pays a loop
over its rows (no read).

## 8. What kiln's hod route and WP-078 need

kiln's hod route (K-1 onward): write the unit exactly as `meta write
--ll` does (one private `[N x i8]` constant, `section ".mason.meta"`,
`align 8`, `!exclude !{}` as the **first** `!exclude`, in
`@llvm.compiler.used`, never `@llvm.used`, never in a comdat, no pointer
in the initializer, never thread-local, no large-data name); anchor rows
only to global definitions (an internal definition has no anchor); and
expect hod to put several such globals in one section (fine by MT-4).
Not shown here: kiln's own records (no kiln writes them yet); a kiln
unit beside a hod-made object of another kiln version (MT-35's minor
versions); hod at `-O1`/`-O2` (kiln uses opt + llc there, never hod).

WP-078 (the verifier's container rules) should check, on a Mason object:
MT-1 exactly (name, `SHT_PROGBITS`, flags `SHF_EXCLUDE` only, align 8,
entsize 0, link/info 0); no `SHF_GNU_RETAIN`, `SHF_GROUP`,
`SHF_X86_64_LARGE`; no relocation section applying to it (MT-2a); no
`.mason.meta` in an output without `--keep-mason-meta`, and with it a
non-allocated one whose bytes are the live units in `FileId` order
(MT-32); a section of a near name (`.ldata.mason.meta`) is a finding
worth a note (a producer that meant a container).

Open judgement calls for the supervisor: MT-2a itself (refuse a
relocated container as one, rather than an error); MT-32's "when the
output gets the kept section"; and whether `--keep-mason-meta` without
`--odr=strict` should warn when it drops a malformed unit (proposed
text in MT-32's list).

## 9. Findings

- **hod**: none. Everything 9.7.4 promises was measured: flags exactly
  `E`, align 8, no group, no rela, the bytes the initializer's, objects
  deterministic (24 objects made twice, same bytes), the extra flags of
  the brief's list exactly as stated.
- **kiln** (for the supervisor to route; kiln is closed to feature work,
  this is a correctness defect): kiln `-std=c++14` makes the out-of-line
  definition of a `static constexpr` data member `linkonce_odr` in a
  comdat; in C++14 that member is not inline and the out-of-line
  declaration is its one strong definition (clang 22 and GCC emit a
  strong symbol). Smallest input: `struct A { static constexpr int n =
  3; }; constexpr int A::n; const int* p = &A::n;` with `kiln++
  -std=c++14 -S -emit-llvm`: expected `@_ZN1A1nE = dso_local constant
  i32 3`, actual `@_ZN1A1nE = linkonce_odr dso_local constant i32 3,
  comdat`. Effect: two C++14 translation units each with the
  out-of-line definition link without a duplicate-symbol error, and W3
  cannot see a C++14/C++17 mix.

## 10. Not verified

- x86-64 numbers on an x86-64 host: the comparator runs only where hod
  is built (here, AArch64); the hosted x86-64 lane runs `hod_meta.rs` on
  the committed objects.
- i386 (no Mason producer targets it).
- `--odr-table=full` with a shared-object output (M4); the corpus's
  dynamic cases are executables.
- `-r` of hod objects (MT-30, M4).
