### 5.5.1 The read cost of the first version, and the ruling

Experiment 7 could not see it. Its workload is protoc: one top-level
object and two archives, and archive members were never read around
their containers (E2). The first version's extra reads fell only on
top-level objects, so protoc had one object paying them. That is three
reads in a 180 ms link, below the ~2 ms this host can resolve. The cost
grows with the number of top-level objects, so it was measured on links
made of many of them: `synthetic-objects` (1,009 objects over 64 KiB)
and 5,000 small objects of 1,248 B each (one function and one global,
`gcc -O0`). Every object is container-free. Release builds: main
(8f73db0, the merge-base) against this branch. Reads and bytes were
counted from the input files' descriptors by an `LD_PRELOAD` counter of
`open`/`read`/`pread64` (scripts in
`/Volumes/AgentWork/mortar-helper/.build/wp071-reads/`). The counts are
the same at `--threads=1` and at the default thread count, and every
pair of outputs is byte-identical.

| workload | files opened | reads: main → first version → as ruled | per file | bytes read: main → first version → as ruled |
|---|---|---|---|---|
| `synthetic-objects` | 1,009 | 4,072 → 7,093 → **4,072** | 4.0 → 7.0 → **4.0** | 87,919,030 → 88,814,774 → **87,919,030** |

## 6. Findings for the supervisor

### 6.1 MT-42's exceptions (accepted 2026-11-15)

Accepted as **named** exceptions; the text below is in MT-42 (each
exception names the test that pins it), and `spec/input.md` §11.1's
small-file row says members are not read around the container, and why.
The text as proposed:

> Three exceptions, each named and counted by T-MT-42: **(E1) the head.**
> The first 64 bytes of every file are read before its class is known;
> no container byte past the file's first 64 bytes is read (an ELF32
> object whose container starts before byte 64, as GNU as writes it on
> i386 with an empty `.text`, has up to 12 container bytes read).
> **(E2) archive members.** The bytes of a regular archive's members are
> read before their section headers are known: a member of at most
> 64 KiB is read whole and stays resident with its container; the
> chain's windows and a larger member's head and tail reads may cover
> container bytes, which are not kept; a container of a member larger
> than 64 KiB is never resident. With the containers wanted, those bytes
> may be read a second time. **(E3) whole-file reads.** A file made fully
> resident because descriptors ran out (`spec/input.md` §11.4) and every
> file under the resident policy are read whole, containers included.

And in `spec/input.md` §11.1 the row "the same, of at most 64 KiB | the
whole file (member); ..." becomes "... such a file (not an archive
member: `spec/meta.md` MT-42, E2) is read around its container ...".

Tests that pin them (`crates/mortar_input/tests/t_mt_42.rs`): E1
`elf32_head_is_the_named_exception` (removed with E1 under the read rule
of §5.5); E2
`small_member_container_is_the_archive_exception` (the small member's
container read and resident in full, the large member's not resident)
and `member_container_is_not_resident`; E3
`whole_file_paths_are_the_named_exception` (8 large objects: with
`max_open` 2, the 6 made full read their containers whole; under the
resident policy all 8). Measured extent of E2 on protoc: §5.3 (11.4 % of
the container bytes read, 2.7 % resident). The alternative for E2 (read
each member's section header table before its bytes) costs one or more
reads per member in every archive, Mason or not; not done, as it would
make every link pay.

### 6.3 Spec questions met by the reader (conservative choice taken)

- **MT-35 / MT-10, fixed offsets across majors.** To skip a unit of
  another major the reader needs `unit_size` at offset 8 and the magic at
  0; MT-35 says the unit is skipped but no rule says a later major keeps
  those offsets. Proposed MT-35 sentence: "Every major keeps the magic
  at offset 0, `major` at 4 and `unit_size` at 8, so that any reader can
  skip a unit it does not read."
- **MT-14, what is skipped.** MT-14 says the units around a malformed
  one are read; after a bad magic, a truncated header or an unusable
  `unit_size` nothing says where the next unit starts. The reader reports
  one `meta-malformed` and stops reading that section (other sections of
  the file are read). Proposed: "... the units around it are read when
  its `unit_size` is usable; a bad magic or `unit_size` ends the
  section."
- **MT-11 vs MT-14.** MT-11 says a kind appears at most once and blocks
  are sorted by kind; MT-14's list of malformations does not name it. The
  reader treats both as malformed (rule MT-11). Proposed: add "blocks not
  strictly increasing by kind" to MT-14's list.
- **MT-12, the string table.** Offset 0 is the empty string, so the
  reader requires a non-empty table to start with a NUL, and a table that
  overlaps the header or runs past the unit is malformed. MT-14 names
  neither; proposed: add both to MT-14's list.
- **MT-13, keys of named rows.** The reader does not check that a named
  row's key is FNV-1a 64 of its name: MT-13 makes every grouping reader
  confirm the name, so a wrong key can only make a row miss its group
  (no false positive). A within-file collision of anchored keys is O-4's
  "ambiguous" (`anchor.rs`); across files MT-13 covers it. No change
  proposed.
- **MT-2 (no group, no relocations)** is checked by no component of
  mortar. Measured on an aarch64 object: a `.mason.meta` with
  `SHF_GROUP` (GNU as `"eG"`) fails MT-6's flags test, takes the
  `SHF_EXCLUDE` row (dropped) and gives one `meta-malformed` per file;
  a container with a `.rela.mason.meta` is a container, its relocation
  section is consumed, nothing is applied or reported, and the program
  is right. MT-2 now says so, and names WP-078 (the verifier's container
  rules) as where it is checked on Mason objects.

All of §6.3 was accepted 2026-11-15 and is applied to `spec/meta.md`
(MT-2, MT-13, MT-14, MT-35).

### 6.4 Other

- `spec/odr.md` O-22 "~50 ns a row" measured 80-105 ns (read, parse and
  sort on one thread, §5.4).
- binutils 2.44 `objcopy --add-section` gives `SHF_WRITE` unless the
  flags say `readonly`, and ignores `--set-section-alignment` on a section
  it adds in the same run: the producer's `--into` runs objcopy twice
  (`xtask/src/meta.rs` `add_to`). GNU as on i386 does not 8-align the
