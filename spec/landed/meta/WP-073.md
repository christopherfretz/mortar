### 2.1 What other packages must know

- The diagnostic key of a record finding (`spec/odr.md` §9.1): phase 40,
  the `FileId` of the first file of the second class, then a sequence
  number whose bits 44 and up carry a tag (`records.rs` `mod tag` :51:
  1 ENFORCE, 2 kind 5, 3 kind 3, 4 kind 2, 5 internal, 6 isa, 7 vtable,
  8 meta; the W checks keep tag 0). Keys are unique across kinds; a
  package adding a phase-40 finding takes a new tag.
- `StoreConfig.containers` is `mortar_odr::reads_containers(odr)`: true
  only under `--odr=strict`. A package that moves a record check to the
  default mode (O-46) moves this switch with it, and pays the read cost
  of §5.
- The first note of every record finding names each unit's `source` and
  `producer` summary values (`unit_note`); a producer that leaves them
  out gets the file name only.
- `--odr-stats` gained fields (§2); `crates/mortar/tests/odr.rs` parses
  the line.

## 4. Rulings applied

1. O-41: implemented as written, then narrowed for two legal cases (§6.1).
2. Cross-scheme kind 3 size, alignment and flags: a separate strict-only

## 5. Cost (O-42, O-45)

gone): protoc's link (`cxx-medium-static`) with a container in each of
its 125 units at experiment 7's row counts, 154,819 rows (kind 1 750,
kind 2 51,741, kind 3 38,125, kind 5 64,203), 8,956,440 container bytes;

### 5.3 The O-45 question

O-45's 3 % binds the checks O-47 lists as on; every record check is
strict-only, so the budget does not bind them today. It binds the day
O-46 moves one to the default. The per-kind numbers (an instrumented
build that enables one kind at a time; 11 rounds; p1):

| enabled | 1 thread | default threads |
|---|---|---|
| off | 151.9 ms | 88.7 ms |
| strict, no record check (W3, W4 only; containers read and parsed) | 153.9 | 88.5 |
| kind 2 | 163.6 | 94.5 |
| kind 3 | 161.6 | 93.1 |
| kind 5 | 162.9 | 93.9 |
| ENFORCE/isa | 161.1 | 94.0 |
| vtable | 159.7 | 93.0 |
| all | 174.4 | 99.5 |

The read and parse of the containers costs about 5.8 ms (1 thread);
each kind alone costs its share of the grouping plus a fixed sort. All
record checks: +20.5 ms over "no record check" at 1 thread (13.5 % of
the link), +11 ms (12 %) at the default count. **Not within 3 %.**

Where the time goes (1 thread, after the integer grouping): `sorted`
5 ms, `groups` 1.6 ms, the comparisons 5.1 ms, the COMDAT checks 2.2 ms,
the W checks 4.3 ms, the rest reading, decoding and anchoring the rows.
The integer grouping (one word per entry instead of a comparison on
names) took the sort from 9.4 to 6.7 ms.

Cheaper alternatives, measured or argued:

- done: group by integers; names split only a colliding run (`groups`).
- a radix sort on the 64-bit key, or a hash partition by key into
  per-thread buckets (no global sort: rows of one key meet in one
  bucket); expected to halve `sorted` at the scaled size.
- a smaller entry: the name (16 bytes) recomputed from the anchor or the
  row on a collision only; 48 to 32 bytes a row, a third off the peak.
- read only the kinds a switch wants (a unit's blocks are independent):
  a mode with only kind 2 would skip kinds 3 and 5's decoding.
- move the read and decode into the store's parallel load (it is now a
  pass after resolution).

None of these reaches 3 % alone at 1 thread on this evidence; the
default thread count is closer. **Ruled 2026-11-15:** the record checks
stay strict-only and no budget is set for strict now (the order of work
puts speed last); O-45's 3 % stands for anything that moves to on by
default, so WP-074 cannot move a kind without first bringing its cost
under O-45 or bringing the numbers back; the cheaper layouts above are
recorded as the candidates.

### 5.4 The cost of a small object

WP-071 suspected about 0.3 µs a small object for decoding section
headers when containers are wanted. Measured on the 5,000 small objects
(`--time-phases`, 41 rounds, 1 thread, one binary): `--odr=off` total
64.8 ms (input 42.3), strict 63.9 ms (input 41.9). The difference is
0.1-0.2 µs a small object, and it is the other way round: the path
with containers *unwanted* (off and the default; WP-071's
`stage_small_without_containers`) is the slower one. An earlier run of
31 rounds through the bench script gave 0.34 µs, the 61-round run 0.26
µs (default 70.4 ms against strict 69.1 ms). The cost is WP-071's, the
same in base and branch; this package does not change it. A follow-up
for `mortar_input` if it matters at large small-object counts.

## 6. Spec findings and changes (all applied, accepted 2026-11-15)

### 6.1 O-41: unanchored rows (ruling 1)

Comparing every unanchored row, as written, reports two legal cases of
`records-legal.test`: N12 (kind 2 and kind 5 rows of a function each
unit names differently: "<unnamed entity, key 0x25ca50d29b4e9f0a>
violates..." and "_Z7n12_oldv is declared with a type that does not
match") and N13 (a local `_ZL6helperv`). The narrow reading is kept for
those cases only: an unanchored kind 2 row is compared only if it is
`INLINED_ONLY`, an unanchored kind 5 row never. Why: a row without an
anchor has no symbol to tie its key to an entity of this link; its key
is equal across units by the entity's name, and internal or renamed
entities share names without being one entity. Applied to O-41's strict
bullet: "strict compares the unanchored kind 2 rows flagged `INLINED_ONLY`
(their entity has no symbol by construction); other unanchored rows are
counted, not compared (§3 N12, N13)." Test: `unanchored_rows`.

### 6.5 O-47: the meta findings' row contradicts O-42

O-47's row for `meta-malformed` and `meta-version` reads "**on**
(warning)". In the default mode no container byte is read (MT-42,
O-42), so a malformed container is never found below strict. Applied:
the row reads "strict (error); not reported in other modes, which read
no container (O-42)", and `crates/mortar_odr/src/register.rs`'s mirror
row is `Status::Strict` (its test checks the mode table). One nuance
the proposal missed: `meta-malformed` also covers a section named
`.mason.meta` that is not a container (MT-6), which resolution reports
as a warning in every mode, `--odr=off` included
(`crates/mortar_resolve/src/tables.rs`, `What::MetaNotContainer`); it
reads no container, so O-42 does not touch it. It gets a sentence under
the O-47 table rather than a row (a row would renumber the register).

Every sentence changed to agree:
- `spec/odr.md` O-41, the `--odr=strict` bullet: the meta findings are
  errors and reported only under strict (and the O-41 text of §6.1).
- `spec/odr.md` O-47: the row, and the sentence under the table (MT-6).

## 7. Assumptions about kiln (what its future units could break)

- NOEXCEPT-only (O-16): a kind 5 row whose type differs only in
  noexcept is a warning, found as equal type hashes with a different
  flag. Kiln must hash function types without noexcept and set the
  flag, or every such case becomes an error.
- Kind 3 key: the FNV-1a of the `<type>` encoding, independent of the
  scheme (ruling 2 rests on it). A scheme that keys by something else
  breaks the cross-scheme check.
- `INLINED_ONLY` set exactly for entities with no symbol (§6.1); a row
  of an internal entity without the flag and without an anchor is
  counted, not compared.
- One row per entity per unit; contradictions are set aside (§6.4).
- `source` and `producer` summary rows present (the notes).
- Kind 2 classes: rows of one key in different classes are never
  compared; a class number that drifts between kiln versions splits
  groups silently.
- The hash-equality rows of §3 (N2, N10, N16, N18, N19) are the
  producer's to get right; the linker trusts equal hashes.

- `odr_records.rs` runs on aarch64 only (the link tests run on all

- Kind 3 rows of experiment 7 are a proxy (WP-071's DWARF names
  averaged 107 bytes; the generator's encodings are shorter).
- The bench lane (`cargo xtask bench`) was not used; the timings are
  the interleaved scripts of §5 on a shared host (load 1-2).
