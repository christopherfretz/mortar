## 7. For kiln

1. `[[noreturn]]` hashes apart from `[[gnu::noreturn]]` and
   `__attribute__((noreturn))`; kiln's table says equal. Reproducer:
   the same inline function with each spelling in two units
   (`wp199/k3/n1.cc` against `n3.cc`; `n2`, both spellings, equals
   `n3`).
2. USES_INTERNAL on a closure type that is one entity in every unit:
   a lambda in an inline function, its closure type nested in a
   function type or a template argument (`run<lambda>`, `Arr<int
   (*)(Wrap<lambda>&&), 1>::operator[]`, flags 0x13). Reproducer
   (`wp199/vis/h3.h`, `u3.cc` compiled twice with `-DUNIT=fa`/`fb`):
   ```
   template <class V> struct Wrap { V v; };
   template <class T, int N> struct Arr { T buf[N];
     __attribute__((noinline)) const T& operator[](int i) const { return buf[i]; } };
   template <class V> __attribute__((noinline)) int disp(Wrap<V>&& w) { return w.v(); }
   template <class V> __attribute__((noinline)) int run(V v) {
     constexpr Arr<int (*)(Wrap<V>&&), 1> table = {{&disp<V>}};
     return table[0](Wrap<V>{v}); }
   __attribute__((noinline)) inline int g() { return run([] { return 1; }); }
   ```
   Two odr-internal-reference warnings under strict; the program runs
   as lld's link. In libc++: `std::visit`'s `__farray::operator[]`
   and `__base::__at` (0x113), the 6 internal-user warnings of §5.2.
3. **align-order** (new in 3b77b13c7; d854b23bc does not, and `-O2`
   only hides it by inlining): an inline definition's rows differ when
   an aligned type is declared before it in one unit only. Reproducer:
   ```
   // h.h
   inline void fr() {}
   // a.cc
   struct alignas(8) S { long long a; };
   #include "h.h"
   void ua() { fr(); }
   // m.cc
   #include "h.h"
   void um() { fr(); }
   int main() {}
   ```
   `kiln++ -std=c++20 -O0 -fmason-metadata -c` each; mortar
   `--odr=strict` reports `_Z2frv violates the one-definition rule`.
   `__attribute__((__aligned__(8)))` on a member does the same, and so
   does `#include <stddef.h>` (`max_align_t`); a typedef, an unaligned
   struct, `<stdint.h>`, `<limits.h>` do not, nor does the aligned type
   declared after `fr`.
No hod defect was found.

## 8. What mortar's reader lacks for `.d4` (the reader package's list)

Measured on this head; nothing built.
1. **Flag 16 is read today**: `crates/mortar_odr/src/records.rs`
   `kind2()` reports odr-internal-reference (O-16), a strict-only
   warning, when two or more files' rows of a key carry the flag; across
   schemes; SYSTEM rows are not exempt. Default and warn modes say
   nothing.
2. **Unknown flag bits**: bits 9-14 of a kind 2 row are ignored
   silently; `spec/meta.md` says nothing of a reader meeting a reserved
   bit set (MT-25 covers kinds and versions only). A rule is needed
   (ignore and count, or `meta-malformed`).
3. **Q5 (odr-internal-reference) needs**: (a) a SYSTEM exemption, or a
   note class: all 6 warnings measured are SYSTEM rows of libc++; (b)
   kiln's §7 item 2 fixed; (c) the note's wording: it says "defined
   differently" also when the hashes are equal; (d) corpus counts once
   (a) and (b) land.
4. **`unit.system`: yes.** The case is k14impl: kind 5 rows carry no
   SYSTEM bit, so mortar cannot tell that `iostream.cpp`'s definition of
   `cout` belongs to the implementation's own unit (and the c++17
   `basic_stringbuf::swap` kind 5 warnings likewise). A unit-level key
   decides it for every kind; per-row SYSTEM flags cannot, for kind 5.
5. **`.d3` against `.d4` in one link** (a `.d3` unit made by patching
   the scheme string): no kind 2 finding, `schemes 2, pairs not compared
   2`, as `kiln-k2-schemes` says. The K13 flag check is inside the
   per-scheme comparison, so it is not done across schemes either;
   being flag-only, it could be, as O-11 does for kind 3.
