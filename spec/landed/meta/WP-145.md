## 4. The note texts

Exactly as `spec/odr.md` §9.1 now says. When kind 3 compared layouts in
one scheme, both first rows have `details` and both entries read, the
sizes note (`a.o: size 8, alignment 4; b.o: ...` or `the layouts differ
(members, offsets, bases or vtable) with the same size N and alignment
M`) is replaced by the first difference; a shape-kind note at equal sizes
stays and the first difference follows it. Otherwise (one row only,
neither, version above 1, a malformed entry, a definition-hash or
cross-scheme finding) the notes are unchanged byte for byte.

Items: `member 'y' (i) at offset 8`; `member 'y' (i) at offset 70 bits,
bit-field of 3 bits`; `unnamed member (i) ...`; `base 1B at offset 0`
(`(virtual)`); `vptr at offset 0`; `vtable slot 2: _ZN1S1gEv`;
`enumerator 'B' = 1` (hex when bit 63 is set); `underlying type j`.

| case | note |
|---|---|
| equal | `the layout details are equal: the difference is in something kind 4 does not describe` |
| one entry a prefix of the other | `D in a.o only`, `, and N more items` |
| same identity | `D(A) in a.o; D'(B) in b.o` |
| identity in one entry only | `D in a.o only` / `D in b.o only` |
| neither identity in the other | `D(A) in a.o; D(B) in b.o` |
| both in the other | `the items stand in a different order: D(A) in a.o; D(B) in b.o` |

## 5. The malformed-block rules

Applied when an entry is read (only on a finding), as MT-14's:
`details` not a multiple of 8; the entry header past the body; `offset +
8 + 24 × count` past the body (64-bit arithmetic); a name or type string
of an item of a known kind past the string table or without NUL;
`details` in a unit with no kind 4 block. The result is `meta-malformed`
(error, strict only) at the file's `.mason.meta`, unit offset, reason
`unit at offset U: kind 4 block at offset K: entry at offset E: <fault>`,
once per (file, section, unit, entry) however many findings read it; the
finding itself stays and keeps its sizes note. Not malformed: a set
`reserved`, unknown item kinds (skipped, strings unchecked), flag bits
6-31, a block version above 1 (skipped, MT-25), overlapping, shared,
gapped or out-of-order entries, `count` 0.

## 6. Cost (MT-42, O-42)

The workload: WP-073's protoc link (`cxx-medium-static`). WP-073's
objects were gone, so they were rebuilt: every member of `libprotoc.a`
and `libprotobuf.a` (167 members) gets a container with kind 1 rows,
kind 2 rows anchored to up to 400 of its defined globals, and 305 kind 3
rows drawn from a pool of 2,000 consistent classes of 4-11 members each
(WP-073's per-unit count). Two variants of the same rows: `nok4`
(default level) and `k4` (`level detail`, every kind 3 row with an
entry). There are no findings, so kind 4 must be read 0 times.

Bytes (`--odr-stats`, identical for base and branch):

| objects | strict | default | off | layout details read |
|---|---|---|---|---|
| nok4 | 4,184,464 | 0 | 0 | 0 |
| k4 | 11,281,256 | 0 | 0 | 0 |

The branch reads exactly the base's bytes in every mode. The extra 7.1 MB
under strict with kind 4 present is the container that strict already
reads whole (MT-42, WP-073); it is the base's cost too, not this
package's. Kind 4's entries are parsed only on a finding.

Time: 1 thread, CPU time (user + system) of the link, 21 interleaved
rounds, median. The host's load was 12; wall clock at that load was too
noisy to use (11 rounds gave `off` slower than strict).

| objects, mode | base | branch |
|---|---|---|
| nok4, strict | 233.4 ms | 232.5 ms |
| nok4, default | 218.2 ms | 208.4 ms |
| nok4, off | 206.7 ms | 202.5 ms |
| k4, strict | 241.8 ms | 234.4 ms |
| k4, default | 220.5 ms | 205.0 ms |
| k4, off | 215.4 ms | 208.0 ms |

Wall clock at the default thread count, 11 rounds: strict 163.4 → 154.4
ms (nok4) and 174.2 → 165.8 ms (k4); default 157.8 → 145.0 and 154.8 →

findings costs the same on the branch as on the base. Every difference
is within noise and has no code cause: with no finding, the branch's

note (one entry read per side of each layout finding) was not timed.

## 8. For kiln to confirm (O-19, the lenient reader)

1. Entries may be in any order, with gaps, overlapping, and shared by
   rows.
2. `count` 0 is legal; `count` has no maximum but the block.
3. The block's `row_size` and `row_count` are 0 and unused.
4. Unknown flag bits, and `BITFIELD`/`VIRTUAL` on other kinds, are
   ignored (still compared).
5. A block version above 1 is skipped (O-19 does not say later versions
   only append).
6. Validation happens only when an entry is read; an unread malformed
   entry is never reported.
7. Open: is an enumerator's `value` signed? Printed in hex when bit 63
   is set until kiln says.
8. The item order is O-18's hash order (bases, members, vptr, slots;
   underlying type, enumerators): the vptr item follows the members,
   although it sits at offset 0 in memory.

## 9. What was not verified

- No kiln-produced kind 4: all kind 4 here is the test producer's and
  the writer's.
- The cost workload's containers are synthetic (§6); its link has no
  findings, so the lazy read of kind 4 is measured only as "0 entries
  read", and the cost per entry read was not timed.
- The rendering of hex enumerator values is a placeholder for kiln's
  answer.
