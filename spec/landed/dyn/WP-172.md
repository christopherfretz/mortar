# WP-172: a shared object mentioned again inside a linker script takes its script entry's state

The M2 refusal `unsupported feature: DT_NEEDED order of a shared object
mentioned again inside a linker script` (`What::NeededOrderUnknown`,
`spec/dyn.md` D-19a) is withdrawn. Debian's driver lines meet it with
the system's own scripts (`libgcc_s.so`, glibc's `libm.so` and
`libc.so`) whenever a library is named again with `--as-needed` changed
between, e.g. `g++ -shared plain.o -lgcc_s -Wl,--no-as-needed`.
Measured against GNU ld 2.44, lld 19.1.7 and mold 2.37.1 on AArch64
(native) and x86-64 (qemu): the four linkers' lists and runs are
identical on both. i386 not measured (its dynamic output is M4).

## 1. The rule and where the state is kept

D-19a is unchanged; what changed is that its input is now known. A
mention again inside a script (`OpenedKind::SharedNotLoaded`, `Origin::Input
{entry}`) has no plan row of its own, so the walk now records on each
`ScriptEntry` the as-needed state in force at that entry (the state
where its script was named, `AS_NEEDED(...)` forcing it on,
`--push-state`/`--pop-state` applied) and its group ordinal:

- `mortar_input::walk::ScriptEntry` and `mortar_core::inputs::ScriptEntry`
  gain `as_needed: bool` and `group: Option<GroupOrdinal>`
  (`spec/input.md` §10.3, the `origin` column). The walk pushes every
  entry through `push_entry` with the `MState` in force and keeps the
  entry's `GroupKey` in a side vector; `finish` maps it to the ordinal
  (group ordinals are assigned lazily, so this is done once at the end).
  A nested script's entries are in the group of the entry that named
  the script; an `INPUT` entry beside a `GROUP` in one script is in none.
- `mortar_resolve::tables::shared_link` reads the entry's state and group
  for a `SharedNotLoaded` mention; `MentionGroup::Unknown`, the merged
  `as_needed` inference, the heuristic group search and the problem arm
  are removed. `SharedMention.as_needed` is a plain `bool`.
  `shared::needed_order` keeps a mention when
  `!m.as_needed || by_object || by_shared` (its `unknown` set and the
  `Reasons.any` field are gone).

Cost: a `bool` and an `Option<u32>` per script entry (a script has a
handful), and one `Option<GroupKey>` per entry in the walk, dropped with
it. A static link has no shared object: `shared_link` returns before any
of this, and the static path is unchanged (`cargo xtask static-identical`
in the gate). A link without a mention again is unchanged (the dynamic
lane's `DT_NEEDED` expectations unchanged).

Observations:

- On every line GNU ld links, mortar writes GNU ld's list. D-19a as
  written predicted GNU ld everywhere: **no cell was brought to the
  supervisor.**
- The base refused six cells (`s_twice_off`, `s_then_plain`,
  `nested_group`, `nested_group_asn`, `nested_group_none`,
  `gxx_shared_gccs`) and guessed `input_then_group` wrong (`na nb nx nc`:
  it took the group of the script's other entries). It now gives the
  fallback (`na nx nb nc`), lld's and mold's list; GNU ld refuses that
  line (undefined `f_nx`: it does not search an `INPUT` entry beside a
  `GROUP` again), as it does `before_asn_ref_late` and
  `nested_group_none`.
- lld writes each soname at its first mention; mold drops a library
  whose first mention is as-needed and unreferenced, even when a later
  one is plain (W9), and cannot read `AS_NEEDED` inside a nested script
  (`library not found: AS_NEEDED`).
- Where the order changes the program (shown by runs, `dup-run*`):
  `dup_run`: GNU ld and mortar `dy nx` bind libdy's `who_dup`, lld and
  mold `nx dy` bind the other: the program prints a different name.
  `dup_run_on`, `dup_run_asn`: GNU ld writes only `dy` (it decides
  neededness by binding); mortar writes `dy nx` (D-11 by first mention,
  the documented superset of `needed-order-dup-def` line 1): the same
  binding and output line as GNU ld, plus the other library's
  constructor.
- No mislink found.
