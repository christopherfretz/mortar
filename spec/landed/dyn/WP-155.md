# WP-155: an undefined weak key reached by branches (D-25's call-only cell)

WP-141's finding F1. Before this package, D-25 made an undefined weak key
`Weak0` in `Exec` and `Pie` when it had no GOT use and no absolute word in
a writable place. So a key reached only by calls had no `.dynsym` entry:
on AArch64 the call was skipped (`bl .+4`), on x86-64 it called 0. This
held whatever a later library or `LD_PRELOAD` defined.

GNU ld and lld write a `WEAK UND` entry and a `JUMP_SLOT` for such a key.
mortar now does the same.

The supervisor's ruling (A), taken after the measurement below showed GNU
ld and lld disagreeing in the mixed cell: in `Exec`, a weak undefined key
with a branch use is `WeakDyn` for its branches, whether or not it also
has unfillable uses. The unfillable uses keep today's value (0). In `Pie`,
an unfillable use is still refused by name.

`-z nodynamic-undefined-weak`:
- GNU ld x86-64 honours it, and the result is mold's form.
- GNU ld AArch64 ignores it with a warning.
- lld 19 warns that it does not know it.
- mortar still refuses it by name, as it does `-z dynamic-undefined-weak`.

`-z dynamic-undefined-weak`:
- GNU ld and lld import the key.
- mold refuses x86-64 `-no-pie` (an `_ITM_*` copy).

## 2. The rule (dyn.md D-25, as written)

- "the key is **`WeakDyn`** in `Exec` and `Pie` when it has some GOT use,
  absolute word in a writable place or branch, and no unfillable use (a
  branch alone included, WP-155: GNU ld and lld)."
- "in `Exec`, a key with a branch and an unfillable use but neither a GOT
  use nor an absolute word in a writable place is **`WeakDyn` for its
  branches** (WP-155, the supervisor's ruling (A)): it is in `.dynsym`
  (`WEAK UND`) and every branch goes through a PLT entry with a
  `JUMP_SLOT`, as above; each unfillable use keeps `Weak0`'s value,
  written by the architecture's `weak0` table (a64 §7, x64 X-16: `S = 0`,
  an AArch64 `PC` instruction `S = P`), and demands nothing.
  `target_kind` stays the key's (`WeakDyn`); only the patching of such a
  use is per relocation: the architecture's scan and apply see `Weak0`
  for a relocation at an allocated place whose class by the table above
  is unfillable (`mortar_arch::weak_use_kind`; fill knows the writable
  place from the output section, and a caller that does not say is taken
  as writable). `class_outcome`'s cells (D-43, D-44) are unchanged."
- `Weak0` remains in these cases:
  - in `Exec`, when the key has an unfillable use and a GOT use or an
    absolute word in a writable place;
  - in `Exec`, when its only uses are unfillable;
  - in both kinds, when it has no use at all.
- D-25 also gains the branch-cell table and reasons (1)-(3) of the
  ruling. The GOT+unfillable cell stays `Weak0`, with the references'
  disagreement written out.

Every spec edit (no reflow):
- `dyn.md` D-25: the opening sentence now says "no definition in any

- `dyn.md` §13.1: the row "reached by branches only" is now mortar

## 3. Implementation

- `mortar_scan/src/weak.rs`, `WeakUses::verdict`: a branch makes the key
  `WeakDyn` like a GOT use. In `Exec`, `Some(_)` unfillable together with
  a branch and no GOT/abs word also gives `WeakDyn`.
- `mortar_arch/src/class.rs`: `weak_use_kind(output, kind, alloc, class)
  -> TargetKind`.
  - It returns `Weak0` for an `Exec` relocation at an allocated place
    whose D-25 class is `Unfillable` against a `WeakDyn` key.
  - Otherwise it returns `kind`.
  - The caller passes `None` for a TLS class: that key is refused, so the
    arch-level refusal stays.
  - `class_outcome` is untouched.
- `mortar_arch/src/cx.rs`: `SectionOut.writable: Option<bool>` and
  `with_writable`.
- `mortar_a64/src/apply.rs` and `mortar_x64/src/apply.rs`: `scan` and
  `apply` take the relocation's kind through `weak_use_kind`. In `apply`,
  `sym.kind` is rebound, so the value is `Weak0`'s.
- Writable-place plumbing:
  - `mortar_image/src/reloc.rs`: fill sets `writable` from
    `section_writable`.
  - `mortar/src/sites.rs`: the erratum probe sets it from the output
    section's flags.
- Dynamic records follow automatically, because `dynrel::roles` and
  `zeroed_place` re-run `arch.scan`.
- i386 is untouched: a dynamic i386 output is refused.

## 6. The verifier (for the VERIFIER package)

- It accepts a branch-only key's `JUMP_SLOT` import, from mortar and from
  the references: `weak-branch-call` and `weak-branch-gc` pass under it
  for GNU ld, lld and mortar.
- It reports P-D9 view 3 ("this use still sees the absent definition") on
  the unfillable use beside a branch's `JUMP_SLOT`, for mortar, lld and
  GNU ld AArch64 (`weak-branch-split`).
- What it must change:
  1. Accept, in `Exec`, a `WeakDyn` key whose branches go through a
     `JUMP_SLOT` while its unfillable uses hold `Weak0`'s value (0, or
     `S = P` for an AArch64 `PC` instruction). This is D-25's split key.
     It applies to mortar's and lld's outputs, and to GNU ld's AArch64
     output.
  2. Accept GNU ld x86-64's output for the same input: no entry, the call
     to 0. This is §13.1's named difference.
  3. Keep reporting a GOT use beside an unfillable use (W12) as today.
- After that, lift the three `xfail`s of `weak-branch-split`.

  beside an unfillable use: no compiler emits one against a weak key.

  hosted run.
