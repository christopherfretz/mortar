# WP-125 (part 1): the version-script and dynamic-list parser

The parser of `spec/script.md` §9 (record `spec/landed/dyn/WP-110.md`
§D row WP-125, its parser half): the bytes of `--version-script` and
`--dynamic-list` files into WP-116's AST (`crates/mortar_script/src/ast.rs`,
unchanged), with spans, and the diagnostic kind `version-script-syntax`.
No resolve, no synth, no option: `--version-script` and `--dynamic-list`
stay refused on the command line; the rest of WP-125 follows WP-123. No
link changes: the parser is not called by any link.

Every refusal is `version-script-syntax` (an error, placed at file, line
and column), with a note where a reference reads the text otherwise:
an empty file; a stray or missing `;`; an empty entry; a quoted or
malformed version name (§9.1's byte set); a node defined twice; a parent
not defined earlier; an anonymous node with any other node; an unknown or
unquoted `extern` language; a nested `extern`; a label inside `extern`;
`//`; `/*` or `//` inside a name; `""`; control bytes and NUL; an
unterminated comment or string; in a dynamic list a label, a name before
`{`, or a second block. `extern "C++"` entries are kept with
`Language::Cxx`: their refusal (until the demangler) is the consumer's.

## 3. The 213 scripts (`tests/version_corpus.rs`)

The test reads the directory as `cases.py` does (`scripts_author.txt`,
`scripts_rev.py`, `globs.out` with `gNN.map`, the `S` dicts of `dups.py`,
`expdyn.py`, `atat.py`, each `.symver` case twice for `-E`), asserts the
213 ids are `gnuref.json`'s, and that each parses to the tree
`model_a.py`'s `parse` reads (generated by running the model over the
cases; the table is in the test). **All 213 parse**: none is a syntax
error under §9.1. Re-linked here with the three references (with
`--undefined-version` for lld), their disagreements on syntax are:

- `local:` before `global:` (A-S8, A-L1, A-L2, A-E6, R-r11, R-r32, R-r47,
  R-s10): GNU ld `syntax error in VERSION script`; lld, mold and mortar
  accept (§9.1; rule 8's family, `compare.py`'s eight).
- Several parents (R-r27, `V3 { … } V2 V1;`): GNU ld and mortar accept;
  lld ``; expected, but got V1``, mold refuses the line.
- Globs (G-g05, g10, g11, g35-g39, g41: an unterminated `[`, a final `\`,
  a reversed range; G-g26 `[a-]oo` mold only): lld ``invalid glob
  pattern``, mold ``invalid version pattern``; GNU ld accepts, and so
  does the parser, which keeps the raw text (§9.1: their meaning is
  resolve §9.7's, where mortar sides with GNU ld).

GNU ld's other refusals among the 213 (`duplicate expression`: A-S12,
S13, D2-D4, E5, R-r05, r08, r29, r40, r46, D-d01-d03, d05, d08-d10, d14,
d17 over this object) are resolve §9.7's `duplicate-version-pattern`, the
later half's.

## 4. Hostile input (`tests/version_hostile.rs`)

Seeds: the 213 scripts (each file alone, the `-E` repeats once) and two
dynamic-list/extern shapes. Every prefix of each; 20000 mutations
(xorshift64*, seed `0x5eed_0125_7e75_10a5`: byte changes, deletions,
inserted fragments that open strings, comments and blocks, splices);
every byte alone, as an entry, as a node name; a MiB of `{`, of `:`, of
a name, of `extern "C++" {`, of entries, of an unterminated comment and
string; 50000 chained nodes. Each input is parsed as a version script
alone, after another file, and as a dynamic list, and lexed to its end:
`Ok` with every span inside its file and every parent earlier, or a
`version-script-syntax` placed inside the file it names. 0.5 s in all
(debug build).

## 5. Measured first (record §D, §F.2): lld on e10 and a05

`sv3.o` (`.symver old_impl,old@V1`, `cur@@V1`), `-shared`, lld 22.1.8 and
19.1.7 alike:

- e10 `V1 { global: bar; }; V2 { local: old; };`: ``ld.lld: error:
  version script assignment of 'local' to symbol 'old' failed: symbol not
  defined``
- a05 `V1 { global: bar; }; V2 { global: old; };`: ``ld.lld: error:
  version script assignment of 'V2' to symbol 'old' failed: symbol not
  defined``

lld looks the exact entry `old` up by its plain name, which no symbol
has (the definition is `old@V1`), and refuses under its default
`--no-undefined-version`; with `--undefined-version` it links and the
output is GNU ld's and mold's (`old@V1` kept, unchanged by the other
node). GNU ld links silently; mold warns ``cannot assign version `V2`
to symbol `old`: symbol not found`` (for e10 too) and links. So lld's
refusal is its `--no-undefined-version` rule, the case of D-114's
`version-script-undefined-name` (a `.symver` name in another node's exact
entry is a name no file defines unversioned).

## 7. For the next packages

```rust
// mortar_script::version
pub struct SourceFile<'a> { pub path: &'a str, pub bytes: &'a [u8] }
pub const VERSION_SCRIPT: &str = "VERSION script";
pub const DYNAMIC_LIST: &str = "dynamic list";
pub fn parse_version_script(files: &[SourceFile<'_>]) -> Result<VersionScript, Box<Diagnostic>>;
pub fn parse_dynamic_list(files: &[SourceFile<'_>]) -> Result<DynamicList, Box<Diagnostic>>;
// mortar_script::lex::Mode::Version; mortar_diag::Kind::VersionScriptSyntax { script, what }
```

The caller reads the files of `Plan::version_scripts()` (or
`dynamic_lists()`) in order and passes each path as the user wrote it.
A `VersionEntry` has no file index: in a version script its node's
`file` names it; in a dynamic list of several files an entry's span does
not say which file it is in (no diagnostic needs it yet; if WP-128 does,
`VersionEntry` gains a `file`). `VERSION { … }` in a `-T` script stays
refused (§9.2); the body parser would serve it.
