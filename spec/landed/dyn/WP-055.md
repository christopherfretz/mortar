# WP-055: dynamic executables on x86-64 (WP-M2-X64-JOIN)

Record of WP-055. Scope: the row WP-M2-X64-JOIN of
`spec/landed/dyn/WP-040.md` (target 3: the default lines on x86-64 under
`qemu-x86_64`); the follow-up of `spec/landed/x64/WP-048.md` ("build
`X64::new(status)` at the join"). x86-64 `Exec` and `Pie` link; i386
dynamic output stays refused by name for M2; static-pie stays refused
(WP-052). Static links are byte-identical (`cargo xtask static-identical`).

## 1. What changed, by crate

- `mortar` — `dynamic.rs` `arch_status`: x86-64 `Exec`/`Pie` is
  `Status::M2` (the refusal "dynamically linked output on x86-64" is
  gone); `arch.rs` `LinkArch::of` builds `X64::new(status)`, so every M2
  rule of `mortar_x64` (lazy PLT, X-57, X-58, X-26) reaches the linker.
- `mortar_synth` — `got.rs` `GotPlan::write_plt`: `SynthCx.got_base` is
  the GOT base of `Facts.got_base` (arch.md §3.1), `.got.plt`'s start on
  x86 (x64.md X-36); it was `.got`'s start (§2 (a)). `new_dynamic`: the
  refusal of a PLT of several sections names the IBT PLT when the variant
  is `Ibt` (§2 (b)). Test `tests/dyngot.rs`
  `x64_plt0_reads_got_plt_words` (dev-dependency `mortar_x64`).
- `tests/link` — 67 x86-64 lines of `xfails` removed (61 tagged WP-055,
  6 tagged WP-056 that pass: `gcc-rdynamic`, `gcc-z-now`,
  `init-fini-option`, `norelro-dynamic`, `plt-now`,
  `gxx-static-libstdcxx`); new `dyn/reloc/ibt-plt-refused.test`,
  `dyn/reloc/tls-desc-unrecognized-refused.test`.
- No change to `mortar_x64`, `mortar_scan`, `mortar_image`, or to the one
  table (D-43/D-44 in `mortar_arch::class_outcome`, D-47 in the scan
  driver, D-46 in `mortar_image::dynrel::zeroed_place`).

## 2. Wrong outputs found at the join, and what was done

| case | how found | verdict | choice |
|---|---|---|---|

| (b) every input IBT selects the IBT PLT | `-fcf-protection=full` objects with their own `_start` | not wrong: refused, but named "a PLT of several sections" | renamed to D-49's IBT PLT refusal (`ibt-plt-refused`) |

The AArch64 join's four wrong outputs, looked for on x86-64: (a) a copy
alias twice in `.dynsym` — fixed generically by WP-053; `environ-aliases`,
`copy-reloc`, `mixed-mode` pass on x86-64. (b) `st_other` bits — x86-64
defines no `STO_*` bit; nothing to keep. (c) a versioned export —
`versioned-export-refused` passes (refused). (d) a verifier gap — two on
x86-64 (§4).

## 3. Targets

**1. Default `x86_64-linux-gnu-gcc` line, C hello, PIE and `-no-pie`.**
Both link, run (`hello`), stage 3 findings 0. `readelf -d`: the same tags
in the same order as GNU ld's (values differ by layout; `RELACOUNT` 4
against 3). Kept differences, each with its rule:

- `.dynsym` order: D-22 (same set, same versions).
- PIE: one more `RELATIVE`, for `main`'s GOT slot: Scrt1.o's
  `REX_GOTPCRELX` is relaxed to `lea` (as GNU ld) and the slot is kept,
  X-19 ("the GOT slot exists in every case").
- `__cxa_finalize` (GOT use and a call) has a PLT entry and a
  `JUMP_SLOT` where GNU ld uses `.plt.got`: D-49 ("No `.plt.got`").
- `.relro_padding` (layout L-64); eu-elflint reports it ("expected
  RELR", its `.rel` prefix match, ruled for the errata package); GNU ld's
  output: no errors. No other eu-elflint finding.
- `.plt` `sh_entsize` 0; GNU ld writes 16 in a dynamic output (its lazy
  entry size; 8 for its `.plt.got`, 0 for a static `.plt` of IPLT
  entries), lld and mold 0. Not read by any loader or tool measured;
  kept (lld's and mold's value).
- `.tdata` `sh_addralign` is the inputs' maximum (layout L-76): 4 in
  `gxx-static-libstdcxx`, where GNU ld raises it to 8, the `PT_TLS`
  alignment that `.tbss` sets. `PT_TLS` (`p_align` 8), the addresses and
  the TP offsets are the same in all four linkers. These are the two
  differences WP-015's hosted lane listed (".tdata align 8 vs 16, .plt
  entry 16 vs 8"): GNU ld only, no runtime effect.

Debuggers under qemu: host gdb is AArch64-only (no x86-64 target);

## 4. Findings for the supervisor

- **V1 (verifier request): PLT0 and the entries' `jmp PLT0` are not
  decoded.** P-D10 decodes each entry's `jmp *word` only. Reproducer: a
  mortar C hello PIE (`-Wl,--build-id=none`) with PLT0's rel32 at
  `.plt + 8` lowered by 0x1030, or an entry's `e9` rel32 at `+12` changed:
  `findings: 0`; the program crashes at its first lazy call. The wrong
  output of §2 (a) passed stage 3 in every linktest. Proposed P-D10
  text: "PLT0 decodes (the architecture's header: x86-64 `push
  GOT+8; jmp *GOT+16`, AArch64 `.got.plt[2]`) and each lazy entry's
  return to PLT0 (x86-64 `push n; jmp PLT0`, `n` its `.rela.plt` index)
  decodes to PLT0."
- **V2 (verifier request): TLSDESC → IE whose destination is not `%rax`.**
  Stage 2's R1 expects the local-exec form ("a TLS descriptor in a
  static output") for `lea x@tlsdesc(%rip), %rbp` against a shared key
  and reports the N1 bytes `48 8b 2d <rel32>` on GNU ld's, lld's, mold's
  and mortar's outputs alike; all run. Reproducer (with a library
  `__thread int tlsx = 5;` linked `-L. -ltx`, PIE or `-no-pie`; prints
  `tlsx 5`):

  ```
  main: pushq %rbp; pushq %rbx; subq $8, %rsp
        leaq tlsx@TLSDESC(%rip), %rbp
        movq %rbp, %rax
        call *tlsx@TLSCALL(%rax)
        movq %fs:0, %rbx; movl (%rbx,%rax), %esi
        leaq fmt(%rip), %rdi; xorl %eax, %eax; call printf@PLT
        addq $8, %rsp; popq %rbx; popq %rbp; xorl %eax, %eax; ret
  fmt:  .string "tlsx %d\n"
  ```

  The real case: GCC 14 `-O2 -fPIC -mtls-dialect=gnu2` `cxx_main.cc`
  (`std::call_once`'s `__once_call`). No linktest holds it: the harness
  refuses a test that every reference fails, and the finding is not a
  reference's wrong output (no anomaly id).
- **x64.md X-58** says "the other registers by the same ModRM, not run":
  `%rbp` is now run (V2's program, and the C++ corpus), with GNU ld, lld
  and mold writing the same bytes. Proposed: "(destination `%rax`, and
  `%rbp` as GCC 14 schedules `__once_call`; WP-055)".
- `SynthCx.got_base` (arch.md §3.7) was, in the PLT writer, `.got`'s
  start on every architecture. Only x86-64's dynamic PLT0 and i386's PIC
  IPLT (static-pie, refused) read it, so no static output changes.
- The tests' comments "mortar: … x86-64 WP-055 (X64-JOIN), in
  tests/link/xfails" are now history, as their AArch64 halves were after
  WP-053; not edited.
