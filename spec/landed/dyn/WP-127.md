# WP-127 part 1: x86-64 shared objects (no TLS, no IFUNC)

`-shared` links on x86-64 (record WP-110 §D, row WP-127; x64.md §5.1).
The §4.3 cell table already held x86-64's `Shared` row (WP-117); this
package lets the link through (`arch_status`), keeps X-57's weak-call
rule to executables (X-59), confirms X-60 (GOT relaxation only against
`local`), gives D-117's address-level rule its x86-64 scope (X-62) after
measuring it (§1), and runs every WP-123 shared-object test on x86-64.
TLS (X-61) and the library's own IFUNC (D-121) stay refused by name
until part 2 (§7). Executables, static links and their maps are
byte-identical (§6).

## 1. X-62's premise, measured

The question: does any producer reach an exported data or function
definition through a section-relative PC-relative field in code (a
use X-62 does not judge)? Scratch scripts in
`.build/target-wp-127/x62/` (`build.sh`, `analyse.sh`,
`tools/codepc_exact.py`, `tools/funcpc.py`), with
`tests/shared-design/exp3/x86gt.py` and `s1d.py --x86`.

- **Corpus**: GCC 14, Clang 19, Clang 22, kiln with llc at
  `-O0/-O1/-O2/-O3/-Os`, kiln with hod at `-O0` (all 174 hod objects
  confirmed written by hod); each as `-fPIC`, `-fPIE` and `-fno-pic`
  twins. Sources: zlib (15 units), the Lua core, googletest's
  `gtest-all.cc`, exp3's cases (`boundary.c`, `anchorgap.c`,
  `vague.cc`) and exp3/hod's units (`x1`-`x4`, `c1.cc`, `c2.c`,
  `gap2.c`, `hodt.c`). 3906 compile jobs, 3834 objects; the 72
  failures are kiln's (`boundary.c`, and zlib's `deflate.c`/`trees.c`
  as C++).
- **x86gt** over each producer x level x model (`-fPIE`/`-fno-pic`, 62
  objects; kiln 58): every exported data definition another unit or
  function uses is named by its symbol; `exact` 0 and `codepc` 0 in
  all 42 sets (defs per level: GCC 117/103/100/100/101, Clang
  117/103/103/103/101, kiln 114/100/100/100/98, kiln+hod 114). Clang's
  `-fPIE` twins leave 2 unseen (`boundary.c`'s `asmlabel`, an `asm`
  label, not a compiler use).
- **Every section-relative PC-relative code field** whose addend lands
  inside an exported data definition (167 candidates) was decoded with
  objdump's instruction boundaries to its exact named address: 153 name
  an address outside the definition (the `-4` tail misled the
  candidate); 14 name an address inside one, and all 14 are the
  one-past-the-end address of a static object that equals the next
  exported object's start (`&before[4]` in `boundary.c`, GCC `-O0`;
  `&static_table[4]` in `vague.cc`, GCC `-O0`..`-Os`; `buf + 16` in
  `c1.cc`, kiln+hod): boundary addresses (D-117 m-1), not uses.
- **Functions**: 7 section-relative code `PC32`s land in an exported
  function, all GCC `-O2`/`-O3` jumps from `.text.unlikely` cold parts
  back into the body (`catcher`, `testing::UnitTest::Run`): not the
  entry, and preemption of a function never redirects its own body.
- **Verdict**: no producer reaches an exported definition through a
  section-relative PC-relative code field. X-62 ships as written.
- **s1d `--x86`** over the `-fPIC` objects refuses `boundary.c` at
  `-O0` for GCC, Clang 19 and Clang 22: a `TLSGD` against
  `.tdata+4-4` (`tls_static`) that the oracle judges with its `-4`
  tail. X-62 does not judge `TLSGD` (and mortar refuses TLS in a
  shared object until part 2); the oracle's x86 scope and the question
  whether a TLS code form against a local TLS symbol is judged are
  part 2's (§7).

## 5. Findings

- **An internal error, pre-existing and generic (not a mislink)**:
  when the only `.eh_frame` input is a 4-byte terminator carrying a
  symbol (x86-64 `crtendS.o`'s `__FRAME_END__`), the link stops with
  `internal error in mortar: .symtab: .eh_frame has no place`
  (`crates/mortar_synth/src/symtab.rs:971`, `Where::Eh` with no output
  `.eh_frame`). AArch64 and x86-64, static and shared alike.
  Reproduction: `term.s` = `.section .eh_frame,"a",%progbits;
  .type __FRAME_END__,%object; __FRAME_END__: .long 0`, plus any object
  without `.eh_frame`, `gcc -B<dir with ld -> mortar> -nostdlib -static
  a.o term.o -e get`. The x86-64 tests carry CFI so their objects have
  `.eh_frame`; the fix belongs to the `.eh_frame`/symtab owner.
- **Message wording for a section target**: `32` against `.data+4` (a
  `local` target) reads ``against symbol `.data+0x4' which may bind
  externally``; GNU ld writes ``against `.data'`` for local targets.
  diag.md §3.1 fixes one wording; left as is.
- **References on X-59's cells**: lld refuses all eight; GNU ld links
  the data `PC32` and `GOTOFF64`; mold links the `PC32` call (a PLT
  entry) and `GOTOFF64`. mold writes a relaxed `call *f@GOTPCREL` as
  `call` + `nop`, not `addr32 call`.

  the library's own IFUNC in every `Shared` link; WP-124 lifts it for

  relaxation hooks in `crates/mortar_x64/src/lib.rs` (`window`,
  `consumed`) already stop at `is_exec`.
- WP-124's GOT/RELA writers (`crates/mortar_synth/src/{got.rs,rela.rs}`)
  are the shared machinery; x86-64's record types (16, 17, 18, 36) go
  through the same plans.
