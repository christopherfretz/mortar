# WP-054: C++ dynamic executables against libstdc++.so, AArch64 (WP-M2-CXX)

Record of WP-054. Scope: g++ and clang++ (19, 22) programs linked by the
default dynamic line against libstdc++.so, libgcc_s.so and libc.so on
AArch64, PIE and `-no-pie`. Two wrong outputs were found and fixed; one
case is left to a verifier change. Static links are byte-identical
(`cargo xtask static-identical`: 219 links, 0 differ).

## 1. What changed, by crate

- `mortar` — `syms.rs`: `CoreSyms::dynamic` (`keep_unique`). In an
  output with `.dynamic`, a definition whose entry is `STB_GNU_UNIQUE`
  keeps that binding in `.symtab` and `.dynsym`. Before, resolve §3.7's
  `STB_GLOBAL` was written in both. It is set at the four places that
  build a `CoreSyms` (`front.rs` 180 and 571, `image.rs` 123, `dynlink.rs`
  124). `EI_OSABI` then follows D-23 unchanged.
- `mortar_layout` — `chunk.rs` (the loop after the island and copy
  chunks): the first chunk of every output section is aligned to the
  widest alignment among its chunks. Before, only a leading copy chunk
  was aligned this way.

## 3. Targets

- 1: iostream hello, g++ / clang++-19 / clang++-22 × O0/O2 × PIE/`-no-pie`
  (12 links). All link and run with the same output as GNU ld; plumb
  finds nothing. `readelf -d` and the `-r` multiset are identical to GNU
  ld's. `--dyn-syms` differs only in PIE: GNU ld writes `STT_SECTION`
  entries for `.data` and `.init`, and D-21 says never section symbols.
  eu-elflint gives GNU ld's output no complaints. On mortar's it gives
  only the two `.relro_padding` lines (Q5 allow-list). gdb and lldb stop
  on `main` and on `ns::G::greet` for g++ and clang++-22, PIE and
  `-no-pie` (`dyn/tools/debug-cxx`).
- 2: the C++ programs of E-corpus (`cxx_main.cc` + `cxx_helper.cc`): gcc,
  clang-19, clang-22 × the nine AArch64 modes × O0/O2 × PIE/`-no-pie`.
  That is 108 cells. 8 do not compile: clang has no
  `-mtls-dialect=trad`, which leaves 100 link cells.
  - 90: both link, the outputs are equal, plumb is clean.
  - 4: gcc `pic-tlstrad` (O0/O2 × PIE/`-no-pie`). Both link and the
    outputs are equal. Case (c): plumb gives 17 or 23 R1/S12 findings on
    mortar's output and the same on GNU ld's.
  - 6: `-fno-pic` objects into a PIE. Both refuse. mortar says
    `canonical-plt-in-pie` (D-44, `ADR_PREL_PG_HI21` against a shared
    function). GNU ld reports an unresolvable `ADR_PREL_PG_HI21`.
  - 0: only GNU ld refuses.
- 3: each feature has a running test, with the expected output taken from
  GNU ld's run:
  - copy relocations of typeinfo and vtables into RELRO: the existing
    `dyn/reloc/copy-typeinfo-relro`, plus `exceptions-rtti` (`-fno-pic`).
  - `STB_GNU_UNIQUE`, inline variables, function-local statics shared
    with a library: `unique-shared`.
  - TLS IE `__once_call`, `std::call_once`, `thread_local` with dynamic
    init, `std::thread`, libc's IFUNC `memcpy`, `-static-libgcc` and
    `-static-libstdc++ -static-libgcc`: `threads-tls`.
  - exceptions across the boundary (`.eh_frame_hdr`, frames through the
    library and the PLT), `dynamic_cast`/`typeid` equality: g++ and
    clang++ in `exceptions-rtti`.
  - weak and strong replacement `operator new`, exported and winning:
    `operator-new-replaced`.
  - `-static-libstdc++`: also the existing `dyn/census/gxx-static-libstdcxx`.
  - traditional GD to IE: `tls-gd-to-ie` (xfail, verifier request).

  Every new test passes for bfd, lld, mold and mortar, except that one.
- 4: no `tests/link/xfails` line was tagged WP-054 at the start. The
  package adds one: `tls-gd-to-ie`, as a verifier request.
- 5: kiln + hod. `kiln++ -O0 -std=c++20 -c` with `KILN_BACKEND=hod`
  (strict) compiles a hello that throws and catches `std::runtime_error`.
  `kiln++ -B<mortar wrapper dir> hello.o` links it with clang++ 22's
  default dynamic line (PIE, libstdc++.so). It runs and prints the same
  as the GNU ld link; plumb finds nothing. The output is byte-identical
  to `clang++-22 --ld-path=mortar`.

## 4. Kept differences from GNU ld's dynamic tables

- PIE: GNU ld writes a `JUMP_SLOT` for each function that only a data
  word names: `__gxx_personality_v0` (`DW.ref`), and
  `_ZNKSt13runtime_error4whatEv` and `_ZNSt13runtime_errorD2Ev` (vtable
  words). mortar writes the symbolic `ABS64` record and no PLT entry,
  because nothing branches there (D-46). GNU ld also writes the record.
- `-no-pie`: an absolute word in a writable place against a shared
  function (`__gxx_personality_v0`, the `runtime_error` members, `memcpy`
  (IFUNC), `_ZNSt6thread6_StateD2Ev`). GNU ld makes a canonical PLT, so
  its `.dynsym` value is not 0. mortar writes a symbolic `ABS64` record
  with value 0. Rule: D-46; D-44's canonical PLT is for read-only places
  only.
- `-fno-pic -no-pie`: an `ABS64` record against a copied key (`_ZTIi`,
  `_ZTI6LibErr`, `_ZSt4cout`, `_ZSt7nothrow`) in a writable word. lld
  writes the same; GNU ld writes the copy's address. Both are correct,
  because the loader binds the key to the copy. See finding 4.
- `-fPIC -no-pie`: GNU ld writes a `GLOB_DAT` for the executable's own
  exported vague-linkage definitions (`_ZNKSt5ctypeIcE8do_widenEc`, a
  `basic_string::_M_construct` instance). mortar fills the slot at link
  time (D-50: an executable's definitions are not preemptible; D-46
  `Local`).
- Traditional GD to IE: GNU ld keeps an unused `JUMP_SLOT` for
  `__tls_get_addr`. mortar has none (a64 R4: a relaxed `CALL26` raises no
  PLT demand).
- `-static-libstdc++`: weak `_ITM_*`, `_ZGTtnam` and `_ZGTtdlPv` reached
  by branches only. GNU ld makes them `WeakDyn` with `JUMP_SLOT`s; mortar
  makes them `Weak0` (D-25: a branch alone). With `-no-pie`, mortar makes
  `__cxa_pure_virtual` `WeakDyn`, with 5 `ABS64` records in vtables
  (D-25's `Exec` rule; no reference does this, and lld's missing record
  is anomaly A25).

## 5. Findings for the supervisor

1. Verifier request (plumb.md §5.3): add a W-rule `tlsgd-to-ie`.
   Proposed text: "`ADRP x0, :tlsgd:S; ADD x0, x0, :tlsgd_lo12:S; BL
   __tls_get_addr; NOP` made `ADRP x0, G; LDR x0, [x0, :lo12:G]; MRS x1,
   TPIDR_EL0; ADD x0, x1, x0`, with G a GOT entry holding S's TP offset
   (a `TLS_TPREL64` record in a dynamic output, a64 §8.4 R4)."
   Reproducer: `tests/link/dyn/reloc/tls-gd-to-ie.test`.
2. Verifier request: plumb does not check that an exported unique
   definition stays `STB_GNU_UNIQUE` in `.dynsym`, so case (a) passed.
   Also, plumb's S1 (mortar's `EI_OSABI` rule, plumb.md §6 "(mortar)")
   reads only `.symtab`, while D-23 says "`.symtab` or `.dynsym`".
   Proposed: "EI_OSABI is 3 exactly when `.symtab` or `.dynsym` holds ...".
3. Spec text, dyn.md D-23. "so `.dynsym` of an executable never holds a
   unique symbol" is true of copies only. Proposed: "so a copy is never
   unique in `.dynsym`; an exported unique definition of the executable
   stays `STB_GNU_UNIQUE` there (the export row; GNU ld, lld and mold;
   glibc's unique table then holds the executable's instance, which
   `RTLD_DEEPBIND` libraries bind to)."
4. Spec question, D-46 against D-42/D-50. Should a word against a copied
   key take the key's symbolic record (mortar and lld) or the copy's
   address with no record (GNU ld)? The table has no row for a copied
   target. Proposed: a row "`Copy`: symbolic record, as `Shlib`". This
   keeps `LD_PRELOAD` interposition of the copied object working, as for
   any import.
5. Static links: `.symtab` still drops `STB_GNU_UNIQUE`
   (`crates/mortar_resolve/src/tables.rs:945`, `symtab_entry(d, p,
   false)`). D-23 says an executable's own unique definitions stay unique
   in `.symtab`. Not changed here, because it would change static bytes.
6. Layout (case b): L-5 held only by accident for a body chunk followed
   by a wider merged chunk. Proposed text, layout.md: "the first chunk of
   an output section is aligned to `sh_addralign`, the largest alignment
   of its chunks."
