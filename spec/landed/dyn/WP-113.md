# WP-113: a non-alloc word against a name only a shared library defines

Record of WP-113. Scope: what a word in a non-alloc section holds when
its target is defined only by a shared library (`Shlib`, and
`Preemptible`/`WeakDyn` targets not defined here), on AArch64 and
x86-64; the DTP-offset words against such a library's TLS variable. No
other linker behaviour changed (§5).

## 1. The defects and their cause

- **Defect 1.** A non-alloc word against a library function that the
  output gives an ordinary PLT entry (a function only called, in a PIE
  or an ET_EXEC; a library's IFUNC) held that PLT stub's address, e.g.
  `.quad dfunc` in `.debug_*` of an x86-64 or AArch64 PIE.
- **Defect 2.** x86-64 `DTPOFF64`/`DTPOFF32` (AArch64 `TLS_DTPREL64`)
  against a library's TLS variable, in an output with no `PT_TLS`,
  stopped with `internal error: no PT_TLS in the tables`; with a
  `PT_TLS` it wrote `A − ` its address.

**Cause.** `LinkTables::sym_value_of` (`crates/mortar_image/src/link.rs`)
built the `S` of every key that had any PLT entry from `plt_address`:
the dynamic PLT entry, else the IPLT entry. Its documented interface
(arch.md §3.6) gives `S` the PLT entry only when that entry IS the
symbol's address: the canonical entry (dyn.md D-44, `CANON_PLT`) or the
IPLT of an IFUNC defined here (S-71). Alloc places never observed the
difference: they reach a library's function through the `L` base
(`plt()`), a GOT slot, a dynamic relocation or a thunk's `Plt` target,
never through `S`; only a non-alloc place, which no dynamic relocation
can reach, reads `S` as the word. Defect 2 was `tls_off` in the three
`apply.rs`: it required a `PT_TLS` for every `TlsDtpRel` field, and
`class_outcome` let the word through for a `Shlib` target.

**Other readers of the stand-in.** None observed it:
- the erratum scan (`crates/mortar_a64` `sites.rs`) decides by the
  `IPLT` flag and treats a `Shared` key as unknown;
- the map, `.dynsym` and `.symtab` use `def_addr` (the copy's address
  or nothing); mortar's `.symtab` omits imported undefined symbols
  altogether, where the references list them as `UND 0` (unchanged here,
  noted);
- `.gdb_index` is built from DWARF, not from `S`;
- `-no-pie` alloc words go through D/C demands (a copy or a canonical
  entry), as before.

## 2. The rule (arch.md §4.3, a64.md §13.2, x64.md X-53, x86.md X86-61)

`S` at a non-alloc place, for a target only a library defines:

| The output gives the symbol | `S` |
|---|---|
| a copy (D-43) | the copy's address |
| a canonical PLT entry (D-44, ET_EXEC only) | the entry's address |
| an ordinary PLT entry, an IPLT for a library IFUNC, a GOT slot, or nothing | 0 |

The word is then `0 + A` (absolute) or `0 + A − P` (PC-relative).

- `TlsDtpRel` (`DTPOFF64`/`DTPOFF32`, `TLS_DTPREL64`, i386 `TLS_LDO_32`)
  against a library's TLS variable writes **`0 + A`, with or without a
  `PT_TLS`** (the supervisor's correction to the brief; the symbol is in
  the library's block, so no offset in this output's block is its value).
- `AbsWord`/`AbsNarrow` against a library's `STT_TLS` symbol stays `E`:
  `relocation-incompatible` "it is thread-local" when the reference is
  typed `STT_TLS`, the resolver's `TLS attribute mismatch` when it is
  untyped. It was an internal error (no `PT_TLS`) or `A − start` before.
- A weak undefined that nothing defines keeps the architecture's §7 rule.

## 3. The references, measured

Section `.debug_mortar_dsoref` in `-O1` objects against `libv.so`
(`afunc` address-taken, `dfunc` only called, `cvar` copied, `ifn` an
IFUNC, `tvar` TLS); GNU ld 2.44, lld 22, mold 2.37.

| Case | GNU ld | lld | mold | mortar now |
|---|---|---|---|---|
| AArch64 PIE, abs/PC words | `0 + A`, `0 + A − P` | addend dropped | refuses `PREL64` | = GNU ld (bytes equal) |
| x86-64 PIE, abs words vs functions | the PLT stub | 0 | refuses `PC64` | `0 + A` |
| ET_EXEC (both), only-called function | the PLT stub | 0 | refuses | 0 + A |
| ET_EXEC, address-taken function | canonical entry | canonical entry | refuses | canonical entry + A |
| ET_EXEC, copied datum | the copy | the copy, addend dropped | refuses | the copy + A |
| x86-64 `DTPOFF*`, no `PT_TLS` | `0 + A` | 0 | `0 + A` | `0 + A` (bytes equal GNU ld) |
| x86-64 `DTPOFF*`, with a `PT_TLS` | `A − PT_TLS` | 0 | `A − PT_TLS` | `0 + A` |
| x86-64 typed `.quad tvar` | `0 + A` | links | links | `E` thread-local |
| x86-64 untyped `.quad tvar` | "bad value" | links | links | `E` TLS attribute mismatch |
| AArch64 `TLS_DTPREL64` (by `.reloc`) | refused | refused | refused | `0 + A` |

## 4. Tests

- `crates/mortar/tests/nonalloc_shlib.rs` (cross-gcc driven with
  `-B` to mortar; asserts the words):
  `pie_words_are_zero_plus_addend` (both arches; AArch64 bytes equal GNU
  ld's), `exec_words_take_the_copy_and_the_canonical_entry_only`,
  `dtpoff_against_a_library_tls_variable` (PIE and non-PIE, with and
  without a `PT_TLS`), `dtprel64_against_a_library_tls_variable`,
  `absolute_word_against_a_library_tls_variable_is_refused`.
- Link tests: L3 (mortar_plumb) reports R1 on these words for every
  linker until WP-104's rule (plumb.md §5.8) is in, so no
  `tests/link` file can judge them here. WP-104's
  `tests/link/dyn/reloc/debug-word-shared.test` and
  `debug-word-shared-tls.test` are those link tests; this package's words
  were checked against both by hand (every line they judge on mortar).
  They turn green on mortar when both packages are merged. **After
  WP-104**: nothing in this package to remove; the "red on mortar until
  WP-113" note of those two tests (if any) is what goes.

## 5. What moved

- The `tests/link` corpus, mortar only, before (f426e01) and after:
  same outcomes (459 PASS, 4 XFAIL, 1 XPASS already on main, 6 SKIP).
  All 891 mortar links of the run re-linked with both binaries: no
  successful link's output changed (135 differences, every one a link
  that fails in both, differing in the program name of stderr).
- 16 C++ `-g` links against libstdc++.so (both arches, PIE and -no-pie,
  `-O0 -g`, `-O2 -g`, `-O2 -gsplit-dwarf`, `-O1 -g3 -gdwarf-4`):
  identical outputs before and after. GCC and Clang emit no non-alloc
  word against a library's name in ordinary code; Clang's `.debug_addr`
  `_vtable$` entry (RB-1) is the one known source.
- Static baselines: no static link has a `Shlib` target, so
  `tests/identical` cannot move (the gate's lane confirms).
