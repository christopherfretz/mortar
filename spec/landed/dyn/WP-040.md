# WP-040: M2 (dynamic executables), the work-package cut

Design record of WP-040. The rules are `spec/dyn.md`; this file says how
to build them: what lands first, which packages run in parallel, how each
is tested alone, and in what order they join. **Estimates are estimates**
(agent-days of one implementer, review included, from the size of the
comparable M1 packages); they are not measured.

## 1. Principles of the cut

- **Every package is testable alone.** Each one has an oracle that does
  not need the others: a reference linker's output for the same inputs,
  a fixture `Resolution`/`Demands`/`Slots`, or a program that runs.
- **The refusal stays until the join.** `mortar_input`'s "dynamic
  executable without -dynamic-linker" and the CLI's refusals of `-pie`
  and `-dynamic-linker` stay in place (moved to one guard in the `mortar`
  crate, step 0 e) until WP-M2-JOIN-C lifts it for AArch64. Packages land
  on main behind it; nothing half-done is reachable from a command line.
- **Static links stay byte-identical.** Every package's gate links the M1
  corpus (the `xtask` link tests, L3, the Mason lane, the libc++ static
  suite of WP-034 where available) and compares output digests with a
  baseline recorded at step 0; a differing byte fails the package. The
  one exception is Q7 (S-69's IPLT word), which is its own M1 change and
  lands before the baseline.
- **The verifier is staffed separately** (WP-M2-PLUMB), from `dyn.md` and
  the references' outputs, never from mortar's code.

## 4. Order and parallelism

```
0a-0g ─┬─ CLI ───────────────────────────────┐
       ├─ RES ───────────────────────────────┤
       ├─ DYNSYM ────────────────────────────┤
       ├─ DYNAMIC ───────────────────────────┤
       ├─ RELOC ─────────────────────────────┼─ JOIN-C ─ CXX ─┬─ OPTS
       ├─ A64 ───────────────────────────────┤                │
       ├─ LAYOUT ────────────────────────────┤                │
       ├─ X64 ──────────────────────────────────── X64-JOIN ──┘
       ├─ SPIE (after DYNAMIC, RELOC, LAYOUT)
       └─ PLUMB (independent, from the references' outputs) ──┘ (gates every join)
```

Up to nine packages run at once after step 0 (CLI, RES, DYNSYM, DYNAMIC,
RELOC, A64, X64, LAYOUT, PLUMB). They touch disjoint files except
`mortar_synth` (DYNSYM and DYNAMIC and RELOC in separate new modules;
`lib.rs`'s chunk list is step 0b's) and `mortar_image` (DYNAMIC and RELOC:
the value fill vs the record writer, separate functions). Expected
critical path: step 0 (2-3 d) → RELOC (6-8 d) → JOIN-C (2-3 d) → CXX →
OPTS, about 4 weeks of calendar time with PLUMB in parallel; the
estimates sum to about 50-70 agent-days.

## 5. M1 code touched

`mortar_input` (`walk.rs`: the refusal moves to the guard; closure walk),
`mortar_resolve` (export, needed: the static path does not reach them),
`mortar_scan` (the demand table's Exec/Pie rows: static rows unchanged),
`mortar_synth` (chunk list: new rows absent from static links), 
`mortar_layout` (ranks that hold nothing in a static link),
`mortar_image`, `mortar_a64`, `mortar_x64` (`Status::M2` paths),
`mortar` (`front.rs`, `arch.rs`). Each change is guarded so that a static
link takes the M1 path; the step-0g digest check proves it per package.
In flight elsewhere and to rebase on: WP-031 (`mortar_live`,
`--gc-sections`: D-11's "a gc'd section still counts" needs its mark),
WP-030b (`mortar_x86`; i386 dynamic is M4), WP-028d (verifier mutation
harness, which PLUMB extends), WP-032f/g (`mortar_image` fill, `par`).

## 6. Not cut here (M4)

`-shared` and verdefs, RELR, i386 dynamic links (R-X86-*), `--dynamic-list`,
IBT/PAC PLTs, `-z notext`, `--hash-style=sysv|both`.
