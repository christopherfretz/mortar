# WP-040: M2 (dynamic executables), the work-package cut

Design record of WP-040. The rules are `spec/dyn.md`; this file says how
to build them: what lands first, which packages run in parallel, how each
is tested alone, and in what order they join. Revised after the
adversarial review (`briefs/reviews/review-040-m2.md`, findings F7, F8,
C1, C2).

## 1. Principles of the cut

- **Every package is testable alone.** Each one has an oracle that does
  not need the others: a reference linker's output for the same inputs,
  a fixture `Resolution`/`Demands`/`Slots`, or a program that runs.
- **The refusal stays until the join.** `mortar_input`'s "dynamic
  executable without -dynamic-linker" and the CLI's refusals of `-pie`
  and `-dynamic-linker` stay in place (moved to one guard in the `mortar`
  crate, step 0e) until WP-M2-JOIN-C lifts it for AArch64. Packages land
  on main behind it; nothing half-done is reachable from a command line.
- **Static links stay byte-identical.** Every package's gate links the M1
  corpus (the `xtask` link tests, L3, the Mason lane, the libc++ static
  suite of WP-034 where available) and compares output digests with a
  baseline recorded at step 0g; a differing byte fails the package. The
  one exception is Q7 (S-69's IPLT word), which is its own M1 change and
  lands before the baseline.
- **The verifier is staffed separately** (WP-M2-PLUMB), from `dyn.md` and
  the references' outputs, never from mortar's code, and it recomputes
  every linker decision from the inputs (`dyn.md` §12).
- **Every joined target is gated by stage 3 including P-D9** (the dynamic
  records, three views), not only by the table checks.

## 2. Step 0: interface changes that land first (small commits)

Each is a small commit by the supervisor or a short package (WP-M2-0);
all packages below build on them. The function signatures are the
contract; bodies may be `todo!()`-free stubs returning empty plans so
that packages compile against them.

## 4. Order and parallelism

```
0a-0j ─┬─ CLI ──────────────────────────────────┐
       ├─ RES ──────────────────────────────────┤
       ├─ DYNSYM (owns 0h, 0i) ─────────────────┤
       ├─ DYNAMIC (after 0h; fixture DynStr) ───┤
       ├─ RELOC (after 0i) ─────────────────────┼─ JOIN-C ─ CXX ─┬─ OPTS ─┬─ LANE
       ├─ A64 ──────────────────────────────────┤                │        └─ BENCH
       ├─ LAYOUT ───────────────────────────────┤                │
       ├─ TEST ─────────────────────────────────┤                │
       ├─ X64 ─────────────────────────────────────── X64-JOIN ──┘
       ├─ SPIE (after DYNAMIC, RELOC, LAYOUT)
       └─ PLUMB (independent; P-D9 gates JOIN-C) ┘
```

Up to ten packages run at once after step 0 (CLI, RES, DYNSYM, DYNAMIC,
RELOC, A64, X64, LAYOUT, TEST, PLUMB). Shared crates and who edits what:

- `mortar_synth`: DYNSYM (`dynsym.rs`, `gnuhash.rs`, `version.rs`,
  `dynstr.rs`), DYNAMIC (`dynamic.rs`, `interp.rs`), RELOC (`rela.rs`,
  `got.rs`); `lib.rs`'s chunk list is step 0b's and nobody else edits it.
- `mortar_image`: **WP-032f (fill, in flight) lands first**; then DYNAMIC
  adds `dynamic.rs` (writing `.dynamic`/`.interp` values, no change to
  `fill`), then RELOC adds `dynrel.rs` and is the only M2 package that
  touches `fill`'s call sites (the record emission per relocation). RELOC
  rebases on DYNAMIC, not the other way.
- `mortar_resolve`, `mortar_input`: RES only (WP-031's `mortar_live` mark
  is read, not edited).
- `mortar_plumb`: PLUMB only (WP-028d's mutation harness extended).

The critical path is step 0 → RELOC (L) → JOIN-C → CXX → OPTS → LANE;
with PLUMB (XL) running beside it and gating JOIN-C.

## 5. M1 code touched

`mortar_input` (`walk.rs`: the refusal moves to the guard; closure walk),
`mortar_resolve` (export, needed: the static path does not reach them),
`mortar_scan` (the demand table's Exec/Pie rows: static rows unchanged),
`mortar_synth` (chunk list: new rows absent from static links),
`mortar_layout` (ranks that hold nothing in a static link),
`mortar_image`, `mortar_a64`, `mortar_x64` (`Status::M2` paths),
`mortar` (`front.rs`, `arch.rs`). Each change is guarded so that a static
link takes the M1 path; the step-0g digest check proves it per package.
In flight elsewhere and to rebase on: WP-031 (`mortar_live`,
`--gc-sections`: D-11's "a gc'd section still counts" needs its mark),
WP-030b (`mortar_x86`; i386 dynamic is M4), WP-028d (verifier mutation
harness, which PLUMB extends), WP-032f/g (`mortar_image` fill, `par`).

## 6. Not cut here (M4)

`-shared` and verdefs, RELR, i386 dynamic links (R-X86-*), `--dynamic-list`,
IBT/PAC PLTs, `-z notext`, `-z [no]dynamic-undefined-weak`,
`--hash-style=sysv|both`.
