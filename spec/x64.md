# spec: x86-64 (`mortar_x64`)

**Status: accepted (WP-029 stage 1; reviewed independently). The requests of §16 are applied (WP-029r; R-12 by WP-028c).**

The x86-64 instance of the `Arch` trait (`spec/arch.md`): every
relocation type, what it computes, where it writes, when it overflows,
what it demands and how it may be relaxed; the bytes of every table and
stub the linker writes; GNU properties and CET; TLS; and the ELF header
facts. It replaces the provisional fit check of arch.md Appendix A, which
it cites and, where measurement disagreed, corrects (§16).

Two implementations are written from this document and must agree:
`mortar_x64` and the verifier `mortar_plumb` (`docs/AGENTS.md` rule 10).
Where the text says "the verifier checks", that is the check
`mortar_plumb` makes from the output and the inputs alone.

Rules are numbered `X-1`, `X-2`, … and tagged **[M1]** (static
executables, non-PIE and static-pie, this WP's scope) or **[M2]**
(dynamic executables, PIE with a dynamic loader, shared objects). Every
rule has a test idea in §18. The experiments are `E1`–`E13` (Appendix A);
`synth.md`'s own experiment ids `X-19`, `X-22`, … are a different series
and are cited here as "synth X-22". A statement this document could not
ground in a cited document or an experiment is marked **[open]** and
listed in §17 with a recommended answer.

Documents cited, all public:

- **psABI**: "System V Application Binary Interface, AMD64 Architecture
  Processor Supplement" (the `x86-64-ABI` repository, 2024-2025 text):
  relocation types and their calculations, the GOT/PLT, TLS models,
  `GOTPCRELX`, the x86 GNU properties, APX `CODE_*` types.
- **TLS**: U. Drepper, "ELF Handling For Thread-Local Storage" (variant
  II, the x86-64 sequences and their linker rewrites).
- **TLSDESC**: A. Oliva, "Thread-Local Storage Descriptors for IA32 and
  AMD64/EM64T".
- **binutils**: `bfd/elf64-x86-64.c`, `bfd/elfxx-x86.c` and
  `include/elf/x86-64.h` of binutils 2.44, for GNU ld's behavior where an
  experiment showed it.
- **SDM**: the Intel 64 and IA-32 Architectures Software Developer's
  Manual, volume 2 (instruction encodings only).

Every byte sequence in this document was produced by the reference
container's tools (GNU as 2.44, llvm-mc 19 and 22) and read back with
`objdump -d`; Appendix A gives the scripts.

## 1. Scope and status

- **X-1 [M1] Class, data, machine.** ELFCLASS64, little-endian,
  `EM_X86_64` (62). ELFCLASS32 `EM_X86_64` objects (x32) are refused by
  the reader (`spec/elf.md` §3.1). i386 (`EM_386`) is `spec/x86.md`
  (WP-030).
- **X-2 [M1] RELA only.** Relocation sections are `SHT_RELA`. The psABI
  uses RELA only and no producer of the census writes `SHT_REL` (E1: 0
  sections). An `SHT_REL` section in an `EM_X86_64` object is refused by
  name at resolve (arch.md §3.1, `SectionRefusal::RelForm`; class
  `section-type`, name `SHT_REL`).
- **X-3 [M1] Statuses.** A type is **M1** (implemented for static
  executables, non-PIE and static-pie), **M2** (dynamic outputs only),
  **later** (specified, refused by name until a milestone takes it) or
  **refused** (refused by name, no plan). A type that is not M1 (or M2
  in a dynamic output) is refused at scan by name (class
  `relocation-type`, the psABI name `R_X86_64_*`) with the place of the
  relocation. Every type the census of §2 found is M1.

Summary of §6 (the rows are authoritative): 30 static types are M1
(0, 1, 2, 4, 9–15, 17–27, 29, 31–35, 41, 42), 12 are later (3, 28, 30,
43–51), and 10 numbered types are refused (the dynamic-only 5–8, 16,
36–38 and the withdrawn MPX 39, 40), as is every type ≥ 52. Of the
dynamic types (§6.2) mortar writes `IRELATIVE` (37) and, in static-pie,
`RELATIVE` (8) from M1; the rest from M2.

Static-pie is M1 here, by this WP's brief; `docs/ROADMAP.md` lists
`-static-pie` under a later milestone. Request R-9 (§16) aligns the two:
the static-pie rows are specified and tagged now and `mortar_x64`
implements and unit-tests them in M1; the end-to-end static-pie gate is
M2, with the generic `.dynamic`/`RELATIVE` machinery.

## 3. Terms

### 3.1 Values

Terms are the psABI's ("Relocation Types"), defined against the tables
of `spec/model.md`. Arithmetic is 64-bit two's complement; a check is on
the mathematical value before truncation.

| term | meaning |
|---|---|
| `S` | the address of the symbol (`spec/a64.md` §3.1's definition). For a symbol whose value is its IPLT (or, M2, PLT) entry, that entry's address. `SHN_ABS`: its `st_value`. Undefined weak: §7 |
| `A` | `r_addend` |
| `P` | the address of the place, `addr(section) + r_offset` |
| `X` | the computed value before the field takes its bytes |
| `Z` | the symbol's `st_size` |
| `GOT` | the address of `_GLOBAL_OFFSET_TABLE_`: the start of `.got.plt` (`Facts.got_base = GotPltStart`, §10.2) |
| `G(GDAT(S))` | the address of the GOT slot holding `S`'s address |
| `G(GTPREL(S))` | the address of the GOT slot holding `S`'s TP offset |
| `L` | the PLT (M2) or IPLT entry of `S` when it has one, else `S` |
| `TpRel(x)` | `x − tls.start − align_up(tls.size, tls.align)` (variant II, §12) |
| `DtpRel(x)` | `x − tls.start` |

- **X-4 [M1] Addends.** x86-64 addends are free: every row's `A` column
  is "any". The GOT forms add `A` outside the slot
  (`X = G(GDAT(S)) + A − P`, `add_a`); the slot holds `S`, never
  `S + A` (psABI `G + GOT + A − P`). The census has `A = −4` (the usual
  rel32 bias), `−5` (`cmpq $0, x@GOTPCREL(%rip)`: an imm8 follows the
  field) and arbitrary `TPOFF32` addends (libgomp).

### 3.2 Fields

x86 instructions are variable-length; every field is a little-endian
data field at `P`:

| form | bytes at `P` | used by |
|---|---|---|
| `d64` | 8 | 1, 17, 18, 24, 25, 27, 29, 31, 33 |
| `d32` | 4 | 2, 4, 9, 10, 11, 19–23, 26, 32, 34, 41, 42 |
| `d16` | 2 | 12, 13 |
| `d8` | 1 | 14, 15 |
| `none` | 0 (a marker) | 0, 35 |

- **X-5 [M1] Fields are data.** `apply` writes only the field's bytes,
  except in a matched relaxation (§8), which writes exactly the bytes of
  its window. `Field::Insn` is not used on x86-64; a field never needs
  its instruction decoded.

### 3.3 Checks

| check | range of `X` | types |
|---|---|---|
| `s(32)` | [−2^31, 2^31 − 1] | 2, 4, 9, 11, 19–23, 26, 34, 41, 42 |
| `u(32)` | [0, 2^32 − 1] | 10, 32 |
| `su(16)` | [−2^15, 2^16 − 1] | 12 |
| `s(16)` | [−2^15, 2^15 − 1] | 13 |
| `su(8)` | [−2^7, 2^8 − 1] | 14 |
| `s(8)` | [−2^7, 2^7 − 1] | 15 |
| `none` | — | the 64-bit types |

- **X-6 [M1] Overflow is an error.** A value outside its check is
  `relocation-out-of-range` (`spec/diag.md`; message §9), never a
  truncated write. The psABI says the linker "must verify" that the
  32-bit forms fit; for `16` and `8` (psABI: "not conformant") mortar
  checks `su` as lld does. GNU ld's bitfield check accepts and truncates
  `16` down to −65536 and `8` down to −256, and accepts `PC16` at both
  +32768 and −32769 (E12; §14.2). mold checks `16` and `8` unsigned
  (`[0, 65536)`, `[0, 256)`), stricter than both (E12).
- **X-7 [M1] `SIZE32` is `u(32)`.** GNU ld and mold refuse `SIZE32` =
  −1; lld writes it (E7). The value is a size: unsigned.

### 3.4 Instruction bytes (no mapping symbols)

x86-64 has no mapping symbols and no way to find instruction boundaries
except through relocations.

- **X-8 [M1] Bytes are read only inside a window.** A relaxation reads
  and writes only bytes inside its record's window (§8.6) around `P`;
  nothing outside a relocation window is ever decoded or rewritten
  (`spec/arch.md` apply rule 1). The bytes before `P` are read as the
  form's prefix; the form decides whether they are the expected opcode.
  A window that would reach before the start of the section or past its
  end does not match (the relocation is applied unrelaxed, or refused
  where §8 says so).

## 4. Targets and outputs

Target kinds and output kinds are `spec/arch.md` §4.1's: `local`, `abs`,
`ifunc`, `weak0` (and, M2, `pre`, `shlib`, `weakdyn`); outputs `static`
(non-PIE), `static-pie` (`Pie` without a dynamic loader), `exec`,
`pie`, `shared`. `static-pie` follows the `Pie` rows of §5 with every
target in this output. A weak undefined key is `weakdyn` or `weak0` by
`spec/dyn.md` D-25, per key; the x86-64 column of D-25's class table,
with the branch-opcode test, is X-57 (§7).

- **X-9 [M1] Static-pie is position-independent.** In `static-pie` an
  absolute address in an alloc section needs `R_X86_64_RELATIVE`
  (written by the generic machinery, `spec/synth.md`), and any rewrite
  that bakes a link-time absolute address into code (§8.1's immediates,
  the `mov $imm` of GNU ld) is not taken. Measured: the three reference
  linkers produce static-pie outputs whose only dynamic relocations are
  `RELATIVE`, `IRELATIVE` and `NONE` (E10).

- **X-10 [M1] One class per type.** The class is a function of the type
  alone (the table above), and the demand of a record is §4.3's cell
  for (class, output, target), adjusted only by a relaxation that a §8
  rule takes (kind 1 removes the demand; kind 2 keeps it).
- **X-11 [M1] TLS classes in a static output.** Every TLS target of a
  static link is defined in the output (static has no TLS-dynamic
  target), so: `TlsGd` and `TlsLd` are always relaxed to LE (§8.3, §8.4)
  and demand nothing; `TlsIe` demands a `GTPREL` slot unless relaxed
  (§8.2); `TlsDesc` is always relaxed to LE (§8.5); `TlsLe` and
  `TlsDtpRel` demand nothing. A non-TLS class against a TLS symbol, or a
  TLS class against a non-TLS symbol, is `E` at an alloc place. At a
  non-alloc place `AbsWord`/`AbsNarrow` against a TLS symbol is accepted
  and writes `DtpRel(S + A)` (X-53, GCC `-gsplit-dwarf`).

## 7. Undefined weak

For `weak0` (undefined, weak, not dynamic):

| relocation | what is written |
|---|---|
| `AbsWord`, `AbsNarrow` | `X = 0 + A` (`S = 0`); in `Pie` with no `RELATIVE` |
| `Pc` | static: `X = 0 + A − P`; `Pie`: `E` (X-15) |
| `Branch` (`PLT32`) | `X = 0 + A − P`: a call or jump to address 0 |
| `PLTOFF64` | `X = 0 + A − GOT` |
| `GOTOFF64` | `E` (`GotRel` against `weak0`, arch.md §4.3; X-16) |
| `Got` | the slot holds 0, with no dynamic relocation; never relaxed (§8.1) |
| `Size` | `X = 0 + A` |
| TLS classes | the symbol is TLS-local with offset 0: `TpRel = A`, `DtpRel = A`; relaxed forms write `T = 0` |

- **X-15 [M1] `Pc` against `weak0` in `Pie` is an error.** In
  `static-pie`, a PC-relative reference to `weak0` would need the run-time
  value `0 − (B + P)`, which depends on the load address; no relocation
  can express it, so mortar raises `relocation-incompatible` (reason
  `recompile with -fPIE`, in `Shared` `recompile with -fPIC`: arch.md
  §10's reasons for an `E` cell, GNU ld's text; WP-029r). This is mold's behavior ("can not be
  used; recompile with -fPIC"). GNU ld refuses it too ("relocation
  R_X86_64_PC32 against undefined symbol `wd' can not be used when making
  a PIE object; recompile with -fPIE", E13); lld 19 and 22 write the link-time
  value (`lea -0x127b(%rip)`, `.long wd-.` = −P), which at run time is
  the image base, not 0: wrong code (E9). mold linked every glibc
  static-pie program of E6, so the rule does not fire on real code.
  Request R-6 amends arch.md §4.3.
- **X-16 [M1] `Branch` against `weak0` stays `S = 0`.** (In `exec` and
  `pie` [M2] a key whose only uses are branches is `weak0` by X-57 and
  takes this rule too; a branch against a `weakdyn` key goes through a
  PLT entry.) In static and
  static-pie a call to an undefined weak function is a call to address 0
  (`e8` to 0; in static-pie the displacement is computed at link time,
  so the call goes to `B`, which is never executed because glibc guards
  such calls through a GOT slot that holds 0). All three references
  write 0 in static (E9). `PLTOFF64` against `weak0` is `A − GOT` (E9,
  all three). `GOTOFF64` against `weak0` is `E` (arch.md §4.3). The
  three references write `A − GOT` (E9): correct in static non-PIE (the
  code adds `GOT` back and gets `A`, normally 0) but wrong in static-pie,
  where `GOT` moves with the load address and the sum is `B + A`. No
  producer emits it (GCC and Clang reach undefined weak hidden symbols
  through `GOT64`/`REX_GOTPCRELX`, review finding 11), so one rule for
  both outputs is the error.
- **X-17 [M1] GOT forms against `weak0`.** The slot holds 0 in both
  static and static-pie, with no `RELATIVE`. The reference is never
  relaxed: lld keeps the GOT load (slot 0); GNU ld rewrites it to
  `mov $0` (static and static-pie) and mold to a `lea` of address 0
  (static) (E2, E9). Both rewrites are correct in static; GNU's is
  correct in static-pie only because the value is absolute. Keeping the
  slot is correct everywhere and is what glibc's weak checks
  (`cmpq $0, x@GOTPCREL(%rip)`) expect.
- **X-18 [M1] Thread-local `weak0`.** The TP offset and the DTP offset
  are 0, so `TPOFF32`/`TPOFF64` write `A`, an IE slot holds 0, every
  relaxed GD/LD/IE/TLSDESC form writes `T = 0`, and `DTPOFF*` write
  `A`. This is lld's choice; GNU ld and mold write `TpRel(0)`, a large
  meaningless offset (E2: 0xffffffffffbfd020 for GNU ld). No conforming
  program dereferences it: glibc reaches `_nl_current_LC_*` only after
  the `cmpq $0, …_used@GOTPCREL` check of §2.

- **X-57 [M2] `weakdyn` or `weak0`: x86-64's column of `spec/dyn.md`
  D-25.** D-25 is normative; `weak_use` (arch.md §3.12) implements this
  column. In `exec` and `pie`, each live relocation naming a weak
  undefined key is in one class; a type not listed is unfillable:

  | class | types |
  |---|---|
  | GOT | `GOTPCREL`, `GOTPCRELX`, `REX_GOTPCRELX`, `GOT64` (§8.1's relaxations are off for a `weakdyn` key) |
  | absolute word in a writable place | `64` |
  | branch | `PLT32`, `PLTOFF64`; `PC32` on a branch opcode |
  | unfillable | `64` in a non-writable place; `32`, `32S`, `16`, `8`, `PC32` not on a branch opcode, `PC16`, `PC8`, `PC64`, `GOTOFF64`, every TLS type |
  | no use of the key | `NONE`, `SIZE32`, `SIZE64` (the value is `Z + A`, 0), `GOTPC32`, `GOTPC64` (they name `_GLOBAL_OFFSET_TABLE_`) |

  A writable place is one whose output section has `SHF_WRITE` (RELRO
  included). **The branch-opcode test:** a `PC32` is on a branch opcode
  when the input section's bytes before the place are `e8` (call) or
  `e9` (jmp) at offset −1, or `0f 80`…`0f 8f` (jcc rel32) at offset −2,
  inside the same input section; anything else, a `PC32` at offset 0 or
  1 of its section included, is not. A key with a GOT or writable-`64`
  use and no unfillable use is `weakdyn`: `.dynsym` `WEAK UND`, its
  `GDAT` slots `GLOB_DAT`, its `64` words an `R_X86_64_64` record, every
  branch through a PLT entry with a `JUMP_SLOT` (no `.plt.got`, D-49). A
  key with a TLS-class use is refused by name in `exec` and `pie` at M2
  (thread-local undefined weak; `spec/dyn.md` D-25; X-18 is static
  links'); any other key with an unfillable use is `weak0` in `exec` and refused in `pie`,
  once per key, `weak-undefined-pc-in-pie` (D-25: only `-fno-pic`
  objects produce one, on weak data, always with an `R_X86_64_32` all
  three references refuse in a PIE). A key with branches only is
  `weak0` (X-16).

## 8. Relaxations

A relaxation rewrites the bytes of one record's window (§8.6) so that
the instruction no longer goes through the GOT or the TLS runtime.
`kind 1` and `kind 2` are `spec/arch.md` §5.2's: kind 1 is decided from
the output kind, the target kind and the input bytes at scan (the demand
it would have raised is not raised); kind 2 also depends on an address
and is decided at apply (the GOT slot stays demanded, possibly unused).

`REX'` below is the input REX prefix with REX.R moved to REX.B (`48` →
`48`, `4c` → `49`), because the register moves from ModRM.reg to
ModRM.rm. `reg` is the input ModRM's reg field (bits 5..3).

| id | input (bytes before and at `P`) | when | output | kind | status |
|---|---|---|---|---|---|
| G1 | `REX_GOTPCRELX`, `48\|4c 8b` ModRM `00 reg 101` (mov) | target local, A = −4, `S + A − P` in s(32) | `8d` at `P − 2` (lea); field `S + A − P` | 2 | M1 |
| G2 | `GOTPCRELX`, `8b` ModRM `00 reg 101` (32-bit mov) | as G1 | `8d` at `P − 2`; field `S + A − P` | 2 | M1 |
| G3 | `GOTPCRELX`, `ff 15` (call) | as G1 | `67 e8` at `P − 2`; field `S + A − P` | 2 | M1 |
| G4 | `GOTPCRELX`, `ff 25` (jmp) | as G1 | `e9` at `P − 2`, rel32 `S + A − P + 1` at `P − 1`, `90` at `P + 3` | 2 | M1 |
| G5 | `REX_GOTPCRELX`, `48\|4c` op ModRM `00 reg 101`, op ∈ {`03`, `0b`, `13`, `1b`, `23`, `2b`, `33`, `3b`} | static and `exec` (non-PIE) only; target local, not abs; A = −4; `S` in [0, 2^31) | `REX' 81 (c0 \| (op & 38) \| reg) imm32`, imm32 = `S` | 2 | M1 |
| G6 | `REX_GOTPCRELX`, `48\|4c 85` ModRM `00 reg 101` (test) | as G5 | `REX' f7 (c0 \| reg) imm32`, imm32 = `S` | 2 | M1 |
| I1 | `GOTTPOFF`, `48\|4c 8b` ModRM `00 reg 101` (mov) | every executable kind; A = −4; target TLS, defined in the output, or TLS `weak0` (`T = 0`) | `REX' c7 (c0 \| reg) T` | 1 | M1 |
| I2 | `GOTTPOFF`, `48\|4c 03` ModRM `00 reg 101` (add) | as I1 | `REX' 81 (c0 \| reg) T` | 1 | M1 |
| D16 | `TLSGD` 16-byte forms | every executable kind, target defined in the output | `64 48 8b 04 25 00 00 00 00 48 8d 80 T` | 1 | M1 |
| D22 | `TLSGD` 22-byte form | as D16 | `64 48 8b 04 25 00 00 00 00 48 8d 80 T 66 0f 1f 44 00 00` | 1 | M1 |
| L12, L13, L22 | `TLSLD` forms | every executable kind | §8.4 | 1 | M1 |
| T1 | `GOTPC32_TLSDESC`, `48\|4c 8d` ModRM `00 reg 101` (lea) | every executable kind, target defined in the output | `REX' c7 (c0 \| reg) T` | 1 | M1 |
| T2 | `TLSDESC_CALL`, `ff 10` at `P` | every executable kind (independent of T1 and of the target) | `66 90` at `P` | 1 | M1 |
| N16 | `TLSGD` 16-byte forms (GD16, GD16x) | `exec`, `pie`; target a `shlib` TLS key | `64 48 8b 04 25 00 00 00 00 48 03 05 <rel32>` (`mov %fs:0, %rax; add x@gottpoff(%rip), %rax`) over `[P − 4, P + 12)`, rel32 at `P + 8` = `G(GTPREL(S)) − (P + 12)` (X-58) | 1 | M2 |

### 8.1 GOTPCRELX family

- **X-19 [M1; M2 for `exec`, `pie`] GOT load → address (G1–G4).** In every output kind (arch.md A.2; `spec/dyn.md` D-46, request R-X1) a
  `GOTPCRELX`/`REX_GOTPCRELX` record whose bytes match G1–G4 is rewritten
  when the target is `local` (defined in a live section of this output;
  not `abs`, not `ifunc`, not `weak0`), `A = −4`, and the new
  PC-relative field fits s(32); otherwise it is applied unrelaxed (the
  GOT slot exists in every case: kind 2). These are lld's forms (E2:
  `lea`, `67 e8`, `e9 … 90`, in static and static-pie). The psABI allows
  the rewrite only for the `X` types: they promise the assembler wrote
  one of these instructions.
- **X-20 [M1; M2 for `exec`] GOT load → immediate (G5, G6), non-PIE
  only.** In a static or `exec` (non-PIE) output (`spec/dyn.md` D-46,
  request R-X1; never in `pie` or static-pie, whose `S` moves with the
  load address), a `REX_GOTPCRELX` binary operation or `test` whose
  target is `local` and not `abs`, with `A = −4` and `S` in [0, 2^31),
  becomes the immediate form: the value the GOT slot would hold is `S`,
  and `81 /n` and `f7 /0` sign-extend their imm32. GNU ld and lld both
  write exactly these bytes in static (E2: `48 81 c0+n`, `48 f7 c0+r`,
  for each of `add adc and cmp or sbb sub xor test`); mold leaves them.
  The `mov` is **not** turned into `mov $imm` (GNU ld's choice): G1's
  `lea` is correct in both output kinds and is one rule.
- **X-21 [M1] Anything else keeps the GOT.** A `GOTPCRELX` or
  `REX_GOTPCRELX` whose bytes match no form, or whose condition fails,
  is applied as its §6.1 row; it is never refused. Measured: none of the
  three references refuses an unmatched `GOTPCRELX` (E2).
- **X-22 [M1] `abs`, `ifunc` and `weak0` keep the GOT.** For `abs`
  (`abs1 = 0x1234`, `absbig = 0x123456789`) GNU ld writes `mov $0x1234`
  in static and static-pie, mold writes a PC-relative `lea` in static
  only, lld keeps the GOT; for `ifunc` all three keep the GOT; for
  `weak0` see X-17 (E2). Keeping the slot is correct in every output kind
  and costs one load.

### 8.2 IE → LE (`GOTTPOFF`)

- **X-23 [M1; M2 for `exec`, `pie`] IE → LE.** In every executable
  kind (static, static-pie, `exec`, `pie`: `spec/dyn.md` D-48, request
  R-X2) every `GOTTPOFF` against a TLS key defined in the output (or a
  thread-local `weak0`) whose bytes match I1 or I2, with `A = −4`, is
  rewritten with
  `T = TpRel(S)` (check s(32)), and `T = 0` for a thread-local `weak0`
  (X-18), so `mortar_x64` and the verifier agree on the bytes; its `GTPREL` demand is not raised (kind
  1, decided at scan from the bytes). The `add` becomes `add $T`
  (arch.md A.5), not GNU ld's and lld's `lea T(%reg), %reg` (`48 8d 80+r`,
  with `REX' 81 c0+r` for `%rsp`/`%r12`, whose `lea` would need a SIB
  byte) (E2): one form for every register. `add $T` reproduces the
  original instruction exactly, result **and** flags (the input `add`
  set them from the same sum); the references' `lea` leaves the flags
  unchanged, a divergence mortar does not copy (§14.2, D1). Measured by
  the review harness's `genrelax.py` (216 self-checking sites, every
  register): under GNU ld and lld 14 `I2 add` checks differ on RFLAGS;
  with this rule's bytes written in (`patchmortar.py`), 0 of 216 differ.
- **X-24 [M1] An unrecognized `GOTTPOFF` keeps IE.** Any other
  instruction at a `GOTTPOFF` (E2's `ODD` case: `movq x@gottpoff(%rip),
  %xmm0`, and `subq`) keeps the `GTPREL` slot holding `TpRel(S)`; it is
  never refused. [M2] A `GOTTPOFF` against a `shlib` TLS key is never
  relaxed: its `GTPREL` slot holds 0 with a `TPOFF64` record against the
  key (`spec/dyn.md` D-48). mold does this; GNU ld refuses ("TLS transition from
  R_X86_64_GOTTPOFF to R_X86_64_TPOFF32 against `ie' at 0x124 in section
  `.text' failed") and lld refuses ("R_X86_64_GOTTPOFF must be used in
  MOVQ or ADDQ instructions only") (E2, re-run with the `.reloc` at the
  right byte). The census has only I1/I2 bytes, so this rule is for
  hand-written assembly.

### 8.3 GD → LE (`TLSGD` sequences)

The general-dynamic sequence calls `__tls_get_addr` with `%rdi` pointing
at a `tls_index`; in a static output it becomes the TP-relative address
directly (TLS §4.3; psABI "TLS" relaxations). A `TLSGD` is a sequence
lead (`Facts.seq_leads = [19, 20]`, arch.md §3.5); its follower is the
call's relocation, the next record (§2: always).

| form | input | follower | output over |
|---|---|---|---|
| GD16 | `66 48 8d 3d [TLSGD at P] 66 66 48 e8 [rel32]` | `PLT32` or `PC32` at `P + 8` | `[P − 4, P + 12)` |
| GD16x | `66 48 8d 3d [TLSGD at P] 66 48 ff 15 [rel32]` | `GOTPCRELX` or `GOTPCREL` at `P + 8` | `[P − 4, P + 12)` |
| GD22 | `48 8d 3d [TLSGD at P] 48 b8 [imm64] (48\|4c) 01 (c0 \| r << 3) ff d0` | `PLTOFF64` at `P + 6` | `[P − 3, P + 19)` |

- **X-25 [M1; M2 for `exec`, `pie`] GD → LE.** In every executable kind
  (`spec/dyn.md` D-48, request R-X2), against a TLS key defined in the
  output, a `TLSGD` lead whose
  window matches GD16, GD16x or GD22 (the follower of the listed type at
  the listed offset, against `__tls_get_addr`, and `A = −4`) writes
  D16 or D22 of §8 with `T = TpRel(S)` at `P + 8` (GD16, GD16x) or
  `P + 9` (GD22). The follower is consumed: it writes nothing, raises no
  `PLT`, GOT or `IPLT` demand, and its undefined `__tls_get_addr` is not
  an `undefined-symbol` error (arch.md §3.5). D16 is the psABI's form and
  all three references write it for GD16/GD16x (mold uses `48 81 c0 T`,
  an `add`, in place of `48 8d 80 T`) (E2). D22 is GNU ld's (E2:
  `64 48 8b 04 25 00 00 00 00; 48 8d 80 T; 66 0f 1f 44 00 00`); mold
  writes the same with its `add`; **lld 19 and 22 write 16 bytes from
  `P − 4` and leave `00 00; 4c 01 f8; ff d0`**, and the program
  segfaults (E2 bytes; E6 `gd.c` under qemu, static and static-pie, while
  GNU ld's and mold's outputs print "GD ok 4 7"; and in a PIE and a
  `-no-pie` executable, where GNU ld's, mold's and mortar's print "GD ok
  7": WP-083, `spec/dyn.md` §13.2 W17).
  The `PC32` and plain-`GOTPCREL` followers are real: GCC 14 with
  `-fPIC -fno-plt -Wa,-mrelax-relocations=no` (every `-O` level) writes
  GD16x and LD13 bytes with a `GOTPCREL` follower, and an assembler
  that does not emit `PLT32` for `call __tls_get_addr` writes `PC32`.
  GNU ld, lld 19/22 and mold link both and the programs print the same
  TP offsets, static and static-pie (E13: `linkrun.sh gdnoplt` of the
  review harness, and `pc32f.s`, which prints "pc32 follower 31" under
  all three). The bytes, and so the output, are those of the `PLT32` and
  `GOTPCRELX` forms.
- **X-26 [M1] An unmatched GD or LD is refused by name.** A `TLSGD` or
  `TLSLD` lead that matches no form of §8.3/§8.4 in a static or
  static-pie output is `relocation-incompatible` with the feature name
  `unrecognized general-dynamic TLS sequence` / `unrecognized
  local-dynamic TLS sequence` (arch.md A.4) and the place. A static link
  has no `__tls_get_addr` to call (§2). [M2] In `exec` and `pie` an
  unmatched `TLSLD` is refused the same way; an unmatched `TLSGD` against
  a `shlib` key keeps its call and its `GTLSIDX` pair, with `DTPMOD64` +
  `DTPOFF64` records against the key (`spec/dyn.md` D-48), and against a
  key defined in the output it is refused as in static (D-48 relaxes
  every model against the executable's own TLS; supervisor's ruling after
  WP-040r). WP-048 must show that every GD form the census compilers
  emit (`-fno-plt` included) matches a form of §8.3; an unmatched census
  form is a finding. An unmatched GD in a shared object is
  kept with its `GTLSIDX` pair [M4].

### 8.4 LD → LE (`TLSLD` sequences)

| form | input | follower | LE output | over |
|---|---|---|---|---|
| LD12 | `48 8d 3d [TLSLD at P] e8 [rel32]` | `PLT32` or `PC32` at `P + 5` | `66 66 66 64 48 8b 04 25 00 00 00 00` | `[P − 3, P + 9)` |
| LD13 | `48 8d 3d [TLSLD at P] ff 15 [rel32]` | `GOTPCRELX` or `GOTPCREL` at `P + 6` | `66 66 66 66 64 48 8b 04 25 00 00 00 00` | `[P − 3, P + 10)` |
| LD22 | `48 8d 3d [TLSLD at P] 48 b8 [imm64] (48\|4c) 01 (c0 \| r << 3) ff d0` | `PLTOFF64` at `P + 6` | `66 66 66 66 2e 0f 1f 84 00 00 00 00 00 64 48 8b 04 25 00 00 00 00` | `[P − 3, P + 19)` |

- **X-27 [M1; M2 for `exec`, `pie`] LD → LE.** In every executable kind
  (`spec/dyn.md` D-48, request R-X2) a matching `TLSLD`
  lead (follower as in X-25, `A = −4`) writes its LE output, which
  leaves `%rax` = TP (the module's base becomes TP), and every
  `DTPOFF32`/`DTPOFF64` in an `SHF_EXECINSTR` section is `TpRel` (X-46). LD12 and
  LD13 are GNU ld's and lld's (E2; arch.md A.4); LD22 is GNU ld's (E2).
  mold writes `31 c0; 64 48 8b 00; 48 2d <tls size>` (with a `48 31 c0`
  variant) and keeps `DTPOFF32` = `DtpRel`, a different convention that
  computes the same addresses; lld refuses LD22 ("expected
  R_X86_64_PLT32 or R_X86_64_GOTPCRELX after R_X86_64_TLSLD") (E2, E6).
  This answers image.md R-14 (both 22-byte forms are added) and arch.md
  Q7 for LD.

### 8.5 TLSDESC → LE

- **X-28 [M1; M2 for `exec`, `pie`] TLSDESC → LE.** In every executable
  kind (`spec/dyn.md` D-48, request R-X2), against a key defined in the
  output (or `_TLS_MODULE_BASE_`), each member
  rewrites independently (arch.md A.6): a `GOTPC32_TLSDESC` matching T1
  (`A = −4`) becomes `REX' c7 (c0 | reg) T`, and a `TLSDESC_CALL` with
  `ff 10` at `P` becomes `66 90`. `T = TpRel(S)`, except
  `T = 0` for `_TLS_MODULE_BASE_` (X-47). All three references write
  these bytes for `%rax`, `%rbp` and `%r12` destinations (E2:
  `48 c7 c0`, `48 c7 c5`, `49 c7 c4`). A member that does not match is
  `relocation-incompatible` (`unrecognized TLS descriptor sequence`):
  a static output has no descriptor runtime, and in `exec` and `pie`
  mortar writes no `TLSDESC` record on x86-64 (§6.2).
- **X-58 [M2] GD → IE and TLSDESC → IE (N16, N22, N1).** In `exec` and
  `pie`, against a TLS key whose definition is in a shared object
  (`spec/dyn.md` D-48: IE): a `TLSGD` lead matching GD16 or GD16x writes
  N16 and one matching GD22 writes N22 (the follower consumed as in
  X-25, no `PLT` demand); a `GOTPC32_TLSDESC` matching T1 writes N1 and
  its `TLSDESC_CALL` writes T2's `66 90`. Each raises `GOT_TPREL` (the
  `GTPREL` slot of X-24's M2 sentence: 0 with a `TPOFF64` record against
  the key). The windows are D16's, D22's and T1's (§8.6), so `max_reach`
  is unchanged. Measured (2026-11-15, x86-64 cross GCC 14 `-fPIC -O1`,
  `-mtls-dialect=gnu` / `gnu2`, `-fno-plt`, `-mcmodel=large`, against a
  shared `__thread int tlsx`, PIE and `-no-pie`, run under qemu): GNU ld
  writes exactly N16 (GD16 and GD16x), N22 and N1 (destination `%rax`,
  and every register by the same ModRM, run: WP-082's `tlsdesc-regs`,
  GNU ld, lld, mold; GCC 14's `%rbp` in `__once_call`), and the programs
  print the right value and address; lld writes N16 and N1 too, and for
  GD22 leaves the bytes of its broken GD22 → LE (X-25) and the program
  segfaults. A sequence that does not match is X-26 (GD) or X-28
  (TLSDESC).
- GCC and Clang both use `_TLS_MODULE_BASE_` for
  `-mtls-dialect=gnu2 -ftls-model=local-dynamic` (E6 `-fno-plt`/gnu2
  LD variants, both compilers), which answers arch.md Q7.

### 8.6 Windows, `sequence_extent` and `max_reach`

A window `(before, after)` is the bytes a record's `apply` may read or
write outside its field: `[P − before, P + width + after)`.

| record | window | why |
|---|---|---|
| every unrelaxable row | (0, 0) | field only |
| G1, G5, G6 (`REX_GOTPCRELX`) | (3, 0) | REX at `P − 3` |
| G2, G3, G4 (`GOTPCRELX`) | (2, 0) | opcode and ModRM at `P − 2`, `P − 1` |
| I1, I2 (`GOTTPOFF`) | (3, 0) | REX at `P − 3` |
| T1 (`GOTPC32_TLSDESC`) | (3, 0) | REX at `P − 3` |
| T2 (`TLSDESC_CALL`) | (0, 2) | `ff 10` at `P`, a zero-width field |
| GD16, GD16x lead | (4, 8) | `[P − 4, P + 12)` |
| GD22 lead | (3, 15) | `[P − 3, P + 19)` |
| LD12 lead | (3, 5) | `[P − 3, P + 9)` |
| LD13 lead | (3, 6) | `[P − 3, P + 10)` |
| LD22 lead | (3, 15) | `[P − 3, P + 19)` |
| a consumed follower | (0, 0), writes nothing | |

- **X-29 [M1] `max_reach` = (4, 15).** The maximum `before` is 4
  (GD16) and the maximum `after` is 15 (GD22, LD22); `mortar_arch`
  derives it from the table (image.md I-111). image.md I-111 and arch.md
  §3.1 said `(4, 8)`; requests R-1 and R-2 corrected them (applied).
- **X-30 [M1] `sequence_extent`.** For a lead at record `i` (types 19,
  20; look-back 1), the extent is 2 when record `i + 1` is a follower
  the form allows (type and offset, §8.3, §8.4: `PLT32` or `PC32` after
  an `e8`, `GOTPCRELX` or `GOTPCREL` after `ff 15`, `PLTOFF64` after
  `48 b8`) and 1 otherwise; with extent 1 the lead does not match (X-26). A follower
  type never starts a sequence of its own.

### 8.7 Not relaxed

- **X-31 [M1] Plain `GOTPCREL` is never relaxed.** Type 9 carries no
  promise about the instruction (it is also emitted for `cmpq $0` with
  `A = −5`, `pushq` `ff 35` and `-mrelax-relocations=no` movs, §2). lld
  and mold leave it; GNU ld rewrites a plain-`GOTPCREL` `mov` to `lea`
  (E2), which mortar does not.
- **X-32 [M1] Not taken in M1:** the `GOTPCRELX` immediate forms in
  static-pie and `pie` (X-9); 32-bit (`GOTPCRELX`, non-REX) binary operations
  (GNU ld relaxes them, `f7 c0` / `81 c0`; lld does not; E2; Q5);
  relaxations against `ifunc`, `abs`, `weak0`, `weakdyn`, `shlib`
  (X-22, X-57); any relaxation of a record in a non-alloc section; the
  APX forms (later, X-13). GD → IE and TLSDESC → IE are M2 (X-58).

## 9. Range

- **X-33 [M1] No thunks.** x86-64 calls and jumps have a rel32 (±2 GiB).
  In the small model the psABI requires all code and static data within
  2 GiB; in the medium model it requires that of the code and the small
  data, while large data (X-52) may lie anywhere and is reached through
  64-bit relocations or the GOT; in the large model nothing is assumed.
  Code is never larger than the small sections' 2 GiB in the targets'
  programs, so no range-extension thunk exists (`Facts.thunks = none`);
  X-54 keeps the small sections together whatever the large sections'
  size. A `PC32`/`PLT32`/`GOTPCREL*` that does
  not fit is `relocation-out-of-range`. The large model's 64-bit types
  (`PC64`, `GOTOFF64`, `GOTPC64`, `GOT64`, `PLTOFF64`) have no check.
- **X-34 [M1] The out-of-range message contains "relocation truncated to
  fit".** The diagnostic keeps lld's value and bounds and adds GNU ld's
  greppable phrase, which build scripts and users search for:
  `relocation truncated to fit: {r_type} against '{name}': {value} is
  not in [{min}, {max}]` (request R-5 to `spec/diag.md`). Measured
  messages (E7, `asm/range.s`):
  - GNU ld: `(.text+0x3): relocation truncated to fit: R_X86_64_PC32
    against symbol `far' defined in *ABS* section in ob`;
  - lld: `relocation R_X86_64_PC32 out of range: 4297060001 is not in
    [-2147483648, 2147483647]; references 'far'`;
  - mold: `relocation R_X86_64_PC32 against far out of range: … is not
    in [-2147483648, 2147483648)` (a half-open range).
  `32` is checked `[0, 4294967295]` and `32S` signed by all three (E7).

## 10. Shapes

### 10.1 GOT

- **X-35 [M1] GOT slots.** `.got` holds 8-byte slots, with no header
  word in a static output (`spec/synth.md` orders them). Contents:

| slot | static | static-pie |
|---|---|---|
| `GDAT`, `local` | `S` | `S`, with a `RELATIVE` |
| `GDAT`, `abs` | `S` | `S` |
| `GDAT`, `ifunc` | the IPLT entry | the IPLT entry, with a `RELATIVE` |
| `GDAT`, `weak0` | 0 | 0 |
| `GTPREL` | `TpRel(S)` | `TpRel(S)` |

  The three references write these values (E3, E9, E10). In static-pie
  GNU ld and lld write the same 1326 `RELATIVE` records for the E10
  program; mold writes 1350 (E10).

### 10.2 `.got.plt` and `_GLOBAL_OFFSET_TABLE_`

- **X-36 [M1] `_GLOBAL_OFFSET_TABLE_` is the start of `.got.plt`.** On
  x86-64 the GOT base (`GOT` of §3.1, `Facts.got_base = GotPltStart`) is
  `.got.plt`'s first byte, which in a static output holds 3 reserved
  zero words (`Facts.got_plt_reserved = 3`; `spec/synth.md` S-67),
  followed by one word per IPLT entry. All three references define
  `_GLOBAL_OFFSET_TABLE_` there (E3); mold's `.got.plt` has only the 3
  words (its IFUNC words are in `.got`).

### 10.3 PLT (M2)

The lazy PLT of arch.md A.8, in `.plt` (aligned 16): the header PLT0
(16 bytes) `ff 35 <GOT+8>; ff 25 <GOT+16>; 0f 1f 40 00` (`push
.got.plt[1](%rip); jmp *.got.plt[2](%rip); nopl`), then one 16-byte
entry per PLT key, `ff 25 <word>; 68 <n>; e9 <PLT0>` (`jmp
*word(%rip); push $n; jmp PLT0`), `n` the entry's `.rela.plt` index,
the rel32s relative to the end of their instruction. Each `JUMP_SLOT`
word initially holds the entry's address + 6 (the `push`: the lazy
target, `lazy_target(n) = EntryPlus(6)`, `spec/dyn.md` D-49; in a PIE
the loader adds the bias), and `.got.plt[0]` holds `_DYNAMIC` (D-32).
IPLT entries (X-37) follow the PLT entries. Under `-z now` the bytes are
the same (D-49). **Measured** (`spec/dyn.md` E-reloc §6, and again
2026-11-15 with x86-64 cross GCC 14, PIE and `-no-pie`): GNU ld and lld
write these bytes byte for byte, with the entry + 6 word; mold uses PLT0
with the index in `%r11d`. The IBT shapes (`.plt` lazy entries `f3 0f 1e
fa; 68 <n>; e9 <PLT0>; 66 90` and `.plt.sec` entries `f3 0f 1e fa; ff 25
<word>; 66 0f 1f 44 00 00`, arch.md A.8) stay refused at M2 (`-z ibt`,
`-z ibtplt`; D-49, `spec/dyn.md` §15 Q4).

### 10.4 IPLT and IRELATIVE

- **X-37 [M1] Plain IPLT entry.** 8 bytes, `ff 25 <rel32> 66 90`
  (`jmp *word(%rip); xchg %ax,%ax`), `rel32 = word − (entry + 6)`, in
  `.plt` aligned 16 (`spec/synth.md` S-68). This is GNU ld's static entry
  (E3); lld writes 16-byte `ff 25; 68 n; e9` entries in `.iplt`, mold
  8-byte `ff 25 …; cc cc` in `.plt.got` (E3).
- **X-38 [M1] IBT IPLT entry.** When the output's `FEATURE_1_AND` has
  IBT (§11, after `-z ibt`) or with `-z ibtplt`: 16 bytes
  `f3 0f 1e fa ff 25 <rel32> 66 0f 1f 44 00 00` (`endbr64; jmp
  *word(%rip); nopw`), `rel32 = word − (entry + 10)`. GNU ld (`-z ibt`,
  `-z ibtplt`) and lld (`-z force-ibt`) write exactly this (E3). **mold
  2.37.1 marks the output IBT and writes entries without `endbr64`**
  (E12, `asm/iplt-ibt.s`, every input IBT|SHSTK): an indirect call to the
  IFUNC faults under IBT enforcement (§14.2).
- **X-39 [M1] The IPLT word and its `IRELATIVE`.** Each entry's
  `.got.plt` word is written 0 (`spec/dyn.md` §15 Q7, ruled per
  architecture: on x86-64 the word stays 0; plumb F5(3)) and has one `R_X86_64_IRELATIVE` with
  `r_offset` the word and `r_addend` the resolver (`spec/synth.md` S-69,
  S-70; `__rela_iplt_start`/`__rela_iplt_end` bracket them in a static
  output). Measured (E3, E12, E13 `e13/ifn.c`): GNU ld writes the word as
  the entry's address + 6 (0x401006, 0x40100e: the lazy-PLT convention),
  not 0 as S-69 said GNU does (request R-8, applied); lld writes 0; mold keeps its
  IFUNC words in `.got` and writes the resolver's address (the addend)
  there. With an IBT IPLT (X-38 entries; WP-028c, `crates/mortar_plumb/tests/x64/iplt-ibt.s`, with and without `-z ibt`) GNU ld writes the entry's own address (0x401000, 0x401010), not entry + 6, and a word that only a GOT load reaches (`movq ifn@GOTPCREL`, a `.got` slot with no IPLT entry) holds 0.
  All three set `r_addend` to the resolver. The initial value is
  never read: glibc's static start-up (`apply_irel`) calls the resolver
  named by `r_addend` and stores its result in the word. Evidence that 0
  is safe: E13 links `ifn.c` (two local IFUNCs, a pointer to one, glibc's
  `strcpy`/`strlen` IFUNCs) `-static` with GNU ld, overwrites all 24
  IFUNC words of its `.got.plt` with 0, and the program prints the same
  `ifunc 2 3 2 1` as the unpatched output; lld's static outputs, whose
  words are 0, run every glibc program of E6. GNU ld places the static
  `IRELATIVE`s in `.rela.plt`, lld and mold in `.rela.dyn` (E2, E13).
- **X-56 [M1] `IRELATIVE` in static-pie.** In a static-pie output every
  `IRELATIVE` is in `.rela.dyn`, applied by glibc's self-relocation with
  the `RELATIVE`s; there is no `.rela.plt`, and `__rela_iplt_start`/
  `__rela_iplt_end` are not defined, so glibc's weak references are 0
  and the static start-up's range is empty (resolve.md §8.1,
  `spec/synth.md` S-70). Measured (E13 `e13/ifn.c -fPIE -static-pie`): lld 22
  writes 24 `IRELATIVE` in `.rela.dyn`, no `.rela.plt`, and leaves
  `__rela_iplt_*` undefined; GNU ld writes 24 in `.rela.plt` (reached
  through `DT_JMPREL`) and 1 in `.rela.dyn`; mold writes 25 in
  `.rela.dyn` and defines `__rela_iplt_*` as absolute 0. All three
  run. S-70 credited GNU with lld's placement; request R-17 corrected
  it (applied).
- **X-40 [M1] IFUNC references.** A `Pc`, `AbsWord` or `Branch`
  reference to an `ifunc` uses its IPLT entry (`I`, arch.md §4.3); a
  `Got` reference's slot holds the entry (X-35). `PLTOFF64` and `GOT64`
  against an `ifunc` are accepted with `L`/`S` = the entry (lld and mold
  accept them; GNU ld refuses `GOT64` against an IFUNC: "relocation
  R_X86_64_GOT64 against STT_GNU_IFUNC symbol `strlen' isn't supported",
  E6, Clang `-mcmodel=large`). `32S` against an `ifunc` in static-pie is
  `E` (`AbsNarrow`); all three refuse it (E3).

### 10.5 Copy relocations and canonical PLTs (M2)

M2, by arch.md §4.3's `C` cells and `spec/dyn.md` D-42 (copies: in `exec`
and, for `PC32` against shared data from GCC's default `-fPIE` code, in
`pie`, D-43), D-44 (a canonical PLT in `exec` only; refused in `pie`,
`canonical-plt-in-pie`) and D-23 (their `.dynsym` forms). An
`R_X86_64_32`/`32S` against a shared function in `exec` takes a
canonical PLT (D-44).

### 10.6 IFUNCs in `exec` and `pie` (M2)

`spec/dyn.md` D-45: a non-preemptible IFUNC has one IPLT entry, its
address everywhere; a `GDAT` slot of it holds the entry (`exec`) or the
entry with a `RELATIVE` (`pie`), never an `IRELATIVE` of its own; the
IPLT word carries the only `IRELATIVE`, last in `.rela.plt` (D-41).

## 11. GNU properties and CET

- **X-41 [M1] Merge rules.** `property_merge(pr_type)` for the x86
  processor range (binutils `include/elf/common.h`
  `GNU_PROPERTY_X86_UINT32_*`; E4, `mkprop.sh`):

| `pr_type` | rule | measured |
|---|---|---|
| 0xc0000002 `FEATURE_1_AND` (IBT 1, SHSTK 2) and 0xc0000002..0xc0007fff | `And` | GNU, lld and mold: the AND, omitted when 0 (an absent input counts 0; `0xc0000003` is omitted when one input lacks it) |
| 0xc0008002 `ISA_1_NEEDED`, 0xc0008001 `FEATURE_2_NEEDED`, 0xc0008000..0xc000ffff | `Or` | GNU and mold OR 0xc0009000 and 0xc000f000; lld drops them |
| 0xc0010002 `ISA_1_USED`, 0xc0010001 `FEATURE_2_USED`, 0xc0010000..0xc0017fff | `OrAll` | GNU and mold: present only if every input has it (0xc0017000 too); lld drops them |
| 0xc0000000 `COMPAT_ISA_1_USED` | `OrAll`, no warning | GNU: kept only when every input has it; lld and mold drop it (E13) |
| 0xc0000001 `COMPAT_ISA_1_NEEDED` | `Or`, no warning | GNU ORs it (2 \| 4 → "586, 686"); lld and mold drop it (E4, E13) |
| any other x86 type (0xc0018000 and above) | dropped, warning `unknown-property` | GNU warns on 0xc0018000 (review) |

  The two legacy `COMPAT_*` types (binutils `GNU_PROPERTY_X86_COMPAT_*`,
  written by old assemblers) follow GNU's merge, so a mortar output
  carries what a GNU output carries.

  `spec/synth.md` S-95 said the `Or` range ends at 0xc0008fff; E4 shows
  GNU ld and mold OR 0xc000f000, which matches binutils'
  `GNU_PROPERTY_X86_UINT32_OR_HI` = 0xc000ffff (request R-7, applied).
- **X-42 [M1] Static glibc links are not IBT.** libc.a and libm.a carry
  no property note (§2), so the merged `FEATURE_1_AND` of a static glibc
  link is 0 and no property is written, unless `-z ibt`/`-z shstk`
  force bits.
- **X-43 [M1] `-z ibt`, `-z shstk`, `-z ibtplt`, `-z cet-report`.**
  `-z ibt` ORs IBT into the merged `FEATURE_1_AND` (and so selects the
  IBT IPLT, X-38); `-z shstk` ORs SHSTK; `-z ibtplt` selects the IBT
  IPLT without marking; `-z cet-report=none|warning|error` reports each
  live input object lacking IBT or SHSTK in `FEATURE_1_AND`, as the
  warning or error `cet-report` with the text `{path}: missing {IBT |
  SHSTK} property (-z cet-report)` (requests R-10, R-11). GNU ld and
  mold force the bits with `-z ibt`/`-z shstk`; lld knows `-z shstk`,
  spells IBT `-z force-ibt` and warns "unknown -z value: ibt" (E4).
  Measured `cet-report` messages (E4): GNU ld `an.o: error: missing IBT
  and SHSTK properties`; lld `an.o: -z cet-report: file does not have
  GNU_PROPERTY_X86_FEATURE_1_IBT property`; mold `an.o:
  -cet-report=error: missing GNU_PROPERTY_X86_FEATURE_1_IBT`.
- The note is written as `.note.gnu.property` with `PT_GNU_PROPERTY`
  (`spec/synth.md`); all three write `PT_GNU_PROPERTY` when a property

## 12. TLS

- **X-44 [M1] Variant II.** The thread pointer (`%fs:0`) points at the
  TCB, and the TLS block lies just below it:
  `TpRel(x) = x − tls.start − align_up(tls.size, tls.align)`, with
  `tls.start` the `PT_TLS` `p_vaddr`, `tls.size` its `p_memsz` and
  `tls.align` its `p_align` (TLS §3.4.6; arch.md A.11). Measured: for
  `.tbss`/`.tdata` alignments 16, 64 and 4096, with and without
  `.tdata`, all four linkers (GNU ld, lld 19, lld 22, mold) give
  identical TP offsets under qemu, static and static-pie (E5
  `tlslayout.c`; e.g. A = 4096 with `p_memsz` 0x20a8 gives `big` at
  −4096 and `d1` at −0x3000). mold's static-pie outputs pass only when
  written to a fresh file (§14.2 W7).
- **X-45 [M1] LE ranges.** `TPOFF32`, `GOTTPOFF`→LE and every relaxed
  `T` are s(32); `TPOFF64` has no check.
- **X-46 [M1; M2 for `exec`, `pie`] `DTPOFF32` and `DTPOFF64`.** In a section with
  `SHF_EXECINSTR` of an executable output of any kind (`spec/dyn.md`
  D-48, request R-X2), `X = TpRel(S + A)`: that is where a
  relaxed LD sequence (X-27) or a `_TLS_MODULE_BASE_` descriptor (X-47)
  leaves TP as the module base and adds the field to it. In every other
  section, alloc or not, `X = DtpRel(S + A)`: data and debug information
  hold the offset within the TLS block. GNU ld (it tests `SEC_CODE`) and
  mold key on the same thing; lld writes `TpRel` in every alloc section.
  Measured: GNU ld and lld write `TpRel` in code (E2); all three write
  `DtpRel` in `.debug_info` (E2: `.quad ld@dtpoff` and `gd@dtpoff` give
  0x18 and 0); in `.rodata` and `.data`, `.quad`/`.long tx@dtpoff` with
  `tx` at block offset 0x10 gives 0x10 under GNU ld and mold and −0x10
  (`TpRel`) under lld 22 (E13, `e13/d.s`). No producer of either census
  emits `DTPOFF*` in alloc data. In M2 shared outputs `DTPOFF*` are
  `DtpRel` everywhere.
- **X-47 [M1; M2 for `exec`, `pie`] `_TLS_MODULE_BASE_`.** In every executable kind (`spec/dyn.md` D-48, request R-X2). Defined by the linker when
  referenced, hidden, at `tls.start`. Its descriptor's LE value is
  `T = 0` and the `DTPOFF32` fields added to it are `TpRel` (GNU ld and
  lld; arch.md A.4). mold writes `TpRel(tls.start)` and keeps
  `DtpRel` fields; both programs run (E6 gnu2 LD).
  The symbol's value differs (WP-028c: `crates/mortar_plumb/tests/x64/relax.s`'s TLSDESC block, and a 0x28-byte `.tdata` aligned 16, static, run): GNU ld 2.44 defines it at align_up(p_memsz, p_align) (0x30, TP itself, which is the T = 0 it writes), lld 22 at `tls.start` (0), mold 2.37.1 at `tls.start`'s address (plumb.md A3); mortar's rule above is lld's (symbol at `tls.start`, T = 0, `TpRel` fields), and its code runs as lld's does.
  WP-029b: resolution defines it for x86-64 (resolve.md §8.1's row, a
  conditional candidate; before, it was M2 and a reference failed as an
  undefined symbol), `STT_TLS`, local hidden, `.symtab` value 0; the
  bytes are those of GNU ld, whose value differs (T = 0 is by name, X-28),
  and the program prints GNU ld's (`crates/mortar/tests/x64.rs`
  `x64_tls_module_base`).
- **X-48 [M1] Static links have no TLS runtime calls.** After §8 no
  output byte calls `__tls_get_addr` or a descriptor resolver; the
  verifier checks that no `PLT32`/`GOTPCRELX` against `__tls_get_addr`
  survives unconsumed in a static output.

## 13. Other sections, the header and segments

- **X-49 [M1] Header.** `e_machine` = `EM_X86_64` (62), `ELFCLASS64`,
  `ELFDATA2LSB`, `EI_OSABI` by the arch-independent rule (image.md §5.4
  header fields, a64.md Q11 as ruled by WP-027c): `ELFOSABI_GNU` (3)
  when the output has an `STT_GNU_IFUNC` or `STB_GNU_UNIQUE` symbol or
  an `IRELATIVE` record, else `ELFOSABI_NONE` (0); `Facts.osabi` = 0 is
  the second case. This is GNU ld's rule (lld and mold write 0; glibc
  accepts both; E10); WP-029b measured mortar and GNU ld both writing 3
  on the same static IFUNC links. `e_flags` = 0 (no input `e_flags`
  bit is defined; E10: 0 in every reference output).
- **X-50 [M1] Base, pages and fill.** `Facts.image_base` = 0x400000 (GNU
  ld's; lld and mold use 0x200000; a64.md Q12's reason),
  `max_page = common_page = 0x1000` (every reference writes `p_align`
  0x1000; E10), `code_fill` 0xCC (`int3`, lld's and mold's; GNU ld fills
  with multi-byte NOPs, `66 2e 0f 1f 84 …`) and `code_nop` 0x90 (E10,
  `asm/fill.s`). The default is no separate-code (layout L-71); GNU ld
  defaults to separate-code (R/RX/R/RW). Inside `.init` and `.fini`,
  padding between input sections is `code_nop` (0x90), never the trap
  fill (layout L-82): their fragments, from crti to crtn, run in
  sequence. E13 `e13/f2.s` (a `.p2align 4` `.init` fragment after crti):
  GNU ld pads with multi-byte NOPs (`66 2e 0f 1f 84 00 … 0f 1f 40 00`)
  and the program runs; lld 22 and mold 2.37.1 pad with `cc` and the
  program dies with SIGTRAP at start-up (§14.2 W8). GNU ld also fills
  `.text` gaps with multi-byte NOPs, not zeros (request R-14 corrected
  L-82's description, applied).
- **X-51 [M1] `.eh_frame`.** Accepted as `SHT_PROGBITS` or
  `SHT_X86_64_UNWIND` (0x70000001) (§2; `spec/elf.md`,
  `spec/layout.md`, `spec/resolve.md`). Its pointer encodings are
  `0x1b`/`0x9b` (`PC32`), `0x1c`/`0x9c` (`PC64`), `0x03` (`32`) and
  `0x00` (`64`), all ordinary relocations of §6.
- **X-52 [M1] `SHF_X86_64_LARGE` sections are accepted.** An input
  section with `SHF_X86_64_LARGE` (0x10000000) goes to one of four large
  output sections, which keep the flag: `.ltext` (`SHF_EXECINSTR`),
  `.lrodata` (alloc, not writable), `.ldata` (writable `PROGBITS`) and
  `.lbss` (writable `NOBITS`), by its flags and type, whatever its name
  (GCC's `.lbss.*`, `.ldata.*`, `.lrodata.*`, Clang's `.lrodata.str1.1`
  included). A large section with `SHF_TLS` is refused by name (no
  producer emits one). This is required, not optional: Fortran and old
  C++ codebases with big arrays build with `-mcmodel=medium`, and every
  such object has large sections (§2); refusing them refuses the
  option's purpose. Requests R-15 (layout.md) and R-16 (resolve.md)
  carry the placement and `LCOMMON` into those specs (implemented by
  WP-084, `spec/landed/x64/WP-084.md`).
- **X-54 [M1] Large sections go after every small section.** The four
  large output sections are placed after the last non-large alloc
  section (after `.bss` and the small commons), in the order `.lrodata`
  (its own R `PT_LOAD`), `.ltext` (its own RX `PT_LOAD`), then `.ldata`
  followed by `.lbss` (one RW `PT_LOAD`, `.lbss` its `NOBITS` tail); an
  empty one is omitted (a `.lbss` with no `.ldata` ends the small RW
  segment, layout L-36a). No small section's address depends on the
  large sections' sizes; the large sections add up to three program
  headers, which move the small sections after the header table by
  their size, as in the three references (WP-084:
  `x64_small_sections_do_not_move_with_the_large`). So the distance
  between any two small sections does not depend on how big the large
  data is. Measured placements in a static link (E13 `e13/lg.c` compiled without `-fcommon`
  with `.lbss`, `.lrodata`, `.ldata` of 1 MiB each; `e13/lt.c` for
  `.ltext`):

  | linker | order | segments |
  |---|---|---|
  | GNU ld 2.44 | `.text`, `.ltext`, `.rodata` … `.data`, `.bss`, `.lbss`, `.lrodata`, `.ldata` | `.lbss` at the end of the RW segment's memsz; `.lrodata` R and `.ldata` RW `PT_LOAD`s of their own |
  | lld 22 | `.ltext`, `.lrodata`, `.rodata`, `.text`, … `.data`, `.bss`, `.ldata`, `.lbss` | `.lrodata` in the first R segment; `.ldata`+`.lbss` an RW `PT_LOAD` of their own |
  | mold 2.37.1 | `.lrodata`, `.rodata`, `.ltext`, `.text`, … `.data`, `.ldata`, `.bss`, `.lbss` | `.ldata` and `.lbss` inside the RW segment |

  All three run the 1 MiB program and a 3 GiB `.lbss` (`hb2.c`, non-PIC
  medium model), because all put `.lbss` after `.bss`. The other
  placements move small sections by the size of a large one: lld's and
  mold's `.lrodata` before `.rodata`/`.text` puts the small code above
  `image_base + size(.lrodata)`, so a `.lrodata` over 2 GiB breaks
  non-PIC medium-model code's `32`/`32S` absolute references; mold's
  `.ldata` between `.data` and `.bss` separates them by its size, so an
  `.ldata` over 2 GiB breaks `PC32` from `.text` to `.bss`; GNU's
  `.ltext` before `.rodata` does the same to `.rodata`. These failures
  were derived from the measured order and then run (WP-084, a 2.1 GiB
  `.lrodata` or `.ldata` from `.skip` in a scratch object deleted after
  use, static, non-PIC medium model): with the `.lrodata`, GNU ld's
  program runs, lld and mold refuse the link (`R_X86_64_32S` out of
  range against `.tm_clone_table` from `crtbeginT.o`; mold also
  `PLT32`); with the `.ldata`, GNU ld's and lld's programs run and mold
  refuses the link the same way. mortar's placement is X-54's and runs
  the 3 GiB `.lbss` (section and `LCOMMON`).
- **X-55 [M1] `SHN_X86_64_LCOMMON` is a large common.** A symbol with
  `st_shndx = SHN_X86_64_LCOMMON` (0xff02) is a common symbol (`st_value`
  its alignment, `st_size` its size) resolved as `SHN_COMMON` is
  (`spec/resolve.md`) and allocated in `.lbss` by the common rules of
  `spec/layout.md` (§12.2 there, L-88). When a `COMMON` and an `LCOMMON` of
  one name meet, the result is a small common, allocated in `.bss` with
  the common rules' size and alignment (the largest of the mentions),
  whatever the order and whichever is bigger; only a symbol all of whose
  common mentions are `LCOMMON` goes to `.lbss` (Q14, measured: GNU ld
  2.44 with `.comm x,8,8` and `.largecomm x,64,32` in either order gives
  a 64-byte, 32-aligned `x` in `.bss`, and two `.largecomm`s give `x` in
  `.lbss`). Small is also the only safe answer: small-model code reaches
  `.bss`, and large-model code reaches any address. Measured (E13 `e13/lg.c` with `-fcommon`, `lc` in `LARGE_COM`):
  GNU ld allocates `lc` in `.lbss` and the program prints the right
  values; lld 19 and 22 make `lc` an absolute symbol equal to its
  alignment (0x20) and the program segfaults (§14.2 W9); mold 2.37.1
  refuses the link ("lc refers to a discarded COMDAT section probably
  due to an ODR violation").
- **X-53 [M1] Non-alloc relocations and tombstones.** Non-alloc places
  follow arch.md §4.3; the allowed types are `NONE`, `64`, `32`, `32S`,
  `16`, `8`, `PC64`, `PC32`, `PC16`, `PC8`, `DTPOFF64`, `DTPOFF32`,
  `SIZE32`, `SIZE64` and `GOTOFF64`, with these two additions to
  arch.md §4.3's list (request R-13):
  - `64` (and `32`) against an `STT_TLS` target writes
    `DtpRel(S + A)`, not an address. GCC 14's `-gsplit-dwarf` puts the
    `.debug_addr` entry of every `DW_OP_form_tls_address` location
    there as `R_X86_64_64` against the TLS symbol (Clang writes
    `DTPOFF64`, which X-46 already gives the same value). lld 22 writes
    `DtpRel`; GNU ld and mold write the symbol's template address, and
    gdb 16.3 then reports the variable "at offset 0x49ee20 in the
    thread-local storage" instead of 0x0 (E13 `e13/sd.c`: `tv` at block
    offset 0, `pad` at 0x20; lld gives 0x0 and 0x20) — wrong debug
    information (§14.2 W10). The program itself is unaffected.
    `-gsplit-dwarf` is common in the large C++ codebases mortar targets.
  - `GOTOFF64` (class `GotRel`) writes `S + A − GOT`, a link-time
    constant. GCC 14 `-g -O2 -fPIC -mcmodel=large` emits it in
    `.debug_info` (`.quad .LC0@gotoff` inside a `DW_AT_call_value`
    expression, E13 `e13/t2.cc`); GNU ld and mold link the object and the
    program runs (review finding 3). The GOT base exists because the
    code that the expression describes uses it; the reference raises
    `GOT_BASE` all the same (arch.md §4.3, WP-029r), so that the base
    exists when that code is not live.

  A reference to a dead section gets
  `spec/image.md` I-47's tombstone. Measured (E11, `tomb.c`,
  `--gc-sections`, DWARF 4 and 5): GNU ld, lld and mold write 0 in
  `DW_AT_low_pc` and `.debug_aranges`; `llvm-dwarfdump-22 --verify`
  reports 3 errors for DWARF 4 and none for DWARF 5; lld 22 with I-47's
  all-ones tombstones (`-z dead-reloc-in-nonalloc=…=0xffffffffffffffff`)
  gives 0 errors for both, and gdb 16.3 (`info line live`, `break live`,
  `dead` undefined) and lldb 19 behave identically to the 0 tombstone.

### 14.2 Wrong code in the references

Each was re-run for this draft (E2, E6, E9, E12); the scripts are in
Appendix A.

- **W1 GNU ld truncates `16` and `8`.** `R_X86_64_16` = −32769 is
  accepted and written `ff 7f` (0x7fff); −65536 is written `00 00`;
  −65537 and 65536 are refused. `R_X86_64_8` = −129 is written `7f`;
  the bitfield check allows down to −256 (E12,
  `asm/range-bitfield.s`). lld refuses outside `[−32768, 65535]` and
  `[−128, 255]`.
- **W2 GNU ld accepts `PC16` = +32768 and −32769.** It writes 0x8000
  (read back as −32768) and 0x7fff (read back as +32767). `PC8` is
  checked correctly. lld and mold refuse both (E12,
  `asm/range-pc16.s`, `-Tdata=0x500000`).
- **W3 GNU ld accepts dynamic-only types in an input.** Types 5–8, 16
  and 36–38 in `.data` are written `S + A` with no dynamic relocation
  (E8) — for `DTPMOD64` and `IRELATIVE` that is not the value the type
  means.
- **W4 lld corrupts the 22-byte GD sequence.** lld 19.1.7 and 22.1.8
  write the 16-byte LE form from `P − 4`, which overwrites the end of the
  previous instruction, drops the `%fs` prefix and leaves
  `00 00; 4c 01 f8; ff d0`; the E6 program `gd.c` (GCC `-fPIC
  -mcmodel=large`) segfaults under qemu, static and static-pie (E2, E6).
- **W5 lld's PC-relative reference to `weak0` in static-pie** is the
  link-time value: `lea -0x127b(%rip)` reaches the image base at run
  time, not 0 (E9, `asm/weak.s`).
- **W6 mold's IBT IPLT has no `endbr64`.** With every input IBT|SHSTK
  (`asm/iplt-ibt.s`) or with `-z ibt`, mold 2.37.1 marks the output IBT
  and writes `ff 25 …; cc cc` IPLT entries; an indirect call through the
  IFUNC's canonical address faults under IBT enforcement. GNU ld and lld
  write `endbr64` (E3, E12).
- **W7 mold reuses an existing output file's bytes.** Linking a
  static-pie program to a path that already holds a larger output (E12:
  `tlslayout.c` linked `-static`, then `-static-pie`, to the same path)
  leaves `.rela.dyn`'s two `R_X86_64_NONE` padding records holding the
  old file's bytes; glibc's static-pie self-relocation reads them as
  garbage relocations and the program segfaults. A fresh output is
  correct. This explains the mold static-pie crashes of the first E5/E6
  runs. mortar is immune by construction: it fills a newly created
  temporary file and renames it (`spec/image.md` I-59, I-60), and every
  byte of the image is written (I-1's pure function of the layout).

- **W8 lld and mold trap in `.init` padding.** lld 22 and mold 2.37.1
  fill the gap between `.init` input sections with `int3`; a `.init`
  fragment aligned above crti's end (E13 `e13/f2.s`, `.p2align 4`)
  makes the program die with SIGTRAP at start-up, while GNU ld's NOP
  padding runs. crti's 4-aligned 18 bytes followed by crtn's 1-aligned
  fragment leave no gap, so ordinary programs do not hit it; `f2.s` is
  the regression input.
- **W9 lld makes `SHN_X86_64_LCOMMON` symbols absolute.** lld 19.1.7 and
  22.1.8 give a large common the absolute value of its alignment (`lc` =
  0x20, `A` in `nm`) and allocate nothing; the first store through it
  segfaults (E13 `e13/lg.c`, GCC `-mcmodel=medium -fcommon`). GNU ld
  allocates it in `.lbss`; mold refuses the link with a misleading
  message ("refers to a discarded COMDAT section probably due to an ODR
  violation").
- **W10 GNU ld and mold write template addresses for TLS in
  `.debug_addr`.** For GCC's `-gsplit-dwarf` `R_X86_64_64` against an
  `STT_TLS` symbol (the operand of `DW_OP_form_tls_address`), GNU ld
  writes 0x49ee20/0x49ee40 and mold 0x2a0ab0/0x2a0ad0 (the variables'
  template addresses) where lld writes the block offsets 0 and 0x20; gdb
  16.3 then places `tv` "at offset 0x49ee20 in the thread-local storage"
  (E13 `e13/sd.c`). Wrong debug information, not wrong code.

A divergence mortar does not copy, though the code is correct:

- **D1 `lea` for the relaxed `GOTTPOFF` `add`.** GNU ld and lld rewrite
  `add x@gottpoff(%rip), %reg` to `lea T(%reg), %reg`, which leaves
  RFLAGS as they were; the input set them from the sum. The review's
  `genrelax.py` finds 14 sites (every register but `%rsp`/`%r12`) whose
  flags differ under both linkers. mortar writes `add $T` (X-23).

Not wrong code but worth knowing: GNU ld and mold give a thread-local
`weak0` the meaningless `TpRel(0)` (X-18); GNU ld asserts
(`elf64-x86-64.c:4534`) on `DTPOFF64` in `.text` (E6).

## 15. The differential method (stage 2)

`mortar_x64`'s stage 2 (WP-029's implementation) checks itself against
the references as follows; the verifier's reference mode needs §8.8.

1. Link the E1 corpus and the E6 glibc programs with lld 22
   `--emit-relocs`, with and without `--no-relax` (lld keeps the input
   types in its emitted relocations; GNU ld converts the relaxed GOT
   loads, `GOTPCRELX`/`REX_GOTPCRELX`, to `32`/`32S`/`PC32` — G4's `PC32`
   one byte before `P`, at the `e9`'s displacement — and keeps the input
   type of every relaxed TLS record, so its `--emit-relocs` output is
   read with that mapping: WP-029b, `tests/differential.rs`).
2. Re-apply every record with mortar's `apply` in lld's layout (lld's
   `-Map` gives the placement, `spec/plumb.md` §3.5) and compare the
   bytes. The known differences are listed and nothing else may differ:
   the `GOTTPOFF` `add` (mortar `add $T`, lld `lea`); the 22-byte GD (lld
   W4: mortar must differ); the GOT loads of `abs` and `weak0`
   (identical: both keep the GOT); IFUNC words (identical: 0).
3. For GNU ld, classify the converted types and check each relaxed site
   against §8.8's GNU forms.
4. Link the same inputs with mortar and run every program under
   `qemu-x86_64` (E6's `runprogs.sh`), static and static-pie; compare
   stdout with GNU ld's.
5. Run `mortar_plumb` on every mortar output and on every reference
   output; a reference output it rejects is either a §14.2 entry or a
   verifier bug.
