std::runtime_error; t3 by std::exception with what(); t4 the library catches the host's HostDerived as

all pass with every linker.

library: "terminate called after throwing an instance of 'int'" (and 'libns::LibError', 'HostDerived',
'libns::Derived'), exit 134. On this glibc, libgcc_s finds FDEs only through dl_iterate_phdr and PT_GNU_EH_FRAME.
crtbeginS registers nothing with __register_frame_info (no such symbol in the library's .symtab), so there is no
fallback. PT_GNU_EH_FRAME is therefore required in a C++ shared library, and every reference behaves the same way.

Case 6 under -Bsymbolic is a silent wrong program. The executable gets R_*_COPY for v: on x64 in PIE as well,
because GCC x86-64 PIE code uses copy relocations (d/relocs.txt "R_X86_64_COPY ... v"); on aa only for
-fno-pie code ("R_AARCH64_COPY ... v"). AArch64 PIE code uses R_AARCH64_GLOB_DAT. L, bound to itself, keeps
reading its own v, so the exe's write is lost (L.v->10 after v=99). For f, the non-PIE exe's canonical PLT
address differs from L's own &f.
For the verifier: when the output is a library with preemptible symbols, "every lookup resolves as the linker
assumed" cannot be checked from the library alone. Which definition wins depends on the host (cases 2-5), so
the linker's only assumption is "symbolic relocation, resolved by the loader's scope". The check that can be made
is structural: every reference to a preemptible own symbol must go through a dynamic relocation naming that symbol
(GLOB_DAT/JUMP_SLOT/ABS), and none may be resolved at link time. Under -Bsymbolic(-functions), the bound
references must be exactly the ones the option names. DF_SYMBOLIC cannot be relied on to tell a later executable
link about -Bsymbolic, because mold does not write it.

(1) Disagreements between references
------------------------------------------------------------------------------------------------
No behavioural disagreement. Every program result in parts C, D and E is identical across GNU ld, lld 22, lld 19
and mold on both arches. Static disagreements, none of which changes what a run does:
 a. mold -Bsymbolic writes no DF_SYMBOLIC/DT_SYMBOLIC; GNU ld writes both, lld writes DF_SYMBOLIC
    (d/relocs.txt). The relocations are already bound, so glibc's run is the same (case table D). Only tools and a
    later executable link lose the information.
 b. --as-needed with weak-only references: mold keeps DT_NEEDED libc.so.6; GNU ld and lld drop it (B). Which is
    right: GNU ld and lld, since a weak undefined reference does not make a library needed (the ld manual's
    --as-needed rule). mold's extra entry is harmless here.
 c. GNU ld aarch64 puts STT_SECTION .init/.data in .dynsym; the others do not. They are unused by glibc.
 d. lld 22 sets SHF_AARCH64_PURECODE on .plt; lld 19 does not. elflint 0.192 flags it as an invalid flag.
 e. mold x86-64 .plt is not recognised by BFD's synthetic @plt symbols, so gdb and objdump give no `foo@plt`
    names. mold .rela.plt has no SHF_INFO_LINK.
 f. mold emits __ehdr_start, __executable_start and _TLS_MODULE_BASE_ in every library's .symtab (elflint
    complaints). GNU ld drops STV_HIDDEN on the localised __dso_handle in .symtab.
For mortar's shared-object output, GNU ld's choices in a-c, minus the section dynsyms, are the conservative
ones. GNU ld x64 is the only reference that elflint passes clean.

(2) Wrong outputs found (link without a diagnostic, misbehave)
------------------------------------------------------------------------------------------------
None that is one reference linker's fault. One silent wrong program is common to all four linkers and to mortar
as the executable linker: an executable referencing data that a -Bsymbolic library defines gets a copy
relocation, and the library keeps using its own copy. x64: PIE and non-PIE. aa: -fno-pie only.
Reproduce: part_d.sh case "6 exe writes extern v=99" with L=sym. The program prints "RESULT L.f()->1 L.v->10
exe&f==L&f:1 exe&v==L&v:0" after the exe stored 99. Function-pointer identity also breaks for -fno-pie hosts.
Every linker is silent both when it makes L and when it makes the host (h6k/h6knp). This is a candidate for a
mortar diagnostic when it links an executable: a COPY or canonical PLT against a DF_SYMBOLIC input. Since mold's
-Bsymbolic libraries carry no flag, such a diagnostic cannot cover them.
Also measured, not a linker bug: a C++ library linked with --no-eh-frame-hdr aborts on any throw (C); all
linkers accept the option silently.
